# 任务 20261113-001：收敛隐式缺省空间（handler 层 defaultRoot 移除，MRU 降级为选择器推荐）

> 状态：**已完成（2026-11-13）**（P0/P1/P2 已落地，见 6.5 完成记录；6.4 人工验证项待真机走查，未勾选）

## 一、任务目标需求

### 1.1 背景（痛点）

serve 下存在一条贯穿全后端的「隐式缺省空间」暗线：任一端点只要请求里没带 `?ws=`，就会静默落到「最近使用空间」（MRU）。这不是一个有意的设计，而是历史演进留下的巧合——

- 改造前缺省值是 `process.cwd()`（启动目录）。
- 需求 20261027-004 把缺省值的**来源**从 cwd 换成了 MRU，**但没动「缺省回落」这个机制本身**：`defaultRoot()` 仍被 13 处 handler 直接同步调用。
- 结果是：需求 20261112-008（配置全局化）把 skill 全局化后，`skills.ts` 内 7 处 `ctx.defaultRoot()` 才消失——那是顺带修的。**其余调用点全部还在**。

这条暗线造成三个可观察问题：

1. **行为随「上次去过哪个空间」漂移**：调一次 `/fs/tree` 不带 ws，返回哪个目录取决于用户上一次在哪个空间活动过，既不可预测也无法从请求本身推知。
2. **读写型端点存在误伤面**：`/fs/file`、`/fs/search`、`/fs/fingerprint` 共用 `resolveFsRoot()`，缺 ws 时直接落到 MRU 空间 —— 一个「读文件」请求可能悄悄读到用户没预期的目录。这是安全问题，不只是体验问题。
3. **语义端点暗绑**：`/memory/status`、`POST /memory/dream`、`PUT /memory/dream/schedule` 的 `statusFor(root)` / `runFor(root)` 传入的 root 来自 MRU，**而调度器本身早已是全空间（D4）**——传单个 root 只是因为签名要一个参数，语义上并不成立。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
|---|---|---|
| 缺省空间指针 | `src/api/recent-workspace.ts:37` `defaultRoot() => mruRoot \|\| cwdFallback` | 机制本身可用，但被 13 处调用（9 处 handler + 1 声明 + 3 装配） |
| MRU 推导 | `resolveRecentRoot()`（`recent-workspace.ts:52`，76 行）：扫 `sessions/*/` 取目录树最新 mtime | 能力完好，可原样保留 |
| MRU 写入 | `markWorkspaceUsed()` 3 处（`sessions.ts:99`、`messages.ts:121`、`bootstrap.ts:58`） | 能力完好，可原样保留 |
| cwd 兜底 | `setCwdFallback()` 3 处调用（`bootstrap.ts:47`、`index.ts:28`、定义处） | root 改造后退化为「仅 MRU 降级时不需要」，需单独决策 |
| 冗余分支 | `sessions.ts:124-134`：`isSameWorkspace()` 判定后两个分支体**完全相同**（都是 `resolveWorkspaceRuntime(ctx, target)`） | 纯死代码，直接删 |
| `/fs/dirs` 缺省起点 | `sessions.ts:59` `query.get('path')?.trim() \|\| ctx.defaultRoot()` | 这是**选空间**的浏览器，缺省应有推荐起点而非报错 |
| 全空间 Dreaming | `dream-scheduler.ts:315` `enumerateCandidateRoots()` + `:279` `tick()` 已全空间（`enumerateAllSpaces: true`，`bootstrap.ts:90`） | 已有全空间能力，`POST /memory/dream` 应改走 `tick()` 语义 |
| `statusFor` 签名 | `dream-scheduler.ts:504` `statusFor(root)`：root 只影响 `running` / `lastRunAt` / `lastProcessedDay` 三项，其余是全局配置推导 | 单 root 查询语义不成立，需新增全空间形态 |

### 1.3 任务目标

1. **移除全部 9 处 `ctx.defaultRoot()` handler 调用**，按端点性质分流：读写型报错、语义型改收 `ws`、`/fs/dirs` 给推荐起点。
2. **`/fs/dirs` 缺省起点改为 `MRU \|\| 用户主目录`**：有推荐按推荐预填，无推荐落 `os.homedir()`。盘符 chips 保留作跨盘跳转。
3. **MRU 从「决定缺省空间」降级为「仅 `/fs/dirs` 推荐起点」**：`resolveRecentRoot` / `markWorkspaceUsed` 全量保留，不删。
4. **`POST /memory/dream` 改为全空间整理**，不要求 `ws`。
5. **移除测试中无 `ws` 的 `/fs/*` 用例**：`fs-endpoints.test.ts` 55 处由 `req()` 辅助函数统一注入。
6. **更新 `defaultRoot` 契约声明**（`router.ts:92`）或彻底删除该字段。

### 1.4 设计约束

- `workspaceId()` 公式、`canonicalWorkspacePath()` 语义**不变**。
- `/fs/*` 的「必须是已注册工作空间」白名单校验**不变**。
- CLI 路径**不动**（`--workspace` 已在 20261112-008 明确报错）。
- 零新依赖，只用 `node:os` 的 `homedir()`。
- 中英双语文档同步。

## 二、方案设计

### 2.1 总体思路

```
                    ┌─────────────────────────────────────────┐
                    │  请求进入 handler                        │
                    └────────────────┬────────────────────────┘
                                     │
                     ┌───────────────┴───────────────┐
                     │  该端点「是否已在某空间内」？    │
                     └───────┬───────────────┬───────┘
                             │ 是（读写型）   │ 否（选择型）
                             ▼               ▼
                   ┌──────────────────┐  ┌────────────────────┐
                   │ 缺 ws → 400 报错  │  │ /fs/dirs           │
                   │ (D2)             │  │ 缺 path → MRU ||   │
                   │                  │  │ homedir()     (D3) │
                   └──────────────────┘  └────────────────────┘

   语义型端点（status / dream / dream-history）
   ┌────────────────────────────────────────────────┐
   │ 全空间语义，不接受 ws，也不接受隐式回落  (D4/D5) │
   └────────────────────────────────────────────────┘

   MRU 数据源（保留全部代码）
   ┌────────────────────────────────────────────────┐
   │ resolveRecentRoot() ──► /fs/dirs 推荐起点  (D1) │
   │ markWorkspaceUsed() ──► 仅刷新推荐指针          │
   │ 不再有 defaultRoot() 消费者                     │
   └────────────────────────────────────────────────┘
```

### 2.2 关键设计决策

| 编号 | 决策 | 取舍与被否决项 |
|---|---|---|
| **D1** | **MRU 降级为推荐起点，不删除**：`resolveRecentRoot` / `markWorkspaceUsed` 全量保留，唯一消费者从 `defaultRoot()` 变为 `/fs/dirs` 缺省 `path` | 否决「彻底退役」：`resolveRecentRoot` 76 行 + `markWorkspaceUsed` 3 处是需求 20261027-004 完整做出来的能力，纯删属净损失，且「上次用过哪」对选择器仍有价值。外部佐证：Eclipse Theia 的 `WorkspaceServer` 把 `getMostRecentlyUsedWorkspace()`（推荐）与「隐式默认」明确分离 |
| **D2** | **读写型 `/fs/*` 缺 `ws` 一律 400**：`resolveFsRoot()` 去掉 `defaultRoot()` 回落，改为抛 `ApiHttpError('bad_request')` | 否决「回落用户主目录」：`/fs/file`、`/fs/search`、`/fs/fingerprint` 是「已在空间内读写」的端点，回落到主目录会让「读文件」读到用户没预期的目录——这是误伤面而非体验问题。外部佐证：NVIDIA OpenShell #3048 把「空字符串代表默认空间」列为需重构的反模式 |
| **D3** | **`/fs/dirs` 缺省 `path` = `MRU \|\| homedir()`**：`homedir()` 是真实绝对目录，故 `path` / `parent` / `dirs` / `drives` 四字段语义**完全不变**，前端零改动 | 否决「盘符起点 + `path:null`」：那需要响应结构加分支、前端加判空、面包屑特殊处理。用 `homedir()` 三者全免。`homedir()` 不违反 `user-home.ts` 的纪律（该纪律约束「写用户目录」，此处只读） |
| **D4** | **`POST /memory/dream` 改全空间**：走 `tick()` 同款语义（`enumerateCandidateRoots` + `shouldAttempt` 预判），不要求 `ws` | 否决「强制传 ws」：调度器早已全空间（`enumerateAllSpaces: true`），前端「立即梳理」按钮不带参，强制 ws 会让功能退步到单空间 |
| **D5** | **`statusFor` 改为全空间聚合**：新增 `statusAll()`（或 `statusFor()` 允许 `root` 缺省时走全空间），`/memory/status`、`PUT /memory/dream/schedule` 改用它 | 否决「随便传个 root 占位」：`statusFor(root)` 的 root 只影响 `running`/`lastRunAt`/`lastProcessedDay` 三项，其余全是全局配置推导——这正说明单 root 查询语义不成立。全空间聚合才是真实语义 |
| **D6** | **冗余分支删除**：`sessions.ts:124-134` 的 `isSameWorkspace` 判定整段删除（两分支体相同） | 无取舍，纯死代码。**注意**：删除后 `startup` 变量与 `isSameWorkspace` import 需一并清理（若别处无引用） |
| **D7** | **测试统一注入而非逐例补参**：`fs-endpoints.test.ts` 的 `req()` 辅助函数改为自动追加 `ws`，55 处调用一行不动 | 否决「逐例手工补 55 处」：漏改的用例会因「回归到 400」而**静默变形**（测试仍绿但语义已变），手工改 55 处风险极高。集中改一处可审计 |
| **D8** | **`ctx.defaultRoot` 字段彻底删除**，不保留兼容别名 | 否决「保留但标 deprecated」：保留一个「没人该用」的字段只会诱导后续代码用它，与本次收敛目标矛盾。**但** `resolveDefaultRuntime` 需单独处置（见 3.5） |

#### 补充决策（待确认）

| 编号 | 待确认项 | 推荐 |
|---|---|---|
| **D9** | `cwdFallback` / `setCwdFallback()` 是否一并退场 | **退场**。它唯一用途是 `defaultRoot()` 的兜底值；`defaultRoot` 删除后无消费者，3 处调用点（`bootstrap.ts:47`、`index.ts:28`、定义处）可全删。但 `resolveRecentRoot` 内部也用 `cwdFallbackValue()` 做「无任何会话时的回退」——需改为回退 `homedir()` |
| **D10** | `resolveDefaultRuntime()` 是否一并退场 | **保留**，但改语义。`status.ts:27` 需要「会话计数」和 `sessions.ts:139-140` 需要「创建会话的 store」。前者改全空间聚合，后者**必须要求显式 `workspacePath`**（新建会话本来就必选空间）。若两者都改完则该方法无消费者，可删 |

### 2.3 联网检索结论

| 来源 | 结论 | 采纳 |
|---|---|---|
| Eclipse Theia `WorkspaceServer` | `getMostRecentlyUsedWorkspace()`（推荐上次）与「隐式默认空间」是两个独立 API，MRU 只作 UI 推荐 | 支撑 D1 |

## 三、任务详细设计

### 3.1 `src/api/handlers/fs.ts`（D2）

```ts
// 改造前（:191-200）
async function resolveFsRoot(ctx: HandlerContext, query: URLSearchParams): Promise<string> {
  const ws = query.get('ws')?.trim();
  if (!ws) return ctx.defaultRoot();          // ← 删
  ...
}

// 改造后
async function resolveFsRoot(ctx: HandlerContext, query: URLSearchParams): Promise<string> {
  const ws = query.get('ws')?.trim();
  if (!ws) {
    throw new ApiHttpError('bad_request', '缺少 ws 参数：/fs 端点须显式指定工作空间');
  }
  ...
}
```

影响端点（均共用此函数）：`/fs/tree`、`/fs/file`、`/fs/search`、`/fs/fingerprint`。

### 3.2 `src/api/handlers/sessions.ts`（D3 + D6）

**`/fs/dirs`（:56-84）**

```ts
import { homedir } from 'node:os';
import { currentWorkspaceRoot } from '../recent-workspace.js';

// :59
const explicit = query.get('path')?.trim();
// 缺省起点：MRU 推荐 || 用户主目录（D3）
const target = lexicalWorkspacePath(explicit || currentWorkspaceRoot() || homedir());
```

响应结构零改动（`path` / `parent` / `dirs` / `drives` 语义不变）。

**冗余分支（:120-135）**

```ts
// 改造前：两分支体完全相同，判定只为注释服务
let rt: WorkspaceRuntime | null = null;
if (requested) {
  const target = await canonicalWorkspacePath(requested);
  const startup = await canonicalWorkspacePath(ctx.defaultRoot());
  if (!isSameWorkspace(target, startup)) {
    if (ctx.registry) await ctx.registry.ensureRoot(target);
    else await ensureDirUsable(target);
    rt = await resolveWorkspaceRuntime(ctx, target);
  } else {
    rt = await resolveWorkspaceRuntime(ctx, target);
  }
}

// 改造后：直接一行（ensureRoot 已在 resolveWorkspaceRuntime 内部 :96 完成）
let rt: WorkspaceRuntime | null = null;
if (requested) {
  rt = await resolveWorkspaceRuntime(ctx, await canonicalWorkspacePath(requested));
}
```

> **风险提示**：改造前 `!isSameWorkspace` 分支里有一句 `ensureDirUsable(target)`（无 registry 时）或 `registry.ensureRoot(target)`。`resolveWorkspaceRuntime` 内部已有 `await registry.ensureRoot(target)`（:96），但**无 registry 时它会抛 internal**。需确认是否有「无 registry + 显式 workspacePath」的调用场景（大概率无，因为创建会话的前提是有 registry）。

**创建会话缺省空间（:137-140）** 需改：不再允许「未指定 → 缺省空间」，改为**必填**（与前端「新建会话工作空间必选」一致）。

### 3.3 `src/api/handlers/terminal.ts`（:37）

// 改造前

### 3.6 错误码约定

**与原方案的偏差**

① **`POST /sessions` 缺 `workspacePath` 不报 400，改落「进程启动空间」**（原 3.2/3.6/6.2 写的是必填报 400）。原因：`POST /sessions` 有两个调用面——前端新建弹窗（始终显式传 `workspacePath`）与「首次发送消息自动建会话」（`ChatView` 不传参）。后者若改 400，会让「直接开口说话」这条最常用路径直接失败。落启动空间是进程级常量，可预测、不随 MRU 漂移，已满足本需求「去隐式漂移」的核心目标；语义上比 400 更合理，故保留并回填文档（zh:313 / en:314、`api-docs.ts:63`）。

② **`/fs/dirs` 的 MRU 源用 `currentWorkspaceRoot()` 而非重新 `resolveRecentRoot()`**。`currentWorkspaceRoot()` 是进程内同步读取的 MRU 指针，冷启动时已由 `bootstrap.ts:52` 用 `resolveRecentRoot()` 填好，故二者等价且无需 async——响应仍同步可返回。

③ **`resolveDefaultRuntime` 保留**（D10 允许两种结论）。`status.ts` 已改全空间聚合、`sessions.ts` 仍需「进程启动空间」的 store，故消费者的确还在，按 D10「保留但改语义」落地。

**后续增补（2026-11-13，用户复核后决定）**

用户在复核时明确指出：「发消息的前提是已新建会话，新建会话的前提是选定工作空间，所以发消息必然发生在某个空间的会话内，不必考虑无会话的情形」。据此把 `POST /sessions` 与 `GET /sessions` 的严格度**一并收紧**，取消所有隐式缺省空间兜底：

| 项目 | 变更前 | 变更后 |
|---|---|---|
| `POST /sessions` 缺 `workspacePath` | 400（D6 已落地） | 不变（400，且明确不落任何空间） |
| `GET /sessions` 缺 `ws` | 回落到进程启动空间 | **400 `bad_request`**（`sessions.ts:179-196`） |
| `GET /sessions` 无 registry（嵌入形态） | 直接用 `deps.sessionStore` | 仍须显式 `ws`，且须与唯一空间一致，否则 404（复用 `resolveEmbeddedRuntime`） |
| 跨空间全貌 | — | `GET /workspaces`（唯一入口，语义清晰） |

## 一、背景（痛点）

后台命令任务（`commandRun({background:true})`）完成时，通知进入进程内队列，等下一次 `runMessageTurn` 在首轮 LLM 调用前 `drainBackgroundNotices` 注入。这条链路有两个盲区：

1. **WebUI / `--serve` 没有输入循环**：会话空闲期间任务完成，没有任何事件驱动下一轮 run，通知只能躺在队列里。用户不主动发消息就永远看不到「任务早就跑完了」。
2. **CLI 侧的 20261107-010 P3 只解决了一半**：`/`REPL 有 readline 空闲 drain，但仅在有输入提示符时生效；服务模式完全没有等价物。

后台子任务（`delegate background`）在 20261107-006 已经有「情况2 唤醒」——会话空闲时由 API 层以合成输入发起一轮 wake run 主动消费通知。本任务把同一语义补到后台命令任务上。

## 二、方案与决策点

| # | 决策 | 结论与理由 |
|---|---|---|
| D1 | 唤醒触发点 | 通知**入队成功后**直接请求唤醒（`enqueueFromTask` → `requestWake`），而不是另起定时轮询。入队是唯一的新增通知来源，就地触发最省状态 |
| D2 | 无归属任务不唤醒 | `sessionId=''`（无归属桶）没有可定位的目标会话，维持纯被动注入 |
| D3 | 配置开关 | 新增 `tools.backgroundNotify.wakeIdle`（默认 `true`）。CLI 不注册监听器即维持既有被动注入行为，无需按模式分支配置 |
| D4 | 监听器形态 | 进程级单监听器 `onBackgroundNoticeWake(listener)`，返回注销函数、重复注册覆盖；`server.ts` start 时挂载、close 时**先注销再关流**（close 之后到达的完成通知不再触发唤醒） |
| D5 | 情况1 / 情况2 二分 | 与子 Agent 唤醒镜像：已有 run 在跑 → 不唤醒（该 run 的下一轮 LLM 前 drain 会注入）；会话空闲 → 发起唤醒 run。判定用 `ctx.runs.isRunning(id)` + `peekBackgroundNotices(id)` 双检（后者防通知已被消费/清空） |
| D6 | 唤醒输入不带日志尾部 | 合成输入只做「敲门」（条数 + taskId 列表 + 处置提示）。详情由该 run 首轮 drain 的 display-only 通知卡片承担（注入 LLM + 落盘展示），避免同一份日志尾部在一次请求里出现两遍 |
| D7 | **不能用 `<background_task_notification>` 包裹** | 该格式会被 `isDisplayOnlyContent` 过滤出 LLM 视图——模型将看不到任何输入。改用 `[后台任务完成通知]` 纯文本前缀 |
| D8 | 唤醒轮模型选择 | 沿用会话落盘的 `modelAlias`，避免后台任务把回答切回全局默认模型；别名读取失败按全局默认继续，不阻塞唤醒 |
| D9 | 失败重试与兜底 | 唤醒 run 抛错时**通知仍在队列**（未 drain 即未消费），有限重试 2 次（500ms 间隔）覆盖互斥窗口；仍失败只记日志，交后续 run 注入 |
| D10 | 收尾兜底 | run 收尾时若队列仍有通知（恰在收尾瞬间入队、没赶上最后一轮注入），收尾后补一次唤醒。**仅正常完成时兜底**：失败/中止路径不兜底，否则会形成「失败 → 唤醒 → 再失败」的循环 |
| D11 | 落盘剥离 | 合成输入以 `BACKGROUND_WAKE_PREFIX` 标记，落盘历史按前缀剥离，前端不出现用户气泡（只有 LLM 看到它） |
| D12 | 测试隔离 | `resetBackgroundNoticesForTest` 一并清空 `wakeListener`，避免跨用例泄漏（监听器是模块级单例） |

新增对外 API：`peekBackgroundNotices(sessionId)`（只看不取，供收尾兜底判断）、`onBackgroundNoticeWake(listener)`、`BACKGROUND_WAKE_PREFIX`、`scheduleBackgroundWake(ctx, id, delayMs?, attempt?)`。

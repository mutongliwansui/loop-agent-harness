# task-20261107-008 · P1 后台子任务全局可感知

> 对应需求编号：**20261107-008**（总方案见 [task-20261107-006](task-20261107-006-后台子任务可感知性与消息重复治理.md) §3.2）
> 来源：实测反馈 —— 后台子任务运行中前台「直接结束」的观感、完全感知不到后台在运行；完成后无通知
> 状态：**已完成（2026-11-07）**
> 优先级：**P1**
> 涉及：`webui/src/chat-stream.ts`、`webui/src/views/ChatView.vue`、`webui/src/components/SubAgentDock.vue`（新增）、`webui/src/components/SubAgentResultCard.vue`、`tests/webui-subagent-awareness.test.ts`（新增）

## 一、问题与根因

后台子任务的生命周期远长于主 run：delegate(background) 立即返回后主 run 很快 done、SSE 断开，此后：

| # | 断点 | 位置 |
| --- | --- | --- |
| B1 | `subagent_event`/`subagent_result` 推送无人接收（SSE 已断） | `sse.ts` / `runs.publish` |
| B2 | 前端轮询仅在「SSE 活跃时收到 `sub_` start 事件」才启动，错过即失联 | `chat-stream.ts` 原 `ensureSubAgentPoll` |
| B3 | resync 防重入（`st.reloading`）静默丢弃，两个任务先后完成时第二次通知可能丢 | `chat-stream.ts` 原 `resync` |
| B5 | 无全局进行中指示：状态只存在于消息流卡片，滚走/切页即不可见 | 前端整体 |

用户感知：提交后前台直接结束，后台在跑不知道、结束也不知道，要等下次发消息或刷新页面才看到结果卡片。

**本质**：同步模式的过程事件挂在主 run 的活跃 SSE 流上；后台模式主 run 早已结束，**事件通道与挂载点双双失效**，因此治理方向必须是「以轮询快照为数据源」，而不是继续依赖事件流。

## 二、目标

1. 后台任务运行期间，前台**任意时刻**可见「运行中 N」全局指示（不依赖 SSE）。
2. 刷新页面/错过事件后，轮询与指示**自动恢复**。
3. 任务完成后 ≤5s 内出现完成卡片与提示，无需用户发消息触发。

## 三、实施方案

### 3.1 G1 常驻指示器（`SubAgentDock.vue`，新增）

- 挂载在**聊天输入区上方**（`ChatView.vue` 的 `.composer` 内首个元素）：无论消息滚到哪里都在视野内。
- 数据源为 `subAgentTasksOf(sessionId)`（轮询快照），**完全不依赖 SSE**。
- 收起态：`● 后台子任务运行中 N` + 前两条任务摘要与实时耗时；展开态：任务列表（状态胶囊 / taskId / 任务摘要 / 耗时 / 轮次）。
- 仅在存在 running 任务时渲染；全部收敛后自动隐藏（已完成任务在时间线里有结果卡片，不在此常驻）。
- 实时耗时用 1s 本地走表，**仅在存在 running 任务时开表**（空转零开销），组件卸载清理。

### 3.2 G2 轮询启动条件放宽（`chat-stream.ts`）

`ensureSubAgentPoll(id)` 由「只认 SSE start 事件」改为**数据驱动**，且**先建表再立即 tick**（否则 tick 内的收敛停表会被随后建表覆盖）：

1. （保留）SSE 收到 `sub_` 前缀 start 事件；
2. **会话加载完成**：`fetchDetail` 末尾调用 `bootstrapSubAgents(id)` —— 查一次 `/subagents`，有 running 即启动轮询；
3. **历史残留 running 卡片**：加载时若时间线仍有 `status: running` 的 subagent_result 卡片（进程重启前/轮询错过），也启动一次轮询，由 tick 走「收敛 → resync」把卡片刷成真终态；
4. **对齐后补偿**（替代原 G5 的 EventSource onopen）：`reconcile` 成功路径与 `subagent_result` 事件到达时各补查一次。

> **设计修正**：方案原写「EventSource `onopen` 后补偿」，实际前端 SSE 是 **fetch 流**（`sseFetch`/`sseGet`），没有 `onopen` 钩子。补偿点改为「历史加载完成」与「reconcile 对齐成功」——两者都意味着与后端刚完成一次通信，语义等价且更可靠（页面刷新、断线重连、跨标签页接管都覆盖）。

### 3.3 G3 resync 排队补执行

`SessionStreamState.pendingResync?: boolean`：`reloading` 期间的 resync 请求**置标记后 return**，当前重建的 `finally` 末尾检查标记并补执行一次（补执行前清标记，避免无限递归）。解决「两个后台任务先后完成时第二次完成通知被吞」。

### 3.4 G4 完成主动提示

`refreshSubAgents` 内比对前后快照：`running → 终态` 且 `taskId` 未提示过 → `showToast`（含 taskId、状态、耗时、轮次；失败用 error 色）。
- **仅当本端正在看该会话**（`chatViewMounted && activeSessionId === id`）才弹，否则交给未读标记/侧栏，不打扰。
- `notifiedTaskIds` 去重：bootstrap 与轮询并发时同一任务只提示一次。
- 浏览器 Notification 未纳入（需授权且打扰，方案中已定为可选、默认关，本次不做）。

## 四、决策点汇总

| 编号 | 决策 | 被否决项 |
| --- | --- | --- |
| G1 | 常驻指示器 + 轮询，不依赖 SSE | 仅靠消息流卡片：滚走即不可见（本次反馈核心痛点） |
| G2 | 四条件启动轮询（start 事件 / 加载补偿 / 历史 running 卡片 / 对齐后补偿） | 仅 start 事件：错过即失联（已复现） |
| G2b | 补偿点放在「加载完成 / reconcile 成功」，不用 EventSource onopen | 为拿 onopen 改用 EventSource：需重构 SSE 传输层，收益不值 |
| G3 | resync 排队补执行 | 维持丢弃：连续完成通知会丢（已复现） |
| G4 | 仅本端正在看该会话时 toast | 一律 toast：多会话/后台标签页会打扰 |
| — | 轮询间隔维持 2s（与 20261107-002 一致） | SSE 双通道推送后台事件：需服务端常驻连接，复杂度高，收益边际 |

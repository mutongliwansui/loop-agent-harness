## 一、任务目标需求

### 1.1 背景（痛点）

WebUI 现只能通过对话让 Agent 代为执行命令，用户无法在浏览器里直接验证构建、跑测试、看 git 状态。每做一次小验证都要绕一圈 Agent，既慢又费 token；而 Agent 执行的命令还要占用对话上下文。文件预览区已经是「看代码」的地方，看代码与验证代码本应在同一屏完成。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
| --- | --- | --- |
| HTTP 服务与路由 | `src/api/server.ts`（217 行）纯 `node:http` 组装，`handleRequest` 统一「路由 → 鉴权 → handler」；`server.requestTimeout = 0` 已为长连接放开 | 复用，不新建 server |
| 鉴权 | [`http-utils.ts`](../../../../src/api/http-utils.ts#L89) `isAuthorized(req, token)`：token 非空校验 `Authorization` 头，为空仅放行回环 | 复用判定逻辑，但 **WS 握手取不到自定义头**，需换通道 |
| 前端鉴权约束 | [`webui/src/api/sse.ts`](../../../../webui/src/api/sse.ts#L2) 注释已记录「EventSource 无法携带 Authorization 头 → 改 fetch + ReadableStream 手动分帧」 | 同一约束在 WebSocket 上更彻底（连 header 都改不了），须走子协议 |
| 前端实时流 | 全部走 `fetch` + SSE 手动分帧，**无任何 WebSocket 使用**（全仓仅 1 处匹配且是注释） | 需新建 WS 客户端链路 |
| WS 服务端能力 | Node `node:http` 有 `upgrade` 事件但**无内置 WS 帧编解码**（Node 22+ 只有 client 端 `WebSocket`） | 需引 `ws` 或手写 RFC6455 |
| 伪终端 PTY | 全仓无 PTY 相关代码；`child_process` 仅用于短命令执行 | 必须新增原生依赖，属于「零新依赖优先」的合理例外 |
| 文件预览区 | [`FilesView.vue:1338`](../../../../webui/src/views/FilesView.vue#L1338) `.files-viewer` = `flex:1; overflow:auto; padding:14px 18px`，内部单列排布 `.fv-empty` / `.fv-head` + 分支内容 | 需改为 flex column + 内层滚动，才能容纳定高工具条与终端 |
| 配置 | [`schema.ts:121`](../../../../src/config/schema.ts#L121) `ApiConfig{host,port,token,webRoot}`；`server.ts:171` 已有「非回环绑定且无 token 拒绝启动」校验 | 新增 `webui.terminal` 开关，口径复用同一处校验 |
| 组件粒度 | `FilesView.vue` 已 2472 行 | 终端必须是独立组件，禁止继续内联 |

### 1.3 任务目标

在文件预览区内提供可用的交互式终端：可运行 PowerShell 与 cmd 命令，工作目录为当前会话工作空间；以标签页形式与文件预览共存；覆盖未启动 / 运行中 / 执行中 / 已退出 / 断连 / 缺 PTY 六态；默认关闭、强制鉴权、命令可审计。

### 1.4 设计约束

- **零新依赖优先**：前端仅加 `@xterm/xterm` + `@xterm/addon-fit`，后端仅加 `ws` + `@lydell/node-pty`，每个都要在 D 决策中单独说明为何无法用内置模块替代
- **不破坏既有文件预览**：`.files-viewer` 结构改动必须保证 md/mermaid/echarts/pdf/docx/pptx/img 全部预览路径零回归
- **跨平台**：Windows 走 ConPTY；macOS/Linux 走 forkpty（同一套 `@lydell/node-pty` API），shell 探测三平台都要有
- **默认安全**：未显式开启时终端完全不可用，且不得因引入终端放宽既有 API 的鉴权口径

## 二、方案设计

### 2.1 总体思路

```
浏览器                                  Node 服务
┌──────────────────────┐              ┌──────────────────────────────┐
│ FilesView.vue        │              │ server.ts (node:http)        │
│  └ viewer-tabs ──────┼── D6 ──┐     │  └ upgrade ────┐             │
│  └ TerminalPanel.vue │        │     │                │ D1          │
│      ├ xterm 实例    │◄───────┴────►│  terminal/ws.ts (ws 库)      │
│      ├ 工具条/状态条 │  D5 token    │      │ D5 子协议鉴权        │
│      └ 六态覆盖层    │  子协议      │      ├─ 会话表 + 空闲回收 D8 │
└──────────────────────┘              │      └ pty-session.ts        │
                                      │           │ D2 @lydell/node-pty
                                      │           ▼                  │
                                      │      ConPTY → powershell/cmd │
                                      └──────────────────────────────┘
```

数据流：`pty.onData → 合并(16ms) → WS 文本帧 → term.write`；`term.onData → WS → pty.write`。与官方范式一致，额外加了合并与回放缓冲。

### 2.2 关键设计决策

> 以下 D2/D4/D3 结论均来自本机实测（Windows 10.0.26200，Node v24.17.0），脚本见 §7 完成记录。

**D1：WS 服务端引入 `ws`，而非手写 RFC6455。**
理由：`node:http` 无内置 WS 帧编解码；手写需处理掩码、分片、控制帧、关闭握手约 250 行且有边界风险。`ws@8` 纯 JS、零传递依赖、生态标准。**否决**手写（可靠性差）、否决 SSE + POST 双通道（每条按键一次 HTTP 请求，交互延迟不可接受）。

**D2：PTY 用 `@lydell/node-pty`，不用官方 `node-pty`。**
实测官方 `node-pty` 需 node-gyp + Python + VS Build Tools 编译，普通用户装不上。`@lydell/node-pty` 实测 **12 秒装完、仅 2 个包、无任何编译日志**，且 `powershell.exe`/`cmd.exe` 均能正常 spawn 并收到 ANSI 序列。**同时实测主进程可自然退出**（无官方 node-pty issue #887 的 ConoutConnection 未 unref 问题），但仍保留 `process.exit` 兜底。风险：当前只有 beta 版（`1.2.0-beta.18`），故**必须 lazy require + 缺依赖时降级为 `unsupported` 态**，不得让主程序因缺 PTY 而启动失败。

**D3：shell 列表运行时探测，不硬编码「PowerShell 7」为主选项。**
实测本机 `pwsh.exe` **不存在**（`File not found`），只有 `powershell.exe` 与 `cmd.exe`。原型的「PowerShell 7 主按钮」是不可靠假设。改为启动时用 `existsSync` 探测 `pwsh.exe` / `powershell.exe` / `cmd.exe`（非 Windows 探测 `$SHELL`/`bash`/`zsh`），仅列出存在的，至少一个不可用则整个终端报 `unsupported`。

**D4：不强制 `chcp 65001`，不做编码注入。**
实测 cmd 的 `chcp` 为 **936（GBK）**，但 `echo 中文测试 ✓` 回显**完全正确、无乱码**——因为 ConPTY 内部走 UTF-16，Node 侧拿到的已是 UTF-8。设计方案 §2.1③ 的「需 chcp 65001」假设被实测否定。**否决**启动后注入 `chcp`（会污染用户终端输出、且破坏某些依赖 OEM 代码页的国产命令行工具）。

**D5：WS 鉴权的 token 走 `Sec-WebSocket-Protocol` 子协议。**
浏览器 WebSocket 构造函数无法设置任何自定义头，`Authorization` 不可用；query string 会进服务端访问日志与浏览器历史。故用子协议 `loop-agent.token.<token>` 承载，服务端在 `verifyClient` 中拆出并复用 `isAuthorized` 的判定口径（token 为空时仍校验回环来源）。**否决** query 传 token、否决首帧传 token（握手期存在无鉴权窗口）。

**D6：终端作为预览区顶部标签行的一等公民，`.files-viewer` 改 flex column。**
现状 `.files-viewer` 自身 `overflow:auto; padding:14px 18px`，直接塞定高工具条会被 padding 与滚动容器破坏。改为：外层 `.files-viewer` → `display:flex; flex-direction:column; overflow:hidden`，新增 `.viewer-tabs`（定高 37px），原内容整体包进新增的 `.fv-scroll`（承接原 `overflow:auto; padding`）。**否决**另开浮层/侧栏（用户明确要求「在文件预览区域展示终端」）、否决在 `.fv-head` 里加段控（无法承载多终端多开）。

**D7：终端默认关闭（`webui.terminal = false`）。**
终端 = 当前用户权限下的任意命令执行。默认关闭 + 显式开启，开启时若 `api.host` 非回环且无 token 则**拒绝开启终端**（不是拒绝启动服务，避免影响既有纯对话用法）。

**D8：PTY 会话全部集中在服务进程内，配空闲回收与并发上限。**
单用户并发上限 4（超出返回 `too_many`）、空闲 30 分钟回收、WS 关闭不立即杀 PTY（保留 60s 供重连回放），真正回收时 Windows 用 `taskkill /T /F /PID` 清进程树（ConPTY 会带 `conhost.exe` 子进程，`pty.kill()` 不一定连根拔起）。

**D9：输出侧 16ms 合并 + 每会话 256KB 环形回放缓冲。**
未合并时 `npm run build` 这类高频输出会产生上千个小 WS 帧，主线程被渲染拖死。合并窗口 16ms（≈1 帧），单帧上限 64KB。回放缓冲让「断连 → 重连」后先补历史再续流，避免终端内容凭空消失。

**D10：危险命令拦截只在服务端生效，前端确认仅防手滑。**
前端弹确认框可被任何人绕过（直接连 WS 发字节），因此命令审计与可选拒绝名单（`webui.terminalDeny`）必须在服务端。前端确认只降低误触率，不承担安全职责。

**`pty-session.ts`** — 单个 PTY 会话

```ts
export interface PtySessionOptions { shell: ShellInfo; cwd: string; cols: number; rows: number; env?: Record<string,string> }
export class PtySession {
  readonly id: string;
  get pid(): number;
  /** 合并窗口内的数据回调（已做 16ms 合帧） */
  onOutput(cb: (chunk: string) => void): void;
  onExit(cb: (code: number) => void): void;
  write(data: string): void;
  resize(cols: number, rows: number): void;

  replay(): string;

}
/** 工厂：动态 import @lydell/node-pty，缺失时抛 PtyUnavailableError */
export async function createPtySession(o: PtySessionOptions): Promise<PtySession>
```

**`manager.ts`** — 会话表

```ts
export class TerminalManager {
  constructor(cfg: { maxSessions: number; idleMs: number; deny: string[]; auditLog: (e: AuditEntry) => void });
  async open(o: OpenOptions): Promise<PtySession>;  // 超并发抛 TooManySessionsError
  attach(id: string): PtySession | undefined;        // 重连复用（60s 宽限）
  close(id: string, opts?: { kill?: boolean }): void;
  disposeAll(): void;                                // 服务 close 时全量清理
}
```

**`ws.ts`** — WS 路由与协议

```ts
export function attachTerminalWs(server: http.Server, deps: TerminalDeps): void
// 解析 Sec-WebSocket-Protocol: loop-agent.token.<TOKEN>
// origin 白名单校验（默认允许同源 + 回环）
// 消息协议见下表
```

| 方向 | 消息 | 说明 |
| --- | --- | --- |
| C→S | `{t:'in', d:'dir\r'}` | 键盘输入（原样字节） |
| C→S | `{t:'resize', cols, rows}` | 尺寸变化 |
| C→S | `{t:'signal', sig:'INT'}` | Ctrl+C 等（前端直接发 `\x03` 亦可，此消息供按钮用） |
| C→S | `{t:'replay'}` | 主动请求回放 |
| S→C | `{t:'ready', pid, shell, cwd, shells}` | 会话就绪 |
| S→C | `{t:'out', d:'...'}` | 输出 |
| S→C | `{t:'exit', code}` | 进程退出 |
| S→C | `{t:'err', code, message}` | `pty_missing` / `too_many` / `denied` / `spawn_failed` |

**错误与边界**

| 场景 | 处理 |
| --- | --- |
| `@lydell/node-pty` 未安装 | 动态 import 失败 → `err{code:'pty_missing'}` → 前端 `unsupported` 态并给安装命令 |
| 并发超 4 | `err{code:'too_many'}`，不建 PTY |
| `webui.terminal=false` | 握手即 403，前端 `denied` 态 |
| token 错误/缺失 | 握手 401 |
| `Origin` 不在白名单 | 握手 403 |
| shell 一个都探测不到 | 握手 `err{code:'no_shell'}` |
| 命令命中 `terminalDeny` | 服务端回 `err{code:'denied'}` 并审计，**不写入 PTY** |
| PTY spawn 失败 | `err{code:'spawn_failed', message}`，会话不入表 |

**2026-10-25 · Bug 修复：反复开关终端后「假性达上限」**

**现象**：在浏览器里反复「新建终端 → 关掉」，几次之后新建就提示
「并发终端数已达上限 4 个，请先关闭其他终端」，而此时界面上一个终端都没有。

**根因（会话泄漏，前端接线缺陷）**

页签上的 `✕` 走的是 `FilesView.closeTerminal()`，只把页签从 `terminals` 数组里删掉，
随后 `TerminalPanel` 卸载触发 `onBeforeUnmount → client.dispose()`——而 `dispose()`
按设计**只断 WS、不发 `{t:'close'}`**（保留 PTY 供 60s 内重连）。于是：

1. 服务端 `ws.on('close') → manager.detach(sid)`，会话转入 detached，**但仍计入 `entries.size`**
2. `open()` 的判据是 `entries.size >= maxSessions`，detached 一样占名额
3. 回收要等 `detachedFor > 60s` 且 sweep 每 30s 才跑一次 → 实际最坏约 90s
4. 用户几秒内开关 4 次即占满 → 第 5 次报上限

只有 TerminalPanel 内部的关闭按钮走 `doClose() → closeSession()` 才会真正关闭；
而页签 `✕` 是更自然、更常用的路径，恰恰漏了。`dispose()` 的「保留 PTY 供重连」
本意只服务于**网络闪断自动重连**（`client.connect()` 会带 `sid` 复用会话），
不该被「用户主动关标签」复用。

**修复（双层）**

| 层 | 改动 | 作用 |
| --- | --- | --- |
| 前端主修 | `TerminalPanel` 新增 `defineExpose({ shutdown })`（`closeSession()` + 置空 client，幂等）；`FilesView` 用函数式 `ref` 收集实例到 `termPanels` Map，`closeTerminal()` 先 `shutdown()` 再删页签 | 关页签即刻 kill PTY、立即释放名额 |
| 前端补漏 | `TerminalPanel` 监听 `pagehide`：非 bfcache（`persisted=false`）时 `closeSession()` | 刷新/关标签不再留 detached 占位 |
| 服务端兜底 | `open()` 判定前先 `reclaimStaleDetached()`；仍超限则 `evictOldestDetached()` 顶掉最老的 detached | 前端漏发（崩溃/异常）也能自愈；**只动 detached，活跃会话绝不抢** |
| 可观测性 | `manager` 新增 `log` 选项，回收/顶替各打一行；`ws` 断连日志区分「已关闭」与「进入宽限期」 | 下次同类问题一眼定位 |

被顶掉的会话重连时会收到「会话已不存在，将新建终端」并自动新建，不会卡死
（`ws.ts` 原本就有该分支）。

**教训**：「卸载即断开」与「卸载即关闭」是两个语义，前者为断线重连而设计，
后者才是用户意图。父级删除列表项时若只依赖子组件卸载，就会把「保留」当成「关闭」。

# task-20261027-002 · SEA 内嵌原生模块（PTY 真正单文件分发）

> 对应需求编号：**20261027-002**（SEA 内嵌原生模块）
> 前置任务：[task-20261027-001-文件预览区终端.md](./task-20261027-001-文件预览区终端.md)

## 一、任务目标需求

### 1.1 背景（痛点）

终端功能（20261027-001）依赖 `@lydell/node-pty` 原生模块。SEA 的 blob 只能内嵌 JS 与静态 asset，而 `process.dlopen()` 要求 `.node` 落在**真实文件系统**上，因此当前分发单位被迫是「exe + 同级 `node_modules/`」。

后果（已发生过一次线上故障）：用户只拷走 `loop-agent.exe`，终端即不可用；且旧提示文案让人去 exe 目录执行 `npm i`（该目录没有 npm 工程），把用户带进死胡同。上次只修了文案（bug②），**分发形态没有改变**。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
| --- | --- | --- |
| SEA 读取内嵌资源 | [`static.ts:135`](../../../../src/api/static.ts#L135) `readEmbedded()` 用 `process.getBuiltinModule('node:sea')`，注释已记录「esbuild 打 CJS 会剥掉 `node:` 前缀」 | 复用该写法，抽成共享模块 |
| WebUI 资源内嵌 | [`build-sea.mjs:63`](../../../../scripts/build-sea.mjs#L63) 已把 `webui/dist` 递归灌入 `assets` | 同一机制扩展即可，不新建通道 |
| 原生模块内嵌 | 全仓**没有任何** `.node` 内嵌逻辑；`build-sea.mjs:112` 用 `cpSync` 把包拷到 `dist-sea/node_modules` | 本任务核心改动 |
| 原生模块解析 | [`pty-session.ts:93`](../../../../src/terminal/pty-session.ts#L93) `loadPtyModule()` 三级回退（argv[1] → exe 目录 → execPath+paths），失败缓存 `null` | 追加一级内嵌释放目录 |
| 平台包结构 | `@lydell/node-pty-win32-x64` 含 `lib/*.js`（相对 require）、`prebuilds/win32-x64/conpty.node`、`conpty.pdb`、`conpty/conpty.dll`、`conpty/OpenConsole.exe` | **必须整树内嵌**，不能只嵌 `.node` |
| `getAssetKeys()` | Node **v24.8.0** 才提供；项目 `engines.node >= 20.10` | 不可用，须自建 manifest |
| 失败降级 | `PtyUnavailableError` / `pty_missing` 已贯通前端六态（`ws.ts:238`） | 复用，不新增态 |

### 1.3 任务目标

把 `@lydell/node-pty` 及当前平台的子包**整棵目录树**作为 SEA assets 内嵌进 exe；运行时按内容指纹释放到临时目录后加载，使**单个 exe 自带终端能力**。同时保留「同级 `node_modules/` 优先」的零开销路径作为双保险。释放必须幂等、原子发布、支持多实例并发，并能从半途损坏中自愈。

### 1.4 设计约束

- **零新依赖**：只用 `node:` 内置模块（`node:fs` / `node:path` / `node:os` / `node:crypto` / `node:sea`）
- **不改变终端行为**：PTY 会话、六态、并发上限、审计逻辑零改动，仅换「模块从哪来」
- **失败必须降级**：内嵌释放失败不得让服务起不来，仍走 `pty_missing`，且文案要说清两条路
- **不引入 `process.cwd()` 依赖**：项目有 `tests/no-chdir.test.ts` 红线
- **跨平台**：释放/rename 语义要在 Windows（`EPERM`/`ENOTEMPTY`）与 POSIX 下都正确

## 二、方案设计

### 2.1 总体思路

```
构建期 (build-sea.mjs)                        运行期 (pty-session.ts)
┌──────────────────────────────┐            ┌─────────────────────────────────┐
│ node_modules/@lydell/*       │            │ loadPtyModule()                 │
│   ├ node-pty/**              │            │  1. argv[1] 基准      ─┐        │
│   └ node-pty-win32-x64/**    │            │  2. exe 目录基准       ├ 磁盘优先│
│        ├ lib/*.js            │            │  3. execPath + paths  ─┘        │
│        ├ prebuilds/**.node   │            │  4. ensureEmbeddedPty()  ← D6   │
│        └ conpty/*.dll,.exe   │            │        │ D1 内嵌释放             │
│ 剔除 .pdb / .map      ← D7   │            │        ▼                        │
│        │                     │            │  %TEMP%/loop-agent-pty-<id>/    │
│        ▼  assets['node_modules/@lydell/…'] │        node_modules/@lydell/…    │
│  + assets['pty-manifest.json'] ← D2        │        .ready        ← D5       │
│        │                     │            │        │ D3 指纹目录 / D4 原子发布│
│        ▼ postject 注入 blob   │            │        ▼                        │
│   loop-agent.exe (单文件)     │            │  createRequire(释放目录)(PTY_PKG)│
└──────────────────────────────┘            └─────────────────────────────────┘
```

数据流：`sea.getAsset(key)` → `writeFileSync` 到临时目录 → `renameSync` 原子发布 → `createRequire(dir)` → `require('@lydell/node-pty')` → `spawn()`。

### 2.2 关键设计决策

> 以下结论均来自**本机实测原型**（Windows 10.0.26200，Node v24.17.0）：独立构建 SEA 原型，内嵌 24 文件 1.59MB，`conpty.node` 字节哈希一致，真实 `spawn('powershell.exe')` 收到 `SEA_PTY_OK`，二次释放与双实例并发均通过。

**D1：路线采用官方推荐的「assets 内嵌 + 写临时文件 + dlopen」，而非「直接打进 exe 内存」。**
Node 官方文档明确指出：*"Native addons (`.node` files) cannot be loaded directly from the VFS because `process.dlopen()` requires files on the real file system. To use native addons in a SEA, write the asset to a temporary file first."* 并给出同名示例（`getRawAsset` + `fs.writeFileSync` + `process.dlopen`）。原型实测通过，故这不是权宜之计而是唯一正解。**否决**「要求用户附带 `node_modules/`」（正是本任务要消灭的痛点）、否决「改用纯 JS PTY 实现」（无法提供真实 ConPTY 能力）。

**D2：自建 `pty-manifest.json` 清单，不用 `getAssetKeys()`。**
`getAssetKeys()` 自 **v24.8.0** 才有，项目 `engines.node >= 20.10`，在 Node 20/22 上调用即崩。故构建时把文件相对路径列表写入 `pty-manifest.json` 一并内嵌，运行时读它枚举。附带记录 `id`（内容指纹）与 `pkgDirs`，便于排查。**否决**「构建时把清单内联进 JS 字符串」（会让 manifest 与 assets 脱钩、无法独立校验）。

**D3：释放目录用内容指纹命名：`<tmpdir>/loop-agent-pty-<id>`，`id` = 文件清单+大小+内容哈希的前 12 位。**
好处：① 天然幂等——同版本重复启动命中同一目录，秒开；② 多版本并存——升级 exe 后新旧目录互不干扰，不会在旧实例运行中删掉它的模块；③ 便于排查——目录名即可定位是哪个构建。**否决**固定目录名 `<tmpdir>/loop-agent-pty`（多版本/多实例必互删，原型已识别该竞态）、否决 `os.tmpdir()+pid`（每个进程留一份 1.59MB，永不回收）。

**D4：原子发布：先写 `<目标>.tmp-<pid>-<rand>/`，完成后 `renameSync` 到最终目录；rename 失败且目标已存在则判定他人已完成并直接复用。**
避免「A 边写 B 边读」的半成品目录。Windows 上 `rename` 到已存在目录会抛 `EPERM`/`ENOTEMPTY`/`EEXIST`，故 catch 后**检查目标可用性**再决定复用还是报错，不能无脑重试。**否决**「先 `rm -rf` 再写」（多实例并发下 A 正在删 B 正在写，必炸；原型阶段已识别此风险）。

**D5：完成标记 `.ready` + 关键文件存在性校验，实现损坏自愈。**
`%TEMP%` 可能被清理工具、磁盘清理或用户在实例运行中删掉一半，留下「目录存在但文件缺失」的僵尸态；此时若因目录存在就直接复用，会永久性坏掉（且每次启动都坏）。故：① 选目录前校验 `.ready` 存在**且** `prebuilds/<platform-arch>/conpty.node` 存在；② 不满足则丢弃重建（重建前 `rmSync` 带 `force`，失败也不抛）。**否决**仅凭目录存在判断（原型已暴露问题）、否决每次启动都校验全部文件哈希（1.59MB 每次启动算哈希，得不偿失）。

**D6：解析优先级保持「磁盘优先，内嵌兜底」。**
`loadPtyModule()` 现有三级回退不动，在第 4 级追加内嵌释放。理由：本地开发与「exe + `node_modules/`」老部署形态继续走零开销路径，不因引入内嵌而多一次释放；只有真正单文件分发时才付出释放成本。**否决**「内嵌优先」（每次启动都要校验/释放，且会掩盖开发环境装漏依赖的问题）。

**D7：构建时剔除 `.pdb` 与 `.map`。**
实测平台包含 `.pdb` 调试符号，占绝大部分体积：未剔除 11.71MB，剔除后 **24 文件仅 1.59MB**。`.pdb` 仅调试用，`.map` 对运行无意义。exe 体积从 104MB 增至约 105.6MB，可忽略。**否决**「全量内嵌」（白增 10MB）。

**D8：释放失败必须降级为 `pty_missing`，并向用户暴露真实原因。**
`ensureEmbeddedPty()` 内部所有异常都收敛为 `null` + 记录失败原因；`ptyUnavailableHint()` 文案改为三段式：已查找路径 → 单文件 exe（内嵌缺失原因）→ 开发环境（`npm i`）。**否决**「抛异常让服务起不来」（违反 20261027-001 的降级约束）。

**D9：不在正常路径主动 GC 其他版本目录。**
多实例并发下主动删旧目录可能删掉正在运行实例的模块（Windows 上还会因文件占用报错）。仅清理**本次自身失败产生的 `.tmp-*` 残留**，且限制为「同前缀 + mtime 超过 1 小时 + 删除失败忽略」。其他版本目录留给系统临时目录清理策略处理，作为演进项。**否决**「启动时清空全部旧版本」（会互删）。

**D10：内嵌目录释放到 `os.tmpdir()`，不释放到 exe 同级。**
释放到 exe 同级会让「只读安装目录」（如 `C:\Program Files`）场景失败；`%TEMP%` 一定可写。代价是 exe 与临时目录分处不同盘符时首次启动多一次 1.59MB 拷贝（实测在几十毫秒量级）。**否决**「exe 同级释放」（只读目录不可写）、否决「释放到工作空间」（会污染用户项目、进版本控制）。

**D11：判据升级为「逐文件尺寸校验」，并补「原地补缺 + 备用目录」两条自愈路径（实测后修订 D5）。**
端到端复验时暴露出一个 D5 没覆盖的**死局**：另一个实例正跑着并把 `conpty.node` 映射进地址空间时，Windows 上整个释放目录 **既删不掉**（`rmSync` → `EPERM`）**也覆盖不了那个 `.node`**，于是 D4 的「rm + rename」必然失败、D5 直接判不可用——**重启也修不好，终端永久不可用**（实测复现：`B ptyAvailable=False`，`rename ... EPERM`）。三条修订：
- **判据**：`.ready` 之外，逐个校验清单里每个 `.node` 的**字节数**（构建期把 `sizes` 写进 manifest）。仅校验「存在」无法发现「写一半崩了」的截断态，那种目录会一路坏到 `dlopen`。
- **路径①原地补缺**：目录删不掉时不再放弃，只写缺失/被截断的文件，最后才写 `.ready`（中途失败不会留下「标记在、文件缺」的假可用目录）。指纹目录里按定义是同一份字节，缺什么补什么即可，不需要新建目录。
- **路径②备用目录**：连补都补不齐（缺的正好是被锁的那个文件）时，退到 `loop-agent-pty-<id>-b1` / `-b2`。正常情况永远只碰第一个，不产生额外目录。
**否决**「失败就提示用户手动清 `%TEMP%`」（用户不知道是哪个进程占着，且旧文案让人「重启」——重启根本无效）、否决「用 pid 命名目录绕开」（每个进程留 1.59MB，永不回收，D3 已否决过）。

## 三、任务详细设计

### 3.1 `scripts/build-sea.mjs`（构建期）

新增步骤（在现有 WebUI 内嵌之后、生成 blob 之前）：

```js
// 递归收集平台相关的原生包（剔除调试符号）
const NATIVE_PKGS = ['@lydell/node-pty', `@lydell/node-pty-${process.platform}-${process.arch}`];
const NATIVE_SKIP = /\.(pdb|map)$/i;

// assets key 形如 'node_modules/@lydell/node-pty/lib/index.js'
// → 释放后目录结构天然正确，无需再做路径映射
function collectNativeAssets(root, assets) -> { files: [{ path, size, sha256 }], id }
```

- `id` 计算：对 `path + '\0' + size + '\0' + sha256(content)` 逐行累加后取 SHA-256，`slice(0, 12)`
- 额外 asset：`pty-manifest.json` → `{ id, files: [路径...], pkgDirs: [...] }`
- 平台包缺失时**打印警告并跳过**（保持 `dist-sea` 可产出纯后端 exe），行为与现有 `nativeCopied` 警告一致
- 保留现有 `cpSync` 到 `dist-sea/node_modules`（D6 的磁盘优先路径，且便于本地调试）

### 3.2 `src/sea-assets.ts`（新增，共享）

```ts
export function isSeaRuntime(): boolean;
export function readSeaAsset(key: string): Buffer | null;
```

用 `process.getBuiltinModule('node:sea')`（原因见 `static.ts:132` 注释：esbuild 打 CJS 会剥掉 `node:` 前缀）。`src/api/static.ts` 的私有 `readEmbedded()` 改为调用它，行为不变。

### 3.3 `src/terminal/pty-embed.ts`（新增，核心）

```ts
export interface EmbeddedPtyInfo {
  /** 释放根目录（内含 node_modules/） */
  root: string;
  /** 供 createRequire 使用的基准文件路径 */
  anchor: string;
}

/** 是否有可用的内嵌 PTY（SEA 且 manifest 存在）。非 SEA 直接 false，零副作用。 */
export function hasEmbeddedPty(): boolean;

/** 幂等释放并返回可加载目录；不可用/失败返回 null（不抛）。 */
export function ensureEmbeddedPty(): EmbeddedPtyInfo | null;

/** 上一次失败原因（供提示文案展示）。 */
export function lastEmbedFailure(): string | null;

/** 仅单测：复位缓存。 */
export function resetEmbeddedPtyCache(): void;
```

内部流程：

1. 缓存命中直接返回（进程内只做一次，含失败结果）
2. `isSeaRuntime()` 且 `readSeaAsset('pty-manifest.json')` 非空 → 否则 `null`
3. 解析 manifest 得 `id` / `files` / `sizes`
4. 候选目录依次为 `<tmpdir>/loop-agent-pty-<id>`、同名前缀 `-b1`、`-b2`（D11）
5. `isUsable(target)`：`.ready` 存在 **且** 清单里每个 `.node` 字节数与 `sizes` 一致（有 `sizes` 时）
6. 可用 → 返回（不写盘）
7. 不可用 → `rmSync(root)`；**删得掉**则写 `staging = root + '.tmp-' + pid + '-' + rand`，逐文件解包后原子 rename；**删不掉**则走原地补缺（跳过完好文件，最后补 `.ready`）
8. 该候选仍不可用 → 记录原因，换下一个候选目录；全部失败返回 `null` 并汇总各候选路径
9. 发生过重建时清理超过 1 小时的同前缀 `.tmp-*` 残留（忽略错误）


### 3.4 `src/terminal/pty-session.ts`（改）

`loadPtyModule()` 第 4 级：

```ts
// 4) SEA 内嵌释放目录（单文件分发：exe 自带原生模块）
() => {
  const info = ensureEmbeddedPty();
  if (!info) return undefined;
  return createRequire(info.anchor)(PTY_PKG);
},
```

`describePtySearchPaths()` 追加内嵌释放目录描述；
`ptyUnavailableHint()` 改为三段式（D8）。

### 3.5 错误与边界

| 场景 | 行为 |
| --- | --- |
| 非 SEA（源码 / tsx 运行） | `hasEmbeddedPty()` 返回 `false`，零副作用，走原三级回退 |
| SEA 但构建时未装原生包 | manifest 缺失 → `null`，`pty_missing`，文案提示重新打包 |
| 内嵌目录已被清理工具删除 | `isUsable` 失败 → 自动重建 |
| 释放时磁盘满 / 无权限 | 捕获 → `null` + 失败原因，降级 `pty_missing` |
| 多实例同时首次启动 | 各自写 staging，rename 竞争，后到者复用先到者目录（D4） |
| exe 升级后启动 | `id` 变化 → 新目录，旧目录不动（D3） |
| 实例运行中删临时目录 | 已加载的 `.node` 在内存中，不影响本次；下次启动自动重建（D5） |

### 3.6 演进项（本任务不做）

- 旧版本释放目录的主动 GC
- 从 exe 直接 `dlopen` 内存（Node 不支持，需等官方能力）
- 跨平台交叉打包（仍按目标平台构建）
- 内嵌内容的 zstd 预压缩

## 六、任务验收清单

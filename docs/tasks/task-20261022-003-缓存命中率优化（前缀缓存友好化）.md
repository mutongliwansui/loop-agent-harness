## 一、任务目标需求

### 1.1 背景

glm-5.3-flash 日常开发平均缓存命中率仅约 59%（DeepSeek 前缀缓存要求从 token 0 起逐字节一致）。详见设计方案第一、二节（5 个根因）。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
|---|---|---|
| L2 检索结果稳定性 | `ContextAssembler.assemble()` 每轮重检索并注入最后一条 user 消息，同 run 内 content 漂移 | 需 run 级缓存（R1） |
| L3 curated 稳定性 | `buildSystemPrompt()` 每次读盘重拼 | 需 mtime+size+hash 缓存（R2） |
| system prompt 单一来源 | run() 首轮与 assemble 两处构建、参数不一致 | 需统一复用 run() 产物（R3） |
| run 级冻结 | skills 每 run scan 一次（已满足），system/memoryBlock 未冻结 | 显式约定（R4） |
| 效果可观测 | summary 只有整体 avgCacheHitRate | 需拆分首轮/后续口径（R5） |

### 1.3 任务目标

同一会话连续 10+ 轮工具调用：第 2 轮起命中率 ≥80%（主指标），整体均值 ≥70% 或较 59% 基线提升 ≥20 个百分点（辅指标）。

### 1.4 设计约束

- 不改消息序列结构（D1）、不改 L2/L3 存储结构、不改 SSE/会话协议
- 工具层输出截断不做（D7，P2 前不动）
- `ContextAssembler`/`buildSystemPrompt` 既有调用方与单测保持兼容（新增参数全部可选）

`LLMStatsSummary` 新增：`firstIterationHitRate?: number`、`subsequentIterationsHitRate?: number`（第 2 轮起，含缓存字段的轮次按 token 加权；无数据为 undefined）。`onLLMStatsSummary` 渲染行在「平均缓存命中」后追加「(首轮 x% / 后续 y%)」。

### 3.5 边界与错误处理

| 场景 | 行为 |
|---|---|
| 检索超时（首轮） | 返回 []，缓存空串 memoryBlock（冻结空结果，不再翻转） |
| curated 读文件失败 | 该 section 置空串并更新缓存（与现 buildSystemPrompt 的 try/catch 语义一致，context 侧仍兜底） |
| options.systemPrompt 未传 | 回退旧路径，既有单测/调用方不受影响 |
| sessionId 为 null（CLI 无会话） | key 的 sessionId 分量用 null，同 userMessage 连续 run 间仍会因 userMessage 不同而失效 |

### 3.6 演进项（本任务不做）

- commandRun 非后台输出截尾（D7，待 P0/P1 量化验证后决定）
- tools 参数跨 run 稳定性（MCP 连接状态变化场景，风险低）
- 压缩摘要占位的形态优化

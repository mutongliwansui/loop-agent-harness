## 一、实测反馈（2026-11-07 会话 sess_8dcc67b6）

用户在同一次提交（「做全量测试和README比对更新，两个都用子Agent进行」，仅发送一次）后观察到：

| # | 反馈 | 结论 |
| --- | --- | --- |
| 1 | 会话中出现 8 段重复的对话（同一用户消息 + 同一回复反复出现） | **确认**：用户未重复发送；taskId 时间戳证据见下 |
| 2 | 后台子任务运行过程前台看不到（改后台异步之前同步模式能看到过程） | **确认**：同步模式有 SSE 过程流，后台模式链路断裂 |
| 3 | 子 Agent 完成后前台无任何通知，无法感知何时结束 | **确认**：完成落盘/推送链路在主 run 结束后失效 |
| 4 | 会话中存在任务开始前的源码遗留改动（`src/session/store.ts` +30/-2、`tests/session-file-recovery.test.ts`） | 按用户指示**暂不处理**，仅记录 |
| 5 | 后台运行期间前台「直接结束」的观感，运行中/结束均不可感知 | 与 2/3 同根因 |

**关键证据（排除重复执行）**：8 段重复对话中显示的 taskId 为 `sub_a5d365a6_1794053663` / `sub_c88c761b_1794053663`。taskId 格式为 `sub_<hex8>_<秒级时间戳>`，两次提交时间戳**完全一致**（同一秒内）→ delegate 实际只执行了一次、两个子任务各提交一次。重复发生在**消息历史层**，不在执行层。

## 二、根因分析

### 2.1 消息历史重复（反馈 1）

现象：同一对话段（用户消息 + 助手回复 + tool_use/tool_result）在会话历史中重复出现 8 次，且每段重复伴随一段内容略异的「新」助手回复 → LLM 确实被调用了 8 次，每次输入历史都包含重复段，把重复段末尾的用户消息当作新输入重新响应。

排查方向（按嫌疑排序）：

1. **会话恢复/合并逻辑**：`src/session/store.ts` 当前存在未提交改动（+30/-2，新增 `tests/session-file-recovery.test.ts`，主题即「会话文件恢复」）。恢复路径若把磁盘消息与内存消息**追加合并**而非按消息 ID 去重合并，冷启动/重入即重复。
2. **后台通知注入**：后台任务完成时「将状态注入下一轮对话以替代轮询」的实现，若注入时重放/重拼历史而非只追加增量，则每次通知触发一次重复。
3. **前端 reconcile/resync 合并**：全量重拉历史与本地流式状态合并时按引用/顺序追加，可能产生重复段。
4. **SSE 自动重连**：EventSource 重连后服务端重放事件、前端重复 append（本地渲染层重复，不落盘，优先级低）。

治理原则：**消息写入与恢复必须幂等**——以稳定消息 ID 为唯一去重键；注入类写入只追加增量；恢复合并一律按 ID 去重。

### 2.2 后台子任务过程不可见（反馈 2）

当前链路（20261107-002 已实现部分）：

```
提交: onSubAgentStart → upsertSubAgentCard(running) 落盘 + publish('subagent_result')
过程: runSubAgentOnce.emit → options.onSubAgentEvent → publish('subagent_event')
完成: onSubAgentComplete → upsertSubAgentCard(done) + publish('subagent_result')
兜底: 前端收到 sub_ 的 start 事件 → ensureSubAgentPoll（2s 轮询 /subagents）→ 全部收敛 resync
```

断点（对照 `src/agent/react-agent.ts` 788-902、`webui/src/chat-stream.ts` 885-966）：

| # | 断点 | 位置 |
| --- | --- | --- |
| B1 | **主 run done 后 SSE 断开**：后台任务生命周期远长于主 run；delegate(background) 立即返回后主 run 很快 done、SSE 关闭，此后所有 `subagent_event`/`subagent_result` 无人接收 | `sse.ts` / `runs.publish` |
| B2 | **轮询启动条件苛刻**：`ensureSubAgentPoll` 仅在「SSE 活跃时收到 `sub_` 前缀的 start 事件」才启动；错过该事件（SSE 已断/页面刷新）则轮询永不启动 | `chat-stream.ts:914` |
| B3 | **resync 防重入静默丢弃**：`st.reloading` 期间的新 resync 直接 return；两个后台任务先后完成时第二次完成通知可能被丢弃 | `chat-stream.ts:969-972` |
| B4 | **过程事件挂载失败**：`attachSubAgentSeg` 按 callId 在当前流式消息中找 delegate ToolSeg；主 run 结束消息固化后，后续 `subagent_event` 找不到挂载点，过程区不更新 | `chat-stream.ts:465` |
| B5 | **无全局进行中指示**：后台任务状态只存在于消息流卡片中，滚走/切页即不可见；无顶栏/侧栏 badge 或任务面板 | 前端整体 |
| B6 | **trace 仅完成时落盘**：运行中刷新页面，过程区为空（running 卡片有，但 trace 空） | `messages.ts` |

同步模式可见、后台模式不可见的本质：**同步模式的过程事件挂在主 run 的活跃 SSE 流上；后台模式的主 run 早已结束，事件通道与挂载点双双失效**。

### 2.3 完成不可感知（反馈 3/5）

B1+B2+B3 叠加：完成后 `subagent_result` 推送无人接收（B1）、轮询可能未启动（B2）、resync 可能被丢弃（B3）→ 落盘的完成卡片要等用户下次发消息触发 resync/刷新页面才可见。CLI 侧 `drainCliNotices` 仅在下一次输入前打印，用户不输入则永远看不到（D13 设计如此，但缺少主动提示）。

## 三、方案设计

### 3.1 消息幂等（治本，P0）

- **M1 消息 ID 去重**：`SessionMessage` 增加稳定 `msgId`（写入时生成）；`store.ts` 的恢复/合并路径按 `msgId` 去重（保留首现，丢弃后续重复）；`appendMessages`/`updateSession` 写入前对同 ID 消息做原地替换而非追加。
- **M2 注入只追加增量**：后台通知、记忆注入等「下一轮对话注入」机制审计一遍，确保只追加通知本体，不重放历史。
- **M3 重复检测日志**：恢复合并时若发现重复段，`debug.log` 记录来源（磁盘/内存）与数量，便于定位注入源。

### 3.2 后台任务全局可感知（P1）

- **G1 全局任务指示器**：前端常驻组件（顶栏或输入框上方），显示「后台任务运行中 N」badge + 最近任务摘要；数据源为 2s 轮询 `GET /sessions/:id/subagents`，**不依赖 SSE**。点开展开任务列表（taskId、任务摘要、状态、耗时）。
- **G2 轮询启动条件放宽**：满足其一即启动轮询——① 收到 `sub_` start 事件（现有）；② 页面加载/会话切换时历史消息中存在 `status: running` 的 subagent_result 卡片；③ SSE 重连成功后主动查一次 `/subagents`，有 running 则启动。
- **G3 resync 排队**：`reloading` 期间的 resync 请求置 `pendingResync` 标记，当前 resync 完成后补执行一次，不再静默丢弃。
- **G4 完成主动提示**：任务从 running → 终态时，若完成卡片不在视口，弹轻量 toast（「后台子任务 sub_xxx 已完成」+ 点击滚动到卡片）；可选浏览器 Notification（默认关，配置开启）。
- **G5 SSE 重连补偿**：EventSource `onopen` 后触发一次 `/subagents` 查询，恢复轮询与指示器状态。

### 3.3 过程可见性增强（P2）

- **P1 trace 增量落盘**：后台任务运行中每 N 次工具事件（或每 10s）把当前 trace 写入 running 卡片（复用 `upsertSubAgentCard`，`sub` 字段），刷新后过程区可见部分轨迹；完成时最终 trace 覆盖。
- **P2 running 卡片实时性**：轮询响应中带回 `iterations`/`elapsedMs`，前端 running 卡片显示「已运行 Xs · N 轮」，替代静态「任务执行中…」。
- **P3 后台过程事件挂载兜底**：`attachSubAgentSeg` 找不到 ToolSeg 时，将事件累积到会话级 `orphanSubEvents`，resync 重建后按 callId 回填（尽力而为，不保证完整）。

### 3.4 CLI 增强（P3，可选）

- **C1**：`--verbose` 下启用空闲定时 drain（1s 轮询，readline pause/resume 清行打印），非 verbose 保持「下次输入前打印」。

## 四、决策点汇总

| 编号 | 决策 | 被否决项 |
| --- | --- | --- |
| M1 | 以稳定 msgId 为唯一去重键，恢复合并按 ID 去重 | 按内容哈希去重：同内容合法消息（如重发同文）会误伤 |
| G1 | 前端常驻任务指示器 + 轮询，不依赖 SSE | 仅靠卡片：滚走即不可见，正是本次反馈的核心痛点 |
| G2 | 轮询启动三条件（start 事件 / 历史 running 卡片 / SSE 重连补偿） | 仅 start 事件：错过即失联，本次已复现 |
| G3 | resync 排队补执行 | 维持丢弃：连续完成通知会丢，本次已复现 |
| G4 | toast 提示 + 可选系统通知（默认关） | 强制系统通知：打扰且需授权 |
| P1 | trace 增量落盘（节流） | 每事件落盘：写放大 |
| P3 | 孤儿事件累积回填（尽力而为） | 为孤儿事件重建虚拟卡片：复杂度高、易与真实卡片重复 |

### 8.2 与原方案的偏差（实施中发现的真实问题）

**偏差 1：B1 的本质不是「SSE 断开」，而是「数据源选错」。**

原方案把 G1/G2/G5 当作「补偿断线」处理，实施时改为**数据源根本性切换**：前端轮询快照（`/subagents`）成为后台任务状态的唯一权威来源，SSE 事件退化为「触发一次立即刷新」的加速信号。这样刷新页面、错过事件、主 run 结束三种情况用同一条路径解决，不再需要逐场景补丁。

**偏差 2：P0 新增了方案未包含的两项修复。**

- `renameWithRetry`：Windows 上并发 `rename` 覆盖同一文件抛 `EPERM`，**该轮会话数据直接没落盘**。这比「文件撕裂」更直接地解释了消息丢失。
- `withSessionLock`：`updateSession` 是 read-modify-write，并发调用互相覆盖。这条同时解释了「丢失」与「重复追加」两种表现。
- 详见 task-007 §8.2。

**偏差 3：M1 去重键的兼容策略。**

方案只说「按 msgId 去重」，未处理存量数据（无 msgId）。实施时用「下标 + 角色 + tool_call_id + 内容」的确定性哈希补 ID——**同一文件多次读取必须得到同一 ID**，否则去重与恢复链路全部失效；同内容冲突副本追加 `_n` 序号保证唯一。

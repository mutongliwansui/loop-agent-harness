# task-20261107-009 · P2 后台子任务过程可见性增强

> 对应需求编号：**20261107-009**（总方案见 [task-20261107-006](./task-20261107-006-后台子任务可感知性与消息重复治理.md) §3.3）
> 来源：实测反馈 —— 改后台异步之前（同步模式）能看到子 Agent 执行过程，改后看不到了
> 状态：**已完成（2026-11-07）**（P2-c 经论证不实施，见 §4）
> 优先级：**P2**
> 涉及：`src/api/handlers/messages.ts`、`src/agent/subagent-registry.ts`、`src/api/handlers/sessions.ts`（已支持）、`webui/src/chat-stream.ts`、`webui/src/components/SubAgentResultCard.vue`、`tests/subagent-registry.test.ts`

## 一、问题与根因

同步模式的过程事件挂在**主 run 的活跃 SSE 流**上（`subagent_event` → delegate 卡片过程区），所以可见。后台模式主 run 早已结束，除 20261107-008 已覆盖的「通道断」（B1/B2）外，还有三个「挂载/数据」断点：

| # | 断点 | 位置 |
| --- | --- | --- |
| B4 | 过程事件按 callId 在当前流式消息中找 delegate ToolSeg；主 run 结束消息固化后找不到挂载点，过程区不更新 | `chat-stream.ts attachSubAgentSeg` |
| B6 | trace 仅在完成时随结果卡片落盘；运行中刷新页面，running 卡片有但过程区为空 | `messages.ts` |
| B7 | `/subagents` 响应只有状态，无 iterations/elapsedMs（运行中 registry 也不更新这两个字段）；running 卡片只能显示静态「任务执行中…」 | `sessions.ts` + `subagent-registry.ts` |

## 二、目标

1. 后台任务运行中刷新页面 → 过程区可见**部分轨迹**（已发生的迭代/工具调用）。
2. running 卡片显示实时「已运行 Xs · N 轮」，替代静态文案。
3. 主 run 结束后仍产生的过程事件尽力回填，不静默丢失。

## 三、实施方案

### 3.1 P2-a trace 增量落盘（节流）

`messages.ts` 的 `onSubAgentEvent` 内，对**后台子任务**（`callId` 以 `sub_` 前缀开头，即 taskId）把当前 trace 通过 `upsertSubAgentCard` 原地写进 running 卡片的 `sub` 字段。

- **节流间隔 8s**（方案原写「10s 或 5 个工具事件」，实现简化为纯时间间隔：`tool_progress` 事件是高频流，按事件计数需额外状态机，而时间节流已足以把写放大压到「每任务每分钟 ≤8 次全量 messages 重写」）。
- 落盘前 `structuredClone(trace)` 快照：`rewriteMessages` 是异步的，直接传引用会被后续 `applySubAgentEvent` 改写。
- `onSubAgentStart` 登记 `taskId → task` 文本（事件回调只带 callId，拼卡片内容需要描述）。
- 完成时 `onSubAgentComplete` 照旧以最终 trace 覆盖，节流不影响结果正确性。

### 3.2 P2-b 运行期实时字段（`registry.touch`）

- `SubAgentRegistry.touch(taskId, { iterations, elapsedMs })`：**仅对 running 记录生效**（已完成的记录不允许被运行期采样覆盖）。
- `onSubAgentEvent` 中对后台任务调用 `touch`，因此 `GET /sessions/:id/subagents` 在**运行中**就能返回真实 `iterations`/`elapsedMs`（`sessions.ts` 早已透传这两个字段，此前只是运行期没数据）。
- 前端 `SubAgentResultCard.vue`：`live` 从本轮轮询快照按 `taskId` 取，运行中**优先本地 1s 走表**（`now - startedAt`）——接口带回的 `elapsedMs` 只是 2s 采样点，直接用会显得跳变/停滞；轮次取快照值，回落落盘值。
  - 文案：「任务执行中… · 已运行 12s · 3 轮」。
  - 组件内 1s 定时器**仅在拿到 running 快照时开表**，状态变化即停，`onUnmounted` 兜底清理。

### 3.3 P2-c 孤儿过程事件回填 —— 论证后不实施

方案原设想「`attachSubAgentSeg` 找不到挂载点时把事件累积到 `orphanSubEvents`，resync 后回填」。实施前复核发现**实际链路中不产生孤儿事件**：

- B4 的触发前提是「前端收到了 `subagent_event` 但找不到挂载点」。而后台任务在主 run 结束后，SSE 已断开（B1），前端**根本收不到事件**——没有事件就没有孤儿。
- 主 run 仍存活期间收到的事件，其 delegate ToolSeg 就在当前流式消息中，`attachSubAgentSeg` 可正常挂载（现有 20261107-002 逻辑）。
- 刷新页面后的过程区由 **P2-a 增量落盘**（running 卡片的 `sub`）+ **完成落盘**提供，这才是权威来源，回填孤儿事件只是重复劳动且可能与落盘轨迹冲突。

结论：B4 已被「008 的通道治理 + 本任务的增量落盘」覆盖，`orphanSubEvents` 属于为不复现的场景增加复杂度，**不实施**。

## 四、决策点汇总

| 编号 | 决策 | 被否决项 |
| --- | --- | --- |
| P1 | trace 增量落盘，**8s 时间节流** + structuredClone 快照 | 每事件落盘：写放大；仅完成落盘：运行中刷新不可见（本次反馈）；按事件计数节流：需额外状态机，收益边际 |
| P2 | `registry.touch` 让轮询响应在运行中带实时字段 | 前端自行从事件推算：SSE 断了就没数据 |
| P2b | 运行中耗时前端本地走表，不直接信 2s 采样值 | 直接显示接口 elapsedMs：秒数会跳变/停滞 |
| P3 | **不实施**孤儿事件回填（B4 实际不产生孤儿） | 累积回填：为不复现场景增复杂度，且与落盘轨迹冲突 |

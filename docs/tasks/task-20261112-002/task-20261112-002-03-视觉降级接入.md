## 一、任务目标需求

### 1.1 背景（痛点）

`analyzeImage` 目前在 `vision.enabled=false` 时**第一步就抛错**（[`vision/tools.ts L160-L162`](file:///d:/trae_workspace/loop-agent-command/src/tools/vision/tools.ts#L160-L162)），在现场（内网 + 纯文本模型）等于整条看图链路不可用。用户已经习惯「让 Agent 看看这张截图」，突然必须改用另一个工具名，是明显的体验断裂。

本任务让 `analyzeImage` 在视觉不可用时**自动降级**到任务 01/02 的本地 OCR，并在结果首行显式标注「这是 OCR 结果，不是视觉理解」。

### 1.2 现状梳理

| 环节 | 现状 | 关键约束 |
| --- | --- | --- |
| 视觉开关检查 | `runVision()` L160：`vision.enabled` 为假立即抛错 | 开关检查发生在 `resolveImage` **之前**，而降级需要图片字节，必须调整顺序 |
| 图片解析 | [`resolveImage()` L55-L102](file:///d:/trae_workspace/loop-agent-command/src/tools/vision/image.ts#L55-L102)：三种来源，**本地文件转成 data URI**，远程 URL 原样透传 | 降级可直接复用 `img.uri`：data URI 本地 OCR 支持；`http(s)` URL 本地 OCR 明确拒绝 |
| 结果缓存 | `visionCache` key = `model|kind|args|指纹`，命中直接返回 | 若把 OCR 结果写进去，视觉恢复后会命中 OCR 文本，必须隔离 |
| 调用统计 | `visionStats.recordSuccess/recordError/recordCacheHit` | 需增补「降级」计数，否则现场看不出走的是哪条路 |
| OCR 能力 | `runOcrOnSource()` / `buildOcrResultText()` 已就绪（任务 01） | 降级只调用这两个，不碰引擎内部 |

### 1.3 任务目标

1. `vision.enabled=false` 且本地 OCR 可用时，`analyzeImage`（`describe` / `ask`）返回 OCR 结果而非抛错；
2. `chatVision` 抛错时同样降级，并在标注里带上视觉错误摘要；
3. **`extract` 分支不降级**：OCR 给不出字段结构，降级会产出误导性的非法 JSON；
4. 视觉与 OCR 两条路径的缓存互不命中；
5. 两者都不可用时，**同时保留两条错误信息**，让用户知道两个开关各自的状态；
6. 降级结果首行必须写明降级原因与引擎。

### 1.4 设计约束

- 不改变 `vision.enabled=true` 且调用成功时的任何行为（逐字节一致）。
- 不做「先视觉后 OCR」的双跑：降级只在视觉已确定不可用时发生，避免双倍耗时与双份 token。
- 远程 URL 图片不降级（本地 OCR 不抓网），给出「先下载」的可操作提示。
- 降级前先判断引擎可用性，避免每次失败都多付一次 `powershell.exe` 冷启动。

## 二、方案设计

### 2.1 总体思路

```
runVision(rawArgs)
   │  args / kind / params 解析（提前到开关检查之前）
   │
   ├─ vision.enabled === false
   │     └─ runOcrFallback({reason:'视觉功能未启用（vision.enabled=false）'})
   │           ├─ ok        ──► 直接返回降级文本
   │           └─ 非 ok     ──► composeFallbackError(null, out, {visionDisabled:true})
   │
   └─ vision.enabled === true
         ├─ resolveImage() ──失败──► 原样抛出（OCR 也读不到，不降级）
         ├─ 缓存命中 ──► 原路返回
         ├─ chatVision 成功 ──► 原路返回（写缓存）
         └─ chatVision 抛错 ──► recordError()
               ├─ ocr.fallbackFromVision === false ──► 原样抛出
               └─ runOcrFallback({reason: summarizeVisionError(err)})
                     ├─ ok    ──► 返回降级文本
                     └─ 非 ok ──► composeFallbackError(err, out)
```

降级能力收敛在独立模块 [`vision/ocr-fallback.ts`](file:///d:/trae_workspace/loop-agent-command/src/tools/vision/ocr-fallback.ts)：`runOcrFallback()` **永不抛错**，用 `{status:'ok'|'failed'|'unavailable'}` 三态把「能不能降级」与「降级成不成」交给调用方；`tools.ts` 只负责在两条判定路径上调用它，并用 `composeFallbackError()` 拼装双失败文案。

### 2.2 关键设计决策

| 编号 | 决策 | 被否决项与理由 |
| --- | --- | --- |
| **T3-D1** | `extract` 不降级 | 否决「降级后返回纯文本」：模型期待 JSON，拿到一段散文会解析失败或编造字段，比直接报错更危险 |
| **T3-D2** | 降级结果**写入 `visionCache` 但与视觉结果分通道隔离**：`buildKey(..., channel='ocr')` + 固定 `modelKey='local-ocr'` | 否决「完全不写 `visionCache`」：那样重复降级只剩 `ocrCache`（按图片内容哈希、不含 kind/params），`ask` 带不同 `question` 会命中同一段 OCR 文本、丢掉各自的标注头。分通道后既不复用视觉结果，也能按 kind/params 精确命中；`modelKey` 固定为 `local-ocr`，换视觉模型不会让 OCR 缓存失效 |
| **T3-D3** | 判定放在 `runOcrFallback()` 内部统一做，`tools.ts` 不做「先跑再失败」 | 否决「调用方自行预判引擎」：三处判定（extract / `ocr.enabled` / 引擎可用）分散在调用方会漏；集中后单测可直接覆盖三态 |
| **T3-D4** | 视觉错误摘要**取首个非空行并截断 160 字符**（`summarizeVisionError`） | 否决完整 stack：标注行会失控，且模型对堆栈无感；取首行是因为视觉错误的根因通常在首行，后续是堆栈噪声 |
| **T3-D5** | 远程 URL 不降级：由 OCR 引擎层统一拒绝 `http(s)` | 否决「本地下载再 OCR」：SSRF 与不可控耗时，且与 OCR 引擎自身的 http 拒绝策略保持一致（不在视觉层重复实现） |
| **T3-D6** | 双失败时把两条原因都给出（`composeFallbackError`：视觉原因在前、OCR 补充在后） | 否决「只报视觉错误」：用户会误以为修好视觉就行，实际 OCR 也没配好 |
| **T3-D7** | 判定②不做错误码白名单，一律 fail-open，仅由 `ocr.fallbackFromVision` 总开关控制 | 否决「白名单化」（401/429 才降级）：现场失败形态太多（代理拦截、TLS、网关 502、超时），白名单必漏；错误摘要已写进标注，用户能自行判断 |

## 三、任务详细设计

### 3.1 实现落点（`src/tools/vision/ocr-fallback.ts` + `tools.ts`）

降级能力独立成模块，`tools.ts` 只做两处调用：

```ts
// tools.ts —— 判定①：视觉未启用（先把 args/kind/params 解析完，再判定）
if (!vision.enabled) {
  const out = await runOcrFallback({
    kind, imageSource: args.image,
    reason: '视觉功能未启用（vision.enabled=false）',
    ocr: ocrConfig, params,
  });
  if (out.status === 'ok') return out.text;
  throw new Error(composeFallbackError(null, out, { visionDisabled: true }));
}

// tools.ts —— 判定②：chatVision 抛错
} catch (err) {
  visionStats.recordError();
  if (ocrConfig?.fallbackFromVision !== false) {
    const out = await runOcrFallback({ kind, imageSource: args.image,
      reason: summarizeVisionError(err), ocr: ocrConfig, params });
    if (out.status === 'ok') { debug.log('[vision] 视觉失败，已降级为本地 OCR'); return out.text; }
    throw new Error(composeFallbackError(err, out));
  }
  throw err;
}
```

```ts
// ocr-fallback.ts —— 唯一入口，永不抛错
export async function runOcrFallback(input: OcrFallbackInput): Promise<OcrFallbackOutcome> {
  if (input.kind === 'extract')            return { status: 'unavailable', reason: '…可改用 ocrImage…' };
  if (input.ocr?.enabled !== true)         return { status: 'unavailable', reason: '本地 OCR 未启用（ocr.enabled=false）' };
  const cacheKey = visionCache.buildKey('local-ocr', input.kind, input.params ?? [], input.imageSource, 'ocr');
  if (input.ocr.cacheEnabled) { const hit = visionCache.get(cacheKey); if (hit !== null) { visionStats.recordOcrFallback(); return { status: 'ok', text: hit }; } }
  try {
    const result = await runOcrOnSource(input.imageSource, { config: input.ocr });
    const text = buildFallbackText(input, result.engine, buildOcrResultText(result));
    if (input.ocr.cacheEnabled) visionCache.set(cacheKey, text, input.ocr.cacheTtlMs);
    visionStats.recordOcrFallback();
    return { status: 'ok', text };
  } catch (err) { return { status: 'failed', reason: summarizeVisionError(err) }; }
}
```

降级结果的三段式文本（`buildFallbackText`）：

```
[视觉不可用：<reason>；已降级为本地 OCR（<engine>）]
[OCR 引擎: winrt-ocr | 语言: zh-Hans-CN | 耗时: 0.1s]
……OCR 正文……
说明：本地 OCR 只提供图片中的文字，无法回答颜色、布局、图标、数量等视觉类问题。
```

第三行的能力边界说明是硬性的：不提「只提供文字」时，模型会拿 OCR 文本回答「这张图什么颜色」并编造答案。

### 3.2 配置与统计

- `ocr.fallbackFromVision: boolean`（默认 `true`）：判定②的总开关；关闭后 `chatVision` 抛错原样上抛，行为回到实施前。判定①（视觉未启用）由 `ocr.enabled` 决定，不受此开关影响。
- `visionStats` 新增 `ocrFallbacks: number` 与 `recordOcrFallback()`，**不计入 `calls`/成功计数**，避免拉高视觉成功率、掩盖现场问题。
- `tests/vision-cache.test.ts` 的严格 `toEqual` 全字段快照已同步该字段（本次回归发现的唯一真实缺口）。

### 3.3 缓存通道隔离

- `visionCache.buildKey(model, kind, params, imageIdentity, channel: 'vision'|'ocr' = 'vision')` 增加通道维度；
- 视觉路径维持 `channel='vision'`、key 绑定 model + 文件指纹；
- 降级路径用 `channel='ocr'` + 固定 `modelKey='local-ocr'`，因此：① 视觉恢复后不会命中 OCR 文本；② 换视觉模型不让 OCR 缓存失效；③ `ask` 的不同 `question` 参与 key，不会串味。

### 3.4 边界与约束

- `vision.enabled=true` 且成功：输出与本任务实施前**逐字节一致**（成功路径未改动，仅新增 `channel` 默认值）。
- `extract` 在两条失败路径上都只报错、不降级。
- 图片解析失败（不存在/超限/格式不支持）不触发降级：`resolveImage` 在 `try` 之外抛错，直接上抛。
- `http(s)` 图片不降级，由 OCR 引擎层返回可纠正错误，经 `composeFallbackError` 与视觉错误一并呈现。
- 降级结果不写入成功计数。

### 3.5 演进项（本任务不做）

- 视觉与 OCR 结果融合（同一张图两路都跑并交叉校验）。
- 按图片类型自动选路（截图走 OCR、照片走视觉）。
- 降级开关的独立配置项（当前为 `ocr.fallbackFromVision`，已从「跟随 `ocr.enabled`」升级为独立开关）。

## 一、任务目标需求

### 1.1 背景（痛点）

WebUI 的模型页有完整的性能测速：选几个模型、选档位、跑完出 TTFT / TPOT / 解码 TPS / 端到端 TPS / p90，还有 SSE 实时读数与历史趋势。CLI 侧最接近的能力只有 `/model test <别名>`，它回答的是「**通不通、往返多久**」——一个 `elapsedMs` 而已，既不出流式速度，也没法横向比。

于是出现两类无处安放的场景：

1. **想挑模型**：手上有 3 个候选（云端贵但快、本地慢但便宜），想知道同样的中文写作任务谁先出字、谁的字更快，只能开浏览器点 WebUI。
2. **纯终端环境**：远程 SSH 进服务器、CI 里做模型可用性回归，根本没有 WebUI，只能靠 `curl` 手工掐表。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
|---|---|---|
| 测量引擎（发流式请求 + 采时间点 + 汇分位数） | `src/llm/bench.ts` `runBench()`，文件头注释明写「不碰 HTTP、不碰 UI、不碰落盘，因此 CLI / 脚本 / 单测都能直接复用」 | ✅ 已有，**可直接复用** |
| 提示词档位与预设 | `BENCH_PROMPTS`（short/medium/code 三档固定提示词）、`BENCH_TIERS`（quick=1×1、standard=2×3） | ✅ 已有 |
| 分位统计 / 错误分类 | `percentile()` / `summarize()` / `classifyBenchError()`（401/404/429/超时/网络/中断） | ✅ 已有 |
| 历史落盘与查询 | `src/llm/bench-store.ts`：`appendBenchHistory` / `readBenchHistory` / `queryHistory` / `defaultBenchRoot()`（`~/.loop-agent/model-bench/history.json`，每模型留 20 次、只存 host 不存 apiKey、临时文件 + rename 原子写） | ✅ 已有，**CLI 与 WebUI 共用同一份文件** |
| SSE 进度推送 | `src/api/bench-hub.ts` `BenchRun`（事件回放 + 广播） | ❌ WebUI 专用，CLI 不需要（本地同步跑，不需要回放/重连） |

| CLI 运行中中断 | `src/cli/interrupt.ts` `decideSigint()` 六态分派 + `start.ts` 的 `currentRun` AbortController（需求 20261029-001 刚落地） | ⚠️ 已有，但**只覆盖 `agent.run`**；命令执行期间 `abortable === false`，Ctrl+C 会落到 `ignore-busy` |

一句话：**引擎、统计、历史、中断机制全都现成，缺的只是一个 CLI 入口 + 一个终端视图。**

### 1.3 任务目标

新增 `/model bench` 子命令，把 WebUI 的测速能力搬进终端：

```
# 最常用：快速体检当前模型（约 3–10s）
/model bench

# 横向对比两个模型
/model bench deepseek-flash local-qwen

# 标准档（2 档 × 3 轮，约 30–90s）
/model bench deepseek-flash --tier standard

# 全部已登记模型（上限 4）
/model bench --all

# 机器可读（CI / 脚本）
/model bench --json | ConvertFrom-Json

# 历史
/model bench history
/model bench history deepseek-flash
```

| 维度 | 行为 |
|---|---|
| 测什么 | 与 WebUI 完全同一套提示词、同一套口径、同一个 `runBench`，**不另起一套测量逻辑** |
| 看什么 | 结果表：TTFT p50、TPOT、解码 TPS、端到端 TPS、ITL p90、成功率、样本数，多模型并排 + 高亮最优 + 「相比上次」变化 |
| 实时感 | TTY 下原地刷新（轮次进度 / 首 token 时延 / 实时 TPS），非 TTY 降级为逐轮一行 |
| 中断 | 测速中 Ctrl+C = **只停测速**（已完成样本照常汇总与落盘），进程不退出 |
| 数据 | 写入与 WebUI 共享的 `history.json`，两端互见 |

### 1.4 设计约束

- **零新依赖**：只用 `node:readline`/`process.stdout` + 既有 `bench.ts` / `bench-store.ts` / `colors.ts`。
- **单一测量口径**：所有测量参数（`max_tokens`、`temperature:0`、`bustCache`、超时、`rounds`）都走 `runBench` 的既有默认与 D 决策，禁止在 CLI 另写测量代码——否则 CLI 与 WebUI 的数字不可比，测速就失去意义。
- **串行**：多模型严格串行（沿用 API 侧 D3），避免抢带宽把数字测成噪声；引擎的 `concurrency > 1` 能力本任务不暴露。
- **不改 API/WebUI**：`src/api/handlers/bench.ts`、`bench-hub.ts`、`webui/**` 一行不动。
- **GBK 安全**：表框与进度符号一律用 ASCII（`+ - | *`）与已在本项目验证过回显正常的字符，不引入 box-drawing（`┌─│`）与 block 元素——Windows `chcp 936` 下的乱码风险不值得赌。
- **非 TTY 洁净**：管道/CI 下不输出 `\r`、转义序列与颜色，进度改为逐行日志，`--json` 时 stdout 只允许 JSON。

## 二、方案设计

### 2.1 总体思路

```
/model bench [别名…] [--flag…]                      ← model-command.ts 委派
        │
        ▼
parseBenchArgs(args)  ← 纯函数：位置参数=别名，其余 --flag（D8，可单测）
        │
        ▼
resolveTargets()      ← 开跑前整体校验：别名存在 + apiKey 非空（D2）
        │
        ▼
ctx.setAbortable(controller)   ← 把 bench 纳入 Ctrl+C 的 abort 目标（D7）
        │
        ├──▶ for each alias（串行，D3 沿用 API 语义）
        │      runBench({ model: profile, prompts, rounds, maxTokens, bustCache, signal,
        │                 onRoundStart / onFirstToken / onToken / onSample })
        │           │
        │           ├─ TTY：BenchLiveView 原地刷新 3 行（D4）
        │           └─ 非 TTY：每轮一行
        │           ▼
        │      appendBenchHistory(defaultBenchRoot(), entry)  ← 与 WebUI 共享（D6）
        │           │  失败仅告警，不影响结果
        │           ▼
        │      结果表格（D5，相比上次 = queryHistory 取最新一条）
        │
        └──▶ finally: ctx.setAbortable(null)
                │
                ▼
        回到 Agent> 提示符（进程存活，D7）
```

### 2.2 关键设计决策（D1–D12）

**D1｜命令挂在 `/model bench`，不新建顶层 `/bench`。**
测速对象就是登记簿里的模型，`/model` 已聚了 list/use/add/remove/test；再开顶层 `/bench` 会把「模型相关操作」劈成两个入口，Tab 补全也要多记一条。
被否决项：顶层 `/bench`（入口分裂，且参数语义与 `/model` 高度重叠）。

**D2｜无参默认测「当前激活模型」；多模型必须显式列别名，上限 4。**
`/model bench` 单击即得结果（覆盖 80% 场景：刚切了模型想确认它通不通、快不快）；对比场景显式写别名，语义清楚。上限 4 沿用 API 的 `MAX_ALIASES`（再多用户也读不过来，耗时线性增长）。
无参时的解析顺序：`models.active` → 缺失则回落「生效快照 `model.*`」（虚拟别名 `(当前快照)`，不落历史——它不属于登记簿）。
被否决项：无参跑全部已登记模型（一次手误就跑几分钟，且 CLI 是阻塞式）。

**D3｜CLI 默认 `quick` 档；WebUI 默认 `standard` 保持不变。**
CLI 是交互态，`standard`（2 档 × 3 轮 ≈ 30–90s）会把 REPL 钉住太久；`quick`（1 档 × 1 轮）秒级出数，先给结论再决定要不要细看。要严谨对比就显式 `--tier standard`。
`--rounds/--prompts/--max-tokens/--timeout` 可覆盖档位预设，取值区间与 API 的 `intIn` 一致（rounds 1–10、maxTokens 32–1024、timeout 5–180s）。

**D4｜TTY 下用「固定高度块 + 原地重绘」做实时读数，非 TTY 降级逐轮一行。**
WebUI 测速最有价值的体感是「字在实时涌出」，CLI 要复刻就得原地刷新。实现沿用 `spinner.ts` 已验证的模式：`\r` + `\x1b[K`，多行则先 `\x1b[<n>A` 上移再逐行擦除。`enabled` 由 `process.stdout.isTTY` 决定并可注入（便于单测断言输出串）。
被否决项：复用单行 `Spinner`（只能挤一行，轮次 + TTFT + TPS 三个读数挤不下）；每 token 打一行（刷屏且非 TTY 日志爆炸）。

**D5｜结果表格固定七列 + ASCII 表框 + 最优高亮。**
列：`别名 | 型号 | TTFT | TPOT | 解码 TPS | 端到端 TPS | ITL p90 | 成功率 | 样本`。多模型时对每个指标找最优（TTFT/TPOT/ITL 取最小，TPS 取最大），用绿色 + `*` 标记；无颜色环境只留 `*`（颜色不是唯一信息载体）。
表框用 `+ - |`，输出前按显示宽度补空格（中文按 2 计算，用既有 `visualWidth` 思路或本地实现，纯函数可单测）。
被否决项：box-drawing 字符（GBK 乱码风险）；表格改成逐行 key: value（多模型对比时完全读不出来）。

**D6｜CLI 结果写入与 WebUI 共享的 `history.json`。**
`appendBenchHistory(defaultBenchRoot(), entry)`——路径、裁剪（每 alias 20 条）、原子写、不存 apiKey 全部复用。收益：WebUI 模型页的「性能」列能看到 CLI 在服务器上跑的数据，反之 CLI `history` 也能读 WebUI 的。写入失败只打灰色警告（历史是附属能力，不阻断测速结果）。

**D7｜测速中 Ctrl+C = 只中断测速，已完成样本照常汇总与落盘。**
这是本任务唯一需要动 `start.ts` 的地方：现在 `decideSigint` 的 `abortable` 取自 `currentRun !== null`，而命令执行期 `currentRun` 恒为 `null`，Ctrl+C 会落到 `ignore-busy`（提示「当前命令执行中，暂不支持中断」）。方案：`CommandContext` 增加可选字段 `setAbortable(controller | null)`，由 `start.ts` 注入实现（内部就是 `currentRun = controller`）；`bench` 命令进入时注册、`finally` 释放。同时把 `currentRun = null; aborting = false;` 的复位从 `agent.run` 分支的 `finally` 上移到 dispatch 外层 `finally`（幂等，避免命令分支残留 `aborting` 导致后续 Ctrl+C 一直被 `ignore-busy` 吞掉）。
被否决项：bench 自己 `process.on('SIGINT')`（与 readline 已有的 SIGINT 双触发）；bench 期间保持不可中断（违背用户刚建立的「Ctrl+C 只打断手头这件事」的预期）。

**D8｜参数风格：位置参数只放别名，其余一律 `--flag`。**
`/model bench a b --tier standard --rounds 3 --prompts short,medium --max-tokens 256 --all --json --no-bust-cache`。
解析抽成纯函数 `parseBenchArgs(argv)`，返回 `{ aliases, tier, rounds, prompts, maxTokens, timeoutMs, all, json, bustCache, error }`，非法值返回 `error` 字符串由调用方渲染（不 throw），便于单测覆盖全部奇葩输入。
被否决项：位置参数混入档位（`/model bench a standard` 会与别名撞车）。

**D9｜支持 `--json`：stdout 只输出结构化结果，无动画、无色、无提示文案。**
输出 `{ runId, config, aborted, results: [{ alias, model, baseUrlHost, summary }] }`——即 `BenchModelResult[]` 原样，字段与 `GET /models/bench/history` 完全一致，CI 与脚本可直接消费。这是低成本高价值项（`summary` 本身就可序列化）。
被否决项：只做人类可读输出（CI 集成场景缺失）。

**D10｜加 `/model bench history [别名] [--limit N]`。**
`readBenchHistory` + `queryHistory` 现成：无别名时每个模型最近一次（对齐 WebUI 模型页首屏），带别名时该模型的 N 次趋势（TTFT/TPS 逐次一行 + 变化百分比）。成本极低，且让「CLI 测完的历史怎么回看」有答案。

**D11｜中断时已完成样本照常汇总并落盘，表格标题标注「已中断 n/m」。**
测速是采样型任务，半份数据仍有参考价值，直接丢弃太浪费；且与需求 20261029-001 的 D4-B（中断保留半截回答）语义一致——中断只停继续采样，不否定已发生的采样。
被否决项：中断即全部作废（白等几十秒）。

**D12｜不做 warmup 预热轮，quick 档的 TTFT 含首次握手开销，用表脚注说明。**
首次请求要付 DNS + TCP + TLS 建连成本，理论上该预热一轮再测。但 CLI 默认档就是「秒级出数」，加一轮预热等于把默认耗时翻倍，违背 D3 的初衷。折中：脚注写明「quick 档首轮含连接建立开销；要可比请用 `--tier standard`（多轮取 p50）」。
被否决项：默认预热（默认档耗时翻倍）；完全不做说明（用户会把含握手的 TTFT 当成模型真实首字时延）。

**检索要点（设计阶段联网检索的结论与来源）**

| 结论 | 对本方案的影响 | 来源 |
|---|---|---|
| ITL 是否含 TTFT 各家不统一（AIPerf 明确排除 TTFT）；单请求下 `TPOT = (E2EL − TTFT) / (输出 token − 1)` | 坚持沿用引擎既有口径（`spanMs = 末 token − 首 token`），**绝不在 CLI 侧另算一套**，否则与 WebUI 数字不可比 | [NVIDIA NIM Benchmarking Metrics](https://docs.nvidia.com/nim/benchmarking/llm/latest/metrics.html)、[Anyscale Metrics](https://docs.anyscale.com/llm/serving/benchmarking/metrics)、[Modular LLM Inference Metrics](https://handbook.modular.com/llm-inference-basics/llm-inference-metrics) |
| SLO 实践中 ITL 分位应当用**单个 token 间隔**，而非请求平均值（请求平均会掩盖卡顿） | 引擎的 `itlP90Ms` 正是 interval 的 p90，CLI 表格保留该列（不用 TPOT 代替） | [TTFT, TPOT, and SLOs for Streamed LLMs](https://formation.dev/blog/ttft-tpot-streamed-llm-slos) |
| 基准测试通常排除 warmup 阶段（AIPerf 可配置 warmup 并从 TPS 统计中剔除） | 采纳其精神但不加预热轮：quick 档脚注声明，standard 档靠多轮 p50 消化（D12） | [NVIDIA NIM Benchmarking Metrics](https://docs.nvidia.com/nim/benchmarking/llm/latest/metrics.html) |
| 失败/超时请求应计入违约统计，而不是只报成功样本 | 表格必须有「成功率」与失败分类计数（`errorKinds`），不能静默丢样本 | [TTFT, TPOT, and SLOs for Streamed LLMs](https://formation.dev/blog/ttft-tpot-streamed-llm-slos)、[Cerebrium Goodput 指南](https://cerebrium.ai/resources/llm-serving-goodput-latency-slos) |
| 前缀缓存会显著拉低 TTFT（OpenAI/Azure 均有 `cached_tokens` 计量；Azure 说明同前缀每分钟 >15 次请求可能 miss） | 保持引擎默认 `bustCache: true`（每轮 random nonce 破坏缓存），并在 `--no-bust-cache` 时明确提示「本次 TTFT 含缓存命中收益，不可与其它模型直接比」 | [OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching)、[Azure Prompt Caching](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/prompt-caching) |

## 三、任务详细设计

### 3.1 `src/commands/bench-command.ts`（新增，命令主体）

```ts
/** 解析后的测速计划（纯数据，可单测） */
export interface BenchPlan {
  aliases: string[];          // 显式列出的别名（未含 all 展开结果）
  all: boolean;               // --all：跑全部已登记（上限 4）
  history: boolean;           // 走 /model bench history 分支
  json: boolean;
  tier: BenchTier;
  rounds: number;
  prompts: BenchPromptKey[];
  maxTokens: number;
  timeoutMs: number;
  bustCache: boolean;
  limit: number;              // history 用
  /** 参数非法时的人话说明；非空即拒绝执行，由调用方渲染后 return */
  error?: string;
}

export function parseBenchArgs(argv: string[]): BenchPlan;

/** 从登记簿解析出待测目标；未登记/缺 apiKey 时返回 errors（整体拦截，不跑一半） */
export function resolveBenchTargets(
  cfg: AgentConfig,
  plan: BenchPlan,
): { targets: { alias: string; profile: ModelProfile; fromSnapshot: boolean }[]; errors: string[] };

/** 表格渲染纯函数（不含 IO，便于单测） */
export function renderBenchTable(rows: BenchRow[], opts: { tier: string; colors: boolean }): string[];
export function renderHistoryTable(entries: BenchHistoryEntry[], opts: { colors: boolean }): string[];

export function createBenchRunner(deps?: BenchDeps): BenchRunner;
```

依赖注入（与 `model-command.ts` 的 `ModelCommandDeps` 同风格）：`{ runBench?, now?, benchRoot?, appendHistory?, readHistory? }`，默认取真实实现——单测可注入 fake `runBench` 与临时目录，不联网。

### 3.2 `src/ui/bench-view.ts`（新增，终端视图）

```ts
export interface BenchLiveOptions {
  enabled?: boolean;             // 默认 process.stdout.isTTY
  write?: (s: string) => void;   // 默认 process.stdout.write（测试注入）
  colors?: boolean;
}

/** 固定 3 行原地刷新；enabled=false 时退化为逐行日志 */
export class BenchLiveView {
  constructor(opts?: BenchLiveOptions);
  startModel(info: { alias: string; model: string; index: number; total: number }): void;
  onRoundStart(info: { round: number; total: number; promptKey: BenchPromptKey }): void;
  onFirstToken(ms: number): void;
  onToken(outTokens: number, elapsedMs: number): void;
  /** 一轮结束：累计成功/失败，重绘末行 */
  onSample(sample: BenchSample): void;
  finish(): void;   // 擦除动画块，为表格让出位置
}
```

TTY 渲染形态（3 行，数字右对齐）：

```
  [bench 1/2] deepseek-flash  (deepseek-chat)
  轮次 1/1 · 短问答 · 已出 62 tok · 41.8 tok/s
  TTFT 812ms · 样本 1 成功 / 0 失败
```

非 TTY 退化为每轮两行：`[bench] alias r1/1 short -> TTFT 812ms decode 41.8tok/s ok` / 失败时 `-> failed(auth) apiKey 无效或无权限`。

export interface CommandContext {

### 3.5 边界与错误处理

| 场景 | 行为 |
|---|---|
| 别名不存在 | 开跑**前**整体拦截：`✗ 未找到模型「x」。已登记: a、b`，一个请求都不发 |
| profile 缺 apiKey | 同样前置拦截，并提示 `/config set models.profiles.<别名>.apiKey <key>` |
| `--all` 且登记数 > 4 | 只跑前 4（按 alias 排序），明确列出被忽略的别名（不静默截断） |
| `models.active` 缺失（单模型模式） | 回落生效快照 `model.*`，别名显示为 `(当前快照)`，**不写历史**（不在登记簿里，写进去会污染趋势） |
| 单轮超时 / 429 / 401 / 404 / 网络错误 | 该轮记 `errorKind` 失败样本，**继续后续轮**（引擎不重试，重试会污染统计）；表格成功率按全样本算 |
| 全部轮次皆失败 | 表格照常输出（成功率 0% + 失败分类计数 + `dominantError` 人话），退出码不变（CLI 不因测速失败中断会话） |
| 测速中 Ctrl+C | abort → 已完成样本汇总（`aborted: true`）→ 落盘 → 表格标题标 `已中断 n/m` → 回到 `Agent>`，**进程不退出** |
| 历史写入失败 | 灰色警告，结果照常展示 |
| `--json` | stdout 只输出 JSON（进度动画、颜色、提示文案全部关闭）；警告走 stderr |
| `--no-bust-cache` | 额外打印一行黄字提示：本次 TTFT 含前缀缓存收益，跨模型不可比 |
| 非 TTY（管道/CI） | 无 `\r`、无转义序列、无颜色，进度降级逐行 |
| `bench history` 无记录 | `（暂无测速历史；先跑一次 /model bench）` |

### 3.6 演进项（本任务不做）

- **warmup 预热轮**（D12 已声明方案：靠 standard 档多轮 p50 消化）。
- **并发压测**：引擎 `concurrency > 1` 与 `totalTps` 已存在，CLI 暂不暴露（会与「串行防抢带宽」的默认语义冲突，需要单独的提示与文案）。
- **Agent 工具形态**：让模型自己调 bench 做「这个模型快不快」的自问自答（要考虑工具额度与成本，另议）。
- **CSV / 图表输出**：`--json` 已足够被外部工具消费。
- **WebUI 与 CLI 的趋势图统一**：sparkline（`webui/src/bench-format.ts` 的 `sparkPoints`）在终端画 ASCII 曲线，收益一般。

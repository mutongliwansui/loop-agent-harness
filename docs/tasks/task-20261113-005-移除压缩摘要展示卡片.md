## 一、任务目标需求

### 1.1 背景（痛点）

用户反馈：对话触发 L1 上下文压缩后，消息区开头会出现一条可折叠的
「**已压缩历史摘要（模型当前只能看到这段摘要）**」，点开后是压缩总结原文。

用户的判断是：**这是模型上下文内部如何折叠历史的实现细节，正常用户不需要关注**。
它占据了对话流的视觉位置，又是用户无法操作的只读内容，属于噪声。

### 1.2 现状梳理

关键认知：这张卡片**不是一条对话消息**，而是展示用的替身。

| 环节 | 事实 |
| --- | --- |
| 后端 | L1 压缩时向历史插入 `role=user` / `is_show=false` / `kind=summary` 的摘要占位消息，对**模型可见**、对用户本应隐藏 |
| 前端回读 | `rebuildChatMsgs()`（`webui/src/chat-stream.ts`）把该消息捞出来，挂 `summary` 字段 |
| 渲染 | `ChatView.vue` 的 `<details v-else-if="m.summary" class="summary-card">` 渲染为折叠卡 |

该展示当初是为了解决「压缩是静默的，用户不知道模型已经看不到更早的工具输出」
（旧版直接 `continue` 丢弃）。现在用户明确表示不需要这层可见性。

### 1.3 任务目标

**方案 A（用户已选定）：彻底删除**——模板、样式、`summary` 字段、防御性过滤全部清理，
代码不留死代码。同时**保留压缩过程反馈**（用户在确认时明确要求）。

### 1.4 设计约束（改动边界的四条不变量）

去掉展示**只动渲染层**，以下四条必须逐条守住：

1. **模型上下文不受影响**：`is_show` 仅是展示标记，`LLMClient.normalizeMessages()`
   照常把摘要发给模型。
2. **磁盘数据不受影响**：摘要消息本就在磁盘上，删的只是渲染。
3. **重试锚点不受影响**（最关键）：`viewIdx++` 在 `is_show` 判定**之前**执行，
   摘要占位照样消耗一个恢复视图下标（与后端 `entry.history` 对齐）。
   只要该分支保留 `continue` 而不 push，后续消息 `seq` 全部不变。
4. **归档分界线不受影响**：`flush()` 必须保留。摘要是「归档区」与「保留区」的分界，
   归档段的 assistant 必须在此收束成独立气泡。

> 约束 3、4 是本次改动唯一有真实风险的地方——若一并删掉 `viewIdx++` 或 `flush()`，
> 表现为「重试打错轮次」「压缩前后消息串成一坨」，且不会在类型检查与单测里立刻暴露。

## 二、方案设计

### 2.1 总体思路

`is_show===false` 分支从「渲染为摘要卡」改为「有内容则 flush，随后 continue」：

```ts
const historyIdx = archived ? undefined : viewIdx++;   // 不变量 3：先自增
if (m.is_show === false) {
  // 不变量 4：仅当摘要确有内容时才切分（空摘要不产生分界，与旧行为一致）
  if (m.role === 'user' && (m.content ?? '').replace(/^\[历史摘要\]\s*/, '').trim()) flush();
  continue;
}
```

与旧行为的等价性：旧代码在 `summaryText.trim()` 为真时 `flush()` 并 push，
否则直接 `continue`。新代码 flush 条件完全相同，唯一区别是不再 push。

### 2.2 关键设计决策

| 编号 | 决策点 | 结论 | 理由 |
| --- | --- | --- | --- |
| **D1** | 彻底删除 vs 仅停渲染 | **彻底删除**（用户选定 A） | B 方案会留下永不执行的死代码与 5 处迷惑性 `!m.summary` 过滤，误导后来者以为摘要卡还在 |
| **D2** | `viewIdx++` 是否保留 | **保留**，位置不变 | 摘要占位在 `entry.history` 中确实存在，必须占下标；删掉会让后续所有消息 `seq` 前移，重试锚点整体错位 |
| **D3** | `flush()` 是否保留 | **保留**，条件与旧代码等价 | 摘要是归档区/保留区分界线，缺了它压缩前后两段会合并成一个气泡 |
| **D4** | 空摘要如何处理 | **不 flush 直接跳过** | 与旧代码 `if (summaryText.trim())` 严格等价；空摘要本就不产生分界 |
| **D5** | 压缩过程反馈 | **全部保留**（用户明确要求） | 消息末尾「正在压缩对话历史…」loading（`compaction_start`/`compaction` 事件驱动）与手动压缩 toast 均不动 |
| **D6** | 存量会话兼容 | **天然兼容** | 磁盘 `is_show=false` 消息照旧存在，只是不再渲染；无需数据迁移 |
| **D7** | `!m.summary` 防御过滤 | **全部删除** | 三处（重试锚点定位、`keepLocalUserBubbles`、`preserveOptimisticTail`）过滤的都是过去由摘要卡引入的伪 user 消息，现已不存在 |

### 2.3 外部参考结论

主流 Agent 产品的处理方式可作佐证：Claude Code、Cursor 等均在对话流内
**不暴露上下文压缩细节**——压缩被当作后台维护动作，只在状态栏以百分比等抽象
指标体现（本项目对应的是上下文用量百分比环）。摘要内容对用户是只读且不可操作的，
放在对话流里既占位又无法产生行动，移出符合同类产品惯例。

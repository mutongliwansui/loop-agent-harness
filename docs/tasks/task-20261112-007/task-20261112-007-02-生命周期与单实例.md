## 一、任务目标需求

### 1.1 背景（痛点）

任务 01 只能「起得来」，但生命周期是错的：关窗口后子进程可能变孤儿；重复双击会起第二份后端抢同一批会话文件；最关键的是——**Windows 上关窗口会静默丢弃 Dreaming（记忆整理）**。

本条不是理论风险，已实测证伪原设想：

```text
子进程装了 SIGINT handler，父进程 child.kill('SIGINT')
→ child exit code=null signal=SIGINT
→ handler-ran=false          ← handler 根本没执行
→ 结论：Windows 下等于无条件强杀
```

并且 `router.ts` 中**不存在任何关停端点**，Dreaming 序列只挂在信号处理里（`bootstrap.ts:146-162`）。因此**当前没有任何跨平台手段能触发优雅关停**。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
|---|---|---|
| 优雅关停序列 | `onSignal()` 内联实现：停调度器 → `runAllForShutdown(budget)` → `server.close()` → 断 MCP → `exit`（`bootstrap.ts:146-162`） | 逻辑齐全，但是**闭包内的局部函数**，需抽出可复用 |
| 关停 HTTP 入口 | 无。`router.ts` 无 `/shutdown` 类端点 | **需新增**（本任务唯一后端改动） |
| 二次强退 | `shuttingDown` 标志 + 二次信号 `process.exit(0)`（`bootstrap.ts:147-151`） | 保留，扩展为端点重复调用也幂等 |
| CORS / OPTIONS 预检 | **完全没有**（`src/api` 内无 `Access-Control`、无 `OPTIONS` 处理） | 影响端点安全设计（见 D2-3） |
| 鉴权 | `isAuthorized`：有 token 校验 Bearer，无 token 仅放行回环（`http-utils.ts:89-94`） | 回环校验**不足以防 CSRF** |
| 单实例 | 无 | Electron `requestSingleInstanceLock()` 提供 |
| API 文档 | `api-docs.ts` 运行时反射路由表（唯一真源） | 新端点会自动出现，但需补说明文案 |

### 1.3 任务目标

1. 新增 `POST /admin/shutdown`，可安全触发既有优雅关停序列（含 Dreaming）
2. 关窗口 → 触发优雅关停 → 等进程退出 → 应用退出；超时兜底强杀
3. 重复启动只保留一份：二次启动聚焦已有窗口
4. 后端意外退出给用户可读提示，不静默白屏
5. `--serve` + Ctrl+C 的既有行为**完全不变**

### 1.4 设计约束

- 后端改动**只允许**新增关停端点及其必要重构，不得改变既有信号关停语义
- 关停端点必须防「任意网页触发关机」（见 D2-3）
- 不引入托盘（D12）

## 二、方案设计

### 2.1 总体思路

```text
壳（desktop）                                   后端（loop-agent-core）
   │                                                  │
   │ window 'close'                                   │
   │   → e.preventDefault()                           │
   │   → 显示「正在整理记忆…」遮罩                        │
   │   → POST /admin/shutdown  ────────────────────────▶ 202 {ok:true}
   │        （带 X-LoopAgent-Client 头）                  │  → setImmediate → performShutdown('http')
   │                                                  │     停调度器
   │                                                  │     runAllForShutdown(budget)   ← Dreaming
   │                                                  │     server.close()
   │                                                  │     断 MCP → exit(0)
   │   ← exited（正常） → app.quit()                    │
   │   ← 超时(budget+5s) → taskkill /T /F → app.quit()  │
   │                                                  │
   │ 后端 exit 事件（非主动关停）→ 错误窗「后端已停止」+ 重启按钮
```

### 2.2 关键设计决策

| 编号 | 决策 | 取舍与理由 |
|---|---|---|
| **D2-1** | **把 `onSignal` 内的关停序列抽成 `performShutdown(reason)`，信号处理与 HTTP 端点共用同一实现** | 避免「信号关停」与「端点关停」两套逻辑漂移。`shuttingDown` 标志上提为共享状态，保证**幂等**：重复调用直接返回「已在关停中」。**否决端点内重写一遍序列**（Dreaming 预算、MCP 断开顺序会漏）。 |
| **D2-2** | **端点先 `sendJson(202)` 再 `setImmediate` 触发关停** | 若同步关停，`server.close()` 会把响应吞掉，壳永远等不到确认，只能靠超时。先响应再关停，壳能确认「后端收到了」。 |
| **D2-3** | **端点必须校验自定义请求头 `X-LoopAgent-Client: desktop`，缺失则 403** | **这是本任务的安全要点**：服务端无 CORS/无 OPTIONS 预检（已核实），而 `POST` + 无自定义头属于 CORS「简单请求」——**任意网页都能悄无声息地发出去**，同源策略只拦截读响应、不拦发送。即：不加此校验，用户随便打开一个恶意页面就能让 LoopAgent 关机。自定义头会强制触发预检，浏览器因服务端无 CORS 响应头而拦下请求。Node 侧 fetch 不受 CORS 限制，壳带上即可。**否决「只靠回环 + token 校验」**（无 token 时回环校验挡不住浏览器发起的请求）。 |
| **D2-4** | **关停超时 = `memory.dreaming.shutdownBudgetMs` + 5s 宽限，之后 `taskkill /T /F` 兜底** | 与用户配置的预算对齐，避免「预算 30s 但壳 10s 就砍」。宽限 5s 覆盖 MCP 断开与进程退出。**否决固定 10s**（会按预算配置提前强杀，反而丢记忆）。 |
| **D2-5** | **单实例用 Electron `requestSingleInstanceLock()`；`second-instance` 时恢复并聚焦窗口** | 官方机制，跨平台可靠。**否决文件锁/端口探测自研**（Win 文件锁释放时机不可靠；端口探测无法定位到窗口）。 |
| **D2-6** | **后端意外退出时展示错误窗 + 「重启后端」按钮，不自动无限重启** | 自动重启会在配置错误时陷入重启风暴。给用户「看懂 + 一键重试」的出口。**否决静默自动重启**。 |
| **D2-7** | **关停中显示遮罩「正在整理记忆（Dreaming），最多 N 秒」** | Dreaming 可能耗数秒到数十秒，无提示用户会以为卡死并强杀进程（等于丢记忆）。文案直接用预算秒数。 |

### 2.3 检索依据

- Windows 信号语义：Node 官方 [process 文档](https://nodejs.org/api/process.html)「Sending SIGINT, SIGTERM, and SIGKILL will cause the unconditional termination of the target process」；本机实测 `handler-ran=false` 佐证
- CORS 简单请求与预检：自定义请求头不在白名单内会触发预检，服务端不回 CORS 头则浏览器拦截 → 用作 CSRF 防护

export interface ApiServerDeps {

`bootstrap.ts` 重构要点（保持行为不变）：

```ts
let shuttingDown = false;
let shutdownImpl: ((reason: string) => Promise<void>) | null = null;

const deps = { /* ... */ requestShutdown: (reason) => {
  if (shuttingDown) return false;
  void shutdownImpl?.(reason);
  return true;
} };

// createApiServer(deps) / server.start() 之后：
shutdownImpl = async (reason) => { /* 原 onSignal 主体，日志用 reason */ };
for (const sig of ['SIGINT','SIGTERM','SIGBREAK']) {
  process.on(sig, () => void shutdownImpl?.(sig));
}
```

### 3.3 边界与错误处理

| 场景 | 现象 | 处理 |
|---|---|---|
| 关窗时后端已死 | `POST` 连接失败 | 直接 `app.quit()`，不等待 |
| 关停请求发出后后端 20s 未退（Dreaming 卡住） | 窗口卡在遮罩 | 到达 `budget+5s` 后 `taskkill /T /F`，日志记「强杀」 |
| 用户在遮罩期再次点关闭 | 重复触发 | 幂等：忽略，保持等待 |
| 后端关停中途崩溃（exit 非 0） | — | 视为已退出，`app.quit()`，记日志 |
| 端点被无自定义头的请求调用（网页 CSRF） | 403 | 记审计日志 `[shutdown][denied]`，前端不暴露该端点 |
| 端点被重复调用（两个壳/脚本） | 409 | 幂等返回，不重复关停 |
| 未注入 `requestShutdown`（如单测直接 createApiServer） | — | 端点返回 501，不崩 |
| 后端意外退出（如 OOM） | 窗口白屏 | 错误窗 + 重启按钮；不自动重启 |
| 二次启动 | 起第二份后端风险 | 单实例锁拦截，聚焦已有窗口 |
| 关停期间收到系统关机（SIGTERM/SIGBREAK） | 双路触发 | 共用 `shuttingDown` 标志，只执行一次 |

## 一、任务目标需求

### 1.1 背景（痛点）

20261106-005 已把「上下文占用」搬到每条回答下方（复制 / 重试 / 百分比环），但用户看到的仍是**存量**（当前上下文占了多少），看不到**增量**（这一轮问答本身花了多少 token）：

- 一次 run 内可能有多次迭代（工具调用链），每次都是一次完整 LLM 调用，成本累加，界面上完全不可见；
- `llm_stats_summary` 只在 CLI 会话结束时打印（Task-15），WebUI 从未消费；
- 想知道「刚才那句是不是很贵」「开缓存到底省了多少」，只能去翻日志文件。

期望形态：在百分比环紧左侧增加一个轻量 chip（如 `⇅ 12.3K`），鼠标悬浮弹出小卡片：`总输入 / 总输出 / 总 Token / 平均缓存命中率`，底部一行口径脚注；数据来源与百分比环同源（SSE），不新增后端接口。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
| --- | --- | --- |
| 单次迭代 token | SSE `llm_stats` 已含 `iteration / promptTokens / completionTokens / totalTokens / cacheHitTokens / cacheHitRate`（[types.ts#L185-L197](../../../src/types.ts#L185-L197)） | 数据已有，`chat-stream` 只取了 `contextTokens` 三项，**token 字段未消费** |
| run 级权威累计 | `llm_stats_summary` 事件由 SSE 转发（[sse.ts#L32](../../../src/api/sse.ts#L32) `onLLMStatsSummary → write('llm_stats_summary', { summary })`），字段 `totalPrompt / totalCompletion / totalTokens / totalCacheHit / avgCacheHitRate`（[types.ts#L200-L208](../../../src/types.ts#L200-L208)） | **零后端改动即可用**（首版方案据此成立） |
| 平均缓存命中率口径 | [stats.ts#L70](../../../src/agent/stats.ts#L70) `avgCacheHitRate = hasCache && promptTokensWithCache > 0 ? totalCacheHit / promptTokensWithCache : undefined`（分母为**有缓存字段轮次**的 promptTokens） | 有权威口径，前端不应自行加权 |
| 历史轮次 token | 会话消息不携带任何统计字段（`SessionMessageFlags` 只有 `is_compact / is_show / show_content / kind`） | **缺失**：刷新或重进会话后全丢 |
| 展示位 | 005 已落地操作栏与百分比环（`.ctx-wrap`，`margin-left: auto`） | 只需在环左侧插入 chip |

### 1.3 任务目标

1. 操作栏新增 **Token chip**，展示本轮（一次 run）累计总 token，位于百分比环紧左侧。
2. 悬浮/键盘聚焦浮层展示：**总输入 / 总输出 / 总 Token / 平均缓存命中率** + 口径脚注「多轮迭代累计；命中率 = 命中缓存输入 ÷ 总输入」。
3. 流式中**实时**增长：`llm_stats` 逐迭代累加；run 结束由 `llm_stats_summary` 覆盖为权威累计。
4. 缓存命中率**三级回落**：后端 `avgCacheHitRate` → 前端累计命中 ÷ 累计输入 → `N/A`；厂商无缓存字段时必须显示 `N/A`（不是 `0.0%`）。
5. **每轮可见并可回看**：统计随会话落盘，刷新页面 / 重启服务后各轮 chip 数值不变。
6. 统计字段**绝不进入 LLM 请求**（避免非标准字段触发 400）。

### 1.4 设计约束

- 不改 `llm_stats` / `llm_stats_summary` 的**事件结构与语义**；不新增 REST 端点、不新增 SSE 事件。
- 统计是**展示态 + 存盘态**，不参与上下文计算、不参与压缩预算。
- `TurnUsage` 必须走既有「会话存盘标记」通道（`SessionMessageFlags`），调用 LLM 前统一剥离——与 `is_compact / is_show / show_content / kind` 同族，不另立机制。
- 旧会话（无 `usage` 的历史数据）**不显示 chip、不伪造估算**，不做数据回填迁移。
- 零新依赖；浮层复用 005 的 fixed 视口定位 + 悬停桥方案，规避滚动区裁切。
- 窄屏不换行、浮层不超出视口；数字用 tabular-nums 对齐。

## 二、方案设计

### 2.1 总体思路

```
run 期间（流式）
  Agent onLLMStats ──SSE llm_stats {iteration, promptTokens, ...}──▶ chat-stream
       ├ 更新 state.context（005：百分比环）
       └ 更新 state.turnTokens：iteration<=1 清零重计，否则累加
             └─ 镜像到 currentAssistant(msg).turnTokens ──▶ chip 实时增长

  Agent onLLMStatsSummary ──SSE llm_stats_summary {summary}──▶ chat-stream
       └ state.turnTokens = 权威累计（覆盖累加值）
             └─ 再次镜像到该条回答 ──▶ chip 定格为权威值

run 结束（后端 messages.ts）
  statsRecorder { summary?, accPrompt, accCompletion, accCacheHit }
       ├ 成功路径：attachTurnUsage(result.messages) ──▶ store.updateSession 落盘
       └ 中断路径：attachTurnUsage(sealPendingToolCalls(partial)) ──▶ 落盘
             （summary 优先 → 逐迭代累加兜底 → 一次调用都没有则不写）

会话加载（历史）
  GET /sessions/:id/messages ──▶ ApiHistoryMsg.usage
       └ rebuildChatMsgs：bundle 内任一 assistant 带 usage → 挂到展示消息 turnTokens
             └ ChatView：v-if="m.turnTokens" ──▶ 每轮各显示自己的 chip

调用 LLM 前
  LLMClient.normalizeMessages 剥离 usage（与 is_compact 等同族）──▶ 请求体不含该字段
```

### 2.2 关键设计决策

| 编号 | 决策 | 取舍 / 被否决项 |
| --- | --- | --- |
| D1 | **口径 = 一次 run 内多轮迭代累计**（不是最后一次迭代、不是会话累计） | 否决**只显示最后迭代**：工具调用链会把大头吃掉，显示严重偏低；否决**会话累计**：005 的百分比环已是会话级，两者会重复表意 |
| D2 | **流式中逐迭代累加 + `iteration <= 1` 清零重计**；run 结束由 `llm_stats_summary` **覆盖**为权威值 | 否决**只靠前端累加**：漏事件/中断会永久偏差；否决**只等 summary**：用户整段生成期间看不到任何数字。`<= 1` 而非 `=== 1` 是为兼容 iteration 从 0 或 1 起算的服务端 |
| D3 | **命中率三级回落**：`avgCacheHitRate` → `cacheHitTokens / promptTokens` → `N/A` | 否决**统一用 `totalCacheHit / totalPrompt`**：厂商无缓存字段时该式恒为 0，会显示 `0.0%` 这种「有数据但全 miss」的假象；`N/A` 才是诚实的「厂商不提供」 |
| D4 | **落盘载体 = `SessionMessageFlags.usage`（`TurnUsage`）**，挂在该轮**最后一条有正文**的 assistant 消息上 | 否决**独立侧表/独立统计文件**：要新增存储格式、迁移与一致性维护；否决**挂到 user 消息**：语义错位（成本是生成侧的）；否决**挂到纯 tool_calls 的中间 assistant**：与「该轮回答」的展示 bundle 不对应 |
| D5 | **`usage` 绝不进 LLM 请求**：`normalizeMessages` 统一剥离 | 硬约束。OpenAI 兼容端点遇到未声明字段可能 400；与 `is_compact / is_show / show_content / kind` 同族处理，不新增清洗分支逻辑 |
| D6 | **每条有统计的回答都显示 chip**（初版「仅最后一条」在第二轮提交中改为每轮） | 否决**仅最后一条**：落盘后每轮数据都在，只显示最后一条既浪费又让人猜；用户对 005 的诉求本就是「每条回答下方」 |
| D7 | **布局：`.tok-wrap` 接管 `margin-left: auto`，`.tok-wrap + .ctx-wrap` 让位为 `0`** | 否决**两者都 auto**：两个 auto 均分空隙，chip 与环之间出现一段诡异空白；否决**绝对定位**：操作栏是 flex 且窄屏会挤压，绝对定位会重叠 |
| D8 | 浮层沿用 **fixed 视口定位 + 悬停桥**（与 005 的 `ctx-pop` 同方案） | 否决 `absolute`：对话滚动容器有 `overflow`，浮层会被裁切（005 已踩过） |
| D9 | **旧数据不显示 chip、不估算** | 否决**按上下文 token 反推**：那是「当前上下文」不是「本轮消耗」，反推会给出错误数字；旧轮次的真实值已不可恢复 |
| D10 | **中断轮也尽量落统计**：summary 缺失时用逐迭代累加兜底；一次 LLM 调用都没发生则返回 `undefined` 不写 | 否决**中断就不写**：成本已经真实发生（用户付费了），把数字丢掉等于骗自己；否决**强制写 0 值**：`0` 会被展示成「很便宜」，实际是「未知」 |
| D11 | `TurnTokenStats.at` 改**可选**；`SessionContextUsage.keepRecentTurns` 改**可选**（前端按 3 兜底） | 落盘数据无采集时间戳；旧版服务端不返回 `keepRecentTurns`，硬取会显示「最近 undefined 轮」（顺带修复的兼容缺陷） |
| D12 | 首版承诺**零后端改动**（只消费已有 SSE）；第二轮为「落盘 + 每轮展示」扩展了后端 | 属**需求扩展**而非方案推翻：SSE 侧确实零改动，新增的仅是落盘字段与采集代码 |

### 2.3 参考与已知坑

- 参考形态：Trae 截图的操作栏——`复制 / 重试` 图标组 + 「由 AI 生成」+ 右侧环形百分比；本任务在环左侧加 chip，视觉权重低于环（次要信息）。
- 本项目已知坑：
  1. `llm_stats` 的 `iteration` 在 [stats.ts](../../../src/agent/stats.ts) 中从 **0** 计首轮（`s.iteration === 0`），前端判定用 `<= 1` 才既能识别 0 起算也能识别 1 起算。
  2. 同轮多条 assistant（工具调用链）在 `rebuildChatMsgs` 中合成**一个展示 bundle**；`usage` 只挂在其中一个（最后一条有正文的）上，因此必须用 `pendingUsage` 在 bundle 内**冒泡**，`flush()` 时赋值并清空——否则 bundle 切换时会错挂到下一轮。
  3. `attachTurnUsage` 必须**倒序找 `role==='assistant' && content` 非空**的消息：末尾可能是 `tool_calls`（无正文）或 `tool` 结果消息。
  4. `store.updateSession` 是增量合并，`usage` 作为消息字段随数组一起写入；压缩（005）丢弃消息时其 `usage` 一并消失，属预期（该轮已从视图移除）；保留下来的消息 `usage` 不受影响。
  5. 中断路径写入点在 `sealPendingToolCalls()` **之后**——先补齐合成 tool 消息，再挂统计，避免脏序列。
  6. `turnTokensOf()` 在第二轮改为「按消息自身 `turnTokens` 展示」后已无调用方，仅作为导出 API 留下（`tsc` 不会报未使用）；**不要再把它当作 chip 的数据源**，否则会退回「整个会话只有一个 chip」的旧行为。

## 三、任务详细设计

### 3.1 后端：`TurnUsage` 类型与落盘位置

[types.ts](../../../src/types.ts)：

```ts
/** 单轮（一次 run）token 统计：挂在每轮最终 assistant 消息上随会话落盘 */
export interface TurnUsage {
  promptTokens: number;      // 累计输入
  completionTokens: number;  // 累计输出
  totalTokens: number;       // 累计总
  cacheHitTokens: number;    // 命中缓存输入合计（0 = 无缓存数据）
  avgCacheHitRate?: number;  // 厂商无缓存字段时 undefined
}

export interface SessionMessageFlags {
  is_compact?: boolean;
  is_show?: boolean;
  show_content?: string;
  kind?: 'summary';
  /** 仅每轮最终 assistant 消息携带；不进入 LLM 请求 */
  usage?: TurnUsage;
}
```

要点：走既有「会话存盘标记」通道，不新开顶层字段、不改消息 schema 结构。

### 3.2 后端：`normalizeMessages` 剥离 `usage`

[client.ts](../../../src/llm/client.ts) 的清洗列表追加一项：

```ts
const { is_compact: _c, is_show: _s, show_content: _sc, kind: _k, usage: _u,
        tool_calls, ...rest } = m;
```

注释同步说明 `usage` 是会话存储标记。这样 Agent 内部把 `entry.history` 直接喂给 `LLMClient` 时（005 的实现方式），`usage` 不会漏进请求体。

### 3.3 后端：`statsRecorder` 采集与两个纯函数

[messages.ts](../../../src/api/handlers/messages.ts) 中，`runMessageTurn` 的 `statsRecorder` 从「只写 `lastContext`」扩展为「写 `lastContext` + 累计 + 接 summary」：

```ts
const statsRecorder = {
  summary: undefined as LLMStatsSummary | undefined,  // run 结束的权威累计
  accPrompt: 0, accCompletion: 0, accCacheHit: 0,      // 逐迭代累加（兜底）
  onLLMStats(stats) {
    entry.lastContext = { /* 005 逻辑不变 */ };
    statsRecorder.accPrompt     += stats.promptTokens;
    statsRecorder.accCompletion += stats.completionTokens;
    statsRecorder.accCacheHit   += stats.cacheHitTokens ?? 0;
  },
  onLLMStatsSummary(summary) { statsRecorder.summary = summary; },
};
```

两个纯函数：

- `buildTurnUsage(recorder)`：`summary` → 直接映射五个字段；否则累加值 > 0 → 用累加值（`totalTokens = accPrompt + accCompletion`，无 `avgCacheHitRate`）；两者皆空 → `undefined`（不写）。
- `attachTurnUsage(messages, usage)`：`usage` 为 `undefined` 直接返回；否则**倒序**找第一条 `role === 'assistant' && content` 非空的，赋值 `m.usage = usage`，原地修改（调用方随后交给 `store.updateSession`）。

写入点两处：

| 路径 | 位置 | 说明 |
| --- | --- | --- |
| 成功 | `store.updateSession(...)` 之前 | `attachTurnUsage(result.messages, buildTurnUsage(statsRecorder))` |
| 中断 | `sealPendingToolCalls(partial.messages)` 之后、落盘之前 | 同上，用累加兜底（中断时通常无 summary） |

### 3.4 前端：`chat-stream.ts`

1. 新增 `TurnTokenStats`（`at` 可选）+ `SessionStreamState.turnTokens` + `turnTokensOf(id)`（第二轮改为按消息自身展示后，该导出**保留但当前无调用方**）。
2. `llm_stats` 分支扩展读取 `iteration / promptTokens / completionTokens / cacheHitTokens`：

```ts
const iteration = Number(raw.iteration ?? 0);
const base = iteration <= 1 ? undefined : st.turnTokens;   // 新一轮清零重计
st.turnTokens = {
  promptTokens: (base?.promptTokens ?? 0) + p,
  completionTokens: (base?.completionTokens ?? 0) + c,
  totalTokens: (base?.totalTokens ?? 0) + p + c,
  cacheHitTokens: (base?.cacheHitTokens ?? 0) + Number(raw.cacheHitTokens ?? 0),
  avgCacheHitRate: base?.avgCacheHitRate,
  at: Date.now(),
};
currentAssistant(st).turnTokens = st.turnTokens;   // 镜像到当前回答，实时刷新
```

3. 新增 `llm_stats_summary` 分支：用 `summary.totalPrompt / totalCompletion / totalTokens / totalCacheHit / avgCacheHitRate` **覆盖** `st.turnTokens`，并再次镜像到 `currentAssistant`。
4. `ApiHistoryMsg` 增 `usage?: TurnTokenStats`；`ChatMsg` 增 `turnTokens?: TurnTokenStats`。
5. `rebuildChatMsgs`：bundle 内任一 assistant 带 `usage` 时记入 `pendingUsage`，`flush()` 写入展示消息后清空（见 2.3 坑 2）。

### 3.5 前端：`ChatView.vue`

- 模板：操作栏在「由 AI 生成」之后、`.ctx-wrap` 之前插入 `.tok-wrap`，条件 `v-if="m.turnTokens"`（**每条**回答各自显示）。
- 纯函数化：`tokTotalOf(t)`、`cacheRateOf(t)` 取代原先依赖全局 `turnTokens` 的 computed——因为现在数据源是**消息自身**：

```ts
function cacheRateOf(t: TurnTokenStats): string {
  const rate = t.avgCacheHitRate
    ?? (t.promptTokens > 0 && t.cacheHitTokens > 0 ? t.cacheHitTokens / t.promptTokens : undefined);
  return rate != null ? `${(rate * 100).toFixed(1)}%` : 'N/A';
}
```

- 浮层四行：总输入 / 总输出 / 总 Token / 平均缓存命中率；脚注「口径：多轮迭代累计；命中率 = 命中缓存输入 ÷ 总输入」；定位复用 `placeTokPop` 的 fixed 视口方案 + 悬停桥。
- 样式：

```css
.tok-wrap { position: relative; flex: none; margin-left: auto; }
.tok-wrap + .ctx-wrap { margin-left: 0; }   /* 环让位，chip 与环紧贴 */
```

### 3.6 兼容性兜底

- `SessionContextUsage.keepRecentTurns` 改为可选；`chat-stream` 中原 `st.context.keepRecentTurns` 改为 `st.context?.keepRecentTurns ?? 3`，消除旧版服务端下浮层显示「最近 undefined 轮」。

### 3.7 演进项（本任务不做）

- 按迭代拆分展示（多轮迭代各自的 token / 耗时明细）；
- 费用估算（按 model 单价折算金额）；
- 旧会话 token 回填（数据不存在，无法恢复）；
- 跨轮次成本趋势图 / 会话总成本汇总卡片；
- 把 `usage` 延伸到 L2 记忆条目做「成本-收益」分析。

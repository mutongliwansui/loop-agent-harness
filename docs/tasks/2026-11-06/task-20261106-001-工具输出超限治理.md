## 一、任务目标需求

### 1.1 背景（痛点）

当前工具输出超限处理一律「截断即丢弃」：

| 工具 | 现有截断策略 | 缺失的一环 |
| --- | --- | --- |
| `commandRun` 前台（20261104-006） | `OutputAccumulator` 头尾各 128KB，中间省略并标注 `…(省略 N 字节)…` | 完整 stdout/stderr 无任何地方落盘，超限后中间内容彻底丢失 |
| `fileRead`（20261021-007） | 默认 2000 行 / 256KB、硬上限 16MB，超限返回前 N 行 + 截断提示「请用 startLine/endLine 分段」 | LLM 不知道自己丢了多少行、完整内容还在不在，只能盲猜分段参数反复重试 |
| `grep` | 已有 `maxResults` 默认 50，超限追加 `（已达上限）` | 上限偏小，超限只说「已达上限」不给完整结果通道 |
| MCP 工具 | 无治理 | 大 JSON / 大结果集直接原样进上下文 |

后果链：**大输出 → 高频触发 L1 压缩 → 拉低缓存命中率**（20261021-008 已实证大输出是命中率摊薄原因之一）；同时 LLM 在信息缺失时容易误判或低效重试（盲猜分段参数反复烧 token）。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
| --- | --- | --- |
| 统一后处理入口 | [runner.ts](../../../../src/tools/runner.ts) `run()` 拿到 result 直接 return，无任何后处理层 | 一次性工具（fileRead/grep）可在 runner 层统一治理 |
| 流式管道拆分 | [commandRun.ts](../../../../src/tools/commandRun.ts#L130-L131) spawn 的 stdout/stderr 只进 OutputAccumulator | 需分两路：一路累积截断、一路写临时文件 WriteStream |
| 临时文件目录 | 无 | 新增 `~/.loop-agent/tmp/<sessionId>/` |
| 临时文件 TTL 清理 | [background-tasks.ts](../../../../src/tools/background-tasks.ts#L42-L80) 已有 `pruneRuns()` 按 `retentionDays` 清理 `runs/` 目录 | 复用同框架，新目录纳入同一定时任务 |
| ToolContext 会话归属 | [runner.ts#L56](../../../../src/tools/runner.ts#L56) `ctx.sessionId` 已注入 | 直接用来做临时文件会话隔离 |
| commandRun 现有配置 | [command-run-output.ts](../../../../src/tools/command-run-output.ts#L106-L124) `configureCommandRunOutput({outputLimitKb, timeoutMs})` 由 config 注入 | 新增治理配置：`preserveKb`、`tmpTtlDays` |
| grep 现有上限 | [grep.ts#L40](../../../../src/tools/grep.ts#L40) `maxResults ?? 50` | 默认值可调大 + 超限落盘 |
| SSE tool_result 事件 | 后端 payload 无临时文件路径字段 | 新增可选 `fullOutputPath` 字段 |

### 1.3 任务目标

1. **超限三步骤行为**：截断片段进上下文（继续用现有策略）→ 完整原始输出落 `~/.loop-agent/tmp/<sessionId>/` → observation 末尾追加结构化路径提示（路径 + 总大小 + 总行数 + 再读建议）。
2. **LLM 能按需再读**：看到路径后能正确调用 `fileRead startLine/endLine` 分段读取超限部分，不再盲猜。
3. **不超限零开销**：只有输出超阈值时才触发落盘，小输出完全不走这条路。
4. **临时文件 7 天自动清理**，历史会话回放时若已清理，前端 chip 置灰。
5. **不改动现有截断策略本身**，只做增量叠加。

### 1.4 设计约束

- 保持零新依赖（`node:fs` / `node:path` / `node:os` / `node:crypto` 均为内置）。
- 临时文件写入不得阻塞事件循环（全部 WriteStream 异步管道）。
- 小输出（未超阈值）场景行为与现在逐字节一致，不能引入额外磁盘 I/O。
- 跨平台兼容：Windows/macOS/Linux 路径归一、spawn pipe 行为一致。
- 临时文件属会话隔离，**不得**进工作空间（避免污染 git 工作区）。
- 方案先行，不执行代码——本任务文档为方案阶段交付物。

## 二、方案设计

### 2.1 总体思路

```
工具执行
  │
  ├─ 流式工具（commandRun 前台）
  │    spawn pipe stdout/stderr
  │      ├─▶ OutputAccumulator（头尾截断 → 进上下文）
  │      └─▶ WriteStream（完整原始输出 → tmp 文件）
  │           仅当累计字节 > 阈值时才创建 WriteStream
  │           （小输出：不创建、零磁盘 I/O）
  │
  ├─ 一次性工具（fileRead / grep）
  │    execute(args) → 拿到 result 字符串
  │      │
  │      └─▶ runner 层 OutputGovernor.postProcess()
  │           ├─ 未超阈值 → 原样返回（零开销）
  │           └─ 超阈值   → 完整内容写 tmp 文件
  │                        + 返回截断片段 + 路径提示
  │
  └─ observation 注入 LLM
       [截断片段]
       
       [完整输出已保存]
       路径: ~/.loop-agent/tmp/sess_xxx/fileRead-src-react-agent.ts-1730956800.txt
       总大小: 4.2MB，共 12580 行
       可按需用 fileRead 的 startLine/endLine 分段读取（如 startLine: 1000, endLine: 1500）


临时文件清理（复用 background-tasks 框架）
  ~/.loop-agent/runs/pruneRuns()  ← 同定时任务
  ~/.loop-agent/tmp/pruneTmp()    ← 新增，同 retentionDays 配置
```

### 2.2 关键设计决策

| 编号 | 决策 | 取舍 / 被否决项 |
| --- | --- | --- |
| D1 | **治理层位置分两类**：流式工具（commandRun 前台）在工具内部 spawn pipe 分两路；一次性工具（fileRead/grep）在 runner 层 `OutputGovernor.postProcess()` 统一治理 | 否决**全部放 runner 层**：commandRun 的数据是流式消费的，跑完才一次性拿到结果，此时完整内容已在内存里（OutputAccumulator 只保留截断部分），落盘的必须是流式过程中就分流的完整原始数据。否决**全部放工具内部**：一次性工具各自实现会重复逻辑，runner 层统一更简洁 |
| D2 | **按工具分别配置进上下文的保留阈值**：commandRun 头尾各 64KB（比现有 128KB 更激进，因有完整落盘兜底）、fileRead 默认 500 行 / 128KB、grep 默认 200 行；阈值可通过 `tools.output.preserveKb` / `preserveLines` 全局覆盖 | 否决**全局一个阈值**：commandRun 输出可能上万行日志（行短）、fileRead 可能是 minified 单行超长（行长），不同工具阈值口径不同。否决**不改现有 commandRun 128KB**：落盘兜底后可以更激进地截断进上下文，节省 token |
| D3 | **临时文件目录与命名**：`~/.loop-agent/tmp/<sessionId>/<tool>-<paramDigest>-<unixTs>.txt`；`paramDigest` 取核心参数摘要（commandRun 命令前 32 字符、fileRead 目标文件名、grep search 关键字），过滤路径分隔符；会话未建（CLI 首轮）时 sessionId 用 `nosess_<ts>` | 否决**直接放 `~/.loop-agent/tmp/` 不分子目录**：会话并发时文件混在一起难以清理、难以按会话隔离读取。否决**用短 hash**：人工排查时看不出是什么工具、什么参数产生的 |
| D4 | **observation 路径提示格式（结构化、可解析）**：见下方代码块 | 否决**自然语言散文**：LLM 难以稳定抽取路径、大小、行数三个字段，也难以从「可按需分段」这类模糊提示里得出具体调用参数 |
| D5 | **小输出零开销触发条件**：commandRun 流式过程中累计字节首次 > `preserveKb * 2` 时才创建 WriteStream（比进上下文的截断阈值大一倍，给小输出留宽松空间）；一次性工具在 `postProcess` 里先测 result 字符串字节数，未超阈值原样返回 | 否决**一启动就写**：1KB 的 fileRead 结果也去磁盘写一次，纯属浪费 I/O。否决**跑完再判断要不要写**：commandRun 此时完整输出已在内存里（OutputAccumulator 只保留截断部分），落盘不了 |
| D6 | **清理机制复用 background-tasks**：新增 `tmpDir()` / `pruneTmp()` 到 background-tasks.ts（或独立 output-governor.ts），沿用 `retentionDays`（默认 7）+ `maxTotalMb`（默认 200）双阈值，与 runs 目录同启动时机（后台任务启动前触发清理时一并执行） | 否决**单独起定时器**：多一个定时器多一份复杂度，且 runs 与 tmp 同天清理逻辑完全一样。否决**按会话结束触发清理**：CLI 首轮无会话、serve 模式会话跨天，「会话结束」时机不明确 |
| D7 | **前端兼容（P2 阶段）**：ToolCard 结果区渲染截断片段后追加 chip「查看完整结果」，点击复用 20261028-003 已落地的 `GET /uploads/view` 预览链路（需为 tmp 目录增加受控放行校验：路径前缀必须是 `~/.loop-agent/tmp/`）；SSE `tool_result` 事件 payload 新增可选 `fullOutputPath` 字段；临时文件已清理则 chip 置灰显示「已清理」 | 否决**单独起新预览端点**：20261028-003 刚落地的放行+预览链路已足够成熟，只需放宽前缀校验。否决**chip 必须后端强制渲染**：chip 可选，小输出（未超限）时不出现 |
| D8 | **MCP 工具治理列演进项（P2）**：本期只覆盖内置工具（commandRun/fileRead/grep），MCP 工具的统一治理延后——MCP 工具返回值类型各异（JSON/字符串/二进制），治理策略需按返回类型分别设计，复杂度更高 | 否决**本期一并覆盖**：scope creep 风险大，且 MCP 工具当前治理空白是已知缺陷但不阻塞主链路 |
| D9 | **演进增强（P2）**：超限后除告知路径外，可对完整输出做一次快速扫描定位关键区间（stderr 或 ERROR/FAIL 关键词），给 LLM 追加「建议下一步」提示（如「报错行在第 3200 行附近，建议先读 3180-3220 行」） | 本期不做，属于「让 LLM 更聪明」的增量优化 |

### 2.3 联网检索结论

- **VS Code Task / GitHub Actions Runner**：均采用「流式累积 + 头尾截断 + explicit omitted marker」，不存完整日志——与本方案「截断进上下文 + 完整落盘」的差异在于它们不需要让 LLM 再读，所以没有落盘环节。本方案的落盘正是为 LLM 再读设计的。
- **LangChain / LlamaIndex 文档截断策略**：典型做法是固定窗口截断 + 完整文档另存（retrieval 时按需拉取），思路与本方案一致。
- **已知坑**：
  1. `spawn` pipe 分两路时必须用 `PassThrough` 或直接两个 `.on('data')` 分支，**不能**先 `pipe` 到 Accumulator 再 pipe 到文件（第一个 pipe 会消费 buffer，第二个拿不到）；正确做法是两个消费者并行监听 `stdout.on('data', chunk => { accumulator.push(chunk); if (writer) writer.write(chunk); })`。
  2. WriteStream 在 `close` 事件前 `fs.createWriteStream()` 是惰性打开（第一次 write 才真正 open），所以首次 write 前可以安全判断是否真的超限再决定要不要创建。
  3. 临时文件必须用 `fs.createWriteStream(path, { flags: 'w' })` 而非追加，因为是每次工具执行的新文件。
- 来源：Node.js Stream 文档、VS Code Task API 文档、LangChain 文档（2026-11 检索）。

## 三、任务详细设计

### 3.1 新增模块 `src/tools/output-governor.ts`

```ts
// 统一输出治理器（一次性工具走 runner 层、流式工具走内部 hook）
// 小输出零开销：未超阈值的工具完全不走这套

export interface PreserveThresholds {
  /** 进上下文的保留上限（KB），超此值触发落盘 */
  preserveKb: number;
  /** 进上下文的保留行数上限（grep / fileRead 用） */
  preserveLines: number;
  /** 临时文件完整写入的触发倍数（commandRun 流式）：
   * 累计字节 > preserveKb * triggerMultiplier 才创建 WriteStream
   * 设成 2 给小输出留宽松空间 */
  triggerMultiplier: number;
  /** 临时文件保留天数（默认 7） */
  tmpTtlDays: number;
  /** tmp 目录总量上限（MB，默认 200） */
  tmpMaxTotalMb: number;
}

// 默认值
const DEFAULT: PreserveThresholds = {
  preserveKb: 64,          // commandRun 头尾各 64KB 进上下文
  preserveLines: 500,      // fileRead 默认 500 行、grep 默认 200 行可各自覆盖
  triggerMultiplier: 2,    // commandRun 累计 > 128KB 才落盘
  tmpTtlDays: 7,
  tmpMaxTotalMb: 200,
};

/** 治理结果：截断后的文本 + 可选的完整输出提示 */
export interface GovernedOutput {
  /** 最终注入 LLM observation 的文本（已截断 + 已追加路径提示） */
  text: string;
  /** 完整输出文件路径（未超阈值则为空） */
  fullOutputPath?: string;
  /** 完整输出总行数（未超阈值或无法统计时为 undefined） */
  fullOutputLines?: number;
  /** 完整输出总字节数 */
  fullOutputBytes?: number;
  /** 是否超限（治理器判断） */
  truncated: boolean;
}

/** 一次性工具治理入口（runner 层调用） */
export function governOneShot(
  result: string,
  toolName: 'fileRead' | 'grep' | string,
  args: Record<string, unknown>,
  sessionId: string | undefined,
  thresholds?: Partial<PreserveThresholds>,
): Promise<GovernedOutput>;
```

### 3.2 commandRun 前台流式分路改造

在 [commandRun.ts#L130-L131](../../../../src/tools/commandRun.ts#L130-L131) 的 spawn pipe 消费位置改为并行两路：

```ts
// src/tools/commandRun.ts runInForeground() 内

const tmpWriter = new TmpFileWriter({
  sessionId: ctx?.sessionId,
  toolName: 'commandRun',
  paramDigest: summarizeCmd(cmd),   // 命令前 32 字符
  thresholds: governThresholds(),
});

child.stdout?.on('data', (chunk: Buffer) => {
  out.push(chunk);              // 截断累积进上下文
  tmpWriter.onChunk(chunk);     // 完整流式写临时文件（超限前不做事）
});
child.stderr?.on('data', (chunk: Buffer) => {
  err.push(chunk);
  tmpWriter.onChunk(chunk);
});

child.on('close', async (code, signalName) => {
  const finish = ...; // 现有 finish 闭包收敛逻辑不变
  const fullInfo = await tmpWriter.finalize(); // 拿到 fullOutputPath + 行数
  // finish 里把 fullInfo 拼到 parts 末尾（超限才拼）
});
```

**关键点**：`TmpFileWriter` 类内部延迟创建 WriteStream——`onChunk` 只在累计字节首次 > `preserveKb * triggerMultiplier` 时才真正 `createWriteStream()` 开始落盘，在此之前 chunk 直接丢弃（进不了文件），零磁盘开销。

### 3.3 fileRead / grep 一次性工具改造

**方案 A（推荐，D1 决策）**：fileRead / grep 的 `execute()` 保持原样，在 runner 层统一治理：

```ts
// src/tools/runner.ts run() 内

const result = await this.withTimeout(raced, timeout);
let text: string;
if (typeof result === 'string') text = result;
else try { text = JSON.stringify(result); } catch { text = String(result); }

// 一次性工具走治理器；流式工具（commandRun）已自行处理
if (!toolIsStreamed(tool.name)) {
  const governed = await governOneShot(text, tool.name, args, options.sessionId);
  if (governed.truncated) return governed.text;
}
return text;
```

**方案 B（备选）**：fileRead / grep 各自在 execute 内部自己判断 + 落盘。推荐 A 的原因是逻辑统一、不重复，但 A 有一个小约束：execute 返回的 result 必须是**完整原始内容**，不能已经被 fileRead 的 2000 行截断——否则 runner 层拿到的已经是截断文本，落盘不了完整内容。

**这引出 D1a 子决策**：fileRead / grep 在治理器启用时，execute 应返回完整内容（行迭代器模式下边扫描边落盘同时累积完整字符串），再由 runner 层治理器截断进上下文。或者 fileRead / grep 各自内置治理点（方案 B），在扫描过程中同时做截断+落盘。

> **推荐方案 B（文件内治理）**：fileRead 的 `readFull()` 本来就是流式扫描器，边扫边同时做「截断累积到 shown 数组」和「完整内容写 tmp 文件」最自然；grep 的 `searchFile` 同样在扫描时能同时收集完整 matches 列表和截断保留前 N 行。runner 层的治理器只作为 MCP 等未知工具的兜底。

### 3.4 observation 路径提示格式

超限后在 observation 末尾追加以下结构化块，**用特殊分隔行标记**以便前端和 agent 层识别：

```

── 完整输出已保存 ──
路径: ~/.loop-agent/tmp/sess_ab12cd34/commandRun-npm_test-1730956800.txt
总大小: 4.2 MB
总行数: 12580
建议: 用 fileRead 的 startLine/endLine 分段读取，如 startLine: 3180, endLine: 3220
```

**设计要点**：
- 用 `── 完整输出已保存 ──` 作为边界标记（与正文天然分隔），agent 层可以用 `startsWith` / `includes` 稳定识别；
- 字段用 `路径:` / `总大小:` / `总行数:` / `建议:` 四字头，LLM 容易抽取；
- 大小用人类可读格式（`4.2 MB` / `356 KB` / `12 B`），同时给原始字节数可选；
- 最后一行给**具体可执行的示例参数**，而非「请分段」这种模糊提示。

### 3.5 临时文件命名与路径构造

```ts
// src/tools/output-governor.ts

function tmpDir(): string {
  return join(homedir(), '.loop-agent', 'tmp');
}

/** 生成临时文件路径：
 *  ~/.loop-agent/tmp/<sessionId>/<tool>-<paramDigest>-<unixTs>.txt
 * sessionId 未建时：nosess_<ts>
 */
export function buildTmpFilePath(
  sessionId: string | undefined,
  toolName: string,
  paramDigest: string,
  unixTs: number = Math.floor(Date.now() / 1000),
): string {
  const sessionDir = sessionId ?? `nosess_${unixTs}`;
  const safeDigest = sanitizeParamDigest(paramDigest);  // 过滤 \ / : * ? " < > |，截断到 32 字符
  const fileName = `${toolName}-${safeDigest}-${unixTs}.txt`;
  return join(tmpDir(), sessionDir, fileName);
}

/** 参数摘要构造：
 * - commandRun: 去掉 npm/yarn/pnpm 后的命令前 32 字符，空格替换为 _
 * - fileRead: 目标文件 basename（非路径）
 * - grep: search 关键字前 32 字符
 */
export function summarizeParam(args: Record<string, unknown>, toolName: string): string;
```

### 3.6 TmpFileWriter（commandRun 流式专用）

```ts
// 内部类，供 commandRun.ts 等流式工具使用

class TmpFileWriter {
  private writer: WriteStream | null = null;
  private totalBytes = 0;
  private linesCounted = false;
  private lineCount = 0;
  private finalized = false;

  constructor(private readonly config: {
    sessionId: string | undefined;
    toolName: string;
    paramDigest: string;
    thresholds: PreserveThresholds;
  }) {}

  /** 每次收到流式 chunk 时调用 */
  onChunk(chunk: Buffer): void {
    this.totalBytes += chunk.length;
    // 未达触发阈值：丢弃（既不累积完整内容、也不落盘），零开销
    if (this.writer === null && this.totalBytes < this.config.thresholds.preserveKb * 1024 * this.config.thresholds.triggerMultiplier) {
      return;
    }
    // 首次越过阈值：创建 WriteStream 并补写之前已丢弃的内容
    if (this.writer === null) {
      const path = buildTmpFilePath(this.config.sessionId, this.config.toolName, this.config.paramDigest);
      mkdirSync(dirname(path), { recursive: true });
      this.writer = createWriteStream(path, { flags: 'w' });
    }
    // 后续所有 chunk 都写入
    this.writer.write(chunk);
  }

  /** 完成时关闭 WriteStream，返回完整信息；未触发落盘返回 undefined */
  async finalize(): Promise<{ path: string; bytes: number; lines: number } | undefined>;
}
```

**关键设计点**：
- `triggerMultiplier` 双阈值机制——进上下文的截断阈值是 `preserveKb`，但触发落盘要 `preserveKb * 2`，给 commandRun 这类流式工具留缓冲：输出 < 128KB 时完全不落盘（零开销），> 128KB 才开始写完整内容；
- **首次落盘前已丢弃的 chunk 无法补回**——这是已知取舍：小输出根本不触发落盘；超阈值时只保存阈值之后的完整内容。如果用户需要**绝对完整**（包括阈值之前的部分），可改为「一启动就创建 WriteStream」但会牺牲小输出零开销。推荐前者，因 commandRun 头尾截断已经保住了命令开头。

### 3.8 边界与错误处理

| 场景 | 行为 |
| --- | --- |
| 输出 < 阈值（小输出） | 不创建 WriteStream、不写临时文件、observation 原样返回 |
| 临时文件创建失败（目录权限问题） | 降级：截断片段仍进上下文，但 observation 里不拼路径提示（或拼一行 `[完整输出保存失败: EACCES]`） |
| 工具执行被 abort | TmpFileWriter.finalize() 尽量关闭 WriteStream（用 try-finally 防悬挂），返回的完整信息可能是半截——但截断片段已进上下文，LLM 能看到 abort 标记 |
| sessionId 未建（CLI 首轮） | 用 `nosess_<ts>` 目录，清理时一并处理 |
| 清理时目录不存在 | mkdir 会自动创建；pruneTmp() 先 stat 目录，不存在直接返回 0 |
| 文件路径包含特殊字符（命令里的空格/引号/换行） | `sanitizeParamDigest` 过滤 |

## 一、需求背景

20261021-002-05 已交付**同工作空间多会话并发**（会话级 `inFlight` 锁 + `AgentPool` 按 `sessionId` 租用 + `RunHub` 多 run 并存），但**跨工作空间并行**仍被三处进程级全局态锁死：

1. `switchWorkspace()` 先 `process.chdir()`，再原地重绑 store、改写 configLoader/Writer 路径、清记忆缓存、重置整池（[sessions.ts:132-158](file:///d:/trae_workspace/loop-agent-command/src/api/handlers/sessions.ts#L132-L158)）——一次切换让**所有**空间相关对象重置；
2. `hasInFlight()` 是**全局**互斥，不区分空间（[session-manager.ts:49-54](file:///d:/trae_workspace/loop-agent-command/src/api/session-manager.ts#L49-L54)），A 空间跑着，B 空间连新建会话都被 `busy` 拒绝；
3. `process.cwd()` 被 **33 处 / 17 文件**隐式依赖（其中最关键的 `commandRun` 无 `args.cwd` 时直接落在启动目录）。

另有两处设计期才暴露的硬约束：

4. `workspaceId()` 对**原始字符串**直接取 SHA-256（[store.ts:33-35](file:///d:/trae_workspace/loop-agent-command/src/session/store.ts#L33-L35)），`D:\proj`、`D:\proj\`、`d:\PROJ` 会分裂成三个空间；
5. `sessionId` 是**秒级时间戳**（[store.ts:335](file:///d:/trae_workspace/loop-agent-command/src/session/store.ts#L335)）且作 `RunHub.runs` / `SessionManager.sessions` / 前端流状态的**全局键**，跨空间同秒创建会撞名；`/sessions/:id` 路由只有单段 id，无空间维度。

## 二、总体设计（摘要）

详细设计见设计方案第 3/4 章，此处仅列与任务边界相关的骨架：

```
        WorkspaceRegistry（task-01 建立）
          key = canonicalWorkspacePath(root)，value = WorkspaceRuntime（不可变）
             │ get(root) 懒建
   ┌─────────┼──────────────┬───────────────┬──────────────┐
   ▼         ▼              ▼               ▼              ▼
 root    SessionStore   ConfigLoader   ConfigWriter   AgentPool
(canonical) 每空间一例      每空间一例       每空间一例      每空间一池
   │
   ├─► AsyncLocalStorage<{root,id}>（task-02 兜底）
   │        └─► currentWorkspaceRoot() 被漏改的深层代码读取
   │
   └─► ToolContext.workspaceRoot（task-02 显式，优先）
            └─► runner 注入 → commandRun / fileRead / fileWrite / editFile / grep / fileSearch
                （统一走 resolveInWs 越界校验，不使用 process.cwd()）

 RunHub（全局单例）靠 sessionId 空间命名空间唯一（task-04，D5）
 全局 hasInFlight() → 每 runtime 的 sessions.hasInFlight()（task-04）
 前端撤 foreignActive 只读与 switched toast（task-05）
```

关键取舍：

- **每空间一个 `AgentPool`**（非共享池）——`initAgent` 是池级固定钩子（[bootstrap.ts:38-41](file:///d:/trae_workspace/loop-agent-command/src/api/bootstrap.ts#L38-L41)），共享池无法按会话换根（D4）。
- **`switchWorkspace` 退化为"指针刷新"**：不再 chdir、不再 reset 任何池；其他空间运行中的 run 完全不受影响（task-03/04）。
- **`process.chdir` 全量移除**，仅保留应用自身资源类的 `process.cwd()`（task-03 收口，task-06 断言）。

## 六、风险与注意事项

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| **漏改 cwd → 静默错位**（不报错，只在错误目录读写） | 数据写错项目（最严重） | task-02 的 ALS 兜底 + 启动期一致性断言（`currentWorkspaceRoot()` ≠ runtime.root → fail-fast）；task-03 逐条复核 33 处并加"应用资源/空间资源"分类注释；task-06 以 grep 断言收口 |
| `canonicalWorkspacePath` 改变 `workspaceId` 结果 | 存量会话"消失"（最坏丢数据） | **不改公式**（D2）：只保证同一物理目录经 canonical 后字符串一致；上线前用脚本比对 `<userDir>/sessions/*` 目录名与新 canonical 结果，不一致只告警不迁移 |
| 跨空间 `sessionId` 撞名 | 会话文件互相覆盖 | D5 命名空间；启动扫描重复 id 告警 + 手工处理指引 |
| 老格式 id 无空间段无法 O(1) 定位 | 跨空间查看老会话失败或错位 | task-04 维护进程内 `id → wsId` 映射缓存，miss 时回退全扫（D17） |
| 移除 chdir 后 MCP server 落在启动目录 | 工具根目录错位 | 按 **D19** 明确语义：MCP cwd 固定"配置值 ?? 启动目录"，不随空间切换；`/mcp` 响应与文档显式声明，纳入人工验证（task-02） |
| 记忆索引并发写 | L2/L3 索引损坏 | D8：kit 按 `workspaceId` 隔离（`memory-kit.ts` 现有能力）+ 每空间单例；同空间并发由 002-05 既有机制保证 |
| 内存/句柄随空间数增长 | 长跑进程膨胀 | D1 LRU（默认 4 个 runtime，空闲 30min 释放）+ D6 全局并发上限 |
| Windows 路径大小写 | 同一目录分裂或比较失败 | D2 用 `realpath` 取真实大小写；比较走词法不敏感 |
| ALS 上下文丢失（旧式 callback） | 深层读到错误根 | 显式优先原则：`ctx.workspaceRoot` 优先，ALS 仅兜底；`getStore()` 日志可定位 |
| CLI 与 serve 语义分叉 | 长期维护成本 | D11 CLI 保持单空间；两侧共享 `path-utils`；`*At` 类新增 API **不改造既有签名** |

## 七、全局工程约束

1. **零新依赖**：仅 `node:async_hooks`、`node:path`、`node:fs` 内置能力。
2. **跨平台**：路径归一/比较必须覆盖 win32 大小写与 POSIX；`realpath` 失败（目录不存在）回退 `resolve`。
3. **显式优先、不可变**：空间根经参数/上下文显式传递；`WorkspaceRuntime.root` 建立后不变更（对比现有 `rebindWorkspace` 原地改写）。
4. **失败可见**：宁可启动期断言崩溃，也不要运行时静默错位。
5. **可回退**：P0/P1 每步都能独立上线并保持现有行为；D1 的 LRU 与 D6 的全局上限都可 env 关闭。
6. **CLI 零改动红线**：`src/cli/**`、`src/commands/**` 不得出现 diff；任何需要 CLI 传参的改造方案一律否决（D13）。
7. 每个任务完成：打勾验收项 + 追加完成记录 + `npx tsc --noEmit` + `npx vitest run` 全绿 + 中文提交。

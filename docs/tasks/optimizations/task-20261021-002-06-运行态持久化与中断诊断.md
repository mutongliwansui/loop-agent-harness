## 一、任务目标需求

### 1.1 背景

RunHub 全在内存、终态保留 60s（[run-hub.ts:17,68](file:///d:/trae_workspace/loop-agent-command/src/api/run-hub.ts#L17)）：进程重启后 `GET /sessions/:id` 的 `run` 为 null，前端只能按"空闲"处理。用户看到的是重启前"跑了一半"的会话，但**没有任何提示说明发生了什么**（正常结束？被强杀？断电？）。本任务把 run 生命周期落盘，使重启后可识别"上次运行被中断"。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
|---|---|---|
| run 状态落盘 | 无（RunHub 内存 Map） | **新建 `run-journal.ts`：`<store.path>/runs/<id>.json`** |
| 中断判定 | 无依据（pid 存活探测会被 pid 复用误导） | **`bootId`（进程启动 UUID）≠ 当前 → interrupted** |
| 会话详情暴露 | `GET /sessions/:id` 已返回 `run: runs.snapshot(id)`（[sessions.ts:199-206](file:///d:/trae_workspace/loop-agent-command/src/api/handlers/sessions.ts#L199-L206)） | **并列新增 `lastRun`（磁盘态）** |
| 列表暴露 | `GET /workspaces` 返回 session 概要 | **每 session + `lastRun:{status,finishedAt}`** |
| 诊断日志 | `~/.loop-agent/logs/llm-YYYY-MM-DD.jsonl`（[llm-logger.ts:28](file:///d:/trae_workspace/loop-agent-command/src/llm-logger.ts#L28)） | **新建 `run-log.ts`：runs-YYYY-MM-DD.jsonl**（复用目录/按日切分风格，不改造 llm-logger） |
| 节流写盘参考 | 001 的 `persistSnapshot` 30s 节流（chat-stream 端为前端；服务端 onSnapshot 落会话） | journal 节流写独立实现（500ms 合并 + 终态即写） |
| 删除清理 | `DELETE /sessions/:id` 删 `<id>.json`/`<id>.enc` | **联动删 `runs/<id>.json`** |

### 1.3 任务目标

1. 新建 `src/api/run-journal.ts`：writeJournal（节流）/ readJournal / reconcileInterruptedOnBoot / dropJournal。
2. 新建 `src/api/run-log.ts`：run 生命周期 JSONL 诊断日志。
3. `bootstrap.ts`：启动时执行 `reconcileInterruptedOnBoot`（bootId 不符且 running → interrupted + 记日志）。
4. 端点扩展：`GET /sessions/:id` + `lastRun`；`GET /workspaces` 每 session + `lastRun` 概要。
5. 前端：会话详情按 `lastRun.status` 显示中断/停止注记；侧栏 `⚠` 标记。

### 1.4 设计约束

- 写盘 best-effort：全部失败静默（debug 日志），绝不阻塞 run 主链路。
- 零新依赖；路径基于 `store.path`（与会话文件同根，随会话清理）。
- 中断判定**不依赖** pid 存活探测（pid 复用误判；跨容器语义弱）。
- 前端注记为**前端态**渲染，不进消息数组（D3 已确认）。

## 二、方案设计

### 2.1 总体思路

```
服务启动（bootstrap）
  └─ currentBootId() = randomUUID()（进程内常量）
  └─ reconcileInterruptedOnBoot(store)：
       扫 runs/*.json：bootId ≠ 当前 且 status==='running'
         → 改写 status='interrupted', finishedAt=now
         → run-log.jsonl 记 'interrupted'

run 生命周期（task-03 基础上挂钩）
  ├─ runs.start 后        → writeJournal({status:'running', startedAt, pid, bootId})
  ├─ onSnapshot 节流同步   → writeJournal({lastSeq})（与会话落盘同频）
  └─ finish(id, status)   → writeJournal({status:'done'|'failed'|'aborted', finishedAt, iterations})
                            + runLog.write({event:'start'|'finish'|...})

前端（fetchDetail / 列表）
  ├─ lastRun.status==='interrupted' → 时间线尾注记「⚠ 上次运行被中断（服务已重启）」
  ├─ lastRun.status==='aborted'     → 「上次运行由用户停止」
  └─ 侧栏 interrupted → ⚠ 角标
```

### 2.2 关键设计决策

| 编号 | 决策 | 取舍与被否决项 |
|---|---|---|
| **D1** | 中断判定用 `bootId`（进程启动 UUID）+ `pid` 双因子 | 仅 pid：重启后 pid 复用 → `process.kill(pid,0)` 误判存活；bootId 不等即"非本进程所写"，必然中断。pid 仅诊断展示 |
| **D2** | journal 路径 `<store.path>/runs/<id>.json`（与会话文件同目录树） | 随会话删除/归档天然联动；集中日志目录只放跨会话的 runs-*.jsonl 诊断流 |
| **D3** | `lastSeq` 只节流同步不追求精确 | journal 的用途是"判中断 + 展示概要"，不是续传游标（断线续传走 RunHub 缓冲）；500ms 合并写足够 |
| **D4** | 中断注记放前端态（`SessionStreamState.note`），**不写进消息数组**（D3 已确认） | 消息数组会被 LLM 上下文/压缩/归档反复消费；注记属于"视图层解释"，每次 fetchDetail 都能重算 |
| **D5** | run-log 独立新文件（runs-*.jsonl），**不改造 llm-logger** | llm-logger 被 CLI/API 双路径共用且有轮转逻辑，动它影响面大；新文件仅 40 行且格式自定 |
| **D6** | `interrupted` 是 journal 独有状态，不加入 `RunStatus` | RunStatus 描述"本次进程内 run 的实时状态"，interrupted 只可能由启动扫描写入，二者命名空间分离 |
| **D7** | workspaces 列表只暴露 `{status, finishedAt}` 两个字段 | 列表 payload 控制体量；完整 journal 由详情端点提供 |

## 三、任务详细设计

### 3.1 `run-journal.ts`（新建）

```ts
export type RunJournalStatus = 'running' | 'done' | 'failed' | 'aborted' | 'interrupted';

export interface RunJournal {
  runId: string;
  sessionId: string;
  status: RunJournalStatus;
  startedAt: number;
  finishedAt?: number;
  pid: number;
  bootId: string;
  lastSeq?: number;
  iterations?: number;
}

export function currentBootId(): string;   // 进程内常量 randomUUID()
export async function writeJournal(store: SessionStore, id: string, patch: Partial<RunJournal>): Promise<void>;
export async function readJournal(store: SessionStore, id: string): Promise<RunJournal | null>;
export async function reconcileInterruptedOnBoot(store: SessionStore): Promise<number>;
export async function dropJournal(store: SessionStore, id: string): Promise<void>;
```

- `writeJournal`：读-合并-写；`lastSeq` 类补丁 500ms 合并（内存 pending Map + 定时 flush），终态类补丁（status 变更）立即写。
- `reconcileInterruptedOnBoot`：遍历 `runs/*.json`，`status==='running' && bootId!==currentBootId()` → 改写 interrupted；返回处理条数。
- 所有 IO try/catch 静默。

### 3.2 `run-log.ts`（新建，约 40 行）

```ts
// ~/.loop-agent/logs/runs-YYYY-MM-DD.jsonl（按日切分，同 llm-logger 风格）
// 每行：{ ts, sessionId, runId, event:'start'|'finish'|'abort'|'interrupted'|'failed', durationMs?, iterations?, status }
export function writeRunLog(entry: RunLogEntry): void;
```

### 3.3 挂钩点

| 挂钩点 | 文件 | 内容 |
|---|---|---|
| 启动扫描 | `bootstrap.ts` | `reconcileInterruptedOnBoot(store)`（fire-and-forget，不阻塞启动） |
| run 开始 | `handlers/messages.ts`（start 后） | `writeJournal(store, id, {runId, status:'running', startedAt, pid, bootId})` + `writeRunLog({event:'start'})` |
| 快照同步 | `handlers/messages.ts` 的 onSnapshot 回调 | `writeJournal(store, id, {lastSeq})`（节流由 journal 内部处理） |
| run 终态 | `handlers/messages.ts` 的 finish 前后 | `writeJournal(status, finishedAt, iterations)` + `writeRunLog({event: status==='aborted'?'abort':'finish'})` |
| 删除会话 | `handlers/sessions.ts` DELETE | `dropJournal(store, id)` |

### 3.4 端点扩展（`handlers/sessions.ts`）

- `GET /sessions/:id`：响应根级 + `lastRun: await readJournal(store, id)`。
- `GET /workspaces`：每 session + `lastRun: jr ? { status: jr.status, finishedAt: jr.finishedAt } : null`。

### 3.5 前端（`chat-stream.ts` / `ChatView.vue` / `App.vue`）

- `fetchDetail` 读取 `lastRun`：
  - `interrupted` → `st.note = '⚠ 上次运行被中断（服务已重启），以上为已保存的部分输出'`；
  - `aborted` → `st.note = '上次运行由用户停止'`（不弹 toast，仅注记）；
  - 其余 → `st.note = undefined`。
- `ChatView` 消息列表尾部渲染 `st.note` 灰条（与 aborted 灰条同容器样式）。
- `App.vue` 侧栏：`s.lastRun?.status === 'interrupted'` → 会话名后 `⚠`（title 提示）。需列表接口字段透传到前端 session 类型。

### 3.6 边界与错误处理

| 场景 | 行为 |
|---|---|
| journal 文件损坏（半行 JSON） | readJournal 返回 null，按无记录处理；下次 writeJournal 覆盖重建 |
| 强杀发生在 journal 首写之前 | 无 running 记录 → 无中断提示（可接受：run 未实际开始产出） |
| 会话归档/加密切换 | journal 路径固定明文 `<id>.json`，与 `<id>.enc` 并存不冲突 |
| 用户手删 runs/ 目录 | 全部降级为"无 lastRun"，功能退化但不报错 |
| 多次重启叠加 interrupted | 每次启动扫描都会收敛为终态，不叠加 |

### 3.7 演进项（本任务不做）

- run 断点续跑（从 lastSeq 重新生成）——需 LLM 侧快照，范围大。
- journal 压缩/清理策略（单文件 <1KB，量级无需）。

## 一、任务目标需求

### 1.1 背景

task-01 打通了 signal 通道，但 ReAct 主循环（[react-agent.ts](file:///d:/trae_workspace/loop-agent-command/src/agent/react-agent.ts) `run()` 约 :478 起）尚未消费它：即使 LLM/工具层都能取消，主循环仍会在收到 partial 结果后**继续下一轮迭代**、触发压缩、写入记忆——用户感知是"点了停止还在跑"。本任务把取消检查点织入循环，并把已产生的部分结果以 `AgentAbortedError(partial)` 抛出。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
|---|---|---|
| 迭代间取消 | `run()` 主循环无中断出口 | **需 C1 检查点** |
| LLM 调用前取消 | `streamLLM` 直接调用 | **需 C2** |
| 工具执行前取消 | `callItems` 组装后进 `runner.runParallel`（约 :743-759） | **需 C3（最长耗时环节，"停得下来"的关键）** |
| 压缩期取消 | `planCompaction` + `preCompactionFlush`（额外 LLM 调用，约 :509-620） | **需 C4：压缩前后都判** |
| 记忆写入前取消 | 最终回答写 L2（约 :709）、工具结果写 L2（约 :783） | **需 C5：不产生半条记忆** |
| 部分结果收集 | `messages` / `transcript` / `steps` / 迭代计数都在 `run()` 作用域内 | 抛错时**快照打包进 `AgentAbortedError.partial`** |
| 恢复兜底 | `repairMessageSequence`（[memory/context.ts:35](file:///d:/trae_workspace/loop-agent-command/src/memory/context.ts#L35)）只在 restoreSession 路径调用 | **不依赖它做取消封口**（见 task-03 的 `sealPendingToolCalls`，二者互补） |

### 1.3 任务目标

1. `run()` 内建立 `throwIfAborted(iteration)` 检查点函数，织入五类位置（C1~C5）。
2. 触发时抛 `AgentAbortedError`，partial 携带当时的 `messages/transcript/steps/iterations` 快照。
3. task-01 的 `runner.run` / `chatStream` 抛出的"空 partial"中止错误，在此层统一**换绑为完整 partial**后再向外抛。
4. 压缩路径被取消时，事件层发出 `{failed:true, fallback:'aborted'}` 的 `compaction` 终止事件（前端据此撤 loading）。

### 1.4 设计约束

- 不传 signal 时主循环行为零变化（检查点函数在 `signal?.aborted` 为假时立即返回）。
- 不改动事件语义：既有 `AgentEvents` 钩子时机/参数不变；`compaction` 失败载荷新增 `fallback:'aborted'` 是加法。
- 检查点必须**同步判定**（`signal.aborted` 读属性），不引入额外异步等待。

## 二、方案设计

### 2.1 总体思路

```
run(input, options{signal})
  ├─ const state = { messages, transcript, steps, iterations }   ← 循环内持续演进
  ├─ throwIfAborted(i)：
  │     signal.aborted → throw new AgentAbortedError(snap(state, i))
  │
  ├─ C1 每轮迭代入口 ───────────── 阻止"下一轮"启动
  ├─ C2 streamLLM 前 ──────────── 避免空转一次请求
  ├─ C3 runner.runParallel 前 ─── 不再启动新工具（关键：最长耗时）
  ├─ C4 planCompaction 判定后 / preCompactionFlush 前后 ─ 压缩期不空转
  └─ C5 记忆写入（L2）前 ──────── 不产生半条记忆
        │
        └─ catch 内层（task-01 抛来的空 partial 中止错误）
              └─ 换绑 snap(state) 后重新抛出 → 交 API 层（task-03）落盘
```

### 2.2 关键设计决策

| 编号 | 决策 | 取舍与被否决项 |
|---|---|---|
| **D1** | 检查点**不新增事件钩子**（不加 `onAbort`） | 取消是终态不是过程态，SSE 层的 `aborted` 终态由 API 层发布即可；新增钩子会扩大 `AgentEvents` 面且 CLI 永远不会用 |
| **D2** | partial 快照用**浅拷贝**（`[...messages]`）而非深拷贝 | 中止后无人再改这些数组（run 已退出）；深拷贝在大 transcript 下成本高且无必要 |
| **D3** | 内层 catch 换绑策略：识别 `(e as {aborted?:boolean}).aborted === true` | task-01 的 `runner`/`chatStream` 无法构造 partial（ToolRunner 不掌握上下文），由唯一掌握完整状态的 `run()` 统一补全 |
| **D4** | C4 压缩取消时发 `compaction` 事件 `{failed:true, fallback:'aborted'}` 而非静默 | 前端 `compaction_start` 已置 loading（chat-stream.ts:415），必须配对终止事件才能撤掉；复用既有事件通道，前端零新逻辑即可消费 |
| **D5** | 工具已在跑、raceAbort 先返回时：**等待**在跑工具自然结束（Promise 不悬挂）再抛错 | `runParallel` 已 await；放弃等待会留下游离 Promise 与潜在写文件半态；工具结果照常产生但被丢弃 |
| **D6** | C5 记忆写前取消：跳过记忆写入但**不回滚已写的** | 记忆写入是逐条独立提交；"半条记忆"风险点在写入中途，写前判定已足够；回滚机制不存在且不值得为取消新建 |

## 三、任务详细设计

### 3.1 检查点函数（`run()` 内）

```ts
const signal = options.signal;
const throwIfAborted = (iteration: number): void => {
  if (!signal?.aborted) return;
  throw new AgentAbortedError({
    messages: [...messages],
    transcript: [...transcript],
    steps: [...steps],
    iterations: iteration,
  });
};
```

### 3.2 检查点落位

| 检查点 | 位置（react-agent.ts 现行号） | 说明 |
|---|---|---|
| C1 | 主循环 `for (let i = 0; ...)` 体首行（:478 后） | 阻止下一轮 |
| C2 | `streamLLM` 调用前（:654 上方） | 避免空转请求 |
| C3 | `callItems` 组装后、`runner.runParallel` 前（:743-759） | 不再启动新工具 |
| C4 | `planCompaction` 判定后、`preCompactionFlush` 调用前后（:509-620） | 压缩是额外 LLM 调用，最易"停不下来" |
| C5 | 最终回答写 L2 前（:709）、工具结果写 L2 前（:783） | 不产生半条记忆 |

> 行号为方案编写时的快照，实施时以语义定位为准。

### 3.3 内层换绑（`run()` 的 catch）

```ts
try {
  // ...主循环
} catch (e) {
  if ((e as { aborted?: boolean }).aborted === true && !(e as AgentAbortedError).partial?.messages.length) {
    // task-01 层抛来的空 partial：换绑完整快照
    throw new AgentAbortedError({ messages: [...messages], transcript: [...transcript], steps: [...steps], iterations });
  }
  throw e;
}
```

> 语义：若 partial 已有内容（理论上是 C1~C5 直接抛的），原样上抛，不二次构造。

### 3.4 压缩取消的事件配对

`preCompactionFlush` / 压缩调用处用 try/catch 包裹：

```ts
try { /* 压缩流程 */ }
catch (e) {
  if ((e as { aborted?: boolean }).aborted === true) {
    events.onCompaction?.({ failed: true, fallback: 'aborted' });  // 撤前端 loading
  }
  throw e;  // 继续向上抛，由换绑逻辑处理
}
```

前端现状（chat-stream.ts `case 'compaction'`）已能消费 `{failed, fallback}`，`fallback==='aborted'` 时 toast 文案按"已停止"处理（该 UI 微调归 task-04）。

### 3.5 边界与错误处理

| 场景 | 行为 |
|---|---|
| abort 与最后一轮 done 竞争 | 谁先判定谁生效：`throwIfAborted` 在 done 返回后的 C5 处仍会触发 → 中止生效（部分结果即完整结果，落盘无害） |
| 并行多工具，其一已完成 | 已完成结果在 `steps` 中保留；未完成的被 raceAbort 打断，结果丢弃 |
| abort 发生在 `onSnapshot` 回调期间 | 回调本身不判 abort（写盘是 best-effort），下一次检查点拦截 |
| signal 在 run 结束后才 abort | 无影响：检查点不再执行；RunHub 对非 running 返回 null（task-03 保证） |

### 3.6 演进项（本任务不做）

- CLI 模式的 Ctrl+C 中断映射（CLI 有自己的 Ctrl+C 退出语义，不在本批次范围）。
- 检查点粒度配置（如"仅工具前检查"），YAGNI。

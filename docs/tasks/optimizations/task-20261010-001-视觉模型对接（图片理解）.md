## 一、任务目标需求

### 1.1 背景

当前 Agent 仅支持纯文本对话：`ChatMessage` 的 user content 为 `string`（[types.ts:48-52](file:///d:/trae_workspace/loop-agent-command/src/types.ts#L48-L52)），无任何图片输入通道。用户给出截图/图片路径时，Agent 只能当作一段字符串处理，无法理解像素内容。

### 1.2 现状梳理（框架契合度）

参考"Function Call 直连版"设计思路，与现有框架对照后确认**大量基础设施可零成本复用**：

| 方案需要的能力 | 当前框架现状 | 结论 |
|---|---|---|
| 工具定义与注册 | `Tool` 接口 + `ToolRegistry`（[registry.ts](file:///d:/trae_workspace/loop-agent-command/src/tools/registry.ts)） | 直接复用 |
| 错误回填不中断循环 | `ToolRunner.run()` 异常转 `工具执行失败: xxx` 字符串（[runner.ts:39-44](file:///d:/trae_workspace/loop-agent-command/src/tools/runner.ts#L39-L44)） | 直接复用 |
| 多 tool_calls 并行 | 主循环 `Promise.all`（[react-agent.ts:585-608](file:///d:/trae_workspace/loop-agent-command/src/agent/react-agent.ts#L585-L608)） | 直接复用 |
| 长耗时可见性 | 每 1s `onToolProgress` 心跳 + Spinner（20260930-001 已落地） | 直接复用 |
| 单次任务调用上限 | `model.maxIterations` | 直接复用 |
| 参数校验 | 主循环按 `parameters.required` 检查缺失（[react-agent.ts:589-593](file:///d:/trae_workspace/loop-agent-command/src/agent/react-agent.ts#L589-L593)） | 直接复用 |
| 配置分层 | `deepMerge` 五层合并 + `/config set` 点分路径写入无白名单（[config-command.ts:80-81](file:///d:/trae_workspace/loop-agent-command/src/commands/config-command.ts#L80-L81)） | 新增 `vision` 组即可 |
| 可观测性 | `llmLogger.request/response` + `debug.toolCall` | 直接复用 |

**关键结论**：

1. **不改 `ChatMessage` 类型**——主模型永不接收像素，图片以字符串（路径/URL/data URI）形式出现在消息文本中。记忆系统（L1 `estimateTokens`/`compact`）、会话加密持久化**零改动**。
2. **参考方案的"本地调度器"无需新建**——就是现有的 `ToolRegistry + ToolRunner + ReAct 主循环`。视觉对接的形态是 **4 个内置 `Tool`，各自 `execute()` 内调用视觉 API**。
3. 唯一框架级扩展点：`Tool` 增加 `timeoutMs?`（视觉调用建议 60s，超出 runner 默认 30s）。

### 1.3 任务目标

- 用户在消息中给出图片（本地路径 / http URL / data URI），Agent 可调用视觉工具看图并基于结果继续推理。
- 4 个工具覆盖主场景：`describe_image`（整体描述）、`ask_image`（定向提问，主力）、`extract_json`（结构化提取）、`ocr_image`（文字识别）。
- 视觉服务三元组（baseUrl/apiKey/model）独立配置，空值回退主模型；`vision.enabled` 默认 `false`，关闭时主模型 tools 列表与现状**字节一致**（保住前缀缓存）。
- 错误全部回填为 tool 结果，Agent 不中断；视觉输出统一截断防上下文膨胀；同图同参重复调用走缓存。
- **零新依赖**：沿用 `openai` SDK 与 Node 内置模块；不新增服务进程、不引入 MCP 层。

### 1.4 设计约束

- **消息结构不变**：user content 保持 string；base64 图片只在 VisionClient 内部出现，绝不回填。
- **主循环零改动**：不修改 react-agent.ts 的执行/回填/心跳逻辑（runner 超时扩展在 runner 内部完成）。
- **向后兼容**：`vision.enabled=false`（默认）时行为与现状完全一致。
- **前缀缓存友好**：工具列表按名排序 + canonicalize 的既有机制不破坏；系统提示词视觉段仅在启用时注入。
- **可独立验证**：分 P0/P1/P2 落地，每阶段可单独验收；单元测试全部 mock 视觉 API，不依赖真实服务商。

## 二、方案设计

### 2.1 总体思路

```
用户输入（含图片路径/URL，以文本形式）
        │
        ▼
┌─────────────────────┐
│   主文本模型         │  ← registry.toOpenAITools()（含 4 个视觉工具定义）
│  (Function Call)     │
└─────────┬───────────┘
          │ 返回 tool_calls
          ▼
┌─────────────────────────────────────────┐
│   现有 ReAct 主循环 + ToolRunner          │
│   （校验参数 → Promise.all 并发 → 回填）  │
└─────────┬───────────────────────────────┘
          │ 按函数名路由（registry.get(name).execute(args)）
          ▼
┌─────────────────────────────────────────┐
│  src/tools/vision/                       │
│  image.ts 解析图片 → cache.ts 查缓存      │
│  → llm.chatVision() 调视觉 API           │  ← OpenAI 兼容协议（独立三元组配置）
└─────────┬───────────────────────────────┘
          │ 返回文本/JSON（截断后）
          ▼
   结果作为 tool 消息回填（tool_call_id）→ 主模型继续推理
```

角色划分：主模型负责"想"（不看图）、本地调度负责编排（= 现有主循环，不看图）、视觉模型负责"看"（不决策）。

### 2.2 关键设计决策

1. **D1 图片不进消息结构**：`ChatMessage` 保持 string content。视觉请求的多模态 content 数组只在 `chatVision()` 内部临时构造，不进历史、不进持久化。
2. **D2 视觉能力 = 4 个内置 Tool**：完全复用注册/执行/校验/心跳/Tab 补全/`/tools enable` 管控，无新增协议层。
3. **D3 `vision.enabled` 默认 false**：不注册工具 → tools 列表字节一致 → DeepSeek 等模型前缀缓存不受影响。
4. **D4 视觉三元组独立配置 + 空值回退**：`vision.baseUrl/apiKey/model` 为空时回退 `model.*`。同服务商多模型零重复配置；跨服务商（主 DeepSeek + 视觉 GLM-4V/Qwen-VL）也可独立。
5. **D5 `Tool.timeoutMs?`**：runner 超时优先级改为 `options.timeout ?? tool.timeoutMs ?? 30000`，主循环调用点不变。
6. **D6 结果缓存按"模型+工具种类+参数+图片指纹"**：本地文件指纹 = mtime+size（内容变缓存自动失效），URL 直接用字符串。LRU 20 条 + TTL。
7. **D7 结果统一截断 `maxResultChars`（默认 8000）**：长 describe 是上下文膨胀主源，在工具内部截断，runner 保持通用。
8. **D8 `extract_json` 用 prompt 强约束 + 解析容错**：不依赖 `response_format`（部分服务商不支持）；`chatVision` 首次带 JSON 模式失败自动降级重试一次。

### 3.1 配置组 `VisionConfig`（P0）

[schema.ts](file:///d:/trae_workspace/loop-agent-command/src/config/schema.ts)：

```typescript
export interface VisionConfig {
  enabled: boolean;        // 默认 false
  baseUrl: string;         // 默认 '' → 回退 model.baseUrl
  apiKey: string;          // 默认 '' → 回退 model.apiKey
  model: string;           // 默认 '' → 回退 model.name
  temperature: number;     // 默认 0
  maxTokens: number;       // 默认 2048
  timeoutMs: number;       // 默认 60000
  maxImageBytes: number;   // 默认 10 * 1024 * 1024
  maxResultChars: number;  // 默认 8000
  cacheEnabled: boolean;   // 默认 true（P1 生效）

```

- `AgentConfig` 增加 `vision: VisionConfig`；`PartialAgentConfig` 增加 `vision?: Partial<VisionConfig>`；`DEFAULT_CONFIG` 补默认值。
- [loader.ts](file:///d:/trae_workspace/loop-agent-command/src/config/loader.ts) `envFrom` 增加：`VISION_API_KEY`（→ vision.apiKey，并视为 enabled=true）、`VISION_BASE_URL`、`VISION_MODEL`（同前）。

### 3.3 `llm.chatVision()`（P0）

[client.ts](file:///d:/trae_workspace/loop-agent-command/src/llm/client.ts)：

- 新增独立视觉客户端缓存字段（`visionClient` + `_lastVisionKey/_lastVisionUrl`），模式与主 `getClient()` 一致，配置变化时重建。
- `chatVision(messages, options)`：非流式（视觉调用无需流式）；`jsonMode=true` 时首次带 `response_format: { type: 'json_object' }`，若 400/不支持则自动降级重试一次（仅一次）。
- 复用 `retry()`（网络/429/5xx）与 `wrapError()`；照常走 `beginLLMCall` + `llmLogger.request/response`（model 字段即视觉模型名，日志天然可区分）。
- 返回 `{ content, usage, elapsedMs }`。
- 多模态 content 数组（`{ type:'text'|'image_url' }[]`）仅在构造请求参数时使用，SDK 类型转换就地完成。

### 3.4 图片解析模块 `src/tools/vision/image.ts`（P0）

```typescript
export interface ResolvedImage {
  uri: string;            // 发给视觉 API 的 image_url 值（URL 或 data URI）
  source: 'url' | 'data' | 'file';
  bytes: number;
  fileFingerprint?: string; // mtime+size，缓存 key 用；URL 场景 undefined
}

export async function resolveImage(raw: string, maxBytes: number): Promise<ResolvedImage>
```

| 输入形态 | 处理 |
|---|---|
| `http(s)://` | 透传 URL（由视觉服务端下载，本地不发起任意请求） |
| `data:image/...;base64,...` | 直接透传 |
| 其他（视为本地路径） | 存在性检查 → 扩展名 → MIME（png/jpg/jpeg/webp/gif/bmp）→ readFile → 大小校验 → 转 data URI |

分类错误消息（throw，由 runner 转回填）：`图片文件不存在: <path>`、`不支持的图片格式: <ext>（支持 png/jpg/jpeg/webp/gif/bmp）`、`图片超过大小限制: <size> > <maxBytes>`。

### 3.5 四个视觉工具 `src/tools/vision/tools.ts`（P0）

| 工具名 | 用途 | 必填参数 | 超时 |
|---|---|---|---|
| `describe_image` | 整体描述（兜底） | `image` | 60s |
| `ask_image` | 定向提问（主力） | `image`, `question` | 60s |
| `extract_json` | 结构化提取 | `image`, `fields`(string[]) | 60s |
| `ocr_image` | 纯文字识别 | `image` | 60s |

- 描述写"什么时候用"（主模型靠 description 选择），如 ask_image：「针对图片回答一个具体问题…已明确要看什么时优先用它，不确定时用 describe_image」。
- 共享执行管道（文件内私有函数）：读 `cfg.vision`（未启用 throw 明确提示）→ `resolveImage` → 查缓存（P1）→ `llm.chatVision()` → 解析容错 → 截断 → 写缓存（P1）→ 返回。
- `extract_json` 容错：剥离 ```` ```json ```` 围栏与前后缀文本 → `JSON.parse` → 失败**不 throw**，降级返回 `注意：视觉模型输出不是合法 JSON，以下为原始文本：\n<原文>`。
- 截断：超 `maxResultChars` 截断并追加 `\n…（已截断，原文共 N 字符）`。
- prompt 模板：describe =「客观详尽描述…」；ask = question 原文；extract =「只输出 JSON 对象，找不到填 null，不要解释或围栏」；ocr =「提取全部文字保持换行，只输出文字」。
- 导出 `VISION_TOOL_NAMES` 供注册与补全复用。

### 3.10 边界与错误处理

| 场景 | 处理 | 主模型收到的信息 |
|---|---|---|
| 视觉超时 60s | runner withTimeout | `工具执行超时 (60000ms)`，可换 ask_image 缩小问题 |
| 限流/5xx | chatVision 复用 retry 两次 → 工具 throw | `视觉模型调用失败(429): …` |
| extract_json 输出非法 | 工具内降级不 throw | 原始文本 + 降级说明 |
| 图片不存在/超限/格式错 | resolveImage 分类 throw | 分类错误消息（含路径与支持格式） |
| vision 未启用 | 工具 throw | `视觉功能未启用，请先 /config set vision.enabled true 并配置 vision.model` |
| 参数缺失 | 主循环现有校验 | 现有 `缺少必需参数` 消息 |

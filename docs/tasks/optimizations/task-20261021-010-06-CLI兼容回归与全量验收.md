## 一、任务目标需求

### 1.1 背景

本需求是**纯内部重构**，产品可见收益只有一个（跨空间并行），但风险面覆盖几乎所有模块。CLI 与 HTTP 服务共享 4 个进程级单例（`configLoader`、`configWriter`、`skillLoader`、`agent`，见 [runtime/init.ts:8-12](file:///d:/trae_workspace/loop-agent-command/src/runtime/init.ts#L8-L12)）——任何"为 serve 按空间实例化"的改动都可能顺手改到 CLI 路径。因此 **CLI 零回退不是"顺便验一下"，而是 P1 的出口闸门**：不通过就不许进入 task-05/07。

### 1.2 现状梳理

| 验收对象 | 依据 | 现状 |
|---|---|---|
| CLI 入口 | `src/cli/**`、`src/commands/**` 与 serve 分支解耦（[index.ts](file:///d:/trae_workspace/loop-agent-command/src/index.ts) → `initRuntime` → 二选一） | 无 `--serve` 时不加载 `api/*`、`agent-pool` |

## 二、方案设计

### 2.1 总体思路

```
① 静态断言（快，先跑）
   - grep process.chdir            → 必须 0
   - grep process.cwd()            → 白名单比对（29+4 分类）
   - git diff --stat src/cli src/commands → 必须为空
                    │
② 单测补强（VM 级）
   - scan(root) vs scan(cwd) 双语义
   - canonical 三种书写 → 同一 workspaceId
   - 同秒两空间 id 唯一性
                    │
③ 全量回归
   - npx tsc --noEmit
   - npx vitest run（串行）
                    │
④ 人工冒烟（真实进程）
   - CLI 七项 + serve 两空间并行（A1/A2/A3）
```

### 2.2 关键设计决策

| 编号 | 决策 | 取舍与被否决项 |
|---|---|---|
| **D13** | CLI 兼容策略 **additive 只增不改**：为新需求新增可选参数/方法，`CommandContext` 与既有方法签名一律不动 | 让 CLI 也传 root：触发 `src/commands/**` 大面积 diff，违反 A7.1，且 CLI 单空间无收益 |
| **D11** | CLI 仍是"启动目录 = 唯一空间"，**不引入 registry** | CLI 也走 registry：内存/句柄开销与启动复杂度上升，用户无感知 |
| **D16** | cwd 白名单口径以 **29 空间资源 + 4 应用资源/默认值 + 8 CLI 保留** 为准（合计 41 处，含 2 处 sqlite 已改 `import.meta.url`） | 以方案原"33 处全改"为准：会把 `static.ts`/`.env`/sqlite 定位改坏 |

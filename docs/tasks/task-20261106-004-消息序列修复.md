## 一、任务目标需求

### 1.1 背景（痛点）

多轮对话中上游偶发 400：`An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'`。复现轨迹具有两个共同特征：

1. **`tool_call_id` 被跨轮次复用**（上游 / 响应缓存对同一段轨迹复用同一批 id，例如反复点「继续」时）。
2. **历史段存在只有 `tool_calls`、没有对应 `tool` 消息的 assistant**。

旧实现 [context.ts](../../src/memory/context.ts) 的 `repairMessageSequence` 用**全局** `tool_call_id → assistant 索引` 映射判断某条 tool 是否合法，隐含假设 id 全局唯一。id 复用时，后出现的 assistant 覆盖映射，导致较早那组的 tool 被判为孤儿删除，而该 assistant 的 `tool_calls` 又被后面的 tool 响应「兜住」保留 → 产出的正是报错中的非法序列。

同类问题还出现在取消链路：[abort-utils.ts](../../src/agent/abort-utils.ts) 的 `sealPendingToolCalls` 把合成 tool 消息**一律追加到数组末尾**，当被中断的 assistant 后面还有消息（用户紧接着发了新问题）时，合成 tool 不紧邻其 assistant，仍然非法。

### 1.2 现状梳理

| 所需能力 | 现状 | 结论 |
| --- | --- | --- |
| 历史消息序列修复 | `repairMessageSequence` 全局 id 映射，依赖 id 全局唯一 | **假设不成立，需重写为按顺序配对** |
| 中止落盘序列封口 | `sealPendingToolCalls` 合成 tool 追加到数组末尾 | **不满足「紧邻 assistant」协议要求，需改作用域补齐** |
| 请求前序列审计 | 无，400 只能靠上游报错反推 | **缺失，需新增只读审计留痕** |
| 「补而非删」口径 | D3（Task-20261021-002-03）已确立 | 保持 |
| 正常（合法）序列 | 两条修复路径都不应改写 | 保持（返回原数组引用） |

### 1.3 任务目标

1. `repairMessageSequence` 改为**一次线性扫描、按顺序配对**：只有紧邻待响应 assistant 的 tool 才归属它，按 id 逐个消费；无归属 tool 丢弃；组内缺失响应原地补合成 tool。
2. `sealPendingToolCalls` 改为**按当前 assistant 作用域**补齐：合成 tool 插在该 assistant 的 tool 区之后、下一条非 tool 消息之前。
3. 新增 `auditToolSequence`（只读）并在发起 LLM 请求前留痕，合法序列零输出、非法序列给出具体下标。
4. 合法序列不改写（返回原数组引用），不影响正常链路性能。

### 1.4 设计约束

- 纯函数、零新依赖（仅 `node:` 内置与既有类型）。
- 审计是旁路：**只记 debug，不影响本次 LLM 调用**，更不能抛错打断对话。
- 不改 OpenAI 协议语义、不改 tool_calls 内容与工具执行链路。
- 跨平台一致，不引入平台相关逻辑。

## 二、方案设计

### 2.1 总体思路

```
正常路径
  messages ──repairMessageSequence（按序配对 / 补合成 tool）──▶ llmMessages
                                                              │
                                        auditToolSequence（只读）──▶ debug 留痕（非空才记）
                                                              ▼
                                                            LLM

取消路径
  partial.messages ──sealPendingToolCalls（按当前 assistant 作用域补齐）──▶ 落盘
                                                              │
                                              下一次 restore 仍过 repairMessageSequence
```

### 2.2 关键设计决策

| 编号 | 决策 | 取舍 / 被否决项 |
| --- | --- | --- |
| D1 | **按顺序配对**：维护「当前待响应的 assistant」，只有紧邻其后的 tool 才归属它，按 id 逐个消费 | 否决**继续用全局 id 映射**：id 全局唯一这个前提在上游/缓存复用场景下不成立，正是本次故障根因 |
| D2 | **合成 tool「补而非删」**，保留 assistant 的 `tool_calls` 不被裁掉 | 否决**删掉未响应的 tool_call**：会丢失「当时确实发起过该工具」的事实，且改动模型可见历史 |
| D3 | **两条路径职责分离**：`sealPendingToolCalls` 只补当前 assistant 缺失项，不归属当前组的 tool 原样保留；`repairMessageSequence` 负责丢弃无归属 tool | 否决**两处都做全量修复**：双策略叠加容易互相抵消，难以定位 |
| D4 | **审计只读、仅 debug 留痕**，异常不抛错、不自动修复 | 否决**审计时自动改消息**：会在主链路之外二次改写，故障更难复现 |
| D5 | **合法序列返回原数组引用**（不复制） | 否决**无条件重建数组**：每轮多一次全量拷贝，且丢失调用方引用比较能力 |

### 2.3 参考与已知坑

本次未做外部检索，结论来自线上报错形态与代码事实。可借鉴的通用原则：

- **协议校验按局部作用域而非全局标识**：流式协议中「紧邻」是结构约束，不能退化为全局 id 集合查询。
- **修复函数与审计函数分离**：修复负责收敛，审计负责观测；审计一旦具备副作用就无法作为回归信号。
- **本项目已知坑**：
  1. `ReactAgent` 的历史视图会混入 L1 摘要占位、通知消息等非工具消息，任何「按全局 id 聚合」的实现都会与这些插入消息冲突，必须按邻接关系判断。
  2. 取消落盘发生在 run 任意迭代，partial 尾部可能形如 `assistant(tool_calls=[A,B]) + tool(→A)`，补齐必须发生在该组 tool 区之后。

## 三、任务详细设计

### 3.1 `src/memory/context.ts`

```ts
/** 合成 tool 消息内容（与取消链路口径一致，便于前端识别） */
export const SYNTHETIC_TOOL_RESULT_TEXT = '（该工具调用未返回结果，已由消息序列修复补齐）';

/** 按顺序配对修复：紧邻 tool 才归属当前 assistant；缺失补合成 tool；无归属 tool 丢弃 */
export function repairMessageSequence(messages: ChatMessage[]): ChatMessage[];

/** 只读审计：返回问题描述数组（空数组 = 合法），不修改入参 */
export function auditToolSequence(messages: ChatMessage[]): string[];
```

边界与行为：

| 场景 | 行为 |
| --- | --- |
| 一组内只有部分响应 | 在该组 tool 区结束处补合成 tool（`SYNTHETIC_TOOL_RESULT_TEXT`） |
| 纯孤立 tool（前面无 `tool_calls`） | 丢弃 |
| 跨轮次复用同一 id | 两组各自独立配对，互不覆盖 |
| 合法序列 | 返回**原数组引用**（`changed=false`） |
| 空数组 | 原样返回 |

### 3.2 `src/agent/abort-utils.ts`

`sealPendingToolCalls` 的补齐时机从「末尾统一 flush」改为「作用域 flush」：

- 遇到新的 `assistant(tool_calls)` 或任何非 tool 消息 → 先 flush 上一组缺失项；
- tool 消息只在当前组的 `pendingIds` 中按 id 消费（同 id 重复时各自计数）；
- 不归属当前组的 tool 原样保留，交给 `repairMessageSequence`。

### 3.3 `src/agent/react-agent.ts`

在 `streamLLM` 发起前调用审计，仅 debug 留痕（最多展示 5 条，其余折叠计数），不影响调用。

### 3.4 `src/memory/index.ts`

导出 `auditToolSequence`，供 agent 层引用（与 `repairMessageSequence` 同级）。

### 3.5 演进项（本任务不做）

- 修复逻辑独立成协议中间件，按 provider 差异化（本任务不引入 provider 分支）。
- 审计结果上报 metrics / SSE（当前只落 debug 日志）。

## 一、任务目标需求

### 1.1 背景（痛点）

`commandRun({background:true})` 把子进程输出直接重定向到 `~/.loop-agent/runs/{taskId}.log`。旧实现 `pruneStaleRuns()` 只在启动时删除超过 24h 的 `.json`，**从不删除 `.log`**：元数据没了、日志还在，`runs/` 目录只增不减（本机曾观测 13374 个文件）。长期运行 `--serve` 时进程不重启，清理甚至一次都不会发生。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
| --- | --- | --- |
| 日志落盘位置 | [commandRun.ts](../../../src/tools/commandRun.ts) `runInBackground()` 用 `openSync(logPath,'w')` 作为子进程 stdout/stderr | 复用，不改落盘方式 |
| 历史清理入口 | [init.ts](../../../src/runtime/init.ts) 启动时调用 `pruneStaleRuns()`（已删除） | 替换为 `pruneRuns()`，并支持运行期触发 |
| 任务状态真源 | [background-tasks.ts](../../../src/tools/background-tasks.ts) `BackgroundTaskRegistry.tasks`（内存 Map）与 `.json` 快照 | 清理必须跳过内存中的活跃任务 |
| 配置体系 | [schema.ts](../../../src/config/schema.ts) `ToolsConfig` 已有 `mcpTranslate` 先例 | 新增 `tools.backgroundLog`，默认开启 |
| 单测基线 | [command-background.test.ts](../../../tests/command-background.test.ts) 覆盖启动/状态/停止；无清理用例 | 新增独立清理用例文件 |

### 1.3 任务目标

1. 启动时清理一次；每次后台任务启动前再清理一次（长驻服务也能收敛）。
2. **按天数**：已结束任务的 `.json` + `.log` 超过 `retentionDays`（默认 7 天）成对删除。
3. **按天数**：无主 `.log`（对应 `.json` 已不存在）超过保留期同样删除。
4. **按大小**：`runs/` 中 `.log` 总量超过 `maxTotalMb`（默认 100MB）时，按 mtime 从旧删起，直到低于上限。
5. 内存中仍活跃（`this.tasks`）的任务永不删除；损坏 JSON 与超过 1h 的 `orphaned-running` 沿用旧口径彻底放弃。
6. 配置可关闭（`enabled=false`），并有中文/英文文档与单测。

### 1.4 设计约束

- 零新依赖：只用 `node:fs` / `node:path` / `node:os`。
- 同步执行且可重复：启动期日志清理不得阻塞太久（13374 文件实测 <1s，仅 stat 粗筛，少量 JSON 解析）。
- 不破坏运行中的任务：任何删除都要先检查 `this.tasks.has(taskId)`。
- 不截断活日志：重定向 fd 的偏移无法安全重置，运行中日志不做截断（见 D2）。
- 跨平台：路径全部走 `join(runsDir(), ...)`，Windows 下 rm 正在被写文件会失败，用 try/catch 忽略。

## 二、方案设计

### 2.1 总体思路

```
启动 / 每次后台启动前
        │
        ▼
pruneRuns(opts)  ← 配置 tools.backgroundLog（init 注入，单例记忆）
        │
        ├─ readdirSync(runs/) + 一次 stat 收集 .log 元数据
        ├─ ① 按天数：非活跃 .json 且 mtime < cutoff → 删 .json + 配对 .log
        ├─ ② 按天数：无 .json 的 .log 且 mtime < cutoff → 删
        ├─ ③ 孤儿：orphaned-running / 损坏 JSON 且 mtime < now-1h → 删（含日志）
        └─ ④ 按大小：剩余非活跃 .log 按 mtime 升序删除，直到总量 ≤ maxTotalMb
```

### 2.2 关键设计决策

| 编号 | 决策 | 取舍 / 被否决项 |
| --- | --- | --- |
| D1 | **清理入口放 `BackgroundTaskRegistry.pruneRuns()`**，init 注入配置 | 否决放独立 CLI 脚本：用户不会主动跑，问题依旧 |
| D2 | **不截断运行中的活日志**，仅清理已结束/无主文件；「按大小」以目录总量为口径 | 否决运行中定期截断：spawn 持有 fd，truncate 后偏移错乱会写出稀疏大文件；否决改为 pipe 流式写入：改动面过大，列入后续演进 |
| D3 | 配置项 `tools.backgroundLog: { enabled, retentionDays=7, maxTotalMb=100 }` | 否决硬编码 24h：日志排障常需跨周；否决只按天数：磁盘仍可能被大日志撑爆 |
| D4 | 启动时 + **每次后台任务启动前**各清一次 | 否决只在启动：`--serve` 长驻进程可能数周不重启 |
| D5 | 活跃任务与内存条目一律跳过；删除前只判断 `this.tasks.has(taskId)` | 否决只看 `status==='running'`：内存条目才是权威，磁盘状态可能滞后 |
| D6 | 返回结构化结果 `{removedTasks, removedLogs, freedBytes}`，仅在有删除时写 debug 日志 | 否决静默：排障时无法确认清理是否生效 |
| D7 | 保留 `orphaned-running` 60 分钟宽限 + 损坏 JSON 直接删 | 沿用 task-20261022-002 D6 口径，不新增状态语义 |

## 三、任务详细设计

### 3.1 接口与数据结构

```ts
export interface BackgroundLogPruneOptions {
  enabled: boolean;
  retentionDays: number; // 默认 7
  maxTotalMb: number;    // 默认 100
}
export interface BackgroundLogPruneResult {
  removedTasks: number; // 成对删除的 .json 数
  removedLogs: number;  // 单独删除的 .log 数
  freedBytes: number;
}
configureBackgroundLogPrune(opts: Partial<BackgroundLogPruneOptions>): void
backgroundLogPruneOptions(): BackgroundLogPruneOptions
pruneRuns(override?: Partial<BackgroundLogPruneOptions>): BackgroundLogPruneResult
```

### 3.2 边界与错误处理

| 场景 | 行为 |
| --- | --- |
| `runs/` 不存在 | 直接返回零值，不创建目录 |
| 文件被并发删除 | `statSync/rmSync` 失败均忽略，继续处理其他文件 |
| `enabled=false` | 直接返回零值，不扫描目录 |
| `.json` 损坏且 mtime > 1h | 删除（与旧实现一致） |
| `.json` 损坏但 mtime < 1h | 保留，避免误删刚写入的临时文件 |
| 日志正在写入（活跃任务） | 四种规则全部跳过 |
| `maxTotalMb=0` | 删除所有非活跃日志（用于极端排障/测试） |

### 3.3 演进项（本任务不做）

- 运行中活日志的滚动（需要改 pipe 写入与轮转 sink）。
- 清理结果暴露到 WebUI 诊断页。
- 按任务类型/命令的差异化保留策略。

## 一、任务目标需求

### 1.1 背景（痛点）

用户在一次长会话中发现消息**落盘顺序错位**：首问排在一整段应答之后，看起来像「先回答了才提问」。

取证对象 `sess_522b6010_20261113_155009.json`（936 条），逐条解析 `msgId` 后事实闭合：

| 位置 | 消息 | `msgId` 解析出的进程序号 seq | 应为 |
|---|---|---|---|
| idx150 | 首问「对话上传文件进行问答，文件的展示样式不好看…」 | **21（全文件最早）** | 最前 |
| idx1 | 该首问的第 1 条应答 assistant | 22 | idx151 |
| idx2–10 | 该首问的 tool / assistant 应答 | 23–31 | idx152–160 |
| 其余 | 900 余条 | 单调递增 | 正常 |

全文件 934 条真实消息中，原始创建顺序的单调性**仅此处被破坏**（另一处倒序由进程重启后 `msgIdSeq` 归零造成，属正常）。无丢失、无重复 `msgId`。

`msgId` 形如 `msg_<时间戳36进制>_<进程内递增序号36进制><随机2位>`（`src/session/store.ts:110-114`），因此 seq 是**消息真实创建顺序的权威依据**，与磁盘顺序无关。

日志（`debug-2026-11-13.log`）把形成过程记全了：

| 时间 | 归档数 | 保留数 | 事件 |
|---|---|---|---|
| 07:50:47 | 0 | 11 | 首问首次落盘，`seq=21`，顺序正常 |
| 07:54:11 | 18 | 34 | 首次 L1 压缩（走轨迹重建） |
| … | 39 | 133 | 保留区始终装得下首问，位置未暴露 |
| **08:01:30** | 39 | **133 → 30** | **预算收缩，保留区骤减** |
| **08:01:38** | **149** | 30 | **归档跃至 149（`dropped=149`）→ 首问被 pin 到头部，落 idx150** |

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
|---|---|---|
| 压缩后保留当前轮原始问题 | `planCompaction` 把当前轮最后一条 user 从原下标抽出、插到 `kept` 头部（`src/memory/working.ts:317-340`） | **缺陷源**：置换了消息顺序 |
| 内存压缩与磁盘恢复同口径 | `buildCompactedView` 有一份**同款 pin 副本**（`src/memory/working.ts:200-207`） | 双处须同改，漏一处即分叉 |
| 模型能看到归档消息 | `getRestoreMessages` 对 `is_compact===true` 直接 `continue`（`src/session/store.ts:996`） | 归档即模型不可见 → **原文必须由摘要承载**，非可选项 |
| 前端展示归档消息 | `rebuildChatMsgs` 保留 `archived` 标记并正常平铺（`webui/src/chat-stream.ts:405-409`） | 原文完整可见，顺序按磁盘 |
| 归档段与保留段的区分 | `toStoredMessage(m,{isCompact})` 仅标记，不移动（`src/session/store.ts:205`） | 机制本身能保序，问题只在 pin 先行挪了位置 |
| 落盘轨迹重排 | `store.ts:719-727` 按 transcript 下标升序 | 它忠实记录的是**已被 pin 挪过的**顺序，无法回天 |
| 重复归档识别 | `countReplayedArchive` 假设「上次 dropped 为本次 dropped 的有序子集」（`store.ts:343`） | pin 让 dropped 中间被打洞，前提被打折 |
| 消息创建顺序的权威依据 | `msgId` 内嵌 `(时间戳, seq)`，`newMsgId()` 单调递增 | 可用于落盘顺序校验（D3 的判据来源） |

### 1.3 任务目标

1. **删除任务锚点 pin**（两处同口径），当前轮 user 压缩后**原位不动**：落入丢弃区即按 `is_compact=true` 归档，`droppable` 恢复为**纯前缀**、`kept` 恢复为**纯后缀**。
2. **摘要占位消息追加当前轮 user 原文段**：由代码拼接（不依赖 LLM 概括），保证模型不因归档丢失原始问题；且原文段顺序在摘要内，不触碰消息数组顺序。
3. `SUMMARY_MAX_CHARS` 500 → **800**（D1），原文段字数单独设上限，并**计入 token 预算**。
4. 落盘写前增加 `msgId` `(时间戳, seq)` 单调性校验，发现倒序**仅告警、不自动重排**（D3）。

### 1.4 设计约束

- **顺序保真是硬约束**：磁盘顺序 == 消息真实创建顺序（轨迹下标序），任何机制不得为「保留」而移动消息。
- 不改 `is_compact` / `is_show` / `kind` 语义，不改 `getRestoreMessages` 恢复口径。
- 不改前端 `rebuildChatMsgs()` 展示逻辑。
- 不改压缩触发阈值、`compactionThreshold`、`needsCompaction` 判定公式。
- 不动 L2 / L3 记忆链路、不动 `/sessions/:id/compact` 端点契约。
- **不新增 npm 依赖**（校验只用既有 `debug.log`）。
- **不对存量错位文件做自动重排**：存量错位只允许被新校验「发现并告警」，修复靠用户重建会话或后续人工处理。
- 存量会话数据必须继续可读（旧摘要无原文段时按「无原文段」处理，不报错）。

## 二、方案设计

### 2.1 总体思路

```
                       ┌──────────────────────────────────────┐
   压缩触发            │ planCompaction()                     │
 (needsCompaction) ───▶│  nonSystem ─┬─ droppable(纯前缀) ────┼──▶ 送 flush 载荷
                       │             └─ kept     (纯后缀) ────┼──▶ 上下文保留
                       │                                      │
                       │  ★ pin 删除（D2）                    │
                       │  当前轮 lastUser 若∈droppable:       │
                       │    → anchorUserText = 原文（D6）      │
                       │    → 仍留在 droppable 内（原地归档）  │
                       └───────────────┬──────────────────────┘
                                       │ anchorUserText
                                       ▼
       ┌───────────────────────────────────────────────────────────┐
       │ preCompactionFlush()  ──LLM──▶ summaryText（≤800字, D1）   │
       └───────────────────────────────┬───────────────────────────┘
                                       ▼
       ┌───────────────────────────────────────────────────────────┐
       │ buildCompactedView()   ★ pin 副本删除（D2）                │
       │  占位 content = "[历史摘要] <summaryText>"                 │
       │                 "\n[当前问题] <anchorUserText>"  ← 代码拼（D4/D5）
       │  上文 previousSummary 提取时剥离 [当前问题] 段（D5 幂等）   │
       │  keepBudget 扣除占位预估 token（D1 计入预算）              │
       └───────────────────────────────┬───────────────────────────┘
                                       ▼
       ┌───────────────────────────────────────────────────────────┐
       │ updateSession() 落盘                                       │
       │  rebuilt = [旧归档…, summaryMsg, …transcript 按下标升序]   │
       │  ★ 写盘前 assertOrderByMsgId()（D3 仅告警）                │
       └───────────────────────────────────────────────────────────┘
```

关键点：**「保留哪些」与「放在哪」彻底解耦**。`planCompaction` 只决定消息归属（归档 / 保留），`buildCompactedView` 只按归属组装，二者都不再移动消息位置；原文的「可见性保障」改由摘要文本承载。

### 2.2 关键设计决策

#### D1｜摘要上限 800 字，原文段计入预算　【已确认】

- `SUMMARY_MAX_CHARS`：500 → **800**；`SUMMARY_TRUNCATE_MAX_CHARS` 随动为 `ceil(800×1.2)=960`。
- 原文段单独上限 `ANCHOR_USER_MAX_CHARS = 800`，同样 1.2 上浮兜底。
- **计入预算的实现口径**：占位消息是一条真实 message，`estimateMessageTokens` 天然按 `content.length/4` 计入；额外在 `planCompaction` 计算 `keepBudget` 时扣除「占位预估 token」`⌈(SUMMARY_MAX_CHARS + ANCHOR_USER_MAX_CHARS)/4⌉ = 400`，避免「压缩后总量仍超阈值 → 立刻又触发压缩」的空转。
- 取舍：固定扣除 400（上界）而非按实际长度动态计算——实现简单、结果只偏保守（多留少丢），且压缩本身可自愈（下一轮 `needsCompaction` 继续收敛）。
- **被否决**：把原文段排除在 token 估算外（会让压缩判定偏松、触发滞后）。

#### D2｜直接删除 pin，不留可配置开关　【已确认】

- 删除 `src/memory/working.ts:317-340`（`planCompaction` pin）与 `:200-207`（`buildCompactedView` pin 副本）。
- 连带删除 `:325-332` 的「扣掉锚点 token 重新截尾」分支——该分支只为让被 pin 的锚点塞进预算，pin 没了即失去意义。
- `CompactionPlan.withinTurnTrim` 的注释「当前轮的原始 user 消息会作为任务锚点被固定保留」改写为描述新口径。
- **理由**：双路径正是本次事故的温床；留开关等于保留一个「会破坏顺序」的潜在分支。
- **被否决**：保留 pin 作为 opt-in 配置项。

#### D3｜落盘顺序校验仅告警，不自动重排　【已确认】

- 新增 `checkMsgIdOrder(messages)`：解析每条 `msgId` 得 `(ts, seq)`，单次线性扫描检查
  - `ts` 非递减；
  - `ts` 相同的连续段内 `seq` 非递减。
- 无法解析者一律跳过（legacy `msg_l<hash>`、`ensureMsgIds` 的 `_n` 去重后缀、无 `msgId`）。
- 命中违例 → `debug.log` 告警，**最多报前 5 处**（含下标、当前 `msgId`、应大于的前一条 `msgId`）。
- 调用点：`updateSessionLocked` 的 `writeSession(data)` **之前**。
- **理由**：存储的职责是忠实反映轨迹；自动重排会把「忠实」也变成可篡改，且可能与 `dedupeByMsgId`、`countReplayedArchive` 的假设打架。
- 开销：n ≤ 4000 的线性扫描，每次 `updateSession` 一次，可忽略。
- **被否决**：自动按 seq 重排（掩盖真实缺陷来源）；用 `console.warn`（项目统一走 `debug.log`）。

#### D4｜原文承载形式：合并进摘要占位 content　【已按方案 A 落地】

- **方案 A（推荐，贴合用户表述）**：原文段作为摘要占位 `content` 的固定后缀段，仍是**一条** message。
  - 优点：消息数不变；不新增 `kind` 语义；`is_show=false` 使其继续对前端不可见；`getRestoreMessages` 零改动即可让模型看到。
  - 代价：需从 `content` 文本里切分原文段（D5 处理）。
- **方案 B**：原文作为独立隐藏消息（`kind='anchor'`、`is_show=false`）紧跟摘要之后。
  - 优点：无需文本解析，字数上限与幂等独立控制。
  - 代价：新增 `kind` 语义（`isSummaryMessage` / `toStoredMessage` / 前端 `rebuildChatMsgs` 都要认），且用户明确说「压缩总结消息里加入」。
- 默认按 **A** 实施；若确认选 B，第三章 3.1/3.3 需相应调整。

#### D5｜原文段的分隔标记与幂等剥离　【已落地】

- 占位 `content` 格式（`\n` 字面换行）：

  ```
  [历史摘要] <LLM 摘要正文>
  [当前问题] <用户原始问题原文>
  ```

- 解析：新增 `splitAnchorSection(text)`，`text.indexOf('\n[当前问题] ')` 命中即切分；未命中视为「无原文段」（兼容存量数据）。
- **幂等三层保障（实现与初稿略有差异，以此为准）**：
  1. **写回侧单点剥离**：`buildCompactedView` 组装占位时统一走 `composeSummaryBody(summaryBody, anchorText)`，后者内部先 `splitAnchorSection` 剥掉 summary 里可能残留的旧原文段，再拼**本次**原文段 —— 故 `\n[当前问题] ` 在占位里永远只出现一次，重复压缩不叠加。
  2. **`previousSummary` 刻意不剥**（与初稿相反）：`planCompaction` 喂给 LLM 的历史摘要**保留**原文段，让模型仍能看到历史轮次的原始问题；为防它照抄标记，`FLUSH_SYSTEM_PROMPT` 明确要求「作为要点合并，不要原样照抄该标记」。剥离只发生在写回侧。
  3. 同一 run 多次快照均从 `existingPlaceholder` 重新提取，天然收敛。
- 标记选 `\n[当前问题] ` 而非 `[当前问题]`：带前置换行，降低与用户原文/摘要正文误撞的概率。
- **被否决**：用 JSON 包裹占位（模型可读性差、破坏纯文本摘要约定）；用结构化字段 `summaryAnchor`（`toStoredMessage` 落盘会丢字段，且模型看不到）。

#### D6｜取哪条原文、取什么内容、如何截断　【已落地】

- **触发条件与原 pin 严格一致**：`lastUserIdx >= 0 && lastUserIdx < keptStart`（即「当前轮最后一条 user 落在丢弃区」）。若它本来就在 `kept` 里，模型直接可见，**不追加原文段**（避免重复占字数）。
- 取值：`nonSystem[lastUserIdx].content`，并 `stripMemorySection()` 剥 L2 记忆前缀（与 `compaction-payload.ts` 口径一致）；**保留上传附件 note**（模型需要绝对路径才能调 `analyzeImage`）。
- 截断（`ANCHOR_USER_MAX_CHARS=800`）：**头尾保留**而非单纯头部截断——头 500 字 + 中间 `…（已省略 N 字）…` + 尾 300 字。理由：附件 note 位于 user 正文尾部，纯头部截断会把它整段切掉，导致模型「知道有问题、不知道有附件」。
- 空内容 / 纯空白：不追加原文段（退化为原行为）。
- **被否决**：只保留头部 800 字（丢附件 note）；不截断（长粘贴可把摘要撑爆，与 D1 预算冲突）。

#### D7｜flush 载荷里是否排除当前轮 user　【已采纳（载荷保留，仅加提示）】

- 删 pin 后，当前轮 user 会进入 `droppable`，从而进入 flush 载荷 → LLM 摘要可能复述它，与代码追加的原文段**语义重复**。
- 建议：载荷**保留**（LLM 需要上下文才能概括本轮），但在 `FLUSH_SYSTEM_PROMPT` 追加一句「当前轮的原始用户问题会由系统单独追加，无需在摘要中复述」。
- 纯字数优化，不影响正确性；如认为不必要可整体跳过，不动 `compaction-payload.ts`。

### 3.1 `src/memory/summary-message.ts`

```ts
/** 压缩摘要的目标长度上限（D1：500 → 800） */
export const SUMMARY_MAX_CHARS = 800;

/** 硬截断上限：目标值上浮 20% */
export const SUMMARY_TRUNCATE_MAX_CHARS = Math.ceil(SUMMARY_MAX_CHARS * 1.2); // 960

/** 当前轮 user 原文段字数上限（D1） */
export const ANCHOR_USER_MAX_CHARS = 800;
/** 原文段头/尾保留字数（D6） */
export const ANCHOR_HEAD_CHARS = 500;
export const ANCHOR_TAIL_CHARS = 300;
/** 原文段分隔标记（带前置换行，D5） */
export const ANCHOR_SECTION_MARK = '\n[当前问题] ';
/** 占位在保留预算里的 token 预留上界（D1）= ⌈(800+800)/4⌉ = 400 */
export const SUMMARY_PLACEHOLDER_RESERVE_TOKENS: number;
/** 原文段「是否已在摘要正文里」的判据长度（去重指纹，120 字） */
export const ANCHOR_DEDUPE_CHARS = 120;

/** 把 LLM 摘要 + 原文段拼成占位 content 主体（不含 [历史摘要] 前缀）；内部先剥旧原文段再拼（幂等） */
export function composeSummaryBody(summary: string, anchorText?: string): string;

/** 切分：返回 { summary, anchor }，anchor 为空表示无原文段（D5 幂等 + 存量兼容） */
export function splitAnchorSection(body: string): { summary: string; anchor?: string };

/** 原文段字数兜底截断（头尾保留，D6），max 可调小，按 500:300 等比缩放 */
export function truncateAnchorText(text: string, max = ANCHOR_USER_MAX_CHARS): string;

/** 原文段去重（`flushFailure='archive'` 回退时 summaryText 已含原文 → 丢弃原文段） */
export function dedupeAnchorText(summaryBody: string, anchorText?: string): string | undefined;
```

### 3.4 边界与错误处理

| 场景 | 期望行为 |
|---|---|
| 当前轮 user 在 `kept` 内 | 不追加原文段（模型直接可见） |
| 当前轮 user 原文为空 / 全空白 | 不追加原文段，退化为仅摘要 |
| 存量占位无原文段 | `splitAnchorSection` 返回 `anchor=undefined`，按仅摘要处理，不报错 |
| LLM 摘要写满 800 字 | 摘要截到 960，原文段**完整保留**（分别截断后拼接） |
| 原文 > 800 字 | 头 500 + `…（已省略 N 字）…` + 尾 300 |
| flush 失败 + `flushFailure='skip'` | 不压缩、pin 已删 → 消息原样、顺序天然正确 |
| flush 失败 + `flushFailure='archive'` | `rawContent` 已含当前轮 user → 仍追加原文段会重复；**去重**：若 `rawContent` 已包含该原文则跳过追加（P0 必做） |
| 旧会话从未压缩过 | 全链路不触发，行为零变化 |
| `msgId` 为 legacy 哈希 | 校验跳过，不误报 |
| `ts` 相同、`seq` 回绕（进程重启后归零） | 理论上 `Date.now()` 已变 → `ts` 变；若极端相同则可能误报一次，可接受（仅告警） |

### 3.5 演进项（本任务不做）

- 存量错位会话的自动修复工具（按 `msgId` seq 重排并重写文件）。
- 展示层按 `msgId` 时间戳排序兜底（当前认为存储保真后不必要；若前端仍要求「首问置顶」属另一需求）。
- 把原文段升级为「多轮 user 原文都保留」（当前只保当前轮）。
- 摘要与原文段的结构化落盘（`attachments` 式的独立字段）。

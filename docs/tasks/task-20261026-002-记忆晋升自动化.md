## 一、任务目标需求

### 1.1 背景（痛点）

CLI 在 REPL 退出时会自动执行 Dreaming，把 L2 情景记忆抽取为 L3 Curated 事实（SOUL/USER/MEMORY）。
但 `--serve` / WebUI 侧**只有手动路径**，而 serve 是常驻进程——「退出时晋升」这个模型在它身上根本不成立：

| 场景 | CLI | `--serve` / WebUI |
| --- | --- | --- |
| 正常结束使用 | `quit`/`exit`/`Ctrl+C` → readline `close` → `await agent.runDreaming()` → `process.exit(0)` | 进程不退出，**无任何时机** |
| 服务关停 | 同上 | SIGINT 只 `server.close()` + `mcpManager.disconnectAll()` 后 `process.exit(0)`，**不做 Dreaming** |
| 会话新建 / 切换 / 删除 | 不适用 | **无触发** |
| 关闭浏览器标签 | 不适用 | 前端关页面服务端无感知，**无触发** |
| 手动整理 | `/memory dream` | `POST /memory/dream`（202 即走即忘）+ MemoryView「✦ 梳理」按钮 |

后果：WebUI 长期使用下，L3（用户画像、项目事实）**不随对话演进**，等于「聊了很多但没记住」；能否晋升完全取决于用户是否记得点那个按钮。

`docs/tasks/task-20261016-001-自定义REST API服务.md:266` 已把此事明确记为演进项：

> SIGINT 处理：serve 模式下 `server.close()` + `mcpManager.disconnectAll()` 后退出（**不做 Dreaming，属演进项**）。

### 1.3 任务目标

1. `--serve` 模式下**自动晋升**：定时为主力（跨天后真正有新增才调 LLM），进程关停兜底。
2. 把「手动点按钮」从常态降为可选；手动端点与自动触发**共用同一把进程内锁**。
3. 晋升状态**可观测**：WebUI 能看到「上次晋升时间 / 结果 / 下次计划 / 是否正在跑」。
4. 修补**停机漏数**：触发时按「距上次处理的天数」放大读取窗口，避免停机多日后中间的天永久丢失。
5. CLI 既有行为**零回退**（退出时 Dreaming 逻辑不动）。

### 1.4 设计约束

- **零新依赖**：只用 `node:` 内置（`setInterval`/`AbortController` 不需要，超时用 `Promise.race` + `setTimeout`）。
- **跨平台**：信号面须覆盖 Windows（无 POSIX `SIGTERM`）与 Linux/macOS（`SIGTERM` 为主）。
- **默认可用**：`schedule.enabled` 默认开启，但必须有独立的关闭开关与间隔可调。
- **不阻塞对话**：定时任务不进入 `runAgent` 的并发闸门，但撞上同空间 in-flight run 时**本轮跳过**。
- **状态权威**：以 `.dreaming-state.json` 与内存态为准，不引入第二份缓存真值。
- **单测可注入**：调度器不硬编码定时器与时钟，便于用假 timer 验证。

## 二、方案设计

### 2.1 总体思路

```
                     ┌──────────────────────────────────────────┐
   定时（每 intervalHours，startupDelayMin 后首次）             │
   ──────────────────┤  DreamScheduler                          │
                     │   · per-root 单飞锁 Map<root, Promise>    │
   SIGINT/SIGTERM   │   · runFor(root, reason)                 │
   SIGBREAK（Win）  │   · runAll(reason)                       │
   ──────────────────┤   · shutdown(budgetMs)                   │
                     │   · statusFor(root)                      │
   POST /memory/    │                                          │
   dream（手动）     │                                          │
   ──────────────────┘                                          │
                     └───────────────┬──────────────────────────┘
                                     │ 抢到锁才跑
                                     ▼
                 registry.list() → rt.getMemoryKit() → kit.dream.run(effectiveDaysBack, …)
                                     │
                     ┌───────────────┴───────────────┐
                     ▼                               ▼
        {L2}/.dreaming-state.json            DreamScheduler 内存态
        lastProcessedDay（原有）              lastRunAt / lastSummary / running / nextRunAt
        + lastRunAt / lastSummary（新增）              │
                     │                               ▼
                     └──────────►  GET /memory/status（新增 dreaming 字段）
                                          │
                                          ▼
                                  MemoryView.vue 展示
```

触发与关停时序（关停兜底）：

```
SIGINT(#1) → shuttingDown=true（调度器立即 stop，拒绝新定时轮）
           → runAll('shutdown') 逐空间串行，总预算 30s（超时不再等，打印警告）
           → server.close() → mcpManager.disconnectAll() → process.exit(0)
SIGINT(#2) → 立刻 process.exit(0)（跳过剩余 Dreaming）
```

### 2.2 关键设计决策

| 编号 | 决策（一句可确认的判断） | 取舍与被否决项 |
| --- | --- | --- |
| **D1** | 触发组合 = **定时为主 + 关停兜底**；不做前端「会话切换 / 空闲 debounce」触发 | 否决纯关停：serve 常年不退，等于不晋升；否决纯定时：进程被杀时丢失最后一轮。前端 debounce 依赖页面在线、收益低且请求量大，列为演进项 |
| **D2** | 定时节奏 = **固定间隔检查（默认 24h）**，首次在 `startupDelayMin`（默认 5 分钟）后；是否真正调 LLM 由增量判定决定 | 否决「每日固定时刻（03:00）」：笔记本常关机，固定时刻大概率错过。否决 6h：当天内容本就不处理（`d.day < today`），6h 一轮纯属空跑刷日志 |
| **D3** | **补齐停机漏数**：触发时 `effectiveDaysBack = clamp(今天 − lastProcessedDay + 1, daysBack, 30)` | 现状 `readRecentDays(3)` 只往前看 3 天，停机一周后中间 4 天永久读不到。上限 30 天防一次性灌爆上下文；`daysBack` 仍为下限，配置语义不变 |
| **D4** | 关停兜底范围 = `registry.list()` **全部已装载 runtime 串行**，总预算 `shutdownBudgetMs`（默认 30000） | 否决只跑当前空间：多空间并存（Task-20261021-010）后其余空间会集体饿死。串行而非并行：Dreaming 走 LLM，并行只为抢配额 |
| **D5** | 关停顺序 = **先停调度器并抢锁 → 跑 Dreaming → `server.close()` → 断 MCP → `exit(0)`** | 否决先 `server.close()`：等存量连接关闭可能挂住（SSE 长连接），Dreaming 就永远排不上。Dreaming 期间新到达的请求仍会写入 L2，但 Dreaming 只处理 `<today` 的天，互不干扰 |
| **D6** | 信号面同时监听 **`SIGINT` + `SIGTERM` + `SIGBREAK`**；二次信号立即强退 | Windows 无真 POSIX `SIGTERM`，监听它不报错但收不到（`process.kill(pid,'SIGTERM')` 在 Windows 是**强杀**，JS 清理不会跑）；`SIGBREAK` 覆盖 Windows 关控制台窗口/部分进程管理器。二次 Ctrl+C 给用户「别等了」的出口 |
| **D7** | **进程内单飞锁**（`Map<root, Promise>`）：撞车即「跳过并记日志」，不排队 | 否决排队：迟到的晋升意义本就极小，排队反而在关停时拖时间。**跨进程不做文件锁**——CLI 的 `/memory dream` 与 serve 是两个进程，用 `.dreaming-state.json` 的 `lastProcessedDay` 幂等兜底；真正的跨进程锁见优化建议 20261022-002 遗留项 |
| **D8** | 定时触发时若该空间 `hasInFlight()` 为真 → **本轮跳过**（写日志，不重试） | 否决排队等待：会与对话抢 API 配额与带宽，进而拖慢首 token。关停兜底**不受此限**（那时已无新对话） |
| **D9** | 可观测 = 扩展 `.dreaming-state.json` 增 `lastRunAt` / `lastSummary`（**读取容错，缺省不影响增量判定**）+ `GET /memory/status` 增 `dreaming` 字段 + MemoryView 展示一行 | 否决新建独立状态文件：状态分散、两份真值易分叉。否决持久化调度器内存态：`lastRunAt` 用状态文件本身就够，`nextRunAt` 重启后按启动时间重算 |
| **D10** | 配置 = **复用 `memory.dreaming.onExit`**（语义由「CLI 退出」扩为「进程关停」），新增 `memory.dreaming.schedule = { enabled: true, intervalHours: 24, startupDelayMin: 5 }` 与路径级 `shutdownBudgetMs: 30000` | 否决新增 `onShutdown`：同一件事两个开关会让用户困惑。新增子键经 `deepMerge` 自动补默认，旧配置文件无需迁移 |
| **D11** | 手动端点改走调度器：`ctx.dreamScheduler?.runFor(root, 'manual')`，**缺省（未注入）时回退现有即走即忘行为** | 保持既有单测与嵌入用法零改动；同时让「按钮 / 定时 / 关停」三者天然互斥 |
| **D12** | 定时器与超时定时器一律 `.unref()`，并在 `server.close()` 里 `dispose()` | 避免调度器把进程/单测挂住；`server.close()` 已持有 `runs.dispose()` 等先例 |
| **D13** | 非目标（本任务**不做**）：DreamingPipeline 提取算法与 L1/L2 改动、Curated 文件格式与去重策略、前端会话切换触发、CLI 加定时、跨进程文件锁 | 各自独立成议题；混进来会让本任务的验收边界糊掉 |

### 2.3 外部检索结论（设计阶段）

| 结论 | 对本方案的影响 | 来源 |
| --- | --- | --- |
| `process.on('exit')` 回调里**只能同步**操作，异步写入不保证完成 | 关停兜底**必须**放在信号处理器里 `await`，不能挂 `exit` 事件 | [Node Process 文档](https://nodejs.org/api/process.html) |
| `'SIGTERM'` 在 Windows 上不受支持（可监听但收不到）；Windows 上 `process.kill(pid,'SIGTERM')` 是强制终止，不跑 JS 清理；Ctrl+C 映射为 `SIGINT`，`SIGBREAK` 是 Windows 最接近「优雅停止」的信号 | D6：三信号并列监听 + 二次信号强退；文档须写明 Windows 关控制台窗口可能拿不到清理时机 | [The Node Book: Signals, Exit Codes, and Graceful Shutdown](https://www.thenodebook.com/process-os/signals-exit-codes)、[Node Process 文档](https://nodejs.org/api/process.html) |
| `setInterval` 默认 ref，会阻止事件循环退出，必须 `.unref()` | D12：调度器定时器与超时定时器全部 unref，`close()` 时清理 | [Node timers 文档](https://github.com/nodejs/node/blob/main/doc/api/timers.md)、[SO: setInterval without extending process life time](https://stackoverflow.com/questions/43254854/nodejs-setinterval-without-extending-process-life-time) |

## 三、任务详细设计

### 3.1 新增 `src/api/dream-scheduler.ts`

```ts
/** 单次晋升结果（对外可观测） */
export interface DreamRunSummary {
  root: string;
  reason: 'schedule' | 'shutdown' | 'manual';
  ok: boolean;
  /** 实际读取窗口（D3 放大后） */
  daysBack: number;
  promoted: number;
  skipped: number;
  errors: number;
  /** 提前结束原因（未真正跑） */
  skippedBecause?: 'disabled' | 'busy' | 'already-running' | 'no-kit';
  startedAt: string;   // ISO
  finishedAt: string;  // ISO
  durationMs: number;
}

export interface DreamSchedulerStatus {
  running: boolean;
  lastRunAt?: string;
  lastSummary?: Pick<DreamRunSummary, 'reason' | 'promoted' | 'skipped' | 'errors' | 'ok' | 'skippedBecause'>;
  lastProcessedDay?: string;
  nextRunAt?: string;
}

export interface DreamSchedulerDeps {
  registry: WorkspaceRegistry;
  getConfig: () => AgentConfig;
  log: (msg: string) => void;
  /** 测试注入：时钟 */
  now?: () => number;
  /** 测试注入：定时器工厂（默认 setInterval/setTimeout，均 unref） */
  createTimer?: (fn: () => void, ms: number) => { cancel(): void };
}

export class DreamScheduler {
  /** 定时轮检查全部已装载空间（D2/D8） */
  async tick(reason?: 'schedule'): Promise<DreamRunSummary[]>;
  /** 单空间单飞执行（D7），撞车返回 skippedBecause='already-running' */
  runFor(root: string, reason: DreamRunSummary['reason']): Promise<DreamRunSummary | null>;
  /** 关停兜底：串行 + 总预算（D4/D5） */
  runAllForShutdown(budgetMs: number): Promise<DreamRunSummary[]>;
  start(): void;   // 注册定时器（unref）
  stop(): void;    // 清定时器，拒绝新 tick
  statusFor(root: string): DreamSchedulerStatus | null;
}
```

**`runFor` 主流程**

```
1. cfg = getConfig(); if (!cfg.memory.enabled || !cfg.memory.dreaming.enabled) → skippedBecause='disabled'
2. if (inflight.has(root)) → skippedBecause='already-running'
3. if (reason==='schedule' && rt.sessions.hasInFlight()) → skippedBecause='busy'   // D8
4. kit = await rt.getMemoryKit()
5. state = await kit.dream.loadState?()  ← 见 3.3（新增只读访问器）
   daysBack = clamp(今天 − (state.lastProcessedDay || 今天−daysBack) + 1, cfg.daysBack, 30)   // D3
6. p = kit.dream.run(daysBack, onProgress→log, {dedupeEnabled, batchByDay, incremental})
   inflight.set(root, p); try { result = await p } finally { inflight.delete(root) }
7. 更新 state.lastRunAt / lastSummary（D9）；写内存态；log 一行统一格式
```

**日志统一格式**（便于 grep 与后续告警）

```
[api] dream schedule ws=<id8> 窗口=4d 晋升=3 跳过=1 错误=0 用时=8.2s
[api] dream shutdown ws=<id8> 跳过（busy）
[api] dream manual   ws=<id8> 已在运行，忽略本次请求
```

### 3.2 关停链路改造（`src/api/bootstrap.ts`）

```ts
const scheduler = new DreamScheduler({ registry, getConfig: () => configLoader.load().config, log });
scheduler.start();
// 传给 server，使 POST /memory/dream 也能抢锁（D11）
createApiServer({ …, dreamScheduler: scheduler });

let shuttingDown = false;
const onSignal = async (sig: string): Promise<void> => {
  if (shuttingDown) {                 // D6：二次信号立即强退
    console.log(`\n[api] 再次收到 ${sig}，立即退出（未完成的晋升会被丢弃）`);
    process.exit(0);
  }
  shuttingDown = true;
  scheduler.stop();                   // D5：先停调度器
  const budget = cfg.memory.dreaming.shutdownBudgetMs;   // 默认 30000
  console.log(`[api] 正在整理记忆（Dreaming），最多等待 ${budget / 1000}s；再按一次 Ctrl+C 立即退出`);
  await scheduler.runAllForShutdown(budget).catch(() => []);
  await server.close().catch(() => {});
  await mcpManager.disconnectAll().catch(() => {});
  process.exit(0);
};
for (const sig of ['SIGINT', 'SIGTERM', 'SIGBREAK'] as const) process.on(sig, () => void onSignal(sig));
```

**超时语义**：`runAllForShutdown` 用 `Promise.race([串行任务, 预算超时])`；超时后不再等（LLM 调用无法回滚，本轮写入可能不完整，属 best-effort），打印警告后继续关停。

| 手动端点 | `POST /memory/dream` 抢锁成功回 `202 {accepted:true, reason:'manual'}`；已在跑回 `202 {accepted:false, skippedBecause:'already-running'}`（仍 202，语义是「已受理/无需受理」，不引入新错误码） |

| 日志 | 统一前缀 `[api] dream <reason> ws=<id8>` |

### 3.5 边界与错误处理

| 场景 | 行为 |
| --- | --- |
| `memory.enabled=false` 或 `dreaming.enabled=false` | 调度器 `start()` 仍注册定时器但每轮直接跳过并`debug.log`，避免配置热改后需重启（**定时器不因配置关而卸载**） |
| `dreaming.schedule.enabled=false` | `start()` 不注册定时器；关停兜底仍按 `onExit` 走（二者独立） |
| `onExit=false` | 关停不做 Dreaming；定时与手动不受影响 |
| 某空间 runtime 已被 LRU 淘汰 | `registry.list()` 只返回已装载的，天然不处理；下次该空间被访问时重新装载，由定时轮补上（D3 保证补得到） |
| 单空间 Dreaming 抛错 | 记入 `summary.ok=false` 与 `errors`，**继续处理下一个空间**，绝不中断关停链路 |
| 关停预算超时 | 打印警告后强退；已完成的空间结果保留 |
| 定时轮与手动同时到达 | 单飞锁生效，后来者 `skippedBecause='already-running'`，无重复晋升 |
| 单位置并发（CLI 与 serve 同时跑） | 无文件锁（D7）：靠 `lastProcessedDay` 幂等 + 失败不推进状态；极端情况可能重复晋升一天，去重归并会拦掉重复事实 |
| 时钟回拨 / 跨时区 | `effectiveDaysBack` 用 `new Date().toISOString()` 的日期差（与现有 `day` 口径一致），差值 ≤ 0 时回落到 `cfg.daysBack` |

### 3.6 演进项（本任务不做）

- 前端「会话切换 / 空闲 30min」debounce 触发（依赖页面在线）。
- CLI 侧定时（CLI 是短生命周期进程，收益低）。
- 跨进程文件锁（见优化建议 20261022-002 遗留项）。
- 晋升结果的前端 SSE 实时推送（当前刷新即可见）。
- 定时轮的多空间并行（受全局并发闸门约束，暂无必要）。

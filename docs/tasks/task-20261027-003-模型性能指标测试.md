## 一、任务目标需求

### 1.1 背景（痛点）

「模型」页（`#/models`）此前只到**连通性**：`POST /models/:alias/test` 复用一个「首发一小块就 abort」的探测（`defaultCheckConnectivity`），只回一个毫秒数。它回答的是「这个 key / baseUrl 能不能通」，不回答「这个模型快不快」——

- 不区分**排队 + prefill**（首 token 延迟）与**解码速度**，把两段耗时揉成一个数；
- 只跑一轮，没有 p50 / p90，抖动看不见；
- 不落历史，换 provider 前后的对比只能靠体感。

而流式对话里最影响体感的恰恰是 **TTFT**（首 token 延迟）与**纯解码吞吐**。用户换模型时真正想知道的是「这个模型首字多久出来、每秒吐多少 token、稳不稳」。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
| --- | --- | --- |
| 跑在服务端的计时 | `src/llm/connectivity.ts` 已有「显式 fetch + `maxRetries: 0`」的 OpenAI 客户端注入范式 | 复用同一范式，**禁止自动重试**（重试会污染统计） |
| 流式读取 | `src/llm/*` 全部走 `chat.completions.create({stream:true})` 的 `for await` | 复用；额外开 `stream_options.include_usage` 拿权威 token 数 |
| SSE 推送 | `src/api/http-utils.ts` 的 `sseFrame()` 已是全站统一分帧器 | 复用，不新建 | 
| 路由优先级 | `src/api/server.ts` 已含 `/models/:alias/test` 这类带参数段的路由 | **静态段 `/models/bench` 必须先于 `:alias` 匹配**，否则 `alias=bench` 会抢走 |
| 前端抽屉 | `.drawer` / `.drawer-mask` / `.drawer-h` / `.drawer-b` 已在 `style.css`（文件预览等场景在用） | 复用组件骨架与令牌，不新增色值 |
| 前端纯逻辑可测 | `webui/src/tool-meta.ts` 已确立「纯函数放独立模块、Node 下 vitest 直测」的约定 | 新增 `bench-format.ts` 同款处理 |

### 1.3 任务目标

在模型管理页为每个已登记 profile 增加**性能测试**能力：后端以固定提示词档位 + 固定 `max_tokens` 发起真实流式请求并精确计时，产出 TTFT / TPOT（ITL）/ 纯解码 TPS / 端到端 TPS / 输出 token 数 / 成功率与错误分类，多轮取 p50/p90；前端给出档位面板（运行中实时读数可中断）、结果指标卡、多模型横向对比条形图、每轮明细与最近 N 次历史趋势。

### 1.4 设计约束

- **连通性 ≠ 性能，两者并存互不替代**：「测试」近免费（收首块即断），「测速」按输出 token 计费
- **跨模型可比**：固定提示词、固定 `max_tokens`、`temperature: 0`，且默认破坏前缀缓存
- **不污染既有链路**：测试不进会话、不进记忆、不触发工具调用、不消耗 Agent 上下文
- **不存密钥**：历史只落可公开的数值与模型标识
- **不新增色值**：全部复用 `style.css` 既有令牌

## 二、方案设计

### 2.1 总体思路

```
浏览器                                   Node 服务
┌────────────────────────┐             ┌──────────────────────────────────┐
│ ModelsView.vue         │             │ server.ts                        │
│  └「性能」列 + 测速按钮 │             │  └ /models/bench/*  ← 静态段优先 │
│  └ BenchDrawer.vue     │── POST ────►│     handlers/bench.ts            │
│      ├ 配置区（档位）   │   202 runId │       ├ bench-hub.ts（run 表）   │
│      ├ 运行中实时读数   │◄── SSE ─────│       └ llm/bench.ts（计时引擎） │
│      ├ 指标卡/对比条    │  进度事件    │            └ OpenAI SDK 流式      │
│      ├ 每轮明细         │── stop ────►│ llm/bench-store.ts               │
│      └ 历史迷你走势     │◄── history ─│   └ ~/.loop-agent/model-bench/    │
└────────────────────────┘             └──────────────────────────────────┘
```

数据流：`runBench()` 每轮发一次流式请求 → 只记时间点与 `usage`（循环内不做计算）→ 结束后统一算指标 → `onToken` 100ms 节流后经 SSE 推给前端 → 全部跑完落历史并回放终态。

### 2.2 决策落地（D1–D11）

| 决策 | 落地位置 | 说明 |
| --- | --- | --- |
| D1 测试跑在后端 | `src/llm/bench.ts` | 浏览器测不出真实链路：CORS/代理/网关都在后端这一侧 |
| D2 TTFT 只认首个**非空内容** chunk | `measureOnce()` | 空串（仅 role）与纯 usage 尾块一律不计（坑 ①） |
| D3 多模型对比服务端串行 | `postBench` + `concurrency: 1` | 并行会互抢带宽，对比结论失真 |
| D4 主指标 = 纯解码 TPS | `decodeTps = (out-1)/span*1000` | 端到端 TPS 作副行（含 TTFT 与 prefill，易被网关拉低） |
| D5 推理模型 TTFT 含 reasoning 首 token | `Timing.firstReasoningMs` | 另单列「首答案 token」时间 |
| D6 `/models/bench/*` 先于 `:alias` 注册 | `src/api/server.ts` | 否则 `alias=bench` 抢路由 |
| D7 进度走 SSE | `handlers/bench.ts` + `sseFrame` | 先回放已有事件，断线重连幂等 |
| D8 默认破坏前缀缓存 | `bustCache` 默认 `true`（注入 `bench-nonce` system 消息） | 并记录 `prompt_cache_hit_tokens`（坑 ②） |
| D9 历史落 `~/.loop-agent/model-bench/history.json` | `src/llm/bench-store.ts` | 每 alias 留最近 20 次（`BENCH_HISTORY_KEEP`），不存 apiKey |
| D10 固定提示词 + `max_tokens` + `temperature:0` | `BENCH_PROMPTS` / `runBench` | `maxTokens` 夹在 32–1024，`temperature` 默认 0 |
| D11 样本 < 3 轮不出 p90 | `percentile()` 的调用侧 | 少样本 p90 = max，会误导 |

### 2.3 指标口径（公式）

| 指标 | 公式 | 备注 |
| --- | --- | --- |
| TTFT | `t(首个非空 delta) - t0` | 含 reasoning 首 token；单列首答案 token |
| TPOT | `(tLast - tFirst) / (outTokens - 1)` | 每 token 平均耗时 |
| ITL p90 | 相邻 chunk 间隔序列的 90 分位 | 抖动看这个 |
| 纯解码 TPS | `(outTokens - 1) / (tLast - tFirst) * 1000` | **主指标** |
| 端到端 TPS | `outTokens / tLast * 1000` | 副行，含 TTFT 与 prefill |
| 成功率 | `ok / total` | 失败不重试，失败即记一轮 |

`outTokens` 以 `usage.completion_tokens` 为权威；服务商不回 `usage` 时才按 chunk 数 / 字符数估算，并标 `estimated: true`（前端显示估算提示）。

### 2.4 五个坑的处理

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| ① 空 delta 毒化 TTFT | 首个 chunk 只有 `role` 或只有 `usage`，被当成首 token → TTFT 虚低 | 只在 `content`/`reasoning_content` 长度 > 0 时记首 token |
| ② 前缀缓存压低温启动 TTFT | 第二轮起 provider 命中缓存，TTFT 掉一半，误判「模型很快」 | 默认每轮注入随机 nonce 前缀，并记录 `prompt_cache_hit_tokens` |
| ③ 网关攒包 | 代理把整段响应攒齐再一次性下发 → TPS 虚高到几十万 | `suspectBuffered` 判定并在前端标「疑似被网关缓冲，TPS 仅供参考」 |
| ④ 用 chunk 数当 token 数 | 一个 chunk 可能含多个 token，也可能只含 usage | 以 `usage` 为权威，估算时标 `estimated` |
| ⑤ 少样本 p90 | 3 轮以下 p90 = 最大值 | 样本 < 3 轮不出 p90 |

> 攒包阈值刻意不写成 `itlP90 === 0`：真实网关攒包时仍可能有 0.1ms 级抖动（E2E 实测），而任何真流式模型的分块间隔都不可能 < 1ms（那已越过每秒 1000 token 的物理上限）。

### 3.2 实施中处理的真实问题

1. **路由顺序**：`/models/bench` 若注册在 `/models/:alias` 之后，`bench` 会被当成 alias 解析，直接 404 —— 已在 `server.ts` 中前置注册并补用例（`bench-api.test.ts`）。
2. **TTFT 被空块毒化**：首版用「第一个 chunk 到达时间」做 TTFT，mock 里首个 chunk 只有 `role`，TTFT 落到 0.2ms。改为只认非空内容后，与 vLLM/NVIDIA 口径一致。
3. **攒包判定阈值**：首版写 `itlP90 === 0`，E2E 实测网关攒包时仍报出 0.1ms 抖动导致漏判；改为 `itlP90 < 1`（物理上限论证见 §2.4）。
4. **截图与 rect 不同步（验证链路的真问题）**：抽屉是 `transform` 0.2s 过渡，`.open` 类一加 `vis()` 就为真，首轮截图恰在动画中途 → `done-dark` 的状态条取样整体偏 20px，被误读成「深色主题没画状态条」。已在 `verify-bench-ui.mjs` 的 `shot()` 里加 `settle()` 稳定判定，并要求「截图前布局已稳定」。这条经验对所有带过渡的抽屉截图都适用。
5. **满负载回归暴露一处既有用例的时序脆性**：首次全量 `vitest run` 有 1 例失败（`tests/api-stop-endpoint.test.ts` 6.2.6「停止后落盘」，`waitFor` 只给 3s 等异步落盘），单跑必过、满负载偶发超时。该用例与本需求无关，但会污染「全绿」结论——把等待落盘与等 run 启动的 `waitFor` 超时放宽到 8s（断言内容不变，只给慢机器余量），复跑全量转为 111 文件 / 1261 用例全绿。

## 六、已知限制

- **物理链路仍受网关影响**：客户端只能标注「疑似缓冲」，无法证明网关内部行为。
- **单机单并发**：不做分布式压测，结论只代表本机到 provider 的这一条链路。
- **不做质量评测**：只测速度与稳定性，不测正确率（需评测集，属另一需求）。
- **CLI 无 `/model bench`**：当前只在 WebUI 提供，CLI 子命令列为演进项。
- **`usage` 缺失时退化为估算**：部分兼容服务不回 `usage`，此时 token 数与 TPS 均为估算（前端有提示）。

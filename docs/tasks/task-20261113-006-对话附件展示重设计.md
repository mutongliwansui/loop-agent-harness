## 一、任务目标需求

### 1.1 背景（痛点）

用户反馈「对话上传文件进行问答，文件的展示样式不好看」。取证结论：**同一批附件在对话里被画成两套互不相干的形态**，且两边各自都缺信息。

| 位置 | 现状（代码核对 `webui/src/views/ChatView.vue`） | 症状 |
| --- | --- | --- |
| 待发送区 | `.file-pill`（`:2361`）胶囊：`padding:2px 4px 2px 8px`、`font-size:11.5px`、`--bg` 底 + `--line` 边 + `999` 圆角 | 图片与非图片仅靠有无 24px 缩略图区分；文件名 `max-width:190px` 硬截断且无 hover 全文 |
| 已发送气泡 | `.msg-file-chip`（`:1992`）另一套胶囊：`padding:3px 9px 3px 7px`、`font-size:12px`、`color-mix(currentColor 6%/22%)` 底边、**恒用文档 SVG 图标** | **图片附件退化为「文档图标 + 文件名」**，看图问答后回看无法辨认是哪张图（本期最重） |

六项具体缺陷：① **信息丢失**（气泡内图片无缩略图、无大小）；② **两套形态**（圆角/内距/字号/图标全不同，发送前后观感断裂）；③ **无类型识别**（PDF/Word/Excel/图片/代码全用同一枚图标）；④ **对比度不足**（气泡 chip 用 `--muted` 12px 灰字 + 6% 底，落在 `--brand-weak` 浅绿气泡上几乎融底，这是「不好看」的直接来源）；⑤ **无分组与容量感**（无分隔、无「共 N 个 / 共多大」，多附件把输入框顶高）；⑥ **无过程态**（上传完成才 push chip，上传期间零反馈）。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
| --- | --- | --- |
| 待发送区能渲染附件 | `ChatView.vue:1505-1532` `.chips` + `.file-pill`，`uploads: UploadChip[]` | ✅ 有数据源，形态需重做 |
| 待发送图片缩略图 | `UploadChip.thumbUrl`（`:106`），粘贴链路 `URL.createObjectURL`（`:984`），发送成功后 `releaseChips` 释放（`:856`） | ✅ 已具备，blob 生命周期已有管理 |
| 气泡内附件数据 | `m.attachments: MessageAttachmentVM[]`（`chat-stream.ts:147`），含 `fileName/bytes/path/mime`；`m.files` 由其派生（需求 20261113-003 D10） | ✅ **`bytes` 已有**，D7「显示大小」无需后端改动 |
| 气泡内图片缩略图 | `GET /uploads/view?path=&disp=raw`（`src/api/handlers/uploads.ts:140`），`path` 支持绝对路径 | ⚠️ 端点就绪，但**鉴权要求 Bearer**（`http-utils.ts:88-91`：`api.token` 非空时强制 `authorization` 头），`<img src>` 无法携带 → 必须 fetch→blob（见 D2） |
| 附件点击预览 | `onOpenAttachment`（`:435`）→ `onOpenPath` → `FilesView` → `openControlled`（`FilesView.vue:743`），图片走 `disp=raw` blob | ✅ 复用，不新增端点 |
| 视觉不可用警告 | `UploadChip.warn`（`:109`）+ `visionSkipReason`（`paste-files.ts:153`） | ✅ 保留，改为角标形态 |
| 上传中/失败态 | `uploadRaw` 后才 push chip（`:891`、`:977`），期间只有 toast | ❌ 缺失 —— **本期不做（D6 用户否决）** |
| 现有样式失效令牌 | `.msg-file-chip:hover` 用 `var(--fg)`、`:focus-visible` 用 `var(--accent)`，全仓 `style.css` **均未定义** | ❌ 现存 bug：悬停变色与键盘聚焦描边实际都不生效，本期顺带修掉 |

### 1.3 任务目标

1. **统一「附件卡」语言**：待发送区与气泡内共用一套视觉语法（同一圆角/描边/字号阶/图标族），发送前后不再割裂。
2. **气泡内图片显示真实缩略图**（D2）：88×88 图片砖 + `IMG` 类型字标 + 底部尺寸带，让「哪张是图」一眼可辨。
3. **补齐类型识别**（D3）：折角文件图标按族区分（图片/文档/表格/代码/压缩/PDF/PPT）+ 扩展名字标，纯中性色不引入彩色。
4. **补齐容量感**（D5/D7）：顶行「共 N 个 · 共多大」、单卡显示大小、超过 3 个折叠为「+N」。
5. **修掉失效样式**：`--fg` / `--accent` 换成真实令牌 `--text` / `--brand`。
6. **不新增后端端点**、不改 SSE 协议、不改 `attachments` 字段结构（沿用 20261113-003）。

### 1.4 设计约束

- **纯中性色 + 品牌绿**：不引入文件类型彩色，避免与既有图标体系冲突（D3）。
- **令牌不新增全局变量**：`--att-bg`/`--att-line`/`--att-cap` 用现有令牌表达；仅 `--att-card-bg`/`--att-card-line` 因「气泡底是 `--brand-weak`，卡片须恒定更亮一档」而必须给独立值，作用域限定在 `.msg-files` 内。
- **缩略图必须走 fetch + objectURL**：`api.token` 非空时端点强制 Bearer，`<img src>` 直连会 401（D2 修正）。
- **不动现有上传通道语义**：`✕` 仍为「移出注入列表，服务器文件保留」。
- **不擅自重启用户服务**（当前 `loop-agent.exe --serve` 占 3000 端口）。

## 二、方案设计

### 2.1 总体思路

```
                     ┌── 待发送区（composer）────────────────────────┐
  pick/paste ───────►│ uploads: UploadChip[]                         │
                     │  ├ 图片 → 52×52 图片砖（thumbUrl: blob）      │
                     │  └ 文档 → 52px 文档卡（折角图标+名+大小+字标）│
                     │  顶行：共 N 个 · 共多大        清空           │
                     └───────────────────────────────────────────────┘
                                        │ send()
                                        ▼
                     ┌── 已发送气泡 ─────────────────────────────────┐
                     │ m.attachments: {fileName,bytes,path,mime}     │
                     │  ├ 图片行：88×88 图片砖 ← fetch(/uploads/view │
                     │  │          ?disp=raw, Bearer) → objectURL    │  ← D2
                     │  └ 文档行：30px 胶囊（图标+名+大小+扩展名）    │  ← D7
                     │  两行分组（不混排，见 D9）                     │
                     └───────────────────────────────────────────────┘
                                        │ click
                                        ▼
                        onOpenAttachment → /uploads/view（已有）
```

### 2.2 关键设计决策

**D1｜待发送区改为「图片砖 + 文档卡混排流」，不再统一胶囊。**
图片用 52×52 砖（一眼可辨），文档用同高 52px 卡（名 + 大小 + 扩展名字标）。被否决：统一胶囊——图片只能挤在 24px 缩略图里，识别度不足，正是本次要解决的问题。

**D2｜气泡内图片缩略图走 `fetch + objectURL`，不直连 URL。**（**对原型的修正**）
原型推荐「复用 `/uploads/view?disp=raw`」。核对后发现：`api.token` 非空时该端点强制校验 `authorization` 头（`src/api/http-utils.ts:88-91`），而 `<img src>` 无法附加请求头 → 直连必 401。故实现为 `fetchRawUploads(path)` → `URL.createObjectURL(blob)`，并在组件卸载/路径变化时 `revokeObjectURL`。
*被否决*：给端点加 query token（会污染 URL 与日志）；改成 cookie 鉴权（跨全局改动，超出本需求范围）。

**D3｜文件图标按「族」区分，纯中性色 + 扩展名字标。**
四族覆盖上传场景：图片（山形+太阳）、文档（折角页+文本线）、表格（折角页+网格）、代码（折角页+`</>`）；PDF 复用文档族加 `PDF` 语义线，压缩包用拉链页形。被否决：按类型上色（与项目既有单色线性图标体系冲突）。

**D4｜删除按钮悬停浮出，不常驻。**
图片砖/文档卡 hover 或自身聚焦时才显示 17×17 圆形删除钮（`opacity:0 scale(.85)` → `1`）。省宽度、降噪声。被否决：常驻——多附件时每张卡上方都挂一个叉，视觉噪声明显。

**D5｜待发送区超过 3 个附件折叠为「+N」。**
第 4 个起折叠为虚线胶囊，点击展开。被否决：全部平铺——多附件把输入框顶高 2–3 行，正文输入区被压缩。

**D6｜不补上传中/失败重试态。**（**用户明确否决**）
原型推荐「先占位再上传」，用户答复「D6 不用补」。故保持现状：`uploadRaw` 成功后 push chip，上传期间仍只有 toast。列入演进项。

**D7｜气泡内文档胶囊显示大小，与待发送区一致。**
`MessageAttachmentVM.bytes` 已存在（`chat-stream.ts:149`），无需后端改动；`bytes` 缺失（存量数据）时不显示该段而非显示 0 KB。

**D8｜缩略图加载失败降级为文档胶囊，不出破图。**
`fetch` 失败或 `createObjectURL` 异常时，该附件按文档族渲染。理由：气泡内破图比缺图更难看，且失败原因（文件已删、越权）对用户无用。

**D9｜气泡内「图片行」与「文档行」分组渲染，不混排。**
图片要够大（88px）才看得清，文档胶囊要够扁（30px）才不臃肿；强行同高会让两者都变形（原型实测 64px 图 + 30px 胶囊混排时上下沿错位 34px）。被否决：混排一层 flex。

**D10｜顺带修复失效令牌，不改其他既有样式。**
`.msg-file-chip:hover` 的 `var(--fg)` → `var(--text)`；`:focus-visible` 的 `var(--accent)` → `var(--brand)`。这两个令牌全仓无定义，属既有 bug。仅修这两个选择器，不连带重构。

### 2.3 外部检索结论

| 来源 | 结论 | 对本任务的指导 |
| --- | --- | --- |
| MDN《Using object URLs to display images》 | `URL.createObjectURL` 创建的 URL 生命周期与 document 绑定，需显式 `revokeObjectURL` 释放，否则整页存续期内 blob 不回收 | D2 的缩略图必须登记并在卸载/切换时 revoke（气泡内附件数量随会话增长，不释放会持续吃内存） |
| Chrome 安全模型（fetch 规范） | `<img>` / CSS `url()` 发起的请求无法携带自定义请求头 | 直接支撑 D2 的修正：Bearer 鉴权下只能 fetch→blob |

### 3.3 气泡内缩略图缓存（新增，对齐 D2/D8）

```ts
/** path → objectURL；仅缓存已成功取到的，失败记入 failed 集合走文档胶囊降级 */
const sentThumbs = reactive(new Map<string, string>());
const sentThumbFailed = reactive(new Set<string>());
function ensureSentThumb(path: string): void;   // 幂等；内部 fetchRawUploads → createObjectURL
function sentThumb(path: string): string | undefined;
function releaseAllSentThumbs(): void;          // onUnmounted 调用
```

**边界**：

| 场景 | 行为 |
| --- | --- |
| `path` 为空（存量数据） | 直接落文档胶囊，不发请求 |
| 扩展名非图片 | 不请求 |
| fetch 非 2xx / 网络失败 | 记入 `sentThumbFailed`，降级文档胶囊，不重复重试 |
| 组件卸载 | `releaseAllSentThumbs()` 遍历 revoke |
| 同一 `path` 出现多次 | 缓存命中，只请求一次 |

**补正二（超长文件名，用户反馈）**：用户指出「上传文件名字超长没有处理」。CDP 几何实测复现并修复——
根因：`.msg-files` 是 `display:grid`，`.att-docs`/`.att-imgs` 是它的**直接网格项**，默认 `min-width:auto` 使其按 `min-content` 参与定宽。超长文件名（尤其无断点的中文、无空格的英文长串）把 `.att-docs` 的 min-content 顶到 642.8px，而气泡可用宽仅 550px → 整条胶囊溢出气泡右边界 79px，`bubble.scrollWidth(657) > clientWidth(578)`。文件名自身的 `text-overflow:ellipsis` 是生效的，但那只截断文字，**拦不住容器被 min-content 撑宽**，这正是原先遗漏的点。

| 修复点 | 改动 |
| --- | --- |
| `.att-docs` / `.att-imgs` | 补 `min-width: 0`（解除网格项 min-content 定宽） |
| `.s-doc` 胶囊 | 补 `min-width: 0`（允许被压缩，配合既有 `max-width:100%`） |
| `.att-doc` 待发送卡 | 补 `min-width: 0`；`max-width` 由 `230px` 改 `min(230px, 100%)`（极窄输入坞不再顶出） |
| `.ad-name` | 补 `min-width: 0` |

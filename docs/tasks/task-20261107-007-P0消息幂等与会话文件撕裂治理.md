# task-20261107-007 · P0 消息幂等与会话文件撕裂治理

> 对应需求编号：**20261107-007**（总方案见 [task-20261107-006](task-20261107-006-后台子任务可感知性与消息重复治理.md) §3.1）

## 一、问题与根因

### 1.1 现象

会话 sess_8dcc67b6 中，用户一次提交后，同一对话段（用户消息 + 助手回复 + tool_use/tool_result）重复出现 8 次。taskId 时间戳证据（`sub_a5d365a6_1794053663` 多次显示时间戳一致）证明 delegate 只执行了一次，重复发生在**消息持久化层**。

### 1.2 根因链（高置信）

会话文件**并发写入撕裂** → 解析失败按前缀恢复 → **历史回退到旧快照** → 以回退历史为基线继续追加 → 重复段累积：

```
两个 writeFile 交错写同一 tmp 文件（pid+毫秒撞名）
  → tmp 内容 = 新 payload 头 + 旧 payload 尾（撕裂）
  → rename 覆盖正式文件
  → 下次读取 JSON.parse 失败（"Unexpected non-whitespace character after JSON"）
  → 按错误 position 截取前缀恢复
  → 恢复出的是「旧消息列表的一部分」（历史回退）
  → 内存以此回退历史为基线继续追加新消息 → 落盘
  → 每撕裂一次，重复段 +1，滚雪球至 8 段
```

**证据**：`src/session/store.ts` 当前存在未提交改动（+30/-2），内容正是该问题的修复——① `tmpWriteSeq` 序号防 tmp 撞名；② `parseSessionJson` 容忍尾部残留按有效前缀读取。改动时间（20:07）早于出问题会话（20:12 启动），说明**运行中的服务进程加载的是修复前代码**，撕裂在旧代码下真实发生。新增的 `tests/session-file-recovery.test.ts` 即其回归测试。

### 1.3 遗留改动的定位

该改动是撕裂修复的**未提交部分**，与本任务直接相关：P0 实施第一步即**评审并提交该改动**（而非搁置），再在其上叠加幂等防线。

## 二、目标

1. 会话文件写入彻底消除撕裂（已由遗留改动修复，本任务收口提交）。
2. 即使文件损坏/历史回退，恢复路径也**不产生重复段**（幂等防线）。
3. 注入类写入（后台通知等）只追加增量，审计确认无历史重放。

## 三、方案设计

### 3.1 S1 收口撕裂修复（合流遗留改动）

- 评审 `store.ts` 遗留改动（tmpWriteSeq + parseSessionJson）与 `tests/session-file-recovery.test.ts`，补齐边界后随本任务一起提交。
- **parseSessionJson 前缀恢复的风险补丁**：前缀恢复只能作为「兜底可读」，不能作为「可信基线」——恢复成功时必须在返回数据上打标记（如 `degraded: true`），调用方（session-manager）对该会话**只读降级**：提示用户历史可能不完整，禁止在其上继续追加落盘（防止回退历史被固化、重复段滚雪球）。这是遗留改动未覆盖的关键缺口。

### 3.2 S2 消息稳定 ID 与追加幂等

- `SessionMessage` 增加稳定 `msgId`（`msg_<hex12>`，写入时生成，随消息持久化）。
- `updateSession`/`appendMessages` 写入路径：按 `msgId` 对**同 ID 消息原地替换**，不追加；内存合并（磁盘读入 + 内存新增）按 `msgId` 去重（保留首现）。
- 旧会话文件无 msgId：读取时按规则补生成（`msg_<seq>_<fileHash8>`，确定性可重算），保证同一文件多次恢复生成一致 ID。

### 3.3 S3 注入机制审计（M2）

- `background-notice.ts` 审计结论：注入本身为增量设计（drain 队列 → 注入 user 尾部消息），有 `notifiedAt`（runs JSON 落盘）+ 内存 `queued` 双重去重，**无历史重放**。
- 两个残余风险修复：① `markNotified` 失败时通知已 drain 但未落盘标记 → 进程重启后 `restoreBackgroundNotices` 会**重复补投**；修复：drain 成功后重试 markNotified，仍失败则 debug.log 并加入本次进程的 `queued`（已有）+ 考虑把 notifiedAt 冗余写一份到会话目录。② `''` 无归属桶会投给下一个 drain 的任意会话，多会话下可能投错——改为只投给「通知产生时活跃的会话」，找不到则丢弃并记日志。

### 3.4 S4 重复检测日志（M3）

- 恢复合并时发现重复段（同 msgId 或撕裂降级恢复）→ `debug.log` 记录来源、数量、文件名，便于事后定位。

### 8.2 与原方案的两处偏差（均为实施中发现的真实问题）

**偏差 1：S1b「禁止降级会话继续追加落盘」→ 改为「备份原始文件后允许继续写入」。**

- 原因：硬性拒写会让撕裂过的会话**彻底不可用**（用户每一轮都报错），比重复段更糟。
- 替代方案：写回前把原始文件复制为 `<file>.torn`（仅首次，不覆盖），再依赖 msgId 去重阻断重复段滚雪球。既保住原始数据可取证，又不牺牲可用性。

**偏差 2：新增「同会话写操作串行化」+ `rename` 退避重试（原方案未包含）。**

- 触发：T1 并发测试直接暴露生产 bug —— Windows 上并发 `rename` 覆盖同一文件时，后者抛
  `EPERM: operation not permitted`，**该轮会话数据直接没落盘**（调用方看到异常、历史停在旧版本）。
- 根因：`updateSession` 是「读文件 → 内存合并 → 写回」的 read-modify-write，并发调用会互相覆盖；
  即便临时文件不再撞名，目标文件的原子替换本身也会争用。
- 修复：① `renameWithRetry`（EPERM/EBUSY/EACCES 指数退避重试，最多 5 次）；
  ② `withSessionLock` 按 sessionId 串行化 `updateSession`/`rewriteMessages`（前序失败不阻塞后续）。
- 意义：这条比 msgId 更**根本**——它同时解释了「消息丢失」与「重复追加」两种表现。

## 一、需求背景

需求 20261114-003 落地了 `@loop-agent/core`，但分层出了偏差：把**宿主层职责**（插件清单挂载）放进了内核。

- `core/src/registry.ts` 的 `PluginRegistry` 只是 `createHost()` + `createRootContext()` 的薄封装，**没有**侵入 `context.ts` / `fiber.ts` / `service.ts` 一行——这说明它本就不属于内核。
- 设计 5.10 写明「**纯内存，无磁盘 IO**（磁盘动态加载是明确非目标）」，而用户要的注册中心**必须支持持久化**。留着它要么破坏内核纯净性，要么生造第二个注册中心。
- 仓库内**零业务引用**：`src/` / `webui/` / `desktop/` 对 `@loop-agent/core` 均无 import，`PluginRegistry` 只在 core 自身 `index.ts` / `README.md` / `CHANGELOG.md` 与 3 个测试文件出现。迁移零回溯成本。

用户原话：「core 之前我设计错了，core 里只做插件核心的定义，具体的注册中心放在 main 模块里。」

## 二、总体设计

```
┌───────────────────────────────────────────────────────────┐
│  main/  @loop-agent/main（新的主工程入口）                  │
│                                                            │
│   PersistentPluginRegistry ──▶ PluginStore ──▶ registry.json│
│        │  （挂载/卸载/启停/排序）  （原子写）  ~/.loop-agent/ │
│        │                                                   │
│        └── 组合 core 的定义层 ─────────────┐                │
│   createMainHost / 基础服务 / 启停骨架      │                │
└────────────────────────────────────────────┼───────────────┘
                                             │ import（workspaces 单副本）
┌────────────────────────────────────────────▼───────────────┐
│  core/  @loop-agent/core（收敛为纯定义层，0.2.0）            │
│   Plugin / Context / Fiber / Event / Service / Errors      │
│   ✗ PluginRegistry（本需求删除）                            │
└────────────────────────────────────────────────────────────┘
        ▲
        │ 零引用（本轮不动，后续逐步插件化迁移）
┌───────┴────────────────────────────────────────────────────┐
│  src/ 现有主工程（ReActAgent / api / webui 后端）            │
└────────────────────────────────────────────────────────────┘
```

**分层判据（写进设计文档 D 决策）**：内核只回答「插件怎么被定义、怎么被挂载、怎么被撤销」；`main` 回答「挂载哪些插件、按什么顺序、下次进程起来还记不记得、清单存哪」。

**依赖说明**：01 必须先做——`main` 的任务 03 要「实现」注册中心，若 core 还留着一个同名类，会出现两套语义并存的歧义窗口。02 是 03 的地基（先有 host 与包骨架才能写注册中心）。04 需两侧同时回归（core 删净 + main 新增）。05 是收口验证，须最后跑。

**与 P0/P1/P2 的映射**：任务 01+02 = P0（分层纠正 + 骨架可跑通），任务 03 = P1（持久化核心能力），任务 04+05 = P2（测试与文档收口）。

## 五、风险与约束

| 风险 | 影响 | 处置 |
|---|---|---|
| `PluginRegistry` 是 core `0.1.0` 的**已发布公开符号**，删除属 breaking | 若有外部消费方会断 | 按 `CHANGELOG` 既定约定「`0.x` 期 breaking 只升次版本」→ 升 `0.2.0`；CHANGELOG 单列「移除项」段落 |
| `main` 也进 `workspaces` 后，`@loop-agent/main` 依赖 `@loop-agent/core` 可能装出副本 | 双副本 → `instanceof` 静默失效 | 沿用 core 的 `boundary.test.ts` 思路，在 main 侧断言 `node_modules/@loop-agent/core` 是链接；`tsup` 配 `external: ['@loop-agent/core']` |
| 持久化落全局目录，测试会污染真实 `~/.loop-agent` | 测试残留 | 沿用主工程 `loopAgentHome()` 语义，读 `LOOP_AGENT_HOME` 环境变量（main 内自查实现，不 import `src/`，保持零反向依赖） |
| main 作为「新主工程入口」但没有实际入口进程 | 语义悬空 | 本轮只交付可编程入口（`createMainHost` + `restore` 骨架），不做 CLI/HTTP；**不声明** `src/` 已被替代，避免误导 |

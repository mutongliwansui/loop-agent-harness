## 一、任务目标需求

### 1.1 背景

任务 01–03 已交付可用的内核：包骨架落地、主链路跑通、进阶能力齐备，core 自身 97 个用例全绿。但**内核的「纯净性」目前只靠人工遵守，没有任何自动断言兜底**：

| 缺口 | 现实后果 |
|---|---|
| 无 boundary 测试 | 任何人后续在 `core/src` 里 `import` 一个三方包（或反向 import 主工程），都不会有人发现，「零三方依赖 / 零反向依赖」在几天内就会腐化 |

| 无 README / CHANGELOG | 其他模块要引用本包时无入口文档；`0.1.0` 的公开符号清单没有基线，后续无法判断何为 breaking |
| CJS 兼容边界未记录 | 「只收 ESM」的代价（`ERR_REQUIRE_ESM` 的 Node 版本门槛）散落在设计方案里，`core/README.md` 的消费方看不到 |

## 二、方案设计

### 2.1 总体思路

```
                    core/tests/（本任务新增 3 个文件）
   ┌──────────────────────────────────────────────────────────┐
   │ boundary.test.ts        ← 读源码/产物/依赖树，静态断言     │
   │   ① core/src/** 只 import 相对路径                          │
   │   ② package.json dependencies === {}                        │
   │   ③ 依赖树中 @loop-agent/core 计数 === 1                    │
   │   ④ dist/ 恰好 3 文件、无 .cjs/.d.cts                       │
   │   ⑤ core/src/** 无顶层 await                                │
   │   ⑥ exports 解析回归（C1/F1/G1/G2 口径）                    │
   ├──────────────────────────────────────────────────────────┤
   │ types.test-d.ts         ← 纯类型断言（编译期）              │
   ├──────────────────────────────────────────────────────────┤
   │ external-consumer.test.ts ← 临时目录造外部工程，真跑 tsc/node│
   └──────────────────────────────────────────────────────────┘
                              │
                              ▼
              core/README.md + core/CHANGELOG.md（消费方视角）
```

三条测试线各有明确职责：`boundary` 查**静态属性**、`types.test-d` 查**类型契约**、`external-consumer` 查**真实消费**。前两条快（毫秒级），第三条慢（要起 `tsc` 与 `node` 子进程），但在 core 自己的 `vitest` 里跑、不进主工程全量回归，可接受。

### 2.2 关键设计决策

| 编号 | 决策 | 选项 | 结论与理由 |
|---|---|---|---|
| **D19** | boundary 断言的实现方式 | A 正则扫源码 / B 起 `tsc` 走 AST / C 用 TS Compiler API | **A**：零依赖即可完成（`node:fs` 足够），且断言语义简单（「所有 `from` 的说明符要么以 `.` 开头，要么以 `node:` 开头」）。B 会让 core 的 devDeps 强依赖 TS 编译器行为，且慢 100 倍。C 同 B。**代价**：正则可能误判字符串里的 `from`——用「逐行匹配行首 import/export 语句」收窄，且 core 源码风格统一，风险可控 |
| **D20** | 单副本断言放在哪一层 | A 只断言 `node_modules/@loop-agent/core` 是链接 / B 递归遍历整棵树数 `@loop-agent/core` 出现次数 / C 运行期比对类引用 | **B**：A 会漏掉 `core/node_modules/@loop-agent/core`（嵌套副本，正是要防的场景）；C 就是 D15 已否决的 `CORE_INSTANCE_ID` 路子。B 用 `node:fs` 递归即可，遇到 `node_modules` 里的 `node_modules` 也要继续钻 |

| **D22** | 外部消费冒烟是否真起子进程 | A 只在进程内 `import` 一次 / B 临时目录 + 真跑 `tsc --noEmit` 与 `node` | **B**：A 验证的是「本仓库内能 import」，而 `exports` 解析**只在包作为依赖被消费时才生效**——进程内 `import` 走的是相对/绝对路径，压根不经过 `exports` 字段。B 是唯一能测出契约真实行为的办法，也是设计方案 8.3 明确要求的 |
| **D23** | CJS 冒烟失败是否让测试红 | A 期望通过，失败即红 / B 记录实测结果、不判红 / C 不测 | **B**：设计方案 8.3 原文即「目的是把兼容边界测出来写进 README，不要求全绿」。本机 Node 版本决定结果（支持 `require(esm)` 则通过，否则 `ERR_REQUIRE_ESM`），两种都是**正确行为**。测试只断言「二者必居其一，且错误码符合预期」，并把实际结果写进 README |
| **D24** | 临时消费工程放哪 | A 仓库内 `core/tests/fixtures/` / B `os.tmpdir()` 下建临时目录 / C `temp/` 目录 | **B**：A 会被 `files:["dist"]` 之外的目录污染、且 `tsc` 可能顺着上溯的 `node_modules` 解析到本仓库依赖，**测不出真实消费**。B 物理隔离，`afterAll` 清理。C 依赖仓库目录布局，且 `temp/` 被 `.gitignore` 忽略但仍在仓库内，仍有上溯解析风险 |
| **D25** | README 与 CHANGELOG 的语言 | A 中文 / B 双语 / C 英文 | **A**：与 `docs/` 现有文档一致（本项目文档主体为中文），且 `core/README.md` 是**代码库内**文档而非对外发布文档。用户已约定「双语同步」针对 `docs/readme/zh` 与 `docs/readme/en` 的用户手册，不是子包 README |

### 2.3 联网检索与既有结论复用

本任务的断言口径不引入新结论，全部复用设计方案 4.1② 已完成的实测矩阵（C1–C5 / F1–F3 / G1–G2），来源为 Node v24.17.0 + TS 5.x 在本机的实测记录。检索侧补充确认两点：

- **`require(esm)` 的 Node 门槛**：Node 20.19.0 与 22.12.0 起默认启用（无需 flag），此前需 `--experimental-require-module`。这与设计方案 8.3「README 写明 CJS 消费方需 Node ≥ 20.19 / 22.12」一致。
- **`tsc` 的声明推断**：`moduleResolution: nodenext` 下，`exports` 中 `import` 指向 `index.js` 时，TS 会优先同目录同名 `.d.ts`——这正是 F1（无 `types` 条件仍可解析）成立的机制。

## 三、任务详细设计

### 3.1 `boundary.test.ts` — 源码纯净性

```ts
/** 从 core/src 下所有 .ts 收集模块说明符 */
function collectSpecifiers(): Array<{ file: string; spec: string }>
```

逐行匹配 `^\s*(?:import|export)\b[^'"]*from\s+['"]([^'"]+)['"]`，以及副作用导入 `^\s*import\s+['"]([^'"]+)['"]`。

断言：
- 每个 `spec` 要么以 `.` 开头（相对路径），要么以 `node:` 开头；
- **不得**出现裸包名（`@scope/pkg`、`pkg`、`pkg/sub`）；
- 不得出现 `file://`、绝对盘符路径。

> 之所以连 `node:` 也允许但要求显式前缀：`import fs from 'fs'` 这种无前缀写法在 ESM 下虽可用，但会让人误以为有依赖；统一要求 `node:` 前缀，`boundary` 才能用一条规则同时排除三方包与「忘记前缀」的写法。

### 3.2 `boundary.test.ts` — 依赖树与产物

**零运行时依赖**：读 `core/package.json`，断言 `dependencies` 是空对象（`Object.keys().length === 0`）。`peerDependencies` / `optionalDependencies` 也须为空（否则同样是运行时依赖）。

**单副本**：

```ts
/** 递归找所有名为 @loop-agent/core 的目录，返回其 realpath 集合 */
function findCoreCopies(dir: string, acc: Set<string>): void
```

从仓库根 `node_modules` 开始递归（跳过 `.bin`、`dist`、`.vite*` 等缓存目录），命中目录名 `@loop-agent/core` 时记录 `realpathSync` 并**不继续下钻**（避免把同一个包的嵌套依赖重复计数）。

断言：`realpath` 集合大小 === 1，且该路径 === `core/` 的 `realpath`。

**产物形态**：`dist/` 下的文件集合恰好为 `['index.d.ts', 'index.js', 'index.js.map']`；断言无 `.cjs` / `.d.cts` / `.mjs` / `wrapper.*` 后缀文件。

**无顶层 await**：`core/src/**/*.ts` 每行不得匹配 `^\s*(?:const|let|var)?\s*await\b`（在模块顶层深度为 0 时）。简化实现：整文件不得出现行首（允许前导空白）`await` 语句——core 全是类/函数式代码，顶层 await 必然出现在行首无缩进处，用 `^await\b` 与 `^export\s+await\b` 两条即可，宽松且不会误伤函数体内的 `await`（那些都有缩进）。

### 3.3 `boundary.test.ts` — 无 CJS 产物

并入 3.2 的产物形态断言（同一处，避免重复读目录）。

### 3.4 `boundary.test.ts` — `exports` 解析回归（对应 D21）

按 4.1② 的**实测结论**写三条，全部为正向断言：

| # | 断言 | 对应实测 |
|---|---|---|
| ① | `dist/index.d.ts` 与 `dist/index.js` **同址同名**（同目录、主名相同） | 这是「`types` 顺序不构成风险」的真正前提（F2/F3 均通过） |
| ② | 构造「完全无 `types` 条件」的临时 `package.json` 副本（`exports` 仅 `import`+`default`），断言 `dist/index.d.ts` 存在 → 类型**仍可解析** | F1：证明 `types` 条件属零成本惯例，非常规硬依赖 |
| ③ | 断言当前 `core/package.json` 的 `exports["."]` 中 `types` 指向 `./dist/index.d.ts`，且该文件存在 | 锁死「契约与产物一致」这一事实 |

> **不写**的断言：「去掉 `types` 必须报 `TS7016`」（C5 的形态）——它需要「同时不存在同址声明」才成立，而 core 的产物**永远**有同址声明，写出来就是永远失败的假断言。③ 的 G1/G2 机制（异地声明时顺序影响选中哪份）在 core 布局下不可达，改为**文档记录**（§3.7 README 的「契约说明」段），不做测试。

### 3.5 `types.test-d.ts` — 公开契约类型断言

用 `expectTypeOf` 断言：

- `createRootContext()` 返回 `Context`，`ctx.get<Foo>('k')` 推导为 `Foo | undefined`；
- `ctx.provide('k', v)` 返回 `Disposer`；
- `Plugin` 的函数形态与对象形态都被接受；`inject` 支持 `string[]` 与 `{required, optional}`；
- `TypedEventBus<E>` 的 `emit`/`serial`/`parallel`/`waterfall` 参数与返回类型；
- 错误族 6 类的 `code` 为 `string` 字面量类型（若实现为 `CoreErrorCode` 联合类型则断言具体值）；
- `DiagnosticReport` 的 `disposeErrors` 为可选。

文件名用 `.test-d.ts`，在 `vitest.config.ts` 的 `include` 里**不被收集**（只收 `*.test.ts`）。执行方式二选一：
- 让 `tsc --noEmit` 覆盖它（core 的 `tsconfig.json` `include` 若含 `tests/**` 则自动生效）；
- 或用 `vitest typecheck`（需 `typecheck.include` 配置）。

**采用前者**：`npm run typecheck -w @loop-agent/core` 即验证，零新配置。需确认 `core/tsconfig.json` 的 `include` 覆盖 `tests/`，否则补上。

### 3.6 `external-consumer.test.ts` — 外部消费冒烟（对应 D22/D23/D24）

```
tmp = os.tmpdir()/loop-agent-core-consumer-<rand>/
├── package.json      { "type": "module", "dependencies": { "@loop-agent/core": "file:<repo>/core" } }
├── node_modules/@loop-agent/core  → 由 npm install 建立（或直接建链接）
├── tsconfig.json     { moduleResolution: "nodenext", module: "nodenext", strict: true }
└── src/main.ts       import { ServiceRegistry, CoreError } from '@loop-agent/core';
                      const r = new ServiceRegistry(); …
```

步骤：
1. 建临时目录与 `package.json` / `tsconfig.json` / `src/main.ts`；
2. `npm install --no-audit --no-fund --install-links=false`（把 `file:` 依赖装成链接）——**在临时目录内执行**，不污染仓库；
3. 跑 `npx tsc --noEmit -p tsconfig.json` → 断言退出码 0（**ESM 类型解析通过**）；
4. 跑 `node src/main.ts`（或先 `tsc` 出 js 再 `node`）→ 断言退出码 0 且 stdout 含预期标记（**ESM 运行时 import 通过**）；
5. CJS 支线（D23）：写 `cjs/main.cjs` 做 `require('@loop-agent/core')`，跑 `node cjs/main.cjs`：
   - 若成功 → 记录「本机 Node 支持 `require(esm)`」；
   - 若失败 → 断言 `stderr` 含 `ERR_REQUIRE_ESM` 或 `ERR_PACKAGE_PATH_NOT_EXPORTED`；
   - **两种都不判红**，把实际结果写入模块级变量供 README 断言引用（或不引用，仅 `console.info`）；
6. `afterAll` 递归删临时目录（Windows 下注意 `maxRetries` / `force`）。

耗时控制：`tsc` 一次约 2–5s，`npm install` 可能要 5–15s。给该文件设 `testTimeout: 120000`。

### 3.7 `core/README.md`（D25：中文）

结构：

1. **这是什么** — 零依赖插件机制内核，不接入任何业务
2. **如何在其他模块引用本包** — workspaces 已链接，直接 `import { … } from '@loop-agent/core'`；`engines.node >= 20.10`

### 7.3 关键实现说明

**boundary 用正则而非 AST（D19）**：只用 `node:fs` + 逐行匹配 `(?:import|export)\b[^;'"]*?\bfrom\s*['"]([^'"]+)['"]` 与副作用导入，core 源码风格统一，足以覆盖。断言规则简化为「说明符以 `.` 或 `node:` 开头」。

**单副本断言的递归边界（D20）**：从仓库根 `node_modules` 递归，命中 `@loop-agent/core` 后记录 `realpathSync` 且**不再下钻**；跳过 `.bin`、`dist`、`.vite*`、`.cache` 等目录，避免把缓存误算成副本。

**外部消费冒烟必须真起子进程（D22）**：进程内 `import` 走相对/绝对路径，**不经过** `exports` 字段，测不出契约。临时工程放 `os.tmpdir()`（D24），避免上溯解析到本仓库依赖。

**CJS 支线不判红（D23）**：本机 Node 是否支持 `require(esm)` 决定结果，两种都是正确行为；测试只断言「成功」或「`ERR_REQUIRE_ESM`/`ERR_PACKAGE_PATH_NOT_EXPORTED`」必居其一。

**未复活已证伪结论（D21）**：`boundary.test.ts` 只写三条正向断言；「异地声明 + `import` 在前 → 选中实现旁声明」的机制（G1 vs G2）在 core 布局下不可达，改为 README 文档记录，不做测试。

### 7.4 实施中实测发现的三处偏差（均已修正并锁成回归）

| # | 原计划假设 | 实测结论 | 处理 |
|---|---|---|---|
| 1 | 消费方 `interface Ev { … }` 可直接传给 `Plugin<Ev>` | **不成立**，报 `TS2344`：`Index signature for type 'string' is missing`。`EventMapBase` 带字符串索引签名，而 `interface` 不会隐式获得索引签名（`type` 别名不受影响） | 消费示例改为 `extends EventMapBase`；README §六「易踩的坑」记录；`external-consumer.test.ts` 加正/反双向回归 |
| 2 | `ctx.on('不在事件表里的名字', …)` 会报错 | **不成立**，因上述索引签名，`keyof E & string` 退化为 `string`，任意名字都合法。收益是「已声明名字有精确签名」，而非「未声明名字被拒绝」 | `types.test-d.ts` 把 `@ts-expect-error` 改为如实断言，并注明这是被实测校正的认知 |
| 3 | 断言「`core/node_modules` 不存在」即可证明 workspaces 提升生效 | **不成立**，vitest 4 仍会在 `core/node_modules` 下建 `.vite` / `.vite-temp` 缓存（`vitest.config.ts` 的 `cacheDir` 对缓存根未生效） | 断言口径改为「无依赖副本」：目录内除缓存外无其他条目，且绝无 `@loop-agent` 作用域目录 |

另有一处方法论陷阱值得记录：`tsc` 的诊断信息写在 **stdout** 而非 stderr，最初按 stderr 断言导致失败原因被掩盖。

还有一条与断言有效性直接相关的坑：F1 的「无 `types` 也能解析」用例，其临时 probe 目录最初建在 consumer 根之下，导致 `tsc` 上溯 `node_modules` 时命中指向真实 core 的 junction，**即使删掉 `index.d.ts` 也仍报解析成功**。把 probe 移到平级目录后反向对照才真正变红——这说明「无 `types` 可解析」的前提确实是「同址声明存在」，而非别的包在兜底。

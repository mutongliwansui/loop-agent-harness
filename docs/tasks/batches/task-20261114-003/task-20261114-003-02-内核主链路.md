## 二、方案设计

### 2.1 两处必要的接口补充（对设计方案 5.3 / 5.4 的增补）

设计方案给的 `Fiber` / `Context` 接口是**能力描述**，但直接照抄有两个死结，故增补两项：

**① `Fiber.ready(): Promise<void>`**（设计方案 5.4 未列）

`ctx.plugin(p)` 必须**同步返回** `Fiber`（`apply` 可能是异步的），于是调用方拿不到「加载已结束」的时刻，测试只能靠轮询或数微任务次数——两者都脆弱。故补一个 `ready()`：**本次加载尝试结束**即 resolve（终态为 `ACTIVE` / `FAILED`，若依赖未满足则停在 `PENDING` 后 resolve）。语义是「这次尝试结束了」，不是「已激活」，调用方仍需读 `state`。

**② `createRootContext<E>()`**（设计方案 5.11 的导出面未列）

设计方案 5.10 说「`PluginRegistry` 创建根 Context」，但 `PluginRegistry` 属任务 03。若本任务不提供任何 Context 入口，则整个包无法被使用、也无法测试。故先导出 `createRootContext()`，任务 03 的 `PluginRegistry` 建在它之上。

### 2.2 关键设计决策

- **D10：服务存放在**共享**的 `ServiceRegistry`，不按 Fiber 分层**
  - 理由：插件间共享服务是内核存在的意义；若每个 Fiber 各持一层，兄弟 Fiber 互相看不见，「同一 key 被两个 ACTIVE Fiber 提供 → 冲突」这条规则也无从判定
  - `isolate`（任务 03）实现为「在共享 store 之上按 key 覆盖的分支」，不改本任务结构

- **D11：Fiber 的**所有**清理都走统一的 disposer 栈**
  - `provide` / `effect` / `on` / 子 Fiber 全部折算成 disposer 入栈
  - 好处：撤销顺序、幂等、错误聚合只有一处实现，四条不变量天然一致；不会出现「服务被忘删」这类分支遗漏
  - 子 Fiber 单独存 `children` 集合，仅在**顺序**上先于自身 disposer 执行（不变量 4）

- **D12：`serial` 首个非 `undefined` 胜出即停；`emit`/`parallel` 的监听器异常只记录不外抛**
  - 与设计方案 5.6 表一致
  - core 零依赖、无 logger，故异常收集到 `TypedEventBus.listenerErrors()`，任务 03 的 `diagnose()` 可读取；**不 `console.error`**（库不应污染宿主输出）

- **D13：`apply` 抛错后立即回滚已注册副作用**
  - 保证 FAILED 状态**无泄漏**（设计方案 8.1 明确要求）
  - 回滚复用 `dispose()` 的同一套逆序逻辑

- **D14：`dispose()` 幂等靠缓存同一个 Promise**
  - 重复调用返回**同一** Promise 引用，disposer 不会二次执行

### 2.3 状态机实现要点

```
ctx.plugin(p)
   ↓
PENDING ──required 依赖满足──> LOADING ──apply 成功──> ACTIVE
   ↑                              │
   │                              └─apply 抛错→ FAILED（立即回滚，终态）
   │
   └──（任务 03：依赖重新满足时自动重载）

任意非 DISPOSED 状态 ──dispose()──> UNLOADING ──子先父后逆序撤销──> DISPOSED
```

- `apply` 执行期间若 Fiber 已被 `dispose()`（`state` 已离开 `LOADING`），**不得**把状态覆盖成 `ACTIVE`
- `FAILED` 不自动重试；`reload()` 显式重来（`dispose` 后重新 `start`）

## 三、任务详细设计

### 3.1 `src/types.ts`

```ts
export type Disposer = () => void | Promise<void>;
export type Inject = string[] | { required?: string[]; optional?: string[] };
export interface AnyListener { (...args: any[]): any }
export interface EventMapBase { [event: string]: AnyListener }
export type PluginFunction<E extends EventMapBase = EventMapBase> = (ctx: Context<E>) => void | Promise<void>;
export interface PluginObject<E extends EventMapBase = EventMapBase> {
  name?: string; inject?: Inject; apply(ctx: Context<E>): void | Promise<void>;
}
export type Plugin<E extends EventMapBase = EventMapBase> = PluginFunction<E> | PluginObject<E>;
export type FiberState = 'PENDING' | 'LOADING' | 'ACTIVE' | 'FAILED' | 'UNLOADING' | 'DISPOSED';
export interface DiagnosticReport { fibers: [...]; services: [...] }   // 类型先定，实现留 03
```

`Context` 用**泛型参数**注入事件表（不用 TS 全局声明合并，避免多模块撞名，见设计方案 5.3）。

### 3.2 `src/errors.ts`（补全 5 个子类）

| 类 | code |
|---|---|
| `CoreError`（已有） | `CORE_ERROR` |
| `CircularDependencyError` | `CORE_CIRCULAR_DEP` |
| `ServiceNotFoundError` | `CORE_SERVICE_MISSING` |
| `ServiceConflictError` | `CORE_SERVICE_CONFLICT` |
| `PluginLoadError` | `CORE_PLUGIN_LOAD` |
| `FiberDisposedError` | `CORE_FIBER_DISPOSED` |

子类只固定 `code` 与 `name`，其余走基类。

### 3.3 `src/service.ts`

```ts
export interface ServiceEntry<T = unknown> { key: string; impl: T; ownerFiberId: string }

export class ServiceRegistry {
  private readonly entries = new Map<string, ServiceEntry>();
  get<T>(key: string): T | undefined;
  has(key: string): boolean;
  keys(): readonly string[];
  provide<T>(key: string, impl: T, ownerFiberId: string): void;  // 冲突抛 ServiceConflictError
  remove(key: string): boolean;
  entriesSnapshot(): readonly ServiceEntry[];                   // 供 diagnose（03）
}
```

### 3.4 `src/events.ts`

| 方法 | await | 顺序 | 返回 | 异常 |
|---|---|---|---|---|
| `emit` | 否 | 注册序 | 无 | 记录，不外抛 |
| `serial` | 是 | 注册序，首个非 `undefined` 即停 | 有 | 外抛 |
| `parallel` | 是 | 全部并行 `allSettled` | 无 | 记录，不外抛 |

监听器按注册序保存在 `Map<string, Set<entry>>`（`Set` 保序），每条带 `ownerFiberId` 便于排障。

### 3.5 `src/fiber.ts`（四条不变量）

1. `dispose()` 幂等（同一 Promise 引用）
2. disposer **逆序**、异步**串行** `await`
3. 单个 disposer 抛错**不中断**其余，聚合为 `AggregateError` 记录
4. 父 Fiber 先递归 dispose 子 Fiber，再撤销自身 disposer

### 3.6 `src/context.ts`

`ContextImpl` 委托给 `ServiceRegistry` / `TypedEventBus` / 当前 `FiberImpl`：

- `provide` → `store.provide(...)` + 注册「删 key」disposer
- `effect` → 立即执行 `body()` + 把返回的 disposer 入栈
- `on` → 注册监听 + 入栈「移除监听」disposer
- `plugin` → 建 `FiberImpl`、挂到当前 Fiber 的 children（或根集合）、异步 `start`、**同步返回**

### 3.7 `src/index.ts`（本任务导出面）

`Plugin` 系类型、`Context`、`Fiber`、`FiberState`、`Disposer`、`Inject`、`EventMapBase`、`DiagnosticReport`(type)、`TypedEventBus`、`ServiceRegistry`、`createRootContext`、6 个错误类。

`PluginRegistry` / `isolate` / `diagnose` / `waterfall` 留任务 03。

### 6.3 实施期三处修正（已体现为最终代码）

1. **`effect` 的 body 语义按设计落实，测试写法先错后改**
   初版测试把 disposer 直接当 `body` 传入，误以为「body 就是 disposer」。实际契约为 `effect(body)`：`body` **立即执行**，其**返回值**才是 disposer。已按 D11 修正测试并补三点断言：body 立即跑、返回非函数抛 `TypeError`、卸载时执行 disposer。

2. **`ctx.plugin` 不接受泛型参数（测试侧多写了类型实参）**
   `Context<E>` 在 `createRootContext<AppEvents>()` 时已绑定事件表，`plugin(p: Plugin<E>)` 无需再传 `<AppEvents>`。初版测试写成 `ctx.plugin<AppEvents>(...)` 导致 `TS2558`，已全部去掉。

3. **`serial` 的事件表签名需容纳异步监听器**
   `decide: (n: number) => number | undefined` 不接受 `async` 监听器（返回 `Promise<number>`）。事件表签名改为 `number | undefined | Promise<number | undefined>`；这与 `serial` 实现一致——它对每次调用都 `await`。

### 6.4 两处对设计方案的增补（已在 2.1 说明，实际生效）

- **`Fiber.ready()`**：`ctx.plugin()` 同步返回 Fiber，调用方否则拿不到「本次加载尝试结束」的时刻。语义是「尝试结束」，终态仍需读 `state`（`PENDING` 也 resolve）。
- **`createRootContext()`**：`PluginRegistry` 属任务 03，本任务若无 Context 入口则整包不可用、不可测。

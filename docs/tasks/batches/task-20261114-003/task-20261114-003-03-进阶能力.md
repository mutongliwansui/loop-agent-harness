## 二、方案设计

### 2.1 D18（**本任务唯一的设计冲突裁决**）

**冲突原文**：设计方案 8.2 P1 写

> 依赖动态重载：撤销提供者 → 依赖方自动 `UNLOADING → DISPOSED`；重新提供 → 自动回 `ACTIVE`

**冲突点**：`DISPOSED` 在 5.5 状态机与任务 02 实现中都是**终态**——
- `FiberImpl.start()` 见 `DISPOSED` 直接 `return`，不执行 `apply`；
- `FiberImpl.reload()` 见 `DISPOSED` 抛 `FiberDisposedError`。

因此「→ DISPOSED」与「自动回 ACTIVE」**不可能同时成立**：已经 DISPOSED 的 Fiber 没有任何合法路径回到 ACTIVE。

**裁决：依赖失效时回滚到 `PENDING`，不是 `DISPOSED`。**

理由：
1. `PENDING` 的语义本来就是「已声明、硬依赖未就绪、`apply` 不被调用」，恰好等于「等 provider 回来」。这比新造一个「软卸载」态更省概念。
2. 副作用照样撤销干净（复用 `rollback` 的逆序 disposer 栈），无泄漏——P1 的实质诉求（不留悬空引用）已满足。
3. 只有 `PENDING` 才可能「自动回 ACTIVE」，与同一句验收的后半段自洽。

**设计文档同步**：§8.2 该条措辞改为 `UNLOADING → PENDING`，并在 11.1 修订记录留痕。

### 2.2 isolate 的落地方式

`isolate(keys)` **返回一个新的 Context**（不创建 Fiber、不改状态机）：

```ts
ctx.isolate(['store'])   // → 新 Context，其子树内 'store' 走独立分仓
```

每个隔离域是一层 `IsolationScope { keys: Set<string>, store: ServiceRegistry }`。Context 持有一个**从外到内的 scope 链**；查找按「最内层声明该 key 的 scope 胜出，且不回退到外层」：

| 操作 | 规则 |
|---|---|
| `get(k)` | 若某层 scope 声明了 `k` → 只问该层 store（没有就 `undefined`，**不回退根 store**）；否则问根 store |
| `provide(k)` | 同上定位目标 store；冲突检测在各 store 内部独立进行 |
| `services()` | 根 store 的 key **扣除**被任何 scope 遮蔽的 key，再并上各 scope 实际提供的 key |
| `inject` 探针 | 改用子 Context 的可见性判定，使「隔离域内的插件依赖隔离域内的服务」成立 |

事件总线**不隔离**（D12）：跨域通知必须全局。

### 2.3 epoch reconcile 的落地方式

host 上跑一个**单飞 + 脏标记**的收敛循环，服务增删后触发：

```
service provide/remove  ──scheduleReconcile──>  reconcile pump
                                                 │
        ┌────────────────────────────────────────┘
        ↓  循环直到无新变更
   ① 依赖失效的 ACTIVE Fiber → deactivate()（回滚副作用 → PENDING）
   ② 依赖就绪的 PENDING Fiber → start()（→ ACTIVE 或 FAILED）
```

要点：
- **单飞**：已在跑时只置 `dirty`，返回同一个 in-flight Promise，避免并发重入把同一 Fiber 拉两次。
- **脏标记循环**：`apply` 内部又注册服务会再次触发，必须循环到收敛，否则一次挂载多插件会漏掉后续重算。
- **只碰 ACTIVE / PENDING**：`FAILED` 是终态（D10），重试会掩盖 bug。
- 注销路径天然复用：Fiber 卸载 → 其 disposer 栈里 Context 注册的「删 key」disposer 执行 → 同样触发 reconcile。

### 2.4 waterfall 语义

```ts
waterfall(event, fallback, ...args)
```

监听器比普通监听器**多一个尾部参数 `next`**：调用 `next()` 表示「我不处理，交给下一个」；**不调用即短路**，其返回值就是结果。全链都委托则调 `fallback`。

- 无监听器 → 直接 `fallback(...args)`
- 监听器抛错 → **外抛**（调用方在等值，吞掉会拿到错误结论，与 `serial` 一致）

## 三、任务详细设计

### 3.1 `src/types.ts`（增量）

```ts
export interface DiagnosticReport {
  fibers: Array<{
    id: string;
    name: string;
    state: FiberState;
    missing: string[];
    error?: { code: string; message: string };
    /** 卸载期 disposer 抛错的摘要（可选，不变量 3 要求可诊断） */
    disposeErrors?: string[];
  }>;
  services: Array<{ key: string; ownerFiberId: string; isolated: boolean }>;
}
```

`disposeErrors` 为**可选增量**，不破坏任务 02 已定契约。

### 3.2 `src/service.ts`

`ServiceRegistry` 结构不变（`isolate` 靠**多实例**而非改单例结构实现），仅补 `entriesSnapshot()` 的既有能力复用。

### 3.3 `src/events.ts`（新增 `waterfall`）

```ts
async waterfall<K extends keyof E & string, R>(
  event: K,
  fallback: (...args: Parameters<E[K]>) => R | Promise<R>,
  ...args: Parameters<E[K]>
): Promise<R>
```

内部用游标 `i` + 递归 `next()` 实现；监听器以 `(entry.fn as (...a: unknown[]) => unknown)(...args, next)` 调用（`E[K]` 不含 `next`，需断言）。

### 3.4 `src/fiber.ts`（新增 `deactivate()`）

```ts
/** 依赖失效时回滚到 PENDING（不置 DISPOSED，见 D18） */
async deactivate(): Promise<void>
depsSatisfied(): boolean
```

`rollback` 增加子 Fiber 处理模式：`dispose`（原路径，子也彻底卸载）与 `deactivate`（子也回 PENDING，保留重载可能）。父 Fiber 重新激活时子树可随之复活。

### 3.5 `src/context.ts`

- `Context` 接口补 `isolate(keys): Context`、`diagnose(): DiagnosticReport`
- `ContextImpl` 增加 `scopes: readonly IsolationScope[]`、`hasService(key)`、`findScope(key)`
- `CoreHost` 增加 `scopes: IsolationScope[]`（供 diagnose 汇总）与 `scheduleReconcile(): Promise<void>`
- `plugin()` 的 `probe` 改为 `(key) => childCtx.hasService(key)`

### 3.6 `src/registry.ts`（新增 `PluginRegistry`）

```ts
export class PluginRegistry<E extends EventMapBase = EventMapBase> {
  readonly context: Context<E>;
  readonly host: CoreHost<E>;
  mount(plugins: readonly Plugin<E>[]): Promise<readonly Fiber[]>;
  fibers(): readonly Fiber[];
  diagnose(): DiagnosticReport;
  dispose(): Promise<void>;   // 逆序整体卸载
}
```

纯内存、无磁盘 IO。

### 3.7 `src/index.ts`

补导出 `PluginRegistry`。其余内部结构（disposer 栈、host 序号、收敛循环）不导出。

> 实施补充：`IsolationScope` 因是公开接口 `CoreHost.scopes` 的字段类型而**必须**导出（否则 `tsc` 报私有类型泄漏），属**类型级最小暴露**——仅供类型推导，不提供任何构造函数或运行时句柄，使用方无法据此造出隔离域。

### 6.3 关键实现说明

**D18 裁决落地**：依赖失效时依赖方回滚到 `PENDING` 而非 `DISPOSED`。`PENDING` 语义本就是「已声明、硬依赖未就绪、`apply` 不被调用」，副作用照样经逆序 disposer 栈撤销干净（无悬空引用），且只有它才可能自动回 `ACTIVE`。

**reconcile 收敛循环**：单飞 + 脏标记。已在跑时只置 `dirty` 并返回同一 in-flight Promise；`apply` 内部再注册服务会再次触发，循环到无新变更为止。只碰 `ACTIVE`/`PENDING`，`FAILED` 为终态不重试。

**isolate 用多实例实现**：`isolate(keys)` 返回新 Context（不建 Fiber、不改状态机），每个隔离域是一个独立 `ServiceRegistry`，查找按「最内层声明该 key 的 scope 胜出且不回退」。事件总线不隔离（D12）。

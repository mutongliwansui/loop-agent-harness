## 一、批次目标

把 `ocrImage` 从「纯文本提取器」升级为「保留版面的取字器」：一条链路修掉「名称与日期不对应」，另一条补上「表格与小字」能力。

## 二、必要性

实测（2026-11-12）确认三件事，构成拆两个任务的依据：

1. `result.Lines` 有 45 行，但 `engine-winrt.ts` 只落盘 `result.Text`，而 `Text` 里**控制字符数为 0**——后处理三条规则全部空转。这是**纯缺陷**，修复收益立竿见影、风险最低 → 任务 01。
2. 只按 `Lines` 分行仍读不出表格：名称与日期被引擎切成不同 `Line`，需按 `OcrWord.BoundingRect` 做 y 聚类重建视觉行（实测 45 Lines → 23 视觉行，名称日期全部同行）。这一步是**算法新增**，要配单测与真机对比 → 任务 01（y 聚类）/ 任务 02（列聚类成表格）。
3. `scale`/`crop` 是用户已在手工做的事（`temp/` 两个临时脚本），且放大收益非单调，必须做成**显式参数**而非默认 → 任务 02。

## 三、为什么要拆两个任务，而不是一个

| 判据 | 结论 |
| --- | --- |
| 改动性质 | 任务 01 是**缺陷修复**（既有规则没生效），任务 02 是**能力新增**（schema 变更 + 新算法 + 缓存结构变更） |
| 验收方式 | 任务 01 可用「23 行、名称日期同行」单点判定；任务 02 需多张图对比 table/scale 效果，验证成本高 |
| 风险面 | 任务 01 只动引擎输出与 layout 纯函数；任务 02 要动工具 schema（影响前缀缓存与预算测试）与缓存结构（影响所有 OCR 调用方） |
| 可回退性 | 任务 01 完成即可上线并获得主体收益；任务 02 若受阻可整体不做，不影响 01 |

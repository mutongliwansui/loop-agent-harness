## 一、任务目标需求

### 1.1 背景（痛点）

用户上传资源管理器文件列表截图（1293×1164，21 行文件、每行「名称 + 修改日期」）请 `ocrImage` 取字，得到的是 **21 个文件名连成一坨、21 个日期连成另一坨**，名称与日期无法对应。

根因不在光识别质量，而在**结构信息在引擎出口就被丢弃**：

| 观测项 | 实测值 | 含义 |
| --- | --- | --- |
| `result.Lines.Count` | 45 | 引擎已按行切好 |
| `result.Text` 长度 | 1261 | 却被拼成一整行 |
| `result.Text` 内控制字符数 | **0** | 换行符一个都没有 |

`engine-winrt.ts:205` 只落盘 `result.Text`，`result.Lines` 弃用；而 `postprocess.ts` 的 `collapseInnerSpaces`（行内空白压缩）与 `normalizeOcrLines`（空行收敛、行尾去空白）都以 `\n` 为切分前提，单行输入下**永不触发**。更糟的是 `collapseInnerSpaces` 会把单元格之间的多空格压成单个，**连最后的列分隔线索也一并抹掉**。

### 1.2 现状梳理

| 环节 | 现状 | 结论 |
| --- | --- | --- |
| 引擎输出 | `engine-winrt.ts:205-208` 只写 `[string]$result.Text` 到 `out.txt` | 需改为同时落结构化 `out.json` |
| 行数回传 | `:212` 已 `Emit 'LINES'`，但 `OcrResult` 无该字段，Node 侧白取 | 需让 `OcrResult` 带上行/词计数 |
| 后处理 | `postprocess.ts` 三规则齐备，缺 `\n` 输入使其空转 | **规则不需要改**，只需给它真换行 |
| `\r` 清理 | `:206` `Replace([char]13,'')` 是死代码（`Text` 无控制字符） | 保留无害，注释需改口径 |
| 视觉行 | 引擎的 `Lines` 粒度 ≠ 人眼行：名称与日期 y 相同却被切成两个 `Line` | 需按 `BoundingRect` 做 y 聚类重建（**本任务核心**） |
| 调用方 | `analyzeImage` 降级、`fileRead` 文档图片都走 `runOcr` 只要 `text` | 输出变好即自动受益，签名不变 |

### 1.3 任务目标

1. 引擎按 `OcrLine` / `OcrWord.BoundingRect` 落盘结构化结果（`out.json`），并保留 `out.txt` 纯文本；
2. Node 侧解析结构化数据，`OcrResult` 新增 `lines`、`imageSize`，并把 `行数/词数` 透出到工具结果头；
3. 新增 `src/ocr/layout.ts` 的 `buildVisualLines()`：按 y 中心聚类把词归并为**视觉行**，使名称与日期同行（实测 45 Lines → 23 视觉行）；
4. 让 `collapseInnerSpaces` / `normalizeOcrLines` 在真实多行输入上生效（补单测证明触发）；
5. 结构化解析失败时回落 `out.txt`，绝不因解析失败丢结果。

### 1.4 设计约束

- 脚本须保持 **Windows PowerShell 5.1 兼容**且**全 ASCII 无 BOM**（内网机 Win10）；
- 中文只走 OutPath 文件回传，stdout 仅放 `KEY=VALUE` ASCII（沿用 `engine-winrt.ts:10-11` 约定）；
- 不用 `ConvertTo-Json`（PS 5.1 对单元素数组会退化为标量），手写 JSON 拼接 + `Escape-Json`；
- 布局层为**纯函数**（零 IO），可独立单测；
- 幂等：对已分行输入重复执行逐字节不变；有/无 CJK 字间空格两种输入结果一致；
- 零新增 npm 依赖。

## 二、方案设计

详见 [设计方案 §三/§四](../../../designs/2026-11-12/设计方案-20261112-003+OCR行结构与版面还原.md)。本任务采纳的决策：

| 决策 | 采纳 | 要点 |
| --- | --- | --- |
| D1 行结构传输 | **JSON 文件回传** | 新增 `out.json`，保留 `out.txt`，解析失败回落 |
| D2 `layout` 默认值 | **`text`** | 本任务只实现 `text`，不猜表格 |
| D3 聚类参数 | **相对中位字高** | `tolY = max(3, median(h) × 0.6)`，行中心迭代收敛 |
| D8 耗时口径 | 本任务只加**词数/行数**，分段计时留任务 02 | 避免一次改太多 |
| D10 幂等 | **硬约束** | 补两种输入的等价性单测 |

### 2.1 关键实现点：为什么不是「按 Lines 分行」就够

实测对比（同一张图）：

| 方案 | 行数 | 首行 | 名称/日期同行 |
| --- | --- | --- | --- |
| 按 `Lines` 分行 | 45 | `小 智 前 后 台 … .zip` | ❌ 仍是两坨 |
| 按 y 聚类重建 | **23** | `winrt-ocr-probe.ps1 \| 2026/11/12 17:19` | ✅ 全对齐 |

原因：引擎把「名称」和「日期」当成两个 `Line`（中间空白大），但两者 **y 基线相同**——它们是同一个**视觉行**。所以必须按 `BoundingRect` 的 y 中心聚类，而非信任 `Line` 切分。

### 2.2 数据流

```
PowerShell: BitmapDecoder → RecognizeAsync
   → 遍历 result.Lines[i].Words[j].BoundingRect → 拼 out.json
   → 同时把 result.Text 写 out.txt（兼容）
Node: readFile(out.json) → JSON.parse
   → 失败则回落 out.txt，warnings 记一条
   → buildVisualLines(lines) → 每行词按 x 排序拼接 → 行文本
   → postProcessOcrText(joined) → 三条规则真正生效
```

## 三、实施计划

1. **脚本侧**（`src/ocr/engine-winrt.ts` 的 `WINRT_PS1`）
   - 新增 `Escape-Json` 函数（转义 `\ " \b \f \n \r \t` 与 U+0000–U+001F）；
   - 遍历 `result.Lines` / `line.Words` / `word.BoundingRect` 手写拼 JSON，写 `-OutPath` 同目录的 `out.json`；
   - `out.txt` 继续写 `result.Text`（保持既有行为，供回落）；
   - stdout 追加 `WORDS` 与 `IMGSIZE`（纯 ASCII）；
   - 把 `:206` 死代码注释改为「Text 实测不含 CR/LF，此行为防御性保留」。

2. **类型侧**（`src/ocr/types.ts`）
   - 新增 `OcrWord {t,x,y,w,h}`、`OcrLine {text,words}`；
   - `OcrResult` 增 `lines?: OcrLine[]`、`imageSize?: {width,height}`；
   - `OcrOptions` 预留 `layout?`（本任务固定 `text`）。

3. **布局层**（新增 `src/ocr/layout.ts`）
   - `buildVisualLines(lines): VisualLine[]`——摊平全部词，按 y 中心聚类（容差 `max(3, median(h)*0.6)`），行内按 x 排序；
   - `renderTextLayout(lines): string`——逐视觉行按词拼接后接 `\n`，分隔**三档**：横向空隙大于列阈值（`0.4×medH` 以上且大于列阈值 `1.5×medH`）用 ` | ` 标记列、极小空隙（`< 0.4×medH`）视为同一 token 被引擎切开而**直接相连不插空格**（否则 `2026/11/12` 会变 `2026 / 1 1 / 1 2`，这是实测缺陷）、其余用单空格；两侧均为拉丁字母时即使小间隙也保留空格（避免 `hello world` 粘连）；行内 CJK 间隙交由既有 `mergeCjkSpaces` 处理；
   - 全函数纯、无 IO。

4. **编排侧**（`src/ocr/run-ocr.ts`）
   - `runOcr` 在拿到 `raw.lines` 时用 `renderTextLayout` 生成文本再进 `postProcessOcrText`；无 `lines`（http 引擎）时走原路径；
   - `buildOcrResultText` 头部加 `行数: N | 词数: M`（有结构化数据时才加，避免 http 引擎出现 `行数: 0`）。

5. **单测**（新增 `tests/ocr-layout.test.ts`，扩充 `tests/ocr-engine.test.ts`）
   - y 聚类：构造「名称 y=100 / 日期 y=101」的两 `Line`，断言合并为 1 个视觉行且按 x 排序；
   - 23 行回归：以实测样本（脱敏后内联为 fixture）断言行数与首行形态；
   - 幂等：`renderTextLayout` 输出再经 `postProcessOcrText` 两次结果一致；有/无字间空格两种输入归一化后一致；
   - 后处理生效：多行输入断言空行收敛与行尾去空白**确实被触发**（用 `spy` 或断言中间态）；
   - `Escape-Json`：引号、反斜杠、换行、制表符、控制字符全覆盖；
   - 解析失败回落：`out.json` 写成坏 JSON，断言仍返回 `out.txt` 内容且带告警。

6. **文档**
   - `docs/readme/{zh,en}/project-structure.md` 新增 `src/ocr/layout.ts`；
   - `docs/readme/{zh,en}/built-in-tools.md` 的「保持原始阅读顺序与换行」措辞在此任务后**变为事实**，核对无需改动，但需在结果示例里补「行数/词数」标注。

## 六、风险与回滚

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 手写 JSON 转义漏字符 | 解析失败或文本损坏 | `Escape-Json` 单测覆盖全部特殊字符；解析失败回落 `out.txt` |
| PS 5.1 不支持某语法 | 内网机脚本报错 | 只用 5.1 特性；本地 Win11 用 `powershell.exe`（Desktop 5.1）验证 |
| `out.json` 体积大（长文档图） | 临时文件写入耗时 | 仅含 bbox 整数与词文本，实测图约 20KB；`rm` 兜底在 `finally` |
| y 聚类并入大标题 | 行错位 | 容差基于中位字高，大字天然不合并；23 行样本已证无错并 |

**回滚**：`renderTextLayout` 短路为「直接返回 `out.txt`」即恢复原行为，改动 3 行内；`out.json` 与 `out.txt` 并存保证任何一步失败都有退化路径。

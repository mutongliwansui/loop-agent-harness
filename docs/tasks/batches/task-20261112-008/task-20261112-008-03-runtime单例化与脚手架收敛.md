## 一、任务目标需求

### 1.1 背景（痛点）

即使配置层四层化，`WorkspaceRuntime.build()` 仍然为**每空间**新建 `ConfigLoader`、`ConfigWriter`、`SkillLoader` 并 `skillLoader.scan(root)`：

- `src/api/workspace-runtime.ts:277,282,285-286`
- 结果：N 个空间 → N 份配置实例、N 次 skill 扫描；`dream-scheduler.ts` 还在循环里 `rt.configLoader.load()`

另外 `resolveWorkspaceRuntime()`（`src/api/handlers/sessions.ts:92-120`）会把 `ctx.configLoader/configWriter/skillLoader/deps.getConfig` 全部改写到目标空间。配置全局化后这些改写不仅多余，还会让「本该读全局的 handler 读到某空间实例」。

最后，`ensureScaffold`（`src/bootstrap/scaffold.ts:39-47,73`）与 `defaultBootstrapPaths`（`doctor.ts:50-57`）仍会为每个新空间创建 `.agent-config.json` 的 `{}` 与 workspace skills 目录——不清理，全局化形同虚设。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
|---|---|---|
| 配置实例 | `workspace-runtime.ts:277,282` 每空间新建 | 收敛为进程级单例 |
| skill 加载器 | `workspace-runtime.ts:285-286` 每空间 scan | 收敛为进程级单例，scan 一次 |
| ctx 指针改写 | `sessions.ts:106-111` 改写六个字段 | 只保留 sessionStore/runAgent/sessions/createMemoryKit |
| 脚手架 | `scaffold.ts:73` 建 workspace skills；`39-47` 写 `{}` 配置 | 只建 global skills |
| 体检 | `doctor.ts:98-119` 检查 workspace 配置与 skills | 删除对应检查项 |
| Dreaming 配置 | `dream-scheduler.ts:390,507,832` 读 `rt.configLoader` | 改读进程级 |
| 启动注入 | `bootstrap.ts:109-113` 注入 rt 的 loader/writer/skillLoader | 改注入单例 |

### 1.3 任务目标

- `WorkspaceRuntime.build()` 不再创建 ConfigLoader/ConfigWriter/SkillLoader；对应字段从 `WorkspaceRuntime` 移除（或改为只读引用进程级单例）
- `WorkspaceRuntime` 仍按 root 创建 `SessionStore`、`AgentPool`、memory kit —— **内容仍按空间**
- `resolveWorkspaceRuntime` 不再改写 config/skill 相关 ctx 字段
- `ensureScaffold` 只建 `~/.loop-agent/skills`；不再写 `{ws}/.agent-config.json`
- `checkBootstrap` 删除「工作空间配置缺失」「工作空间 skills 缺失」检查项
- `dream-scheduler` 与 `bootstrap` 改为读进程级 `configLoader`
- `models`/`tools`/`mcp`/`skills` handler 在无 registry 改写的情况下仍读全局

### 1.4 设计约束

- 不改变 `/sessions`、`/fs`、`/terminal`、`/memory` 的 `ws` 语义（内容仍按空间）
- 不改 `AgentPool` 容量与 ALS 包裹逻辑
- `Dimensions`：`initAgentMemory(rt.root)` 与 `runWithWorkspace` 保持不变
- 单测可注入性不降低（`createApiServer(deps)` 仍可注入）

## 二、方案设计

### 2.1 总体思路（D8）

```
改造前                              改造后
─────────────────────────────      ─────────────────────────────
每空间 runtime：                     进程级单例（一次）：
  ConfigLoader(root)      ──┐          configLoader
  ConfigWriter(root)      ──┼──►       configWriter
  SkillLoader().scan(root)──┘          skillLoader.scan()
  mcpManager（已单例）                  mcpManager / mcpMonitor

每空间 runtime（保留）：              每空间 runtime（保留）：
  SessionStore(root)                   SessionStore(root)
  AgentPool                            AgentPool
  memory kit                           memory kit
```

### 2.2 关键设计决策

- **D8**：`WorkspaceRuntime` 去 Config/Skill 组件，`WorkspaceRuntime` 接口不保留这些字段（避免「指向某空间」的错觉）。
  - 理由：这是本次最大架构收益——MCP 连接与 skill 扫描从 O(空间数) 降为 O(1)
  - 被否决：只收敛读路径、保留 per-space 实例（N 份实例与 N 次扫描仍在）
  - 风险：`ctx` 改写面广，需逐端点核查
- **D7**：`ensureScaffold` 不再产出 workspace 配置与 workspace skills。
  - 理由：不清理会让每个新空间重新长出 `{}` 配置，全局化形同虚设
  - 被否决：保留目录但不用（磁盘残留 + 体检永久告警）
- **D11**：`memory.dreaming.*` 读进程级配置。
  - 理由：Dreaming 已按全空间三段式运行，按空间配开关自相矛盾

### 2.3 兼容性取舍

`WorkspaceRuntime` 若被外部（测试/嵌入用法）依赖 `rt.configLoader`，采用**过渡做法**：保留字段但赋值为进程级单例（类型不变、指向全局）。P2 再考虑彻底删除字段。这样单测改动面最小，且语义立即正确。

> 本决策为实施期裁定：优先「保留字段 + 指全局」，若 `tsc` 显示无外部依赖再彻底删字段。

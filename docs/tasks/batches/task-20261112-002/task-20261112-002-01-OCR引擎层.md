## 一、任务目标需求

### 1.1 背景（痛点）

现场环境是内网、离线、只有纯文本模型。要让 Agent 能「读图上的字」，必须有一条完全不依赖大模型与外部服务的文字提取通道。本任务只做这条通道的底座（引擎 + 后处理 + 缓存 + 编排），不碰任何工具接入——工具由任务 02 提供，降级与文档图片由任务 03/04 调用。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
| --- | --- | --- |
| 视觉调用（对照组） | [`vision/tools.ts L157-L220`](file:///d:/trae_workspace/loop-agent-command/src/tools/vision/tools.ts#L157-L220) `runVision()` 统一走 `llm.chatVision` | OCR 必须与之并列成独立管道，不复用其消息构造 |
| 图片字符校验 | [`vision/image.ts`](file:///d:/trae_workspace/loop-agent-command/src/tools/vision/image.ts) `resolveImage()`：三来源 + 大小/格式校验 | OCR 侧需要「字节流」形态（文档内图片没有路径），故本任务自带 `sniffImageFormat()` + `runOcrOnSource()` |
| 外部进程调用范式 | [`documents/external.ts`](file:///d:/trae_workspace/loop-agent-command/src/documents/external.ts) `pdftotext` 探测缓存 + 静默回退 + 超时 + 输出上限 | WinRT 引擎按同一范式实现（探测缓存、超时、输出上限） |
| 结果缓存范式 | [`vision/cache.ts`](file:///d:/trae_workspace/loop-agent-command/src/tools/vision/cache.ts) 进程内 LRU + TTL，key 含文件指纹 | OCR 复用形态但 key 改用**内容哈希**（文档内图片是 Buffer，无 mtime） |
| 配置读取 | [`config/loader.ts L84-L90`](file:///d:/trae_workspace/loop-agent-command/src/config/loader.ts#L84-L90) `deepMerge(DEFAULT_CONFIG, …)` 通用深合并 | 新增 `ocr` 段**无需改 loader**，默认值放 `schema.ts` 即自动生效 |
| package 依赖与 Node 下限 | [`package.json`](file:///d:/trae_workspace/loop-agent-command/package.json) `dependencies` 6 个、`engines.node >= 20.10` | 本任务**不新增依赖**，Node 下限不变（light-ocr 转演进项后 Q8 作废） |

### 1.3 任务目标

1. 新增 `src/ocr/` 目录，提供可被三个调用方复用的唯一入口 `runOcr(buffer)` / `runOcrOnSource(source)`；
2. Windows 上用系统自带 `Windows.Media.Ocr`（WinRT，经 `powershell.exe`）识别中文与中英混排图片；
3. 结果做 CJK 后处理：合并汉字之间的空格、保留英文单词内空格、**对紧凑输入逐字节不变**；
4. 提供进程内 LRU + TTL 结果缓存，key 由内容哈希构成，与视觉通道互不污染；
5. 所有失败走 `OcrError` 错误码分类，文案为可纠正的中文；非 Windows 平台明确报「演进项」而非泛化失败；
6. 引擎抽象 `OcrEngine` 留作演进项接口位，补齐 macOS/Linux 实现时不改动编排层。

### 1.4 设计约束

- 零新增 npm 依赖；`powershell.exe` 用 `spawn` 参数数组，不经 shell。
- 探测结果进程内缓存一次，不得每次调用都起子进程试探。
- 引擎只负责「拿文本」，缓存、截断、后处理、标注一律在编排层，防止多引擎行为漂移。
- 后处理只做「删除/压缩空白」，**不插入任何字符**——这是幂等性的根本保证。
- 不支持 `http(s)` 图片地址（避免 SSRF 与不可控耗时），明确拒绝并指向 `analyzeImage`。

## 二、方案设计

### 2.1 总体思路

```
调用方（任务 02/03/04）
        │
        ├─ runOcrOnSource('a.png' | 'file://…' | 'data:image/…')   ── 解析来源为 Buffer
        └─ runOcr(buffer, opts)
                    │
                    ▼
        resolveOcrConfig() ── ocr.enabled? ──否──► OcrError('engine_missing')
                    │
             大小 / 魔数格式校验 ──失败──► image_too_large / unsupported_format
                    │
                    ▼
        pickOcrEngine(cfg) ── resolveEngineOrder: ['winrt-ocr'] (+ 'http' 若配了端点)
                    │            非 win32 且无 http ──► platform_unsupported
                    ▼
        cache.get(key = hash(版本|引擎|语言|内容)) ──命中──► 直接返回（warnings: 缓存命中）
                    │
                    ▼
        engine.recognize() ──► RawOcrOutput ──► postProcessOcrText()（D4）
                    │                              │
                    │                              ├─ mergeCjkSpaces：只删 CJK↔CJK 空格
                    │                              ├─ collapseInnerSpaces：行内多空格→1（保留缩进）
                    │                              └─ normalizeOcrLines：去行尾空白、空行收敛、LF
                    ▼
        truncateOcrText(maxChars) ──► OcrResult ──► cache.set()
```

### 2.2 关键设计决策

| 编号 | 决策 | 被否决项与理由 |
| --- | --- | --- |
| **T1-D1** | 编排层（`run-ocr.ts`）独占缓存/截断/后处理/标注，引擎只出原文 | 否决「各引擎自带后处理」：WinRT 与 HTTP 会给出不一致的输出，调用方还得各自适配 |
| **T1-D2** | Windows 用 WinRT 系统能力，脚本内嵌为常量 | 否决 tesseract CLI / light-ocr：前者现场未装且转演进项，后者 130MB + Node ≥22 + 与 SEA 冲突（方案 D1/D9） |
| **T1-D3** | 探测结果进程内缓存，`probeWinrt()` 提供 `resetWinrtProbeCache()` 供测试 | 否决每次调用实时探测：每次多一次 `powershell.exe` 冷启动（0.6–1.5s） |
| **T1-D4** | 缓存 key 用**内容哈希**，含 `OCR_CACHE_VERSION` | 否决 size-mtime：文档内图片是从 zip 解出的 Buffer，没有 mtime；且内容相同即应命中 |
| **T1-D5** | CJK 后处理用**正则替换（只删不插）**，且行首缩进单独保护 | 否决「按空格 split 再 join」：会重排原始空白，紧凑输入无法逐字节不变（方案 D4 幂等性硬约束） |
| **T1-D6** | 非 Windows 用独立错误码 `platform_unsupported` | 否决复用 `engine_missing`：两者给用户的行动完全不同（一个去装语言包，一个是平台限制） |
| **T1-D7** | `http` 引擎可用性来自**当次配置**而非探测 | 否决探测缓存：端点可热更新，缓存会导致改配置不生效 |
| **T1-D8** | 明确拒绝 `http(s)` 图片地址 | 否决静默下载：SSRF 风险 + 耗时不可控；远程抓取列演进项 |

核心签名：

```ts
export async function runOcr(image: Buffer, opts?: RunOcrOptions): Promise<OcrResult>;
export async function runOcrOnSource(source: string, opts?: RunOcrOptions): Promise<OcrResult>;
export function buildOcrResultText(result: OcrResult, opts?: { cached?: boolean; note?: string }): string;
export async function describeOcrStatus(cfg?: OcrConfig): Promise<{
  platform: string; enabled: boolean; engine: string; available: boolean; langs: string[]; detail: string;
}>;
```

`RunOcrOptions` 比方案多两个字段，都服务于测试与热更新：

```ts
export interface RunOcrOptions extends OcrOptions {
  config?: OcrConfig;   // 注入配置，单测跳过 configLoader
  noCache?: boolean;    // 跳过缓存
}
```

### 3.2 错误分类与文案

| code | 触发条件 | 文案要点 |
| --- | --- | --- |
| `engine_missing` | `ocr.enabled=false`，或 Windows 上无可用引擎 | 给出装语言包的具体路径（`Add-WindowsCapability` + 设置页勾选「光学字符识别」） |
| `platform_unsupported` | 非 `win32` 且未配 `ocr.http.endpoint` | 明说「仅支持 Windows，macOS/Linux 为演进项」，并给出 http 端点这条替代路径 |
| `lang_unsupported` | 指定语言引擎不支持 | 列出可用语言标签 |
| `image_too_large` | 超过 `ocr.maxImageBytes` | 回显实际大小与上限，提示先压缩 |
| `unsupported_format` | 魔数不在 png/jpeg/bmp/gif/webp/tiff | 列出支持格式 |
| `timeout` | 超过 `ocr.timeoutMs` | 回显超时阈值 |
| `empty` / 空结果 | 引擎成功但无文字 | 不抛错，走 `warnings`：图片可能不含文本或分辨率过低 |
| `engine_failed` | 脚本报错、进程非零退出 | 保留原始错误摘要 |
| `bad_input` | 空参数、来源不存在、不是文件、http(s) 地址 | 分别给针对性说明 |

### 3.3 边界与约束

- 图片大小上限与 `vision.maxImageBytes` 同口径（默认 10MB），但读的是 `ocr.maxImageBytes`。
- `runOcrOnSource()` 的 `file://` 前缀、`data:` 前缀均做显式解析；`data:` 同时支持 base64 与 URL-encoded。
- WinRT 临时文件：按魔数选扩展名写 `os.tmpdir()`，`finally` 删除；单次识别结束即清理。
- 缓存只在 `text` 非空时写入，避免把「没识别到字」的失败结果固化。

### 3.4 演进项（本任务不做）

- macOS Vision framework、Linux/macOS tesseract CLI 引擎实现（方案 §4.9-A，接口位已留）。
- `@arcships/light-ocr` 作为可选高精度引擎（optionalDependency + 运行时探测）。
- 落盘级缓存与跨会话复用。
- `http(s)` 图片地址抓取、指定区域 OCR。

## 一、任务目标需求

### 1.1 背景（痛点）

现场大量资料是「Word/PPT 里贴截图、PDF 是扫描件」。当前 `fileRead` 只能拿到文字层：

- 扫描件 PDF 直接抛 `scanned` 错误（[`pdf.ts L1113`](file:///d:/trae_workspace/loop-agent-command/src/documents/pdf.ts#L1113)、`L1150`），提示用户「用 analyzeImage」——而内网根本没有视觉模型，这条路是死的；
- docx/pptx/xlsx 的内嵌图片**完全不提取**，`word/media/image3.png` 里的内容对 Agent 而言不存在。

### 1.2 现状梳理

| 能力 | 现状 | 对任务 04 的意义 |
| --- | --- | --- |
| Office 解包 | [`zip-text.ts`](file:///d:/trae_workspace/loop-agent-command/src/documents/zip-text.ts) `readOfficeZip(absPath)` 返回 `Map<entryName, Buffer>`；`pptx.ts` 已用 `zip.keys()` 枚举条目 | **零依赖即可拿到 `word/media/*` 字节**，无需新增库 |
| 提取结果契约 | [`types.ts L44-L54`](file:///d:/trae_workspace/loop-agent-command/src/documents/types.ts#L44-L54) `ExtractResult { text, pages?, pageCount?, warnings, truncated }` | 新增可选 `images?: DocImage[]`，向后兼容 |
| 分页映射 | `PageRange` 已由 PDF/PPTX 提供 | PDF 场景可把图片归到页 |
| 外部命令范式 | [`external.ts`](file:///d:/trae_workspace/loop-agent-command/src/documents/external.ts) `pdftotextAvailable()` 探测缓存 + `resetPdftotextCacheForTest()` | 光栅化探测照抄该范式 |
| PDF 解析 | [`pdf.ts`](file:///d:/trae_workspace/loop-agent-command/src/documents/pdf.ts) 自研解析器（`node:zlib` inflate、dict 解析、`skipInlineImage` 直接跳过内联图像） | **具备流解码基础但无图像抽取能力**；图像抽取需新增 XObject 分支 |
| 文本落盘/截断 | `fileRead` 已有行号渲染、512KB 截断、可操作提示 | 图片块必须并入同一套截断与提示风格 |

### 1.3 任务目标

1. `ExtractResult` 增加 `images?: DocImage[]`（`index/path/bytes/page?`），按文档流顺序；
2. 新增 `doc-images.ts`：用 `readOfficeZip()` 从 docx/pptx/xlsx/odt 解出 `*/media/*` 图像条目并自然排序；
3. `fileRead.readDocument()` 在文本行管线之外，为每张图插入独立 OCR 块，块头标注来源文件与引擎/耗时；
4. **三重预算**：`doc.maxImagesPerDoc`（张数）、`doc.maxCharsPerImage`（单图字符）、`doc.timeBudgetMs`（总时间），超预算给可操作提示而非静默丢弃；
5. 扫描件 PDF 的 `scanned` 错误改为「能 OCR 就 OCR，不能就说明缺什么」。

### 1.4 设计约束

- 不改动既有文本提取逻辑与行号语义；图片块**追加在文本之后**（不插入正文中间，避免破坏 `startLine/endLine` 语义）。
- `ocr.doc.enabled=false` 时行为与当前版本**逐字节一致**（不枚举图片、不加任何块）。
- 图片一律走 `runOcr(buffer)`，不落临时文件（Office 场景）；PDF 光栅化不可避免时临时文件用完即删。
- 非 Windows 且无 http 端点：不报错，只在结果末尾给一条说明。
- 失败不阻断：单张图 OCR 失败只影响该块（块内写失败原因），文档主体照常返回。

## 二、方案设计

### 2.1 总体思路

```
extractDocument()
   ├─ detect → 各提取器
   │     ├─ word/pdf/pptx/xlsx/odt：产出 text + images?（新）
   │     └─ images 来源：
   │           Office  → readOfficeZip() 过滤 word|ppt|xl|media
   │           PDF     → ⚠ 方案见 2.2 T4-D1（待确认）
   ▼
fileRead.readDocument()
   ├─ 文本块（现状：行号 / 512KB 截断）
   └─ 图片块（新增）：对每张图 runOcr(buffer)
         ├─ ok       → `[图片 2（word/media/image2.png）：OCR 文本 · winrt-ocr · 1.1s]\n…\n[/图片 2]`
         ├─ 空文本   → `[图片 3（…）：OCR 未识别到文字]`
         ├─ 失败     → `[图片 4（…）：OCR 失败（code）：中文说明]`
         └─ 超预算   → `[图片 21-33 未 OCR：超出单文档图片上限 20，可用 ocrImage 单独识别 word/media/image21.png]`
```

### 2.2 关键设计决策

| 编号 | 决策 | 被否决项与理由 |
| --- | --- | --- |
| **T4-D1** | ⚠ **PDF 图片来源待用户拍板**（见 §2.3） | 方案原文 D8 只写了「光栅化（`pdftoppm`/`mutool`/`gs`）」；但现场内网机是否装了 poppler 未知，而自研解析器已具备解码能力，「抽取内嵌图像流」可能零依赖够用 |
| **T4-D2** | 图片块**追加在文本之后**，不嵌入正文 | 否决「原位插入」：会打乱 `PageRange.startLine/endLine` 与 `pages` 参数语义，破坏既有分页能力 |
| **T4-D3** | 图片走 `readOfficeZip()` 的 `Buffer`，落盘为 0 | 否决「解到临时目录再读」：Office 场景完全没必要，且多一层清理 |
| **T4-D4** | 三重预算独立生效，任一触发即停止并给提示 | 否决「只限张数」：一张超大截图（4000×6000）识别结果可能上万字符，同样会把上下文打爆 |
| **T4-D5** | 单图失败只污染该块 | 否决「整体失败」：一张坏图不该让整份文档读不出来 |
| **T4-D6** | `ocr.doc.enabled=false` 走完全旧路径 | 否决「总是枚举」：枚举 + 排序对大文档有成本，且旧行为可回滚是本需求的硬要求 |

### 2.3 T4-D1 定稿：光栅化为主 + 自定义模板兜底（A 转演进项）

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| **A. 抽取内嵌图像流** | 解析 `Resources → XObject → /Subtype /Image`，`DCTDecode` 直出、`FlateDecode` 拼 PNG | **未采用，转演进项**：需新写 XObject 解析 + CMYK/索引色/JPX 转换，工作量与风险远高于光栅化；且扫描件里「文字转曲」的矢量页本就抽不到内容 |
| **B. 光栅化** | 探测 `pdftoppm` → `mutool` → `gs` → 自定义 `ocr.pdfRasterizer` 模板，按页渲染 PNG | **采用**：覆盖最全（矢量、表格、版式都能「看」），实现简单；缺工具时保留原 `scanned` 错误并附安装指引，不静默 |
| **C. A + B 兜底** | 先抽内嵌图，抽不到再光栅化 | 不采用：A 的代价已否决，C 的一半收益不足以承担双路径维护成本 |

定稿理由：现场内网机无 poppler 也能用 `ocr.pdfRasterizer` 指向已有工具（如本机已有的 PDF 组件），
而「有 OCR 引擎 ≠ 有光栅化工具」这一组合已实测确认，方案 B 把缺口变成**可操作提示**而非静默失败即可。
若后续真机反馈「扫描件抽图精度不足」，再启动 A 作为增强路径。

## 三、任务详细设计

### 3.1 类型扩展（`src/documents/types.ts`）

```ts
export interface DocImage {
  /** 1-based，按文档流顺序 */
  index: number;
  /** zip 内条目名（Office）或 `page-3` 形式（PDF） */
  path: string;
  bytes: number;
  /** PDF 场景页码 */
  page?: number;
}

export interface ExtractResult {
  // …既有字段
  images?: DocImage[];
}
```

### 3.2 `doc-images.ts`（新增）

```ts
/** 从 Office 容器解出图像条目（零依赖，复用 readOfficeZip） */
export async function collectOfficeImages(absPath: string): Promise<Array<DocImage & { buffer: Buffer }>>;
```

- 条目过滤：`word/media/`、`ppt/media/`、`xl/media/`（odt 为 `Pictures/`）。
- 扩展名白名单：`png/jpg/jpeg/bmp/gif/webp/tiff`（与 `sniffImageFormat()` 对齐）。
- 自然排序：`image2.png` 排在 `image10.png` 之前（按数字段比较，不用字典序）。
- 单图上限：超过 `ocr.maxImageBytes` 的条目直接跳过并计入 warnings。

### 3.3 `pdf-raster.ts`（新增，取决于 T4-D1）

- 探测顺序 `pdftoppm` → `mutool` → `gs`，结果进程内缓存（照抄 `pdftotextAvailable()`）。
- 输出到 `os.tmpdir()/ocr-pdf-<rand>/`，`finally` 整目录删除。
- 只渲染 `pages` 请求范围内或无文本层的页，不整本渲染。

### 3.4 `fileRead` 图片块渲染

```
[图片 2（word/media/image2.png）：OCR 文本 · winrt-ocr · 1.1s]
识别出的文字……
[/图片 2]
```

- 块头保留 `index`、`path`、通道、引擎、耗时，便于模型引用与用户核对。
- 块内文本已由 `runOcr` 做过 CJK 后处理与截断（`doc.maxCharsPerImage`）。
- 时间预算耗尽时追加：`[图片 12-33 未 OCR：单文档时间预算 8s 已用尽，可用 ocrImage 单独识别]`。

### 3.5 扫描件 PDF 错误改造

```
有引擎 + 有图像来源 → 返回 OCR 文本（标注「文本来自 OCR，非 PDF 文字层」）
缺引擎            → 原 scanned 错误 + 「本地 OCR 也不可用：<原因>」
缺图像来源         → 原 scanned 错误 + 「需要 pdftoppm/mutool/gs 之一才能渲染该页」
```

### 3.6 演进项（本任务不做）

- 图片区域切分（表格图、多栏扫描件版面分析）。
- OCR 结果与原图坐标对齐（可点选定位）。
- 图片去重（同一张 logo 在 PPT 出现 20 次只 OCR 一次——可先用内容哈希去重，列为优化项）。

### 五、实施记录与偏差（2026-11-12）

| 项 | 计划 | 实际 | 原因 |
| --- | --- | --- | --- |
| 文件名 | `doc-images.ts` | `images.ts` | 目录内已有 `pdf.ts`/`zip-text.ts` 等短名，`doc-` 前缀与目录语义重复 |
| 类型名 | `DocImage { path, bytes }` | `DocumentImage { name, data, source, page? }` | 直接携带字节，省掉「先取元信息再二次读包」；`source` 区分 OOXML 内嵌图与 PDF 光栅化页，块标签据此切换 |
| 块头 | `[图片 2（…）：OCR 文本 · winrt-ocr · 1.1s]` | `[图片 N（…）：OCR 文本]` | 块文本长期留上下文，逐块写引擎/耗时会随机器与缓存抖动，对模型无决策价值；引擎信息保留在 `ocrImage` 工具结果中 |
| 超限提示 | 一行区间式 `[图片 21-33 未 OCR：…可用 ocrImage 单独识别 …]` | 逐张一行 `[图片 N（…）：未 OCR（超过单文档 20 张上限）]` | 逐张保留条目名，模型可直接把该 name 喂给 `ocrImage`，比区间更可操作 |
| PDF 来源 | 待定（A/B/C） | B（光栅化）+ 自定义模板兜底 | 见 §2.3 定稿 |
| `python -m pypdfium2` | 设计文档原探测链含此项 | 未实现 | 多一条 Python 环境探测链，收益不抵复杂度，转演进项 |
| 时间预算文案 | `超出 Ns` | `>1s` 用 `Ns`、`≤1s` 用 `Nms` | 避免出现「超过 0s 时间预算」这种读不懂的提示（单测暴露） |

关键实现要点：

- `collectZipImages()` 只认 `word|ppt|xl/media/` 下且魔数可识别的条目（`emf`/`wmf` 等矢量图直接跳过），
  按 `localeCompare(..., {numeric:true})` 自然排序后赋 1-based `index`。
- `ocrDocumentImages()` 三重预算的执行顺序为「先张数、再时间、最后单张字符」；单张超时取
  `min(ocr.timeoutMs, 剩余预算)` 且不低于 1s，保证单张不会击穿文档级预算。
- 引擎整体不可用（`engine_missing` / `platform_unsupported`）且尚未成功识别过任何一张时**整块清空**，
  只留一条汇总告警；部分失败仍逐块产出，主体文本照常返回。
- PDF 侧 `pdfScannedPagesOnly=false` 时全部页都光栅化，`true`（默认）只渲染无文本层页，
  两处分支都会把页图以 `source:'pdf-page'` + `page` 交回 `fileRead` 统一 OCR。

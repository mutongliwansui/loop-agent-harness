## 一、需求背景

项目所有「看图」能力都绑在视觉大模型上，内网/离线/纯文本模型现场整条失效：`analyzeImage` 直接报错、`fileRead` 读扫描件 PDF 抛 `scanned` 错误并把用户指向一条走不通的路、docx/pptx/xlsx 的内嵌图片根本不提取。方案用「本地 OCR 抽取型管道」补齐：新增 `ocrImage` 工具、`analyzeImage` 视觉失败时降级到 OCR、`fileRead` 把文档内图片的 OCR 文本并入既有行号/截断/落盘管线。

平台范围已收窄为 Windows 优先：目标现场（Windows 10 企业版 G 神州网信政府版 19044）与开发机（Win11）双环境实测 WinRT 可用，非 Windows 平台本需求内**不注册工具、不降级、不报错**，行为等同当前版本。

## 四、统一设计约束（四个任务共同遵守）

- **零新增 npm 依赖**：只用系统能力（`powershell.exe` + WinRT），`dependencies` 不增；`.ps1` 作为 SEA asset 内嵌。
- **平台边界**：非 `win32` 一律走 `platform_unsupported` 分支，不注册工具、不抛错到用户可感路径外、只在诊断里说明「演进项」。
- 引擎抽象 [OcrEngine](file:///d:/trae_workspace/loop-agent-command/src/ocr/types.ts#L69-L77) 是演进项接口位：补齐 macOS/Linux 实现时不得改动 [run-ocr.ts](file:///d:/trae_workspace/loop-agent-command/src/ocr/run-ocr.ts#L99-L148) 及以上调用方。
- **结果必须标注来源**：首行 `[OCR 引擎 | 语言 | 耗时]`，防止主模型把 OCR 文本当成视觉理解结论。
- **CJK 后处理幂等**：紧凑输入（无 CJK-CJK 空格对）必须逐字节不变；不插入任何字符。
- **前缀缓存**：`ocr.enabled` 默认 `true`，但仅在探测到可用引擎时注册 `ocrImage`（D7）；关掉开关后 tools 列表与当前版本完全一致。
- 外部子进程：参数数组传参、不经 shell、固定超时、stdout 上限（沿用 [`external.ts`](file:///d:/trae_workspace/loop-agent-command/src/documents/external.ts) 范式）。

## 五、风险与依赖

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 非 Windows 平台误报错 | 用户以为功能坏了 | `platform_unsupported` 专用错误码 + 文案明确「演进项，可配 http 端点」 |
| 中文精度不足（`V1.0` → `VI · 0`） | 看似成功实则错字 | 结果固定标注引擎与语言；不做纠错猜测；文档内图片块标注来源 |
| `powershell.exe` 启动开销 0.6–1.5s | 单次调用变慢 | 工具级 60s 超时；文档场景有三重预算（张数/字符/时间） |
| 文档内图片拖慢 `fileRead` | 大文档超时 | D3 三重预算；超预算给可操作提示而非静默丢弃 |
| 新增工具破一次前缀缓存 | 升级首轮成本上升 | 属一次性代价；`ocr.enabled=false` 可完全回滚 |

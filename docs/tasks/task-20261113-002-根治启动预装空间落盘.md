# 任务 20261113-002：根治启动预装空间落盘（幽灵空空间被当成工作空间）

> 对应需求编号：**20261113-002**
> 状态：**P0/P1 已实施完成（2026-11-13）**；P2（存量幽灵收口）待实施。

---

## 一、任务目标需求

### 1.1 背景（痛点）

用户在 WebUI 左侧栏看到 `C:\Users\muton`（用户主目录）被当成一个「工作空间」列在最前面，且点进去是空的。用户先怀疑版本未更新，已排除：服务以 tsx 直跑 `src/index.ts`，即最新代码。

这不是显示问题，而是**启动过程真的在磁盘上创建了一个空工作空间记录**，然后这个记录又被当成「最近使用空间」反复自我强化。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
|---|---|---|
| 冷启动缺省空间推导 | `src/api/recent-workspace.ts:44` `resolveRecentRoot()`：扫 `sessions/*/`，无任何可用会话时回落 `os.homedir()`（20261113-001 D9） | 兜底值本身合理（选空间浏览器需要真实目录起点），但**它同时被当成「要预装落盘的空间」**，这是错配 |
| 启动预装 | `src/api/bootstrap.ts:52-59` `recentRoot = resolveRecentRoot()` → `registry.get(recentRoot)` | 预装这一动作只要执行，就必然落盘（见下行），故首次启动必产出一个主目录空间 |
| 落盘点 1（会话） | `src/session/store.ts:506-512` `init()` **无条件** `mkdir(workspaceDir)` + `touchWorkspaceMeta()` | 根因。`init()` 语义是「初始化」，但实际做了「登记到磁盘」——只要有 store 被 init，就产生 meta.json |
| 落盘点 2（记忆） | `src/api/bootstrap.ts:70` `initAgentMemory(rt.root)` → `src/memory/episodic.ts:124` `episodic.init()` `mkdir` + 建 `index.sqlite` | 根因。实测 `~/.loop-agent/memory/776e97820388b15d/index.sqlite` 存在（24576B，时间戳与进程启动同毫秒） |
| 侧栏可见性 | `src/session/store.ts:1011` `listAllWorkspaces()` 只校验 `meta.json` 可解析，**不看会话数**；按 `createdAt` 升序 | 0 会话空间照常进入 `GET /workspaces`，且因 createdAt 最早而排最前 |
| 前端渲染 | `webui/src/App.vue:214` `v-for="w in filteredGroups"` 直接渲染分组；`webui/src/sessions.ts:46` `filteredGroups` **仅在有关键词时**才丢弃空组 | 无关键词时 0 会话组照常显示（一个 `0 条` 的分组） |
| MRU 判据（自强化源） | `src/api/recent-workspace.ts:71` `latestMtimeMs()`：recency = 目录树内最新 mtime | 幽灵 meta.json 每次启动被 `touchWorkspaceMeta()` 刷新 mtime → 下次启动恒被选中 → 再落盘，**永不自愈** |

磁盘证据（`~/.loop-agent/sessions/`）：`776e97820388b15d` 仅含 `meta.json`、**无任何会话文件**，其 createdAt 与进程启动时间（9:42:04）毫秒吻合；`522b6010f5ea7e0b` 才是真实项目空间 `D:\trae_workspace\loop-agent-command`。

### 1.3 任务目标

1. **启动预装不再产生任何磁盘痕迹**：会话存储目录、`meta.json`、记忆目录与索引一律「按需懒建」——用户真的在该空间创建会话/写记忆时才落盘。
2. **断开自强化闭环**：MRU 推导只认「真实含会话文件」的空间，幽灵记录不再被选为最近使用，也不再被刷新 mtime。
3. **0 会话空间不出现在侧栏**：后端聚合与前端渲染双层收敛，用户看不到空工作空间。
4. **存量幽灵提供安全清理路径**：严格条件下清理，**绝不触碰用户真实工作空间目录**。
5. 修复后「首次启动 → 打开 WebUI」不应再出现主目录分组；重启多次也不应复发。

### 1.4 设计约束

- `ApiServerDeps` 构造签名不变（既有单测零改动为第一优先）；`deps.sessionStore` 仍是合法 store 实例。
- CLI 单空间模式落盘语义不变（CLI 下 `init()` 后正常建会话必须照旧可用）。
- `canonicalWorkspacePath()` / `workspaceId()` 公式不变；`workspaceId` 是纯哈希，改动会分裂全部存量空间。
- 绝不删除任何**用户工作空间目录**；清理动作只作用于 `~/.loop-agent/{sessions,memory}/<wsId>` 这类本应用私有存储目录。
- 零新依赖；中英双语文档同步（`docs/readme/zh`、`docs/readme/en`）。

## 二、方案设计

### 2.1 总体思路

核心思想一句话：**「空间被登记」必须由用户行为触发，不能由服务启动触发。**

```
现状（有 bug）                          修复后
─────────────────────────────          ─────────────────────────────
启动                                   启动
 ├ resolveRecentRoot()                 ├ resolveRecentRoot()
 │   └ 无会话 → homedir()               │   └ 无会话 → homedir()（仅"建议起点"，不落盘）
 ├ registry.get(recentRoot)   ←落盘1    ├ registry.get(recentRoot)   ← 不落盘（D1/D2）
 │   └ store.init() mkdir+touch meta    │   └ store.init() 只解锁密钥
 ├ initAgentMemory(rt.root)   ←落盘2    ├ initAgentMemory 仅当记忆已存在（D3）
 │   └ episodic.init() mkdir+sqlite     │   └ 空空间：跳过，无目录
 └ GET /workspaces                      └ GET /workspaces
     └ 0 会话空间照常返回                    └ 过滤 0 会话组（D5）

首次真实使用（新建会话）
 └ createSession()
     └ ensureWorkspaceDir()：此刻才 mkdir + touch meta（D1 配套）
```

### 2.2 关键设计决策

| # | 决策 | 结论 / 取舍 |
|---|---|---|
| **D1** | `SessionStore.init()` 的落盘语义 | **`init()` 改为纯内存初始化**：只做密钥解锁（加密模式），**不再** `mkdir`、**不再** `touchWorkspaceMeta()`。新增私有 `ensureWorkspaceDir()`（`mkdir` + `touchWorkspaceMeta`，幂等缓存），由 `createSession()`/`writeSession()` 落盘前调用。**取舍**：`init()` 语义回归「初始化」本义；代价是必须给所有写入路径补齐目录保障，漏一处会在无目录时写文件失败——故 `ensureWorkspaceDir()` 在 `writeSession()` 与 `appendIndex()` 前都要调（防御式）。**被否决**：给 `init()` 加 `touch=false` 参数由调用方区分——调用点太多（92 处），必然漏改，且「默认落盘」这个反直觉默认值正是 bug 温床。 |
| **D2** | 启动预装的形态 | **保留 `registry.get(recentRoot)` 预装**，磁盘痕迹由 D1 消除。理由：`deps.sessionStore` 是必填项，且被 9 处 handler 当「跨空间聚合读」的入口（`listAllWorkspaces`、journal 读取、`/fs` 白名单），移除会连带改装配与大量单测。**被否决**：①bootstrap 改为「不预装、只 new 一个未 init 的轻量 store」——`registry` 缺失会让 `resolveDefaultRuntime()` 走伪 runtime 分支（`server.ts:161`），跨空间语义崩；②把预装根改为「无则为空」——`SessionStore` 构造需要真实 root 推导 `sessions` 根目录（`dirname(workspaceDir)`），空值会破坏 `listAllWorkspaces`。 |
| **D3** | 启动期记忆初始化 | `bootstrap.ts:70` 的 `initAgentMemory(rt.root)` 改为**条件执行**：先探测 `~/.loop-agent/memory/<wsId>/` 是否已存在（已有记忆才做启动自检与旧目录迁移），不存在则**跳过**。运行时记忆仍按需：`rt.getMemoryKit()` 首次调用才 `createMemoryKit()` → `episodic.init()`。**取舍**：全新空间启动不再预生成 `index.sqlite`；对已有记忆的空间行为完全不变（迁移/自检照旧）。**被否决**：改 `episodic.init()` 不建目录——sqlite 打开必须父目录存在，且写入路径依赖它，改动面更大更危险。 |
| **D4** | MRU 推导判据 | `resolveRecentRoot()` 增加「**该空间必须含至少一个真实会话文件**」的准入判定：目录下存在非 `meta.json`/`sessions.json` 的 `.json`/`.enc` 文件（即 `sess_*` 会话体），或 `sessions.json` 解析后非空数组。仅含 `meta.json` 的幽灵目录**不参与 recency 竞争**。**取舍**：这是断开自强化闭环的关键——幽灵记录再也不会被选为「最近使用」，其 mtime 不再被刷新。**被否决**：改用 `meta.lastAccessedAt` 字段判新旧——同样可被 `touchWorkspaceMeta` 伪造，且需全量 JSON.parse（本机 ~180 空间），成本高一个量级。 |
| **D5** | 0 会话空间的可见性 | **在 handler 层过滤**：`handleListWorkspaces`（`sessions.ts:210`）返回前丢弃 `sessions.length === 0` 的分组。`listAllWorkspaces()` 自身语义**保持不变**（它同时是 `/fs/*` 的「已注册工作空间」白名单来源，`fs.ts:201`，收紧会误伤「已建空间未建会话」的文件浏览）。**被否决**：直接改 `listAllWorkspaces()` 过滤空空间——`/fs/tree`、`/fs/search`、`/stop`、`/stream` 的白名单判定全部依赖它（5 处），风险远大于收益。 |
| **D6** | 存量幽灵数据的清理 | **默认只识别、不自动删**：启动自愈阶段扫描 `sessions/*/`，对「仅含 `meta.json`（或 + 空 `sessions.json`）且无会话文件」的目录，打印一行告警并追加到 `~/.loop-agent/ghost-workspaces.log`。**删除需用户显式触发**（新增 `POST /workspaces/prune` 或 CLI 一次性命令，P2 可选）。**取舍**：本应用私有存储目录虽可安全删除，但「自动删」在用户误配（如把 `userDir` 指到别处）时会扩大故障面，默认告警更稳。**待确认**：是否要 P2 真的提供 prune 端点（见 5.1 问题 2）。 |
| **D7** | 前端防御性收敛 | `webui/src/sessions.ts:46` `filteredGroups`：**无关键词时也丢弃 0 会话分组**（不仅有关键词时）。理由：后端已过滤（D5），前端再兜一层可覆盖「前端缓存了旧响应/旧版本后端」的窗口期。**取舍**：纯防御，不改变任何有会话分组的展示。 |
| **D8** | `/fs/*` 白名单兜底 | D1 后「新建空间但未建会话」时 `meta.json` 尚不存在，`/fs` 白名单会 403。**兜底**：`resolveFsRoot()` 的白名单改为 `listAllWorkspaces()` **∪** `registry.list()`（已装载 runtime 的 root 视为已注册）。**取舍**：保证「打开空间 → 立即浏览文件」链路在无会话时也可用。若评估确认前端 FilesView 恒随活跃会话（有会话才浏览），本项可降级为 P2 可选。 |

### 2.3 外部实践参考

- VS Code 的「最近打开」列表只在**用户真实打开动作**时记账，并专门提供 `--skip-add-to-recently-opened` 参数用于阻止自动入列（[vscode#245122](https://github.com/microsoft/vscode/issues/245122)）——反面印证：**启动即记账必然产生幽灵条目**，用户随后只能手工清理历史。
- 窗口管理器的 phantom workspace 概念（[AeroSpace#710](https://github.com/nikitabobko/AeroSpace/issues/710)、[#996](https://github.com/nikitabobko/AeroSpace/discussions/996)）给出的成熟做法是「**工作空间仅在真正承载内容时实体化**，无内容即不占位」——与本方案 D1/D4 的「懒落盘 + 有会话才算最近使用」同构。
- 已知坑：Cypress/AeroSpace 一类工具在「按磁盘状态重建列表」时普遍遇到「空壳记录被当成真实记录」问题，共同结论是**判据必须落在「内容存在」而非「元数据存在」**。本方案 D4 的判据即按此设计（会话文件存在，而非 meta.json 存在）。

- 调用点：`writeSession()` 首行、`appendIndex()` 首行（两者独立防御，避免任一入口被单独复用时失败）。
- `this.dirReady` 为实例级布尔缓存，避免每次写会话都 stat/写 meta（写会话是高频路径）。
- **`touchWorkspaceMeta()` 逻辑不变**（更新 `lastAccessedAt` + `workspaceName`）。

```ts

// 改：仅当该空间已有记忆目录时才做启动自检/迁移
```

- `memoryDirExists` 复用 `memory-kit.ts` 的目录推导口径（`join(loopAgentHome(),'memory',workspaceId(root))`），需把该推导抽成共享函数避免两处口径漂移。

### 3.4 `/workspaces` 过滤（`src/api/handlers/sessions.ts:210`，D5）

```ts
const workspaces = (await ctx.deps.sessionStore.listAllWorkspaces())
  .filter((w) => w.sessions.length > 0);   // D5：0 会话空间不进侧栏
```

### 3.5 幽灵空间识别（新增 `src/api/ghost-workspaces.ts`，D6）

- `scanGhostWorkspaces(userDir): Promise<GhostWorkspace[]>`（**只读**）
  - 条件（全部满足才判定幽灵）：①目录仅含 `meta.json`（或 + `sessions.json` 但解析为空数组）；②不含任何其它文件/子目录（`sess_*` 会话体、`runs/`、散落文件一律视为真实活动）；③`meta.workspacePath` 存在（否则属孤儿，不处理）。
  - **不删除、不改名、不移动**任何目录或文件。
- `reportGhostWorkspaces(userDir, log?)`：启动期调用，有幽灵才打印告警 + 追加 `~/.loop-agent/ghost-workspaces.log`（单行 JSON，超 256KB 重写）；无幽灵零落盘。
- **安全边界**：本模块**不包含任何删除逻辑**，也**不提供 prune / 清理端点**（用户已明确决定：存量由用户自行删除）。将来若加 prune，必须重新走需求评审。


### 3.6 边界与错误处理

| 场景 | 期望行为 |
|---|---|
| 首次启动、无任何会话 | 不创建 `sessions/<wsId>`、不创建 `memory/<wsId>`；`GET /workspaces` 返回空数组；侧栏显示「暂无会话」 |
| 用户新建首个会话 | `createSession()` → `ensureWorkspaceDir()` 落 mkdir + meta，此后再启动被 D4 识别为「有会话」 |
| 存储目录存在但 `sessions.json` 损坏 | `hasRealSessions` 走文件枚举分支；`listAllWorkspaces` 已有的容错不变 |
| 加密模式 | `init()` 仍 `keychain.ensureUnlocked()`；`ensureWorkspaceDir` 不涉及密钥 |
| `userDir` 被指到异常位置 | D6 仅告警不删除；D1 的 mkdir 仍由 writeSession 触发，不会预建 |
| CLI 模式 | `startCli` 的 `sessionStore.init()` 不落盘，但 CLI 必然建会话 → 行为等价；需回归确认首条会话写盘正常 |

### 3.7 演进项（本任务不做）

- 侧栏展示「空空间」可选开关（用户主动想看磁盘上已知但未使用的空间）。
- `POST /workspaces/prune` 自动清理端点的权限与审计设计——**用户已明确否决**：不提供一键清理，存量幽灵由用户自行删除。
- 记忆目录与 sessions 目录的生命周期统一回收策略（`evictIdle` 只回收 runtime，不动磁盘）。

判据（三条**同时**满足才判幽灵，任一不满足即放过）：

1. 目录内只有 `meta.json`，或 `meta.json` + 解析为空数组的 `sessions.json`；
2. 不含任何其它文件/子目录——`sess_*` 会话体、`runs/`、散落文件一律视为真实活动；
3. `meta.json` 能解析且 `workspacePath` 非空（否则属孤儿目录，无从给出可读告警，不处理）。

设计要点：判据**刻意偏保守**——「看见任何多余的东西就放过」。误报会让用户删掉真正在用的空间，代价远高于漏报，因此宁可漏报。

告警形态：启动日志逐条列出，同时追加一行 JSON 到 `~/.loop-agent/ghost-workspaces.log`（`{ts, count, ghosts:[{wsId,workspacePath,reason}]}`）。日志超 256KB 时重写而非无限追加。**无幽灵时零落盘**（保持 P0 的「启动零痕迹」不被破坏）。

- 判据③：缺 `workspacePath` 的孤儿、损坏的 `meta.json` —— 不判幽灵。
- 边界：`sessions/` 根目录不存在返回空数组；混合场景只挑出幽灵。
- 告警：无幽灵时不打印也不建日志文件；有幽灵时打印并写日志（含 count/wsId/路径）；多次启动追加不覆盖；超限重写只留一行。
- **只读保证**：扫描与告警前后，目录内容与 `meta.json` mtime 完全不变，`wsDir` 仍存在。

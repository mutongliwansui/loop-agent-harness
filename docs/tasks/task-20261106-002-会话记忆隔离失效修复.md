## 一、任务目标需求

### 1.1 背景（痛点）

**现象**：同一工作空间（WebUI / `--serve`）下新建一个会话，对模型提问时能检索到该空间**其他会话**的历史记忆。

**根因（两处叠加，均已定位）**：

1. **会话身份从未到达 Agent**。多会话改造（[task-20261021-002-05](../tasks/optimizations/task-20261021-002-05-同工作空间多会话并发.md)）只做了「实例隔离」，没做「身份注入」：
   - [workspace-runtime.ts#L300-L301](../../src/api/workspace-runtime.ts#L300-L301) 的 `pooledRun` 把 `sessionId` 仅作为 `AgentPool` 的 key，`a.run(input, options)` 里不带会话信息；
   - [types.ts#L277-L313](../../src/types.ts#L277-L313) 的 `AgentOptions` **没有 `sessionId` 字段**；
   - API 实例的三个赋值入口全部失效：`setSessionStore` 只有 CLI 调用（[start.ts#L144](../../src/cli/start.ts#L144)）；`onSnapshot` 由 [messages.ts#L124-L136](../../src/api/handlers/messages.ts#L124-L136) 提供 → [react-agent.ts#L556-L559](../../src/agent/react-agent.ts#L556-L559) 提前 `return`，走不到 [L566-L571](../../src/agent/react-agent.ts#L566-L571) 的 `createSession`；`restoreSession` 仅 CLI `/session load` 使用。
   - 结论：**API 模式下 `_currentSessionId ≡ null`**，这是恒定状态而非并发竞态。
2. **写入侧产出「裸条目」，检索侧又给裸条目开了后门**：
   - 工具结果经 [callback.ts#L26-L30](../../src/memory/callback.ts#L26-L30)，`_sessionId` 为 null 时不写 `scope`/`sessionId` → 条目头只剩时间戳；
   - 检索侧 [episodic.ts#L454-L456](../../src/memory/episodic.ts#L450-L456) 保留「无 `scope` 标记 → 默认可见」的向后兼容分支 → 裸条目对**所有会话**可见。

**为什么单会话 CLI 一直正常**：CLI 通过 `/session load`、`/upload`、首轮落盘显式设置 `_currentSessionId`（[session-command.ts#L124](../../src/commands/session-command.ts#L124)、[upload-command.ts#L31](../../src/commands/upload-command.ts#L31)、[start.ts#L341](../../src/cli/start.ts#L341)），身份链路是通的。

### 1.3 任务目标

1. **A：会话身份 run 级注入**。`AgentOptions` 新增 `sessionId`；`run()` 入口解析一次局部值，本 run 内所有下游（L2 检索、L2 写入、工具 ctx、后台通知收发、debug 日志）统一使用该值，不再散读 `_currentSessionId`。
2. **A：API 侧显式传参**。`POST /sessions/:id/messages` 在 `runOptions` 注入 `sessionId: id`。
3. **B：写入侧契约化**。`AppendOptions.scope` 变为必填；`scope='session'` 且无 `sessionId` 时**拒绝写入**并记 debug 日志（不抛错、不产出裸条目）。
4. **B：检索侧 fail-closed**。删除「无 scope 标记 → 全部可见」兜底；新增 `SearchScope = 'session' | 'global' | 'all'`，`'all'` 仅供管理检索显式使用。
5. **B：管理检索显式全量**。`/memory search`（CLI）与 `GET /memory/search`（API）显式传 `scope: 'all'`。
6. **行为可验证**：会话 A 的 session 级工具结果/压缩笔记/最终答案，会话 B 检索时**一条都拿不到**；global 级条目两会话都能拿到。

### 1.4 设计约束

- **历史 L2 数据不迁移、不清理、不提供删除命令**（用户已确认可舍弃）。旧裸条目对 Agent 上下文检索不可见，管理检索仍可读。
- 记忆是旁路能力：写入/检索失败**不得**中断主回答（维持 best-effort 语义）。
- 不改 FTS BM25 / 向量检索 / RRF 融合算法本身，不改混合检索流程。
- 零新依赖（仅 `node:` 内置模块）。
- 跨平台一致（Windows/macOS/Linux），不引入平台相关路径处理。
- 方案先行，不执行代码 —— 本任务文档为方案阶段交付物。

### 2.2 关键设计决策

| 编号 | 决策 | 取舍 / 被否决项 |
| --- | --- | --- |
| D1 | **会话身份用 run 级入参传递**：`AgentOptions.sessionId?: string`，API handler 在 `runOptions` 注入；`run()` 入口解析 `const sessionId = options.sessionId ?? this._currentSessionId ?? null` | 否决**只在 `pooledRun` 里 `a.setCurrentSessionId(sessionId)`**：仍是实例可变状态，未来池策略放宽为非粘性复用时就会串会话，且覆盖不到 programmatic 调用方。否决**ALS 隐式传递**（给 `runWithWorkspace` 加 sessionId）：深层记忆/工具代码隐式取值，漏传难以发现 |
| D2 | **`_currentSessionId` 保留但降级为 CLI 兼容 fallback**，不再作为 API 正确性来源 | 否决**彻底删除**：`/session load`、`/upload`、CLI 中断落盘、命令层都依赖它 |
| D3 | **`AppendOptions.scope` 改必填**；运行时 `scope='session'` 且无 `sessionId` → **跳过写入 + debug 告警**（不抛错） | 否决**默认 `session`**：无 id 时仍产出不可见脏条目，且掩盖调用方错误。否决**抛错**：记忆写入是旁路，不能中断 run |
| D4 | **检索可见性 fail-closed**：删除 `!entryScope → true`；新增 `SearchScope = MemoryScope \| 'all'`，与存储用 `MemoryScope` 分开 | 否决**保留兼容分支只修注入**：历史数据已确认可舍弃，留后门会让裸条目继续泄漏 |
| D5 | **管理检索显式传 `scope:'all'`**（CLI `/memory search`、`GET /memory/search`） | 否决**给 `search()` 默认 `'all'`**：Agent 上下文调用方一旦漏传就重新 fail-open |
| D6 | **既无 sessionId 又无 scope 的检索 → 返回空 + debug 告警**（fail-closed） | 否决**默认只返回 global**：语义含糊，管理检索与上下文检索边界不清 |
| D7 | **CLI 首轮无会话**（`_currentSessionId` 仍为 null）→ 该轮记忆写入**跳过 + debug 记录** | 否决**写 `sessionId:'unassigned'`**：制造永久不可见脏数据。eager 建会话列为演进项（D11） |
| D8 | **`ToolMemoryCallback` 去掉可变状态**：删除 `setSessionId`/`_sessionId`，`log/logError/logGlobal` 增加 `sessionId` 入参 | 否决**保留 setSessionId 在 run 开头 set**：实例可变状态本身就是本次事故的结构性成因 |
| D9 | **历史数据不迁移、不清理、不提供删除命令**；旧裸条目对上下文不可见，`scope:'all'` 仍可读 | 否决**一次性迁移脚本**：用户已明确可舍弃，徒增成本与误删风险 |
| D10 | **并发健壮性（FTS WAL / busy_timeout / 进程内写队列 / markBroken 自愈）不在本任务范围**，列为演进项 | 与隔离失效是两个独立问题，混做会显著扩大验证面 |
| D11 | **演进项**：CLI run 起始即 eager 建会话，彻底消除 D7 的首轮空窗 | 本期不做，需评估「失败 run 产生空会话」对列表与统计的影响 |

### 2.3 参考与已知坑

本次未做外部方案检索，结论基于代码事实与通用实践。可直接借鉴的通用原则：

- **身份显式传递优于隐式上下文**：多租户系统普遍在请求入口显式带上 tenant/thread id 并逐层下传（LangGraph 的 `thread_id`、Mem0 的 `user_id/run_id` 均属此类）。
- **授权默认拒绝（fail-closed）**：过滤条件缺失时应返回空集而非全集，这是避免跨租户数据泄漏的标准做法；本项目现状恰好相反（fail-open）。
- **已知坑（本项目内）**：
  1. `ContextAssembler.runCache` 以 `(userMessage, sessionId)` 为 key（[context.ts#L209-L222](../../src/memory/context.ts#L209-L222)），当前依赖池的粘性复用侥幸正确；本次修正 sessionId 后该缓存键才真正有意义，**不要**顺手改成非粘性复用。
  2. `EpisodicMemory` 的 `index`/`vector` 按 workspace 共享，过滤只发生在结果层；向量检索结果同样必须过 `isSectionVisible`，否则改了一半等于没改。
  3. `searchViaHybrid` 在向量无结果时会回落 `searchViaIndex`，两条路径都要经过同一个 `filterEntries` —— 保证改动单点生效。

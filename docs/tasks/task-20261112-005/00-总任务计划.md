## 一、根因（构造性验证）

`word-extractor@1.0.4` 的 docx 路径是：

```
yauzl → fd-slicer（highWaterMark=16384 切片）→ pipe(zlib.inflateRaw)
```

`fd-slicer._read` 单块上限取 `highWaterMark`（16384 字节）。某条目「压缩后 ≥16384」时，首块
16384 字节膨胀出的数据击穿 zlib 可写缓冲 → `pipe` 暂停源流；源流此后既不补发 `data` 也不再
`resume`，滞留尾块与 EOF 永不发出 → inflate 既不 `end` 也不 `error` → yauzl 的 Promise 永不
settle → `extract()` 无限挂起 → `fileRead` 一直等到 runner 30s 工具超时，全程无错误输出。

判据只与「条目压缩后大小 ≥16384」有关，与文档字节数、文字量无关：

| 样本 | `word/document.xml` 压缩后 | 原始大小 | 结果 |
| --- | --- | --- | --- |
| 现场必挂文档 | 16453 | 285735 | 永久挂起 |
| 中间样本 | 11864 | 20202 | 12ms 正常 |
| 小样本（同生成器） | 远小于 16384 | — | 9ms 正常 |

底层数据完好：直接 `inflateRaw` 得 285735 字节、CRC 匹配，改用同步解压后重打包 35–45ms 正常；
mammoth 解同批 17 个正常样本 10–42ms。故这是依赖库流控缺陷，不是文档问题。

## 二、为什么不拆成多个任务

四条措施指向同一个缺陷、同一条代码路径（docx 正文取文），且第 ② 条（正文与图片共用一次解包）
必须与第 ① 条同时改才成立（否则重复解压）；第 ③ 条的兜底与第 ④ 条的用例是它们的守卫。
拆开会出现「中间态：正文已换实现但图片仍重复解包」这种半成品，故合并为一个任务。

## 四、实施内容

1. **新增 `src/documents/docx.ts`**：`docxBodyFromXml()` 轻量标签扫描 + `docxBodyFromZip()`，
   零依赖、同步解压（`readOfficeZip` → `inflateRawSync`），不存在流控面；分段/跳过上下文/
   标点归一逐项对齐 `word-extractor/lib/filters.js`，保证输出口径不漂移。
2. **正文与图片共用一次解包**：`extract.ts` 的 docx 分支改为 `readOfficeZip()` 一次 →
   `collectZipImages(zip)` 取图 + `docxBodyFromZip(zip)` 取文，不再各自解压。
3. **硬超时兜底**：`word.ts` 新增 `withTimeout()` 与 `WORD_PARSE_TIMEOUT_MS = 15_000`；
   `.doc`（OLE）仍走 `word-extractor` 并套该超时，到点抛 `DocumentExtractError('timeout')`
   （<1s 时文案用毫秒），保证调用方总能收敛、不静默挂起。
4. **回归用例与夹具**：`tests/helpers/docx-fixture.ts` 的 `makeZip`/`makeDocx` 增加
   `deflate` 能力（原先只有 stored，压根无法触发该 bug）；新增
   `tests/doc-extract-docx-stream.test.ts` 13 例（挂起回归 3 + 正文语义 7 + 超时兜底 3）。

### 顺带修复（改造落地时才暴露）

- `docxBodyFromXml` 曾把 `<?xml ...?>` 声明当正文输出（旧路径走 word-extractor，从未进该函数）；
- docx 损坏时错误措辞与 `.doc` 不一致（缺「解析失败」语义，`fileRead` 端提示不可纠正），
  现由 `withDocxCorruptContext()` 统一补齐，`corrupt` 之外的 `too_large` / `timeout` 保持原语义。

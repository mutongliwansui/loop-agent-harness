> 对应需求编号：20261028-005（见 [需求台账](../requirements/需求.md)）
> 提出时间：2026-10-28　　实施时间：2026-10-28

## 一、任务目标需求

### 1.1 背景（痛点）

对话输入区的附件入口只有 📎 一条（点击开系统文件框），`textarea` 上只挂了 `@input` / `@keydown.enter` / 组词事件，**没有 `@paste`**。于是：

1. **截图不能直接贴**——用 `Win+Shift+S` 或 QQ/微信截图后，在输入框里 `Ctrl+V`，什么都没发生（浏览器既不插入内容，也没有 handler 接收，事件被静默丢弃），用户只能先存成文件再点 📎 选。
2. **资源管理器复制的文件不能直接贴**——在资源管理器里 `Ctrl+C` 一个文件，回到输入框 `Ctrl+V`，同样无反应。而这恰恰是最顺手的一条路径（比 📎 → 找目录 → 选文件快得多）。
3. **无提示的静默失败**——因为没有任何反馈（toast/提示），用户容易误判为「页面卡了」或「浏览器不支持」，而不是「这个功能没做」。

### 1.2 现状梳理

| 所需能力 | 现状 | 结论 |
| --- | --- | --- |
| 接收粘贴的位图/文件 | `ChatView.vue:892-902` textarea 只有 `@input` / `@keydown.enter` / `@compositionstart|end` | **缺失** |
| 剪贴板 → `File` | 浏览器 paste 事件的 `clipboardData.files` 原生提供 `File[]`（见 1.3 实测） | 已具备（免费） |
| 上传链路 | `webui/src/api/client.ts:112` `uploadRaw(file, sessionId)`：`POST /uploads/raw?sessionId=`，`x-file-name: encodeURIComponent(file.name)`，body 为文件字节 | **可直接复用** |
| 落盘规则 | `src/upload/manager.ts:273` `writeUpload()`：时间戳前缀 `${stamp}-${fileName}` + 同秒同名冲突链（毫秒段 → 序号）+ 单文件上限 | 可直接复用 |
| 会话隔离 | `src/api/handlers/uploads.ts:66-94`：`sessionId` 必填且须存在（否则 404），按会话分隔目录 | 可直接复用 |
| 附件 chip 展示 | `ChatView.vue:866-890` `.chips` / `.file-pill`（SVG + 文件名 + 大小 + 圆形删除），样式 `1681-1717` | 可直接复用（需加缩略图变体） |
| 上传后注入对话 | `ChatView.vue:498-500`：`uploads.map(u => u.contextNote)` 拼进 `message` 文本；`512` 行把文件名放进 `files` 供历史展示 | 可直接复用 |
| 无会话时发送 | `ChatView.vue:482` `ensureSession()`：无会话自动创建 | 可直接复用 |
| 视觉可用性判定 | `GET /vision`（`src/api/handlers/vision.ts:15-29`）返回 `{available, provider, model, reason?}`，已含「enabled 但无 Key」的回退判断 | **直接复用**（勿自己读 enabled 判断） |
| 视觉支持格式 | `src/tools/vision/image.ts:20-32` `MIME_BY_EXT` / `SUPPORTED_IMAGE_EXTS`：png/jpg/jpeg/webp/gif/bmp | 需在前端镜像一份常量 |

### 1.3 实测取证（2026-10-28，Windows 11 + Chrome，CDP 有头真实按键）

| # | 场景 | 观察结果 |
| --- | --- | --- |
| ① | 资源管理器 `Ctrl+C` 文件 → 输入框 `Ctrl+V` | `paste.clipboardData.files` 拿到**真实 `File[]`**，`name` 为原始文件名（`sample-a.txt` / `sample-b.png`）、`type` 为正确 MIME |
| ② | 截图位图 → `Ctrl+V` | 同样落在 `files`；Chrome 自动命名为 `image.png`，`type='image/png'` |
| ③ | 纯文本 → `Ctrl+V` | `files.length === 0`，`items[0].kind === 'string'` |
| ④ | 文件 + 文本混合剪贴板（模拟 Excel 复制区） | 浏览器只暴露 `text/plain`，`files` 为空 → 天然不会「吞图」 |
| ⑤ | `navigator.clipboard.read()` 读文件 | `types: []`，拿不到任何内容 → **异步读剪贴板这条路不可用**，必须走 paste 事件 |
| ⑥ | headless Chrome | 剪贴板与系统隔离，任何模式下都拿不到 → 自动化验证**必须用有头 Chrome** |

**结论**：图片与文件是**同一条** `clipboardData.files` 路径，不存在「位图要特殊处理」的分叉；缺的只是「剪贴板 → `File` → 既有上传链路」这段约 40 行的接线，加上 chip 的图片形态。

### 1.4 任务目标

- `textarea` 增加 paste 处理：`files.length > 0` 时 `preventDefault()` 并走既有上传链路；`files.length === 0` 时**完全放行**默认行为（文本粘贴零影响、零回归）。
- 普通文件保留原始文件名；Chrome 截图位图的默认名（`image.png` 等）重命名为 `paste-YYYYMMDD-HHmmss[-seq].<ext>`，避免多张截图同名难分辨。
- 图片 chip 显示 24×24 本地缩略图（`createObjectURL`），删除 / 发送成功 / 卸载三处释放，不泄漏 blob URL。
- 视觉链路不可用（`GET /vision` → `available=false`）或图片超过 `vision.maxImageBytes` 时，在 chip 上给出**可观测警告**而不是静默假装「贴上去了」。
- 单次粘贴上限 6 张，串行上传，streaming 期间拦截（与 📎 行为一致）。

### 1.5 设计约束

- **零新增依赖**：只用浏览器原生 `DataTransfer` / `createObjectURL` 与既有 `uploadRaw`。
- **不新建上传端点**：`POST /uploads/raw` 已能承载任意字节，粘贴只是多一个「文件来源」。
- **不碰主模型多模态**：图片不进 `message` 的 `image_url`，仍走「文件落盘 + contextNote 注入 + 视觉工具按需查看」这条既有架构。
- **纯逻辑下沉**：命名/分类/上限/警告判定全部放进 `webui/src/paste-files.ts` 纯函数，`tests/webui-paste-files.test.ts` 可直接覆盖（沿用 `tests/webui-*.test.ts` 既有模式）。
- **不改既有 chip 语义**：`.file-pill` 的排版、`removeChip` 的 toast 文案保持不变，图片只增不改造。

## 二、方案设计

### 2.1 总体思路

```
      用户 Ctrl+V（焦点在 textarea）
                 │
                 ▼
        onPaste(ev: ClipboardEvent)
                 │
                 ▼
   collectPasteFiles(ev.clipboardData, now)      ← paste-files.ts（纯函数）
   ┌─────────────┴──────────────┐
   │ files.length === 0         │ files.length > 0
   ▼                            ▼
  直接 return                 ev.preventDefault()
  （文本粘贴走默认）              │
                               ▼
                    capPasteFiles(files, 6)     ← 超限截断 + dropped 计数
                               │
                               ▼
                  ensureSession() → sessionId
                               │
                               ▼
              for (const p of accepted)  （串行，沿用 onPickFiles 结构）
                               │
                               ▼
        uploadRaw(p.file, sessionId, p.name)    ← client.ts 新增第三参
                               │
                               ▼
        uploads.push({ ...r, isImage, thumbUrl, warn })
                               │
                               ▼
                    chip 渲染（缩略图 / 警告角标）
```

### 2.2 关键设计决策

**D1：图片与文件走同一条 paste → `clipboardData.files` 通道，不做两套分支。**
理由：1.3 实测 ①② 表明位图与文件都落在 `files`，只有 `type`/`name` 不同；分两套会重复上传、chip、错误处理三处逻辑。被否决项：图片走 `clipboardData.items` 的 `getAsFile()`（多一层类型判断，收益为零）；走 `navigator.clipboard.read()`（实测 ⑤ 拿不到文件）。

**D2：`files.length === 0` 时一个字都不拦——不 `preventDefault`、不 toast。**
理由：文本粘贴是输入框最高频操作，任何拦截面都是灾难性回归；「检测到不是文件就提示一下」也会在每次粘文本时打扰用户。被否决项：粘贴非图片文件时提示「仅支持图片」（用户明确要的就是文件，且 ④ 证明混合剪贴板根本不会进 `files`）。

**D3：paste 只绑在 `textarea` 上，不做文档级监听。**
理由：粘贴意图几乎都发生在输入框内（截图后手已经在打字）；文档级监听会在配置页/搜索框等其它输入处劫持粘贴，且这些页面的默认行为本就正常。被否决项：绑 `.composer` 容器（点空白处粘贴也能用，但要处理冒泡去重与 focus 语义）；绑 `document`（风险最大）。

**D4：仅当文件名是「浏览器默认名」时才重命名，普通文件一律保留原名。**
判定：`''` / `image.png` / `image.jpg` / `image.jpeg` / `image.webp` / `image.gif` / `image.bmp`（不区分大小写）。
重命名：`paste[-seq].<ext>`，`ext` 优先取原名后缀，缺失时由 MIME 反推（`image/jpeg → jpg`），同一批内 `seq` 从 2 起递增。
**实施调整（2026-10-28，E2E 实测驱动）**：初版设计为 `paste-YYYYMMDD-HHmmss[-seq].<ext>`；实测发现服务端 `writeUpload()` 已给每个落盘名加 `YYYYMMDD-HHmmss-` 前缀，前端再带就成双时间戳 `20261028-163901-paste-20261028-163901.png`——同秒连贴的多张截图前缀完全一致，被 chip 的 190px 省略号截断后彼此无法区分，恰与 D4 的意图相反。故前端只产 `paste.png` / `paste-2.png`，落盘名 `20261028-163901-paste.png` / `20261028-163901-paste-2.png` 既含时间又可区分。
理由：`sample-a.txt` 被改成 `paste-…` 会让用户认不出自己贴的是哪个文件；而截图全叫 `image.png`，多张连贴后 chip 无法区分。被否决项：全部重命名（破坏原名信息）；全部不重命名（多张截图同名，且服务端同秒冲突链会产出 `-2`/`-3` 的毫秒段文件名，更难读）。

**D5：给 `uploadRaw` 加可选第三参 `fileName?: string`，不构造新的 `File` 对象。**
理由：`new File([file], newName)` 会复制 blob 引用，且 `File` 的 `lastModified` 等信息与真实文件脱钩；只需在发请求时把 `x-file-name` 换成目标名即可（`body` 仍是原 `file`）。改动 4 行，向后兼容（既有调用点不传第三参，行为不变）。被否决项：改 `writeUpload` 让它自己识别默认名（后端不该猜前端来源）。

**D6：图片判定看 `file.type.startsWith('image/')`（缩略图），视觉可读性判定看扩展名白名单（警告）。**
理由：两者语义不同——缩略图只要浏览器能渲染就给（`svg` 也能显示，用户可判据），而视觉工具只认 `png/jpg/jpeg/webp/gif/bmp`（`src/tools/vision/image.ts:20-27`）。用一个判据会导致「svg 无缩略图」或「svg 被标记可用」二选一的错误。被否决项：统一按 MIME 白名单（漏掉 svg 缩略图；且服务端判定的是**扩展名**，MIME 与扩展名可能不一致）。

**D7：blob URL 只在「发送成功 / 删除 chip / 组件卸载」三处释放，发送失败**不**释放。**
理由：`send()` 失败时执行 `uploads.value = chipsSnapshot` 恢复输入（`ChatView.vue:518-522`），若在清空时就 revoke，恢复后的 chip 会变成碎图；而「失败不释放、成功再释放」既不会泄漏也不会碎图。被否决项：失败后按 `File` 重建 URL（多一份 `File` 常驻内存、多一条重建路径）；用 `URL.revokeObjectURL` 兜底定时清理（时机不可控）。

**D8：视觉可用性用 `GET /vision` 的 `available`，图片尺寸上限用 `GET /config/vision.maxImageBytes`，两者惰性加载一次并缓存。**
理由：`available` 已包含「`enabled=false`」与「无 API Key（含回退主模型 Key）」两种情况的合并判定与 `reason` 文案（`handlers/vision.ts:18-27`），自己读 `enabled` 会漏掉无 Key 的场景；`maxImageBytes` 不在 `/vision` 里，单键读一次即可（默认 10MB，`config/schema.ts:238`）。两者失败（网络/权限）时降级为「不显示警告」，不阻断上传。被否决项：`GET /config` 全量（响应大、含无关配置）。

**D9：单次粘贴上限 6 张、串行上传、streaming 期间拦截。**
理由：6 张与「人一次截图的合理批量」量级匹配，也远低于上传面板的心智负担；串行沿用 `onPickFiles` 的 `for await` 结构，避免并发打爆服务端与 toast 刷屏；streaming 拦截与 📎 按钮 `:disabled="streaming"` 语义一致（发送中改附件会与「下一条消息」的注入语义打架）。被否决项：不限数量（误贴 50 张会连发 50 个请求）；并发上传（toast 与 chip 顺序错乱）。

**D10：纯逻辑全部下沉到 `webui/src/paste-files.ts`，`ChatView.vue` 只做接线。**
理由：`ChatView.vue` 已 1872 行，再塞判据逻辑不可维护；纯函数可被 vitest 直接覆盖（项目既有 `tests/webui-autogrow.test.ts` 等 14 个同类文件即此模式）。被否决项：写成 `ChatView.vue` 内的局部函数（只能靠浏览器 E2E 验证，边界用例写不出来）。

**D11：后端 `buildContextNote` 追加一行图片类型提示（P1）。**
产出形如：

```
[文件上传] 20261028-143012-paste.png
  上传路径: C:\Users\…\.loop-agent\uploads\<sid>\20261028-143012-paste.png
  大小: 128.4 KB
  类型: 图片 image/png（可用 ask_image / describe_image / extract_json / ocr_image 查看）
```

理由：目前 note 只有文件名/路径/大小，主模型看到 `paste.png` 并不知道这是「能看的图」，容易只用 `fileRead` 读出二进制垃圾或干脆不复用视觉工具；显式标出类型与可用工具能把「贴图 → 问图」这条路走通。**代价**：`tests/api-uploads-raw.test.ts:113` 是 `toBe()` 精确断言、`tests/upload-manager.test.ts:281` 的 `buildContextNote` 用例需同步更新（已列入文件清单）。被否决项：不改 note、改在前端拼提示（前端拼接会与 `contextNote` 的单一来源分叉）。

## 三、任务详细设计

### 3.1 新增 `webui/src/paste-files.ts`

```ts
/** 单次粘贴最多接受的附件数（D9） */
export const PASTE_MAX_FILES = 6;

/** 视觉工具可读的图片扩展名（镜像 src/tools/vision/image.ts 的 SUPPORTED_IMAGE_EXTS，D6） */
export const VISION_IMAGE_EXTS: readonly string[];

/** 浏览器/系统贴图时的默认文件名（D4） */
export const DEFAULT_PASTE_NAMES: readonly string[];

export interface PastedFile {
  file: File;
  /** 上传时使用的文件名（默认名已重命名，D4） */
  name: string;
  /** 是否按图片处理（决定是否出缩略图，D6） */
  isImage: boolean;
}

/** 从 DataTransfer 取文件并按 D4 重命名；无文件返回 []（D1/D2） */
export function collectPasteFiles(dt: DataTransfer | null, now?: Date): PastedFile[];

/** 截断到上限，返回保留项与被丢弃数量（D9） */
export function capPasteFiles(list: PastedFile[], max?: number): { accepted: PastedFile[]; dropped: number };

/** 默认名判断（D4） */
export function isDefaultPasteName(name: string): boolean;

/** paste[-seq].<ext>（D4；ext 优先取原名后缀，缺失时按 MIME 反推；不带前端时间戳） */
export function renamePastedFile(name: string, mime: string, seq?: number): string;

/** 视觉可读性警告文案；无问题返回 null（D8） */
export function visionSkipReason(
  name: string,
  mime: string,
  bytes: number,
  cfg: { available: boolean; unavailableReason?: string; maxImageBytes: number },
): string | null;
```

边界与错误处理：

| 情况 | 行为 |
| --- | --- |
| `dt === null` | 返回 `[]`（不抛错，交由调用方走默认粘贴） |
| `files` 为空 | 返回 `[]` → 调用方不 `preventDefault`（D2） |
| 文件名为空串 | 视作默认名并重命名（D4） |
| MIME 为空但后缀是 `.png` | `isImage` 按扩展名兜底为 `true`（资源管理器个别场景 `type` 为空） |
| 超过 `PASTE_MAX_FILES` | 保留前 N 个，`dropped` 交给调用方 toast |
| `bytes > maxImageBytes` | `visionSkipReason` 返回「超过视觉上限 X MB，Agent 无法查看此图」 |
| `available === false` | 返回「视觉链路未启用/无 Key」+ 服务端 `reason` |
| 非图片文件 | `visionSkipReason` 返回 `null`（文本类文件 Agent 用 `fileRead` 就能读，无需警告） |

## 七、风险与已知限制

| 项 | 说明 |
| --- | --- |
| 浏览器差异 | 已只按 Chrome/Edge（Chromium）实测；Firefox/Safari 的 `clipboardData.files` 行为未验证（列非目标） |
| headless 不可验 | 剪贴板与 headless 隔离，E2E 必须用有头 Chrome（1.3 ⑥），CI 无头环境下此链路只能靠单测覆盖纯逻辑 |
| 跨会话 chip 归属 | chip 在上传时绑定 `sessionId`，随后切换会话再发送会把文件名带进新会话（文件仍在旧会话目录）。此为**既有问题**（📎 同款），本任务不扩大也不修复 |
| 截图内存态 | 粘贴位图无源文件路径，`contextNote` 里只有落盘后的上传路径；与 📎 上传的 `originalPath: ''` 语义一致 |
| `keep-alive` 未验证 | 若路由对 `ChatView` 启用 `keep-alive`，`onUnmounted` 不触发，blob URL 释放将依赖「发送成功/删除」两处（上限 6 个，影响可控）。本轮已确认组件卸载路径存在但未做「切路由后 revoked 计数增加」的实测 |
| 超限文案精度 | `fmtMb()` 用 `toFixed(1)`，当 `vision.maxImageBytes` 小于约 51KB 时警告会显示「超过视觉上限 0.0 MB」（本轮把上限压到 1KB 构造用例时出现）。默认 10MB 不会触发；已记入优化建议台账待改 |
| 视觉工具看图未闭环 | E2E 只验到「粘贴 → 上传 → chip → `contextNote` 注入」，「Agent 实际调用 `ask_image` 看图」依赖真实模型视觉能力（本机 DeepSeek 视觉链路不稳定），需在可用环境下补一次人工走查 |

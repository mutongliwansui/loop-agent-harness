## 一、任务目标需求

### 1.1 背景（痛点）

WebUI 上传图片并基于图片完成问答后，**刷新重新进入页面**，最初那条用户消息不再显示附件 chip，而是把给模型看的附注原文整段裸渲在气泡里：

```
[文件上传] 20261113-094256-paste.png
  上传路径: C:\Users\muton\.loop-agent\uploads\sess_522b6010_20261113_094254\20261113-094256-paste.png
  大小: 71.3KB
  类型: 图片 image/png（可用 analyzeImage 查看）
```

同一件事在「发送当场」与「刷新之后」呈现完全不同：当场是「📎 附件 chip + 干净正文」，刷新后是「内部实现细节原文」。用户感知为「样式坏了」，本质是**两条渲染路径取了不同的数据源**。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
| --- | --- | --- |
| 发送时气泡只显示用户输入正文 | `ChatView.vue:794-806` 把各附件 `contextNote` 与正文以 `\n\n` 拼成 `message` 提交，同时把 `text`（纯净正文）与 `files`（文件名数组）传给 `sendMessage`；`chat-stream.ts:1649-1654` 用 `opts.text` 建乐观气泡 | ✅ 发送当场正确 |
| 落盘时能生成「纯净展示版」 | `store.ts:214-218` 只用 `stripMemorySection()` 生成 `show_content`，**不识别上传 note**；note 与正文同在 `content` 里，故 `stripped === m.content`，`show_content` 根本不写入 | ❌ 缺失：note 无剥离规则 |
| 消息能承载附件元信息 | `src/types.ts:260-264` 的 `ChatMessage` 联合类型**无任何附件字段**；附件信息只以文本形式编码在 `content` 里 | ❌ 无结构化字段 |
| 刷新后能恢复附件 chip | 前端 `chat-stream.ts:434` 取 `stripMemorySection(show_content \|\| content)` 渲染；`m.files` 只有流式临时态（`chat-stream.ts:1488` 的 `keepLocalUserBubbles`，凭空重建时无值） | ❌ 磁盘无数据可恢复 |
| 重试时不丢附件 | `sessions.ts:566` `const text = (userMsg.show_content ?? userMsg.content ?? '').trim()` 优先取 `show_content` | ⚠️ 陷阱：一旦写入剥离版 `show_content`，重试将丢附件（详见 D4） |
| 新字段不污染 LLM 请求 | `llm/client.ts:153-162` `normalizeMessages()` 用 `...rest` 透传，只显式解构 `is_compact/is_show/show_content/kind/usage/msgId/tool_calls` | ⚠️ 陷阱：新字段必须加进解构白名单，否则触发 API 400 |
| 附件可点击预览 | `GET /uploads/view`（需求 20261028-006）已具备受控只读预览，`FilesView.openUploads` 已接线 | ✅ 能力已就绪，仅缺数据与入口 |

**关键结论**：这不是样式问题，而是**三处断点叠加**——落盘不剥 note、消息无附件字段、前端无数据源。三者共同造成「刷新即裸渲」。

### 1.3 任务目标

1. **落盘侧生成纯净展示版**：`toStoredMessage()` 生成 `show_content` 时，在 `stripMemorySection()` 之后**再剥离上传 note 前缀段**；`content` **一字不动**（模型可见性、路径、MIME 全部保留）。
2. **新增磁盘字段承载附件元信息**：`SessionMessageFlags` 增 `attachments?: MessageAttachment[]`（`fileName` / `bytes` / `path` / `mime`），由落盘时从 `content` 解析填充。
3. **前端渲染数据驱动**：用户气泡优先取 `show_content`，附件 chip 优先取 `attachments`；两者缺失时（存量数据）**前端解析 `content` 兜底**，保证老会话刷新后同样正确。
4. **重试不丢附件**：重试路径改为「`show_content` 正文 + `attachments` 重建 note」拼接，而非直接用 `show_content` 当整条消息。
5. **模型请求零变化**：`content` 不变 + `attachments` 加入 `normalizeMessages` 剥离白名单，`toOpenAITools` / 前缀缓存均不受影响。

### 1.4 设计约束

- **`content` 语义不可变**：模型侧必须仍能看到完整 `[文件上传]` 附注（含绝对路径与 MIME），否则视觉链路（`analyzeImage` 按路径读图）会断。
- **存量会话不改写磁盘**：不批量重写老会话 JSON（已被多轮压缩覆盖，且改写风险高），仅保证「新写入带字段 + 老数据前端兜底」。
- **零新增依赖**：解析用 `node:path` + 现有 `MIME_BY_EXT`。
- **三平台兼容**：`content` 里的路径是 Windows 绝对路径（含 `C:\`），解析须按「行首两空格缩进 + 固定中文标签」而非路径正则，避免盘符/分隔符差异。
- **不碰 SSE 协议与 `POST /messages` 请求体**：附件仍随 `message` 文本上送，本任务只改「落盘与回读」。
- **不擅自重启用户服务**（当前 `loop-agent.exe --serve` 占 3000 端口），验证另起端口。

## 二、方案设计

### 2.1 总体思路

```
                    ┌──────────────── 发送（不变）────────────────┐
  用户贴图/选文件 → uploads chip → send(): message = note + "\n\n" + text
                                                      │
                                                      ▼
  磁盘落盘 ── toStoredMessage() ──┬─ content      = 原文（note + 正文）   ← 不动
  （本任务新增）                  ├─ show_content = 剥离(note, 记忆前缀)   ← D1/D2
                                  └─ attachments  = 解析(note) 结构化     ← D3/D5
                                                      │
  ┌───────────────────────────────────────────────────┴──────────────┐
  ▼                                                                  ▼
  LLM 请求                                                  前端回读渲染
  normalizeMessages 剥离 attachments                       GET /sessions/:id
  → 只用 content（note 完整）                                ├─ 正文 = show_content   （缺失→前端剥 note 兜底 D6）
  → 前缀缓存不变（D8）                                       └─ chip = attachments    （缺失→前端解析 content D6）
                                                             → 点击走 /uploads/view（已有）
  重试 ── show_content + 重建 note → 完整 content（D4）
```

### 2.2 关键设计决策

**D1｜剥离动作发生在落盘层 `toStoredMessage()`，不改请求侧拼接逻辑。**
在 `store.ts` 已有的 `stripMemorySection()` 之后追加 `stripUploadNotes()`，产出 `show_content`。理由：请求侧拼接（`ChatView.vue:794-796`）是「上送报文」，落盘侧才是「展示语义」，职责分离；且 CLI `/upload` 路径也会经过 `toStoredMessage`，一处修改两端受益。
*被否决*：在 `POST /messages` handler 里预剥离——会丢掉原始 `content`，模型看不到附件路径。

**D2｜`show_content` 只在「确实发生变化」时写入，保持既有幂等语义。**
沿用现有 `if (stripped !== m.content) out.show_content = stripped` 判断（`store.ts:217`），只是把 `stripped` 的来源从「仅剥记忆前缀」扩为「剥记忆前缀 + 剥 note」。这样无附件、无记忆前缀的普通消息**不会**新增 `show_content` 字段（磁盘零膨胀，与今日行为逐字节一致）。

**D3｜附件元信息用新字段 `attachments` 承载，不塞进 `show_content`。**
结构：`{ fileName: string; bytes: number; path: string; mime?: string }[]`，挂在 `SessionMessageFlags` 上（与 `show_content` 同层，天然不进 LLM 请求语义）。
*被否决*：把 JSON 塞进 `show_content` 的隐藏段——前端要二次解析、且污染展示文本；用 `files: string[]` 只存文件名——丢失路径无法点击预览。

**D4｜重试改为「正文 + 重建 note」，不是「正文单发」。**
`retry` 目前 `const text = (userMsg.show_content ?? userMsg.content ?? '')`。本任务改为：`text = show_content`，若 `attachments` 非空则用与 `buildContextNote()` 同构的函数重建 note 段拼回。理由：重试是「让模型重新回答同一问题」，输入必须与首轮等价，否则「这张图里有什么」会因丢附件而答错。
*待确认*：见 Q2——是否改为「直接复用 `content` 原文」更简单（等价性最强，但会把记忆前缀一起重发）。

**D5｜解析规则按「结构行」而非「路径正则」。**
note 格式固定（`buildContextNote()`，`upload/manager.ts:359-370`）：
```
[文件上传] <fileName>
  上传路径: <abs path>
  大小: <formatBytes>
  类型: 图片 <mime>（可用 analyzeImage 查看）     ← 仅图片有
```
解析按行匹配四个固定中文标签（`^\[文件上传\] `、`^  上传路径: `、`^  大小: `、`^  类型: 图片 `），天然跨平台；多条附件以 `\n\n` 分隔（`ChatView.vue:796` 的 join 结果）。**解析函数放在 `src/upload/manager.ts` 并导出**，与 `buildContextNote` 同文件成对维护（单一出处，防格式漂移）。

**D6｜存量数据前端兜底，后端不做一次性迁移。**
`chat-stream.ts` 目前取 `stripMemorySection(m.show_content || m.content)`。改为：先取 `show_content || stripMemorySection(content)`，再**无条件**追加 `stripUploadNotes()`；`attachments` 缺失时用同一个前端纯函数解析 `content` 补 `m.files`。
*被否决*：启动期批量迁移存量会话——用户已明确「程序不改写任何存量数据」，且改写会被压缩轨迹重建路径反复覆盖，收益不抵风险。

**D7｜`show_content` 保持「纯展示」定位，压缩载荷读取需单独评估。**
`compaction-payload.ts:112-115` 优先取 `show_content` 写 L1 摘要载荷。剥离 note 后，摘要里只保留正文、丢失附件路径。这与该处注释「真实用户输入」一致，且摘要是给人看的精简版，**判定为可接受的行为变化**，不做特殊处理（列入验收观察项）。

**D8｜`attachments` 必须加入 `normalizeMessages` 解构白名单。**
`llm/client.ts:153-162` 是 `...rest` 透传结构，漏一个字段就发给模型触发 400（非标准字段）。这是本任务**最高风险的改动点**，须配单测锁定「落盘带 `attachments` 的消息经 `normalizeMessages` 后不含该键」。

**D9｜前端 chip 复用既有 `/uploads/view` 预览通道，不新增端点。**
`tool-meta.ts` 已有 `/.loop-agent/uploads/` 段判定 → `FilesView.openUploads`（需求 20261028-006/007 已验证）。chip 点击直接把 `attachments[i].path` 交给该通道即可，后端零改动。

**D10｜`files` 前端字段保留一版兼容，语义收敛为「由 attachments 派生」。**
`ChatMsg.files` 被 `ChatView.vue:1209`（`📎 {{ m.files.join('、') }}`）与 `keepLocalUserBubbles` 使用。本任务把刷新路径改为填 `attachments`，气泡模板升级为 chip 列表；`files` 保留但我们内部统一从 `attachments.map(a => a.fileName)` 派生，避免两套真相。

### 2.3 外部检索结论（可借鉴方案与坑）

| 来源 | 结论 | 对本任务的指导 |
| --- | --- | --- |
| BYOKchat《How File Attachments Flow Through AI APIs》 | 「Keep transport strategy separate from attachment identity」；「Attachment semantics belong to the user message」；「Provider IDs are not portable conversation content」 | 附件元信息应作为**用户消息的属性**持久化，与传给模型的传输形态解耦——正是 D3 的思路 |
| assistant-ui cloud persistence docs | 附件以独立 `Attachment` 记录保存，消息里存引用；重新加载时由 `load_thread_items` 重新组装 | 我们选择内联在消息上（本地单机、无 blob 服务），但同样坚持「元信息结构化」 |
| ai-agent-builder SPEC-0029 | 「We persist file parts in UI history for user-visible context, but … file parts are stripped; a text hint is appended `[Attached files: ...]`」 | 与我们既有架构高度同构：UI 存结构化、模型侧收文本提示。佐证 D1「content 保留文本提示」的合理性 |
| Vercel AI SDK message persistence | 存的是 `useChat` 展示格式，加载时用 `validateUIMessages` 校验 | 提示**回读需校验**：我们应在解析 `attachments` 失败时静默降级为「无附件」而非抛错 |
| Google Chat `spaces.messages.attachments` | `contentName` / `contentType` / `thumbnailUri` / `downloadUri` 分离 | 印证字段拆分为「名称 / 类型 / 访问路径」是通用做法 |

**已知坑汇总**：① 新字段漏出到模型请求 → 400（D8）；② 只存文件名导致无法预览（D3）；③ 存量数据无字段 → 必须前端兜底（D6）；④ 回读解析失败 → 必须降级不抛错。

## 三、任务详细设计

### 3.1 数据结构（`src/types.ts`）

```ts
/** WebUI 上传附件元信息（需求 20261113-003 D3）：随用户消息落盘，仅展示与重试用，不进 LLM 请求 */
export interface MessageAttachment {
  /** 上传后文件名（含时间戳前缀，如 20261113-094256-paste.png） */
  fileName: string;
  /** 字节数 */
  bytes: number;
  /** 上传后的绝对路径（用于 /uploads/view 预览与重试重建 note） */
  path: string;
  /** 图片 MIME（非图片或缺省为 undefined） */
  mime?: string;
}

export interface SessionMessageFlags {
  // …既有字段不变…
  /** 结构化附件元信息；缺省表示该消息无附件（存量数据由前端解析 content 兜底） */
  attachments?: MessageAttachment[];
}
```

### 3.2 解析与剥离（`src/upload/manager.ts` 新增导出）

```ts
/** 从 content 解析附件元信息（D5）：按固定中文标签逐行匹配，跨平台安全；解析不出返回 [] */
export function parseUploadNotes(content: string): MessageAttachment[];

/** 从 content 剥离上传 note 段，返回纯净正文（D1）；无 note 时原样返回 */
export function stripUploadNotes(content: string): string;

/** 由附件元信息重建 note 段（D4 重试用）：输出与 buildContextNote 逐字节一致 */
export function rebuildContextNote(a: MessageAttachment): string;
```

**边界与错误处理**

| 输入场景 | 行为 |
| --- | --- |
| `content` 无 `[文件上传]` 行 | `parseUploadNotes` → `[]`；`stripUploadNotes` → 原样返回 |
| note 段只解析出部分字段（如缺「大小」） | 该条附件跳过 `bytes`（置 0）仍收录，不整条丢弃 |
| 多条附件（note 之间 `\n\n`） | 按 `[文件上传]` 行分块解析，全部收录 |
| 正文本身以 `[文件上传]` 开头（用户手打） | 仅在「其后紧跟 `  上传路径: ` 行」时认定为 note，避免误剥 |
| 剥离后正文为空（只传文件没打字） | `stripUploadNotes` → `''`；落盘时 `show_content` 写 `''`？**否**——判据 `stripped !== m.content` 仍成立，写空串，前端渲染「仅附件」气泡 |
| `attachments` 字段结构损坏 | 前端回读时 try/catch → 降级为 `[]`（D6/检索结论④） |

### 3.3 落盘侧（`src/session/store.ts`）

`toStoredMessage()` 的 user 分支改为：

```ts
if (m.role === 'user' && typeof m.content === 'string') {
  // 既有：剥 L2 记忆前缀
  let stripped = stripMemorySection(m.content);
  // 本任务：再剥上传 note（D1/D2）
  const notes = parseUploadNotes(stripped);
  if (notes.length > 0) {
    out.attachments = notes;            // D3：结构化元信息
    stripped = stripUploadNotes(stripped);
  }
  if (stripped !== m.content) out.show_content = stripped;
}
```

**注意**：`out.attachments` 须在 `if` 内赋值，避免无附件消息产生空数组字段（保持 D2 的「零膨胀」）。

### 3.4 模型请求隔离（`src/llm/client.ts`）

`normalizeMessages()` 的解构列表追加 `attachments`（D8）：

### 3.5 重试路径（`src/api/handlers/sessions.ts:565-567`）

```ts
// D4：正文取展示版，附件由元信息重建（避免重试丢图）
const body = (userMsg.show_content ?? '').trim();

  || (userMsg.content ?? '').trim();   // 兜底：无 show_content 的存量消息仍用原文
```

### 3.6 前端回读（`webui/src/chat-stream.ts:428-441`）

```ts
if (m.role === 'user') {
  flush();
  // D6：show_content 优先 → 前端剥记忆前缀 → 前端剥上传 note（存量兜底）
```

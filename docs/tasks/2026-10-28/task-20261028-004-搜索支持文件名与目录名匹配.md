# 任务 20261028-004：文件目录搜索支持文件名与目录名匹配

> 对应需求编号：20261028-004（见 [需求台账](../../requirements/需求.md)）
> 提出时间：2026-10-28　　实施时间：2026-10-28

---

## 一、任务目标需求

### 1.1 背景（痛点）

文件目录面板右侧顶部有一个搜索框，占位符是「搜索文件…」，但它的后端实现只做**全文内容匹配**：递归遍历工作空间的每个文件，读入后按行 `toLowerCase().indexOf(needle)`，命中行才产出一条结果。文件名、目录名只作为「命中位置」的附带信息出现在结果里，**不参与匹配**。

由此产生三个实际困扰：

1. **按名字找文件找不到**——搜 `task-20261026`、`nav-menu`、`bench-format` 这类只出现在文件名里的词，结果为空，用户会误判「这个文件不存在」。
2. **文案与行为不一致**——输入框写「搜索文件…」、`title` 写「搜索文件内容」，用户无法从界面上判断匹配范围到底是什么。
3. **改完文件想按名找回很费劲**——刚编辑过 `autogrow.ts`，只能靠树里逐层展开目录去找。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
| --- | --- | --- |
| 内容匹配 | `src/api/handlers/fs.ts` `scanFor()`：逐文件 `readFile` → 按 `/\r?\n/` 切行 → 每行 `toLowerCase().indexOf(needle)`，命中 push `{path,name,line,text}` | 已具备 |
| 文件名匹配 | 同上，`e.name` 只用于构造结果字段与 `childRel`，未参与比较 | **缺失** |
| 目录名匹配 | 同上，目录仅在 `filtered.filter(x => x.isDirectory())` 里被递归下钻 | **缺失** |
| 结果结构 | `GET /fs/search` 返回 `{ query, truncated, results: [{path,name,line,text}] }` | 需扩 `kind` 字段 |
| 前端分组 | `webui/src/fs-tree.ts` `groupHits()` 按 `path` 分组、组内按 `line` 升序；`FilesView.vue` 用 `hitGroups` 渲染 | 需支持 `line=0` 的名称命中与目录命中 |
| 目录定位 | `FilesView.vue` `gotoCrumb(path)`：逐段 `expandDir` + `scrollIntoView` 滚动定位 | **可直接复用** |
| 关键词高亮 | `highlightParts(text, kw)`：`indexOf` 实现，元字符安全 | 可直接复用（文件名也走它） |

### 1.3 任务目标

把匹配范围从「内容」扩为「**文件名 + 目录名 + 内容**」三类，具体要求：

- 名称命中**优先于**内容命中（名称更精准，不能被前面的内容命中挤占 200 条上限）。
- 目录名命中点击后**在树中展开并定位**该目录。
- 顶部计数与分组区分文件与目录：`N 处命中 · M 个文件 · K 个目录`（K 为 0 时省略）。
- 大小写不敏感、`hidden` 开关、`node_modules`/`__pycache__` 恒排除三条既有规则对名称匹配同样生效。
- 同一文件既命中文件名又有内容命中时，两类信息都保留：组头高亮文件名，徽标仍为内容命中数。

### 1.4 设计约束

- **零新增依赖**：只用 `node:` 内置模块与既有前端工具函数。
- **向后兼容**：`kind` 字段为新增可选字段；旧前端忽略它仍能正常按行号渲染（名称命中因 `line=0` 会被当作第 0 行，属可接受的降级）。
- **不改搜索范围语义**：仍为整个工作空间，不随当前展开目录收缩。
- **不建索引**：仍为逐文件扫描（工作空间规模远小于需要索引的量级）。
- 前端纯逻辑下沉到 `webui/src/fs-tree.ts`，便于 vitest 直接覆盖。

## 二、方案设计

### 2.1 总体思路

```
                       GET /fs/search?q=&hidden=
                                  │
                                  ▼
                       handleSearch()  ← 入口不变
                                  │
                                  ▼
                    searchWorkspace(root, hidden, q)   ← 新增编排层
                    ┌─────────────┴─────────────┐
                    ▼                           ▼
        阶段① 只 readdir 遍历            阶段② 逐文件读内容
        （不读文件，很快）                （耗 IO，200 条上限兜底）
          D1 文件名 / 目录名匹配            D3 内容行匹配
                    │                           │
                    └─────────────┬─────────────┘
                                  ▼
                   results: [{ path, name, line, text, kind }]   ← D2
                     kind='name'   文件名命中（line=0）
                     kind='dir'    目录名命中（line=0）
                     kind='content' 内容行命中（line≥1）
                                  │
                                  ▼
                    WebUI splitHits(results)   ← D6/D7
                    ┌─────────────┴─────────────┐
                    ▼                           ▼
              dirs: DirHit[]              files → groupHits()
              （目录行，点击 gotoCrumb）    （组头 nameHit 高亮 + 内容行）
```

### 2.2 关键设计决策

**D1：文件名与目录名都参与匹配。**
理由：用户搜 `task` 时，`docs/tasks/` 目录与 `task-20261026-001-*.md` 文件都在期望内；只匹配文件名会让「找目录」仍然无解。被否决项：仅匹配文件名（目录仍需靠树展开）。

**D2：结果项新增 `kind: 'name' | 'dir' | 'content'`，名称命中 `line` 置 0。**
理由：前端需要区分三种渲染方式（文件名高亮 / 目录行 / 内容行），而 `line=0` 天然不可能与真实行号冲突，可作为兼容旧前端的降级信号。被否决项：拆成 `results` + `nameHits` 两个数组（响应结构分叉，客户端要合并两处逻辑）。

**D3：名称命中优先——两阶段扫描（先只 readdir 收集名称命中，再逐文件扫内容）。**
理由：单次深度优先遍历时，深层目录的名称命中会晚于浅层文件的内容命中，一旦 200 条上限被浅层内容命中占满，最精准的名称命中反而丢失。两阶段以「多跑一遍 readdir」换取「名称命中必有位置」，readdir 远比 readFile 便宜。被否决项：单次遍历 + 名称命中插队到数组头部（需反复 splice，且截断后仍可能丢名称命中）；调大上限（治标，响应体变大）。

**D4：同一文件名称命中后仍继续扫其内容。**
理由：搜 `fs` 时 `fs-tree.ts` 既要出现在「文件名命中」也要露出「含 fs 的行」，否则用户还得二次搜索。被否决项：名称命中即短路跳过内容（漏信息）。

**D5：目录名命中只产出目录自身，不展开其下文件。**
理由：目录命中的点击语义是「在树里定位到它」，其下文件由树承担浏览职责；若把目录下所有文件都作为命中塞进来，会把 200 条上限吞掉且与「内容搜索」语义混淆。被否决项：目录命中连带列出子项（结果爆炸）。

**D6：前端新增 `splitHits(results)`，保留 `groupHits` 原语义。**
理由：`groupHits` 已被 8 条单测锁定「按文件分组、组内行号升序、组顺序取首次出现」的契约，改成返回 `{files, dirs}` 会破坏既有用例与调用点；新增一个只做「分离」的纯函数，`groupHits` 保持只管文件。被否决项：直接改 `groupHits` 签名（连带改单测与调用点，收益为零）。

**D7：`groupHits` 增加 `nameHit` 标记，`line=0` 的条目不计入 `hits` 行。**
理由：组头需要知道「这个文件是因为文件名命中而出现」以决定是否高亮文件名；把 `line=0` 混进 `hits` 会让模板渲染出一个空行号 + 空文本的假行。`nameHit` 为新增字段，不影响既有断言（既有用例都是字段级断言，非整对象 `toEqual`）。被否决项：用 `hits.length === 0` 反推（名称命中 + 内容命中同时存在时判断失真）。

**D8：计数与空态文案同步更新。**
顶部状态条：`N 处命中 · M 个文件`，有目录命中时追加 `· K 个目录`；输入框 `title` 改为「搜索文件名与内容（Ctrl K 聚焦）」，占位符保持「搜索文件…」（窄面板 204px 下仍完整可见，已由 20261026-001 的容器查询验证）。空态副文案追加「文件名与内容都会搜索」。被否决项：改占位符为「搜索文件名与内容…」（窄面板下会被截断）。

## 三、任务详细设计

### 3.1 后端 `src/api/handlers/fs.ts`

```ts
/** 搜索命中项（kind 为 20261028-004 新增；名称命中 line=0） */
interface SearchHit {
  path: string;                     // 相对工作空间根，'/' 分隔
  name: string;                     // 条目名（最后一段）
  line: number;                     // 内容命中为 1-based 行号；名称/目录命中为 0
  text: string;                     // 内容命中为命中行（裁剪至 240 字符）；名称/目录命中为 ''
  kind: 'content' | 'name' | 'dir';
}

/** 阶段①：只 readdir，收集文件名与目录名命中（D1/D3） */
async function scanNames(dirAbs, dirRel, hidden, needle, results): Promise<void>

/** 阶段②：逐文件读内容做行匹配（原 scanFor 主体，补 kind） */
async function scanContents(dirAbs, dirRel, hidden, needle, results): Promise<void>

/** 编排：名称命中先跑、先行占位，再跑内容（D3） */
async function searchWorkspace(root, hidden, q): Promise<SearchHit[]>
```

边界与错误处理：

| 情况 | 行为 |
| --- | --- |
| 目录不可读（`readdir` 抛错） | 静默跳过该目录（沿用现状），不影响其余分支 |
| `stat` 失败 / 文件为 0 字节 / > 512KB | 内容阶段跳过（沿用现状）；名称阶段**仍可命中**（名称与大小无关） |
| 二进制文件 | 名称阶段可命中（如 `blob.png`），内容阶段跳过 |
| 恒排除目录 | `node_modules`/`__pycache__` 自身名字也不参与匹配，其下不下钻 |
| dot 条目 | `hidden=0` 时目录/文件名均不参与匹配（与内容一致） |
| 达到 `MAX_SEARCH_RESULTS` | 名称阶段命中满即停，内容阶段在剩余额度内继续；`truncated` 语义不变 |

### 3.2 前端 `webui/src/fs-tree.ts`

```ts
export interface SearchResult {
  path: string; name: string; line: number; text: string;
  kind?: 'content' | 'name' | 'dir';   // 可选：兼容旧后端响应
}

export interface HitGroup {
  path: string; dir: string; name: string;
  hits: SearchResult[];                // 仅内容命中（line ≥ 1），行号升序
  nameHit: boolean;                    // D7：该文件是否文件名命中
}

export interface DirHit { path: string; name: string; dir: string }

/** D6：把目录命中分离出来，其余交给 groupHits */
export function splitHits(results: SearchResult[]): { files: HitGroup[]; dirs: DirHit[] }
```

演进项（本任务不做）：搜索历史、正则/glob、结果高亮跳转到具体行、把搜索限定在展开目录。

### 3.3 前端 `webui/src/views/FilesView.vue`

- `hitGroups` → 改由 `splitHits` 得出 `fileGroups` / `dirHits`；`footCount` 增加目录计数。
- 模板：无命中 → 空态（文案更新）；有命中 → 目录段（`.res-dir` 行，点击 `gotoCrumb`）+ 文件组（组头 `nameHit` 时用 `highlightParts` 高亮文件名，徽标仅在 `hits.length > 0` 时显示）。
- 样式：新增 `.res-dir`（复用 `.res-file` 的排版，图标换目录配色）。

## 一、任务目标需求

### 1.1 背景（痛点）

用户上传扫描件 PDF 让 `fileRead` 读文字，链路走到 `src/documents/pdf-raster.ts` 的 `rasterizePdfPages()` 后直接断掉：

- 现状只支持**外部工具**（`pdftoppm` / `mutool` / `gs`）与用户自定义命令模板；
- 现场内网机（Windows 10 神州网信政府版 19044）三者都没装，扫描页一张也渲不出来；
- 结果 `fileRead` 只能抛「该 PDF 没有可提取的文本层（可能是扫描件）；可用 analyzeImage 识别图片，或先转换为文本型 PDF」——而 `analyzeImage` 要用户自己先有 PNG，形成死循环。

矛盾在于：**Windows 自己就带一个 PDF 渲染器**（`Windows.Data.Pdf`，Edge/PDF 阅读器同款），通过 WinRT 投影即可调用，而项目已经为 OCR 建立了「`powershell.exe -File` 调用 WinRT」的完整范式（`src/ocr/engine-winrt.ts`，20261112-002 已在现场机实证可用）。渲染这件事完全可以零依赖借过来。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
| --- | --- | --- |
| PDF → 页图片 | [`src/documents/pdf-raster.ts`](file:///D:/trae_workspace/loop-agent-command/src/documents/pdf-raster.ts) 仅 `pdftoppm`/`mutool`/`gs`/自定义模板 | ❌ 三者皆无时能力完全缺失 |
| 零依赖 WinRT 调用范式 | [`src/ocr/engine-winrt.ts`](file:///D:/trae_workspace/loop-agent-command/src/ocr/engine-winrt.ts) 已有 `powershellPath()`、脚本落盘（sha1 命名）、`runPowerShell()` 超时/输出截断、`parsePsOutput()` | ✅ 可直接复用，避免第二套 spawn 逻辑 |
| 脚本编码与中文路径 | 同文件注释已确立「纯 ASCII 无 BOM + `-File` 调用」；20261112-003 的探针脚本处理中文路径成功 | ✅ 范式成立 |
| WinRT PDF 渲染可行性 | 本次实测（见 3.1） | ✅ 单页端到端 263ms |
| 外部工具缺失时的提示 | `RASTERIZER_HINT` 只讲「装 poppler/MuPDF/Ghostscript」 | ⚠️ Windows 上该提示已不准确，需改写 |
| 探测缓存 | `probeCache` + `resetRasterizerProbeCache()`（单测钩子） | ✅ 沿用，新增 winrt 条目 |

### 1.3 任务目标

1. 为 `rasterizePdfPages()` 增加 **Windows 内建后端**（`Windows.Data.Pdf`），在没有任何外部工具时也能把扫描页渲成 PNG。
2. 建立明确探测链：**自定义模板 → 内建 WinRT → pdftoppm → mutool → gs**，逐级回落，任一级失败不吞掉根因。
3. 把「脚本落盘 + spawn + 超时 + 输出解析」从 `ocr/engine-winrt.ts` 抽成共用模块，OCR 与 PDF 渲染共用一份实现。
4. 新增 `ocr.pdfRasterEngine`（`auto` / `winrt` / `external`）开关，现场 WinRT 组件被裁剪时可一键回落外部工具。
5. 改写 `RASTERIZER_HINT` 与 `fileRead` 的相关提示文案，Windows 上不再要求用户装外部工具。

### 1.4 设计约束

- **零新增 npm 依赖**；不动 `package.json` 的 `engines`（维持 `>=20.10`）。
- **SEA 单文件可打包**：不得引入需读取磁盘资源文件的 npm 包。
- **非 Windows 零影响**：`process.platform !== 'win32'` 时探测链与行为**逐字节等同当前版本**。
- 不改变既有预算：`MAX_RASTER_PAGES = 5`、`PAGE_TIMEOUT_MS = 15000`、`MAX_PAGE_IMAGE_BYTES = 12MB`、`RASTER_DPI = 150`。
- 脚本必须**纯 ASCII**（GBK 代码页机器安全），路径一律 `-LiteralPath`。
- 单页失败不得影响其余页；不得因渲染失败把已有文本层结果作废。

## 二、方案设计

### 2.1 总体思路

```
rasterizePdfPages(absPath, pages, { customTemplate, engine })
│
├─ 选引擎（D2）
│   customTemplate 非空            → custom
│   engine != 'external' && winrt  → winrt        ← D1 新增
│   engine != 'winrt'   && 外部工具 → pdftoppm/mutool/gs
│   都没有                          → null（RASTERIZER_HINT）
│
└─ 逐页循环（D3）
     ├─ custom / 外部工具：runCommand(cmd, args, 15s) → 读输出文件
     └─ winrt：renderPdfPageWinrt({ input, page, output, dpi, timeoutMs })
          ├─ exit 0  → 读输出文件（大小上限 12MB）
          ├─ exit 3  → 页级失败：warning，继续下一页
          └─ exit 2  → 引擎级不可用（D8）：
                 engine == 'auto' 且外部工具可用 → 记 warning + 整体切到外部工具重渲该页
                 否则 → 记 warning + RASTERIZER_HINT，终止剩余页
```

### 2.2 关键设计决策

#### D1 渲染后端选 Windows.Data.Pdf（WinRT），不引入 PDFium WASM

| 维度 | A. Windows.Data.Pdf | B. @hyzyla/pdfium 3.0 |
| --- | --- | --- |
| 新依赖 | 0 | 1（5.2MB wasm / 6.9MB 内联 JS） |
| engines | 不变（>=20.10） | 需 ≥22（冲突） |
| SEA 打包 | 无影响 | 需处理 wasm 资源 |
| 单页耗时 | 263ms | 153ms |
| PNG 体积 | 944KB | 237KB |
| 跨平台 | Windows only | 全平台 |

**否决 B 的理由**：与项目 `engines.node >= 20.10` 直接冲突；为一项「Windows 现场才用得上」的能力引入 7MB 体积与打包复杂度不划算。**B 转演进项**（若将来要支持 macOS/Linux 渲染，再按需引入，接口面已按 `RasterizerId` 留好）。

**否决「两者都做」的理由**：双后端意味着两条 CI 覆盖路径与两套 PNG 体积特征，当前无跨平台诉求。

#### D2 探测顺序：customTemplate 优先于内建，内建优先于外部工具

- `customTemplate` 是用户**显式**配置，任何自动探测都不得越过它（保持现状语义）。
- 内建 WinRT 优先于 `pdftoppm/mutool/gs`：零安装、零 PATH 依赖，是这套环境里的「默认路径」。
- `engine` 取值语义：`auto`（默认，全链）/ `winrt`（只用内建，缺则报错并给外部工具指引）/ `external`（只用外部工具与自定义模板，**这是现场排障的一键回落开关**，也是非 Windows 上的唯一路径）。

#### D3 逐页 spawn，不做「一次进程渲染多页」

- 现有外部工具后端就是每页一次进程，语义是「单页超时 15s + 单页失败隔离 + 单页大小上限」。
- WinRT 一次进程多页可省 ~84ms/页启动开销（5 页省 0.4s），但会让超时粒度变粗、失败隔离变难、临时文件清单变复杂。
- 实测单页 263ms（含启动），5 页上限下总耗时 ~1.3s，完全在 `fileRead` 的时间预算内。

#### D4 `DestinationWidth/Height = Size / 96 * DPI`（**不是 / 72**）

`PdfPage.Size` 报的是 **DIP（96/英寸）**，而 PDF 的 MediaBox 用 pt（72/英寸）。实测：同一 A4 页按 `/72*150` 得到 1646×2346（等效 200 DPI，PNG 1.57MB），按 `/96*150` 得到 1235×1760（PNG 944KB），与 PDFium 同参数输出 1233×1758 一致。**这是本任务最容易写错的一行，必须带注释**。

#### D5 输出走临时文件，不走 stdout base64

- 与外部工具后端**完全同构**：Node 侧 `mkdtemp` 建目录 → 脚本写 `page-N.png` → Node 读文件做 12MB 大小检查。
- 避免 944KB~数 MB 的 base64 走 stdout（编码风险 + 64KB 输出截断逻辑冲突，`runPowerShell` 现有 64KB stdout 上限会直接吃掉）。

#### D6 新增 `ocr.pdfRasterEngine`，默认 `auto`

现场 WinRT 组件可能被精简（神州网信版存在裁剪先例），此时需要**不改代码、只改配置**就能回落外部工具；同时它也让我们能在真机上一键复现/对照两条路径。

#### D7 把 PowerShell 运行时抽成共用模块，OCR 模块改为 import

- 现状 `runPowerShell()`、`ensureScriptFile()` 都是 `engine-winrt.ts` 的私有实现（约 90 行）。
- PDF 渲染要用的正是同一套：spawn `powershell.exe`、超时 kill、stdout/stderr 截断、`KEY=VALUE` 解析、脚本按内容 sha1 落盘。
- 复制一份会立刻产生「两套超时/截断口径」，故抽到 `src/util/powershell.ts`；`engine-winrt.ts` 保留同名 re-export，对外 API 与既有 65 例单测**零改动**。

#### D8 退出码三分：0 成功 / 2 引擎不可用 / 3 页级失败

区分「这台机器没有这个能力」与「这一页渲不出来」是回落策略的前提：
- `2` → 可回落外部工具，且应**整段切换**而不是逐页重试 5 次；
- `3` → 只记该页 warning，继续下一页（加密页、异常页不影响其他页）。

#### D9 不做的（本任务边界）

- 不做 macOS/Linux 渲染后端；不做 PDFium 集成；不改 `RASTER_DPI`（不引入 DPI 配置项）；不做多页合并进程；不强制渲染背景色（实测默认白底，OCR 正常）；不改 OCR 侧任何逻辑。

### 3.1 共用 PowerShell 运行时 `src/util/powershell.ts`（新文件，D7）

```ts
/** powershell.exe 路径：LOOP_AGENT_POWERSHELL 覆盖 → 系统目录 */
export function powershellPath(): string;

 * 同内容同 prefix 只写一次（进程内 Promise 缓存）。脚本内容必须纯 ASCII 无 BOM。

  stderr: string;

  timedOut: boolean;

/** spawn powershell.exe；超时 kill；stdout 上限 64KB、stderr 上限 8KB */
export function runPowerShell(args: string[], timeoutMs: number): Promise<PsRunResult>;

```

迁移方式：把 `engine-winrt.ts` 中 `powershellPath` / `winrtOcrLikelyAvailable` / `ensureScriptFile` / `runPowerShell` / `parsePsOutput` 的实现**原样搬入**（仅 `ensureScriptFile` 增加 `content`/`prefix` 参数），`engine-winrt.ts` 改为从 util import 并 `export { powershellPath, runPowerShell, parsePsOutput }` 保持既有导出名不变。

> 落盘目录从 `<tmpdir>/loop-agent-ocr-script` 变为 `<tmpdir>/loop-agent-ps`。旧目录不清理（幂等、无副作用），新旧脚本并存不影响。

### 3.2 新增 `src/documents/pdf-raster-winrt.ts`（新文件）

```ts
/** 内建渲染脚本内容（纯 ASCII；导出供单测断言「不含非 ASCII 字符」） */
export const WINRT_PDF_PS1: string;

/** 同步可用性判断：win32 且 powershell.exe 存在（不 spawn，不验证组件） */
export function winrtPdfLikelyAvailable(): boolean;

export interface WinrtRasterRequest {
  /** 源 PDF 绝对路径（含中文/空格安全，脚本内用 -LiteralPath） */
  input: string;
  /** 页码，1-based */
  page: number;
  /** 输出 PNG 路径（由调用方在 mkdtemp 目录内指定） */
  output: string;
  /** 目标 DPI，默认 150 */
  dpi?: number;
  /** 单页超时，默认 15000 */
  timeoutMs?: number;
}

export interface WinrtRasterOutcome {
  ok: boolean;
  /** true = 引擎级不可用（应回落外部工具）；false = 页级失败 */
  engineUnavailable: boolean;
  /** 失败原因（ok=false 时给可读文案） */
  error?: string;
  /** 耗时（毫秒） */
  elapsedMs: number;
}

export async function renderPdfPageWinrt(req: WinrtRasterRequest): Promise<WinrtRasterOutcome>;
```

进程退出码契约：

| 退出码 | 语义 | 脚本内触发点 |
| --- | --- | --- |
| `0` | 成功，PNG 已写到 `-Out` | 正常结束 |
| `2` | **引擎级不可用** | PowerShell Core（`PSEdition -eq 'Core'`）、`System.Runtime.WindowsRuntime` 加载失败、`AsTask` 反射失败、任一 WinRT Pdf 类型投影失败 |
| `3` | **页级失败** | PDF 不存在/打不开（`LoadFromFileAsync` 抛错）、页码越界、`RenderToStreamAsync` 抛错、写文件失败 |

`renderPdfPageWinrt` 的判定：
- `spawnError` → `{ ok:false, engineUnavailable:true }`（powershell 起不来 = 引擎不可用）
- `timedOut` → `{ ok:false, engineUnavailable:false }`（单页超时，属页级）
- `code === 0` 且输出文件存在且非空 → `{ ok:true }`
- `code === 2` → `engineUnavailable: true`，`error` 取 stdout 中 `[FAIL] ...` 行
- 其他 → `engineUnavailable: false`，`error` 取 `[FAIL] ...` 行或 stderr 首行

### 3.3 渲染脚本 `WINRT_PDF_PS1` 关键结构

以下为**已实测通过**的脚本骨架（探针版 → 生产版：去掉探测输出、加退出码三分、加 `-Out` 必填校验）：

```powershell
param(
    [Parameter(Mandatory=$true)][string]$Pdf,
    [Parameter(Mandatory=$true)][int]$Page,
    [Parameter(Mandatory=$true)][string]$Out,
    [double]$Dpi = 150
)
$ErrorActionPreference = 'Stop'

# 1) 环境门禁：必须 Windows PowerShell 5.1（WinRT 投影只在其上可解析）
if ($PSVersionTable.PSEdition -eq 'Core') { Write-Output '[FAIL] Powershell Core'; exit 2 }
if (-not (Test-Path -LiteralPath $Pdf))  { Write-Output '[FAIL] PdfNotFound'; exit 3 }
$Pdf = (Resolve-Path -LiteralPath $Pdf).Path

# 2) 反射取 AsTask 重载（泛型用于 IAsyncOperation<T>，非泛型用于 IAsyncAction）
Add-Type -AssemblyName System.Runtime.WindowsRuntime
# ... $asTaskGeneric / $asTaskAction 两个重载（缺一不可，见 D-坑 3）

# 3) 预热 WinRT 类型投影（程序集限定名，见 D-坑 4）
foreach ($tn in @(
    'Windows.Storage.StorageFile, Windows.Storage, ContentType=WindowsRuntime',
    'Windows.Data.Pdf.PdfDocument, Windows.Data.Pdf, ContentType=WindowsRuntime',
    'Windows.Data.Pdf.PdfPage, Windows.Data.Pdf, ContentType=WindowsRuntime',
    'Windows.Data.Pdf.PdfPageRenderOptions, Windows.Data.Pdf, ContentType=WindowsRuntime',
    'Windows.Storage.Streams.InMemoryRandomAccessStream, Windows.Storage.Streams, ContentType=WindowsRuntime',
    'Windows.Storage.Streams.DataReader, Windows.Storage.Streams, ContentType=WindowsRuntime'
)) { if (-not [type]::GetType($tn, $true)) { Write-Output '[FAIL] WinrtTypeMissing'; exit 2 } }

# 4) 加载 → 取页 → 渲染（注意 Size 是 DIP，除以 96）
$sf  = Await ([Windows.Storage.StorageFile]::GetFileFromPathAsync($Pdf)) ([Windows.Storage.StorageFile])
$doc = Await ([Windows.Data.Pdf.PdfDocument]::LoadFromFileAsync($sf))  ([Windows.Data.Pdf.PdfDocument])
if ($Page -lt 1 -or $Page -gt $doc.PageCount) { Write-Output '[FAIL] PageOutOfRange'; exit 3 }
$pg  = $doc.GetPage([uint32]($Page - 1))
$size = $pg.Size                                        # DIP (96/inch)!!
$opts = [Windows.Data.Pdf.PdfPageRenderOptions]::new()
$opts.DestinationWidth  = [uint32][math]::Round($size.Width  / 96.0 * $Dpi)
$opts.DestinationHeight = [uint32][math]::Round($size.Height / 96.0 * $Dpi)

# 5) RenderToStreamAsync（IAsyncAction → 非泛型 AsTask）→ DataReader → 写文件
# ... 见 3.1 实测骨架；Dispose 前先判 [System.IDisposable]（PdfPage 无 Close）
Write-Output ('OK_BYTES=' + $fi.Length)
exit 0
```

约束：**整段纯 ASCII**（注释也写英文），文件末尾无 BOM；单测断言 `Buffer.byteLength(WINRT_PDF_PS1) === WINRT_PDF_PS1.length` 且 `/^[\x09\x0a\x0d\x20-\x7e]*$/.test(WINRT_PDF_PS1)`。

### 3.4 `src/documents/pdf-raster.ts` 改动

```ts
/** 实际生效的渲染器标识（并入既有 string 联合，便于调用方与日志区分） */
export type RasterizerId = 'custom' | 'winrt' | 'pdftoppm' | 'mutool' | 'gs';

/** ocr.pdfRasterEngine 取值 */
export type PdfRasterEngine = 'auto' | 'winrt' | 'external';

export interface RasterizeOptions {
  timeoutMs?: number;
  customTemplate?: string;
  signal?: AbortSignal;
  /** 引擎策略，默认 'auto'（D6） */
  engine?: PdfRasterEngine;
}
```

- `pdfRasterizerAvailable(customTemplate?, engine?)`：`engine === 'external'` 时不算 winrt；`auto` 时 winrt 可用即返回 `true`（**不再 spawn 任何外部命令**，Windows 上是纯 `existsSync`）。
- `RasterizeResult.tool` 增加 `'winrt'`。
- `RASTERIZER_HINT` 改写为分平台文案：

  > PDF 扫描页需要光栅化能力：Windows 上通常由系统内置 PDF 渲染器提供（若被裁剪或已用 `ocr.pdfRasterEngine=external` 关闭，可安装 poppler（pdftoppm）、MuPDF（mutool）或 Ghostscript（gs））；其他平台请安装上述任一工具，或配置 `ocr.pdfRasterizer` 自定义命令模板（占位符 `{input} {page} {page0} {output}`）。

- 探测缓存增加 winrt 条目（通过 `winrtPdfLikelyAvailable()`，走同一 `probeCache`，`resetRasterizerProbeCache()` 一并清空）。

### 3.5 配置项 `ocr.pdfRasterEngine`

`src/config/schema.ts` 的 `OcrConfig` 增加：

```ts
/** PDF 光栅化引擎策略（D6）：auto=自定义模板→内建→外部工具；winrt=仅内建；external=仅外部工具 */
```

### 3.6 错误与降级矩阵

| 场景 | 行为 | 用户可见文案 |
| --- | --- | --- |
| 非 Windows | 不选 winrt，走外部工具；全无则 `RASTERIZER_HINT` | 与当前版本一致 |
| Windows 但 `powershell.exe` 缺失 | 不选 winrt（`existsSync` 判定） | 同上 |
| winrt 渲染 exit 2（组件裁剪） | `auto`：warning + 整体切外部工具；`winrt`：warning + HINT | 「内建 PDF 渲染不可用（…），已回落到外部工具」 |
| winrt 渲染 exit 3（该页坏） | 该页 warning，继续下一页 | 「第 N 页渲染失败（内建渲染器返回失败）」 |
| winrt 超时 | 该页 warning，继续下一页 | 「第 N 页渲染失败（内建渲染器超时）」 |
| 输出 > 12MB | 丢弃该页 + warning | 沿用既有文案 |
| 全部页失败 | 返回 `pages: []`，调用方保持原 `scanned` 错误 | 既有文案 + 首条 warning |

**与方案的偏差（3 处）**

1. 单测文件由计划的 3 个合并为 2 个：`tests/pdf-raster-winrt.test.ts` 与 `tests/powershell-util.test.ts` 合并为 `tests/pdf-raster-winrt-script.test.ts`（PowerShell 运行时当前只服务于 winrt 脚本落盘，拆开会产生同一批重复断言）；`tests/pdf-raster.test.ts` 的探测/回落断言并入新文件 `tests/pdf-raster-fallback.test.ts`，不改动既有 PASS 用例。
2. 选型记录：`@hyzyla/pdfium` 要求 Node ≥ 22，本项目 `engines` 为 ≥ 20.10，故不采用，改走 WinRT（零 npm 依赖）。
3. `PdfPage.Size` 单位在实现阶段核对为 **96 DPI 的 DIP**（不是 pt），渲染尺寸 = `round(Size / 96 * dpi)`；脚本注释里显式标注 `DIP (96/inch)`，避免后人按 pt 误改。

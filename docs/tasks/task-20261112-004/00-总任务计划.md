## 一、需求背景

用户上传了一份扫描件 PDF（`20261112-195345-7.2024年国网江苏电力-平台域-大模型智能体应用管理及服务能力建设-开发实施项目-部署方案评审意见.pdf`，实测 **1 页**、MediaBox A4），要求 `fileRead` 直接读出文字。链路走到的位置是：

1. `src/documents/pdf.ts` 自研零依赖 PDF 解析器扫内容流 → 无文本层（扫描件）；
2. 命中「无文本层」分支 → `rasterizeForOcr()` → `src/documents/pdf-raster.ts` 的 `rasterizePdfPages()`；
3. `rasterizePdfPages()` **只认外部工具**（pdftoppm → mutool → gs）与自定义模板，三者都没装 → 返回空数组；
4. `fileRead` 抛「该 PDF 没有可提取的文本层（可能是扫描件）」。

而这条链路上还有第二个、方向相反的缺陷：

5. 即便扫描页成功渲成图片，`src/documents/images.ts` 的 `ocrDocumentImages()` **直接调 `runOcr()`**——全程没有任何视觉模型调用；
6. 与之对照，`analyzeImage` 走的是 `src/tools/vision/ocr-fallback.ts`：**视觉优先 → 本地 OCR 兜底**。

即：同一份代码里，独立图片走「视觉→OCR」，而文档内图片（含 PDF 扫描页）走「只有 OCR」。用户明确期望的是前者。

## 三、关键技术结论（实测，2026-11-12）

### 3.1 渲染后端选型实测

样本：上述 1 页扫描件 PDF，A4，含中文路径与中文文件名。

| 指标 | A. `Windows.Data.Pdf`（WinRT） | B. `@hyzyla/pdfium` 3.0（PDFium WASM） |
| --- | --- | --- |
| 新增 npm 依赖 | **0** | 1（含 5.2MB 磁盘 wasm / 6.9MB 内联 base64 双入口） |
| Node 版本要求 | 无 | **≥22**（项目 `engines` 为 `>=20.10`） |
| SEA 单文件打包 | ✅ 无影响（子进程 + 系统 powershell） | ⚠️ 需把 wasm 资源一并处理 |
| 加载耗时 | 50ms（含进程启动 ~84ms） | 24ms（wasm init 30ms） |
| 渲染耗时 | 186ms | 119ms |
| 端到端（单页） | **263ms** | 153ms |
| 150 DPI 输出 | 1235×1760，PNG 944KB | 1233×1758，PNG 237KB |
| 跨平台 | ❌ Windows only | ✅ |
| 许可 | 随系统（BSD 系组件） | MIT + PDFium BSD-3 |
| OCR 结果 | 完整读出全文（18 行） | 完整读出全文（17 行，尾部少一行） |

**结论**：A 在「零依赖 / 不动 engines / 打包无风险」三项上是压倒性的，代价是仅 Windows + 慢 110ms、PNG 体积大 4 倍（仍远低于 12MB 上限）。项目在 20261112-002 已确立「**Windows 为一等公民，其他平台行为等同当前版本**」的平台策略，A 与之一致。

### 3.2 已踩实的实现坑（必须写进代码注释）

| # | 坑 | 现象 | 正确做法 |
| --- | --- | --- | --- |
| 1 | `PdfPage.Size` 单位是 **DIP（96/英寸）** 不是 pt（72/英寸） | 按 `/72*DPI` 算出 1646×2346，比正确值大 1.33 倍，PNG 1.57MB | `DestinationWidth = Size.Width / 96 * DPI` |
| 2 | `PdfPage` **没有 `Close()` 方法** | 调 `$pg.Close()` 抛 `MethodNotFound`，中断整个脚本 | `$pg -is [System.IDisposable]` 时才 `Dispose()` |
| 3 | `IAsyncAction` 用泛型 `AsTask<T>` 无法 await | 在 PS 5.1 里轮询 `.Status` 恒为空、`GetResults()` 报错 | 从 `[System.WindowsRuntimeSystemExtensions]` 反射取**非泛型** `AsTask(IAsyncAction)` 重载 |
| 4 | WinRT 类型必须**程序集限定**才能 `[type]::GetType` | 直接写 `[Windows.Data.Pdf.PdfDocument]::LoadFromFileAsync` 在 PS 5.1 类型解析器下不可靠 | 逐个 `[type]::GetType('Windows.X.Y, Windows.X, ContentType=WindowsRuntime')` 预热 |
| 5 | 脚本编码 | 含中文的 .ps1 在 GBK 代码页机器上被按本地码页解读 | 脚本内容**纯 ASCII 无 BOM**（20261112-002 已确立的范式） |
| 6 | 中文路径 | `-Path` 对含中文/空格路径的通配展开有风险 | 一律 `-LiteralPath`，且 `Resolve-Path -LiteralPath` 先归一 |

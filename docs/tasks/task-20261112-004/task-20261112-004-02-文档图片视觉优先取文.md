## 一、任务目标需求

### 1.1 背景（痛点）

框架里「图片取文」有两条路，方向恰好相反：

| 入口 | 现状链路 | 语义 |
| --- | --- | --- |
| `analyzeImage`（独立图片） | `chatVision` → 失败/未启用 → `runOcrFallback` → 本地 OCR | ✅ **视觉优先 → OCR 兜底** |
| `fileRead`（文档内图片：PDF 扫描页、docx/pptx/xlsx 内嵌图） | `ocrDocumentImages()` → 直接 `runOcr()` | ❌ **只有 OCR，无任何视觉调用** |

用户期望的是前者。而且文档内图片恰恰是**最需要视觉**的场景：

- 扫描件 PDF 的页图是「排版 + 印章 + 手写签名 + 表格」的混合体，本地 OCR 只给出一串行文本，丢掉了「哪一栏是哪一栏」；
- PPT 转出来的图、Excel 里的图表截图，OCR 只能读到坐标轴数字，读不出「趋势」；
- 用户的原话就是「视觉模型优先，未启用或失败才降级 OCR」。

技术上这不需要新能力——`chatVision`、`visionCache`、`visionStats`、`runOcrFallback` 全都现成，缺的是**在文档图片这条路上把顺序接对**。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
| --- | --- | --- |
| 视觉调用 | [`src/tools/vision/`](file:///D:/trae_workspace/loop-agent-command/src/tools/vision) 有 `chatVision`、`visionCache`（含 `ocr` 通道隔离）、`visionStats` | ✅ 直接复用 |
| 视觉→OCR 降级语义 | [`ocr-fallback.ts`](file:///D:/trae_workspace/loop-agent-command/src/tools/vision/ocr-fallback.ts)：`runOcrFallback()` + `composeFallbackError()` + `summarizeVisionError()` + 能力边界说明 | ✅ 语义与文案直接对齐 |
| 文档图片预算 | [`images.ts`](file:///D:/trae_workspace/loop-agent-command/src/documents/images.ts)：张数 `doc.maxImages`、总预算 `doc.timeBudgetMs`、单图 `maxCharsPerImage` | ✅ 沿用，视觉调用并入同一预算 |
| 文档图片调用方 | `src/tools/fileRead.ts` → `ocrDocumentImages(images, cfg)` | ⚠️ 需接线注入视觉能力 |
| 分层 | `tools/* → documents/* → ocr/*` 单向；`tools/vision` 在 tools 层 | ⚠️ documents **不能**直接 import tools/vision（反向依赖） |
| 视觉大小上限 | `vision.maxImageBytes`（默认 10MB）、`vision.timeoutMs`（默认 20s） | ✅ 渲染页 944KB 远低于上限 |

### 1.3 任务目标

1. 文档内图片取文改为 **视觉优先 → 本地 OCR 兜底**，与 `analyzeImage` 语义一致。
2. 保持 documents 层的**单向依赖**：视觉能力由 `fileRead` 以函数注入，documents 层只定义接口。
3. 每个图片块**显式标注来源**（视觉 / OCR 降级 / 失败），绝不静默降级；OCR 降级时附能力边界说明。
4. 视觉调用并入既有三重预算（张数、总时间、单图字符数），并新增 `ocr.doc.preferVision` 开关（默认 `true`，但受 `vision.enabled` 双重约束）。
5. 视觉失败**不吞掉**：降级 OCR 时把视觉错误摘要写进块内，OCR 也失败时两条信息都保留。

### 1.4 设计约束

- **不改 `analyzeImage` 既有链路**（它已正确，改动会牵动 20261112-002 的 65+ 例单测与缓存口径）。
- **非 Windows 零影响不变**：OCR 引擎不可用的平台（非 Windows 且未配 `ocr.http`），视觉优先**照常生效**——此时视觉是唯一可用路径，恰好弥补了原来「整块降级不产出」的缺陷。
- **不外发**：`vision.enabled === false`（默认）时一律不调视觉，行为等同当前版本。
- 不改变块格式的机器可读性：`[图片 N（标签）：…]` … `[/图片 N]` 的配对结构不变。
- 不引入图片压缩/缩放（视觉模型收到的是原始页图，见 D9）。

## 二、方案设计

### 2.1 总体思路

```
src/tools/fileRead.ts
   │  const ocrCfg = resolveOcrConfig()
   │  const describe = buildVisionDescriber()      ← 新增：包装 chatVision + 缓存 + 统计（D2）
   ▼
src/documents/images.ts
   readDocumentImages(images, ocrCfg, { describe, preferVision })   ← 新增（D1）
   │
   └─ 逐图（同一套张数/时间预算，D4）
        ├─ 视觉可用（preferVision && vision.enabled）→ describe(img)
        │     ├─ 成功 → 块头「视觉描述」
        │     └─ 失败 → 摘要错误 → 降级 OCR（D5）
        └─ 视觉不可用 / 已降级 → runOcr(img.data)
              ├─ 成功 → 块头「OCR 文本」（降级时附「[视觉不可用：…；已降级为本地 OCR]」+ 能力边界）
              └─ 失败 → 块头「取文失败」，两条原因都写
```

### 2.2 关键设计决策

#### D1 用**回调注入**接视觉能力，不让 documents 层 import tools/vision

```ts
// src/documents/images.ts
/** 单图视觉取文能力（由 tools 层注入；抛错即视为该图视觉失败） */
export type ImageDescriber = (img: DocumentImage) => Promise<{ text: string; model: string }>;

export interface ReadDocumentImagesDeps {
  /** 缺省则不启用视觉，行为等同纯 OCR */
  describe?: ImageDescriber;
  /** 视觉未启用/不可用的原因（用于块内标注，如「视觉功能未启用」） */
  visionUnavailableReason?: string;
}
```

理由：`documents` 层被 `tools` 层依赖，反向 import 会形成环（`tools/vision/ocr-fallback.ts` 已 import `ocr/index.js`，再让 documents import tools/vision 会踩到 `tools/vision/cache` 与 `config` 的加载顺序）。回调注入同时让 documents 层零配置依赖、可单测（传入 `describe: async () => ({ text:'x', model:'m' })` 即可覆盖全部分支）。

否决替代方案：把预算逻辑从 `images.ts` 搬到 `fileRead.ts`（重复 60 行预算代码，且块格式与告警文案要跨文件对齐，比注入更难维护）。

#### D2 视觉实现放在 `src/tools/vision/describe-document-image.ts`（新文件）

职责：把「文档内图片」适配成视觉调用，并复用既有缓存与统计。

```ts
export function buildDocumentImageDescriber(opts: {
  vision: VisionConfig;
  /** 主模型回退链，与 analyzeImage 一致 */
  fallback: { baseUrl: string; apiKey: string; model: string };
}): ImageDescriber | undefined;
```

- `vision.enabled !== true` → 返回 `undefined`（调用方据此走纯 OCR 并标注「视觉功能未启用」）。
- 内部调既有 `chatVision`（`src/tools/vision/*` 已有实现），`kind` 用**新增的 `describe_doc_image`**，避免与 `analyzeImage` 的 `describe` 缓存串味。
- 缓存：走 `visionCache`（`modelKey` = 实际视觉模型名，`kind='describe_doc_image'`，`params=[]`，通道 = 视觉默认通道），命中即返回；这与 OCR 降级走的 `local-ocr` + `'ocr'` 通道天然隔离（沿用 20261112-002 D2 的通道隔离原则）。
- 统计：`visionStats.recordDescribe()`（新增计数项，供 `/status` 类观察点复用）。
- 单图超时：`min(vision.timeoutMs, 剩余总预算)`。
- 大小门禁：`img.data.length > vision.maxImageBytes` → 直接抛错（由上层降级 OCR），不浪费一次请求。

#### D3 「视觉优先」的双重开关，默认开启但默认不生效

| 配置 | 默认 | 作用 |
| --- | --- | --- |
| `vision.enabled` | `false` | 总闸：关闭时 `buildDocumentImageDescriber()` 返回 `undefined`，完全不走视觉 |
| `ocr.doc.preferVision` | **`true`** | 分闸：只想用本地 OCR 读文档图时一键关闭，回落到当前行为 |

即：用户装了视觉并 `vision.enabled=true` 后，文档图**自动**变为视觉优先（符合用户期望）；内网/隐私场景保持 `vision.enabled=false` 则行为逐字节不变。

#### D4 视觉调用并入既有三重预算，不新增预算项

- 张数：`ocr.doc.maxImages` 仍是硬上限（视觉更贵，绝不能绕过它）。
- 总时间：`ocr.doc.timeBudgetMs` 覆盖**视觉 + OCR 合计**耗时；每图开始前检查剩余预算，视觉超时取 `min(vision.timeoutMs, remaining)`。
- 字符：视觉输出同样按 `ocr.doc.maxCharsPerImage` 截断（沿用 `truncateOcrText`），保证「图片块不撑爆上下文」的既有承诺不被视觉绕过。

> 说明：字符上限配置名带 `maxCharsPerImage`，语义为「单图取文上限」，视觉走同一口径；不改名（改名会波及配置文档与既有测试），在注释与文档中明确其跨视觉/OCR 通用。

#### D5 降级与失败矩阵

| 视觉 | OCR | 块内容 | 计数 |
| --- | --- | --- | --- |
| 成功 | — | `[图片 N（标签）：视觉描述]` + 正文 + `[/图片 N]` | `visionDone++` |
| 失败（非未启用） | 成功 | `[视觉不可用：<摘要>；已降级为本地 OCR（<引擎>）]` + OCR 正文 + 能力边界说明 | `ocrDone++`、`degraded++` |
| 未启用（`vision.enabled=false` 或 `preferVision=false`） | 成功 | `[图片 N（标签）：OCR 文本]` + 正文（**不加降级头**，因为本来就没打算用视觉） | `ocrDone++` |
| 失败 | 失败 | `[图片 N（标签）：取文失败（视觉：<摘要>；OCR：<原因>）]` | `failed++` |
| 未启用 | 失败 | 沿用当前文案 `[图片 N（标签）：OCR 失败（<code>）：<msg>]` | `failed++` |
| 成功 | — （跳过 OCR） | 不调用 OCR（省时间与本地资源） | — |

「未启用」与「失败」必须区分：前者是用户的主动选择，不该在正文里反复出现「视觉不可用」；后者是能力缺口，必须显式标注（这是 20261112-002 已确立的「绝不静默降级」原则）。

#### D6 引擎不可用（WinRT OCR 缺失）时的行为改善

当前 `ocrDocumentImages()` 在「第一张图就引擎不可用」时会**整块丢弃**（`blocks.length = 0`）。改为视觉优先后，语义应为：

- 视觉可用 → 全部图走视觉，OCR 缺失完全不影响 → **这次改动顺带修掉了「非 Windows 平台文档图片完全没有产出」的缺陷**；
- 视觉也不可用 → 维持整块降级（返回空文本 + 一条 warning），行为与当前一致。

这是本任务的附带收益，需在验收清单单独验证（非 Windows 或禁用 OCR 引擎时，文档图片块仍产出视觉描述）。

#### D7 块头文案：`=== 文档内图片 OCR ===` → `=== 文档内图片文本 ===`

原因：块内可能全是视觉描述，标题写「OCR」会误导模型与用户。

- 中英双语文档同步（`built-in-tools.md` 的 `fileRead` 段）。
- **既有测试断言需要同步更新**（这是有意的文案变更，不是回归）；`grep '文档内图片 OCR'` 全量核对命中点后一次改净。

#### D8 `ocrDocumentImages()` 保留不动

新增 `readDocumentImages()` 承载新语义，`ocrDocumentImages()` 保留为「纯 OCR」内部实现（被 `readDocumentImages` 在无 `describe` 时直接委托），**既有 20 例 `ocrDocumentImages` 单测零改动**，降低回归面。

#### D9 不做的（本任务边界）

- 不做图片压缩/降采样/DPI 调整（`944KB → base64 1.26MB` 的阶段会显著增加视觉 token；若现场触发模型拒绝，走 D5 的降级路径，不在此任务引入压缩策略）。
- 不改 `analyzeImage`、不改 `runOcrFallback` 的既有语义。
- 不做视觉结果的表格结构化/坐标提取。
- 不做多图批量合并为一次视觉请求（当前逐图调用，便于预算与失败隔离）。
- 不为视觉结果单独设缓存开关（沿用 `vision.cacheEnabled`）。

## 三、任务详细设计

### 3.1 `src/documents/images.ts` 改动

新增（不动 `ocrDocumentImages`）：

```ts
/** 单图视觉取文能力（tools 层注入） */
export type ImageDescriber = (img: DocumentImage) => Promise<{ text: string; model: string }>;

export interface ReadDocumentImagesDeps {
  describe?: ImageDescriber;
  /** 视觉不可用的人话原因（仅用于日志/统计，不写进正常块） */
  visionUnavailableReason?: string;
}

export interface DocImageReadOutcome extends DocImageOcrOutcome {
  /** 视觉成功的图片数（新增） */
  visionDone: number;
  /** 视觉失败后由 OCR 兜底的图片数（新增） */
  degraded: number;
}

export async function readDocumentImages(
  images: DocumentImage[],
  cfg: OcrConfig,
  deps?: ReadDocumentImagesDeps,
): Promise<DocImageReadOutcome>;
```

- 无 `deps.describe` 或 `cfg.doc.preferVision === false` → 直接 `return ocrDocumentImages(images, cfg)` 并补 `visionDone: 0, degraded: 0`（**纯委托，零行为变化**）。
- 有 `describe` → 走视觉优先循环：预算检查与 `ocrDocumentImages` 同口径（抽出内部 `checkBudget()` 复用，避免两处口径漂移）。
- 视觉成功路径不调用 `runOcr`，也不消耗 OCR 引擎。
- 新增 `CAPABILITY_NOTE` 复用：`src/tools/vision/ocr-fallback.ts` 的能力边界说明常量**需导出**（目前是私有 `const`），由 documents 层 import？——不行（反向依赖）。改为：documents 层持有自己的同文案常量（`images.ts` 内），并在 `tests` 中断言两者文案一致（防止漂移）。

### 3.2 新增 `src/tools/vision/describe-document-image.ts`

```ts
import type { DocumentImage } from '../../documents/images.js';

export interface VisionRuntime {
  vision: VisionConfig;
  fallback: { baseUrl: string; apiKey: string; model: string };
}

/** 构建文档图片视觉取文器；vision 未启用时返回 undefined */
export function buildDocumentImageDescriber(rt: VisionRuntime): ImageDescriber | undefined;
```

实现要点：
1. `rt.vision.enabled !== true` → `return undefined`。
2. `img.data.length > rt.vision.maxImageBytes` → `throw new Error('图片超过视觉大小上限 …')`。
3. 组 `dataUri`（PNG/JPEG 按 magic 推断 MIME，复用 `ocr` 侧已有的 sniff 逻辑或直接在 documents 层算好传入）。
4. 缓存 key：`visionCache.buildKey(实际视觉模型名, 'describe_doc_image', [], 内容哈希, 'vision')`；`img.data` 无路径，故用 `crypto.createHash('sha256').update(img.data).digest('hex').slice(0,32)` 作 source。
5. 提示词（固定，纯中文，要求：读出正文文字、保留阅读顺序、指出表格/印章/签名/勾选项等结构信息、不臆测看不清的内容）。
6. `visionStats.recordDescribe()`；超时 → 抛错（由上层降级）。

### 3.3 `src/tools/fileRead.ts` 改动

当前（约）：
```ts
const outcome = await ocrDocumentImages(images, ocrCfg);
```
改为：
```ts
const visionRt = resolveVisionRuntime(cfg);                 // 既有配置解析
const describe = buildDocumentImageDescriber(visionRt);      // 未启用则 undefined
const outcome = await readDocumentImages(images, ocrCfg, {
  describe,
  visionUnavailableReason: describe ? undefined : '视觉功能未启用',
});
```
- 告警文案基于 `outcome.visionDone` 增加一条：`文档内共 N 张图片，已由视觉模型描述 X 张、本地 OCR 识别 Y 张（其中 Z 张为视觉失败降级）`。
- 顶部 `import` 调整（新增 `readDocumentImages`、`buildDocumentImageDescriber`）。

### 3.4 配置项 `ocr.doc.preferVision`

`src/config/schema.ts` 的 `OcrConfig.doc` 增加：

```ts
/** 文档内图片是否视觉优先（默认 true；需 vision.enabled=true 才实际生效） */
preferVision: boolean;
```

默认 `true`；反序列化时非布尔值回落 `true`。

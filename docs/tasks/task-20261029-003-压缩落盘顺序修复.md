## 一、任务目标需求

### 1.1 背景（痛点）

用户在 Agent 回复「确认『按推荐项来』（或指出要改的 D 点）我就开始 P0」之后追问「按推荐来」，该消息在界面上却被排到了一整轮实施过程（98 条工具调用）**之后**，看起来像是「用户消息跑到了它引发的回答后面」。同类问题当日第二次出现（用户原话「又出现用户消息位置错误的问题」），前一次表现为「D4选B，其他按你推荐的来」被排到 236 条之后。

这不仅是观感问题：会话历史是 LLM 上下文与用户回溯的唯一依据，顺序错乱会让「问题—回答」的因果链在重载后断裂，长任务会话几乎必然触发（工具调用越多越容易超预算）。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
|---|---|---|
| 压缩计划应知道「哪些消息被丢弃、哪些保留、保留段在原始轨迹中的位置」 | `src/memory/working.ts` `planCompaction()` 返回 `droppable` / `kept` / `droppedCount` / `withinTurnTrim`，但**不返回 kept 在轨迹中的下标** | 缺下标，导致下游只能按「先 dropped 后 kept」拼接 |
| 单轮长任务应能压缩 | `planCompaction()` 的 `withinTurnTrim`：`droppedCount===0` 且 token 超 `messageTokensBudget` 时按 token 从尾部截尾 | 能力已有（正是本 bug 的触发路径） |
| 当前轮原始 user 不应被截尾丢掉 | 同文件 260-278 行「任务锚点 pin」：把最后一条 user 从 `droppable` 摘出、`kept = [anchor, ...tail]` | 意图正确，但**只摘走 anchor 自身**，anchor 与其后 tail 之间的消息留在 droppable |
| 落盘时应保持原始轨迹顺序 | `src/session/store.ts` `updateSession()` 压缩分支 `rebuilt = [...compacted, summaryMsg, ...recent]` | **缺陷所在**：按「归档段→摘要→保留段」布局，anchor 被钉进保留段后即排到本轮归档消息之后 |
| 恢复上下文应按折叠标记过滤 | `SessionStore.getRestoreMessages()` 只取 `is_compact !== true` | 正确，且本修复无需改动 |
| 展示应按磁盘顺序平铺 | WebUI `chat-stream.ts` / CLI 均按 `messages` 数组顺序渲染 | 正确，故修复点应在落盘顺序而非渲染层 |

### 1.3 任务目标

压缩落盘后，`messages` 的**磁盘数组顺序**必须等于本轮 `transcript` 的原始轨迹顺序；`is_compact` 折叠标记的语义与 `getRestoreMessages()` 恢复出的上下文集合**逐条不变**。即：只修顺序，不改压缩省 token 的效果，不丢任何消息。

### 1.4 设计约束

- 零新依赖；只改 `src/session/store.ts`（压缩分支）与新增单测。
- `buildCompactedView()`（给 LLM 的上下文视图）保持 `[system, summary, anchor, ...tail]` 不变——该顺序对「锚点优先」语义是正确的，且被 pin 的 anchor 本就是为剩余迭代保留的精确约束。
- 已有 4000 条封顶（`capStoredMessages`）只在未压缩分支生效，本任务不改。
- 落盘条数必须与修复前一致（集合不变），避免触发 `messageCount`、`archivedCount` 等统计口径漂移。

## 二、方案设计

### 2.1 总体思路

```
planCompaction()                        updateSession()（压缩分支）
  droppable = t[1..99]  ────┐             keptArchived（上轮旧归档）
  kept = [t[0], t[100..102]] │                    │
  （anchor = t[0] 被 pin）    │                    ▼
                             └────►  ┌──────────────────────────────┐
                                     │ rebuilt = [                  │
         transcript 原始顺序 ───────► │   ...keptArchived,           │  ← 旧归档（D2）
         t[0], t[1..99], t[100..102] │   summaryMsg,                │  ← 摘要占位（is_show=false 不渲染）
                                     │   ...ordered(dropped∪recent) │  ← 【修复】按 transcript 下标升序
                                     │ ]                            │
                                     └──────────────────────────────┘
                                                  │
                                    is_compact: recent=false / dropped=true（语义不变，只改顺序）
                                                  ▼
                                     getRestoreMessages() → [summary, t[0], t[100..102]]（集合不变）
```

修复前：`[...compacted(t[1..99]), summary, t[0], t[100..102]]` → t[0] 排在其引发的 99 条消息之后。
修复后：`[...keptArchived, summary, t[0], t[1..99], t[100..102]]` → 顺序正确。

### 2.2 关键设计决策

**D1：在落盘层（`updateSession`）修，不在压缩层扩大保留范围。**
否决「让 `planCompaction` 把 anchor→tail 之间的消息一并保留」——那样单轮长任务的压缩基本失效（等于整轮都留在 recent），token 预算形同虚设，且违背「压缩是为了省上下文」的初衷。落盘层修复不动压缩语义，磁盘顺序与 LLM 上下文视图各取所需。

**D2：压缩分支把 dropped 与 recent 按 transcript 下标升序合并；summary 固定置于旧归档之后、本轮消息之前。**
以 `keptIdx`（`locateInTranscript` 返回且保证递增）构造 `keptSet`，遍历 transcript 全量，命中 keptSet 者 `is_compact=false`、否则 `true`——一次遍历同时完成「重排」与「打标」。summary 位置沿用原相对语义（旧归档之后、本轮轨迹之前），因其 `is_show=false` 不参与展示，且恢复上下文时作为首条最自然。

**D3：`buildCompactedView()` 不同步调整。**
它产出的是给 LLM 的上下文视图，`[system, summary, anchor, ...tail]` 中 anchor 紧跟 summary 是刻意的（锚点即当前任务约束，应最先被读到）。若为迁就落盘顺序而改它，会降低剩余迭代的任务一致性。

**D4：存量已错乱数据提供检测脚本，但需手动执行，不自动改写；且脚本只做「可确定」的修复。**
诚实说明：`transcript` 从未落盘，多轮压缩反复重建后历史顺序**无法无损还原**。脚本默认只输出诊断报告（哪些会话、哪些 user 消息位置可疑），`--fix` 仅在能唯一确定时重排，不确定项跳过并列出。不自动改用户数据。

**D5：必须补回归单测，锁定「单轮内 token 截尾 + 锚点 pin」场景。**
构造 1 条 user + 大量 tool 消息 + token 超预算的场景，断言压缩落盘后该 user 仍排在其引发的消息之前，且 `is_compact` 标记与恢复集合符合预期。

## 三、任务详细设计

### 3.1 `src/session/store.ts` — `updateSession()` 压缩分支

改动点（现有 457-481 行的 `if (transcript && keptIdx && prevCovered)` 分支）：

```ts
if (transcript && keptIdx && prevCovered) {
  const keptSet = new Set(keptIdx);
  const dropped = transcript.filter((_, idx) => !keptSet.has(idx));
  const replayed = countReplayedArchive(prevArchived, dropped);
  const keptArchived = prevArchived.slice(0, prevArchived.length - replayed);
  // 【修复】按 transcript 原始下标升序重建本轮轨迹：归档(dropped) 与保留(recent) 合并后排序，
  // 保证磁盘顺序 = 原始轨迹顺序。压缩语义只由 is_compact 标记表达，与顺序无关。
  const ordered = transcript.map((m, idx) =>
    toStoredMessage(m, { isCompact: !keptSet.has(idx) }),
  );
  rebuilt = [...keptArchived, summaryMsg, ...ordered];
}
```

- 集合不变：`ordered` 条数 = `dropped.length + keptIdx.length` = 修复前 `compacted(去掉 keptArchived) + recent` 条数。
- `keptArchived` 与 `summaryMsg` 位置不变。
- 原 `log` 里的 `compacted` / `recent` 计数改为由 `ordered` 派生，日志口径不变。

### 3.2 边界与错误处理

| 情形 | 处理 |
|---|---|
| `transcript` 为空 / `keptIdx` 为 null / `prevCovered` 为 false | 不进入本分支，回退 legacy 逻辑（行为不变） |
| legacy 回退分支（`if (!rebuilt)`） | 无 transcript 下标信息，**无法**重排；保持现有「先 compacted 后 recent」并在注释中标注局限，不作为本任务修复目标 |
| `transcript` 中含 system / 摘要占位 | 已在上游 `filter` 排除（419-421、446-448 行） |
| 同一 run 内多次压缩快照 | `countReplayedArchive` 逻辑不变，`ordered` 每次全量重建，天然幂等 |

### 3.3 演进项（本任务不做）

- legacy 回退分支的顺序修正（需引入「kept 起源下标」推断）。
- 把 `keptIdx` 从 `store.ts` 上移到 `planCompaction` 返回值（更彻底，但要改 CompactionPlan 契约与调用方）。
- 会话文件的顺序一致性校验（落盘前断言「任一轮首条 user 先于其引发的 assistant」）。

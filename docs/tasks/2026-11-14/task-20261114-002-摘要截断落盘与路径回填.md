## 一、任务目标需求

### 1.1 背景（痛点）

L1 压缩的摘要长度治理目前是「三重防线只做了两重半」：

| 防线 | 现状 | 问题 |
|---|---|---|
| ① 提示词约束 | `SUMMARY_MAX_CHARS = 800` 写进 `FLUSH_SYSTEM_PROMPT` | 有效，但**模型不一定遵守**，长会话中实测会超写 |
| ② 允许小幅超写 | `SUMMARY_TRUNCATE_MAX_CHARS = ceil(800 × 1.2) = 960` | 存在，但**用户期望是 10%（880）**，与实现对不上（D1） |
| ③ 物理截断 | `working.ts:247` 直接 `slice(0, 960)` | **超出部分静默丢弃**：不落盘、无提示，模型与用户都不知道曾有过完整摘要 |

第③重是**有损**的：一旦模型写出 1500 字摘要，被砍掉的 540 字永久消失，且没有任何回捞线索。
用户在长任务中依赖摘要承载「用户偏好 / 已确认决策 / 未完成任务」，这部分丢失会直接导致后续推理漂移
（外部佐证见 2.3）。

同时明确一点：**「截断不影响用户当前轮原文」这条已经成立**——`working.ts:247` 先 `splitAnchorSection`
剥掉 `\n[当前问题] ` 段、只截 LLM 摘要主体，再由 `composeSummaryBody` 拼回原文段，原文段不受 960 影响。
本任务要补的是**摘要主体**被砍掉的那部分。

### 1.3 任务目标

1. **截断内容不丢**：摘要主体被 `SUMMARY_TRUNCATE_MAX_CHARS` 物理截断时，把**截断前的完整摘要主体**写入临时文件。
2. **路径回填进摘要**：把临时文件绝对路径作为独立段落写进摘要占位，与 `\n[当前问题] ` 段并列、互不干扰。
3. **幂等**：重复压缩时路径段只保留最新一份，不叠加（对齐 20261113-008 D5 的既有幂等口径）。
4. **不诱导无谓读回**：回填文案声明「仅在需要核对细节时读取」，避免模型每轮都 fileRead 一遍。
5. **预算自洽**：路径段的 token 计入 `SUMMARY_PLACEHOLDER_RESERVE_TOKENS`，防止压缩后立刻二次触发（空转）。
6. **失败不阻断**：落盘失败静默降级为「仅截断提示、不写路径」，压缩主流程不受影响。

### 1.4 设计约束

- **零新依赖**：复用 `output-governor` 的 `buildTmpFilePath` / `pruneTmp`，只用 `node:fs`。
- **模块依赖方向不变**：`src/memory/*` 目前**不引用** `src/tools/*`。`output-governor` 只依赖 `node:*` + `user-home` + `debug`（无反向依赖），但跨层引用仍需评估（D5）。
- **跨平台**：路径分隔符、`~/.loop-agent/tmp/` 目录创建三平台一致。
- **存量兼容**：旧摘要无路径段时按「无路径」处理，不报错、不迁移磁盘数据。
- **不改用户可见行为**：WebUI 摘要卡片已于需求 20261113-005 移除，本段落天然仅模型可见，无前端改动。
- **不改变既有语义**：`SUMMARY_MAX_CHARS` 目标值、`FLUSH_SYSTEM_PROMPT` 的要点清单、`[当前问题]` 段的截断与去重口径一律不动。

## 二、方案设计

### 2.1 总体思路

```
preCompactionFlush() ──LLM──> summaryText（模型可能写 1500 字）
                                  │
                                  ▼
                    buildCompactedView()  ← 本次改动集中在这一层
                                  │
                    ┌─────────────┴──────────────┐
                    │ splitAnchorSection(summary)│  先剥 [当前问题] 段
                    └─────────────┬──────────────┘
                                  ▼
                    summaryBody（可能 > 960 字）
                                  │
                    ┌─────────────┴────────────────────────────┐
                    │ overflow = summaryBody.slice(960)        │  ★ 新增：探测溢出
                    │ if (overflow.length >= MIN_SPILL_CHARS)   │  ← D3 阈值
                    │   spillSummary({body, sessionId}) ────────┼──> ~/.loop-agent/tmp/<sess>/summary-xxx.txt（完整主体）
                    │      └─> path 或 undefined                │       └─ 沿用 7 天 TTL（D4）
                    └─────────────┬────────────────────────────┘
                                  ▼
                    summaryBody = summaryBody.slice(0, 960)     （原逻辑不变）
                    anchorText  = dedupeAnchorText(...)         （原逻辑不变）
                    pathSection = path ? composeSummaryPathSection(path, 溢出字数) : undefined   ★ 新增
                                  ▼
        占位 content = "[历史摘要] " + 摘要主体
                                    + "\n[当前问题] " + 原文段      （原有）
                                    + "\n[完整摘要] <绝对路径> …"    ★ 新增段
                                  ▼
                    SessionStore.updateSession() → kind='summary' 落盘
```

关键点：**探测溢出与落盘发生在截断之前**，而**拼接发生在截断之后**——这样「完整版落盘」与「上下文只留 960 字」两件事互不干扰，也不碰 `[当前问题]` 段。

### 2.2 关键设计决策

#### D1｜硬截断容忍度：保持 20%（960）还是改为 10%（880）　【**须用户拍板**】

用户表述为「允许超 10%」，但代码现状是 `ceil(800 × 1.2) = 960`（20%）。

- **方案 A（保持 20%，960）**：不动现有常量。理由：960 是 `SUMMARY_MAX_CHARS=800` 的上界宽容度，模型「小幅超写」20% 属常见；收紧到 880 会让更多正常摘要被判定溢出、进而频繁落盘 + 频繁回填路径，反而增加上下文噪音。
- **方案 B（改为 10%，880）**：`SUMMARY_TRUNCATE_MAX_CHARS = ceil(800 × 1.1) = 880`。贴合用户原话，但会改变既有单测断言（`tests/compaction-anchor-summary.test.ts:195-196` 明确断言 `Math.ceil(800 * 1.2)`），需同步改测试。

> 推荐 A，并**在回填文案与文档里如实写「上浮 20%」**，把口径对齐；若用户坚持 10%，则连带改测试断言与 `SUMMARY_PLACEHOLDER_RESERVE_TOKENS` 估算。

#### D2｜落盘范围：只写摘要主体，还是连原文段一起写　【**须用户拍板**】

- **方案 A（只写摘要主体，推荐）**：原文段（`\n[当前问题] `）本身**不参与截断**（20261113-008 D1 已保证），落盘它属冗余；且原文段可能含上传附件绝对路径等敏感信息，多写一份到 tmp 只是扩大暴露面。
- **方案 B（主体 + 原文段全写）**：文件成为「完整摘要快照」，语义最完整。代价是多存一份用户原文。

> 推荐 A。若用户希望临时文件就是「当时那份完整摘要」，选 B 也可实现（拼接后落盘，但上下文仍只注入截断版）。

#### D3｜溢出多少字才落盘　【推荐值，可调】

固定小阈值，避免「溢出 3 个字」也建文件造成 tmp 目录噪音：

- **推荐 `SUMMARY_SPILL_MIN_CHARS = 40`**：溢出 ≥ 40 字才落盘并回填路径；< 40 字只在摘要尾部追加一句「…（摘要已截断 N 字）」，不写文件。
- 理由：40 字以下的信息密度不足，读回成本高于收益；40 字以上通常意味着模型明显超写，内容值得保全。
- 备选：溢出 > 0 一律落盘（最保守，但 tmp 噪音大；可接受，只需把常量设 1）。

#### D4｜临时文件命名与清理口径　【推荐值】

- **命名**：沿用 `buildTmpFilePath(sessionId, 'summary', digest)` → `~/.loop-agent/tmp/<sessionId>/summary-<digest>-<ts>.txt`，与工具输出同目录、同命名结构，`pruneTmp` **零改动**即可覆盖（`output-governor.ts:452` 只处理 `.txt`，摘要文件同样是 `.txt`）。
- **清理**：沿用 `tmpTtlDays = 7` 天 + `tmpMaxTotalMb = 200` 总量上限。
- **被否决**：写到工作空间内（污染 git，且用户明确 tmp 不进工作空间）；写进会话 json（撑大落盘文件，且摘要消息已存在，会造成双份）。

#### D5｜落盘能力放哪一层：memory 直接引用 tools，还是注入回调　【**须用户拍板**】

`src/memory/*` 现状**不 import `src/tools/*`**（已核对）。两种做法：

- **方案 A（memory 直接 import `output-governor`）**：改动最小，`buildTmpFilePath`/`pruneTmp` 是纯函数、无状态、只依赖 `node:*`，无循环依赖风险（已核对 `src/tools/*` 不 import `src/memory/*`）。代价：打破「memory 不依赖 tools」的既有分层习惯。
- **方案 B（注入回调）**：`WorkingMemory` 构造时可注入 `spillSummary?: (body: string) => string | undefined`，由 `react-agent` 侧实现（它本就在 tools 邻域）。分层最干净，但要多穿一层参数，且 `buildCompactedView` 是**导出的纯函数**（单测直接调用），注入回调会污染其签名。

> 推荐 A：`output-governor` 是「基础设施」而非「业务工具」，`subagent-notice.ts` 已有跨层复用的先例（`src/api/subagent-notice.ts:10` 直接 import 它）。若用户更看重分层纯净度，选 B。

#### D6｜路径段的标记与幂等　【推荐值】

- 标记定为 `\n[完整摘要] `（带前置换行，与 `\n[当前问题] ` 同风格）。
- 段内容形如：
  ```
  [完整摘要] C:\Users\xxx\.loop-agent\tmp\sess_x\summary-abcdef-1763xxxxxx.txt（完整摘要 1523 字，此处仅保留前 960 字；仅在需要核对被省略的细节时才读取该文件，否则忽略本行）
  ```
- **幂等**：`splitAnchorSection` 同级新增 `splitPathSection`，拼装前先剥离旧的 `[完整摘要]` 段，保证重复压缩只留最新一份（复用 20261113-008 D5 的「先剥后拼」模式）。
- **被否决**：把路径写进摘要正文让它自然参与 LLM 合并（会被模型当成要点复述，产生幻觉式路径）；用 JSON 结构化字段（`toStoredMessage` 落盘会丢，且模型看不到）。

#### D7｜占位预算是否扩算　【推荐值：是】

`SUMMARY_PLACEHOLDER_RESERVE_TOKENS` 现为 `ceil((800+800)/4) = 400`，未含路径段。路径段约 120–180 字符 ≈ 30–45 token。

- **推荐**：新增常量 `SUMMARY_PATH_SECTION_MAX_CHARS = 200`，预算公式改为
  `ceil((SUMMARY_MAX_CHARS + ANCHOR_USER_MAX_CHARS + SUMMARY_PATH_SECTION_MAX_CHARS) / 4) = ceil(1800/4) = 450`。
- 理由：不扩算的话，压缩完成后占位实际占用会略超预留，极端情况下下一轮立刻二次触发压缩（既有注释 `summary-message.ts:33-35` 已记录过这个坑）。
- 代价：`keepBudget` 少 50 token，保留消息略少一点，可接受。

**已知坑（检索所得，实施时注意）**：
1. **回填路径本身会诱发读回**——必须写明「仅在需要核对细节时读取」，否则模型每轮都 `fileRead` 一次，反噬 token。
2. **临时文件被清理后路径失效**——7 天 TTL 到期后模型若仍尝试读取会拿到「文件不存在」，属可接受降级（文案用「仅在需要时」已弱化依赖）。
3. **不要把路径塞进 system prompt**——会导致 prompt 前缀缓存失效（上述第四篇明确提到 KV Cache 失效问题）。本方案注入在 user 角色的摘要占位里，前缀缓存影响与现状一致。

## 三、任务详细设计

### 3.1 `src/memory/summary-message.ts`（新增常量与函数）

```ts
/** 完整摘要临时文件路径段的字数上界（D7：用于 token 预算扩算） */
export const SUMMARY_PATH_SECTION_MAX_CHARS = 200;

/** 路径段分隔标记（D6，带前置换行，与 ANCHOR_SECTION_MARK 同风格） */
export const PATH_SECTION_MARK = '\n[完整摘要] ';

/** 溢出多少字才值得落盘（D3） */
export const SUMMARY_SPILL_MIN_CHARS = 40;

/** 占位 token 预留（D7：加入路径段上界） */
export const SUMMARY_PLACEHOLDER_RESERVE_TOKENS = Math.ceil(
  (SUMMARY_MAX_CHARS + ANCHOR_USER_MAX_CHARS + SUMMARY_PATH_SECTION_MAX_CHARS) / 4,
); // ceil(1800 / 4) = 450

/**
 * 构造路径段文本（不含分隔标记）。
 * @param path 临时文件绝对路径
 * @param fullChars 完整摘要字数
 * @param keptChars 上下文实际保留字数
 */
export function composeSummaryPathSection(
  path: string,
  fullChars: number,
  keptChars: number,
): string;

/** 从占位正文中剥离路径段（幂等，D6）。无该段时原样返回。 */
export function stripPathSection(body: string): string;

/** 切出路径段（用于诊断/单测）；无则返回 undefined */
export function splitPathSection(body: string): { body: string; path?: string };
```

> 注意：`composeSummaryBody` 的签名与行为**完全不变**，路径段在 `working.ts` 侧拼装，
> 避免影响 20261113-008 已固化的「先剥原文段再拼」幂等逻辑与既有 26 个单测。

### 3.2 `src/memory/summary-spill.ts`（新增文件，约 60 行）

```ts
// 摘要溢出落盘：完整摘要主体写入 ~/.loop-agent/tmp/<sessionId>/summary-<digest>-<ts>.txt
// 复用 output-governor 的路径构造与 7 天 TTL 清理，不新建清理框架。
import { buildTmpFilePath, sanitizeParamDigest } from '../tools/output-governor.js';

export interface SpillResult {
  path: string;
  /** 文件真实字节数 */
  bytes: number;
  /** 完整摘要字数 */
  chars: number;
}

/**
 * 把完整摘要主体写入临时文件。
 * @returns 成功返回路径信息；失败（含未配置 sessionId 且无可写目录）返回 undefined，静默降级
 */
export function spillSummaryBody(
  body: string,
  sessionId: string | undefined,
): SpillResult | undefined;
```

实现要点：
- 用 `mkdirSync(dirname(path), { recursive: true })` + `writeFileSync(path, body, 'utf-8')`，与 `fileRead.ts:217-227` 的 `spillExtractedText` 同构。
- digest 取 `sanitizeParamDigest('summary')` → 固定 `summary`，路径形如 `summary-summary-<ts>.txt`；**改为** digest 用 `sanitizeParamDigest(\`${sessionId ?? ''}${ts}\`)` 会更可读，实施时统一（见 D4 细节）。
- 全程 `try/catch`，失败仅 `debug.log`，返回 `undefined`。

|---|---|
| `CompactedViewOptions`（:56-73） | 新增 `sessionId?: string`（供落盘用；缺省则不落盘只提示） |
| `buildCompactedView`（:233-255） | ① 取 `summaryBody` **完整值**（不先 slice）；② 探测 `overflow = summaryBody.length - SUMMARY_TRUNCATE_MAX_CHARS`；③ `overflow >= SUMMARY_SPILL_MIN_CHARS` 时调 `spillSummaryBody(summaryBody, opts.sessionId)` 拿 `path`；④ 再 `summaryBody = summaryBody.slice(0, SUMMARY_TRUNCATE_MAX_CHARS)`（原逻辑）；⑤ 拼 `composeSummaryBody(summaryBody, anchorText)` 后再追加 `composeSummaryPathSection(...)` |
| `compact()`（:471-482） | 透传 `sessionId`：签名加 `opts?: { sessionId?: string }` 或由 `CompactionPlan` 带出（见 3.4 取舍） |
| `debug.log`（:259-265） | 日志增加 `摘要溢出=N字 落盘=有/无` 字段 |

**关键顺序（最易翻车处）**：必须 `切片前探测溢出 → 落盘 → 切片 → 拼接`；
若先 slice 再探测，永远探测不到溢出（正是当前 bug 的形态）。

### 3.4 sessionId 的传递路径

两条压缩链路：

| 链路 | 调用点 | 传参方式 |
|---|---|---|
| 自动压缩 | `react-agent.ts:1083` `preCompactionFlush(messages, llmAdapter, plan)` → `:1097` `compact(messages, extracted, plan)` | `sessionId` 在该作用域内可用（`:1088` 已用它写 L2）。**推荐**：`compact(messages, extracted, plan, { sessionId })` 或把 `sessionId` 放进 `CompactionPlan`（`planCompaction` 加可选参数） |
| 手动压缩 | `react-agent.ts:315` → `:322` 同样两处 | 同上，`opts.sessionId` 已在作用域 |

> **推荐**：`CompactionPlan` 新增可选 `sessionId?: string`，由 `planCompaction(messages, opts)` 的 `opts` 透传（`opts.sessionId`）。
> 理由：`plan` 已在两条链路上贯穿传递，避免给 `compact()` 再加一个位置参数。

### 3.5 边界与错误处理

| 场景 | 期望行为 |
|---|---|
| 摘要 ≤ 960 字（正常情况） | 不落盘、不加路径段，行为与现状**完全一致** |
| 摘要 970 字（溢出 10 < 40） | 不落盘；仅在摘要尾部追加 `…（摘要已截断 N 字）` |
| 摘要 1500 字（溢出 540） | 落盘完整 1500 字 → 回填路径段；上下文只留 960 字 |
| `sessionId` 缺失（CLI 首轮等） | 不落盘，仅加截断提示（`buildTmpFilePath` 支持 `nosess_<ts>`，但摘要场景无会话语义，建议直接跳过） |
| 落盘失败（磁盘满 / 权限） | 静默降级为仅截断提示，**不抛错、不阻断压缩** |
| 重复压缩两次 | 路径段只留最新一份（`stripPathSection` 先剥后拼） |
| 存量摘要无路径段 | `splitPathSection` 返回 `path=undefined`，按无路径处理 |
| 模型摘要含 `[完整摘要]` 字样（撞标记） | 概率极低；`stripPathSection` 用 `indexOf` 只认首个标记，且路径段永远追加在最后；撞标只影响幂等不影响正确性 |
| 临时文件 7 天后被清理 | 模型若仍读该路径 → fileRead 报文件不存在，属可接受降级（文案已弱化依赖） |
| `flushFailure='archive'`（摘要= droppable 全文） | 该路径摘要常常 > 960 字 → **会触发落盘**。需注意此时「完整摘要」= 全部被丢弃消息原文，落盘量可能很大；建议沿用 `pruneTmp` 的 200MB 总量上限兜底，不额外限制 |

### 3.6 演进项（本任务不做）

- 摘要结构化落盘（JSON 字段承载主体/原文段/路径，替代文本标记切开）。
- 临时文件内容加密或脱敏（当前与工具输出同口径，明文存于用户 home）。
- 溢出内容做二级摘要再压缩（当前是「全量落盘 + 指针」）。
- 清理失效路径段（文件被 prune 后，摘要里仍留着失效路径，当前不主动清理）。

## 一、任务目标需求

### 1.1 背景（痛点）

`core` 解决「插件长什么样、怎么挂、怎么撤」，`main` 解决「挂哪些、什么顺序、存哪、重启怎么还原」。但「一个大模型服务商」在这套体系里**没有契约**，表现为三处硬耦合：

1. `src/llm/client.ts:664` 是 `export const llm = new LLMClient()`，`src/` 内 15 处直接 import 该单例——无法成组撤销、无法替换实现。
2. `LLMClient` 内部直接 `new OpenAI()`（`client.ts:2`），抽象边界就是「OpenAI 兼容协议」。换非 OpenAI 协议的服务商只能改这个类，不能以「加插件」方式扩展。
3. `src/llm/` 5 文件 1505 行（`client.ts` 664 / `bench.ts` 477 / `bench-store.ts` 140 / `usage.ts` 139 / `connectivity.ts` 85）全部服务于单一实现，**没有一行是 provider 契约**，「默认实现」与「用户自定义实现」无处安放。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
|---|---|---|
| 插件形态与 Fiber 生命周期 | `core/src/types.ts`：`Plugin` = `PluginFunction \| PluginObject`（`name`/`inject`/`apply`）；`FiberState` 六态 | 直接复用，llm 不新造插件形态 |
| 服务容器与自动撤销 | `core/src/context.ts:42`：`ctx.provide(key, impl): Disposer`，Fiber 卸载自动执行 | 直接复用 |
| 同 key 冲突语义 | `core/src/service.ts:47`：重复 key **抛 `ServiceConflictError`，不覆盖** | 约束项：多 provider 必须多 key（D3） |
| 依赖声明 | `core/src/types.ts:24`：`Inject`，硬依赖未满足停 `PENDING`、`apply` 不执行 | 直接复用（provider 依赖 `llm:registry`） |
| 可逆副作用 | `core/src/context.ts:222`：`ctx.effect(body, label)` | 直接复用（目录登记挂 Fiber） |
| 类型化事件 | `core/src/events.ts`：`TypedEventBus` 四模式 | 直接复用，llm 只定事件表 |
| 错误族机制 | `core/src/errors.ts:22`：`CoreError` 带 `code`/`pluginName`/`fiberId`/`cause` | 继承复用（D7） |
| 诊断 | `core/src/context.ts:312`：`diagnose()` → `DiagnosticReport` | provider 挂载状态自动进诊断 |
| 清单 options 通道 | `main/src/registry.ts:46-57`：`defaultLoadPlugin` 把 `entry.options` 传给**模块默认导出工厂**；`ctx` 无 options 通道 | **关键约束**：必须提供工厂形态导出（D4 双导出） |
| 包脚手架范式 | `core/{package.json,tsconfig.json,tsup.config.ts,vitest.config.ts}` | 照抄，保持三包一致 |
| workspaces | 根 `package.json`：`["core","main"]` | 追加 `"llm"` |
| **大模型 provider 契约** | **完全缺失**：无接口、无抽象类、无 provider 注册概念 | **本任务新增** |
| 领域类型 | 仅存于 `src/types.ts:286-673`（`ChatMessage`/`ToolCall`/`LLMResponse`/`LLMUsage`/`StreamChunk`） | 在 llm 包内自持，不 import `src/`（D1） |
| 现有 OpenAI 实现 | `src/llm/client.ts:112` `LLMClient`（凭据缓存、重试、abort、视觉） | 本期不动，将来默认实现的取材来源 |

### 1.3 任务目标

1. 新建独立子包 `llm/`（`@loop-agent/llm`），与 `core/`、`main/` 平级；`dependencies` 只允许 `@loop-agent/core`。
2. 包内自持领域类型（消息/内容分片/工具定义/工具调用/用量/请求/响应/流式事件），与上游协议解耦。
3. 定义**可继承的抽象基类** `LlmProvider`：抽象 `id` + `complete()`，默认 `capabilities()`/`stream()`/`onDispose()`。
4. `defineLlmProvider()` / `defineLlmProviderFactory()` 把 provider 编译成 core 插件；`installLlm()` 提供 `llm:registry`；每 provider 独占 `llm:provider:<id>` 服务 key。
5. 能力协商：`capabilities()` 显式声明，超能力**显式抛错**，不静默忽略参数。
6. 错误族 9 类（继承 `CoreError`）+ 事件表 5 个。

### 1.4 设计约束

| 约束 | 来源 | 落地要求 |
|---|---|---|
| 只依赖 core | 用户原话 | `dependencies` 仅 `@loop-agent/core`；其余用 `node:` 或不引入 |
| 零反向依赖 | 沿用 core/main 范式 | `llm/src/**` 不 import `src/`/`webui/`/`desktop/`/`main/`；`boundary.test.ts` 断言锁死 |
| 本期零接入 `src/` | 沿用 D1「先搭骨架」 | 不改 `src/` 任一行、不替换 `client.ts`、不接 `initRuntime` |
| 只收 ESM、单产物 | 沿用 core Q12 定案 | `tsup` 只 `format:['esm']`；`exports` 三键；产物恰好 3 文件 |
| strict 无 `any` | 项目规范 | 上游未知报文用 `unknown` + 显式收窄 |
| 零三方运行时依赖 | 工程默认约束 | schema 校验手写，不引 zod/ajv |
| 契约一次写对 | 20261114-003 教训 | P0 定稿签名，P1 只做加法式演进 |
| 跨平台 | 工程默认约束 | 本包无路径/无外部命令，测试不写死分隔符 |

## 二、方案设计

### 2.1 总体思路

```
┌──────────────────────────────────────────────────────────────────┐
│  llm/  @loop-agent/llm （本期新增，只做契约层）                     │
│                                                                  │
│   LlmProvider (抽象基类, D2)        defineLlmProvider (D4)        │
│    ├ id            abstract          ├ defineLlmProvider          │
│    ├ capabilities() 可覆写(D5)        └ defineLlmProviderFactory   │
│    ├ complete()    abstract              → PluginObject           │
│    ├ stream()      默认降级(D8)             inject ['llm:registry']│
│    └ onDispose()   钩子                     apply: create→provide  │
│                                              key 'llm:provider:<id>'│
│   types.ts(D1) errors.ts(D7) events.ts(D10) keys.ts(D3)           │
│   registry.ts: LlmRegistry + installLlm → provide 'llm:registry'  │
└───────────────────────────────┬──────────────────────────────────┘
                                │ 只依赖 core
              ┌─────────────────▼──────────────────┐
              │ @loop-agent/core（零改动）           │
              │ provide/plugin/on/effect/diagnose   │
              │ 同 key 重复 → ServiceConflictError   │
              └─────────────────▲──────────────────┘
                                │ 清单挂载
              ┌─────────────────┴──────────────────┐
              │ @loop-agent/main（零改动）           │
              │ PersistentPluginRegistry + 落盘      │
              └────────────────────────────────────┘
```

**数据流①（安装目录服务）**：`main.registry.restore()` → `import('@loop-agent/llm')` → `ctx.plugin(installLlm())` → Fiber `ACTIVE` → `llm:registry` 可取。

**数据流②（挂 provider）**：`ctx.plugin(def)` → 硬依赖 `llm:registry` 就绪后 `apply` → `create(mergedOptions)` → `registry.register()` → `ctx.provide('llm:provider:<id>')` → 卸载时 Fiber 自动 `unregister` + `onDispose()`。

**数据流③（一次调用）**：`registry.complete(id, req)` → `require(id)` → `assertCapability()` → `emit 'llm/request'` → `provider.complete()` → `emit 'llm/response'` → 返回；抛错归一为 `LlmError` 并发 `llm/error`。

### 2.2 关键设计决策

| 编号 | 决策 | 取舍与被否决项 |
|---|---|---|
| **D1** | 领域类型在 llm 包内**自持**，不 import `src/types.ts`，也不下沉进 core | 否决下沉 core（core 是领域无关内核，塞大模型术语会让 `boundary.test.ts` 失去意义）；否决直接 import（违反零反向依赖，且 `src/types.ts` 混着会话标记与通知边界常量等无关杂质）。代价：短期结构重复，靠 3.2 对照表在迁移时对账 |
| **D2** | provider 契约用**抽象基类**，必实现项只有 `id` + `complete()` | 用户原话是「继承」；否决纯 interface（每个实现重复写流式降级与能力默认值，且无法 `instanceof`）；否决 interface + helper（分裂成两套符号） |
| **D3** | `llm:registry` 一个目录服务 + 每 provider 独占 `llm:provider:<id>` | **硬理由**：`core/src/service.ts:47` 重复 key 抛 `ServiceConflictError` 不覆盖。否决单 key 存 Map（丢掉 core 的归属追踪，`diagnose()` 无法按 provider 报 owner，卸载也失去自动撤销） |
| **D4** | 双导出：`defineLlmProvider()` 与 `defineLlmProviderFactory()`，共用 `buildPlugin(def, runtimeOptions)` | **硬理由**：`main/src/registry.ts:46-57` 的 options 只能经「模块默认导出工厂」传入，`ctx` 无此通道。只给前者 → 清单 options 静默丢弃；只给后者 → 无覆盖时也要包一层 |
| **D5** | 能力协商显式声明，超能力**显式拒绝**（抛 `LlmCapabilityError`，不发请求） | 检索要点⑤：能力不一致必须显式拒绝或降级，不能悄悄忽略。否决布尔大杂烩（失去类型提示与穷举） |
| **D6** | 领域类型 camelCase（`promptTokens`），上游 snake_case 由各 provider 自行映射 | 保住抽象层纯度；代价是迁移需一次映射。**列入 Q2 交用户拍板** |
| **D7** | `LlmError` 继承 core 的 `CoreError`，code 前缀 `LLM_` | 复用稳定 `code` + `pluginName` + `fiberId` + `cause`；`instanceof CoreError` 兜底不漏。否决独立 `Error` 基类（宿主错误处理会分裂） |
| **D8** | `stream()` 非抽象，默认由 `complete()` 降级；原生流式可覆写 | 接口最小化：不实现流式的 provider 也能用。否决 `stream()` 设抽象（把不支持者挡在门外，与 D5 矛盾） |
| **D9** | 本期不做中间件链，只留 `hooks?: LlmCallHooks`（只读观测） | 重试/限流/预算/路由的正确形态强依赖「谁决定降级」，现在定是拍脑袋。留最小钩子位，等真实诉求 |
| **D10** | 事件表 `LlmEvents extends EventMapBase`，命名 `llm/<verb>` | 必须 `extends`，否则 `Plugin<LlmEvents>` 报 `TS2344`（core 实测教训）。副作用：该索引签名使 `keyof E & string` 退化为 `string`，未声明事件名不被拒绝，须写入 README |
| **D11** | `installLlm()` 重复安装时不静默忽略，重抛为 `LlmError('LLM_REGISTRY_EXISTS')` 并给可读提示 | 沿用 core 冲突显式化哲学；但把 `CORE_SERVICE_CONFLICT` 翻译成人话，避免使用者猜 |
| **D12** | 本期零接入 `src/`，只用测试内联假 provider 验证 | 沿用 core/main「先搭骨架、渐进迁移」；否则「契约够不够用」会被「迁移是否成功」的噪音掩盖 |
| **D13** | 视觉只做能力位 + 内容分片，不加 `completeVision()` | `src/llm/client.ts` 的独立视觉客户端是**实现层缓存优化**，不是契约差异。把实现细节提升为契约会让不支持的 provider 多一个永远抛错的方法。将来若真需独立端点，加可选方法属加法式演进 |

### 2.3 联网检索要点（2026-11-14）

| # | 结论 | 印证 |
|---|---|---|
| ① | 抽象要「足够通用容纳差异，又足够结构化让实现可互换」；契约须覆盖流式、工具调用、token 用量、优雅降级四件套 | D5 + D8 |
| ② | **provider 在构造期一次性接收配置**，运行期只暴露 `complete()`/`stream()`；否则抽象双向泄漏 | D4：`create(options)` 收配置，`complete(req)` 只收本次请求变量 |
| ③ | 核心价值是让业务代码**永不写 `if provider == 'x'`**；错误命名/客户端构造/role 词表须先归一 | D1 + D7 |
| ④ | 三条反面教训：最低公分母接口、任意参数透传、把 SDK 当领域层 | D5（能力位而非删能力）、D1（不引 SDK 类型）、D13 |
| ⑤ | 能力须显式声明并在路由前拒绝；用量缺失记**未知**而非 0 | D5 两个独立能力位 + `LlmUsage` 字段可空 |
| ⑥ | 注册表存**类/工厂而非实例**，实例化在调用点，否则模块加载期就要配置、测试极难 | D4 的 `create()` 工厂形态 |
| ⑦ | 注册表以 id → 定义索引，另支持别名与默认 provider | D3 + `setDefault()` |
| ⑧ | **受控逃生口**（自由 metadata 字段）是有意保留的泄漏，须注明消费方要容忍缺失/异形 | `LlmResponse.raw?: unknown` 及注释要求 |
| ⑨ | 接口变更是移动靶，须有明确变更纪律 | 1.4「契约一次写对，P1 只加法式演进」 |

**反面案例自校验**：有实现因第三方抽象的「token 记账/重试语义/结构化工具调用」漏抽象而弃用之。本任务同样**不引入任何第三方抽象层**，契约自持。

### 3.2 领域类型（`src/types.ts`）

```ts
export type LlmContentPart =
  | { type: 'text'; text: string }
  | { type: 'image'; mimeType: string; data: string };

export type LlmMessage =
  | { role: 'system'; content: string }
  | { role: 'user'; content: string | LlmContentPart[] }
  | { role: 'assistant'; content: string | null; toolCalls?: LlmToolCall[] }
  | { role: 'tool'; toolCallId: string; content: string };

export interface LlmToolDef {
  name: string;
  description: string;
  parameters: Record<string, unknown>;   // JSON Schema；手写校验，不引三方库
}

export interface LlmToolCall {
  id: string;
  name: string;
  arguments: string;                     // 保持 JSON 字符串，避免二次序列化丢精度
}

/** 缺失字段一律 undefined，不填 0（检索要点⑤） */
export interface LlmUsage {
  promptTokens: number;
  completionTokens: number;
  totalTokens: number;
  cacheHitTokens?: number;
  cacheMissTokens?: number;
}

export type LlmFinishReason = 'stop' | 'tool_calls' | 'length' | 'content_filter' | (string & {});

export interface LlmRequest {
  model: string;
  messages: LlmMessage[];
  temperature?: number;
  maxTokens?: number;
  tools?: LlmToolDef[];
  toolChoice?: 'auto' | 'none' | 'required' | { name: string };
  responseFormat?: { type: 'text' } | { type: 'json'; schema?: Record<string, unknown> };
  stop?: string[];
  metadata?: Record<string, string>;     // 透传元信息（如 sessionId），不得含密钥
}

export interface LlmResponse {
  content: string | null;
  toolCalls?: LlmToolCall[];
  finishReason: LlmFinishReason;
  usage?: LlmUsage;
  model: string;                         // 实际模型名（服务商可能改写别名）
  raw?: unknown;                         // 受控逃生口（要点⑧），核心逻辑不得依赖
}

export type LlmStreamEvent =
  | { type: 'text-delta'; delta: string }
  | { type: 'tool-call-start'; index: number; id: string; name: string }
  | { type: 'tool-call-delta'; index: number; argumentsDelta: string }
  | { type: 'usage'; usage: LlmUsage }
  | { type: 'done'; response: LlmResponse };
```

### 3.3 `LlmProvider` 抽象基类（`src/provider.ts`）

```ts
export abstract class LlmProvider {
  abstract readonly id: string;
  get displayName(): string { return this.id; }

  /** 保守默认：全 false，逼实现者显式声明 */
  capabilities(): LlmCapabilities { /* 全 false + usageReporting:false */ }

  abstract complete(req: LlmRequest, opts?: LlmCallOptions): Promise<LlmResponse>;

  /** 默认由 complete() 降级；覆写须保证末事件是 {type:'done'} */
  async *stream(req: LlmRequest, opts?: LlmCallOptions): AsyncIterable<LlmStreamEvent> { … }

  protected async onDispose(): Promise<void> {}
}

export interface LlmCallOptions {
  signal?: AbortSignal;
  hooks?: LlmCallHooks;   // 只读观测，不得改变语义
}

export interface LlmCapabilities {
  streaming: boolean;
  toolCalling: boolean;
  vision: boolean;
  jsonMode: boolean;
  maxContextTokens?: number;   // 未知不填，不伪造
  usageReporting: boolean;
  cacheReporting: boolean;
}
```

默认 `stream()`：调 `complete()` → 有文本则发 `text-delta` → 有用量则发 `usage` → 发 `done`。**工具调用场景默认降级不发 `tool-call-start`/`tool-call-delta`**（`complete()` 里已是完整结果，伪造增量无意义），`done.response.toolCalls` 足以表达——须写入 README。

### 3.4 `defineLlmProvider` / `defineLlmProviderFactory`（`src/define.ts`）

```ts
export function defineLlmProvider(def): PluginObject
  → buildPlugin(def, {})
export function defineLlmProviderFactory(def): (options?) => PluginObject
  → (runtimeOptions) => buildPlugin(def, runtimeOptions ?? {})

function buildPlugin(def, runtimeOptions): PluginObject {
  assertValidDefinition(def);                              // id 非空、不含 ':'、create 是函数
  const mergedOptions = { ...def.options, ...runtimeOptions };   // 浅合并，清单侧优先
  return {
    name: `llm-provider:${def.id}`,
    inject: { required: [LLM_SERVICE_KEYS.registry] },
    async apply(ctx) {
      const registry = ctx.get<LlmRegistry>(LLM_SERVICE_KEYS.registry);
      if (!registry) throw new LlmError('llm:registry 不可见（不应发生）');
      const provider = await def.create(mergedOptions);
      if (provider.id !== def.id) throw new LlmConfigError(…);   // key 与实例 id 错位是致命错误
      ctx.provide(`${LLM_SERVICE_KEYS.providerPrefix}${def.id}`, provider);
      ctx.effect(() => registry.register(provider, { isDefault: def.isDefault }), …);
    },
  };
}
```

**options 两级合并（浅合并，后者覆盖同名键）**

| 来源 | 语义 | 谁写入 |
|---|---|---|
| `def.options` | 代码侧默认值 | provider 作者 |
| `manifestEntry.options` | 部署侧覆盖值（多配置档案） | 用户 / 宿主编排 |

只做一层浅合并：深合并的数组语义（拼接还是替换）与嵌套覆盖规则每次都要争辩，而 provider 配置以扁平标量为主。合并放在 `apply` 内而非 registry 内——放 registry 会让它必须知道 manifest 结构，破坏 llm 对 main 的零依赖。

### 3.5 `LlmRegistry` 与 `installLlm`（`src/registry.ts`）

```ts
export interface LlmRegistry {
  list(): LlmProviderInfo[];
  get(id: string): LlmProvider | undefined;
  require(id: string): LlmProvider;
  defaultProvider(): LlmProvider | undefined;
  setDefault(id: string): void;
  complete(id: string, req: LlmRequest, opts?: LlmCallOptions): Promise<LlmResponse>;
  stream(id: string, req: LlmRequest, opts?: LlmCallOptions): AsyncIterable<LlmStreamEvent>;
  register(provider: LlmProvider, opts?: { isDefault?: boolean }): Disposer;
}
export function installLlm(): PluginObject;   // provide 'llm:registry'
```

`complete()` 固定流水线（顺序不可乱）：`require(id)` → `assertCapability()` → `emit 'llm/request'` → `provider.complete()` → `emit 'llm/response'(elapsedMs)` → 返回。

### 3.6 错误族与事件

| 类 | code | 触发条件 | 重试 |
|---|---|---|---|
| `LlmError` | `LLM_ERROR` | 基类 / 未分类 | 视 cause |
| `LlmConfigError` | `LLM_CONFIG_INVALID` | 定义校验失败、options 非法 | 否 |
| `LlmProviderNotFoundError` | `LLM_PROVIDER_NOT_FOUND` | 指定 id 未注册 | 否 |
| `LlmProviderConflictError` | `LLM_PROVIDER_CONFLICT` | 同 id 重复 register | 否 |
| `LlmCapabilityError` | `LLM_CAPABILITY_UNSUPPORTED` | 请求超出 capabilities | 否（应换 provider） |
| `LlmAuthError` | `LLM_AUTH_FAILED` | 401/403 | 否（沿用 `client.ts:110`） |
| `LlmRateLimitError` | `LLM_RATE_LIMIT` | 429 | 是（交上层退避） |
| `LlmRequestError` | `LLM_REQUEST_FAILED` | 其余服务商侧错误 | 视 code |
| `LlmAbortedError` | `LLM_ABORTED` | `signal.aborted` | 否（短路，沿用 `client.ts:16`） |

事件 5 个：`llm/registered`、`llm/unregistered`、`llm/request`、`llm/response`、`llm/error`。事件**只读**，监听器抛错不中断调用链（由 core 的 `TypedEventBus` 语义保证）。

### 3.7 边界与错误处理

| 场景 | 行为 |
|---|---|
| `llm:registry` 未安装就挂 provider | Fiber 停 `PENDING`（`inject.required` 生效），`diagnose().fibers[].missing = ['llm:registry']` |
| 重复 `installLlm()` | 撞 `ServiceConflictError` → 重抛 `LLM_REGISTRY_EXISTS`，提示「请勿重复安装」 |
| 同 id 挂两个 provider | `ctx.provide` 抛 `ServiceConflictError` → Fiber `FAILED`，条目留清单，`diagnose()` 见 `loadError` |
| provider 卸载 | Fiber 逆序 disposer → 注销目录 → `onDispose()`；其抛错记 `disposeErrors`，不阻断其他 disposer |
| `complete()` 抛非 `LlmError` | 归一包装，`cause` 挂原始错误，`pluginName`/`fiberId` 从 ctx 补全 |
| 请求带 `tools` 但 `toolCalling:false` | 调用前抛 `LlmCapabilityError`，**不发网络请求** |
| `usage` 缺失 | `undefined`，不构造全 0 对象 |
| `signal` 已 aborted | 立即抛 `LlmAbortedError` |
| 流式实现无 `done` 收尾 | `registry.stream()` 末尾补 `done`（响应体用已累积分片尽力构造），**不上抛错误**；行为写入 README |
| `options` 含不可序列化值 | 属 main 清单层职责（`PluginManifestEntry.options` 只收 JSON）；llm 侧不二次校验 |

## 一、任务目标需求

### 1.1 背景（痛点）

`commandRun({background:true})` 启动后立即返回 taskId，Agent 想知道结果只能反复调用 `commandStatus` / `commandLogs` 轮询：多耗轮次与 token，且轮询间隔要么太密（浪费）要么太疏（结果迟到）。WebUI 侧用户也看不到「跑完了」的即时反馈。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
| --- | --- | --- |
| 任务完成回调 | [background-tasks.ts](../../../src/tools/background-tasks.ts) `finish()` 在进程 exit/close 时更新内存与 `.json`，无任何事件出口 | 需新增完成事件（EventEmitter 或回调注册） |
| 会话归属 | `BackgroundTask` 无 `sessionId`；[types.ts](../../../src/types.ts) `ToolContext` 只有 `signal/workspaceRoot` | 需补 `sessionId` 并在 runner 注入 ctx |
| Agent 循环注入点 | [react-agent.ts](../../../src/agent/react-agent.ts) 每轮「压缩 → 组装 messages → LLM → 工具」循环 | 在每轮 LLM 调用前 drain 通知，追加到 messages 尾部 |
| 上下文与前缀缓存 | messages 前缀决定缓存命中；运维文档强调 `toOpenAITools()` 逐字节不变 | 通知只能追加在**尾部**，不得插到 system/历史中间 |
| 会话恢复 | [react-agent.ts](../../../src/agent/react-agent.ts) `restoreSession()` + `SessionStore.getRestoreMessages()` | 未投递通知需可从 runs/*.json 补投 |
| 单测 | `command-background.test.ts` 用假进程模拟 exit | 可复用同一套假进程模式验证事件 |

### 1.3 任务目标

后台任务结束（`exited` / `killed` / 启动失败）时：

1. 生成一条结构化通知（taskId、命令、状态、退出码、耗时、日志尾部）。
2. 在**同一会话**的下一次 Agent 轮次注入（若 Agent 已空闲，则等下一次用户消息的 run 开始时注入）。
3. 注入位置固定在 messages 尾部、以 `role:'user'` 承载，保证 system/历史前缀不变、缓存不失效。
4. 每条通知**只投递一次**（磁盘 `notifiedAt` + 内存去重），跨进程重启不重复。
5. 通知失败（日志读不到、磁盘不可写）不得影响主回答流程。
6. 可通过 `tools.backgroundNotify` 关闭；日志尾部行数/字符数可配。

### 1.4 设计约束

- 不改变 `commandRun`/`commandStatus`/`commandLogs` 的工具语义与返回格式。
- 通知注入体 ≤ 2000 字符、≤ 20 行，避免一条通知撑爆上下文。
- 多会话隔离：会话 A 的后台任务绝不注入会话 B。
- 同一 taskId 并发结束只发一次（幂等）。
- 零新依赖。

## 二、方案设计

### 2.1 总体思路

```
commandRun(background) ──ctx.sessionId──▶ backgroundTasks.start(task)
                                              │ 子进程 exit/close
                                              ▼
                                        finish(task) ──▶ emit('finish', task)
                                              │                │
                                              │                ├─ 写 .json：status/exitCode/finishedAt（已有）
                                              │                └─ 写 .json：sessionId（新增）
                                              ▼
                     BackgroundNoticeQueue（进程级单例）
                       ├─ push({sessionId, taskId, text, createdAt})
                       └─ 持久化标记：runs/<taskId>.json 的 notifiedAt
                                              │
                        Agent 每轮 LLM 调用前（压缩后）
                                              ▼
                     drain(sessionId) → 有通知则 messages.push({role:'user', content: <background_task_notification>…})
                                              │
                                              ▼
                                       LLM 请求（前缀不变，仅尾部追加）
```

恢复补投：`restoreSession()` 后扫描 `runs/*.json`（mtime 近 7 天、`status≠running`、`sessionId` 匹配、`notifiedAt` 为空），按 `finishedAt` 升序入队。

### 2.2 关键设计决策

| 编号 | 决策 | 取舍 / 被否决项 |
| --- | --- | --- |
| D1 | **通知以 `role:'user'` 追加在 messages 尾部**，用 `<background_task_notification>` 包裹 | 否决 `role:'system'`：插到 system 位置会破坏前缀缓存；否决 `role:'tool'`：没有对应 tool_call_id，上下文非法 |
| D2 | 每轮 LLM 调用前 drain 一次；空闲时保留到下次 run 开始 | 否决「用定时器直接调 LLM」：会与用户输入抢跑、产生并发 run；否决「立即中断当前回答」：破坏正在进行的推理 |
| D3 | 去重真源 = `runs/<taskId>.json` 的 `notifiedAt`，内存队列只是加速 | 否决仅内存去重：进程重启会重复投递 |
| D4 | 日志尾部取最后 `tailLines`（默认 20）并截断到 `maxChars`（默认 2000），保留行首缩进 | 否决全文：长日志会挤占上下文；否决只给日志路径：Agent 仍要再调工具 |
| D5 | `BackgroundTask` 增加可选 `sessionId`，`ToolContext` 增加可选 `sessionId`，由 API/CLI runner 注入 | 否决按 workspace 归属：同一工作空间可有多会话，会串台 |
| D6 | 通知注入放 try/catch，任何异常只记 debug，不抛出 | 与既有「记忆/压缩失败不阻塞主流程」口径一致 |
| D7 | 配置 `tools.backgroundNotify: { enabled:true, tailLines:20, maxChars:2000 }` | 否决硬编码：不同模型上下文预算差异大 |
| D8 | 只通知「结束态」，不通知中间状态变化 | 中间态高频、价值低；WebUI 卡片（任务 20261104-005）负责实时展示 |

### 2.3 联网检索结论

- 主流 Agent 框架（Claude Code / OpenHands / OpenAI Agents SDK）均采用「后台任务完成后以 user 角色注入消息」的做法，避免中断当前轮次；注入内容带 `<task_notification>` 类标签便于模型识别。
- 已知坑：在历史中间插入 system/user 消息会导致前缀缓存整体失效，必须只追加尾部；通知需幂等，否则重启后重复注入。
- 来源：OpenHands runtime 事件队列文档、OpenAI Agents SDK `RunContext` 事件说明（2026-11 检索）。

## 三、任务详细设计

### 3.1 数据结构

```ts
// types.ts
interface ToolContext { signal?: AbortSignal; workspaceRoot?: string; sessionId?: string; }

// background-tasks.ts
interface BackgroundTask {
  // ...既有字段
  sessionId?: string;   // D5
  notifiedAt?: number;  // D3：非空表示已投递
}

interface BackgroundNotice {
  sessionId: string;
  taskId: string;
  text: string;      // 已渲染好的 XML 片段
  finishedAt: number;
}
```

### 3.2 模块接口

```ts
// src/agent/background-notice.ts
export function enqueueBackgroundNotice(task: BackgroundTask): void; // finish 回调
export function drainBackgroundNotices(sessionId: string): string[];  // 取走并标记
export function restoreBackgroundNotices(sessionId: string, runsDir: string): number; // 恢复补投
```

- `enqueue` 内部完成日志尾部读取与渲染；`drain` 返回 0..N 条文本，并按 `sessionId` 过滤。
- 标记 `notifiedAt` 采用「先取内存 → 推送消息 → 异步写 JSON」；写失败仅告警，内存已去重。
- 渲染模板：

```
<background_task_notification>
taskId: bg_ab12cd34_1762345678
command: npm run build
status: exited (exitCode=0)
duration: 12.3s
logTail:
<最后 20 行 / 最多 2000 字符>
</background_task_notification>
```

### 3.3 边界与错误处理

| 场景 | 行为 |
| --- | --- |
| 任务被 `commandStop` 主动终止 | `status=killed`，通知里标注「用户停止」 |
| 启动即失败（spawn error） | 同样通知，`exitCode=null`，附错误文本 |
| 日志已被清理策略删除 | 通知仍发，`logTail` 显示「(日志已清理)」 |
| 同一 task 二次 finish | `notifiedAt` 已存在 → 不再入队 |
| Agent 已空闲 | 队列保留；下次 run 开始时注入 |
| 会话被删除 | drain 时发现无活跃会话 → 丢弃并标记，避免无限堆积 |
| `enabled=false` | 不产生队列项、不写 notifiedAt |

### 3.4 演进项（本任务不做）

- 通知推送到飞书/IM。
- 后台任务失败自动重试。
- 日志实时流式注入（只给结束态尾部）。

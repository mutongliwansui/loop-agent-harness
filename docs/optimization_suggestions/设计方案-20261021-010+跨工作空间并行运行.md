## 一、背景与目标

### 1.1 需求来源

20261021-002-05 已实现**同工作空间多会话并发**：会话级 `inFlight` 锁 + `AgentPool` 按 `sessionId` 租用实例 + `RunHub` 多 run 并存 + 前端 `chat-stream` 按会话独立维护流状态。默认池容量 4（`LOOP_AGENT_POOL_CAPACITY` 可调）。

但**跨工作空间并行**仍被三处进程级全局态锁死，表现为：A 空间有会话在跑时，用户在 B 空间新建/切换会话会收到 `busy：存在正在处理的会话，暂不能切换工作空间`；即便没有 run 在跑，`switchWorkspace()` 也会把整个进程的"当前空间"整体搬走，影响所有管理页（Config/Tools/Memory/Skills 的 `workspace` scope）与文件浏览器根目录。

本方案目标：让「服务实例」与「工作空间」解耦——**任意空间的任意会话可同时运行**，切换或查看空间不再干扰其他空间正在跑的 run。

### 1.3 差距清单

1. **空间状态无法并存**：所有"当前空间"相关的可变状态（进程 cwd、store 的 `workspaceId`、configLoader/Writer 的 `workspacePath`）各只有一份。
2. **运行时对象绑死单空间**：`AgentPool.initAgent` 在构造时把 `process.cwd()` 写进钩子，池内实例天然只服务一个空间。
3. **互斥粒度错**：`hasInFlight()` 是全局的，把"空间切换安全"错做成了"全局串行"。
4. **路径标识不稳定**：`workspaceId` 对同一目录的多种书写形式（大小写、尾斜杠、相对路径）产生不同 id。
5. **会话标识可能跨空间撞名**：秒级 `sessionId` 无空间命名空间，且是 RunHub/SessionManager 的全局键。
6. **API 契约无空间维度**：`/sessions/:id` 无法表达"哪个空间的这个会话"。

### 1.4 目标

- **G1** 任一空间任一会话可并发运行，互不影响（含 `process.chdir` 彻底移除）。
- **G2** 同一目录无论以何种书写形式引用，解析出**同一个** `workspaceId`。
- **G3** 跨空间 `sessionId` 不歧义（`RunHub` / `SessionManager` / 路由 / 前端 key 均安全）。
- **G4** 存量会话数据**零迁移**可见（不改变既有 `workspaceId` 算法结果）。
- **G5** CLI 单空间模式行为不回退。

### 1.5 设计原则

- **显式优先**：空间根通过参数/上下文显式传递，不依赖隐式全局变量；隐式通道（`AsyncLocalStorage`）只作兜底。
- **不可变**：`WorkspaceRuntime` 一旦建立，其 `root` 不再变更（对比现在的 `rebindWorkspace` 原地改写）。
- **失败可见**：宁可启动期断言崩溃，也不要运行时静默错位（对应最大风险）。
- **零新依赖**：仅用 `node:async_hooks`、`node:path`、`node:fs` 内置能力。
- **可回退**：P0/P1 每步都能独立上线并保持现有行为。

### 1.6 非目标

- 多用户/多租户鉴权体系（仍是单用户单 token）。
- 跨空间共享会话（会话永远归属单一空间）。
- 水平扩展/多进程（本方案仍是单进程内的多空间并存）。
- 记忆 L2/L3 跨空间共享（按"空间即项目"完全隔离，见 D8）。
- WebUI「是否保留当前空间概念」的产品决策（见 D9，与"移除工作空间切换逻辑"议题联动的部分留给该议题定）。

## 二、现状架构（改造前）

### 2.1 空间切换的六步动作

```
POST /sessions {workspacePath} | GET /sessions/:id（跨空间）| POST /sessions/:id/messages（兜底）
        │
        ├─ hasInFlight()  ← 全局互斥，任一会话在跑就 busy
        │
        └─ switchWorkspace(target)
             1. process.chdir(target)              ← 进程级，全局生效
             2. store.rebindWorkspace(target)      ← 原地改写 workspaceId
             3. configLoader.setWorkspacePath()    ← 可变全局
             4. configWriter.setWorkspacePath()    ← 可变全局
             5. resetMemoryKitCache()              ← 清空全进程 kit 缓存
             6. ensureScaffold() + reinitMemory() → pool.reset()  ← 池全废
```

一次切换让**所有**空间相关对象重置，因此不可能有两个空间同时处于活动状态。

### 2.2 全局互斥链

| 层 | 现状 | 位置 |
| --- | --- | --- |
| 会话级 | `SessionEntry.inFlight`（同会话第二条消息 → busy） | `session-manager.ts:20-23` |
| 全局级 | `hasInFlight()` 遍历全部会话 | `session-manager.ts:49-54` |
| 池级 | `AgentPool` 容量 4，全 busy 则排队 | `agent-pool.ts:75-95` |
| 空间级 | 切换前必须"全局空闲" | `sessions.ts:93`、`messages.ts:33` |

                    │   回收策略：LRU / 常驻（D1）              │

                                       │ get(root)
        ┌──────────────────┬───────────┴────────┬─────────────────┐

 └────────────┘   └──────────────┘   └──────────────┘   └──────────────┘
        │                  │                    │                 │

        │          sessions.json / 会话文件   .loop-agent/     initAgent 注入
        │          <userDir>/sessions/<wsId>  .agent-config    getMemoryKit(root)
        │

                                       │
                                       ▼
                     ToolContext.workspaceRoot（显式，优先）
                     runner 注入 → commandRun / fileRead / fileWrite / editFile / fileSearch

  RunHub（全局单例）+ 路由：靠 sessionId 空间命名空间保证唯一（P2，D5）

要点：
- **每空间一个 `AgentPool`**（非共享池）。原因见 1.2 #9：`initAgent` 是池级固定钩子，共享池无法按会话切换根目录。
- **`switchWorkspace` 退化为"指针刷新"**：不再 chdir / 不再 reset 任何池；其它空间运行中的 run 完全不受影响。
- **`process.chdir` 全量移除**，仅保留应用自身资源类的 `process.cwd()`。

## 四、详细设计

### 4.1 P0：WorkspaceRuntime registry（纯重构，行为不变）

**新增 `src/session/path-utils.ts`**

```ts
/** 空间路径规范化：绝对化 + 去尾斜杠 + Windows 保留磁盘真实大小写 */
export function canonicalWorkspacePath(input: string): string;
/** 词法比较（大小写/分隔符不敏感），替代现有 samePath */
export function isSameWorkspace(a: string, b: string): boolean;
```

实现要点（对应 **D2**）：
1. `resolve(input.trim())` 绝对化（`normalizeDirPath` 的现有逻辑并入）；
2. Windows 用 `fs.realpath()` 获取磁盘真实大小写，失败（目录不存在）回退 `resolve` 结果；
3. **不改变 `workspaceId()` 公式本身**（保证 G4 存量零迁移）——只保证"同一物理目录的各种书写形式，经 canonical 后得到同一字符串"。

> 现有 `workspaceId()` 直接 hash 原始串（1.2 #10），因此 canonical 必须在**所有入口**统一调用，否则同一目录会分裂成多个空间。

**新增 `src/api/workspace-runtime.ts`**

```ts
export interface WorkspaceRuntime {
  readonly root: string;                       // canonical 绝对路径
  readonly id: string;                         // workspaceId(root)
  readonly store: SessionStore;
  readonly configLoader: ConfigLoader;
  readonly configWriter: ConfigWriter;
  readonly sessions: SessionManager;            // 每空间一份 → 天然 per-workspace 锁
  readonly pool: AgentPool;
  getMemoryKit(): Promise<MemoryKit>;
  lastUsedAt: number;
}

export class WorkspaceRegistry {
  constructor(opts?: { maxRuntimes?: number; poolCapacity?: number });
  async get(root: string): Promise<WorkspaceRuntime>;   // 懒建（每次建都 store.init()，幂等）
  peek(root: string): WorkspaceRuntime | undefined;     // 只读查询，不建
  async ensureRoot(root: string): Promise<void>;        // stat + R|X 校验（沿用 ensureDirUsable）
  async evictIdle(): Promise<void>;                      // 按 D1 策略
  list(): WorkspaceRuntime[];
  reset(): Promise<void>;                                // 测试/关停用
}
```

`bootstrap.ts` 改造：把现有单例 `store` / `configLoader` / `configWriter` / `pool` 全部收进 registry，`server.ts` 注入 `registry` 替代 `sessionStore`；**P0 阶段 registry 只装一个（启动目录）runtime**，行为与现在完全一致。

### 4.2 P1：去 `process.chdir`（解耦关键）

#### 4.2.1 工具层消费 `workspaceRoot`

`src/tools/runner.ts` 调用处注入上下文：

```ts
const ctx: ToolContext = { signal: opts.signal, workspaceRoot: wsRoot };
await tool.execute(args, ctx);
```

各工具改造：

| 工具 | 现状 | 改造（**D20 修正**） |
| --- | --- | --- |
| `commandRun` | 无 `args.cwd` → `exec` 默认 cwd | `cwd = args.cwd ? resolveToolPath(wsRoot, args.cwd) : wsRoot` |
| `fileRead` / `fileWrite` / `editFile` / `grep` | 直接 `String(args.path)` 交给 fs | 先 `resolveToolPath(wsRoot, path)`，再交给 fs |
| MCP client | `cwd: c.cwd` 可为空 | **D19 修正**：`cwd` 固定为「配置显式值 ?? 启动目录」，不随空间切换（进程级单例，启动期一次性连接） |

`toSlash` / `resolveInWs` 从 `handlers/fs.ts` 私有实现**抽到 `src/tools/workspace-fs.ts` 共享**（D15）：API 侧继续用 `resolveInWs` 的越界拒绝语义（行为零变化），工具侧使用 `resolveToolPath`。

**D20 修正（工具层路径策略）**：相对路径按空间根解析，**绝对路径原样放行**，不新增「必须落在空间内」的拒绝——`activate_skill` 引导的 `~/.loop-agent/skills/...`、上传目录均在空间外，强制越界拒绝属行为变更，本批次不做。

**根目录取值统一走 `const root = options.workspaceRoot ?? currentWorkspaceRoot() ?? process.cwd()`**（见 4.2.2）。这样 CLI 不注入 `workspaceRoot` 时自动回退到自身 cwd（= 唯一空间，语义正确），serve 侧则始终拿到显式根。**这是 D13 允许 `workspaceRoot` 保持 optional 的前提**。

#### 4.2.2 隐式兜底：`AsyncLocalStorage`

**新增 `src/runtime/workspace-context.ts`**

```ts
const als = new AsyncLocalStorage<{ root: string; id: string }>();
export function runWithWorkspace<T>(ws: {root: string; id: string}, fn: () => Promise<T>): Promise<T>;
export function currentWorkspaceRoot(): string | undefined;  // als.getStore()?.root（无上下文 → undefined）
```

调用点：`handleMessage`、`handleCreateSession`、各 handler 在拿到 runtime 后，用 `runWithWorkspace` 包裹整个请求处理体；`runAgent` 内部同样包裹。
**task-02 先落地 `runAgent` 包裹**（bootstrap 的 `runAgent` 闭包），handler 级包裹随 task-04「请求携带空间解析 runtime」一并接入。
`currentWorkspaceRoot()` 保持返回 `undefined`（而非回退 cwd），三级回退统一由 `ToolRunner.run` 完成，避免"兜底值"与"显式值"语义混淆。

作用：即便某个深层工具忘记用 `ctx.workspaceRoot`，仍能通过 `currentWorkspaceRoot()` 读到正确根，**避免 33 处逐一漏改的静默错位**（这是本方案最重要的安全网）。

**为什么用 ALS**（本阶段检索结论）：`node:async_hooks` 的 `AsyncLocalStorage` 是官方推荐做法，`run()`/`getStore()` 自 Node 16.4 起稳定，官方文档明确其适用场景包含 **tenant metadata** 这类"请求级但非业务逻辑"的横切数据；已知坑是**非原生 Promise / 旧式 callback API 会丢上下文**（`util.promisify` 通常可修复），排查方式是打 `getStore()` 日志定位。因此本方案：显式 `workspaceRoot` 为主，ALS 为辅，二者不一致时以显式为准并 debug 告警。

#### 4.2.3 存储层

- `SessionStore` 保留构造参数，**移除 `rebindWorkspace()`**（或标注 `@deprecated` 并在 P3 删除）；每空间一个实例，`init()` 幂等。
- `listAllWorkspaces()` 逻辑保留（扫描 `<userDir>/sessions/*`），但其中 `current: dir === this.workspaceId` 语义改为"是否为本 runtime 所属空间"；`GET /workspaces` 的 `current` 标记由 registry/请求参数决定（见 D9）。

#### 4.2.4 配置层

`ConfigLoader` / `ConfigWriter` 当前持有可变 `workspacePath`（`loader.ts:49-66`、`writer.ts:12-31`）：

- 方案：**每空间一个实例**（构造即定根，无 `setWorkspacePath`），由 `WorkspaceRuntime` 持有。成本仅为对象构造 + 路径拼接，可忽略。
- `.env` 加载（`loader.ts:21`）**保持用 `process.cwd()`**（应用自身资源）。

#### 4.2.5 技能层

`skillLoader` 现有 12 处 cwd 依赖（`handlers/skills.ts` 7 + `skill-command.ts` 5）。按 **D13（additive）** 分两侧处理：

- **serve 侧**（`handlers/skills.ts` 7 处）：改用**新增**的带根方法 `listAt(root)` / `reloadAt(root)` / `loadAt(root)` / `getWorkspaceDir(root)`；
- **CLI 侧**（`skill-command.ts` 5 处、`start.ts` 4 处、`session-command.ts` 1 处）：**保持无参调用不变**，无参版本内部默认 `process.cwd()`；
- 两级目录语义不变：`<root>/.loop-agent/skills`（工作空间层）+ `~/.loop-agent/skills`（全局层）；
- 验收要求（A7.2）：同一 root 下 `list()` 与 `listAt(root)` 结果必须一致。

**修正（D14）**：实施期核对源码后发现 `SkillLoader.scan(cwd)` / `reload(cwd)` / `getWorkspaceDir(cwd)` 本就是**必填 cwd 参数**且无无参版本（`src/skill/loader.ts:18/60/65`），CLI 侧传的正是 `process.cwd()`。因此实际**未新增 `listAt/reloadAt/loadAt/getWorkspaceDir(root)` 等方法**——只把 serve 侧 7 处 `process.cwd()` 换成 `rt.root`，签名零变更，additive 天然满足。A7.2 的对应表述修正为：同一 root 下 `scan(root)` 与 `scan(process.cwd())` 结果一致。（4.2.7 兼容表中 skillLoader 行的"新增 `listAt/reloadAt/loadAt`、serve 走 `*At`"表述同此修正——实际为同一签名直接传 `rt.root`。）

#### 4.2.6 记忆与实例池

- `getMemoryKit(root)` 已按 `workspaceId` memoized，**天然支持多空间并存**；`resetMemoryKitCache()` 不再于"切换"时调用（不存在切换），仅在关停/测试时清空。
- `AgentPool`：**每空间一池**。`initAgent` 钩子改为 `await getMemoryKit(rt.root)` + `attachMemory(kit, rt.root)`（在 runtime 构造时闭包绑定正确 root，而非 `process.cwd()`）。
- 并发总上限：`maxRuntimes × poolCapacity`（见 **D6**）。

#### 4.2.7 CLI 兼容层（P1 的硬约束，见 **D13**）

CLI 与 serve 的差异必须先讲清（对应 1.2 #14/#15）：

| 维度 | CLI（`src/cli/start.ts` + `src/commands/*`） | serve（`src/api/*`） |
| --- | --- | --- |
| 空间数量 | **恒为 1**（启动目录） | 多空间 |
| `process.chdir` | **从不调用**（0 处） | 现依赖 `switchWorkspace` |
| `AgentPool` | **不使用**（`react-agent.ts` 导出 `agent` 单例） | 使用 |
| 单例消费 | **重度**：`CommandContext` 直接持有 6 个单例 | 经 `HandlerContext` 注入 |

结论：**CLI 不需要"支持多空间"，只需要"改造后仍能编译且行为不变"**。因此 P1 改造必须遵守 **additive（只增不改）** 原则：

| 被改对象 | ❌ 禁止（会打穿 CLI） | ✅ 采用（CLI 零改动） |
| --- | --- | --- |
| `configLoader` / `configWriter` | 删除 `config/index.ts` 的单例导出、强制每次传 root | **保留单例导出**，语义固定为"启动目录空间"；新增 `registry.get(root).configLoader` 供 serve 用。CLI 的 `ctx` 构造与 21+7 处 `ctx.configLoader` 调用**不动** |
| `skillLoader` | 把 `list()/reload()/load()` 改成**必填** root 参数 | **保留无参版本**（内部默认 `process.cwd()`），**新增** `listAt(root)`/`reloadAt(root)`/`loadAt(root)`。serve 走 `*At`，CLI 走无参 → 10 处调用零改动 |
| `ToolContext.workspaceRoot` | 改为**必填** | **保持 optional**，未传时由 `currentWorkspaceRoot()` 兜底 `process.cwd()`。CLI 不注入也天然正确（CLI 的 cwd 就是工作空间） |
| `react-agent` 的 `agent` 单例 | 改为必须注入 root 才能构造 | 构造保持"未注入 → `process.cwd()`"；serve 侧经 `initAgent` 注入 `rt.root`，CLI 单例不受影响 |
| `initAgentMemory()` | 改为必填 root | 加**可选** `root` 参数，缺省 `process.cwd()`（CLI `start.ts:150` 不传，serve 传入） |
| `SessionStore.rebindWorkspace()` | 立即删除 | 标注 `@deprecated`，**P3 才删**；CLI 本就只 `new SessionStore(process.cwd())`（`start.ts:99-102`），不受影响 |

**双语义共存的合法性**：P1 后进程内会同时存在"显式传根（serve）"与"隐式 cwd（CLI）"两套取值方式，看似不一致，但二者**不会同时作用于同一次请求**：CLI 进程内从不出现 chdir，cwd 恒等于唯一空间，隐式取值 100% 正确；serve 进程的所有入口都显式注入，隐式通道仅作兜底。因此无需为 CLI 引入 registry。

**CLI 回归验证清单**（P1 必须逐项过）：

1. `loop-agent` 启动 → 横幅正确（`configLoader.load()`、`skillLoader.list()`、`registry.list()`）；
2. `/config get|set|delete`（21 处 `ctx.configLoader` + 7 处 `ctx.configWriter` 的代表路径）；
3. `/skill list|show|upload|remove`（10 处无参 `skillLoader` 调用）与 Tab 补全；
4. `/session list|load|delete` + Tab 补全（`sessionStore` 2 处）；
5. `/model`、`/tools`、`/mcp`、`/memory`、`/vision`、`/doctor`、`/upload`、`/setup` 各一次冒烟；
6. 普通对话 `agent.run()`：确认 `commandRun` 的 cwd 仍是启动目录、`fileWrite` 落点不变；
7. 退出时的 Dreaming 与 `mcpManager.disconnectAll()` 正常。


### 4.3 P2：调度放开

1. **互斥粒度**：`hasInFlight()` → 每 runtime 的 `sessions.hasInFlight()`（因为 `SessionManager` 已按空间分例，天然隔离）。全局 `hasInFlight()` 删除。
2. **sessionId 空间命名空间（G3，见 D5）**：
   - 推荐 **A：新 id 带空间片段** —— `sess_<wsId8>_<YYYYMMDD_HHMMSS>`。新老 id 共存（老 id 无 `wsId8` 段，解析时按"无段=兼容模式，走全局唯一假设"）。
   - 理由：`RunHub.runs`、`SessionManager.sessions`、前端 `chat-stream` 的 `states`、路由 `/sessions/:id` 全以 id 为键，只要**保证新建 id 全局唯一**即可全部沿用，无需改路由结构（改动面最小）。
   - 存量风险：历史数据中"两空间同秒创建"的撞名概率极低，启动扫描发现重复 id 时记 warning 并提供手工处理指引。
3. **`switchWorkspace` 退化**：仅刷新"当前空间指针"（供兼容旧路由/旧前端），不再 chdir、不再 `pool.reset()`、不再清 kit。
4. **`GET /sessions/:id` 自动切换移除**：跨空间会话直接按 id 定位其归属 runtime 并读取，**不再改变当前空间指针**（这正是"并行"的意义）。`messages.ts` 的兜底切换同步删除，改为"按 id 定位归属空间后直接在该空间执行"。

## 七、需要确认的决策点

| 编号 | 决策 | 建议 | 备选与不选理由 |
| --- | --- | --- | --- |
| **D1** | `WorkspaceRuntime` 回收策略 | **B：LRU 限量（默认 4 个 runtime）**，空闲超 30min 释放 | A 常驻：空间越多内存/句柄越多且无上界；C 仅空闲释放不设上限：仍无上界 |
| **D2** | 路径归一化与存量兼容 | **A：不改 `workspaceId` 公式，所有入口统一 `canonicalWorkspacePath()`（含 Windows `realpath` 取真实大小写）** | B 改公式并迁移目录：存量会话需 rename，失败即丢数据；C 双读新旧 id：复杂度高、长期技术债 |
| **D3** | 根目录传递方式 | **C：显式 `ToolContext.workspaceRoot` 为主 + `AsyncLocalStorage` 兜底**，不一致时以显式为准并告警 | A 纯显式：33 处逐一改，漏改静默错位；B 纯 ALS：隐式难排查、单测须包 `run()` |
| **D4** | `AgentPool` 组织 | **A：每空间一池**（`initAgent` 闭包绑定该空间 root） | B 共享单池：`initAgent` 是池级固定钩子（`bootstrap.ts:38-41`），无法按会话换根 → 必须改造钩子签名，收益低 |
| **D5** | 跨空间 `sessionId` 消歧 | **A：新 id 加空间片段 `sess_<wsId8>_<ts>`**，老 id 共存；启动扫描重复 id 告警 | B 全量引入 `/workspaces/:wsId/sessions/:id` 路由：契约大改、前端全动；C 只靠"同秒不可能"：跨空间并行下恰恰很可能 |
| **D6** | 并发总上限 | **`maxRuntimes(4) × poolCapacity(4)`，并设全局信号量上限 8** | 不设全局上限：多空间同时跑会打爆 API 限速与内存 |
| **D7** | 配置层实现 | **A：每空间一个 `ConfigLoader/Writer` 实例（构造定根，废弃 `setWorkspacePath`）** | B 单实例 + 每次传 root：少一处缓存，但需改所有调用点签名，且易忘传 |
| **D8** | 记忆隔离度 | **A：L1/L2/L3 全部按空间隔离**（kit 已按 `workspaceId` memoized，现成能力） | B 仅 L1 隔离、L2/L3 共享：跨项目记忆串味，且共享索引文件存在写冲突（`memory-kit.ts:46-51` 已踩过） |
| **D9** | "当前工作空间"概念去留 | **B：退化为"最近使用空间"排序提示，不再作为全局状态** | A 保留 `current` 徽标：与并行语义冲突（多个空间同时在跑，谁是当前？）；C 完全删除：侧栏分组失去锚点 |
| **D10** | 跨空间会话是否可续聊 | **A：可以**（这正是并行的意义，`foreignActive` 撤除） | B 仍只读：并行无收益，方案失去意义 |
| **D11** | CLI 单空间模式 | **A：保持现状**（`cli/start.ts` 仍以启动目录为唯一空间，只是不再 chdir） | B 同步支持多空间：CLI 交互无"空间"概念，收益低 |
| **D12** | 是否与"移除 WebUI 工作空间切换逻辑"合并推进 | **B：分开推进**，本方案只做并行能力；UI 是否保留切换入口由该独立议题决定（本方案为其提供前提） | A 合并：两议题结论互相牵制，任一未定则整体阻塞 |
| **D13** | **CLI 兼容策略（P1 改造的 API 形态）** | **A：additive 只增不改**——保留 `configLoader/configWriter/skillLoader` 单例导出与无参方法（语义固定为"启动目录空间"），serve 侧改用 `registry.get(root)` 与新增的 `listAt(root)` 等带根方法；`ToolContext.workspaceRoot` 保持 optional | B 统一改造为"必填 root"：API 更纯粹，但打穿 CLI 约 42 处调用点（21+7+10+2+2）且使 CLI 必须引入 registry；C 为 CLI 单独维护一套 loader：两份实现分叉，长期维护成本更高 |

## 十一、验收标准

- **A1** 两空间可同时运行并各自流式，事件不串、`/workspaces` 的 `running` 各自正确。
- **A2** A 空间运行中可在 B 空间新建/切换/删除会话，**不再出现 `busy`**。
- **A3** 两空间 `commandRun` 的实际 cwd 与文件写入落点均正确（人工以 `cd`/绝对路径断言）。
- **A4** 代码中 `process.chdir` **零出现**；`process.cwd()` 仅剩 `static.ts` 与 `.env` 两处（附注释）。
- **A5** 同一目录的不同书写形式解析出同一 `workspaceId`，存量会话目录**未迁移即可见**。
- **A6** 跨空间并行创建的会话 `sessionId` 不重复。
- **A7** CLI 单空间模式行为不回退（按 4.2.7 七项清单逐项验证：横幅、`/config`、`/skill`、`/session`、`/model` `/tools` `/mcp` `/memory` `/vision` `/doctor` `/upload` `/setup`、普通对话 cwd 与写入落点、退出 Dreaming）。
- **A7.1** CLI 代码**零改动**（`src/cli/**`、`src/commands/**` diff 为空）；`CommandContext` 类型签名不变。
- **A7.2** `skillLoader` 无参方法仍可用，且新增的 `*At(root)` 方法在 serve 侧生效；两者对同一 root 返回一致结果。
- **A8** `tsc --noEmit` 与 `vitest run` 全绿。

## 十二、参考（本方案阶段检索所得）

- Node.js 官方文档《Asynchronous context tracking》：`AsyncLocalStorage` 为推荐实现（性能与内存安全优化不显然可自行复刻），`run()`/`getStore()` 自 Node 16.4 稳定；官方适用场景列举含 **tenant metadata**；已知坑为"非原生 Promise / 旧式 callback API 导致上下文丢失"，排查方式为打 `getStore()` 日志定位首个 `undefined`。来源：<https://nodejs.org/api/async_context.html>
- 同主题工程实践文章指出：请求入口 `run()` 建立一次上下文，业务代码任意深度 `getStore()` 读取；适合 request id / tracing / **tenant metadata** / auth context，不宜承载业务状态。来源：<https://blog.openreplay.com/async-context-nodejs/>

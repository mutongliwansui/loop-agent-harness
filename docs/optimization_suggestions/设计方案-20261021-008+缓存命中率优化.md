## 一、背景与目标

### 1.1 需求来源

日常开发使用 glm-5.3-flash，`stats.ts` 口径（累计 `prompt_cache_hit_tokens / prompt_tokens`）的平均缓存命中率仅约 59%。DeepSeek 风格的缓存命中价约为未命中价的 1/50（V4-Flash 实测 hit $0.0028 vs miss $0.14），命中率每提升 20 个百分点，输入费用近似减半；同时首 token 延迟显著下降。目标：同一会话连续 10+ 轮工具调用场景下，平均命中率 ≥80%（或较 59% 基线提升 ≥20 个百分点），且压缩前后不出现连续多轮 0 命中。

### 1.2 缓存机制要点（联网检索结论，方案的技术依据）

来源：DeepSeek 官方文档《上下文硬盘缓存》（api-docs.deepseek.com/zh-cn/guides/kv_cache）及 2024-08-02 官方公告：

1. **命中条件**：只有从第 0 个 token 开始逐字节一致的前缀才算重复，「中间开始的重复不能被缓存命中」；遇到首个不匹配 token 起即开始未命中。一致范围包括 system prompt、历史 messages、role 顺序、空白与 JSON 序列化形式。
2. **落盘时机**：请求的「用户输入结束位置」与「模型输出结束位置」各产生一个缓存前缀单元；系统还会做公共前缀检测落盘与固定 token 间隔落盘。缓存构建秒级完成，TTL 数小时到数天，best-effort 不保证 100%。
3. **存储粒度**：以 64 tokens 为存储单元（实测 V4 实践中 ~256 token 块粒度、~1024 token 以上前缀才稳定命中）；前缀中段一个字节变化，会使该变化点之后的整段缓存失效，变化点之前的部分仍可命中。
4. **多轮对话天然受益**：第 N 轮请求 = 第 N-1 轮完整请求 + 新增内容，前缀完全匹配上一轮的「输出结束位置」单元，理论命中率为「上轮全量 / 本轮全量」。

推论：**Agent 多轮工具调用链路本应拿到极高命中率（工具链越长越高）**。当前 59% 说明存在系统性前缀污染——只要污染点之前的段落足够长，命中率就趋近于「污染点前长度 / 全量长度」。

### 1.3 关键判定：为什么刚好是 ~59%

污染源在每轮 LLM 调用视图的**最后一条 user 消息内部**（见 2.2 根因①）。消息序列为：

```
[system] → [user(含L2注入)] → [assistant+tool_calls] → [tool] → [tool] → ...
```

第 i+1 轮调用时，第 i 轮的全部消息都在新请求的前缀里；但 user(含L2注入) 的 content 每轮都可能变化，于是「该 user 消息之后的所有 tool/assistant 消息」全部 miss。命中率近似 = user 消息及之前部分 / 全量 prompt。**工具链越长、tool 消息占比越高，污染造成的损失越大**——这正是 Agent 场景命中率被压低的核心机制。

## 二、现状链路与根因分析（逐条代码走读）

### 2.0 调用链概览

```
run() 每轮迭代
  ├─ [压缩检查] WorkingMemory.planCompaction / preCompactionFlush / compact   ← 根因④
  ├─ [组装视图] ContextAssembler.assemble()                                   ← 根因①②③
  │     ├─ curated.buildSystemPrompt()   每轮重读 3 个文件                     ← 根因②
  │     ├─ buildSystemPrompt(skills)     与 run() 首轮参数不一致               ← 根因③
  │     └─ episodic.search()             每轮检索，结果写进最后一条 user 消息   ← 根因①
  ├─ [LLM 调用] streamLLM(llmMessages, openaiTools)                           ← 根因⑤
  └─ [记忆写入] ToolMemoryCallback.log()  每个工具结果写 L2（scope:session）
        └─ 下一轮 assemble() 检索可能召回本轮新条目 → 加剧根因①
```

### 2.1 根因清单

### 2.2 关键代码事实（方案依据）

- `assemble()` 注入点：`rawMessages[lastUserIdx] = { ...lastUser, content: withMemorySection(memoryBlock, stripMemorySection(lastUser.content)) }`——**只改 LLM 视图（llmMessages），不回写 messages/transcript**（react-agent.ts L745-747 注释明确）。因此落盘历史是干净的，污染只发生在「发给 LLM 的请求序列」里。
- `withMemorySection` 前缀有固定哨兵头尾（`memory-section.ts`），格式稳定；不稳定的是 memoryBlock 内容本身（检索结果集）。
- `episodic.search()` 已过滤 `tag: compaction` 条目（episodic.ts L428-430），但**不过滤 `tag: tool` / `tag: final_answer`**——同 run 写入的条目下一轮就能被召回。
- `safeSearch()` 有 500ms 超时兜底，超时返回 `[]` → memoryBlock 为空 → user 消息恢复原始 content。**这是隐性前缀翻转源**：同一 user 消息在第 i 轮带注入、第 i+1 轮检索超时变干净（或反之）。
- 工具 schema `registry.toOpenAITools()` 在 run() 开始时生成一次（L466），单 run 内稳定 ✅；但多轮 run 之间若有 MCP 连接状态变化，tools 参数变化也会 miss（tools 参数不属于 messages 前缀但参与请求序列）。本方案不处理该场景（MCP 配置 run 间不变化，风险低）。

## 三、目标架构

```
                     run() 开始
                         │
              ┌──────────▼──────────┐
              │ ① system prompt 单次构建并冻结（run 级）           │
              │   base + curated(hash 校验) + skills 快照         │
              └──────────┬──────────┘
                         │
   每轮迭代               │
  ┌──────────────────────▼───────────────────────────┐
  │ L1 压缩检查（现有逻辑保留）                          │
  │   └─ 触发时：丢弃式压缩（一次性损失，可接受）          │
  ├──────────────────────────────────────────────────┤
  │ L2 检索：run 级缓存（②）                            │
  │   hit  → 复用首轮 memoryBlock（字节级稳定）           │
  │   miss→ 检索一次并缓存                               │
  ├──────────────────────────────────────────────────┤
  │ 组装视图：注入点不变（最后一条 user 消息）             │
  │   memoryBlock 稳定 → 该消息 content 逐轮稳定          │
  │   → 其后 tool/assistant 前缀可跨轮命中                │
  ├──────────────────────────────────────────────────┤
  │ LLM 调用（现有 streamLLM 不动）                      │
  └──────────────────────────────────────────────────┘
```

核心思想：**把「随时间漂移的内容」收敛为「run 级稳定」**——同一 run 内 system、memoryBlock、消息历史形态全部逐轮稳定，只有新增消息追加在尾部，前缀命中率即可逼近理论上限。

## 四、详细设计（改造项 R1~R5 与决策点 D1~D8）

### R1｜L2 检索结果 run 级缓存（对应根因①，核心改造）

- `ContextAssembler` 新增实例字段 `private runCache: { userMessage: string; sessionId: string | null; result: string } | null`。
- `assemble()` 入口判断：`userMessage` 与 `sessionId` 均与缓存一致 → 直接复用缓存的 memoryBlock（**跳过检索，含超时翻转隐患一并消除**）；否则执行检索并回写缓存。
- 注入位置不变（最后一条真实 user 消息，`withMemorySection` 拼接），消息 content 在同一 run 内字节级稳定。
- 缓存生命周期 = agent 实例生命周期（全局单例），key 含 sessionId 防串会话；新 run 的 userMessage 必然不同，天然失效，**无需显式 invalidate**。
- 兼容性：ToolMemoryCallback 继续每轮写 L2 不变——只是本 run 检索结果冻结，新条目留给后续 run 检索（下一个 run 的 userMessage 不同，语义上「本轮工具产生的记忆对本轮冻结、对下轮可见」，符合记忆语义）。

### R2｜L3 curated 内容 hash 缓存（对应根因②）

- `CuratedMemory` 新增 `buildSystemPromptCached(): Promise<string>`：按 key 记录 `{ mtimeMs, size, hash, prompt }`；文件 mtime+size 未变直接返回缓存 prompt。
- 变化时重读+重算并更新缓存。mtime 粒度风险（1s 内连续写入）由 run 级冻结（R4）兜底：system 在 run 边界确定一次，run 中途不再读。
- 落盘消息不含 curated 内容 → 无持久化兼容问题。

### R3｜system prompt 统一构建（对应根因③）

- `ContextAssembler` 新增可选构造参数 `buildSystem: () => string`（或 options 传入已构建的 systemPrompt 字符串）。
- `react-agent.run()` 把首轮已构建的 `systemPrompt`（`buildSystemPrompt(skills, wsRoot, cfg.vision.enabled)` 的产物，含 `cfg.agent.systemPrompt` 覆盖逻辑）传给 assemble；assemble 内 `basePrompt` 改为直接使用传入值。
- **自愈**：run() 首轮的 `llmMessages` 初始视图直接就是 `[{ role:'system', content: systemPrompt }, ...]`；开启记忆时首轮也会走 assemble 覆盖 system——统一后两处产物字节级一致，首轮之后不再变化。
- `buildSystemPrompt` 函数签名与既有调用方不变；`ContextAssembler` 构造函数新增可选参数，默认值保持旧行为（既有单测兼容）。

### R4｜system 与 memoryBlock 的 run 级冻结（防 run 中途漂移，组合 R1/R2）

- run() 内每轮 assemble 传入的 `skills` 改为 run 开始时的快照（现状：L436 只在 run 开始 scan 一次，已满足 ✅，本项只是显式约定写入任务文档，防回归）。
- systemPrompt 与 memoryBlock 均为 run 级常量后，「run 中途 Dreaming/工具改记忆文件」不再影响本次 run 的请求序列。

### R5｜压缩回稳与可观测性（对应根因④⑤）

- **压缩后稳定窗口**：`compact()` 后的下一迭代起，连续 N 次（N=3）跳过压缩检查的重复触发判定已由 `_lastContextTokens` 回写保证（现有逻辑 ✅），本项只补：压缩发生后在 debug 日志输出「压缩后 memoryBlock 是否命中 R1 缓存」，确认无连锁失效。
- **repairMessageSequence 零改动承诺**：现有实现对无损坏序列返回原引用（L97 `return ... : messages`），不破坏前缀；任务中补单测锁定「无损坏输入 → 返回同一引用」。
- **大输出治理（P2 可选）**：`commandRun` 非后台模式输出超过阈值（如 8KB）时只回传头部 + 尾部（后台模式已有 tail 语义），fileRead 已有截断提示 ✅；目的为降低每轮新增 token 占比、推迟压缩触发。
- **统计增强（P1）**：`stats.ts` 的 `buildLLMStatsSummary` 增加字段 `firstIterationHitRate`（首轮命中率，含 system/工具 schema 的冷启动 miss）与 `subsequentIterationsHitRate`（第 2 轮起命中率）——后者是本优化效果的真实指标；`onLLMStatsSummary` 渲染行同步展示两口径。

### 决策点清单（D1~D8）

| # | 决策点 | 结论（待确认） | 取舍与被否决项 |
|---|---|---|---|
| D1 | memoryBlock 注入位置 | **维持「最后一条 user 消息」** | 否决「移到 system 内独立段」：system 在最前，检索结果一变则其后全部 miss，比现状更差；否决「独立 assistant 消息插在历史中间/尾部」：改消息序列结构，落盘/恢复/去重全链路要跟着改，收益不明确 |
| D2 | L2 检索冻结粒度 | **run 级**（同 userMessage + sessionId 即复用） | 否决「会话级永久缓存」：长会话中新记忆永不召回；否决「每轮重算」：即现状，是命中率低的主因 |
| D3 | curated 缓存失效策略 | **mtime+size 短路，hash 兜底** | 否决「纯定时 TTL」：TTL 内文件变化感知不到；mtime 粒度风险由 R4 的 run 级冻结兜底 |
| D4 | system 构建统一方向 | **assemble 复用 run() 首轮产物** | 否决「assemble 内补齐 workspaceDir/visionEnabled 参数独立构建」：两处独立构建永远有漂移风险，单一来源才彻底 |
| D5 | `cfg.agent.systemPrompt` 自定义覆盖 | **保持现状语义**（run() L437 的 `??` 分支优先） | assemble 只复用最终产物，不感知配置细节；自定义 prompt 用户自行保证稳定性 |
| D6 | 检索超时翻转 | **随 R1 自然消除**（冻结后不再每轮重检索） | 否决「超时重试」：加重延迟，且冻结后该路径不再触发 |
| D7 | 大输出治理 | **列为 P2 可选项，默认不做**（本轮不动工具层） | 理由：R1~R4 预期已把命中率拉到目标；先量化验证，不够再做。避免一次改动铺得太宽 |
| D8 | 验收指标口径 | **以「第 2 轮起命中率 ≥80%」为主指标，整体均值 ≥70% 为辅**；较 59% 基线提升 ≥20 个百分点 | 理由：首轮（冷启动）必然 miss，混入整体均值会低估优化效果；两口径都记录，便于回归对比 |

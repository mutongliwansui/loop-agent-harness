# 设计方案：会话上下文三视图统一（压缩视图单一权威形态）

> 优化建议编号：20261019-001
> 提出时间：2026-10-19
> 方案状态：已实施（P0/P1/P2 全量交付，2026-10-19）
> 后续修订：2026-10-20 —— 移除 `ephemeral` 字段，摘要占位「LLM 可见、不展示、不落盘」的语义统一由 `is_show=false` 承载（详见 4.1 与第十三节）

---

## 一、背景与目标

### 1.1 需求来源

期望把会话内容按职责拆成三份可维护的数据：

1. **完整对话消息上下文**——用于前台展示；
2. **压缩后的消息 + 最近 N 轮对话**——用于恢复会话时重现内存 messages，叠加新用户消息后提供给大模型；
3. **内存里的 messages**——运行时给 LLM 的上下文。

### 1.2 现状结论（先回答"是不是这样"）

**方向正确，但现状不是三份独立数据**，而是「**内存 1 份 + 磁盘 3 类字段**」：

| 期望职责 | 现状载体 | 差距 |
|---|---|---|
| ① 完整上下文（展示） | 磁盘 `SessionData.messages`（全量字段），WebUI 详情直接读取 | 只存在于磁盘；内存无全量副本（且头部丢失 bug 修复前不完整） |
| ② 压缩视图（恢复/给 LLM） | **被拆成两套**：内存侧 `WorkingMemory.compact()`；磁盘侧 `SessionStore.getRestoreMessages()` | 两套参数独立（3 轮 vs 12 条）、形态不一致（有无摘要占位） |
| ③ 内存 messages | CLI `_chatHistory` / API `SessionEntry.history` | 它就是给 LLM 的上下文，压缩时被原地重写，**兼职了 ② 的内存形态** |

### 1.3 具体问题清单

1. **L1 压缩后 LLM 失忆**：`compact()` 丢弃头部轮次，flush 提取的笔记只写 L2 episodic，**不进消息流**；压缩后内存里只剩 system + 最近 3 轮，没有摘要占位。
2. **恢复视图与压缩结果不同形态**：`getRestoreMessages()` 注入 `[会话历史摘要]` user 消息 + `recentMessages`（≈12 条硬滑窗），与内存压缩结果不一致。
3. **摘要消息污染全量历史**：恢复注入的摘要 user 消息会被当作真实消息，经 `updateSession` 合并写盘，混入 ①。
4. **两套"最近 N 轮"参数独立**：L1 `keepRecentTurns=3` 轮 vs store `recentTurns×4=12` 条，且条数滑窗可能从轮中间截断（悬空 tool 隐患）。
5. **双恢复链靠约定对齐**：CLI `restoreSession`（含 `repairMessageSequence`）与 API `SessionManager.ensureEntry`（filter 掉 system）是两套独立实现。

### 1.4 目标

**让 ①②③ 各归其位：**

- ① 全量历史：磁盘唯一真源，保持"干净"（永不混入恢复占位消息），供前台展示。
- ② 压缩视图：由**一个纯函数** `buildCompactedView()` 生成，内存压缩与磁盘恢复**共用同一逻辑、同一参数、同一形态**。
- ③ 内存 messages：就是 ② 在内存中的实例，不再有独立形态。

核心原则：

- **单点定义**：压缩视图只允许一个生成器，禁止两处各写一套切轮逻辑。
- **占位可见但不可持久化**：摘要占位对 LLM 可见、不展示给用户；写盘时转写为「总结消息」，内容保留、前缀剥离。该语义统一由 `is_show=false` 承载，不再使用 `ephemeral`。
- **向后兼容**：不新增 SessionData 持久化字段，旧会话 JSON 无需迁移。
- **不改 L2/L3 的实现，但补交互防护**：L2/L3 的存储与检索策略保持现状；仅针对「L1 摘要占位与 L2 语义检索注入的交互」增加三处防护（见第六节），避免同一份信息被重复注入。

## 三、目标架构（改造后）

```
┌──────────────────────── 运行时内存 ────────────────────────┐
│                                                             │
│   内存 messages（③ 归位为 ② 的实例）                          │
│   = buildCompactedView() 产物                                │
│   [system, (摘要占位†), 最近 N 轮]                            │
│                        │                                    │
│                        └──────────────► 大模型（LLM）         │
└────────────────────────┬────────────────────────────────────┘
                         │ 每轮写盘（占位转写为总结消息，前缀剥离）
                         ▼
┌──────────────────── 磁盘 SessionStore · 唯一真源 ───────────────────┐
│                                                                     │
│   data.messages ① 全量历史（单一数组 · 唯一真源）                     │
│   · is_compact=true ：被折叠进摘要，不进入 LLM 上下文                 │
│   · is_show=false   ：不展示（system / 摘要总结消息†）                │
│         ▲                                                           │
└─────────┼───────────────────────────────────────────────────────────┘
          │
     WebUI 会话详情
                               getRestoreMessages()
                               = system + 全部 is_compact!==true 的消息
                               （含 is_show=false 的总结消息 → 即摘要占位）
                                       │
                                       └──► 恢复进内存（CLI / API 共用）
```

关键点：**压缩视图只有一个生成器** `buildCompactedView()`；磁盘只存一条「全量历史」真源，摘要以 `is_show=false` 的总结消息就地保存在其中，恢复视图由 `getRestoreMessages()` 从真源现场生成。

> † = `is_show=false` 的摘要占位：对 LLM 可见（内容保留），界面上不展示，落盘时前缀 `[历史摘要]` 被剥离后作为总结消息留存。

## 四、详细设计

### 4.1 消息标记：`is_compact` / `is_show` / `show_content`

位置：[src/types.ts](../../src/types.ts) L47-72

```ts
/** 会话持久化标记（仅存盘语义，调用 LLM 前由 LLMClient.normalizeMessages 统一剥离） */
export interface SessionMessageFlags {
  /** 是否已被压缩折叠进摘要；true=不参与 LLM 上下文，仅保留用于界面展示 */
  is_compact?: boolean;
  /** 是否在对话界面展示（缺省视为 true；system 与压缩总结消息为 false） */
  is_show?: boolean;
  /** 界面展示内容；缺省或为空时取 content（content 可能含记忆/摘要注入前缀） */
  show_content?: string;
}

export type ChatMessage =
  | ({ role: 'system'; content: string } & SessionMessageFlags)
  | ({ role: 'user'; content: string } & SessionMessageFlags)
  | ({ role: 'assistant'; content: string | null; tool_calls?: ToolCall[] } & SessionMessageFlags)
  | ({ role: 'tool'; tool_call_id: string; content: string } & SessionMessageFlags);
```

规则一句话：**LLM 能看见摘要占位的内容，磁盘落盘时把它转写为「总结消息」。**

- 摘要占位与已落盘的总结消息统一为「`role='user'` 且 `is_show=false`」这一形态，由 `isSummaryPlaceholder()`（内存）/ `isSummaryMessage()`（落盘）判定，**不再有独立的 `ephemeral` 字段**。
- `is_show=false` 同时承担「不展示给用户」与「这是摘要/总结」两重语义；system 消息天然 `is_show=false`。
- `is_compact=true` 表示该消息已被折叠进摘要、不进入 LLM 上下文（详见 4.5）。
- 不新增 SessionData 字段，旧 JSON 天然兼容；LLM 协议不受影响（标记字段在 `normalizeMessages` 中统一剥离，仅保留 `role`/`content`/`tool_calls`）。

> 修订说明：方案最初用 `ephemeral?: boolean` 标记占位；2026-10-20 收敛为 `is_show=false`，与会话「单一真源」的 `is_compact/is_show/show_content` 标记体系统一，避免两套标记并存。

### 4.2 统一生成器：`buildCompactedView()`

位置：`src/memory/working.ts`（与 `compact()` 同文件，便于替换）

```ts
export const SUMMARY_PLACEHOLDER_PREFIX = '[历史摘要]';

/** 摘要占位注入时的最大字符数（避免占位长期占用上下文 token） */
export const SUMMARY_PLACEHOLDER_MAX_CHARS = 500;

/** 判断是否为摘要占位/总结消息：role=user 且 is_show=false */
export function isSummaryPlaceholder(msg: ChatMessage): boolean {
  return msg.role === 'user' && msg.is_show === false;
}

export interface CompactedViewOptions {
  /** 保留最近多少轮（每轮 = 一条 user 及其后的 assistant/tool 消息） */
  keepRecentTurns: number;
  /** 头部被裁剪部分的摘要文本；为空则沿用输入中已有的占位文本 */
  summaryText?: string;
  /** 消息里没有 system 时的兜底 system prompt */
  systemPrompt?: string;
}

/**
 * 统一压缩视图：内存压缩与磁盘恢复共用同一形态。
 * 输出 = [system, (摘要占位 · is_show=false), 最近 N 轮]
 */
export function buildCompactedView(
  messages: ChatMessage[],
  opts: CompactedViewOptions,
): ChatMessage[] {
  const systemMsg =
    messages.find((m) => m.role === 'system') ??
    (opts.systemPrompt ? { role: 'system' as const, content: opts.systemPrompt } : undefined);

  // 1) 提取已有占位（本轮已压缩过）：重复压缩时若头部无新丢弃仍需保留占位，
  //    否则落盘链路（updateSession 靠 is_show=false 识别压缩轮次）会漏写总结消息
  const existingPlaceholder = messages.find((m) => isSummaryPlaceholder(m));

  // 清掉旧占位与旧总结消息（由本次新摘要取代），system 不参与切轮
  const nonSystem = messages.filter((m) => m.role !== 'system' && m.is_show !== false);

  // 2) 从后向前按 user 切轮，保留最近 N 轮
  const { turns, droppedCount } = pickRecentTurns(nonSystem, opts.keepRecentTurns);

  const result: ChatMessage[] = [];
  if (systemMsg) result.push(systemMsg);

  // 3) 注入摘要占位：有新摘要用新摘要；无新摘要但输入已有占位（重复压缩）时沿用原摘要文本
  let summary = opts.summaryText?.trim();
  if (!summary && existingPlaceholder) {
    const text = typeof existingPlaceholder.content === 'string' ? existingPlaceholder.content : '';
    summary = text.startsWith(SUMMARY_PLACEHOLDER_PREFIX)
      ? text.slice(SUMMARY_PLACEHOLDER_PREFIX.length).trim()
      : text.trim();
  }
  if ((droppedCount > 0 || existingPlaceholder) && summary) {
    result.push({
      role: 'user',
      content: `${SUMMARY_PLACEHOLDER_PREFIX} ${summary.slice(0, SUMMARY_PLACEHOLDER_MAX_CHARS)}`,
      is_show: false,
    });
  }

  result.push(...turns.flat());
  return result;
}

/** 从后向前按 user 切轮，返回保留的轮次与被丢弃的消息数 */
function pickRecentTurns(
  messages: ChatMessage[],
  keepRecentTurns: number,
): { turns: ChatMessage[][]; droppedCount: number } {
  const turns: ChatMessage[][] = [];
  let currentTurn: ChatMessage[] = [];
  for (let i = messages.length - 1; i >= 0; i--) {
    currentTurn.unshift(messages[i]);
    if (messages[i].role === 'user' && currentTurn.length > 1) {
      turns.unshift(currentTurn);
      currentTurn = [];
      if (turns.length >= keepRecentTurns) break;
    }
  }
  if (currentTurn.length > 0) turns.unshift(currentTurn);

  const keptCount = turns.reduce((n, t) => n + t.length, 0);
  return { turns, droppedCount: messages.length - keptCount };
}
```

`compact()` 退化为薄包装，保持对外签名兼容：

```ts
compact(messages: ChatMessage[], summaryText?: string): ChatMessage[] {
  return buildCompactedView(messages, {
    keepRecentTurns: this.config.keepRecentTurns,
    summaryText,
  });
}
```

> 注意：现有 `compact()` 在"循环自然结束时"会把头部残片 `unshift` 保留（头部可能以 tool 开头）。
> `pickRecentTurns` 延续该行为，避免丢消息；残片对应的 `droppedCount` 计算保持准确。

### 4.4 接入点二：恢复视图从单一真源生成

位置：[src/session/store.ts](../../src/session/store.ts) L310-322（上下文恢复视图）；展示层全量取用见同文件 `getAllAvailableMessages`（L300-302）

```ts
/**
 * 获取用于恢复对话的消息：system（当前配置重建） + 所有 is_compact!==true 的消息。
 * 被压缩折叠进摘要的历史（is_compact=true）不参与上下文；摘要本身是一条
 * is_show=false、is_compact=false 的 user 消息，会自然进入上下文。
 */
static getRestoreMessages(data: SessionData, systemPrompt?: string): ChatMessage[] {
  const result: ChatMessage[] = [];
  if (systemPrompt) result.push({ role: 'system', content: systemPrompt });
  for (const m of data.messages ?? []) {
    if (m.role === 'system') continue;
    if (m.is_compact === true) continue;
    result.push(m);
  }
  return result;
}
```

收益：

- CLI `restoreSession` 与 API `SessionManager.ensureEntry` 两条恢复链共用同一实现，无需各写一套；
- 恢复结果与"压缩后内存"形态一致：`system + 摘要总结消息 + 未折叠轮次`；
- 被折叠历史靠 `is_compact=true` 精确剔除，不再依赖条数滑窗，避免从轮中间截断（消除悬空 tool 隐患）。

> 修订说明：磁盘真源收敛为单一 `messages` 数组后，摘要不再单独存放（原 `lastSummary` / `recentMessages` 字段已废弃），恢复直接读取该数组中的 `is_show=false` 总结消息。

### 4.5 接入点三：写盘——占位转写为总结消息 + 压缩边界标记

位置：[src/session/store.ts](../../src/session/store.ts) `isSummaryMessage`（L44-46）、`createSession`（L168-201）、`updateSession`（L214-260）

```ts
/** 判断一条已落盘消息是否为「压缩总结消息」（role 非 system 且 is_show===false） */
function isSummaryMessage(m: ChatMessage): boolean {
  return m.role !== 'system' && m.is_show === false;
}
```

- **压缩轮次识别**：`updateSession` 用传入消息里是否存在 `isSummaryMessage` 判定本轮是否发生压缩。
- **压缩轮次落盘**：以全量历史重建压缩边界——边界前消息 `is_compact=true`（折叠进摘要，不进 LLM 上下文），边界后 `is_compact=false`；在边界处插入总结消息（`role='user'`、`is_show=false`、`is_compact=false`，内容已剥离 `[历史摘要]` 前缀）。旧总结消息被新总结取代，不堆积。
- **`createSession` 分支**：首轮即压缩（CLI `_currentSessionId=null`）时，同样把传入的摘要占位原位转写为总结消息，保证总结不丢失。

即：**占位只存在于内存/传给 LLM 的视图；磁盘上永远是「折叠标记 + 一条干净总结消息」。**

### 4.6 接入点四：基线剔除已折叠历史 + 展示层过滤

- [messages.ts](../../src/api/handlers/messages.ts)：持久化后 `entry.history = stored.filter((m) => m.role !== 'system' && m.is_compact !== true)`——摘要总结消息（`is_show=false`）保留，下一轮 LLM 继续看到摘要；已折叠历史（`is_compact=true`）被剔除，避免重复进入上下文与每轮重复压缩。

## 五、端到端例子

场景：10 轮对话（u1~u10），第 8 轮结束触发压缩（`keepRecentTurns = 3`），用户关页重开，继续第 9 轮。

### 5.1 改造前

```text

t8 磁盘全量   : [s, u1,a1 … u8,a8]                          ← 头部已修复，完整
重开恢复(API) : [假user"[会话历史摘要]…", …recent 12 条]      ← 另一套形态，可能截断轮

```

### 5.2 改造后


### 5.3 具体消息级示例

## 六、与 L2 语义检索注入的关系（防护设计）

### 6.1 为什么结构上不冲突

| 维度 | 说明 |
|---|---|
| 时序 | L1 压缩在前（[react-agent.ts](../../src/agent/react-agent.ts) L415-488），Context 组装在后（同文件 L512 起） |
| 产物归属 | 组装产物 `llmMessages` 只用于本次调用：不回写内存 messages、不落盘（同文件 L512 起的注释即该设计意图）；写盘走的是 `result.messages` |
| 位置 | L1 摘要占位在头部（紧跟 system）；L2 检索块拼接到**最后一条 user 消息**的 content 前面（[context.ts](../../src/memory/context.ts) L215-229） |
| 性质 | 两条通道都是「LLM 可见、磁盘不可见」，与摘要占位（`is_show=false`）的定位一致 |

结论：两者不会互相破坏数据；但同一份信息可能经两条通道重复注入，需要三处防护。

### 6.2 三处防护（纳入 P0）

**防护 A：压缩 flush 笔记的 L2 scope 由 `global` 改为 `session`**

- 现状：flush 笔记写入 L2 时用 `scope: 'global'`、`tag: 'compaction'`（[react-agent.ts](../../src/agent/react-agent.ts) L437-442）。
- 而 global 条目**对所有会话可见**（[episodic.ts](../../src/memory/episodic.ts) L427-436），`safeSearch` 第二轮还有全局兜底检索（[context.ts](../../src/memory/context.ts) L243-257）。
- 后果：同一份笔记经「L1 占位 + L2 检索」两条通道重复注入；跨会话时 A 会话的压缩笔记会在 B 会话被召回。
- 改法：写入时 `scope: 'session'`（笔记本就属会话内上下文语义）。

**防护 B：检索侧跳过 `tag: 'compaction'` 条目**

- 在 `filterEntries` / `isSectionVisible` 增加 tag 解析，命中 compaction 的条目直接不返回。
- 与 A 分工：A 解决跨会话泄漏，B 解决同会话重复。

**防护 C：查询增强拼接时过滤摘要占位**

- [context.ts](../../src/memory/context.ts) 取 `currentMessages` 里 user/assistant 消息拼成检索 query；占位 role 为 user，会被拼进去，摘要文本会污染 BM25/向量查询。
- 改法：`filter((m) => (m.role === 'user' || m.role === 'assistant') && m.is_show !== false)`。

### 6.3 副作用：token 阈值反馈环

压缩判定用上一轮**真实** `prompt_tokens`（[react-agent.ts](../../src/agent/react-agent.ts) L420-424、L568），该值**已包含 L2 注入**。占位再增加 token → 更早触发压缩 → 更多 compaction 笔记进 L2 → 召回更频繁 → 注入更多。

缓解：D3 摘要截断（500 字符）必须做；再叠加防护 A/B 削减重复召回。

### 6.4 明确不冲突的两点

- `repairMessageSequence` 对占位无影响：占位既非 tool 消息，也不带 `tool_calls`。
- 二次压缩时，旧占位会随 `preCompactionFlush` 一起送去提取，滚动摘要（rolling summary）是期望行为；但旧占位文本会被再次写入 L2，需靠防护 B 避免在检索侧堆积同义条目。

## 七、需要确认的决策点

| 编号 | 决策点 | 建议 | 备选 |
|---|---|---|---|
| D1 | 恢复裁剪单位改为"轮" | 采纳：按轮切语义正确，消除悬空 tool | 保留 12 条滑窗 |
| D2 | 占位（user）后紧跟轮首 user，出现连续两条 user | 采纳：OpenAI/DeepSeek/Anthropic 均接受 | 占位后补一条 `is_show=false` 的 assistant `"已了解历史上下文"`（provider 要求严格交替时） |
| D3 | 占位长度截断 | 采纳：摘要注入时截断 500 字符 | 不截断，完全透传 flush 文本 |
| D4 | 压缩 flush 笔记的 L2 scope 由 `global` 改为 `session` | 采纳：笔记属会话内上下文，避免跨会话泄漏与双通道重复 | 保留 `global`，仅靠防护 B 在检索侧过滤 |

> D2 建议在实现时留一个常量开关，若线上 provider 报严格交替错误，可一行切换为补 assistant 方案。

## 十、兼容性与风险

| 项 | 说明 | 处置 |
|---|---|---|
| 旧会话 JSON | 无新持久化字段，摘要占位仅在内存出现 | 天然兼容，无需迁移 |

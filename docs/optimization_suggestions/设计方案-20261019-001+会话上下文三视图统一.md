# 设计方案：会话上下文三视图统一（压缩视图单一权威形态）

> 优化建议编号：20261019-001
> 提出时间：2026-10-19
> 方案状态：已实施（P0/P1/P2 全量交付，2026-10-19）

---

## 一、背景与目标

### 1.1 需求来源

期望把会话内容按职责拆成三份可维护的数据：

1. **完整对话消息上下文**——用于前台展示；
2. **压缩后的消息 + 最近 N 轮对话**——用于恢复会话时重现内存 messages，叠加新用户消息后提供给大模型；
3. **内存里的 messages**——运行时给 LLM 的上下文。

### 1.2 现状结论（先回答"是不是这样"）

**方向正确，但现状不是三份独立数据**，而是「**内存 1 份 + 磁盘 3 类字段**」：

| 期望职责 | 现状载体 | 差距 |
|---|---|---|
| ① 完整上下文（展示） | 磁盘 `SessionData.messages`（全量字段），WebUI 详情直接读取 | 只存在于磁盘；内存无全量副本（且头部丢失 bug 修复前不完整） |
| ② 压缩视图（恢复/给 LLM） | **被拆成两套**：内存侧 `WorkingMemory.compact()`；磁盘侧 `SessionStore.getRestoreMessages()` | 两套参数独立（3 轮 vs 12 条）、形态不一致（有无摘要占位） |
| ③ 内存 messages | CLI `_chatHistory` / API `SessionEntry.history` | 它就是给 LLM 的上下文，压缩时被原地重写，**兼职了 ② 的内存形态** |

### 1.3 具体问题清单

1. **L1 压缩后 LLM 失忆**：`compact()` 丢弃头部轮次，flush 提取的笔记只写 L2 episodic，**不进消息流**；压缩后内存里只剩 system + 最近 3 轮，没有摘要占位。
2. **恢复视图与压缩结果不同形态**：`getRestoreMessages()` 注入 `[会话历史摘要]` user 消息 + `recentMessages`（≈12 条硬滑窗），与内存压缩结果不一致。
3. **摘要消息污染全量历史**：恢复注入的摘要 user 消息会被当作真实消息，经 `updateSession` 合并写盘，混入 ①。
4. **两套"最近 N 轮"参数独立**：L1 `keepRecentTurns=3` 轮 vs store `recentTurns×4=12` 条，且条数滑窗可能从轮中间截断（悬空 tool 隐患）。
5. **双恢复链靠约定对齐**：CLI `restoreSession`（含 `repairMessageSequence`）与 API `SessionManager.ensureEntry`（filter 掉 system）是两套独立实现。

### 1.4 目标

**让 ①②③ 各归其位：**

- ① 全量历史：磁盘唯一真源，保持"干净"（永不混入恢复占位消息），供前台展示。
- ② 压缩视图：由**一个纯函数** `buildCompactedView()` 生成，内存压缩与磁盘恢复**共用同一逻辑、同一参数、同一形态**。
- ③ 内存 messages：就是 ② 在内存中的实例，不再有独立形态。

核心原则：

- **单点定义**：压缩视图只允许一个生成器，禁止两处各写一套切轮逻辑。
- **占位可见但不可持久化**：摘要占位对 LLM 可见，写盘时过滤（`ephemeral` 标记）。
- **向后兼容**：不新增 SessionData 持久化字段，旧会话 JSON 无需迁移。
- **不改 L2/L3 的实现，但补交互防护**：L2/L3 的存储与检索策略保持现状；仅针对「L1 摘要占位与 L2 语义检索注入的交互」增加三处防护（见第六节），避免同一份信息被重复注入。

## 四、详细设计

### 4.1 类型扩展：`ephemeral` 占位标记

位置：[src/types.ts](../../src/types.ts) L50-54

```ts
export type ChatMessage =
  | { role: 'system'; content: string }
  | { role: 'user'; content: string; ephemeral?: boolean }  // 新增：恢复/压缩占位专用
  | { role: 'assistant'; content: string | null; tool_calls?: ToolCall[] }
  | { role: 'tool'; tool_call_id: string; content: string };
```

规则一句话：**LLM 能看见 `ephemeral`，磁盘永远看不见。**

选择 `ephemeral` 而不是新增自定义 role 的原因：

- 不改 role 取值，不影响 LLM 协议兼容；
- 不新增 SessionData 字段，旧 JSON 天然兼容；
- 语义明确，序列化时会被 `updateSession` 过滤。

### 4.2 统一生成器：`buildCompactedView()`

位置：`src/memory/working.ts`（与 `compact()` 同文件，便于替换）

```ts
export const SUMMARY_PLACEHOLDER_PREFIX = '[历史摘要]';

export interface CompactedViewOptions {
  /** 保留最近多少轮（每轮 = 一条 user 及其后的 assistant/tool 消息） */
  keepRecentTurns: number;
  /** 头部被裁剪部分的摘要文本；为空则不注入占位 */
  summaryText?: string;
  /** 消息里没有 system 时的兜底 system prompt */
  systemPrompt?: string;
}

/**
 * 统一压缩视图：内存压缩与磁盘恢复共用同一形态。
 * 输出 = [system, (摘要占位 · ephemeral), 最近 N 轮]
 */
export function buildCompactedView(
  messages: ChatMessage[],
  opts: CompactedViewOptions,
): ChatMessage[] {
  const systemMsg =
    messages.find((m) => m.role === 'system') ??
    (opts.systemPrompt ? { role: 'system' as const, content: opts.systemPrompt } : undefined);

  // 1) 清掉旧占位（多次压缩不堆积），system 不参与切轮
  const nonSystem = messages.filter(
    (m) => m.role !== 'system' && !(m.role === 'user' && m.ephemeral),
  );

  // 2) 从后向前按 user 切轮，保留最近 N 轮（复用现有切轮语义）
  const { turns, droppedCount } = pickRecentTurns(nonSystem, opts.keepRecentTurns);

  const result: ChatMessage[] = [];
  if (systemMsg) result.push(systemMsg);

  // 3) 头部确实被裁掉且有摘要 → 注入临时占位
  if (droppedCount > 0 && opts.summaryText) {
    result.push({
      role: 'user',
      content: `${SUMMARY_PLACEHOLDER_PREFIX} ${opts.summaryText}`,
      ephemeral: true,
    });
  }

  result.push(...turns.flat());
  return result;
}

/** 从后向前按 user 切轮，返回保留的轮次与被丢弃的消息数 */
function pickRecentTurns(
  messages: ChatMessage[],
  keepRecentTurns: number,
): { turns: ChatMessage[][]; droppedCount: number } {
  const turns: ChatMessage[][] = [];
  let current: ChatMessage[] = [];
  for (let i = messages.length - 1; i >= 0; i--) {
    current.unshift(messages[i]);
    if (messages[i].role === 'user' && current.length > 1) {
      turns.unshift(current);
      current = [];
      if (turns.length >= keepRecentTurns) break;
    }
  }
  if (current.length > 0) turns.unshift(current);

  const keptCount = turns.reduce((n, t) => n + t.length, 0);
  return { turns, droppedCount: messages.length - keptCount };
}
```

`compact()` 退化为薄包装，保持对外签名兼容：

```ts
compact(messages: ChatMessage[], summaryText?: string): ChatMessage[] {
  return buildCompactedView(messages, {
    keepRecentTurns: this.config.keepRecentTurns,
    summaryText,
  });
}
```

> 注意：现有 `compact()` 在"循环自然结束时"会把头部残片 `unshift` 保留（头部可能以 tool 开头）。
> `pickRecentTurns` 延续该行为，避免丢消息；残片对应的 `droppedCount` 计算保持准确。

### 4.4 接入点二：恢复视图复用同一生成器

位置：[src/session/store.ts](../../src/session/store.ts) L321-346

```ts
static getRestoreMessages(
  data: SessionData,
  systemPrompt?: string,
  opts?: { keepRecentTurns?: number },
): ChatMessage[] {
  // 原材料：优先全量历史；旧格式会话兜底 recentMessages
  const full = data.messages?.length ? data.messages : (data.recentMessages ?? []);

  return buildCompactedView(full, {
    systemPrompt,
    keepRecentTurns: opts?.keepRecentTurns ?? 3,
    summaryText: data.lastSummary || undefined,
  });
}
```

收益：

- CLI `restoreSession` 与 API `SessionManager.ensureEntry` 两条恢复链**自动统一**，无需各改一处；
- 恢复结果与"压缩后内存"形态一致；
- 按轮裁剪，不再从轮中间截断（消除悬空 tool 隐患）。

### 4.7 参数收敛（P1）

| 参数 | 现状 | 目标 |

## 六、与 L2 语义检索注入的关系（防护设计）

### 6.1 为什么结构上不冲突

| 维度 | 说明 |
|---|---|
| 时序 | L1 压缩在前（[react-agent.ts](../../src/agent/react-agent.ts) L423-493），Context 组装在后（同文件 L495-519） |
| 产物归属 | 组装产物 `llmMessages` 只用于本次调用：不回写内存 messages、不落盘（同文件 L496-497 的注释即该设计意图）；写盘走的是 `result.messages` |
| 位置 | L1 摘要占位在头部（紧跟 system）；L2 检索块拼接到**最后一条 user 消息**的 content 前面（[context.ts](../../src/memory/context.ts) L213-226） |
| 性质 | 两条通道都是「LLM 可见、磁盘不可见」，与 `ephemeral` 占位的定位一致 |

结论：两者不会互相破坏数据；但同一份信息可能经两条通道重复注入，需要三处防护。

### 6.2 三处防护（纳入 P0）

**防护 A：压缩 flush 笔记的 L2 scope 由 `global` 改为 `session`**

- 现状：flush 笔记写入 L2 时用 `scope: 'global'`、`tag: 'compaction'`（[react-agent.ts](../../src/agent/react-agent.ts) L441-445）。
- 而 global 条目**对所有会话可见**（[episodic.ts](../../src/memory/episodic.ts) L427-436），`safeSearch` 第二轮还有全局兜底检索（[context.ts](../../src/memory/context.ts) L243-257）。
- 后果：同一份笔记经「L1 占位 + L2 检索」两条通道重复注入；跨会话时 A 会话的压缩笔记会在 B 会话被召回。
- 改法：写入时 `scope: 'session'`（笔记本就属会话内上下文语义）。

**防护 B：检索侧跳过 `tag: 'compaction'` 条目**

- 在 `filterEntries` / `isSectionVisible` 增加 tag 解析，命中 compaction 的条目直接不返回。
- 与 A 分工：A 解决跨会话泄漏，B 解决同会话重复。

**防护 C：查询增强拼接时过滤 `ephemeral`**

- [context.ts](../../src/memory/context.ts) L163-171 取 `currentMessages` 里 user/assistant 消息拼成检索 query；占位 role 为 user，会被拼进去，摘要文本会污染 BM25/向量查询。
- 改法：`filter((m) => (m.role === 'user' || m.role === 'assistant') && !m.ephemeral)`。

### 6.3 副作用：token 阈值反馈环

压缩判定用上一轮**真实** `prompt_tokens`（[react-agent.ts](../../src/agent/react-agent.ts) L431-433、L535-537），该值**已包含 L2 注入**。占位再增加 token → 更早触发压缩 → 更多 compaction 笔记进 L2 → 召回更频繁 → 注入更多。

缓解：D3 摘要截断（500 字符）必须做；再叠加防护 A/B 削减重复召回。

### 6.4 明确不冲突的两点

- `repairMessageSequence` 对占位无影响：占位既非 tool 消息，也不带 `tool_calls`。
- 二次压缩时，旧占位会随 `preCompactionFlush` 一起送去提取，滚动摘要（rolling summary）是期望行为；但旧占位文本会被再次写入 L2，需靠防护 B 避免在检索侧堆积同义条目。

|---|---|---|---|
| D1 | 恢复裁剪单位改为"轮" | 采纳：按轮切语义正确，消除悬空 tool | 保留 12 条滑窗 |
| D2 | 占位（user）后紧跟轮首 user，出现连续两条 user | 采纳：OpenAI/DeepSeek/Anthropic 均接受 | 占位后补一条 ephemeral assistant `"已了解历史上下文"`（provider 要求严格交替时） |
| D3 | 占位长度截断 | 采纳：摘要注入时截断 500 字符 | 不截断，完全透传 flush 文本 |
| D4 | 压缩 flush 笔记的 L2 scope 由 `global` 改为 `session` | 采纳：笔记属会话内上下文，避免跨会话泄漏与双通道重复 | 保留 `global`，仅靠防护 B 在检索侧过滤 |

> D2 建议在实现时留一个常量开关，若线上 provider 报严格交替错误，可一行切换为补 assistant 方案。

## 十、兼容性与风险

| 项 | 说明 | 处置 |
|---|---|---|
| 旧会话 JSON | 无新持久化字段，`ephemeral` 仅在内存出现 | 天然兼容，无需迁移 |
| `ChatMessage` 类型扩展 | 可选字段，不破坏现有构造 | 编译期即暴露误用 |
| L2 内容重复 | flush 文本同时写 L2 与占位，可能经两条通道重复注入 | 已纳入 P0 防护 A/B（见第六节）；P1 可评估"占位改由 L2 检索结果供给"的替代方案 |
| L2 检索查询被污染 | 占位 role 为 user，会被拼进 query 增强的检索词 | 已纳入 P0 防护 C |
| 压缩笔记跨会话可见 | `scope: global` 使 A 会话的压缩笔记在 B 会话被召回 | 已纳入 P0 防护 A（D4） |
| 连续 user 消息 | 部分 provider 严格交替 | D2 常量开关兜底 |
| 摘要漂移 | 多次压缩后占位被替换为最新 flush 文本，早期摘要只在 `lastSummary`/L2 | 可接受；P1 可做摘要累积合并 |
| 磁盘 `recentMessages` 冗余 | 统一后它不再是恢复权威源 | 保留作为旧格式兜底与归档输入，P1 再评估是否裁剪职责 |

## 十二、验收标准

1. 压缩触发后，内存 messages 首部出现 `[历史摘要]` 占位（`ephemeral: true`），LLM 能回答"之前我们聊了什么"。
2. 会话重开后，`getRestoreMessages()` 产出与压缩后内存一致的形态（条数、角色序列、占位位置相同）。
3. 磁盘 `data.messages` 始终保持全量、干净：无 `ephemeral` 消息、无重复占位、头部不从首轮 user 丢失。
4. CLI 与 API 两条恢复链行为一致（含 `repairMessageSequence` 处理后无悬空 tool）。
5. 压缩笔记不再经两条通道重复注入：同会话后续提问时 L2 检索结果不含 `tag: compaction` 条目，且不跨会话被其他会话的压缩笔记召回；占位文本不进入检索 query。
6. 全量测试通过，`tsc --noEmit` 无错。

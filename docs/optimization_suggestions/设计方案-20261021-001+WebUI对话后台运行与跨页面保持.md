## 一、背景与目标

### 1.1 需求来源

对应 [优化建议.md](./优化建议.md) 中的 `20261021-001`，用户实际遇到两个现象：

1. **对话进行中无法切换到其他会话**：点击侧栏其他会话直接提示「正在生成回复，请先停止」；
2. **切到配置等页面后正在对话的会话「直接断连」**：回到聊天页看不到后续输出，感知为请求被中止。

期望效果：

- 对话流脱离视图生命周期，切换会话或切换到管理页都不影响后台运行；
- 仅「停止」按钮显式中止；
- 会话列表能看出哪个会话正在运行，非当前会话完成时能收到提醒；
- 页面刷新或重新进入会话时能续接正在生成的增量，而非只能看到最后一次落盘快照。

### 1.2 现状结论（先回答"是不是这样"）

**两个现象根因不同：一个是前端主动拦截，一个是前端状态随组件销毁；服务端 run 本身一直在跑。**

| 能力 | 现状 | 差距 |
|---|---|---|
| 运行中切换会话 | [selectSession](../../webui/src/views/ChatView.vue#L349-L355) 首行 `if (streaming.value) { showToast('正在生成回复，请先停止'); return; }` | 纯前端硬拦截，与后端能力无关 |
| 切页面后继续生成 | 流状态（`messages` / `streaming` / `abortCtrl`）是 **ChatView 组件实例级**（[ChatView.vue L91-129](../../webui/src/views/ChatView.vue#L91-L129)）；路由切走即卸载 | [onUnmounted](../../webui/src/views/ChatView.vue#L700-L704) **没有 abort**，fetch 仍在后台读流，但 `handleEvent` 写入的是已卸载组件的 `reactive` 对象，界面再也拿不到 |
| 返回会话后的内容 | `onMounted` → `selectSession(activeId)` → `GET /sessions/:id` 重新拉磁盘历史 | 只有节流快照（每 3 次迭代或 30s，见 [messages.ts L55-67](../../src/api/handlers/messages.ts#L55-L67)），最后一段必然缺失 |
| 刷新页面 | 同上，且内存中的流状态全部丢失 | 无法续接正在进行的 run |
| 运行状态可见性 | `GET /workspaces` 返回的会话项只有 `title/updatedAt/messageCount`（[sessions.ts L164-168](../../src/api/handlers/sessions.ts#L164-L168)） | 侧栏无法标记「运行中」 |
| 服务端事件去向 | 所有事件只写入**当次 HTTP 响应**（[messages.ts L75-83](../../src/api/handlers/messages.ts#L75-L83)），`clientGone` 后直接丢弃 | 无 run 注册表、无事件缓冲、无事件序号、无 attach 端点 |
| 断连后的 run | `clientGone` 只停止写流，`deps.runAgent` 继续执行并在结束时 `updateSession` 落盘 | **这正是可复用的基础行为**，不需要改 run 生命周期 |

补充约束（决定分期边界）：

- `deps.runAgent` 是 API Server 注入的**单个共享函数**（[server.ts](../../src/api/server.ts) `ApiServerDeps.runAgent`），agent 实例与 `_chatHistory` 共享，**当前不具备多会话并发运行能力**；
- `switchWorkspace` 要求全局无 in-flight（[sessions.ts L93-95](../../src/api/handlers/sessions.ts#L93-L95)、[L181-188](../../src/api/handlers/sessions.ts#L181-L188)）；
- 删除运行中会话、向运行中会话再次发消息均返回 `busy`（[messages.ts L39-41](../../src/api/handlers/messages.ts#L39-L41)、[sessions.ts L202-206](../../src/api/handlers/sessions.ts#L202-L206)）。

因此本方案的 P0 目标是「**单 run 后台保活 + 任意切换查看/续接**」，而不是「多会话同时运行」。

### 1.3 具体问题清单

1. **P-1 切换被拦截**：`selectSession` 把 `streaming` 当作全局互斥，用户被迫等待。
2. **P-2 跨页面状态丢失**：ChatView 卸载导致消息数组、`streaming`、`AbortController` 一起被丢弃；请求仍在但无人消费，用户感知为「断连」。
3. **P-3 回流只能看快照**：重进会话走 `GET /sessions/:id`，拿到的可能是 30s 前的节流落盘结果，末尾内容缺失。
4. **P-4 刷新无法续接**：服务端没有 run 标识与事件序号，客户端无从表达「我已经收到第 N 条」。
5. **P-5 运行态不可见**：侧栏无「运行中」标记，非当前会话完成时无任何提醒。
6. **P-6 停止语义不清**：前端 `abortCtrl.abort()` 只断前端读取，服务端照常跑完；提示语已说明，但 UI 上没有区分「已停止查看」与「已终止任务」。

### 1.4 目标

| 编号 | 目标 | 验收形态 |
|---|---|---|
| G1 | 流状态按 `sessionId` 全局持有 | 切换会话/切换页面后返回，消息区内容不丢、仍在增长 |
| G2 | 运行中可自由切换会话 | `selectSession` 无 `streaming` 拦截；仅另一会话发送消息时受服务端 `busy` 限制 |
| G3 | 服务端 run 可 attach、可续传 | 刷新页面或重进会话，能从 `cursor` 之后续接增量，最终与完整结果一致 |
| G4 | 运行态可见、完成可提醒 | 侧栏运行中标记；非当前会话完成 toast/未读点 |
| G5 | 不改变现有落盘与互斥语义 | 断开继续跑并落盘、`busy` 互斥、删除保护均保持 |

### 1.5 设计原则

- **单一数据源**：一个会话的展示消息只由 `chat-stream` 单例持有，ChatView 退化为纯视图。
- **状态按会话维度**：`messages` / `status` / `controller` / `cursor` 全部以 `sessionId` 为键，不再有全局 `streaming`。
- **服务端事件可重放**：run 拥有 `runId + seq`，事件先入缓冲再 fan-out，attach 即「补发 + 订阅」。
- **断开不终止**：延续 `clientGone` 语义——客户端只是订阅者，退订不影响 run。
- **不新增持久化字段**：运行态只在内存（RunHub），进程重启后统一回 `idle`，旧会话零迁移。
- **不引入新依赖**：前端继续用「fetch + ReadableStream 手工分帧」，不引 Pinia、不引 EventSource。

### 1.6 非目标

- 多会话**并发执行**（受共享 `runAgent` 限制，列入 P2 独立方案）；
- 服务端「真正取消 run」（`AbortSignal` 注入 Agent 执行链，列入 P2）；
- WebSocket / 其他传输替换；
- 会话内容的持久化结构变更。

### 2.1 前端：流状态绑定在视图组件上

```
                 App.vue（常驻）
        ┌──────────────────────────────────────┐
        │ 侧栏会话列表  chatStreaming(全局禁用)  │
        └───────────────┬──────────────────────┘
                        │ <component :is="currentView" />
        ┌───────────────▼──────────────────────┐
        │ ChatView.vue（#/chat 才挂载）          │
        │                                      │
        │  messages: Ref<ChatMsg[]>            │  ← 随组件创建/销毁
        │  streaming: Ref<boolean>             │
        │  abortCtrl: AbortController | null   │
        │                                      │
        │  sseFetch(POST /sessions/:id/messages)│
        └───────────────┬──────────────────────┘
                        │ 切到 #/config → 组件卸载
                        ▼
             fetch 还在读，handleEvent 写进已卸载组件的对象
                        │
                        ▼
                 界面不再更新（用户感知：断连）
```

关键代码事实：

- `messages` / `streaming` / `abortCtrl` 均为组件顶层变量，见 [ChatView.vue L91-129](../../webui/src/views/ChatView.vue#L91-L129)；
- `onUnmounted` 只做 `registerChatBridge(null)`、移除 keydown、取消 `scrollRaf`，**不 abort**（[L700-704](../../webui/src/views/ChatView.vue#L700-L704)）；
- 重新挂载时 `onMounted` 用 `GET /sessions/:id` 恢复（[L688-698](../../webui/src/views/ChatView.vue#L688-L698)）；
- `selectSession` 的 `streaming` 拦截见 [L349-355](../../webui/src/views/ChatView.vue#L349-L355)；
- 侧栏「新建对话」按 `chatStreaming` 禁用（[App.vue L52](../../webui/src/App.vue#L52)），该值由 ChatView `watchEffect` 单向写入（[ChatView.vue L676-678](../../webui/src/views/ChatView.vue#L676-L678)）。

### 2.2 服务端：事件只写给当次响应

```
POST /sessions/:id/messages
        │
        ▼
 entry.inFlight ── deps.runAgent(input, { events: [forwarder] })
        │                    │
        │                    ├─ onLLMStream  ─┐
        │                    ├─ onToolStart   ─┤ forwarder → sseFrame(res)
        │                    └─ ...           ─┘   （res 是当次请求的响应）
        │
        ├─ res.on('close') → clientGone = true → 事件被丢弃
        │
        └─ run 结束 → updateSession 落盘 → sseFrame('done') → res.end()
```

事实依据：

- `sseFrame` 只有 `event:` + `data:`，无 `id:`（[src/api/sse.ts L7-10](../../src/api/sse.ts#L7-L10)）；
- 事件写入闭包绑定单个 `res`，`clientGone` 后 `if (!clientGone)` 直接不写（[messages.ts L75-83](../../src/api/handlers/messages.ts#L75-L83)）；
- `SessionEntry` 只有 `history` 与 `inFlight`，没有 runId/事件缓冲（[session-manager.ts](../../src/api/session-manager.ts)）；
- 前端 `sseFetch` 仅支持 POST，且不解析 `id:` 行（[webui/src/api/sse.ts L13-30](../../webui/src/api/sse.ts#L13-L30)）。

**结论**：现状不是「不能后台跑」，而是「跑了但没人能再订阅它」。

核心变化：

1. 流状态从 ChatView **上移到 `chat-stream` 单例**，组件只做渲染；
2. 服务端新增 **RunHub** 作为 run 的事件总线与短期回放缓冲，HTTP 响应只是它的一个订阅者；
3. 新增 **attach 端点**，用 `cursor`（最后收到的 `seq`）表达续接位置，事件帧补 `id:` 便于统一解析。

## 四、详细设计

### 4.1 前端：`webui/src/chat-stream.ts`

#### 4.1.1 状态模型

```ts
export interface SessionStreamState {
  /** 该会话的展示消息（含乐观 user 消息与流式 assistant 占位） */
  messages: ChatMsg[];
  /** 是否正在接收流 */
  status: 'idle' | 'running';
  /** 服务端 run 标识（attach 时可校验是否同一个 run） */
  runId?: string;
  /** 已消费的最大事件序号，作为下次 attach 的 cursor */
  lastSeq: number;
  /** 当前 run 的 AbortController（仅「停止」使用） */
  controller?: AbortController;
  /** run 开始时间（侧栏运行中标记/耗时） */
  startedAt?: number;
  /** 非当前会话完成后的未读标记 */
  unread: boolean;
  /** 历史是否已从服务端加载过（避免重复拉取） */
  loaded: boolean;
}

const states = reactive(new Map<string, SessionStreamState>());
```

说明：

- 每个 state 内的 `messages` 为 `reactive` 数组，沿用现状「必须 reactive 才能流式累加渲染」的约定（[ChatView.vue L542-552](../../webui/src/views/ChatView.vue#L542-L552)）；
- `msgSeq` 从 ChatView 的模块变量迁入本模块，避免跨视图 ID 冲突；
- `ChatMsg` / `TextSeg` / `ToolSeg` / `LivePhase` / `handleEvent` 一并从 ChatView 迁出到本模块（或拆 `chat-events.ts`），ChatView 通过 import 复用。**这是本方案最大的纯搬运改动，逻辑本身不改。**

#### 4.1.2 对外 API

```ts
/** 供视图订阅：返回会话消息数组（无状态时返回空数组常量） */
export function messagesOf(sessionId: string): ChatMsg[];
/** 供侧栏订阅：该会话是否运行中 */
export function isRunning(sessionId: string): boolean;
/** 供侧栏/新建按钮：是否存在任意运行中的会话 */
export const anyRunning = computed(() => [...states.values()].some((s) => s.status === 'running'));

/** 首次进入/刷新：拉历史，如有运行中的 run 则自动 attach */
export function ensureLoaded(sessionId: string): Promise<void>;
/** 发送消息：内部创建 user + assistant 占位，POST messages，消费 SSE 直到 done/fatal */
export function send(sessionId: string, text: string, files?: string[]): Promise<void>;
/** 停止：仅中断前端订阅（服务端照常完成，语义与现状一致） */
export function stop(sessionId: string): void;
/** 续接：GET /sessions/:id/stream?cursor=lastSeq */
export function attach(sessionId: string): Promise<void>;
/** 视图可见时清除未读 */
export function markRead(sessionId: string): void;
/** 会话删除后清理 */
export function drop(sessionId: string): void;
/** 订阅 run 终态（供 ChatView 触发高亮/mermaid、滚动） */
export function onRunFinished(cb: (sessionId: string) => void): () => void;
```

`ensureLoaded` 的决策顺序：

```
有本地状态且 loaded=true ──► 直接返回（视图立即有内容）
        │
        └─► GET /sessions/:id（历史 + run 状态）
                 │
                 ├─ run=null     ──► 渲染历史，status=idle
                 └─ run=running  ──► 渲染历史 + 创建流式 assistant 占位
                                     attach(cursor=0)，从缓冲补发增量
```

> 刷新场景下 `lastSeq` 只能从 0 开始；缓冲若已溢出，服务端会下发 `reset`，前端改为「重拉历史 + 只渲染后续增量」（见 4.4）。

#### 4.1.3 ChatView 改造

| 现状 | 改造后 |
|---|---|
| `const messages = ref<ChatMsg[]>([])` | `const messages = computed(() => activeId.value ? messagesOf(activeId.value) : EMPTY)` |
| `const streaming = ref(false)` | `const streaming = computed(() => activeId.value ? isRunning(activeId.value) : false)` |
| `let abortCtrl` | 删除（由 `stop(sessionId)` 内部持有） |
| `selectSession` 拦截 `streaming` | **删除拦截**；仅 `activeId=id` + `ensureLoaded(id)` |
| `send()` 内自建占位并调用 `sseFetch` | 委托 `send(sessionId, text, files)`；输入框/上传清空仍在视图侧 |
| `handleEvent` 定义 | 迁至 chat-stream，ChatView 不再持有 |
| `onUnmounted` | 仅移除 keydown、取消 `scrollRaf`、`registerChatBridge(null)`；**对 run 无任何副作用** |
| `postRenderMsgs()` 在 finally 调用 | 改为订阅 `onRunFinished`：仅当 `sessionId === activeId` 且组件在场时执行高亮/mermaid |
| `watchEffect(chatStreaming = streaming)` | 删除；`chatStreaming` 改由 `anyRunning` 派生 |

滚动策略：`scrollBottom()` 只在 `activeId === 当前运行会话` 时由视图的 `watch(messages.length)` / `onRunFinished` 触发，避免用户在别的会话时产生无效滚动。

#### 4.1.4 侧栏与共享 store

- [sessions.ts](../../webui/src/sessions.ts) 新增派生状态（不重复存一份）：

```ts
export const runningIds = computed(() => new Set(
  workspaces.value.flatMap((w) => w.sessions.filter((s) => isRunning(s.id)).map((s) => s.id)),
));
export const chatStreaming = computed(() => anyRunning.value);
```

- [App.vue](../../webui/src/App.vue) 会话条目 `.sess` 内增加运行中样式（小圆点/呼吸动画）与未读点；`title` 提示「正在生成」。
- 非当前会话 `done` 时：`showToast('会话「xxx」已完成', 'success')` + `unread=true`；点击会话即 `markRead`。
- `clickSession` 不再依赖 ChatView 挂载：`activeId=id; location.hash='#/chat'`，ChatView 挂载后 `ensureLoaded` 即可。`registerChatBridge` 仅保留给「新建弹窗」（弹窗仍在 ChatView 内）。

> P0 保留「新建对话」按钮由 `chatStreaming` 禁用：当前服务端只能同时跑一个 run，新建后立即发送会遇到 `busy`。
> P1 已解禁该按钮（`chatStreaming` 一并删除）：新建本身不涉及 in-flight，发送时若其他会话在跑，以前端 `isRunning` 扫描给出带会话名的提示，服务端 `busy` 仍作兜底。

### 4.2 服务端：`src/api/run-hub.ts`

#### 4.2.1 数据结构

```ts
interface BufferedEvent {
  seq: number;          // 从 1 开始，单调递增
  event: string;        // start / llm_stream / tool_start / ... / done / fatal
  data: unknown;
}

interface RunState {
  runId: string;              // 随机 ID，用于 attach 校验与日志
  sessionId: string;
  seq: number;
  status: 'running' | 'done' | 'failed';
  startedAt: number;
  finishedAt?: number;
  buffer: BufferedEvent[];    // 环形：事件数 + 字节双上限
  bytes: number;
  droppedBefore: number;      // 已丢弃的最旧 seq（用于判断 cursor 是否过期）
  subscribers: Set<(ev: BufferedEvent) => void>;
  terminal?: { event: 'done' | 'fatal'; data: unknown };
}
```

容量参数（常量，便于测试覆盖）：

```ts
export const RUN_BUFFER_MAX_EVENTS = 2000;
export const RUN_BUFFER_MAX_BYTES = 2 * 1024 * 1024; // 2MB
export const RUN_RETAIN_AFTER_FINISH_MS = 60_000;    // 完成后保留 60s 供 attach 收尾
```

#### 4.2.2 接口

```ts
class RunHub {
  /** 新建 run；同一 session 已有 running 时返回 null（调用方仍以 entry.inFlight 为主判据） */
  start(sessionId: string): RunState | null;
  /** 追加事件：分配 seq → 入缓冲（必要时丢弃最旧）→ fan-out 给所有订阅者 */
  publish(sessionId: string, event: string, data: unknown): number;
  /** 终态：记录 terminal，通知订阅者后关闭订阅，保留元数据 60s 后清理 */
  finish(sessionId: string, status: 'done' | 'failed', terminal: { event: 'done' | 'fatal'; data: unknown }): void;
  /** 补发 seq>cursor 的事件并订阅后续；run 已结束则补发后返回 false（调用方关流） */
  subscribe(sessionId: string, cursor: number, write: (ev: BufferedEvent) => void): { unsubscribe: () => void; replayEnded: boolean };
  /** 运行态快照（GET /workspaces、GET /sessions/:id 使用） */
  snapshot(sessionId: string): { runId: string; status: 'running' | 'done' | 'failed'; startedAt: number } | null;
  isRunning(sessionId: string): boolean;
  /** cursor 是否已被丢弃（需要 reset） */
  isCursorStale(sessionId: string, cursor: number): boolean;
}
```

实现要点：

- **先入缓冲再 fan-out**：保证任何时刻 attach 的新订阅者拿到的 seq 与实时订阅者一致，不会漏帧；
- **fan-out 容错**：单个订阅者 `write` 抛错（socket 已断）时从 `subscribers` 移除，不影响其他订阅者与 run；
- **结束后保留**：`done`/`fatal` 也是普通事件入缓冲；`finish` 后新 attach 仍能 replay 完并收到终态，然后服务端主动 `res.end()`；
- **重启即清空**：RunHub 纯内存，进程重启后所有会话 `snapshot` 返回 `null`，前端按「无运行」回退拉历史。

#### 4.2.3 `sseFrame` 增加事件序号

```ts
/** SSE 帧写入：`id: <seq>\n` + `event: <type>\n` + `data: <JSON>\n\n` */
export function sseFrame(res: ServerResponse, event: string, data: unknown, id?: number): void {
  res.write(`${id != null ? `id: ${id}\n` : ''}event: ${event}\ndata: ${JSON.stringify(data)}\n\n`);
}
```

- 带 `id:` 后，浏览器原生 `EventSource` 也能在将来直接使用（当前仍用 fetch 以携带 Authorization）；
- 前端 `parseFrame` 增加 `id:` 解析，`SseEvent` 增加 `id?: number`。

#### 4.2.4 `POST /sessions/:id/messages` 改造

```ts
const run = runHub.start(id);            // 若为 null 仍按 entry.inFlight 抛 busy
const runOptions: AgentOptions = { ... };

if (stream) {
  res.writeHead(200, { 'Content-Type': 'text/event-stream; charset=utf-8', ... });
  let clientGone = false;
  res.on('close', () => { clientGone = true; });
  const forwarder = createSseForwarder((event, data) => {
    const seq = runHub.publish(id, event, data);       // ① 入缓冲 + fan-out
    if (!clientGone) sseFrame(res, event, data, seq);  // ② 当前响应只是订阅者之一
  });
  runOptions.events = [forwarder];
}
```

- `done` / `fatal` 也走 `publish`，随后 `runHub.finish(...)`，最后再 `res.end()`：
  - 现有实现中 `done` 是 handler 直接写的（[messages.ts L111-114](../../src/api/handlers/messages.ts#L111-L114)），改造后必须先 publish，保证 attach 端能收到终态；
  - `warning` 同理（现状 [L112](../../src/api/handlers/messages.ts#L112)）。
- `entry.inFlight` 与 `finally { entry.inFlight = null }` **保持不变**，互斥、删除保护、工作空间切换前置检查全部沿用。

### 4.3 新增端点：`GET /sessions/:id/stream?cursor=<seq>`

路由表新增一行（[router.ts L87-89](../../src/api/router.ts#L87-L89) 附近）：

```ts
{ method: 'GET', path: '/sessions/:id/stream', handler: (ctx, req, res, p) => handleAttachStream(ctx, req, res, p.id) },
```

行为：

| 条件 | 响应 |
|---|---|
| 会话不存在 | 404 `not_found` |
| 无运行中的 run（且无保留中的终态） | **204 No Content**（前端直接回退 `GET /sessions/:id` 拉历史） |
| 有 run / 有保留终态 | `200 text/event-stream`，先补发 `seq > cursor` 的事件，再订阅后续 |
| `cursor` 已被缓冲丢弃 | 先发 `reset` 事件（`{ reason:'buffer_overflow', oldestSeq }`），再补发当前缓冲全部事件 |
| run 已结束 | 补发完成后合成 `done`/`fatal`（若缓冲里已有则直接补发），`res.end()` |

注意事项：

- **不切换工作空间**：attach 是只读订阅，若会话属于其他空间，run 本来也不在该空间执行；此处不做 `switchWorkspace`，避免刷新页面时意外改变服务端 cwd。
- **鉴权**：沿用现有 token 校验中间件，无需新配置。
- **响应头**：与 `POST` 流一致（`Cache-Control: no-cache`、`Connection: keep-alive`），额外建议 `X-Accel-Buffering: no` 以防反代缓冲（可选）。
- **keep-alive**：run 可能长时间无事件（如长工具执行），每 15s 写一行 SSE 注释 `: ping\n\n`，避免代理超时断连；前端 `parseFrame` 无 `data:` 时返回 `null`，天然忽略。

### 4.4 前端 GET 流消费：`sseGet`

### 4.5 事件消费与消息合并规则

`chat-stream` 的 `handleEvent(ev, state, asst)` 延续现有 ChatView 的 15 种事件处理，仅补充：

| 事件 | 处理 |
|---|---|
| 任意事件带 `id` | `state.lastSeq = max(state.lastSeq, ev.id)` |
| `reset` | 丢弃当前流式 assistant 占位 → `GET /sessions/:id` 重拉历史 → 重新创建占位 → 继续消费后续事件（此时服务端会补发缓冲全部事件，`lastSeq` 重置为 0 后再累加） |
| `done` | 置 `status='idle'`、`asst.streaming=false`、`asst.live=null`、写 `meta`；`lastSeq` 保留；`loadSessions()` 刷新计数；非当前会话 → `unread=true` + toast |
| `fatal` | 标记 `failed` + `failedText`，`status='idle'` |
| `done`/`fatal` 后 | 关闭 attach 流（服务端会 `end`，前端 `reader` 自然结束） |

**避免重复渲染**的三条规则：

1. 同一会话同一时刻只允许一个 `attach`（`state.attaching` 布尔守卫），重复调用直接返回；
2. `send` 成功后记录 `runId`；attach 收到的事件若属于更早的 run（服务端返回的 `runId` 与本地不一致），先 `reset` 再消费；
3. `done` 后**不做全量重拉**（P0）：`done` 事件已含 `result`，且落盘刚完成；仅在用户重新进入该会话（`loaded=false`）时从磁盘拉取，避免流式结束后界面闪烁。P1 可评估静默重拉一次做一致性对齐。

### 4.6 运行时序

#### 场景 A：正常发送（停留在当前会话）

```
ChatView          chat-stream              POST /messages            RunHub
   │  send(text) ──► │                          │                     │
   │                 │ push(user, asst占位)      │                     │
   │                 │ status=running            │                     │
   │                 │──── sseFetch ────────────►│ start() ───────────►│
   │                 │                          │ events → publish ──►│ seq=1..n
   │                 │◄──── SSE(id:seq) ────────│◄── sseFrame ────────│
   │◄─ 响应式渲染 ───│ handleEvent 累加           │                     │
   │                 │                          │ done → publish ────►│ finish()
   │                 │◄──── done ───────────────│                     │
   │◄─ meta/高亮 ────│ status=idle               │                     │
```

#### 场景 B：运行中切到另一个会话（同页面）

```
点击侧栏 B
   │
   ├─ activeId = B（无 streaming 拦截）
   ├─ A 的 state 保持 status=running，SSE 读取继续进行
   ├─ ChatView 渲染 B：messagesOf(B)；未加载则 GET /sessions/B
   └─ 侧栏 A 显示「运行中」呼吸点
A 完成时：state(A).unread=true + toast；B 的界面不受影响
```

#### 场景 C：运行中切到配置页

```
ChatView 卸载
   │
   ├─ onUnmounted：只解绑 keydown/滚动（不再影响 run）
   ├─ chat-stream 仍持有 fetch reader 与 AbortController
   ├─ handleEvent 继续写入 state(A).messages
   └─ 返回 #/chat → messagesOf(A) 立即有完整内容（无需重拉）
```

#### 场景 D：刷新页面 / 重新进入运行中的会话

```
ensureLoaded(A)
   │
   ├─ GET /sessions/A ──► { messages(节流快照), run:{status:'running', runId} }
   ├─ 渲染历史 + 创建流式 assistant 占位
   ├─ attach(cursor=0) ──► GET /sessions/A/stream?cursor=0
   │        │
   │        ├─ 200：补发 seq=1..N（含已发生但未落盘的增量）→ 订阅后续
   │        ├─ reset（缓冲溢出）：重拉历史 + 置 cursor=oldestSeq-1 → 继续
   │        └─ 204：run 已结束/不存在 → 以磁盘历史为准
   └─ done 到达 → 与正常发送一致收尾
```

### 4.7 边界与异常

| 场景 | 行为 | 依据/处置 |
|---|---|---|
| 服务端进程重启 | RunHub 清空；attach 返回 204 | 前端回退磁盘历史；运行中内容可能缺失最后一次快照 |
| 事件缓冲溢出 | attach 时 `cursor < oldestSeq` | 服务端发 `reset`，前端重拉历史后继续 |
| 浏览器网络短暂断开 | fetch reader reject；`status` 置 `idle`，保留已收内容 | P0 不做自动重连；P1 可加一次 `attach` 重试 |
| 401 | 与现有 `sseFetch` 一致：清 token、弹登录 | 复用现有错误处理 |
| 多标签页 | 各自独立 RunHub 订阅者（服务端天然多订阅） | 前端状态不共享（P2 可用 BroadcastChannel 同步） |
| 跨工作空间会话 | attach 只读、不切空间 | 见 4.3 注意事项 |
| 删除运行中会话 | 仍 409 `busy` | 保持不变 |
| 运行中再发消息 | 仍 409 `busy` | 不变；P2 才考虑并发 |
| 停止按钮 | 只中断前端订阅，服务端照常完成并落盘 | 沿用现有提示「服务端将照常完成并保存」 |
| 运行中切换会话后点停止 | 侧栏不提供停止；只有当前会话视图有停止按钮 | P0 简化；P1 可在侧栏运行中条目提供停止 |
| run 完成后的 attach | 60s 内可 replay 终态；超时后 204 | 避免内存长期驻留 |

## 七、需要确认的决策点

| 编号 | 决策点 | 建议 | 备选 |
|---|---|---|---|
| D1 | P0 是否支持多会话并发运行 | **否**：保持单 run，只做「后台保活 + 任意切换查看」 | 同步改造 `runAgent` 为工厂（工作量大，风险高） |

| 侧栏运行中标记 | 仅运行会话显示呼吸点，完成后消失 |
| 删除运行中会话 | 提示「会话正在处理消息，暂不能删除」 |
| 跨工作空间会话 | 查看/attach 不改变服务端「当前」空间标记（与现有行为一致） |

### 8.3 回归

- `npx tsc --noEmit`；
- `npm --prefix webui run build`；
- 现有 API 用例：`api-endpoints` / `api-server` / `session-isolation`；
- 全量 `npx vitest run`。

## 九、兼容性与风险

| 项 | 说明 | 处置 |
|---|---|---|
| 旧会话数据 | 运行态只在内存，响应层派生 `running` / `run` | 零迁移 |
| `sseFrame` 签名 | 新增可选参数 `id?` | 现有调用不传即无变化 |
| 客户端解析 | 旧前端忽略 `id:` 行 | 向后兼容；前后端可分别发布 |
| 内存占用 | RunHub 按会话保留事件缓冲 | 双上限 + 完成后 60s 清理；会话删除时 `drop` |
| 长任务无事件 | 代理/浏览器可能超时断流 | 15s keep-alive 注释帧 |
| 断开后继续跑 | 与现状一致，但用户可能不知道任务仍在进行 | 侧栏运行中标记 + 完成后提醒（G4） |
| 单 run 限制 | 另一个会话发送仍 busy | P0 明确提示；并发能力列 P2 |
| 事件顺序 | 高并发 publish 均为同步调用 | Node 单线程内同步 `seq++`，天然有序 |
| 前后端版本不一致 | 新前端 + 旧服务端：attach 404 | `ensureLoaded` 捕获 404 后按 `run=null` 处理，退化为现状 |
| 刷新丢最后一次快照 | 服务端崩溃时内存事件丢失 | 现有节流落盘（3 迭代/30s）兜底 |

## 十一、验收标准

1. 对话进行中点击侧栏其他会话，**不再出现**「正在生成回复，请先停止」；原会话继续生成并在侧栏显示运行中标记。
2. 运行中切换到配置页停留 ≥10s 再返回聊天页，原会话消息区包含该期间产生的全部增量（无需刷新）。
3. 运行中刷新浏览器，重新进入该会话可自动续接增量，最终结果与 `sess_*.json` 落盘内容一致（无重复、无缺失）。
4. 完成后 60s 内重新进入会话（或刷新）仍能看到完整结果；超过 60s 从磁盘恢复同样完整。
5. 非当前会话完成时给出 toast/未读提示，点击后清除。
6. 停止按钮行为与现状一致：仅停止前端接收并提示「服务端将照常完成并保存」。
7. 现有互斥语义不变：另一会话发送仍返回 `busy`；删除运行中会话仍 409。
8. `npx tsc --noEmit`、`npm --prefix webui run build` 通过；全量测试通过。

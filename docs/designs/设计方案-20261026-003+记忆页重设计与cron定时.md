## 一、需求完善

### 1.1 原始诉求（用户原话拆解）

> 「目前是 timer 的方式，能不能改成 crontab 表达式；后续允许用户在记忆配置页面设置每天几点触发；最近触发的记录在记忆配置页面也能看到；按照我的需求重新设计下记忆的页面，出个原型和方案。」

四条独立诉求：

| # | 诉求 | 现状 |
| --- | --- | --- |
| ① | 定时机制从 timer 间隔改成 crontab 表达式 | `schedule.intervalHours = 24` + `startupDelayMin = 5`，语义是「启动后 5 分钟首轮，之后每 24h」 |
| ② | 记忆页能设置「每天几点触发」 | 记忆页那行是**只读** mono 文本；只能去「配置」页通用配置树改，且**改完要重启** |
| ③ | 记忆页能看到最近触发记录 | 只有一条 `lastRunAt` + `lastSummary`（最后一次），无列表、无耗时、无失败原因 |
| ④ | 重新设计记忆页 | 5 张卡片平铺，信息挤在一行文本里，无操作入口、无层级 |

### 1.2 完善后的需求描述

**目标用户**：长期用 WebUI（`--serve` 常驻）跑 Agent 的个人开发者。

**使用场景**：用户希望「每天凌晨 3 点、我在睡觉时把昨天的对话整理进长期记忆」，并且第二天上班打开记忆页就能确认「昨晚 3 点跑了，晋升了 12 条，耗时 118 秒，没有错误」。有时也想改成「每周一 9 点跑一次」或临时关掉定时改手动。

**输入**：
- cron 表达式（5 字段：分 时 日 月 周，服务器本地时区），或通过「每天 HH:mm / 每周 X HH:mm」两个图形化档位间接生成 cron；
- 定时开关、错过补跑宽限分钟数；
- 手动触发按钮。

**输出**：
- 保存后**立即生效**（不重启），返回解析结果与未来若干次触发时刻；
- 记忆页展示：当前 cron 的可读描述（「每天 03:00」）+ 下次触发相对时间 + 后续 3 次预览；
- 最近触发记录列表（时间 / 来源 / 结果 / 窗口 / 晋升·跳过·错误 / 耗时 / 失败原因），最多 20 条，可清空。

**边界与异常**：
- cron 非法（字段越界、语法错、6 字段、含 `L/W/#/?`）→ 保存 400 + 中文错误（指出第几个字段、期望范围），前端输入框红色 + 行内提示，**不落盘、不打断现有排期**；
- `cron` 表达「永不触发」（如 `0 0 30 2 *`）→ 视为非法拒绝，提示「该表达式不会触发」；
- 进程休眠/系统时间回拨越过触发点 → 在 `misfireGraceMin`（默认 60）内补跑一次并标记「补跑」，超出则记一条「错过」不补（避免开机瞬间猛跑）；
- 同空间已有晋升在跑 → 与现状一致，让位跳过并记一条「跳过（进行中）」；
- 记忆/Dreaming 关闭时保存 cron → 允许（配置先存着），响应里 `enabled:false` 提示「当前记忆未启用，定时不会执行」；
- 历史文件损坏/不可写 → 读回落空列表，写失败只记 debug 日志，**绝不影响晋升主链路**。

**明确的非目标**：
- 不引入 IANA 时区库，不做「按浏览器时区触发」（统一以**服务器本地时区**为准，UI 显式标注 UTC 偏移）；
- 不支持 6 字段秒级 cron、`L/W/#/?` 扩展语法、Quartz 方言；
- 不做 cron 表达式历史版本/回滚；
- 不改 DreamingPipeline 的提取算法、Curated 文件格式与去重策略；
- 不做跨进程文件锁（沿用「`lastProcessedDay` 幂等兜底」）；
- 不做多用户权限隔离（沿用单用户本地工具定位）。

**验收预期**（用户视角一句话）：在记忆页把「每天 03:00」改成「每天 04:30」→ 点保存 → 立即看到「下次 2026-10-27 04:30（还有 5 小时 12 分）」，无需重启；次日回来能在「最近触发记录」里看到 04:30 那一轮的完整结果。

## 三、关键技术调研（联网检索结论）

检索时间 2026-10-26，数据取自 npm registry 元数据。

| 库 | 最新版 | 依赖 | unpacked 体积 | 结论 |
| --- | --- | --- | --- | --- |
| `croner` | 10.0.1 | 无 | 154,686 B | 功能最全（含 L/#/时区），但体积是自写实现的数倍，且需进 SEA 打包链 |
| `cron-parser` | 5.10.2 | `luxon` | 155,712 B | 拖一个完整的时区库进来，与「零依赖优先」冲突 |
| `node-cron` | 4.6.0 | 无 | 327,912 B | 面向「长驻任务调度」设计，其 overlap/分布式协调能力本场景用不到 |

**已知坑（决定实现细节）**：

| # | 已知坑 | 本方案对策 |
| --- | --- | --- |
| 1 | `setTimeout` 最大延迟 `2^31-1 ms ≈ 24.8 天`，超限会**立即触发**（Node Timer 文档） | 「每年 1 月 1 日」这类 cron 的 next 可能 >24.8 天 → 单次等待**上限 6 小时**，到点重算（D4） |
| 2 | vixie cron 中 day-of-month 与 day-of-week **同时受限**时是**并集**语义，不是交集 | 显式实现并集，并在 `describeCron` 里提示（D6） |
| 3 | DST 回拨时同一墙钟时刻出现两次，逐毫秒推进的实现会**重复触发** | 用「本地墙钟分钟键 `YYYY-MM-DDTHH:mm`」去重（D4） |
| 4 | DST 前拨时某些墙钟时刻**不存在**（如 02:30） | 直接跳过不存在的本地时刻，顺延到下一个匹配（本地时间构造 + 校验回读） |
| 5 | `0 0 29 2 *` 四年一次，next 搜索需有界 | 搜索上限 4 年（1461 天），超出判定「永不触发」 |
| 6 | `*/n` 的起点是**字段最小值**（`*/7` 分 = 0,7,…,56），`5/10` = 5,15,…,55 | 按字段 min 起步行进，单测覆盖 |
| 7 | 周字段 `0` 与 `7` 都是周日 | 解析时归一化 `7 → 0` |
| 8 | cron 无秒，触发点应落在整分 | 定时器回调里比较「已到点的最小整分」，不在 59.9s 抢跑 |

结论：**自写 5 字段解析器**（约 200 行 + 单测），零新依赖、零 SEA 打包风险、错误消息可中文化、行为可精确断言（D1）。

## 五、关键设计决策

> 每条给推荐值；按项目惯例，未特别说明即按推荐项执行。

### D1 cron 引擎：自写零依赖 5 字段解析器（**推荐**）

- 位置 `src/api/cron.ts`，导出 `parseCron / nextFireTime / nextFireTimes / describeCron`。
- 支持：`*`、`N`、`a-b`、`a,b,c`、`*/n`、`a-b/n`、`a/n`，月/周支持 3 字母英文缩写（`JAN`、`MON`），另支持 `@hourly/@daily/@weekly/@monthly/@yearly` 宏。
- 不支持：`L/W/#/?`、6 字段、Quartz 方言 → 解析期返回中文错误（含字段序号与期望范围）。
- 被否决：引 `croner`（功能溢出 + 154KB + SEA 打包链风险）、`cron-parser`（拖 luxon）、`node-cron`（327KB + 面向长驻分布式任务）。

### D2 配置形态：新增 `schedule.cron`，保留旧字段为回落（**推荐**）

```ts
schedule: {
  enabled: boolean;          // 不变
  cron: string;              // 新增，默认 '0 3 * * *'（每天 03:00）
  misfireGraceMin: number;   // 新增，默认 60
  intervalHours: number;     // 保留：cron 为空时回落旧间隔语义
  startupDelayMin: number;   // 保留：同上
}
historyLimit: number;        // 新增，默认 20；0 = 不留历史
```

- 行为变更需在升级说明里显式写：默认触发时刻由「启动后 5 分钟 + 每 24h」变为「每天 03:00」。
- 被否决：直接删除 `intervalHours/startupDelayMin`（老配置文件里的值会静默失效，且失去「无 cron 时零回退」的兜底）。

### D3 时区：一律服务器本地时区（**推荐**）

- 用 `Date` 的本地字段（`getFullYear/getHours/…`）计算，不引 IANA 库。
- `GET /memory/status.dreaming` 返回 `timezoneOffsetMin`（如 `-480`），前端在 cron 输入框下方标注「以服务器本地时间 UTC+08:00 为准」。
- `lastProcessedDay` 仍是 UTC 日期口径（DreamingPipeline 既定），UI 加 `UTC` 角标消除歧义（不改口径）。
- 被否决：浏览器时区触发（服务端与浏览器常不同机，且 `--serve` 可远程访问）。

### D4 定时器：分片等待（≤6h）+ 整分对齐 + 墙钟键去重（**推荐**）

```ts
private scheduleNextByCron(fields: CronFields): void {
  const now = this.now();
  const next = nextFireTime(fields, now);       // 本地时区，整分
  if (next === null) { /* 记日志：永不触发 */ return; }
  this.nextRunAt = next;
  const delay = Math.min(Math.max(next - now, 0), MAX_WAIT_MS); // MAX_WAIT_MS = 6h
  this.timer = this.createTimer(() => { this.timer = null; void this.onTimer(); }, delay);
}
```

- `onTimer()`：`now < nextRunAt` → 只是分片到点，直接重排；`now >= nextRunAt` → 走触发判定。
- 墙钟键 `localMinuteKey(nextRunAt)` 与 `lastFireKey` 相同 → 判定为 DST 回拨重复，跳过并重排。
- 被否决：一次性 `setTimeout(next - now)`（>24.8 天溢出立即触发；休眠唤醒/时钟回拨后不知自愈）；每分钟轮询（无缺口但每日 1440 次无谓唤醒）。

### D5 错过补跑：`misfireGraceMin`（默认 60）（**推荐**）

- 到点时 `late = now - nextRunAt`；`late <= grace` → 正常执行，摘要标 `catchup: true`；`late > grace` → 不执行，写一条 `reason='schedule', skippedBecause='missed'` 的历史并重排。
- 被否决：无条件补跑（笔电合盖一周后开机会立刻跑，且窗口已放大到 30 天，一次 LLM 调用成本与耗时不可控）。

### D6 cron 语义：DOM/DOW 取并集 + 5 个宏（**推荐**）

- `0 3 1 * 1` = 「每月 1 号 03:00 **或** 每周一 03:00」，`describeCron` 输出「每月 1 日或每周一 03:00」。
- 宏：`@hourly`=`0 * * * *`、`@daily`=`0 0 * * *`、`@weekly`=`0 0 * * 0`、`@monthly`=`0 0 1 * *`、`@yearly`=`0 0 1 1 *`。

### D7 运行历史：独立文件 `.dreaming-runs.json`（**推荐**）

- 路径 `{L2 记忆目录}/.dreaming-runs.json`，结构 `{ version: 1, runs: DreamRunRecord[] }`，环形裁剪到 `historyLimit`。
- 与 `.dreaming-state.json` **分离**：后者承载「增量正确性」（`lastProcessedDay`），前者只是展示数据；展示层的 bug 不得污染增量状态，且「清空历史」不应触碰增量进度。
- 被否决：塞进 `.dreaming-state.json`（`saveState` 每次整文件重写，5KB 数组跟着 `run()` 每天重写；损坏回退逻辑会连带丢失历史）。

### D8 历史记录范围：只记「真跑」与「有意义跳过」（**推荐**）

- 记：`success / partial(有错误) / fail(异常) / busy / already-running / missed`。
- 不记：`disabled`、`no-runtime`（配置关闭期间每轮都产生噪声，无观测价值）。
- 单条字段：`startedAt, finishedAt, durationMs, reason, catchup?, ok, skippedBecause?, daysBack, promoted, skipped, errors, errorMessage?`（截断 200 字符）。

### D9 API 形态：4 个专用端点 + status 扩展（**推荐**）

| 端点 | 语义 |
| --- | --- |
| `PUT /memory/dream/schedule` | body `{enabled?, cron?, misfireGraceMin?}`；校验 → 落 workspace 配置 → `reschedule()` → 返回 `{ok, cron, describe, nextRunAt, nextRunTimes[3]}`；非法 400 `{error, fieldIndex?}` |
| `GET /memory/dream/preview?cron=…` | 只算不存，返回 `{ok, describe, next: string[5]}` 或 `{ok:false, error}`，供输入时防抖预览 |
| `GET /memory/dream/history?limit=20` | 返回 `{runs: DreamRunRecord[]}`（新→旧） |
| `DELETE /memory/dream/history` | 清空历史，返回 `{deleted: n}` |

`GET /memory/status.dreaming` 扩展：`cron, cronValid, cronError?, describe, timezoneOffsetMin, misfireGraceMin, intervalMode: 'cron'|'interval', nextRunTimes: string[]`；保留 `intervalHours/startupDelayMin` 一版（标 deprecated）。

- 被否决：复用 `PUT /config/<key>`（三次请求才能改 enabled+cron+grace，且中间态可能短暂非法；也无法在响应里返回 next）。

### D10 保存即生效：`reschedule()` 热重排（**推荐**）

- `PUT /memory/dream/schedule` 成功后调 `scheduler.reschedule()`：取消现定时器 → 重读配置 → 若 `enabled` 且 cron 合法则按新 cron 排下一次；`enabled:false` 则只清定时器（`nextRunAt` 置空）。
- 定时轮执行中改 cron：只影响下一次排期，不影响正在跑的这一轮（沿用单飞锁）。
- 兜底：`onTimer()` 每轮都会重读配置并重新解析 cron（解析失败则回退 interval 模式 + 记日志），避免「配置被别处改坏后调度器永久失灵」。

## 六、详细设计

### 6.1 `src/api/cron.ts`

```ts
export interface CronFields {
  minute: number[]; hour: number[]; dayOfMonth: number[]; month: number[];
  dayOfWeek: number[];          // 0-6，7 已归一化为 0
  domRestricted: boolean; dowRestricted: boolean;
  expr: string;                 // 归一化后的 5 字段表达式（宏已展开）
}
export type ParseResult =
  | { ok: true; fields: CronFields }
  | { ok: false; error: string; fieldIndex?: number };

export function parseCron(expr: string): ParseResult;
/** 从 fromMs 之后（严格大于）的下一个整分触发时刻；永不触发返回 null */
export function nextFireTime(fields: CronFields, fromMs: number): number | null;
export function nextFireTimes(fields: CronFields, fromMs: number, count: number): number[];
/** 「每天 03:00」「每月 1 日或每周一 03:00」 */
export function describeCron(fields: CronFields): string;
```

`nextFireTime` 算法（按天/时/分跳跃，非逐分钟）：

```
start = 下一分钟整（秒+毫秒清零）
for day in [start.date .. start.date + 4 年]:
    if !month.includes(day.month) → 跳到下月 1 日 00:00, continue
    if !(domMatch(day) || dowMatch(day)) → 跳次日 00:00, continue   // D6 并集
    for hour in sorted(hour) 且 >= (day==start.date ? start.hour : 0):
        for minute in sorted(minute) 且 >= 同时刻约束:
            cand = 本地构造(day, hour, minute)
            if 本地回读(cand) !== 期望值 → continue   // DST 不存在的墙钟时刻，坑4
            if cand > fromMs → return cand
return null
```

复杂度：最坏按天扫描（4 年 ≤ 1461 次），单次微秒级。

### 11.4 原型阶段发现并已回写方案的两处设计缺陷

| # | 缺陷 | 处理 |
| --- | --- | --- |
| 1 | 「失败 / 部分失败」判定顺序错误：后端 `ok = (errors === 0)`，若先判 `!ok` 就归「失败」，会把「部分天失败但已有产出」误标为整体失败 | 改为 `!ok && promoted > 0` → 部分失败，`!ok && promoted === 0` → 失败。**实施要求**：`DreamRunRecord` 必须同时保留 `promoted` 与 `errors`，不能只存 `ok` |
| 2 | cron 非法时右侧排期不应清空或跳变 | 非法时**保留上一次合法排期**并提示「表达式非法，排期保持不变」，与 D9「非法 → 400、不落盘、不打断现有排期」语义对齐 |

### 11.5 验证环境注意（可复用经验）

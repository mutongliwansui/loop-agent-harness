## 1. 需求与范围

### 1.1 背景与痛点

侧边栏（`.nav`，宽 224px）底部承担着「进入管理页」的唯一入口：`.nav-bottom > .grp` 这个「🗂️ 管理」折叠组。用户反馈「配置菜单目录样式不好看」，实测（2026-10-28，CDP 量取 1440×900）确认问题不只是观感：

| 序号 | 问题 | 实测证据 | 性质 |
| --- | --- | --- | --- |
| P1 | 空间侵占 | `.nav-bottom` 展开态高 **337.3px**，占 900px 视口 **37.5%**；会话列表被压到不足 200px | 布局 |
| P2 | 图标风格撕裂 | 9 个平台彩色 emoji（🗂️⚙️🤖🔧🔌🧩🧠🩺🌗），饱和度与视觉重量不一，且各平台渲染不同 | 视觉 |
| P3 | 无信息层次 | 7 个管理项 + 主题按钮同层平铺，无任何分组 | 信息架构 |
| P4 | 主从权重相同 | 入口行与子项同为 13.5px 字号、`7px 10px` 内边距、同款 `--bg` hover；箭头仅 11px | 视觉层级 |
| P5 | 发现性差 | 收起态只剩「管理」二字，看不出内含 7 项；外观切换藏在二级 | 可用性 |
| P6 | 展开突变 | `.grp-body` 在 `display:none ↔ block` 间硬切，无过渡 | 动效 |
| **P7** | **窄屏不可达（bug）** | `@media (max-width:900px)` 同时把 `.grp-body` **与** `.grp.open .grp-body` 置为 `display:none`，≤900px 时管理菜单**完全无法进入** | **功能缺陷** |

P7 是关键：现有窄屏适配只保留了「图标条」，但管理菜单的展开体被整体隐藏，等于窄屏用户彻底失去配置/模型/工具/MCP/技能/记忆/诊断 7 个页面的人口。本方案顺带修掉。

### 1.2 现状梳理

| 所需能力 | 代码现状 | 结论 |
| --- | --- | --- |
| 菜单数据 | [`router.ts`](../../webui/src/router.ts) `adminItems`：7 项 `{path,label,icon}`，icon 为 emoji 字符串 | **数据可原样复用**，仅 icon 字段换为 SVG key |
| 底部结构 | [`App.vue`](../../webui/src/App.vue) `.nav-bottom > .grp > .grp-head + .grp-body`，`mgrpOpen` 控制显隐，进入非 chat 页自动展开 | 改为入口 + 浮层，`mgrpOpen` 语义变为 `panelOpen` |
| 主题切换 | `App.vue` `toggleTheme()`：`data-theme` 覆盖 + `localStorage` 记忆 + 未设置时跟随系统 | **扩为三态**（跟随/浅/深），逻辑已有，只需把「循环切换」改为「显式选择」 |
| 线性图标体系 | [`tool-meta.ts`](../../webui/src/tool-meta.ts) `TOOL_ICON_PATHS`（16×16、`fill:none`、`stroke:currentColor`、`stroke-width:1.5`、圆头圆角）与 [`chart-box.ts`](../../webui/src/chart-box.ts) `ICON` 完全同源，已含 `gear` / `wrench` / `puzzle` | **直接复用 3 个 + 新增 5 个**，零新依赖、风格天然一致 |
| 设计令牌 | [`style.css`](../../webui/src/style.css)：`--hover` `--active` `--line-strong` `--text-2` `--radius-card` `--radius-ctl` `--shadow-pop` `--brand-weak` | **零新增令牌** |
| 弹层先例 | `.model-picker`（ChatView）、`.pop`（多处）已用 `--shadow-pop` + `--radius-card` 浮层范式 | 沿用同一套浮层视觉语言 |

### 1.3 目标

1. 常驻高度从 **337px → ≤40px**（单行入口），展开内容改为**覆盖式浮层**，不占布局高度。
2. 图标全部换为自绘 16px 线性 SVG，与项目既有 stroke 体系同源。
3. 按「运行 / 扩展 / 数据与排查」三组分层，2 列网格排布。
4. 入口行常驻显示**当前所在页名**，位置状态可见。
5. 外观切换提为面板内「跟随 / 浅色 / 深色」三段控件。
6. 修 P7：窄屏入口保持可见，浮层向右弹出。
7. 补键盘与无障碍：`role=menu`、方向键、Home/End、ESC、点击外部关闭、焦点回归入口。

### 1.4 非目标

- 侧边栏整体布局、宽度、会话列表交互改动
- 管理项增减、路由变更、页面内容改动
- 引入图标库或任何新 npm 依赖
- 移动端抽屉式导航重构（窄屏仍为图标条）

## 2. 方案设计

### 2.1 三种候选与取舍

| 方案 | 形态 | 常驻高度 | 评价 |
| --- | --- | --- | --- |
| A 分组竖排压缩 | 保留内联折叠，加组标题、行高压到 30px | ≈320px | 高度几乎没省（3 组标题 66 + 7 行 210 + 外观 32），**否决** |
| **B 入口 + 向上浮层** | 底栏单行入口，点击向上弹出面板 | **36px** | 高度降 89%，可承载分组与更多内容，**推荐** |
| C 底栏横向图标条 | 8 个 28px 图标横排 | 40px | 224px 内 8 个图标过密（每格 28px），纯图标无文字，发现性最差，**否决** |

选 **B**。核心差异：面板是 `position:absolute` 浮层，覆盖在会话列表之上，**不参与文档流**。

### 2.3 关键设计决策

| 编号 | 决策（推荐值） | 取舍 / 被否决项 |
| --- | --- | --- |
| **D1** | 交互形态采用**入口 + 向上弹出浮层**（`position:absolute; bottom:100%`），非常驻内联展开 | 否决 A（省不下高度）、C（纯图标发现性差）；浮层方式使常驻高度与内容量解耦，后续加管理项不再挤占会话列表 |
| **D2** | 图标全部换为**自绘 16px 线性 SVG**，`viewBox="0 0 16 16"` / `stroke-width:1.6` / `currentColor` / 圆头圆角，复用 `TOOL_ICON_PATHS` 的 `gear` `wrench` `puzzle`，新增 `chip`(模型) `link`(MCP) `stack`(记忆) `pulse`(诊断) `sliders`(入口) | 否决保留 emoji（跨平台渲染不可控、视觉重量不一）、否决引入图标库（违反零新依赖） |
| **D3** | 面板采用**2 列网格**，每格 34px 高、横排「图标 + 标签」 | 否决单列长列表（7 项 7 行过高，失去压缩意义）；2 列把 7 项压到 4 行 |
| **D4** | 「MCP 服务器」项**标签简化为「MCP」**，全称放 `title` | 2 列格宽约 92px，"MCP 服务器" 6 字放不下；`label` 字段保留原值，仅渲染时短化 |
| **D5** | 分组固定三组：**运行**（配置/模型/工具）、**扩展**（MCP/技能）、**数据与排查**（记忆/诊断） | 按「改运行参数 / 装扩展能力 / 看数据与排障」的心智切分；否决不分组（仍是 7 项平铺） |
| **D6** | 外观切换为面板内**三段控件**（跟随 / 浅色 / 深色，`aria-pressed`），替代原单个循环按钮 | 三态可见优于循环盲切（当前循环无任何状态提示）；`localStorage` 语义不变 |
| **D7** | 入口行右侧**常驻显示当前页名**（如「配置」），`aria-current` 项同步 | 让"我在哪"常驻可见；否决不显示（收起态信息量为零） |
| **D8** | 常驻高度目标 **≤48px**（实测容器 **45px** = 1px 分隔线 + 8px 间距 + 36px 入口按钮），较改造前 337.3px 压缩 **87%** | 入口按钮 36px 与「新建对话」同高，形成底栏节奏 |
| **D9** | 动效：面板 `opacity 0→1` + `translateY(6px)→0`，120ms `ease-out`；箭头 `rotate(180deg)` 150ms；`prefers-reduced-motion: reduce` 时全部禁用 | 否决无动画（P6 的突变观感）与长动画（>150ms 显拖沓） |
| **D10** | 窄屏（≤900px）：入口缩为**纯图标按钮**（居中 40px），面板**向右弹出**（`left: calc(100% + 8px)`，宽 210px，底部对齐） | 修 P7；否决窄屏隐藏（现状 bug）、否决窄屏用全屏抽屉（超出本需求范围） |
| **D11** | 无障碍：入口 `aria-haspopup="menu"` `aria-expanded` `aria-controls`；面板 `role="menu"`，项 `role="menuitem"`；打开时焦点移到当前页项；↑↓/Home/End 移动、ESC 关闭并焦点回入口、点击外部关闭 | 对齐 WAI-ARIA Menu 模式；否决仅鼠标可用 |

## 3. 验收口径

1. 原型在 headless Chrome 下 DOM 断言：入口 `aria-expanded` 随状态翻转、面板 `role=menu` 且含 8 个可聚焦项（7 管理项 + 外观 3 按钮中的当前项）、点外部关闭、ESC 关闭且焦点回入口、↑↓ 循环移动。
2. 像素采样：亮/暗两套主题下入口与面板背景、当前项高亮色与令牌一致；面板与入口无重叠（间距 ≥4px）。
3. 高度指标：改造后 `.nav-bottom` 容器高度 ≤48px（实测 45px，入口按钮本身 36px），改造前 337.3px，压缩 87%。
4. 窄屏（≤900px）：入口仍可见且可点开，面板可见（修 P7），右弹间隙 ≥6px（实测 8px）。

### 5.3 实施阶段发现的真缺陷：可见性过渡吞掉键盘焦点

首轮真机验证出现 7 项连败（焦点未落、方向键无效、ESC 失效、外部点击状态错）。根因不是断言写错，而是**产品缺陷**：

- `.nav .panel` 写了 `transition: opacity .12s, transform .12s, visibility .12s`。`visibility` 是离散属性，在过渡期会保持旧值（`hidden`），于是 `openPanel()` 里 `nextTick` 执行的 `focus()` 打在**仍不可聚焦**的元素上被浏览器丢弃，`document.activeElement` 停在 `body`；后续 ESC（监听在面板上）与方向键自然全部收不到事件。
- 修根因（非兜底）：展开方向把可见性改成**立即生效** —— `.panel.open { transition: ..., visibility 0s }`，收起方向保留 `visibility 0s linear .12s` 让淡出不被截断；同时 `openPanel()` 的聚焦改为 `nextTick → requestAnimationFrame`，等面板真正可见后再聚焦。
- 回归防护：`tests/webui-nav-menu.test.ts` 增加断言，锁住「展开态可见性过渡必须是 0s」「收起态仍是 0s linear .12s」两个方向，防止后人改回单值过渡。

### 5.4 验收过程中修正的断言假象（非产品问题）

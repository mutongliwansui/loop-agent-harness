## 1. 需求与范围

### 1.1 背景与痛点

WebUI「模型」页（`#/models`）当前能做的事只有一件跟「快不快」有关的：点「测试」→ 拿到一个毫秒数。而这个数字来自 [`defaultCheckConnectivity`](../../src/llm/connectivity.ts)：发一条 `ping`、`max_tokens: 16`，**收到第一块就 `abort()`**。它回答的是「能不能连上、首包大概多久」，回答不了下面这些真实问题：

| 用户真实问题 | 现状 | 后果 |
| --- | --- | --- |
| A provider 与 B provider，哪个在流式对话里更跟手？ | 只有一个首包毫秒数，且被 `abort` 截断，不含解码速度 | 换模型靠体感，切换后才发现「更聪明但打字一顿一顿」 |
| 同一个 provider 今天是不是比上周慢了？ | 无历史，测完即丢（`tests` 是组件内 `ref`，刷新页面即清空） | 无法判断是网络抖动还是服务降级 |
| 同一个模型在不同 baseUrl（官方 / 中转网关）差别多大？ | 需手工来回切 `active` 再造一句长回复肉眼看 | 结论不可量化，也没法回头对比 |
| 推理模型（`reasoning_content`）的「慢」慢在哪一段？ | 完全不可见 | 以为是模型笨，其实是首推理 token 前排队太久 |
| 高并发下发长文，谁的吞吐先塌？ | 无并发测量能力 | 批量任务选型的唯一依据只能是价格 |

一句话：**连通性 ≠ 性能**。需要把「延迟（TTFT）」与「吞吐（TPS）」这两类真正影响体感的指标，做成模型管理页的一等能力。

### 1.3 目标

1. **可量化**：为每个 profile 产出 TTFT / TPOT / 解码 TPS / 端到端 TPS / 输出 token / 成功率，多轮取 p50、p90。
2. **可对比**：同一面板内横向对比 2–4 个 profile（同档位、同提示词、同一时刻），并以条形图呈现相对快慢。
3. **可回溯**：每次测试落盘（含配置快照），模型页显示「最近一次」，面板内可看近 N 次趋势与差异。
4. **过程可观测**：运行中实时显示轮次进度、本轮首 token 到达、已生成 token 数与当前 TPOT，可随时中断。
5. **口径诚实**：默认破坏前缀缓存（随机 nonce）以免 TTFT 被缓存命中虚低；对「疑似被网关缓冲（chunk 攒包一次到）」的测量结果明确标注为不可信。

### 1.4 非目标（本期不做）

- 质量 / 正确率评测（跑评测集、打分、排行榜）—— 与性能正交，另立需求。
- 成本计费与性价比排序（需要价格表维护）。
- 多机分布式压测、长时间 soak 测试。
- CLI `/model bench`（**列演进项**：引擎写成纯函数后 CLI 只是薄壳）。
- 模型 CRUD、真实对话链路的任何改动。

## 2. 联网调研结论

### 2.1 业界口径（三家以上一致）

| 指标 | 定义 | 来源 |
| --- | --- | --- |
| **TTFT**（Time to First Token） | 从发出请求到收到**第一个 token** 的时间，含网络 + provider 排队 + prefill | [NVIDIA NIM Benchmarking](https://docs.nvidia.com/nim/benchmarking/llm/latest/metrics.html)、[Azure OpenAI latency doc](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/latency)、[OpenRouter](https://openrouter.ai/docs/guides/best-practices/latency-and-performance) |
| **TPOT / ITL**（Time per Output Token / Inter-Token Latency） | 相邻输出 token 的平均间隔；vLLM 明确 `TPOT = (e2e - TTFT) / (output_tokens - 1)`，且「**不含**第一个 token」 | [vLLM metrics](https://docs.vllm.ai/en/stable/design/metrics)、[vLLM benchmark CLI](https://github.com/vllm-project/vllm/blob/main/docs/benchmarking/cli.md) |
| **TPS per user** | 单用户视角吞吐 = 输出 token 数 / 端到端时延 | NVIDIA NIM 同上 |
| **Total TPS per system** | 多并发下总吞吐 = 总输出 token / 墙钟（并注明 batch-oriented、非实时指标） | NVIDIA NIM 同上 |
| **TTLT** | `TTLT = TTFT + TBT × Tokens`（总时延构成，用于解释「为什么长回答体感差」） | Azure OpenAI latency doc |
| **分位数** | 延迟必须看 p90/p99，而不只看均值/典型值 | [OpenRouter · How to Evaluate LLM Provider Performance](https://openrouter.ai/blog/insights/evaluate-llm-provider-performance) |

三家不约而同给出的「体感公式」：

```
总时延 = TTFT（网络 + 排队 + prefill） + 输出 token 数 × TPOT
```

### 2.2 五个必须提前决策的坑

**① 空 chunk 会毒化 TTFT。** OpenAI 兼容流里首个 chunk 常见 `delta.content === ""`（仅 `role`），部分网关还会先发 `usage` chunk。NVIDIA GenAI-Perf 与 LLMPerf 明确「首响应无 token 的一律不计」。→ 首 token 必须定义为**首个 `delta` 里有非空内容**的 chunk。

**② 前缀缓存会把第二轮 TTFT 打得虚低。** 同一条 prompt 连打多轮，DeepSeek/OpenAI 的前缀缓存会命中，TTFT 掉一个量级，于是「多轮平均」变成缓存命中率测试。→ 每轮在 prompt 前缀注入随机 nonce 破坏缓存，并把 `prompt_cache_hit_tokens` 记录在案（本仓库 [`usage.ts`](../../src/llm/usage.ts) 已归一化该字段）。

**③ 网关/代理可能「攒包」再吐。** 若中间层开了 buffering，几十个 chunk 会一次到达，ITL 变成 0、TPS 虚高。→ 记录 chunk 到达间隔序列，若「chunk 数 ≈ 1 且生成 token > 8」或「相邻间隔方差极小」，结果标注 `suspect_buffered: true`，UI 显示「⚠ 疑似被网关缓冲，TPS 不可信」。

**④ TTFB ≠ TTFT。** 有网关会立刻发 HTTP 头/心跳先占位，首个**字节**远早于首个 **token**。→ 只认首个非空内容 chunk（与 ① 同一实现），并在文档中明确本项目不采用 TTFB 口径。

**⑤ 推理模型的「首 token」分歧。** OpenRouter 2025-05 起把 reasoning 模型的 latency 定义为「到首个 **reasoning** token」，throughput 则把 reasoning + output token 一起计入。→ 本项目同时记录 `firstAnyTokenMs`（含 reasoning，作 TTFT）与 `firstContentTokenMs`（首个答案 token），两者之差即「思考期」。见 D5。

另有一条工程侧注意：OpenRouter 2025-12 起把初始延迟并入吞吐计算，理由是**防止端点靠攒包刷高 TPS**——这条佐证了 ③ 的标注策略比单纯提高 TPS 数字更有意义。

### 2.3 和「已有的连通性测试」怎么分工

| | 连通性（现有） | 性能测试（本方案） |
| --- | --- | --- |
| 目的 | 能不能用 | 有多快、稳不稳 |
| 请求 | `ping` / `max_tokens:16` / 首块即 abort | 固定提示词 / `max_tokens:256` / 跑完整流 |
| 输出 | 1 个 `latencyMs` | 6 类指标 × p50/p90 + 每轮明细 |
| 成本 | 近乎免费、亚秒级 | 一次标准档约 3 轮 × 2 提示词，按输出 token 计费 |
| 触发 | 表格行内「测试」按钮 | 面板「开始测试」 |

**两者并存、互不替代**：连通性当健康检查（快、频繁），性能测试当体检（慢、按需）。

## 3. 指标定义与计算口径（本项目落地版）

计时全部用 `performance.now()`（单调时钟，不受系统时间调整影响）。记 `t0 = 发请求前一刻`。

| 指标 | 计算式 | 数据来源 | 展示 |
| --- | --- | --- | --- |
| `ttftMs` | 首个**非空内容** delta 到达 − `t0` | 采样 | 卡片大字 + p50/p90 |
| `firstReasoningMs` | 首个 `reasoning_content` 非空 delta − `t0`（无 reasoning 则 N/A） | 采样 | 折叠行「思考期」 |
| `tpotMs` | `(tLastToken − tFirstToken) / max(1, outTokens − 1)` | 采样 + usage | 卡片 |
| `itlP90Ms` | 相邻非空 chunk 间隔序列的 p90（长尾抖动，比均值更能反映「卡顿」） | 采样 | 明细表 |
| `decodeTps` | `(outTokens − 1) / (tLastToken − tFirstToken) × 1000`（**纯解码**，去掉首 token） | 采样 + usage | **卡片大字（主指标）** |
| `e2eTps` | `outTokens / (tLastToken − t0) × 1000`（含首 token，OpenRouter 2025-12 口径） | 同上 | 卡片副行 |
| `totalMs` | `tLastToken − t0` | 采样 | 明细表 |
| `outTokens` | `usage.completion_tokens`；缺失时回退「非空 chunk 数 + 字符数/1.7」估算并标 `estimated:true` | [`normalizeUsage`](../../src/llm/usage.ts) | 明细表 |
| `cacheHitTokens` | `usage.prompt_cache_hit_tokens`（归一化后） | 同上 | 明细表「缓存命中」 |
| `ok / errorKind` | 成功判定；错误分类：`auth`(401/403) / `not_found`(404) / `rate_limit`(429) / `timeout` / `network` / `server`(5xx) / `aborted` | 异常捕获 | 状态 pill |
| **汇总** | 每档位对各轮取 **p50 / p90**（p90 用 nearest-rank，避免样本少时插值外推）；成功率 = ok 轮 / 总轮 | 汇总层 | 结果卡片 |

口径三条纪律：

1. **token 数以 `usage` 为权威**，估算值只在服务商不回 usage 时兜底，且必须在 UI 上标出（否则不同模型间不可比）。
2. **样本 < 3 轮不显示 p90**（显示 `—` 并提示「至少 3 轮才出分位」）。
3. **固定 `max_tokens`（默认 256）与固定提示词**，否则「输出长度不同」会直接扭曲 TPOT 对比。

## 5. 技术方案

### 5.1 总体数据流

```
ModelsView（模型页）
  │ ①点「测速」→ 打开抽屉，选档位
  ▼
POST /models/bench           （创建一次 bench run，返回 runId）
  │                              │
  │ ②GET /models/bench/:runId/stream  （SSE：逐轮 / 逐 chunk 进度）
  ▼                              ▼
src/llm/bench.ts  ── OpenAI SDK（stream + include_usage）──▶ provider
  │  采样：t0 / 首非空 chunk / 每个非空 chunk / 末 chunk
  │  汇总：p50 / p90 / tps / 错误分类
  ▼
~/.loop-agent/model-bench/history.json（每模型保留最近 20 次）
```

**为什么测在后端**（D1）：`apiKey` 不出后端（前端只拿遮蔽值，这是现状安全基线）；计时不含「浏览器→本机 server」这一段；且引擎可被 CLI / 脚本复用。

**为什么用 SSE 而不是轮询**（D7）：进度本就高频（每 chunk 一次），项目已有 `sseFrame` 与长连接范式，落地成本低于新写轮询协议。

### 5.2 后端引擎（新文件 `src/llm/bench.ts`）

```ts
/** 单轮采样（纯数据，可 JSON 化后随 SSE 下发） */
export interface BenchSample {
  prompt: 'short' | 'medium' | 'code';
  round: number;
  ok: boolean;
  ttftMs?: number;          // 首个非空内容 delta（含 reasoning）
  firstReasoningMs?: number; // 首个 reasoning_content delta
  firstContentMs?: number;   // 首个答案 delta（排除 reasoning）
  tpotMs?: number;
  itlP90Ms?: number;
  decodeTps?: number;
  e2eTps?: number;
  totalMs?: number;
  outTokens?: number;
  promptTokens?: number;
  cacheHitTokens?: number;
  estimated?: boolean;      // outTokens 来自估算
  chunkCount?: number;
  suspectBuffered?: boolean;
  errorKind?: BenchErrorKind;
  error?: string;
}

export interface BenchOptions {
  model: ModelCandidate;              // {name, baseUrl, apiKey}
  prompts: BenchPromptKey[];          // 默认 ['short']
  rounds: number;                     // 默认 1（快速）/ 3（标准）
  maxTokens: number;                  // 默认 256
  timeoutMs: number;                  // 默认 60_000
  bustCache: boolean;                 // 默认 true
  onRound?: (i: number, total: number, prompt: BenchPromptKey) => void;
  onFirstToken?: (ms: number) => void;
  onToken?: (outTokens: number, ms: number) => void;  // 节流后回调
  signal?: AbortSignal;               // 中断
}

export interface BenchSummary {
  ttft:   { p50: number; p90: number | null; min: number; max: number; samples: number };
  decodeTps: { p50: number; p90: number | null };
  e2eTps: { p50: number };
  successRate: number;
  suspectBuffered: boolean;
  samples: BenchSample[];
}

/** 单模型跑完整档位；不抛错（失败计入 samples），仅 signal 中断时抛 AbortError */
export async function runBench(opts: BenchOptions): Promise<BenchSummary>;

/** 汇总纯函数（便于单测：给样本数组出 p50/p90） */
export function summarize(samples: BenchSample[]): BenchSummary;

/** 百分位（nearest-rank，无插值）：samples<3 时 p90 返回 null */
export function percentile(values: number[], p: number): number | null;
```

关键实现要点：

1. `new OpenAI({..., fetch: globalThis.fetch, maxRetries: 0, timeout})` —— 与 [`connectivity.ts`](../../src/llm/connectivity.ts) 同款注入，规避 Node 24 下 SDK 内置 fetch 的 Premature close；bench 不自动重试（重试会污染统计），失败即记一轮失败。
2. `stream: true` + `stream_options: { include_usage: true }`。
3. 循环里对每个 chunk：`delta.reasoning_content` 非空 → 记 `firstReasoningMs`（若未记）；`delta.content` 非空 → 记 `ttftMs`（若未记）并 `onToken`。**空串与 undefined 一律跳过**（坑 ①）。
4. `bustCache` 时把 `[{role:'system',content:`bench-nonce:${randomUUID()}`}]` 前置（坑 ②）。
5. 流的最后一个 chunk 若只有 `usage`，把 `tLastToken` 定格在**最后一个非空内容 chunk**，不把 usage chunk 当输出。
6. `suspectBuffered` 判定：`chunkCount <= 1 && outTokens > 8`，或 `itlP90 === 0`（坑 ③）。
7. 中断：`signal.aborted` → `stream.controller.abort()`，已采集样本照常汇总，summary 附 `aborted: true`。

### 5.3 REST 端点（扩展 `src/api/handlers/models.ts`，或新 `bench.ts` 挂进 `modelRoutes()`）

### 5.6 边界与错误处理

| 场景 | 处理 |
| --- | --- |
| profile 无 `apiKey` | 400，前端在按钮上禁用并提示「先补 apiKey」 |
| 401/403 | 该轮失败，`errorKind: auth`，UI 提示「apiKey 无效或无权限」（复用 connectivity 文案） |
| 404 | `not_found`，提示「模型名或服务地址可能有误」 |
| 429 | `rate_limit`，**不重试**，本档位提前结束并在卡片上提示「被限流，样本不足」 |
| 单轮超时 | 记 `timeout`，继续下一轮；全部超时则卡片显示失败 |
| 中断 | 已采样轮次照常汇总，标 `aborted` |
| 服务商不回 usage | `outTokens` 估算 + `estimated:true`，UI 显示 `~` 前缀 |
| SSE 断连 | 前端自动重连一次（`runId` 幂等），仍失败转「结果可能不完整」提示 |
| 面板关闭 | 后台 run 继续（用户可能只是想切页），完成后 toast + 「性能」列刷新 |

## 6. 关键设计决策（待确认）

| # | 决策 | 取舍 / 被否决项 |
| --- | --- | --- |
| **D1** | **性能测试在后端跑**（Node 直连 provider），前端只做展示 | 否决「浏览器直连 provider 测速」：baseUrl 与 apiKey 会暴露到页面，且受浏览器连接池/预检影响；否决「借用 Agent 会话跑」：会污染上下文与记忆 |
| **D2** | **TTFT = 首个非空内容 chunk 的时间**（空 `delta.content` 与纯 `usage` chunk 不计） | 对齐 vLLM / NVIDIA / LLMPerf；否决 TTFB 口径（网关可先发头，坑 ④）与「首个任意 chunk」口径（会被 role-only chunk 提前） |
| **D3** | **多模型对比在服务端串行执行**，不做同面板并行 | 并行会互相抢带宽使 TTFT 失真；并发吞吐作为 P2 独立选项单独测 |
| **D4** | **主指标 = 纯解码 TPS**（`(out−1)/(tLast−tFirst)`），端到端 TPS 作为副行同时显示 | 纯解码反映「打字速度」；端到端反映「整体等待」（OpenRouter 2025-12 口径）。只显示一个都会误导，故并列但分级 |
| **D5** | **推理模型：TTFT 含 reasoning 首 token，另单列 `firstContentMs`** | 与 OpenRouter 2025-05 起口径一致（latency 量到首个 reasoning token）；否决「只算答案 token」（会让推理模型显得不可用）与「只算 reasoning」（漏掉答案首字） |
| **D6** | **端点挂在 `/models/bench/*` 静态段**，注册顺序先于 `/models/:alias/*` | 避免 `bench` 被 `:alias` 吞掉；否决新开 `/bench/*` 顶层组（与「模型管理」归属不符，且鉴权/scope 语义分离） |
| **D7** | **进度用 SSE**（复用 `sseFrame`） | 否决 WebSocket（终端已用 WS，但此处单向、无二进制、无双向需求）；否决长轮询（每 chunk 一次请求开销大） |
| **D8** | **默认注入随机 nonce 破坏前缀缓存**，并把 `prompt_cache_hit_tokens` 一并记录；用户可关 | 混合缓存状态的「平均值」没有意义；开着更接近「冷启动真实体感」。否决「默认复用同一 prompt」（第二轮 TTFT 会被缓存打到 1/10） |
| **D9** | **历史落盘 `~/.loop-agent/model-bench/history.json`，每模型留 20 次，不存 apiKey** | 否决 localStorage（换浏览器丢、脚本读不到）；否决写进 `.agent-config.json`（配置面不该混运行时数据）；否决 SQLite（引新依赖，违背零依赖约束） |
| **D10** | **固定 `max_tokens`（256）+ 固定提示词集 + `temperature: 0`**，保证跨模型可比 | 否决「让模型自由发挥」（输出长度不同 → TPOT 不可比）；否决随机温度（波动掩盖真实差异） |
| **D11** | **样本 < 3 轮不出 p90**，UI 显式 `—` + 提示 | 否决「小样本也算分位」（90 分位在 1–2 个样本上等于最大值，是假精确） |

## 8. 风险与验收

### 8.1 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 真实测试会花钱 | 一次标准档 3 轮 × 2 提示词 × 256 tok 上限 | 默认「快速档」；面板显式显示「预计约 N 万 token 上限」；不建议对未配置限额的 key 反复跑 |
| 网关缓冲导致 TPS 假高 | 决策依据被误导 | `suspectBuffered` 标注 + UI 警示（坑 ③） |
| provider 限流（429） | 样本不足、结论漂移 | 不重试、提前结束、显式提示；档位之间可加 300ms 间隔 |
| model 名变更（同名不同版本） | 历史趋势断裂 | 历史条目存 `model` + `baseUrlHost` 快照，趋势图按 `model` 分组 |
| 长提示词触发 provider 冷启动 | 首轮 TTFT 偏高 | 档位含「预热轮」（默认丢弃第 0 轮，可在面板关闭） |

### 8.2 验收

- 单测：`percentile`/`summarize`（含 <3 轮 p90=null、estimated 标记、buffered 判定）、`bench-format` 格式化与涨跌色、SE 解析；引擎用 `vi.mock('openai')` 造可控 chunk 序列（含空 chunk、reasoning chunk、仅 usage chunk）。
- 回归：`npx tsc --noEmit`、`npx vitest run`、`cd webui && npx vite build` 全绿。
- 真机：对 2 个真实 profile 各跑一次快速档与标准档，比对「面板显示 vs 服务商面板实际的 token 用量」是否一致（允许 ±5%）。
- 原型：headless Chrome 四态 × 亮暗截图 + DOM/像素断言（见 `webui/verify-bench-proto.shot.mjs`）。

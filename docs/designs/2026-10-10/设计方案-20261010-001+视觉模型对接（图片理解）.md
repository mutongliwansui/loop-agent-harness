# 设计方案：视觉模型对接（图片理解）

> 优化建议编号：20261010-001
> 提出时间：2026-10-10
> 方案状态：待评审
> 参考思路：Agent 接入视觉模型设计方案（Function Call 直连版）

---

## 一、背景与目标

当前 Agent 仅支持纯文本对话，无法理解图片。目标：**主文本模型通过 Function Call 决策，本地代码直接对接外部视觉大模型（OpenAI 兼容协议），完成图像理解任务。**

核心原则（沿用参考思路）：

- 主模型只负责"想"，不直接看像素
- 视觉模型只负责"看"，不参与决策
- 本地调度逻辑是两者之间的唯一桥梁
- 不新增服务、不引入额外协议层

## 二、现状梳理（结合当前代码）

在动手前先确认现有框架与该方案的契合度——**大量基础设施已存在，可零成本复用**：

| 参考方案需要的能力 | 当前框架现状 | 结论 |
|---|---|---|
| 工具定义与注册 | `Tool` 接口（[types.ts](../../../src/types.ts)：`name/description/parameters/execute`）+ `ToolRegistry`（[registry.ts](../../../src/tools/registry.ts)，全局单例 `registry`） | 直接复用 |
| 工具执行与错误回填 | `ToolRunner.run()`：异常转 `工具执行失败: xxx` 字符串、30s 超时、结果归一化 string（[runner.ts](../../../src/tools/runner.ts)） | 直接复用，超时需扩展 |
| 多 tool_calls 并行 | ReAct 主循环 `Promise.all` + `runner.runParallel`（[react-agent.ts](../../../src/agent/react-agent.ts) L585-608） | 直接复用 |
| 长耗时任务可见性 | 每 1s `onToolProgress` 心跳 + Spinner（20260930-001 已落地） | 直接复用 |
| 单次任务调用上限 | `model.maxIterations`（默认 10） | 直接复用 |
| 参数校验 | 主循环按 `parameters.required` 检查缺失参数（react-agent.ts L589-593） | 直接复用 |
| 配置分层 | `AgentConfig` 六组 + `deepMerge` 五层合并（defaults/env/global/workspace/cli，[loader.ts](../../../src/config/loader.ts)）；`/config set` 走 `ConfigWriter.setByKey` 点分路径写入，无键白名单 | 新增 `vision` 组即可 |
| 可观测性 | `llmLogger.request/response`（独立 LLM 调用日志）+ `debug.toolCall` | 直接复用 |
| 消息类型 | `ChatMessage` 的 user content 为 `string`（types.ts L48-52）；L1 压缩、会话加密持久化均假设 content 为 string | **本方案不改变消息结构**，图片以 URL/data URI 字符串形式出现在消息文本中 |

### 关键结论

1. **无需扩展 `ChatMessage` 类型**。主模型永远不接收图像像素，图片以字符串（本地路径 / http URL / data URI）形式出现在 user 消息文本里，主模型把它填进工具参数即可。这使记忆系统（L1 `estimateTokens`/`compact`）、会话持久化（AES-256-GCM）全部零改动。
2. **参考方案中的"本地调度器"无需新建**——它就是现有的 `ToolRegistry + ToolRunner + ReAct 主循环`。视觉模型对接在框架内的形态是：**4 个内置 `Tool`，各自 `execute()` 内调用视觉 API**。
3. 仅有的框架级扩展点：`Tool` 接口增加可选 `timeoutMs`（视觉调用建议 60s，超出 runner 默认 30s）。

## 三、总体架构

```
用户输入（含图片路径/URL，以文本形式）
        │
        ▼
┌─────────────────────┐
│   主文本模型         │  ← registry.toOpenAITools()（含 4 个视觉工具定义）
│  (Function Call)     │
└─────────┬───────────┘
          │ 返回 tool_calls
          ▼
┌─────────────────────────────────────────┐
│   现有 ReAct 主循环 + ToolRunner          │
│   （校验参数 → Promise.all 并发 → 回填）  │
└─────────┬───────────────────────────────┘
          │ 按函数名路由（registry.get(name).execute(args)）
          ▼
┌─────────────────────────────────────────┐
│  src/tools/vision/                       │
│  image.ts 解析图片 → cache.ts 查缓存      │
│  → VisionClient.chatVision() 调视觉 API  │  ← OpenAI 兼容协议（独立 baseUrl/apiKey/model）
└─────────┬───────────────────────────────┘
          │ 返回文本/JSON
          ▼
   结果作为 tool 消息回填（tool_call_id）
          │
          ▼
   主模型继续推理，循环直至最终答案
```

**角色划分：**

| 角色 | 职责 | 是否看图 | 对应代码 |
|---|---|---|---|
| 主文本模型 | 任务规划、工具选择、结果推理 | 否 | `model.name` 配置 |
| 本地调度 | 解析 tool_calls、并发执行、回填结果 | 否 | 现有 ReAct 主循环 + ToolRunner |
| 视觉大模型 | 图像理解、文字识别、结构化提取 | 是 | `vision.*` 配置 + VisionClient |

**执行流程（无需改动主循环，全部由现有机制承载）：**

1. 用户输入如「看一下 d:/imgs/error.png 里的报错信息」（图片以文本形式进入 user 消息）
2. 主模型返回 `tool_calls: [{ name: 'ask_image', arguments: { image, question } }]`
3. 主循环校验参数 → `runner.run()` 执行 → 工具内部读图转 base64 → 调视觉 API
4. 结果作为 `tool` 消息回填；错误也被 `ToolRunner` 转字符串回填（不中断循环）
5. 主模型继续推理直至最终答案；期间每 1s 心跳、Spinner 正常工作

## 四、关键设计决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 图片不进 `ChatMessage` content 数组，保持 string | 记忆/会话/统计零改动；主模型是纯文本模型，传像素无意义且浪费 token |
| D2 | 视觉能力做成 4 个内置 Tool 而非独立子系统 | 完全复用注册/执行/校验/心跳/Tab 补全/`/tools enable` 管控，无新增协议层 |
| D3 | `vision.enabled` 默认 `false`，关闭时不注册工具 | tools 列表稳定且字节级一致，保住模型前缀缓存（registry 已按名排序 + canonicalize） |
| D4 | 视觉服务三元组（baseUrl/apiKey/model）独立配置，空值回退主模型配置 | 同一服务商部署多模型时零重复配置；跨服务商（如主 DeepSeek + 视觉 GLM-4V/Qwen-VL）也可独立配置 |
| D5 | `Tool` 增加 `timeoutMs?`，runner 优先使用 | 视觉调用 30-60s，超出默认 30s；改动集中在 runner 一处 |
| D6 | 结果缓存（LRU+TTL）按「模型+工具种类+参数+图片指纹」做 key | 同一张图多轮追问不重复计费；文件指纹用 mtime+size，URL 直接用字符串 |
| D7 | 工具结果统一截断到 `maxResultChars`（默认 8000） | 参考 5.1 节上下文膨胀控制；截断在工具内部做，runner 保持通用 |
| D8 | `extract_json` 用 prompt 强约束 + 解析容错，不依赖 `response_format` | 部分兼容服务商不支持 JSON 模式；首次调用失败自动降级一次 |

## 五、详细设计

### 5.1 配置组 `VisionConfig`

在 [schema.ts](../../../src/config/schema.ts) 新增第七个配置组，接入现有五层合并（`deepMerge` 递归合并，无需改 merge 逻辑）：

```typescript
export interface VisionConfig {
  /** 是否启用视觉工具（默认 false；关闭时不注册工具，主模型 tools 列表不含视觉工具） */
  enabled: boolean;
  /** 视觉服务 baseUrl，空则回退 model.baseUrl */
  baseUrl: string;
  /** 视觉服务 apiKey，空则回退 model.apiKey */
  apiKey: string;
  /** 视觉模型名，空则回退 model.name（主模型需具备视觉能力） */
  model: string;
  /** 采样温度，默认 0（输出稳定） */
  temperature: number;
  /** 单次输出上限，默认 2048（视觉描述可能较长） */
  maxTokens: number;
  /** 单次视觉调用超时毫秒，默认 60000 */
  timeoutMs: number;
  /** 图片大小上限（字节），默认 10MB */
  maxImageBytes: number;
  /** 工具结果最大字符数（超出截断），默认 8000 */
  maxResultChars: number;
  /** 是否启用结果缓存，默认 true */
  cacheEnabled: boolean;
  /** 缓存 TTL 毫秒，默认 600000（10 分钟） */
  cacheTtlMs: number;
}
```

- `AgentConfig` 增加 `vision: VisionConfig`；`PartialAgentConfig` 增加 `vision?: Partial<VisionConfig>`
- `DEFAULT_CONFIG.vision`：`{ enabled: false, baseUrl: '', apiKey: '', model: '', temperature: 0, maxTokens: 2048, timeoutMs: 60000, maxImageBytes: 10 * 1024 * 1024, maxResultChars: 8000, cacheEnabled: true, cacheTtlMs: 600000 }`
- [loader.ts](../../../src/config/loader.ts) `envFrom` 增加：`VISION_API_KEY`（→ vision.apiKey，同时视为 enabled=true）、`VISION_BASE_URL`（→ vision.baseUrl）、`VISION_MODEL`（→ vision.model，同时视为 enabled=true）
- 运行时管理：`/config set vision.enabled true`、`/config set vision.model glm-4v-plus` 等，走既有 `ConfigWriter.setByKey` 点分路径，**config-command 无需改动**
- `config.ts` 动态 getter 对象不加（deprecated），视觉代码统一用 `configLoader.load().config.vision`

### 5.2 LLMClient 扩展：`chatVision()`

在 [client.ts](../../../src/llm/client.ts) 新增非流式方法（视觉调用无需流式，主循环也不会为它打印 Thought）：

```typescript
// 新增独立视觉客户端缓存（与主 client 并列，各自的 apiKey/baseUrl 变化时重建）
private visionClient: OpenAI | null = null;
private _lastVisionKey = '';
private _lastVisionUrl = '';

export interface VisionChatOptions {
  /** 视觉配置三元组（调用方从 cfg.vision 解析回退后传入） */
  baseUrl: string;
  apiKey: string;
  model: string;
  temperature?: number;
  maxTokens?: number;
  /** 尝试 JSON 模式（response_format），不支持时自动降级 */
  jsonMode?: boolean;
}

async chatVision(messages: ChatMessage[], options: VisionChatOptions): Promise<LLMResponse>
```

要点：

- `messages` 中的 user content 使用多模态数组形式 `{ type: 'text' | 'image_url', ... }[]`——**仅在 VisionClient 内部构造，不进入 `ChatMessage` 历史与持久化**（详见 D1）
- `jsonMode=true` 时首次带 `response_format: { type: 'json_object' }` 调用；若服务商返回 400/参数不支持错误，自动降级重试一次不带 `response_format`（仅一次，避免双倍超时）
- 复用 `retry()`（网络/429/5xx 重试）与 `wrapError()`；`beginLLMCall/llmLogger.request/response` 照常记录（日志中 model 字段即视觉模型名，天然可区分）
- 调用结束返回 `{ content, usage, elapsedMs }`（usage 供会话级视觉 token 统计）

### 5.3 图片解析模块：`src/tools/vision/image.ts`

统一三种图片来源（工具参数里的 `image` 字符串）：

| 输入形态 | 处理 |
|---|---|
| `http://` / `https://` URL | 透传 URL 给视觉 API（由服务端下载） |
| `data:image/...;base64,...` | 直接透传 |
| 其他（视为本地路径） | 校验存在性 → 按扩展名识别 MIME（png/jpg/jpeg/webp/gif/bmp）→ `readFile` → 校验大小 → 转 `data:${mime};base64,...` |

```typescript
export interface ResolvedImage {
  /** 发给视觉 API 的 image_url 值（URL 或 data URI） */
  uri: string;
  /** 来源类型 */
  source: 'url' | 'data' | 'file';
  /** 原始字节数（data URI 按解码后计） */
  bytes: number;
  /** 本地文件的缓存指纹（mtime+size），URL 场景为 undefined */
  fileFingerprint?: string;
}

export async function resolveImage(raw: string, maxBytes: number): Promise<ResolvedImage>
```

错误按类别抛出（供 5.5 错误分类）：

- 文件不存在 → `图片文件不存在: <path>`
- 扩展名不支持 → `不支持的图片格式: <ext>（支持 png/jpg/jpeg/webp/gif/bmp）`
- 超大小上限 → `图片超过大小限制: <size> > <maxBytes>`
- 无扩展名/读取失败 → 对应 IO 错误消息

### 5.4 结果缓存：`src/tools/vision/cache.ts`

```typescript
/** key = sha1(model | kind | 归一化参数 | 图片uri或fileFingerprint) */
export class VisionResultCache {
  get(key: string): string | null;
  set(key: string, value: string): void;
  size(): number;
  clear(): void;
}
```

- LRU 上限 20 条 + TTL（`vision.cacheTtlMs`），超限淘汰最旧
- 本地文件场景用 `mtime+size` 做指纹：文件内容变了缓存自动失效
- `describe_image` / `ocr_image` 的 key 只含图片与模型；`ask_image` 额外含 question；`extract_json` 含 fields
- 缓存命中时返回结果并附注释行 `[cache hit]`（仅 debug 日志，不进回填内容）

### 5.5 四个视觉工具：`src/tools/vision/tools.ts`

工具清单（沿用参考方案的最小集合）：

| 工具名 | 用途 | 输入参数 | 输出 |
|---|---|---|---|
| `describe_image` | 整体描述图片内容 | `image`(必填) | 自然语言 |
| `ask_image` | 针对图片回答具体问题（主力） | `image`, `question`(均必填) | 自然语言 |
| `extract_json` | 按字段提取结构化数据 | `image`, `fields`(string[], 必填) | JSON 字符串 |
| `ocr_image` | 纯文字识别 | `image`(必填) | 文本 |

描述遵循参考方案原则——**写"什么时候用"**：

```typescript
export const describeImage: Tool = {
  name: 'describe_image',
  description:
    '对一张图片做整体描述（主体、场景、文字、颜色、数量等）。当用户给出图片且你不确定该问什么时，先用它获取全局信息；已明确要问什么时优先用 ask_image 定向提问。image 支持本地路径或 http(s) URL。',
  parameters: {
    type: 'object',
    properties: {
      image: { type: 'string', description: '图片本地路径或 http(s) URL' },
    },
    required: ['image'],
  },
  timeoutMs: 60000,
  async execute(args) { /* 共享执行管道，prompt 固定 */ },
};
```

共享执行管道（单文件内私有函数，避免重复）：

1. 读 `cfg.vision`（未启用时 throw `视觉功能未启用，请先 /config set vision.enabled true 并配置 vision.model`）
2. `resolveImage(raw, cfg.vision.maxImageBytes)`
3. 查缓存 → 命中直接返回
4. 构造多模态 messages 调 `llm.chatVision()`
5. 解析与容错：
   - `extract_json`：剥离 ```` ```json ```` 代码块围栏与前后缀文本 → `JSON.parse` → 成功则 `JSON.stringify(result, null, 2)` 返回；失败则**不 throw**，降级返回 `注意：视觉模型输出不是合法 JSON，以下为原始文本：\n<原文>`（让主模型自行补救，符合"错误不中断"原则）
   - 其余工具：原文返回
6. 截断：超过 `maxResultChars` 时截断并追加 `\n…（已截断，原文共 N 字符）`
7. 写缓存，返回

prompt 模板（system/user 二段式）：

| 工具 | 指令 |
|---|---|
| `describe_image` | 「客观、详尽地描述这张图片的内容，包括主体、场景、可见文字、颜色、数量与布局。」 |
| `ask_image` | user 消息 = question 原文 |
| `extract_json` | 「从图片中提取以下字段，找不到的填 null。只输出 JSON 对象，不要任何解释或代码块围栏。字段：fields 列表逐行列出」 |
| `ocr_image` | 「提取图中全部文字，保持原始阅读顺序与换行。不要解释、不要总结，只输出识别出的文字。」 |

导出 `VISION_TOOL_NAMES = ['describe_image', 'ask_image', 'extract_json', 'ocr_image']` 供注册与 Tab 补全复用。

### 5.10 错误处理与上下文/成本控制

**错误必须回填，不中断循环**——现有 `ToolRunner` 已天然满足（异常 → `工具执行失败: xxx` 字符串）。按参考方案覆盖的类别落点：

| 错误类别 | 落点 | 主模型收到的可操作信息 |
|---|---|---|
| 视觉超时（60s） | runner withTimeout | `工具执行超时 (60000ms)`，主模型可换 ask_image 缩小问题 |
| 限流/5xx | `chatVision` 复用 `retry()` 两次后退避失败 → 工具内 throw | `视觉模型调用失败(429): 请求过于频繁…` |
| 返回非法 JSON（仅 extract_json） | 工具内降级，不 throw | 原始文本 + 降级说明（5.5 第 5 步） |
| 图片 404/不存在/格式不支持 | `resolveImage` 分类 throw | 5.3 的分类错误消息 |
| 工具名不存在/参数缺失 | 主循环现有校验 | 现有 `未注册`/`缺少必需参数` 消息 |

**上下文膨胀控制**（对应参考方案 5.1）：

- 截断：`maxResultChars` 统一兜底（长 describe 是膨胀主源）
- 缓存复用：同一张图多轮追问不重复注入新内容（内容相同，主模型可引用旧结果）
- 「describe 长输出二次摘要压缩」列为演进项（三、P2 之后），先用截断兜底
- 选择性保留旧工具结果：已有 L1 压缩机制承担，不重复建设

**成本优化**（对应参考方案 5.2）：

- 主模型继续用便宜快速的文本模型，视觉按需调用（D4 支持不同服务商）
- 工具描述引导定向提问（ask_image 输出短于 describe_image）
- extract_json 一次拿结构化数据，减少往返
- 单次任务调用上限 = `model.maxIterations`（现有机制）

### 5.11 可观测性

- `chatVision` 内部走 `beginLLMCall` + `llmLogger.request/response`：函数名/参数/耗时/原始返回/usage 全部落盘（`~/.loop-agent/logs/llm-*.log`，model 字段可区分视觉调用）
- `debug.toolCall` 由主循环照常记录每次视觉工具调用
- 会话级视觉用量累计：`/vision status` 展示（P1），token 汇总不混入主模型 `LLMStatsSummary`（那是上下文压缩决策依据，混入会失真）

### 5.12 安全考量

- 本地路径读取边界与 `fileRead` 一致（无额外沙箱，能力等同）
- base64 图片只在 VisionClient 内部出现，**绝不回填**到 tool 结果（避免撑爆上下文）
- http URL 由视觉服务端下载，本地不发起任意下载（天然规避本地 SSRF）；文档提示：将不可信的 `image_url` 交给第三方视觉服务时注意图片敏感度
- `vision.apiKey` 与主 `model.apiKey` 同等待遇：仅存配置文件/.env，不进日志、不回显（`/vision status` 只显示尾 4 位）

## 九、与 MCP 方案的对比

| 维度 | Function Call 直连（本方案） | MCP Server 方案 |
|---|---|---|
| 工具定义位置 | 本地代码（`vision/tools.ts`） | MCP Server 动态提供 |
| 新增工具成本 | 改代码重新构建 | 改 Server，客户端无感 |
| 多 Agent 复用 | 需抽库或复制 | 天然共享 |
| 动态发现 | 不支持 | 支持 |
| 依赖复杂度 | 低（仅 4 个工具 + 1 个 client 方法） | 中（需维护 Server 进程） |
| 适用规模 | 少量固定工具、单 Agent | 大量工具、多 Agent、跨服务 |

**选型结论**：当前项目工具少（6 内置）、单 Agent、已有 MCP 接入层但视觉工具不值得为其单独起服务——直连更轻、更可控。工具定义（`Tool` 接口）与执行逻辑天然分离，未来若视觉工具膨胀或需要多服务共享，将 `src/tools/vision/` 整体包装为 MCP Server 的迁移成本很低。

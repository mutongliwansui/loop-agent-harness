## 一、任务目标需求

### 1.1 背景（痛点）

对话流中 Agent 的文件类工具调用（读取/写入/编辑/搜索/视觉识别）都带路径参数，但 ToolCard 里路径只是纯文本：副标题只显示 basename，想看 Agent 刚操作的文件只能切到文件面板逐级查找；视觉工具的图片落点 `~/.loop-agent/uploads/{sessionId}/` 在文件面板中根本不可见。FilesView 的完整预览能力（md/html/svg/csv/xlsx/docx/pdf/图片/pptx/文本）与对话页只隔一次点击，缺的只是入口。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
| --- | --- | --- |
| 对话页内嵌文件面板 | `ChatView.vue` 第 1146 行 `<FilesView v-model:open="filesOpen" :ws-path>`，`filesOpen` 控制展开 | ✅ 面板就在对话页内，点路径可直接展开 |
| 完整文件预览 | `FilesView.openFile(path)`（第 634 行）：md 渲染 / html 沙箱 / svg / csv / xlsx / docx / pdf / 图片 / pptx / 文本，含源码切换与文内搜索 | ✅ 直接复用，不新写渲染 |
| 目录定位 | `FilesView.gotoCrumb(path)`（第 406 行，20261028-004 目录名命中同款链路） | ✅ 目录 chip 复用 |
| 跨组件调用 | ToolCard 是 ChatView 子组件（第 915 行），FilesView 是 ChatView 子组件；`openFile` 未 `defineExpose` | ⚠️ 需补 emit 链 + expose |
| ws 内文件读取 | `GET /fs/file`、`/fs/raw`，`resolveInWs` 校验 | ✅ 现状可用 |
| uploads 图片读取 | uploads（`~/.loop-agent/uploads/{sessionId}/`）在工作空间外，`/fs/*` 一律 403；仅有 `POST /uploads/raw` 写入 | ❌ 需新增受控只读端点 |
| 路径参数清单 | tool-meta.ts：fileRead/fileWrite/editFile `path`（文件）、grep `path`（目录或文件）、commandRun `cwd`（目录）、视觉四件套 `image`（文件，多为 uploads） | ⚠️ 缺「哪个参数是路径、是文件还是目录」的结构化定义 |
| 历史会话回放 | ToolSeg.args 已持久化（会话 JSON） | ✅ 渲染层纯函数，历史自动生效，无 schema 变更 |

### 1.3 任务目标

1. 参数表（展开详情）与组卡子行中的路径值渲染为可点击 chip；文件点击 → 自动展开文件面板并打开预览；目录点击 → 面板定位该目录。
2. uploads 图片可点击预览（后端受控放行：只读、限 uploads 根内、realpath 防穿越）。
3. http(s)/data URI/缺失参数/工作空间外绝对路径不渲染为可点 chip（避免必然失败的点击噪音）。
4. 历史会话回放同样生效；失败（文件不存在等）toast 提示且不阻塞界面；不干扰滚动跟随状态机。
5. 零新依赖、零新设计令牌。

### 1.4 设计约束

- 仅改 WebUI 渲染层 + 新增一个后端只读端点；SSE 协议、会话数据结构、`/fs/*` 端点语义零改动。
- chip 视觉对齐项目既有体系：等宽字、内联 SVG 图标（stroke 1.6）、`--line-strong` 虚线下划线、hover `--hover`，不引新色值。
- 安全面不扩大：uploads 放行仅只读、仅限 uploads 根内、保留 403 与安全审计语义。

## 二、方案设计

### 2.1 总体思路

```
对话流消息渲染（ChatView）
  └─ ToolCard（参数表行 / 组卡子行）
       ├─ tool-meta.classifyPathArg(tool, key, raw)          ← D3 路径分类
       │     → file | dir | url | data | missing | outside
       ├─ file/dir → 可点 chip ──emit('open-path', raw)──▶  ← D4 chip 落点
       └─ 其余分类 → 纯文本（title 注明不可点原因）           ← D7
                                          │
                                          ▼
                        ChatView.onOpenPath → filesRef.openPath(path)   ← D1/D2
                              │
                              ├─ 路径含 /.loop-agent/uploads/ → uploads 模式
                              │     → GET /uploads/view?path=<原始路径>&disp=file|raw   ← D5/D6
                              ├─ 目录 → gotoCrumb() 定位 + 面板展开
                              └─ 其余（ws 内相对/绝对）→ openFile()
                                    → GET /fs/file | /fs/raw（既有链路）
```

### 2.2 关键设计决策

> 联网检索说明：本轮 web_search MCP 服务不可用，以下业界参照基于既有知识（Cursor 的工具卡文件引用可跳转编辑器、Claude artifacts 侧栏预览、ChatGPT 分析文件卡片点击打开查看器——共同模式为「引用即入口，预览就地呈现，不弹独立窗口」），已体现在 D1；实施前如需可再补检索。

- **D1 预览呈现：复用对话页内 FilesView 面板**。点击路径 → `filesOpen=true` + 面板预览/定位；窄屏面板本就是抽屉式全覆盖（现有行为）。否决：独立浮层预览组件——需重复实现 md/图片/表格渲染链路且与面板预览双份维护，且对话页内面板一键可达，浮层无增益。
- **D2 跨组件通道：ToolCard `emit('open-path')` → ChatView → FilesView `defineExpose({ openPath })`（组件 ref 直调）**。同页父子层级清晰，不引全局事件总线；不用 hash query 路由（预览属临时视图状态，刷新回到默认态即可接受，不进 URL）。
- **D3 路径分类：tool-meta 显式映射 + 纯函数**。新增 `PATH_ARGS: Record<tool, Record<param, 'file'|'dir'>>`（fileRead/fileWrite/editFile→path:file；grep→path:dir（目录为主，文件点击走同一条 openFile 亦可，归类 dir 定位更稳）；commandRun→cwd:dir；视觉四件套→image:file）+ `classifyPathArg(tool, key, raw)` 返回 `file/dir/url/data/missing/outside`（outside=ws 外且非 uploads 的绝对路径）。单测覆盖六分类。否决：按扩展名启发式猜目录——误判不可观测。
- **D4 chip 落点：仅参数表行值 + 组卡展开子行**。副标题（brief）保持纯文本短语不动——brief 是一行式摘要，内联可点元素会破坏紧凑性与行高稳定（否决并列为非目标）。
- **D5 uploads 读取端点：新增 `GET /uploads/view?path=&disp=file|raw`**（挂 handlers/uploads.ts，语义同源）。`disp=file` 文本预览（512KB 截断、二进制拒绝，响应结构与 `/fs/file` 同构：`{name,bytes,truncated,content}`）；`disp=raw` 原始字节（图片等，上限沿用 `/fs/raw` 的 100MB）。校验链：`resolveInWs(uploadsRoot, path)` → realpath 二次校验 → 只读。否决：给 `/fs/*` 加 uploads 分支——一个端点两种根语义，权限面混淆、审计困难。
- **D6 uploads 识别与可见范围：前端以 `/.loop-agent/uploads/` 子串嗅探（分隔符归一后）+ 后端强校验兜底**；可见范围为 **uploads 根内全部会话目录**（不限定当前会话）——uploads 内容是用户自己上传的文件、本机单用户场景，且历史会话回放需要看到当时的图片；路径可直接透传原始绝对路径，由后端校验归一后必须位于 uploads 根内，误判最多 403 不会越权。403/404 响应结构对齐 `/fs/*` 现状。
- **D7 不可点分类的渲染：纯文本 + `title` 注明原因**（url「外部链接不支持预览」、data「内联数据不支持预览」、outside「文件在工作空间之外」、missing「路径参数缺失」）。不做「渲染可点但点击必失败」的噪音交互。
- **D8 不存在文件：不预检 stat，直接走 openFile 既有错误链路**（预览区错误态）+ `openPath` 层 toast「文件不存在或已被删除」。避免双请求竞态。
- **D9 相对路径基准：相对工作空间根**（与工具语义一致）；Windows 反斜杠先归一为 `/`。绝对路径在 ws 根内则相对化后走既有链路（`/fs/*` 本就兼容绝对路径，无需前端相对化，透传即可）。
- **D10 零新依赖、零新令牌**。chip 样式复用 `--line-strong`/`--hover`/`--brand`；图标复用 FilesView ICONS 的 folder/file 线性 SVG 形制（stroke 1.2~1.4）。

## 三、任务详细设计

### 3.1 `webui/src/tool-meta.ts`（路径分类）

```ts
/** 路径型参数映射：工具 → 参数名 → 文件/目录 */
export const PATH_ARGS: Record<string, Record<string, 'file' | 'dir'>> = {
  fileRead: { path: 'file' },
  fileWrite: { path: 'file' },
  editFile: { path: 'file' },
  grep: { path: 'dir' },
  commandRun: { cwd: 'dir' },
  describe_image: { image: 'file' },
  ask_image: { image: 'file' },
  ocr_image: { image: 'file' },
  extract_json: { image: 'file' },
};

export type PathArgKind = 'file' | 'dir' | 'url' | 'data' | 'missing' | 'outside';

/** 分类单个参数值；outside = ws 外且非 uploads 的绝对路径（win 盘符/UNC 判定） */
export function classifyPathArg(tool: string, key: string, raw: unknown): PathArgKind;

/** 上传图片识别：归一分隔符后含 /.loop-agent/uploads/（供 openPath 分流，后端强校验兜底） */
export function isUploadsPath(raw: string): boolean;
```

边界：`raw` 非字符串/空串 → `missing`；`^https?://` → `url`；`^data:` → `data`；其余按 `PATH_ARGS` 有无映射返回 `file`/`dir`，无映射（非路径参数）返回 `missing` 由调用方按普通值渲染。`outside` 判定仅在绝对路径且既非 uploads 又无法确认在 ws 内时给出——前端不掌握 ws 根绝对路径，策略：**相对路径一律视为 ws 内可点**（工具语义即如此），绝对路径若非 uploads → `outside` 不可点（不猜测盘符映射）。

### 3.2 `webui/src/components/ToolCard.vue`（chip 渲染）

- 参数表行（`.trow`）渲染：`toolParamRows` 产出的值若命中 `PATH_ARGS` 且分类为 `file/dir` → 渲染 `<button class="path-chip">`（folder/file 图标 + 等宽路径文本），`click → emit('open-path', raw)`；其余分类纯文本 + title。
- 组卡展开子行（`.trow-sub`）同步处理。
- 样式：`font-family: var(--mono)`、`border-bottom: 1px dashed var(--line-strong)`、hover `background: var(--hover)`、`cursor: pointer`、图标 14px currentColor。

### 3.3 `webui/src/views/ChatView.vue`（接线）

```html
<ToolCard ... @open-path="onOpenPath" />
<FilesView ref="filesRef" v-model:open="filesOpen" :ws-path="activeWsPath" />
```

`onOpenPath(raw)`：面板已开则保持；调 `filesRef.value?.openPath(raw)`；异常兜底 toast。

### 3.4 `webui/src/views/FilesView.vue`（openPath + uploads 模式）

```ts
defineExpose({ openPath });

/** 对话流入口：自动展开面板；文件→openFile，uploads→uploads 模式，目录→gotoCrumb */
async function openPath(raw: string): Promise<void> {
  open.value = true;
  const p = raw.replaceAll('\\', '/');
  if (isDirArg) { await gotoCrumb(p); return; }            // 目录 chip 由调用方带 kind
  if (isUploadsPath(p)) { await openUploads(p); return; }   // D5/D6
  await openFile(p);                                        // ws 内既有链路（404/403 走 fileError）
  // 错误兜底：openFile 结束后 fileError 非空 → toast「文件不存在或已被删除」
}
```

- `openUploads(p)`：文本类型走 `GET /uploads/view?path=&disp=file`（复用 fileData 渲染分支），图片/二进制走 `disp=raw`（blob 直显，复用 openBinary 的 objectURL 管理）；`wsQuery()` 不附加。
- 目录 chip 的 kind 识别：ToolCard emit 带上 `{ path, kind }`（来自 `PATH_ARGS` 映射），openPath 按 kind 分流，不做二次 stat 猜测。

### 3.5 `src/api/handlers/uploads.ts`（新增 `GET /uploads/view`）

- 入参：`path`（相对 uploads 根，或绝对路径——归一后必须位于 uploads 根内）、`disp=file|raw`（默认 file）、可选 `sessionId`（path 为纯文件名时用于定位会话目录）。
- 校验链：`toSlash` 归一 → `resolveInWs(uploadsRoot, path)`（词法防穿越）→ `fs.realpath` 二次校验（防符号链接逃逸，对齐 `/fs/*` 写操作既有强校验）→ 只读读取。
- 响应：`disp=file` → `{name, bytes, truncated(>512KB 截断), content}`（与 `/fs/file` 同构，前端零适配）；`disp=raw` → 原始字节 + `Content-Type` 按扩展名推断（图片直显），上限 100MB。
- 错误：越界/不存在 → 403/404 JSON，结构对齐 `/fs/*`；审计日志沿用现有安全日志格式。

### 3.6 边界与错误处理

| 场景 | 行为 |
| --- | --- |
| 文件不存在（历史会话常见） | 预览区既有错误态 + toast「文件不存在或已被删除」，面板保持展开 |
| uploads 路径越权（跨根/穿越） | 后端 403，前端 toast 提示，不阻塞界面 |
| 点击时文件正被 Agent 写入 | 现有读取语义原样呈现（截断提示/部分内容），不特殊处理 |
| 滚动跟随（20261027-002） | openPath 不触碰 `.msgs` 滚动位置；面板展开是布局变化，不写 scrollTop |
| 同一路径连点 | openFile 幂等（openSeq 竞态防护既有），无重复实例 |
| 深色主题 | chip 令牌两套主题自动生效（`--line-strong`/`--hover` 均有暗色值） |

### 3.7 演进项（本任务不做）

- 卡片副标题（brief）内联路径可点。
- 对话流消息正文/结果区中出现的路径可点（仅限参数区）。
- `/uploads/view` 支持目录列表（当前仅文件）。
- 历史消息内联图片缩略图（20261028-005 非目标顺延）。

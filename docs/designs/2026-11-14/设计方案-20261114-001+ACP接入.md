## 一、背景与目标

用户要求「让 loop-agent 支持 ACP」。ACP = **Agent Client Protocol**，是编辑器（Zed、JetBrains 系等）与你自己的 Agent 之间的标准协议，JSON-RPC 2.0 over stdio，定位上相当于「Agent 界的 LSP」。

接入后 loop-agent 不再是「只能自己起 REPL 或开 WebUI 的产品」，而是**可以被任何 ACP 编辑器当作外部 Agent 唤起**：用户在 Zed 里选中项目、新建线程、直接对话，loop-agent 在自己的进程里跑 ReAct 循环，编辑器负责渲染流式回答、工具轨迹与权限确认。

**非目标（本期明确不做）**：ACP Registry 上架、跨编辑器线程导入导出（session/list）、多模态 prompt（图像/音频）、把编辑器能力反向暴露成 loop-agent 工具、WebUI 侧改造。

**传输范围说明**：P0/P1 **只做 stdio**（协议唯一标准化传输，也是全编辑器唯一能用的方式）。远程传输（Streamable HTTP / WebSocket）**不是「协议不允许」，而是「客户端普遍还不支持」**——详见 D10，排 P2 可选，且已评估复用成本较低。

### 协议侧要点（联网检索结论，来源 agentclientprotocol.com 与 zed.dev/docs）

- **传输**：JSON-RPC 2.0 over **stdio**（换行分隔 JSON），编辑器以子进程方式 spawn Agent。
- **握手**：客户端先发 `initialize`，携带 `protocolVersion`（当前 1）、`clientCapabilities`（`fs.readTextFile`/`fs.writeTextFile`/`terminal`）、`clientInfo`；Agent 必须回同一版本（不支持则回自己支持的最新版）并声明 `agentCapabilities`（`loadSession`、`promptCapabilities`、`mcpCapabilities`、`sessionCapabilities`）。
- **必做基线**：`session/new`、`session/prompt`、`session/cancel`、`session/update` 四件套是所有 Agent 的强制要求；`session/load`、`session/resume`、`session/close`、`session/list`、`session/delete` 均为可选能力，须先在 initialize 里声明再提供服务。
- **prompt turn 生命周期**：`session/prompt` 期间 Agent 持续发 `session/update`（`plan`/`agent_message_chunk`/`agent_thought_chunk`/`tool_call`/`tool_call_update`），最后用带 `stopReason` 的响应结束该请求。**注意：`session/prompt` 的响应必须在所有 update 之后**。
- **工具语义**：`tool_call` 需 `toolCallId` + `title` + `kind`（read/edit/delete/move/search/execute/think/fetch/switch_mode/other）+ `status`（pending/in_progress/completed/failed）；`tool_call_update` 只需带变化字段。
- **权限**：`session/request_permission` 是 Agent→Client 的请求，选项 kind 为 allow_once/allow_always/reject_once/reject_always；取消时客户端必须回 `cancelled`。这是**协议允许但非强制**的一环。
- **取消**：收到 `session/cancel` 后应尽快停 LLM 与工具，且仍可在响应前发 update，最终以 `cancelled` stopReason 结束 prompt。
- **编辑器接入方式**：Zed 在 settings 的 `agent_servers` 下加 `{"type":"custom","command":"loop-agent","args":["--acp"]}` 即可；用 `dev: open acp logs` 看双向报文。
- **官方 SDK**：`@agentclientprotocol/sdk`，用法为 `agent({name})` + `onRequest(methods.agent.initialize, handler)` + `connect(stream)`。

**分层原则**：`src/acp/` 是全新独立目录，只做「协议翻译 + 编排」，**不侵入 agent/session/tools 的既有实现**。唯一需要触碰既有代码的地方是 `src/index.ts` 加一个分支（以及 stdout 隔离这个横切处理）。

## 四、关键设计决策（D1–D11）

### D1　SDK 依赖：零依赖自研 vs 引入官方 `@agentclientprotocol/sdk`

- **方案 A（推荐）**：零依赖自研。用 `node:readline` + `process.stdout.write` 实现换行分隔 JSON-RPC，自己定义 TS 类型。
  - 理由：协议基线只有 4 个方法 + 6 类通知，接口面很小；项目既有铁律是「零新依赖优先」；`tsup` 打包与 SEA 单文件分发（已有 `build:sea`）不会被新依赖搅乱；出问题时可完全掌控报文。
- **方案 B**：引入官方 SDK，省掉协议类型与连接层，但增加一个外部依赖，且 SDK 版本演进会牵动打包链路。
- **方案 A 的适用边界（已修正）**：仅当范围是「stdio + 4 个方法」时成立。**一旦 D10 选 C（远程纳入 P1），A 的成本急剧上升**——见 D11 的成本对比。
- **修正后的取舍**：D10 选 C 后，**推荐改为方案 B（引入官方 SDK）**。理由见 D11。

### D10　传输范围：只做 stdio 是否够？能不能远程？

**协议事实（已核实 agentclientprotocol.com/protocol/v1/transports）**：

- 规范正文原话：*"The protocol currently defines **one** transport mechanism for agent-client communication: stdio"*，远程传输（Streamable HTTP）目前**仍在 RFD 草案阶段**（`streamable-http-websocket-transport` RFD）。
- 但同时明确：*"The protocol is **transport-agnostic** and can be implemented over any communication channel that supports bidirectional message exchange"*，且官方 Introduction 页写明 **"ACP is suitable for both local and remote scenarios"**——只是标注了「Full support for remote agents is a work in progress」。
- 远程草案的具体形态已基本定型：单端点 `/acp`；`POST /acp` 建连接并返回 `Acp-Connection-Id`；后续 POST 带该头（会话级再加 `Acp-Session-Id`）；`GET /acp` 开 SSE 长连（连接级 + 每会话一条）；`DELETE /acp` 终止；同端点支持 WebSocket upgrade。**要求 HTTP/2**。

**编辑器事实（已核实 zed.dev/docs/ai/external-agents）**：

- Zed 的 custom agent 配置**只有 `command`/`args`/`env` 三种字段**，语义是「本地起子进程走 stdio」。官方文档的 remote projects 一节讲的是「SSH 远程项目里 agent 也在远端跑」，**不是**「直连远端 HTTP agent 端点」。
- 第三方综述（danilchenko.dev）结论一致：*"The spec's only official transport is stdio, so nearly every ACP agent runs as a local subprocess... Until that ships in the SDKs, don't plan an architecture around remote ACP agents."*

**因此「远程」有两种完全不同的含义，必须分开回答**：

| 用户想要的「远程」 | 现状 | 解法 |
|---|---|---|
| ① **在远程机器上跑 agent**（SSH 远程项目 / 开发容器 / 云主机） | Zed 已支持 ACP-over-SSH：把 agent 装到远端主机，在远端 spawn，stdio 跑在 SSH 通道里 | **不需要写任何代码**，只需在远端机器装好 loop-agent 并在 settings 里配 `command` 为远端路径 |
| ② **agent 作为常驻网络服务**（多客户端直连一个 HTTP/WS 端点，如团队共享、Web 端接入） | 协议侧是 RFD 草案，主流编辑器（Zed/JetBrains）**均不支持配 HTTP 端点** | 可自研，但**当下没有编辑器能连**，只能自己写客户端 |

**方案 A（P0/P1 主线）**：只做 stdio。
**方案 B（原 P2，用户已选 C → 提到 P1）**：额外提供远程模式，实现草案版 Streamable HTTP + WebSocket。
  - 成本评估（**已修正，原先「成本低于预期」的判断过乐观**）：材料虽齐（`ws@8.22.0` 已在依赖、`src/terminal/ws.ts` 有 WebSocketServer 用法、`src/api/server.ts:260` 有 `http.createServer` 骨架、`src/api/http-utils.ts:88` 有 Bearer 鉴权、`src/api/server.ts:208` 有「非回环无 token 拒绝启动」护栏），但**这些只能解决鉴权与建服务器，解决不了核心难点**：
    1. **HTTP/2 MUST**，而项目现有 `http.createServer` 是 HTTP/1.1；Node 需换 `node:http2` 或做双栈。
    2. **`ws` 库不支持 HTTP/2 WebSocket**（RFC 8441 扩展 CONNECT），Node 生态无成熟封装。
    3. **长连 SSE 多路复用**：连接级 1 条 + 每会话 1 条，POST 立即 202、响应在 GET 流上按 JSON-RPC `id` 关联——这是全新的路由与生命周期模型，无法从既有 SSE 代码演进。
  - 因此**必须做传输抽象**：`AcpTransport` 接口（`onMessage/send/close`），stdio 与远程各实现一个，handlers/bridge 不感知。

**用户在 D10 选择 C（远程提到 P1）后，本项的成本已无法靠「复用既有材料」抵消，依赖策略须同步调整 → 见 D11。**

### D11　远程纳入 P1 后的依赖决策（D10=C 的直接后果）

**已核实的关键事实**：

| 事实 | 来源 |
|---|---|
| 远程草案 **HTTP/2 是 MUST**（"HTTP/2 is **REQUIRED** for Streamable HTTP transport"） | RFD 正文 |
| 但官方 TS SDK 的 `createNodeHttpHandler` 基于 **`node:http`（HTTP/1.1）**，`createNodeWebSocketUpgradeHandler` 依赖 HTTP/1.1 `Upgrade` 语义 | `src/transports/node-adapter.ts` 源码 import 自 `node:http` |
| 官方 SDK 已在 npm 发布，**最新 2.5.0 / 2.6.0**，Apache-2.0，**0 个运行时依赖**（`zod` 为 peerDependency） | npm registry |
| 本项目 `node_modules/zod` **已有 3.25.76**（既有间接依赖），`ws` 为 8.22.0 | 本地实测 |

**⚠️ 必须明确的偏差**：官方参考实现自己就跑在 HTTP/1.1 上，**与 RFD 的 HTTP/2 MUST 存在张力**。「严格按 RFD 的 HTTP/2」与「跟官方实现互通」是两条路，需用户明确取舍。

**成本对比（D10=C 必须做的核算）**：

| 项 | 方案 A（自研） | 方案 B（官方 SDK） |
|---|---|---|
| stdio 传输 | 手写 ~150 行 | SDK 自带 |
| HTTP/2 + SSE 长连（连接级 + 每会话）| 手写 ~600–900 行 | 用 `createNodeHttpHandler`（实为 HTTP/1.1）|
| WebSocket upgrade | 手写 ~200 行 | `createNodeWebSocketUpgradeHandler` + `ws` |
| 双头路由 + 400/404/415/406 语义 | 手写校验链 | SDK 内部实现 |
| 协议类型/方法常量 | 自维护，随 v1 漂移 | 官方同步 |
| 新增依赖 | 0 | 1（peer zod，已在） |
| **P1 额外工时** | **+5～7 人日** | **+1～2 人日** |

**推荐（修正后）：方案 B**。D10=C 后「零依赖」的收益无法覆盖自研远程传输的成本与漂移风险。

> 若坚持零依赖，则建议 D10 回退为 A（stdio only），否则 P1 工期与风险不可控。


### D2　stdout 纯净性：如何保证协议帧不被日志污染

- **方案 A（推荐）**：ACP 模式启动时做**全局 stdout 劫持**——在进入协议循环前，把 `process.stdout.write` 换成写 `stderr`，仅保留一个内部专用的 `writeFrame()` 直接写原始 stdout（通过捕获劫持前的引用）。
  - 优点：**零侵入**，173 处 console.log 一行不用改，CLI/serve 行为完全不受影响。
  - 风险：需在 ACP 分支内完成，顺序必须早于 `initRuntime()`（它一开始就 `console.log('[startup] ...')`）。
- **方案 B**：逐个改造 173 处日志为注入式 logger。改动面大、回归风险高。
- 取舍：**推荐 A**。

### D3　工作空间与多会话：走 WorkspaceRegistry 还是单 runtime

- **方案 A（推荐）**：复用 `WorkspaceRegistry`。`session/new` 的 `cwd` → `registry.get(canonical(cwd))` 得到该空间的 runtime，`session/prompt` 走 `rt.runAgent(sessionId, ...)`。
  - 优点：天然支持「同一编辑器连开多个项目」、复用既有 LRU/空闲回收、记忆按 workspaceId 共享。与 `--serve` 完全同构。
- **方案 B**：单 runtime 单空间（只服务 `cwd`）。实现更小，但一个进程只能服务一个项目，编辑器开新项目需重连。
- 取舍：**推荐 A**（代码量增加有限，能力差异明显）。

### D4　思考过程可见性：thought 要不要推给编辑器

- **方案 A（推荐）**：`onLLMStream` → `agent_thought_chunk`，`onFinal` → `agent_message_chunk`。
  - 理由：loop-agent 是 ReAct 架构，其「正文输出」在流式阶段本质上就是推理文本（`delta` 直接来自模型 stream），权威最终答案在 `onFinal`。这样编辑器里能实时看到生成过程，且不会被拆成两条重复消息。
- **方案 B**：全推 `agent_message_chunk`（不区分思考），更像普通聊天，但会丢掉「思考」与「回答」的 UI 区分。
- 取舍：**推荐 A**，并作为可调开关（配置项 `acp.thoughtAsMessage` 默认 false）。

### D5　权限确认：是否实现 `session/request_permission`

- **方案 A（推荐，P1 阶段）**：实现。对**破坏性且不可逆**的工具（`commandRun`、`fileWrite`、`editFile`、`delegate`）先发 `session/request_permission`，按用户选择决定放行或中止该工具调用。
  - 安全价值高：编辑器（尤其 Zed）会把命令/路径完整展示给用户，正是 ACP 设计的核心安全机制。
  - 实现代价（**已核实为阻塞性约束**）：`react-agent.ts:1372-1374` 在工具执行前调用 `onToolStart`，但其返回值**完全未被使用**，随后 `Promise.all` 无条件执行工具。因此**不扩展内核就无法在执行前阻断**。
- **方案 B**：不实现权限确认，靠 loop-agent 自有配置（`tools.enabled` 白名单 + 工作空间边界）兜底。P0/P1 可用，但用户失去「逐次确认」能力。
- 取舍：**推荐 A**，且必须配套 D5' 的内核增量。

### D5'　内核增量：新增 `onToolApproval` 钩子（D5 方案 A 的前置）

在 `AgentEvents` 增加**可选**钩子：

```ts
onToolApproval?(tool: string, args: Record<string, unknown>): void | Promise<void>;
```

- 语义：`react-agent.ts` 在 `onToolStart` 之后、`runner.run()` 之前 `await` 它；**抛错即拒绝该工具调用**，observation 记为「用户拒绝了该操作」，模型可据此调整策略（而非整体中断会话）。
- 兼容性：可选钩子，未注册时 `safeEvents` 归一为空实现，CLI/serve/既有单测**零影响**。
- 这是本方案唯一需要改动内核的一处，且为纯增量（不改任何现有钩子语义与调用顺序）。

### D7　会话标识：ACP sessionId 与 SessionStore id 的关系

- **推荐**：**一一对应**。`session/new` 直接返回 `SessionStore.createSession()` 生成的 `sess_<wsId8>_<ts>` 作为 ACP sessionId。好处：ACP 线程与 WebUI 会话共用同一份磁盘数据，用户在两端可看到同一批会话；`session/load` 实现成本极低。

### D8　`session/load`（历史回放）是否本期做

- **推荐**：**做，放在 P1**。SessionStore 已有全量消息，按 ACP 要求逐条回放为 `user_message_chunk`/`agent_message_chunk` 即可，实现量不大，但让「关掉编辑器再打开」体验完整。

### D9　编码与平台

- **推荐**：stdio 固定 UTF-8。`src/index.ts:16` 的 `chcp 65001` 在 Windows 上仅影响终端显示，不影响管道字节流；但 ACP 模式下应设 `process.stdout` 无 BOM、严格 LF 分隔。所有路径经 `canonicalWorkspacePath` 归一，避免 Windows 反斜杠与编辑器传来的 POSIX 风格路径不匹配。

### 5.2 `src/acp/transport.ts` + `src/acp/stdio.ts` — 传输层

**先抽象接口（D10 要求，P0 就做）**：

```ts
export interface AcpTransport {

  send(frame: string): void;   // 已序列化 + LF

}
```

stdio 是默认实现；P2 若要加远程，只需补 `http.ts` / `ws.ts` 两个实现，handlers/bridge **一行不改**。

| 接口 | 签名 | 说明 |
|---|---|---|
| `createStdioTransport` | `() => AcpTransport` | readline 按行解析；`writeFrame` 用劫持前捕获的原始 stdout |
| `installStdoutGuard` | `() => (s: string) => void` | D2：把 `process.stdout.write` 重定向到 stderr，返回原始写函数供协议层用 |


边界与错误处理：

| 情形 | 处理 |
|---|---|
| 非法 JSON 行 | 回 `-32700` ParseError，不崩 |
| 未知 method | 回 `-32601` MethodNotFound |
| 参数校验失败 | 回 `-32602` InvalidParams |
| 处理器抛异常 | 回 `-32603` InternalError，日志写 stderr |
| stdin EOF | 触发优雅关停（停调度器→断 MCP→exit） |

### 5.3 `src/acp/handlers.ts` — 方法分发

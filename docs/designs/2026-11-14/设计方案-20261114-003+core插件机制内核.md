## 一、背景与目标

### 1.1 为什么要这个模块

当前工程的能力单元全部是「模块级单例 + 直接 import」，装配靠人肉编排。以下均为 2026-11-14 代码核对数据（**注：本章数字已按当前代码重新核对，与上一版文档的旧数字有差异，见第十一章**）：

| 现象 | 实测数据 |
|---|---|
| 模块级单例 | `src/**` 共 17 处 `export const x = new X()`：16 处是自有类实例（`agent`/`configLoader`/`mcpManager`/`toolRegistry`/`llm` 等），1 处是 `new Set` 常量（`LOOPBACK_HOST`） |
| 装配编排 | `src/runtime/init.ts:37` 的 `initRuntime()` 串行 6 个编号阶段（`0` 迁移/引导 → `0.1` 配置 → `1` 内置工具+后台配置 → `2` MCP → `3` Skill；含 `0.1`/`1.1` 两个子步）；`src/api/bootstrap.ts:20` 的 `startApiServer()` 共 195 行，其中 9 处 `await import()` 动态装配组件 |
| 扩展点 | `AgentEvents`（`src/types.ts:596`）16 个回调；`createRoutes()` 返回 `Route[]`——都是「内向」的，注册后无法成组撤销 |
| 每空间一套依赖 | `WorkspaceRuntime`（`src/api/workspace-runtime.ts:41`）硬编码 8 个字段，加第 9 个组件要改 4 个文件 |

用户长期方向是接入插件生态，借鉴 Cordis 的插件/依赖注入机制，但**不直接引入 npm 包**：`cordis` 为 `4.0.0-rc.12`、API 未稳定；SEA 单文件打包与其运行期 `import()` 磁盘加载冲突；`deepseek-harness` 是 vendor 源码 + 27 处补丁。

### 1.2 本期只做「定义」，不做「接入」

**core 是一个自包含、不依赖本项目任何代码的独立库；本期也不被本项目任何代码引用。**

必须区分「本期不引用」与「将来不可引用」：用户已明确 core 后续要作为基础模块被其他模块（主工程、插件包、将来可能还有 CLI）引用，所以本期虽零接入，**包契约必须一次写对**（见 4.2），否则 P3 接入时要返工改配置。

```
loop-agent-command/
  src/                       ← 一行不动
  tests/                     ← 一个文件不加（当前 213 个 .test.ts，保持 213）
  desktop/                   桌面壳子包（Electron，自有 node_modules + lock，与本模块无关）
  webui/                     前端子工程（自有 node_modules + lock，与本模块无关）
  core/                      ★ 本期唯一新增：独立插件内核库
    package.json             自有依赖与 scripts
    tsconfig.json            自有编译配置
    tsup.config.ts           只产 ESM 产物
    vitest.config.ts         自有测试配置
    src/*.ts                 内核源码（8 个文件）
    tests/*.test.ts          内核单测（8 个文件）
```

**为什么这样切**：内核 API 一旦与业务耦合，就会被现有单例的形状带偏（比如为省事直接 `get<ConfigLoader>()`），失去通用性。先在空地上把机制定干净，后续接入只做「包装」不做「重塑」。

### 1.3 目标

`core/` 提供四件事，全部与业务无关：

1. **插件定义**：`apply(ctx)` + `inject` 依赖声明
2. **Context 服务容器**：按 key 寻址服务，消费方不 import 实现
3. **类型化事件**：`emit` / `serial` / `parallel` / `waterfall` 四种分发
4. **可逆副作用与 Fiber 生命周期**：注册的东西在卸载时自动、逆序撤销

### 1.4 设计约束

- **零运行时依赖**：只用 `node:` 内置模块（实测内核可以一个都不用）。
- **零反向依赖**：core 不 import 主工程任何代码；由 `boundary.test.ts` 断言锁死。
- **不破坏 SEA**：未来接入时插件来源只能是编译期静态数组，禁止磁盘 `import()`。
- **strict 模式**：与主工程一致（`strict: true`），内核不出现 `any`。
- **只出 ESM、只收 ESM**（用户 2026-11-14 定案 Q12）：产物单 ESM，第三方插件也必须 ESM；同时**禁止顶层 `await`**——TLA 会让将来任何 CJS 侧 `require` 抛 `ERR_REQUIRE_ASYNC_MODULE`。内核本身无 I/O，此约束天然满足，另在 P2 加断言锁死（见 8.3）。
- **主工程改动最小化**：业务代码（`src/`、`tests/`）一行不动；仅 3 处配置改动，详见 2.3 与 4.2。

## 二、现状梳理（2026-11-14 代码核对）

### 2.1 工程现状

| 所需能力 | 现状（带定位） | 结论 |
|---|---|---|
| 插件注册 | 无。全部靠 `import` 具体单例 | 需新建 |
| 服务寻址 | 无。消费方直接 `import { configLoader }` | 需新建 `ctx.get<T>()` |
| 可逆副作用 | 无。`createRoutes()` 返回数组，注册后不可成组撤销 | 需新建 `effect` + disposer 栈 |
| 生命周期 | 无状态机。组件自生自灭 | 需新建 Fiber 六态 |
| 诊断 | 无。插件不生效只能靠读代码 | 需新建 `diagnose()` |

### 2.2 进程边界与加载方式（决定产物格式的前提）

包契约怎么定，取决于「谁会以什么方式加载 core」。按当前实际架构核定：

| 角色 | 现状（已核实代码） | 与 core 的关系 | 加载方式 |
|---|---|---|---|
| **主工程后端**（`src/`） | `type: module`，SEA 全内联（`scripts/build-sea.mjs:31` `noExternal: [/^(?!node:)/]`） | P3 起在同进程内 `import` core | **ESM**，且构建期被内联，**产物层面天然单份** |
| **桌面端**（`desktop/`） | 「`spawn` 后端子进程 + `loadURL('http://127.0.0.1:<port>')`」的**纯外壳**（`desktop/src/main.ts:201` 调 `startBackend`、`:339` 的 `loadURL`、`desktop/src/backend-process.ts:77` 的 `spawn`）；`dependencies` **为空**；`src/**` 27 处 import 全为 `node:*`/`electron`/相对路径 | **不引用 core、不引用主工程**；不参与插件树 | 无（跨进程 HTTP） |
| **第三方插件** | 尚未落地 | 将在后端进程内加载 | **只收 ESM**（用户定案）→ 与宿主同格式，无混合消费 |

**三条由此得出的判断**：

1. **`desktop` 是 CJS 这一点，不构成双产的理由**。它与后端是跨进程关系，对象不跨进程传递，`instanceof` 与服务表跨进程本就不可见——**跨进程重复无害**。
2. **「同进程 core 实例重复」的唯一风险来源**：同一进程内 ESM 加载器与 CJS 加载器各实例化一次（Dual Package Hazard）。
3. **同进程消费方全部是 ESM，且 core 只出 ESM ⇒ 天然单实例**（Node 模块缓存保证同一解析路径只求值一次；已实测：重复 `import` 两次得到同一 `CoreError`/`ServiceRegistry`）。这正是「只收 ESM」后不再需要双入口 wrapper 的原因。

### 2.3 仓库既有子工程布局（决定 workspaces 的落法）

**这是上一版文档完全遗漏的事实，必须补入**——仓库里已有两个自带独立依赖的子工程：

| 子工程 | `node_modules` | `package-lock.json` | 是否纳入 workspaces |
|---|---|---|---|
| `desktop/` | ✅ 有 | ✅ 有 | **本期不纳入**（会提升整棵 Electron 依赖树、拖慢主工程安装） |
| `webui/` | ✅ 有 | ✅ 有（`private: true`） | **本期不纳入**（前端工具链独立演进） |

已用隔离探针实测「根加 `workspaces: ["core"]` 后」的影响：

```
webui/node_modules 仍存在                : true   ← 不被吞并
webui/package-lock.json 未被改写         : true   ← 哈希逐字节未变
core/node_modules 未生成                 : true   ← workspaces 提升生效
node_modules/@t/core 是链接              : true   （Windows 为 JUNCTION）
根 lock 新增条目                          : ['core', 'node_modules/@t/core']  ← 仅 2 条
根 lock 删除条目                          : []
```

**结论**：既有子工程的独立依赖布局**不受影响**，加 workspaces 的 lockfile 代价实测仅 2 条新增、0 条删除、1 条根条目变更（追加 `workspaces` 字段）。

**另一条实测修正**：根 `package.json` **不加 `private` 字段，workspaces 同样生效**（上一版未验证此点，若文档要求「必须加 private」则属多余约束）。

## 三、总体思路

### 3.1 目录切分与依赖方向

```
                    ┌──────────────────────────────┐
                    │  第三方插件（只收 ESM）        │
                    └───────────────┬──────────────┘
                                    │ import（同进程）
┌───────────────┐    P3 接入    ┌────▼─────────────────┐
│ 主工程 src/    │──────────────▶│  @loop-agent/core    │
│ （ESM，SEA）   │   import       │  零依赖 / 零反向依赖  │
└───────────────┘               └──────────────────────┘
        ▲                                 ▲
        │ spawn + HTTP（跨进程）           │ workspaces 链接（单份物理副本）
┌───────────────┐               ┌────────┴─────────────┐
│ desktop/ 外壳  │               │ 根 node_modules       │
│ （CJS，不引用）│               │ @loop-agent/core→core │
└───────────────┘               └──────────────────────┘
```

- **本期只落地最下面的链接与 `core/` 本体**，上面两条引用关系（P3）不在本期。
- 依赖方向严格单向：`core` 不指向任何人；主工程与插件只「引用」core。

### 3.2 与 Cordis 的取舍（已联网核实）

| 机制 | Cordis 做法 | 本内核 | 为什么不同 |
|---|---|---|---|
| 插件形态 | 函数 / 带 `apply` 对象 / `Service` 子类 三形态 | 只支持前两种 | 类继承 + `super(ctx)` 魔法多，strict 下类型复杂；需要提供服务时 `ctx.provide()` 就够 |
| 取服务 | Proxy 拦 `ctx.xxx` | 显式 `ctx.get<T>('key')` | Proxy 在 strict TS 下类型失真、断点调试难 |
| 依赖注入 | `inject` 声明，未满足则停在 PENDING；支持 `{required, optional}` | **采纳**，含动态重载 | 最有价值的一条，尤其对渐进接入 |
| 事件分发 | `emit`/`waterfall`/`parallel`/`serial`/`bail` 五模式 | 前四种 | `bail` 是 `serial` 的同步版，本项目全异步，收益≈0 |
| 可逆副作用 | 逆序撤销，异步**并发** | 逆序撤销，异步**串行** | 本项目 disposer 会关 PTY、断 MCP、写文件，并发易撞车 |
| 隔离 | `ctx.isolate()` 服务分仓 | **采纳**（只隔离服务，不隔离事件） | 多工作空间需要；事件总线必须全局，否则跨空间通知断裂 |
| 加载器 | `cordis.yml` + 运行期 `import()` | 不实现（未来用静态数组） | SEA 单文件没有可 import 的磁盘模块树 |
| 配置改写 | `ctx.intercept()` | 不实现 | 本期无需求 |

### 3.3 包命名：避开 `loop-agent-core` 撞车

**已知冲突**：`loop-agent-core` 已被 SEA 后端二进制占用——`desktop/resources/loop-agent-core.exe`（`scripts/build-desktop.mjs:159` 重命名产物、`desktop/src/backend-path.ts:5` 的 `BACKEND_EXE_NAME`）。若新包同名，将来排查问题、构建产物、日志里会两义。

| 方案 | 包名 | 目录 | 评价 |
|---|---|---|---|
| **A（推荐）** | `@loop-agent/core` | `core/` | npm scope 天然隔离于 exe 文件名；`@loop-agent/` 预留未来 `@loop-agent/cli` 等 |
| B | `loop-agent-plugin-core` | `core/` | 描述最准，但与「模块名称就是 core」字面偏离 |
| C | `loop-agent-core` | `core/` | 与 exe 同名，不推荐 |

**结论 A**：目录名仍是 `core/`（符合「模块名称就是 core」），包名用 scope 避开撞车。

| 编号 | 决策 | 选项 | 结论 |
|---|---|---|---|
| **D1** | 目录与形态 | A `core/` 独立子包 / B `src/core` 主工程内 / C `src/plugin/core` | **A**：用户要求独立模块，且内核要能被多宿主复用 |
| **D2** | 包名 | A `@loop-agent/core` / B `loop-agent-plugin-core` / C `loop-agent-core` | **A**：避开 `loop-agent-core.exe` 撞车 |
| **D3** | 依赖布局 | A **npm workspaces** / B 各管各 `node_modules` + `file:` / C `npm link` | **A**：workspaces 以链接提升到根 `node_modules`，子包 import 解析到同一物理路径，模块缓存保证单实例。B/C 都可能产生嵌套副本。代价：根 `package.json` 加 `workspaces`（见 4.2） |
| **D4** | 本期是否接入现有组件 | A 完全不接 / B 做 1 处验证性接入 | **A**：保持内核纯净，避免 API 被现有单例形状带偏 |
| **D5** | 取服务方式 | A `ctx.get<T>('key')` / B Proxy `ctx.key` | **A**：strict 下类型精确、可断点 |
| **D6** | 插件形态 | A 函数 + 对象两形态 / B 再加 `Service` 子类 | **A**：少一层继承魔法 |
| **D7** | 依赖声明 | A `string[]` 与 `{required,optional}` 并存 / B 只支持硬依赖 | **A**：软依赖是渐进接入的前提 |
| **D8** | 事件模式 | A 四种 / B 五种含 `bail` | **A**：全异步场景 `bail` 收益≈0 |
| **D9** | disposer 撤销 | A 逆序 + 异步串行 / B 仿 Cordis 异步并发 | **A**：可推理、不撞车（disposer 会关 PTY/断 MCP） |
| **D10** | FAILED 处理 | A 终态不自动重试，`reload()` 显式 / B 退避自动重试 | **A**：自动重试会掩盖 bug |
| **D11** | 依赖动态重载 | A 采纳 epoch 机制 / B 只在加载时检查一次 | **A**：否则热替换 provider 会留悬空引用 |
| **D12** | isolate 范围 | A 只隔离服务，事件不隔离 / B 全隔离 / C 不做 | **A**：跨域通知必须走全局总线 |
| **D13** | `exports` 条件 | A `types`+`import`+`default` 单分支 / B `import`+`require` 双分支各带 `types` / C 不写 `exports` | **A**：只出单 ESM 产物，故单分支。`default` 必须补（否则 CJS `require` 解析失败）；`types` 写法见 4.1 |
| **D14** | 产物格式 | A **单 ESM 产物** / B 双入口 + 单实现 / C 简单双产 | **A**：产物实测仅 3 个文件，无 `.cjs`/`.d.cts`/wrapper。C 不可选（实测双实例、`instanceof` 双向 false） |
| **D15** | 双副本防范 | A **workspaces 物理消除** / B 运行期自检 / C `Symbol.for` brand / D `globalThis` 托管 | **A**：「装两份」由 workspaces 解决；「一份装但加载两次」在只收 ESM 后已不可能。B 只能发现不修复且症状会被 `diagnose()` 掩盖；D 会破坏多 Context 隔离 |
| **D16** | 版本策略 | A `0.1.0` 起步、`0.x` 期间 breaking 只升次版本 / B 直接 `1.0.0` | **A**：内核 API 稳定度独立于主工程 `0.2.0` |
| **D17** | 顶层副作用 | A `sideEffects: false`，加载期零副作用 / B 允许加载期建全局单例 | **A**：可被摇树；避免「import 即生效」破坏显式注册语义 |

### 4.1 包契约细则（D13 展开，**含本轮最大的结论纠正**）

`package.json` 关键字段：

```jsonc
{
  "name": "@loop-agent/core",
  "version": "0.1.0",
  "type": "module",
  "main": "./dist/index.js",            // 老工具兜底（无 exports 支持时）
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",     // 类型入口（与实现同址，见下）
      "import": "./dist/index.js",      // 唯一实现（ESM 单产物）
      "default": "./dist/index.js"      // 必需：给 CJS 解析器一个落点
    }
  },
  "files": ["dist"],
  "sideEffects": false,
  "engines": { "node": ">=20.10" }
}
```

#### ① `default` 条件：必须写（实测，上一版此结论正确）

| 配置 | CJS `require('@loop-agent/core')` 实测结果 |
|---|---|
| `{types, import}` | ✗ `ERR_PACKAGE_PATH_NOT_EXPORTED`（CJS 条件集里没有 `import`，整个条件对象无一命中） |
| `{types, import, default}` | ✓ 现代 Node 成功返回 ESM 命名空间 |
| `{types, import, default}` + 旧 Node（`--no-experimental-require-module`） | ✗ `ERR_REQUIRE_ESM`（「只收 ESM」的预期代价） |

`default` 与 `import` 指向**同一文件**，不产生第二份实现、不破坏单实例，成本为零。

#### ② `types` 条件的真实规则（**纠正上一版的错误结论**）

> **上一版结论（错误）**：「`types` 必须放在条件对象最前，否则 TS 报 `TS7016`」。
> **本轮实测矩阵（Node v24.17.0 / TS 5.x，`moduleResolution: nodenext` 与 `bundler` 两套配置均试）证明此说不成立。**

**实测结果**：

| # | `exports["."]` 键顺序 | 声明文件位置 | 结果 |
|---|---|---|---|
| C1 | `types, import, default` | `dist/index.d.ts`（与实现同址） | ✓ 解析到声明 |
| C2 | `import, types, default` | `dist/index.d.ts`（同上） | ✓ 解析到声明 |
| C3 | `import, types, default` | `types/index.d.ts`（异地） | ✓ 解析到声明 |
| C4 | `types, import, default` | `types/index.d.ts`（异地） | ✓ 解析到声明 |
| C5 | `import, default`（**完全无 `types`**） | 无声明文件，仅 `dist/index.js` | ✗ **`TS7016`** |
| F1 | `import, default`（**完全无 `types`**） | `dist/index.d.ts`（与实现同址） | ✓ 解析到声明 |
| F2 | `types, import, default` | `dist/index.d.ts` | ✓ 解析到声明 |
| F3 | `import, types, default` | `dist/index.d.ts` | ✓ 解析到声明 |
| G1 | `types` 在最前，指向 `types/index.d.ts` | 另有 `dist/index.d.ts` | 选中 **`types/index.d.ts`** |
| G2 | `types` 在中间，指向 `types/index.d.ts` | 另有 `dist/index.d.ts` | 选中 **`dist/index.d.ts`** |

**由此得出的三条准确结论**：

1. **`TS7016` 的真因是「完全解析不到声明文件」，与 `types` 键的位置无关**（对照 C5 与 F1：同样的键顺序，有同址声明就不报错）。
2. **在 core 的真实产物布局下（`tsup` 把 `index.d.ts` 与 `index.js` 放在同一 `dist/`），`types` 条件甚至可以省略**（F1 通过）——因为 TS 会按 `.js` 同名推断 `.d.ts`。
3. **顺序只在一种情况下才有影响**：`types` 指向的声明与实现**不同址**，且 `import` 写在 `types` 之前——此时 TS 选中实现旁的声明（G1 vs G2 差异）。core 不存在这种布局，故**顺序对 core 不构成风险**。

**本方案的落地取舍**：仍**照常书写 `types` 并在物理上放在前面**——理由是「零成本惯例 + 对未来改双产/换构建工具的免疫力」，**而不是**因为「不这么写会报错」。验收项也据此改写（见 8.3，不再要求「反向必须报错」这种已被证伪的断言）。

#### ③ 承认的代价（用户已知并接受）

| 代价 | 具体表现 | 缓解 |
|---|---|---|
| CJS 消费方需较新 Node | `require('@loop-agent/core')` 需支持 `require(esm)` 的 Node；< 20.19/22.12 报 `ERR_REQUIRE_ESM` | 当前无任何 CJS 消费方；README 写明门槛 |
| 禁止顶层 `await` | 一旦出现 TLA，CJS `require` 抛 `ERR_REQUIRE_ASYNC_MODULE` | 内核无 I/O、无 TLA，P2 加断言锁死 |
| 第三方插件只能 ESM | CJS 编写的插件不被接受 | 已定案；插件在宿主进程内加载，格式统一反而减少一类故障 |

### 4.2 双副本问题：workspaces 消除「装两份」，单 ESM 消除「加载两次」

**双副本有两个独立来源，解法不同**：

| 来源 | 表现 | 由谁消除 |
|---|---|---|
| **装了两份** | `core/node_modules` + 主工程 `node_modules` 各一份 | **workspaces**（物理消除） |
| **一份装但加载两次** | ESM loader 与 CJS loader 各实例化一次 | **只收 ESM 从架构上排除**（同进程无 CJS loader） |

**为什么必须彻底**：双副本的后果是**静默错误**，不是「慢一点」——

| 症状 | 后果 |
|---|---|
| `instanceof CoreError` 跨副本为 `false` | 错误处理全部失效，被当成未知错误吞掉 |
| 两份 `Fiber` 状态机 | `dispose()` 管不到对方插件，泄露 PTY / MCP 连接 |
| 两份 `ServiceRegistry` | `ctx.get()` 查不到对方提供的服务 |

最危险的是：这三个症状与 `diagnose()` 要诊断的「插件莫名不生效」**完全同形**，而 `diagnose()` 只在单副本内可见，会报告「一切正常」——**问题被完美掩盖**。因此不接受「检测并报警」这类方案。

**A 方案实测数据（隔离目录构造性验证）**：

```
node_modules/@t/core →  链接到 ../core     ← 物理上仅此一份
app/node_modules                            ← 不存在（无嵌套副本）
两次 import ID 相同        : true
解析路径                  : file:///.../core/index.js   ← 直接指向 workspace 源目录
```

**配套四条硬约束（写入 README 与 CI）**：

1. **`@loop-agent/core` 只允许出现在 `dependencies`/`peerDependencies` 的 workspace 声明中**，禁止子包自行 `npm install` 它。
2. **禁止 `npm link`**：workspaces 已用链接达到同一效果，再 `link` 会引入第二套解析路径。
3. **构建期断言（P2）**：`boundary.test.ts` 遍历 `node_modules`，断言 `@loop-agent/core/package.json` **只有一份**。
4. **插件包必须 `external`**：任何将来引用 core 的插件包，tsup/esbuild 必须 `external: ['@loop-agent/core']`，不得把 core 打进自身产物。

**与 SEA 的叠加红利**：主工程 SEA 全内联（`scripts/build-sea.mjs:31`）会把 core 源码打进单文件，**产物层面天然只有一份**。workspaces 保证开发期单份，SEA 保证分发期单份。

**明确不做**：

- ❌ `CORE_INSTANCE_ID` / `import.meta.url` 运行期自检——A 方案下「有两份」应是不可能状态，保留探测只会掩盖配置错误
- ❌ `Symbol.for` brand / `globalThis` 托管——后者会破坏多 Context 隔离（与多工作空间设计冲突）
- ❌ `instanceof` 判别降级为 `code` 字符串比较——A 方案下 `instanceof` 本就正确

> 唯一保留的一处防御：错误族仍带 `code` 字段（见 5.8），因为它在日志、HTTP 状态码映射、跨进程（HTTP 边界）场景下本来就需要，与双副本无关，成本为零。

**`core/tsup.config.ts` 两条硬约束（实测）**：

1. **tsup 的 `outDir`/`entry` 解析基准是 cwd，不是配置文件所在目录**。在仓库根执行 `npx tsup --config core/tsup.config.ts` 会把产物写到**根目录下的 `outDir`**。因此 build 脚本必须在 `core/` 内执行：`npm run build -w @loop-agent/core`，不能从根带 `--config` 调用。

### 5.2 `src/types.ts` — 核心类型

```ts
/** 清理函数：允许异步 */
export type Disposer = () => void | Promise<void>;

/**
 * 依赖声明：
 * - string[]              → 全部硬依赖
 * - { required, optional } → 区分硬/软依赖
 */
export type Inject = string[] | { required?: string[]; optional?: string[] };

export type Plugin = PluginFunction | PluginObject;

export type PluginFunction = (ctx: Context) => void | Promise<void>;

export interface PluginObject {
  /** 诊断显示名；缺省取函数名，再缺省 'anonymous' */
  name?: string;
  /** 硬依赖未满足时 Fiber 停在 PENDING，绝不执行 apply */
  inject?: Inject;
  /** 插件主体：apply 内注册的一切由 Fiber 托管 */
  apply(ctx: Context): void | Promise<void>;
}

export type FiberState =
  | 'PENDING'    // 已声明，硬依赖未就绪
  | 'LOADING'    // 依赖就绪，apply 执行中
  | 'ACTIVE'     // 正常运行
  | 'FAILED'     // apply 抛错（终态，需显式 reload）
  | 'UNLOADING'  // 正在撤销
  | 'DISPOSED';  // 已完全卸载
```

### 5.3 `src/context.ts` — Context 门面

```ts
export interface Context {
  // ── 服务 ──
  /** 读服务；未提供返回 undefined（软依赖用法） */
  get<T>(key: string): T | undefined;
  /** 提供服务；返回的 Disposer 在 Fiber 卸载时自动执行 */
  provide<T>(key: string, impl: T): Disposer;
  /** 当前可见服务 key（诊断用） */
  services(): readonly string[];

  // ── 可逆副作用 ──
  /** 立即执行 body，其返回的 disposer 挂到当前 Fiber */
  effect(body: () => Disposer, label?: string): Disposer;

  // ── 事件 ──
  on<K extends keyof Events>(event: K, listener: Events[K]): Disposer;

  // ── 子插件 ──
  plugin(p: Plugin, opts?: { name?: string }): Fiber;
  /** 隔离域：子树内指定 key 指向独立服务实例 */
  isolate(keys: string[]): Context;

  // ── 诊断 ──
  /** 全部 Fiber 状态 + 未满足 inject + 失败原因 */
  diagnose(): DiagnosticReport;
}
```

`Events` 以泛型参数注入，业务侧自行声明事件表（**不用 TS 全局声明合并**，避免多模块撞名）：

```ts
interface AppEvents extends EventMapBase {
  'agent/tool-start': (tool: string, args: Record<string, unknown>) => void;
  'agent/tool-end': (tool: string, result: string) => Promise<void> | void;
}
const bus = new TypedEventBus<AppEvents>();
```

### 5.4 `src/fiber.ts` — Fiber 生命周期

```ts
export interface Fiber {
  readonly id: string;
  readonly name: string;
  readonly state: FiberState;
  /** FAILED 时有值，含原始 error 与 apply 栈 */
  readonly error?: CoreError;
  /** 显式卸载；等全部 disposer（含异步）执行完才 resolve */
  dispose(): Promise<void>;
  /** 从 FAILED 重新加载；依赖变更时由内核自动调用 */
  reload(): Promise<void>;
}
```

**四条不变量（单测必须逐条覆盖）**：

1. `dispose()` **幂等**——重复调用返回同一 Promise，disposer 不重复执行。
2. disposer **逆序**执行，异步 disposer **串行** await。
3. 单个 disposer 抛错**不中断**后续撤销，错误聚合为 `AggregateError` 记录进 `diagnose()`。
4. 父 Fiber 卸载时先递归 dispose 子 Fiber，再撤销自身 disposer。

### 5.5 状态机

```
ctx.plugin(p)
   ↓
PENDING ──依赖满足──> LOADING ──apply 成功──> ACTIVE
   ↑                    │                      │
   │                    └─apply 抛错→ FAILED   │ 依赖提供者变化(epoch)
   │                                    │       ↓
   └────────依赖重新满足─────────────────┴──> UNLOADING → DISPOSED
                                                （逆序执行 disposer）
```

要点：

- `PENDING` 期间 `apply` **不被调用**（Cordis 最容易踩的坑，`diagnose()` 专门解决它）。
- `FAILED` 是**终态**，不自动重试（避免掩盖 bug），仅 `reload()` 或依赖变更才走。
- 依赖提供者消失 → 依赖方递归卸载；重新出现 → 自动重载回 `ACTIVE`。

### 5.6 `src/events.ts` — 事件四模式

| 方法 | await | 顺序 | 返回 | 用途 |
|---|---|---|---|---|
| `emit(e, ...args)` | 否 | 注册序 | 无 | 纯通知 |
| `serial(e, ...args)` | 是 | 注册序，首个非 `undefined` 胜出即停 | 有 | 单决策 |
| `parallel(e, ...args)` | 是 | 全部并行（`allSettled`） | 无 | 扇出 |
| `waterfall(e, fallback, ...args)` | 是 | 注册序，监听器收 `next` | 有 | 拦截改写 |

- 无监听器：`emit`/`parallel` 空操作，`serial` 返回 `undefined`，`waterfall` 调 fallback。
- 监听器抛错：`emit`/`parallel` 记日志不外抛；`serial`/`waterfall` 外抛（调用方在等值）。
- `waterfall` 语义：监听器不调 `next()` 即短路；全链都委托则执行 `fallback`。

### 5.7 `src/service.ts` — 服务注册表与 isolate

- 同一 key 被两个 **ACTIVE** Fiber 同时提供 → `ServiceConflictError`。
- 提供者卸载 → key 自动失效 → 依赖方重算。
- `ctx.isolate(['store'])`：子树内 `store` 走独立分仓，父子互不可见、互不覆盖。
- **事件总线不隔离**（跨域通知必须全局）。

### 5.8 `src/errors.ts` — 错误族（6 类）

| 类 | code | 场景 |
|---|---|---|
| `CoreError` | — | 基类，携带 `pluginName` / `fiberId` / `cause` |
| `CircularDependencyError` | `CORE_CIRCULAR_DEP` | A↔B 互相硬依赖 |
| `ServiceNotFoundError` | `CORE_SERVICE_MISSING` | 强制 `requireService()` 但未提供 |
| `ServiceConflictError` | `CORE_SERVICE_CONFLICT` | 两个 ACTIVE Fiber 抢同一 key |
| `PluginLoadError` | `CORE_PLUGIN_LOAD` | `apply` 抛错（包装原 error + 栈） |
| `FiberDisposedError` | `CORE_FIBER_DISPOSED` | 在已 DISPOSED 的 ctx 上注册 |

### 5.9 `diagnose()` — 把「我的插件为什么没生效」变成一次调用

```ts
    id: string;
    name: string;
    state: FiberState;

    /** FAILED 时的错误摘要 */

  }>;

}
```

### 11.2 已作废结论与证伪依据（只归档，防止后来者翻出来用）

| 已作废的旧结论 | 当前结论 | 证伪/替换依据 |
|---|---|---|
| 「`types` 必须写在 `exports` 条件对象最前，否则报 `TS7016`」 | `TS7016` 的真因是「完全解析不到声明」；顺序仅在「`types` 指向异地声明且 `import` 在其前」时影响选中哪份声明 | 实测矩阵 C1–C5 / F1–F3 / G1–G2（见 4.1②） |
| 「core 需产出 CJS + ESM 双产物，配 ESM 薄 wrapper 脚本」 | 只出单 ESM，无 wrapper、无 `.d.cts` | Q12 定案 + 实测：单 ESM 重复 import 同实例；SEA 内联不受影响 |
| 「desktop 后续作为插件实现并引用 core，而它是 CJS ⇒ 需双产」 | 前提不成立：desktop 是纯外壳、`dependencies` 空、零 core 引用 | 代码核实（`desktop/src/main.ts:201`、`desktop/src/backend-process.ts:77`、`desktop/src/main.ts:339`） |
| 「简单双产（`format:['esm','cjs']`）可以接受」 | 不可选：实测 `instanceof` 双向 false、两份 `ServiceRegistry` 互不可见 | 实测：`ESM.CoreError === CJS.CoreError : false` |
| 「必须加 `CORE_INSTANCE_ID` 运行期自检」 | 不做：A 方案下双副本为不可能状态，探测只会掩盖配置错误 | D15 定案，改为构建期单副本断言 |
| 「`exports` 顺序反向必须复现 `TS7016`，以此做回归」 | 该验收项本身建立在错误结论上，已替换为 8.3 的三条准确断言 | 同上实测矩阵 |
| 「根 `package.json` 必须加 `private: true` 才能用 workspaces」 | 不需要；无 `private` 亦生效 | 隔离探针实测 |
| 「加 workspaces 会让 lockfile 大面积变动、波及 desktop/webui」 | 实测仅 +2 条、0 删除；`webui/package-lock.json` 逐字节未变 | 探针实测（见 2.3） |
| 「依赖失效时依赖方 → `DISPOSED`」 | → `PENDING`（可自动回 `ACTIVE`，副作用照样撤销干净） | `DISPOSED` 为终态：`start()` 直接 return、`reload()` 抛 `FiberDisposedError`，不存在回 `ACTIVE` 的合法路径（见任务 03 §2.1 D18） |

## 一、任务目标需求

### 1.1 背景（痛点）

需求 20261114-003 把 `PluginRegistry` 放进了 `core`，但这是**分层错位**：

1. **职责错位**：`PluginRegistry` 回答的是「挂载哪些插件、按什么顺序、下次还记不记得」，属于**宿主/应用装配**层；`core` 该回答的是「插件长什么样、怎么挂、怎么撤」。
2. **能力冲突**：用户要求注册中心**支持持久化**，而 core 设计 5.10 明确写死「纯内存，无磁盘 IO」，并把「磁盘动态加载」列为**非目标**。把持久化塞进 core 等于推翻自己的内核设计。
3. **证据充分**：`PluginRegistry` 的实现只有 75 行，全部建立在 `createHost()` + `createRootContext()` 之上，`context.ts` / `fiber.ts` / `service.ts` / `events.ts` 一行都不用改。这说明它天然是可外移的。

用户原话：「core 之前我设计错了，core 里只做插件核心的定义，具体的注册中心放在 main 模块里。」

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
|---|---|---|
| 内核纯定义层（Plugin/Context/Fiber/Event/Service/Errors） | `core/src/{types,context,fiber,events,service,errors}.ts` 齐备，`context.test.ts` 等 10 个测试文件全绿 | **保留，一字不改** |
| 内核里的清单挂载 | `core/src/registry.ts`，75 行薄封装，纯内存 | **删除，外移到 main** |
| core 导出面 | `core/src/index.ts:29` `export { PluginRegistry } from './registry.js'` | 删该行 |
| core 文档与契约声明 | `README.md` §3.8、`CHANGELOG.md` 类清单第 9 项、`types.test-d.ts:282`、`diagnose.test.ts:154-284`、`external-consumer.test.ts:131/148-150/173` | 全部同步删除或替换 |
| 持久化插件清单 | **完全缺失**：仓库内无任何插件清单文件、无 `plugins/` 目录、无清单读写代码 | **新增（main）** |
| 新主工程入口 | 现有入口 `src/index.ts`（CLI / `--serve`），装配靠 `initRuntime()` 串行 6 步 + `startApiServer()` 195 行 | **新增 `main/`，本轮只搭骨架，不迁移 `src/`** |
| 用户目录解析 | `src/user-home.ts:18` `loopAgentHome()`，读 `LOOP_AGENT_HOME` 环境变量，测试隔离依赖它 | **main 内自查实现同语义**（不 import `src/`，保持零反向依赖） |
| 原子写落盘 | 主工程无统一原子写工具（各模块自行 `writeFileSync`） | main 内实现 tmp + rename |
| workspaces 链接 | 根 `package.json` 已有 `workspaces: ["core"]`，实测 `node_modules/@loop-agent/core` 是 Junction 链接 | **追加 `"main"`** |

### 1.3 任务目标

1. **core 收敛为纯定义层**：删除 `PluginRegistry` 及其全部导出、文档、测试；其余契约一字不改；版本升 `0.2.0`。
2. **新建 `main/` 作为新主工程入口**：本轮只做**基础主工程框架**——host 创建、根 Context、少量内置基础服务、启动/关停骨架。**不迁移 `src/` 任何业务代码。**
3. **在 main 中实现支持持久化的 PluginRegistry**：清单落全局 `~/.loop-agent/plugins/registry.json`，写操作后立即原子落盘，重启能还原并重新挂载。

## 二、方案设计

### 2.1 总体思路

```
                        ┌─────────────────────────────────────┐
                        │  main/  @loop-agent/main            │
                        │                                     │
  ┌─────────────────────▼──────────────────┐                  │
  │ PersistentPluginRegistry (D5)          │                  │
  │  ├─ restore()      启动还原 (D6)        │                  │
  │  ├─ mount(entry)   挂载 + 落盘          │                  │
  │  ├─ enable/disable 启停 + 落盘 (D7)     │                  │
  │  ├─ unmount(id)    卸载 + 落盘          │                  │
  │  ├─ reorder(ids)   排序 + 落盘          │                  │
  │  └─ diagnose()     合并 core 诊断        │                  │
  └──────────┬──────────────────┬───────────┘                  │
             │ 组合              │ 读写清单                      │
  ┌──────────▼──────────┐  ┌────▼──────────────────────────┐   │
  │ createMainHost()    │  │ PluginStore (D8/D9)           │   │
  │  host + root ctx    │  │  read / write 原子落盘         │   │
  │  + 内置基础服务      │  │  schemaVersion + 容错          │   │
  └──────────┬──────────┘  └────┬──────────────────────────┘   │
             │                  │                              │
             │                  └──▶ ~/.loop-agent/plugins/     │
             │                        registry.json  (D3)       │
  ┌──────────▼──────────────────────────────────┐              │
  │  @loop-agent/core  0.2.0（纯定义层，D2）      │              │
  │  createHost / createRootContext / Plugin ... │              │
  │  ✗ PluginRegistry                            │              │
  └─────────────────────────────────────────────┘              │
                        ▲                                       │
                        │ workspaces 单副本链接                   │
                        └───────────────────────────────────────┘
```

数据流（挂载一个插件）：`registry.mount(entry)` → 解析 `specifier` 动态 `import()`（D10）→ `ctx.plugin(mod)` → 记录 Fiber 与条目 → `store.write(清单)`（D4，失败只记录）→ 返回 Fiber。

### 2.2 关键设计决策

#### 已由用户拍板（D1–D4）

| 编号 | 决策 | 取舍与被否决项 |
|---|---|---|
| **D1** | `main/` 是**新建独立子包**，作为新主工程入口，本轮只搭基础框架（host + 根 Context + 基础服务 + 启停骨架），**不迁移 `src/`** | 否决 B「main 取代 src 本轮全量迁移」（数千行、与既有「P3 再逐步包装」定案冲突、无收益） |
| **D2** | core 的 `PluginRegistry` **直接删除**，core 升 `0.2.0`；同步删导出/文档/测试 | 否决「保留但 `@deprecated`」（会留下两套注册中心语义并存的歧义窗口，且 core 的「纯内存」契约与持久化需求不可调和） |
| **D3** | 清单落**全局** `~/.loop-agent/plugins/registry.json`，跨工作空间共享一套 | 否决 B「每工作空间一份」（插件是进程级能力，不该随工作空间漂移）；否决 C「全局 + 工作空间覆盖」（两套合并规则，徒增复杂度，本期无需求） |
| **D4** | 写操作后**立即原子写**，失败只记录、不打断挂载 | 否决 B「退出时统一落盘」（崩溃即丢变更，与「重启还原」目标冲突） |

#### 本方案新增，待确认（D5–D12）

| 编号 | 决策 | 理由 | 被否决项 |
|---|---|---|---|
| **D5** | 类名用 **`PersistentPluginRegistry`**，与 core 已删的 `PluginRegistry` 刻意区分；它**组合**而非继承 core 的容器能力（内部持 `createRootContext()` 结果） | 名字直接体现「持久化」这一新增职责；不继承意味着 core 侧零耦合，core 后续演进不会牵动它 | 复用 `PluginRegistry` 同名（迁移期会分不清指哪一层） |
| **D6** | 持久化**只存插件清单**（`id` / `specifier` / `enabled` / `order` / `options`），**绝不存服务快照** | 服务是运行时对象（闭包、句柄、DB 连接），序列化必然失真；core 的不变量是「服务由 Fiber 托管、随卸载撤销」，存快照等于绕过生命周期 | 存服务快照（无法序列化、破坏不变量） |
| **D7** | 清单条目引入 **`enabled`** 布尔位：`disable` 只卸载 Fiber **但保留条目**；`enable` 重新挂载 | 让「暂时关掉某个插件」与「彻底删除」区分开。否则用户临时停用就要丢掉配置 | 只有「挂载/卸载」两态（停用即需重新填写配置） |
| **D8** | 原子写：写 `registry.json.tmp.<pid>.<seq>` → `rename` 到目标；**Windows 上目标已存在时先 `rm` 再 `rename`**（`rename` 覆盖在 Windows 上对已存在文件非原子且可能 `EPERM`） | 保证读方永远看不到半截 JSON；Windows 的 rename 语义必须特殊处理，否则会出现「偶发写失败」 | 直接 `writeFile`（读到半截即解析失败） |
| **D9** | 清单带 **`schemaVersion: 1`**；读到损坏 JSON / 版本不识别 / 字段类型不符时**降级为空清单并保留原文件**（改名为 `registry.json.bad.<ts>`），不抛错阻断启动 | 插件清单损坏不该让主工程起不来；保留坏文件便于用户/开发者取证 | 直接抛错（一个坏文件锁死启动）；静默丢弃（丢证据） |
| **D10** | 插件加载走**动态 `import(specifier)`**，仅支持 ESM；`specifier` 允许相对路径 / 绝对路径 / 包名；加载失败进 `diagnose()`，**不抛出**（与 core「单插件 FAILED 不中断其余」一致） | 沿用 20261114-003 的「只收 ESM」定案；加载失败是常态（插件被删、依赖缺），不该拖垮宿主 | 同步 `require`（core 只出 ESM，且 CJS 消费门槛高）；加载失败直接抛（一个坏插件锁死启动） |
| **D11** | `main` 也配 `tsup` 的 **`external: ['@loop-agent/core']`**，且 `main/tests/boundary.test.ts` 断言「单副本 + 零对 `src/` 的反向依赖 + 依赖仅 core」 | core README §四「打包铁律」：不 external 会双副本，`instanceof` 静默失效、服务表互不可见 | 不 external（本质性 bug，且静默无报错） |
| **D12** | 用户目录解析在 main 内**自查实现**（读 `LOOP_AGENT_HOME`，缺省 `join(homedir(), '.loop-agent')`），**不 import `src/user-home.ts`** | main 要能独立成包，import `src/` 就破坏「零反向依赖」边界；测试隔离语义必须保留，否则测试会污染真实用户目录 | import `src/user-home.ts`（越界依赖，使 main 无法独立演进/发布） |

### 2.3 联网检索要点

`main` 侧实现细节（清单文件、原子写、插件目录）检索了同类实现的已知坑，结论摘录：

- **原子写与 rename**：Node 官方 `fs.rename` 文档明确「若 `newPath` 已存在则覆盖」，但在 **Windows 上对已存在文件执行 rename 可能返回 `EPERM`/`EACCES`**（杀软/索引器持有句柄），社区通行做法是「写 tmp → 删目标 → rename」或重试。→ 采纳进 D8。
- **JSON 配置文件容错**：主流 CLI 配置加载器（如 `npm`、`eslint`）在配置损坏时都采取「报错并提示修复」而非静默重置；但**运行时清单**（插件/扩展列表）通行做法是「降级为空 + 备份坏档」，因为运行时清单损坏不应锁死进程启动。→ 采纳进 D9（备份为 `.bad.<ts>`，不静默丢）。
- **插件清单 schema 版本化**：VS Code `extensions.json`、Oh My Zsh 插件列表等均带版本或可向前兼容的宽松解析；结论是**必须有 `schemaVersion`**，否则后续加字段无法区分「旧数据缺字段」与「数据损坏」。→ 采纳进 D9。
- **插件启用/停用状态位**：VS Code 用 `extensions.json` 记录全局启用态、用清单条目区分「已安装」与「已启用」；结论是**「已安装但停用」必须是一等状态**，不能靠删除条目表达。→ 采纳进 D7。

### 2.4 分层判据（写入 README，防再次错位）

> **core 只回答**：插件长什么样（`Plugin` / `inject`）、往哪挂（`Context`）、挂了怎么撤（`Fiber` 六态 + disposer 栈）、怎么通信（`TypedEventBus`）、怎么诊断（`diagnose`）。
> **main 回答**：挂载哪些插件、顺序如何、启停状态、清单存哪、进程重启后怎么还原。
> **判据**：需要**磁盘 IO** 或**业务装配知识**的，一律不进 core。

### 3.3 持久化注册中心（任务 03）

#### 3.3.1 数据结构

```ts
/** 清单文件（落盘结构） */
export interface PluginManifest {
  /** 结构版本；不识别时降级为空清单并备份坏档（D9） */
  schemaVersion: 1;
  /** 条目数组，数组顺序 == 挂载顺序（D7 的 order 用数组下标表达，不存冗余字段） */
  entries: PluginManifestEntry[];
  /** 最后写入时间（ISO），仅供诊断 */
  updatedAt: string;
}

/** 单条插件清单条目 */
export interface PluginManifestEntry {
  /** 稳定标识（用户可读，重复即冲突）；同时作为清单主键 */
  id: string;
  /** 模块说明符：相对路径 / 绝对路径 / 包名（只收 ESM，D10） */
  specifier: string;
  /** 是否启用；false 表示「已登记但不挂载」（D7） */
  enabled: boolean;
  /** 传给插件工厂的选项（可选，仅 JSON 可序列化值） */
  options?: Record<string, unknown>;
}
```

**不存的东西（D6）**：`Fiber` 引用、服务实例、`apply` 函数、运行期状态（`ACTIVE`/`FAILED`）。这些每次启动重新推导。

#### 3.3.2 `PluginStore`

```ts
export interface PluginStoreOptions {
  /** 清单文件绝对路径；缺省 ~/.loop-agent/plugins/registry.json（D3） */
  file?: string;
}

export interface PluginStore {
  readonly file: string;
  /** 读清单；文件不存在 → 空清单；损坏 → 备份为 .bad.<ts> 后返回空清单（D9） */
  read(): PluginManifest;
  /** 原子写：tmp + rename，Windows 上先删目标（D8）；返回是否成功 */
  write(manifest: PluginManifest): { ok: true } | { ok: false; error: Error };
  /** 最近一次写失败（供 diagnose） */
  lastError(): Error | undefined;
}
```

#### 3.3.3 `PersistentPluginRegistry`

```ts
export interface PersistentPluginRegistryOptions<E extends EventMapBase = EventMapBase> {
  context: Context<E>;
  store?: PluginStore;
  /** 把 specifier 变成 Plugin 的工厂；缺省用动态 import()（D10） */
  loadPlugin?: (specifier: string, options?: Record<string, unknown>) => Promise<Plugin<E>>;
}

export class PersistentPluginRegistry<E extends EventMapBase = EventMapBase> {
  /** 已登记清单（内存镜像，顺序 == 挂载顺序） */
  entries(): readonly PluginManifestEntry[];
  /** 启动还原：读清单 → 逐条挂载 enabled 的插件（D6） */
  restore(): Promise<void>;
  /** 新增并挂载；id 重复抛错 */
  mount(entry: PluginManifestEntry): Promise<Fiber>;
  /** 彻底移除：卸载 Fiber + 删条目 */
  unmount(id: string): Promise<void>;
  /** 停用：卸载 Fiber，保留条目（D7） */
  disable(id: string): Promise<void>;
  /** 启用：按 specifier 挂载，保留条目位置（D7） */
  enable(id: string): Promise<Fiber>;
  /** 排序：按给定 id 顺序重排清单 */
  reorder(ids: readonly string[]): void;
  /** 按 id 取运行期 Fiber（未挂载返回 undefined） */
  fiberOf(id: string): Fiber | undefined;
  /** core 诊断 + 清单/落盘状态合并 */
  diagnose(): RegistryDiagnostic;
  /** 逆序卸载全部，幂等 */
  dispose(): Promise<void>;
}
```

`RegistryDiagnostic`：

```ts
export interface RegistryDiagnostic {
  /** core 原始诊断（Fiber 状态 / 服务归属 / 依赖缺失） */
  core: DiagnosticReport;
  /** 清单条目与运行期状态对照 */
  entries: Array<{
    id: string;
    specifier: string;
    enabled: boolean;
    /** 运行期状态；未挂载为 undefined */
    state?: FiberState;
    /** 加载失败原因（D10） */
    loadError?: { code: string; message: string };
  }>;
  /** 清单文件路径 */
  file: string;
  /** 最近一次落盘失败（D4） */
  persistError?: { message: string };
}
```

#### 3.3.4 边界与错误处理

| 场景 | 行为 |
|---|---|
| 清单文件不存在 | `read()` 返回空清单（不报错，首次启动的正常路径） |
| 清单 JSON 损坏 / `schemaVersion` 不识别 / `entries` 非数组 | 备份为 `registry.json.bad.<ts>`，返回空清单，`lastError()` 记录；**不阻断启动**（D9） |
| 条目 `id` 重复（文件里或运行期 `mount`） | 文件里重复：保留首个，其余记入诊断并忽略；运行期 `mount`：抛带稳定 `code` 的错误 |
| 插件 `import()` 失败（文件不存在 / 语法错 / 非 ESM） | 该条目标 `loadError`，其余条目照常挂载（D10） |
| 插件 `apply` 抛错 | 走 core 的 `FAILED` 语义，记入诊断；不中断其余（与 core 一致） |
| 落盘失败（磁盘满 / 权限） | `write()` 返回 `{ ok: false }`，记录 `lastError()`，**内存清单照常更新**，挂载继续（D4） |
| `disable` 一个已停用的 id | 幂等，不报错、不重复写盘 |
| `unmount` 不存在的 id | 幂等空操作 |
| `dispose()` 重复调用 | 返回同一 Promise（与 core `dispose` 幂等语义一致） |
| `reorder` 传入未知 id / 缺 id | 未知 id 抛错；未列出的 id 按原相对顺序追加到尾部 |
| 并发写（同一进程内） | 串行化：内部维护写队列，保证 last-write-wins 且不交叉（多进程并发写锁为本期非目标） |

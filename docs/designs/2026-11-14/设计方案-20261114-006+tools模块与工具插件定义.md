## 一、任务目标需求

### 1.1 背景（痛点）

`core` 解决「插件长什么样、怎么挂、怎么撤」，`main` 解决「挂哪些、存哪、重启怎么还原」，`llm` 解决「一个大模型服务商该长什么样」。**但「一个工具」在这套体系里还没有契约**，具体表现为五处硬耦合：

1. **契约是纯 interface，不可继承**：`src/types.ts:161` 的 `Tool` 只有 `name`/`description`/`parameters`/`execute`/`timeoutMs` 五个字段，实现方式只能是对象字面量。想加一个「所有工具都该有」的公共能力（参数校验、结果归一、耗时统计、错误包装），没有任何可复写的落点——只能每个工具各写一遍，或在 runner 里 if/else。

2. **注册中心是模块级单例**：`src/tools/registry.ts:229` 是 `export const registry = new ToolRegistry()`，内部一个 `Map<string, Tool>`（`:27`）。**没有归属追踪、没有成组撤销**：某个来源的工具想整批摘掉，只能自己遍历 name 逐个 `unregister()`；`diagnose()` 这类能力对它完全不可见（这正是需求 20261114-003 登记的「17 处 `export const x = new X()`」同源问题）。

3. **重复注册直接抛裸 Error**：`registry.ts:42` 是 `throw new Error('工具 X 已注册，不可重复注册')`——无稳定 `code`、无归属信息，宿主既无法程序化识别「是冲突还是别的错」，也无法在诊断报告里定位是谁抢注的。

4. **超时与错误归一写死在执行器**：`src/tools/runner.ts:65` 的 `options.timeout ?? tool.timeoutMs ?? 30000`、`:107` 的 `工具执行失败: ${msg}` 都固化在 `ToolRunner` 里。契约层无法声明「我这个工具默认给多久」「我的失败长什么样」，第三方工具只能被动接受宿主口径。

5. **装配靠人肉编排**：`src/tools/index.ts` 逐个 `registry.register(...)` 12 个内置工具，再按 `shouldRegisterOcrTools()` / 视觉开关条件注册，MCP 工具由 `registry.registerMCPServer()` 在运行期动态适配。**新增一个工具 = 改主工程代码并改装配代码**，无法以「加一个插件」的方式扩展，「默认实现」与「用户自定义实现」都没有位置。

用户原话：「新建 tools 子模块，tools 依赖 core 模块，tools 模块基于插件基础上定义工具插件定义，供后续默认实现和用户自定义实现继承。」

关键信息拆解：

- 「新建 tools 子模块」→ 与 `core/`、`main/`、`llm/` 平级的独立包；
- 「tools 依赖 core 模块」→ `dependencies` 只允许 `@loop-agent/core`；
- 「基于插件基础上定义」→ 产物必须是 **core 可识别的插件**，能交给 `main` 的 `PersistentPluginRegistry` 挂载；
- 「供后续默认实现和用户自定义实现**继承**」→ 契约形态是**可继承的抽象基类**，不是纯 interface；「默认实现」属后续工作，**本期不做**。

### 1.3 任务目标

1. **新建独立子包 `tools/`**（`@loop-agent/tools`），与 `core/`、`main/`、`llm/` 平级；`dependencies` 只允许 `@loop-agent/core`，零三方运行时依赖。
2. **自持领域类型**：工具规格、参数 JSON Schema、执行上下文、执行结果、行为声明、展示元信息，全部定义在 tools 包内，命名与 `src/types.ts` 解耦。
3. **定义可继承的双层契约**：
   - `ToolBase`（单个工具）：抽象 `execute()` + 模板方法 `invoke()` 统一「参数校验 → 执行 → 结果归一」；
   - `ToolProvider`（一个插件提供多个工具）：覆盖 MCP server 这类集合式注册。
   默认实现与用户自定义实现都通过 `extends` 落地。
4. **把提供者编译成 core 插件**：`defineTools(def)` 返回 `PluginObject`；`defineToolsFactory(def)` 返回接 `options` 的工厂；`installTools()` 提供目录服务 `tools:registry`；每个提供者以 `tools:provider:<id>` 占一个服务 key；挂载/卸载由 core Fiber 自动托管与成组撤销。
5. **注册期前置校验**：工具名（`^[A-Za-z0-9_-]{1,64}$`）、必填字段、`parameters` 必为 `object` 型 JSON Schema、同目录内重名、同 id 提供者重复挂载——全部在挂载期同步炸掉，不留给模型 API 返回 400。
6. **保住输出确定性**：`toToolDefs()` 按 name 排序 + 参数键序规范化，继承 `toOpenAITools()` 已实证的前缀缓存不变量。
7. **错误族与事件表齐备**：`ToolsError` 继承 `CoreError`；事件 `tools/registered`、`tools/unregistered`、`tools/invoke`、`tools/result`、`tools/error` 供宿主观测。
8. **装配期与执行期分离**：core `Context`（装配期）与 `ToolInvokeContext`（执行期：workspaceRoot / sessionId / callId / signal）严格分开，插件对象**不持有任何执行期状态**。

### 2.2 关键设计决策

#### D1 本包只做「工具契约 + 插件编译器 + 目录服务」，不做任何工具实现

**决策：** `tools/` 的产物只有抽象契约、注册期校验、目录服务与插件编译器；不含任何一个真实工具（fileRead / grep / commandRun / MCP 适配都属「默认实现」，后续另立需求）。

**取舍：**
- **必须这样做的硬理由**：用户明确「供**后续**默认实现和用户自定义实现继承」——如果本期顺手把 12 个内置工具搬进来，契约会被 12 个具体实现反向塑造（每个工具的特殊参数、特殊输出治理都会渗进契约），且「契约是否够用」这个问题会被「反正内置工具能跑」掩盖。先只留契契约 + 一个测试内联假工具，才能真正验证「第三方能否只靠 `extends` 落地」。
- 否决「本期顺带把 12 个内置工具迁进 tools」：那是 `src/tools/` 整体迁移，属独立需求；且必然连带 output-governor、documents、ocr、vision、config 等一串依赖，`dependencies` 只允许 core 的约束立刻崩掉。
- 与 llm 同构：llm 本期也只做契约、不实现 OpenAI 兼容 provider（需求 20261114-005 D1），四包策略一致。

#### D2 领域类型在包内自持，**不依赖 llm**；与 `LlmToolDef` 结构对齐但由适配层衔接

**决策：** `tools/src/types.ts` 自定义 `ToolSpec`（含 `name`/`description`/`parameters`/`annotations`/`timeoutMs`/`display`），**不 import `@loop-agent/llm`**，也不 import `src/types.ts`。工具定义投影成模型侧格式由**宿主侧适配函数**完成（P1 提供一个无副作用的纯函数 `toLlmToolDefs()`，产物结构与 `LlmToolDef` 一字等价，但类型声明在 tools 包内）。

**取舍：**
- **为什么不能依赖 llm**：`tools` 与 `llm` 是**平级**的两个领域契约包。若 tools 依赖 llm，则「工具」在概念上从属于「大模型」，将来换掉模型层（或让工具在非 LLM 场景被调用，如 ACP 编辑器的 tool 映射，见需求 20261114-001）时会被连坐；且会形成 `tools → llm → core` 的三层链，把本可正交的两条轴捆成一条。
- **为什么不 import `src/types.ts`**：沿用 core/main/llm 的零反向依赖范式；`src/types.ts` 是主工程内部类型，一旦被包引用，主工程重构就会破坏包契约。
- **为什么仍然「结构对齐」**：`{ name, description, parameters }` 这三个字段与 `llm/src/types.ts:32` 的 `LlmToolDef` 完全同构，适配函数因此是一行 map，不需要字段翻译——「类型自持 + 结构对齐」既保住边界，又避免转换损耗。
- 否决「让 llm 反向依赖 tools 以便 provider 直接用工具」：那是 `llm` 契约层反向依赖一个下游领域包，层级颠倒。

#### D3 服务 key：一个目录服务 + 每个提供者一个 key

**决策：**
```ts
TOOLS_SERVICE_KEYS = {
  registry: 'tools:registry',
  providerPrefix: 'tools:provider:',   // 拼 id → 'tools:provider:mcp-fs'
} as const;
```

**取舍：**
- **必须这样做的硬理由**：`core/src/service.ts:47` 的 `provide()` 遇重复 key **抛 `ServiceConflictError`，不做覆盖**。若所有提供者挤在 `tools:provider` 一个 key 下，第二个提供者挂载即冲突。
- 否决「单 key 存 `Map<string, ToolProvider>`」：能绕过冲突，但会**丢掉 core 的归属追踪**——`diagnose()` 无法按提供者报 `ownerFiberId`，某个提供者卸载时也无法靠 Fiber 自动撤销单条，等于把 core 刚解决的「可成组撤销」重新破坏一次。
- 一提供者一 key 的额外收益：`ctx.get('tools:provider:mcp-fs')` 可在**不碰目录服务**的情况下直取，插件之间可做精确软依赖（`inject: {optional:['tools:provider:mcp-fs']}`）。
- 与 llm 完全同构（需求 20261114-005 D3），四包 key 命名法统一为 `<包>:registry` + `<包>:<实体>:<id>`。

#### D4 双层契约：`ToolBase`（单工具）+ `ToolProvider`（工具集合），两者都可 `extends`

**决策：**
```ts
// 单个工具：绝大多数用户只需要继承这个
export abstract class ToolBase { ... }

// 一组工具：一个插件提供 N 个工具（MCP server、插件包、按条件启用的工具组）
export abstract class ToolProvider { 
  abstract readonly id: string;
  abstract create(): ToolBase[] | Promise<ToolBase[]>;
}
```

`defineTools()` 接受 `ToolDefinition`，其中 `tools` 可以是 `ToolBase[]`、或 `ToolProvider` 实例、或工厂函数。

**取舍：**
- **为什么必须两层**：只有单工具契约时，「一个 MCP server 连上来给出 47 个工具」「视觉三件套按开关成组注册」这类场景只能由用户在外面手写循环 + 手写撤销逻辑；提供者层把「成组」变成一等概念，撤销由 Fiber 一次性托管（`ctx.effect` 批量登记，卸载逆序撤销）。
- **为什么用抽象类而非 interface**：用户原话是「继承」。抽象类能承载**已实现的模板方法**（D6 的 `invoke()`）与**只读访问器**（`name`/`parameters` 从 `spec` 派生），interface 只能声明、什么都给不了；同时抽象类可用 `protected` 限制内部方法，避免用户误覆写 `invoke()` 破坏校验链。
- **为什么 `create()` 可以是异步**：MCP 需要先握手、外部工具包可能要先读磁盘清单；同步签名会逼所有实现写 `await Promise.resolve()` 包装。异步签名对同步实现零成本（返回数组即可）。
- 否决「让 `ToolBase` 同时实现 `PluginObject`」：继承一个类同时又要满足插件形态，是概念污染；`defineTools()` 负责把实例编译成插件，职责归位。

#### D5 双导出：`defineTools()` 与 `defineToolsFactory()`

**决策：** 提供两个导出，内部共用 `buildPlugin()`，差异仅在 `options` 从哪来。

```ts
/** 形态 A：直接得到插件对象（无部署侧覆盖） */
export function defineTools(def: ToolsDefinition): PluginObject;
/** 形态 B：得到工厂，供 main 清单注入 options */
export function defineToolsFactory(
  def: ToolsDefinition,
): (options?: Record<string, unknown>) => PluginObject;
```

**取舍：**
- **必须两个都给的硬理由**（已核对 `main/src/registry.ts` 的 `defaultLoadPlugin`）：`main` 的清单加载兼容三种模块导出——`export default (options) => Plugin`、`export default pluginObject`、`export const plugin`，**`options` 的唯一通道是「外层工厂函数」，`ctx` 上没有任何 options 通道**。只给 A，用户在清单里写的 `options` 会被**静默丢弃**（最难排查的一类「配置不生效」）；只给 B，无覆盖需求时也要多包一层函数，且不满足 `export default pluginObject` 形态。
- 复用 llm 的实现与结论（需求 20261114-005 D4），两个包的用户手册口径一致，减少认知负担。

#### D6 `invoke()` 模板方法固化「校验 → 执行 → 归一」，`execute()` 是唯一抽象方法

**决策：**

```ts
export abstract class ToolBase {
  /** 子类只实现这一个方法 */
  protected abstract execute(
    args: Record<string, unknown>,
    ctx: ToolInvokeContext,
  ): Promise<string | ToolResult> | string | ToolResult;

  /** 宿主唯一调用入口：final 语义（TS 无 final，用文档 + 私有步骤函数约束） */
  async invoke(rawArgs: unknown, ctx: ToolInvokeContext): Promise<ToolResult> {
    // ① 参数必须是对象（null/数组/原始值 → TOOLS_ARGS_INVALID）
    // ② 手写 JSON Schema 校验（D7）→ 不通过抛 TOOLS_ARGS_INVALID
    // ③ 调 execute()，兼容 string | ToolResult 两种返回（D10）
    // ④ 异常归一为 { text: '工具执行失败: …', isError: true }，不向上抛
    // ⑤ 埋点耗时，交事件 tools/result
  }
}
```

**取舍：**
- **为什么在这里固化**：现状 `src/tools/runner.ts` 把「异常 → `工具执行失败: ${msg}`」（`:107`）、「超时兜底」（`:65`）写死在执行器里，每个工具都得等宿主兜。固化进 `invoke()` 后，**校验与归一成为契约的一部分**：用户新写的工具自动获得参数校验与统一失败文案，宿主侧不需要再对每个工具写一遍防御。
- **为什么 `execute()` 是 `protected`**：防止宿主绕过校验直接调裸执行体；同时保留「需要绕过时的逃生口」——子类可自愿在自身内部公开一个 `executeUnsafe()`，责任在实现方。
- **为什么保留 `string` 返回兼容**：12 个内置工具全是 `Promise<string>`，未来迁移时改造成本降到最低（只需 `extends` 并挪实现体，不改返回）。用户自定义实现也可只返回字符串，`invoke()` 自动包成 `{ text, isError:false }`。
- 否决「把校验放 registry 层」：那样第三方工具被别的宿主（不经过 registry）调用时就失去校验；校验属工具自身的**不变量**，应贴着工具。

#### D7 参数校验：手写 JSON Schema 子集，不引三方库

**决策：** `schema.ts` 实现 `validateArgs(parameters, args): ValidationIssue[]`，支持子集：`type`（`object`/`string`/`number`/`integer`/`boolean`/`array`/`null`）、`properties`、`required`、`items`、`enum`、`minimum`/`maximum`、`minLength`/`maxLength`、`pattern`、`additionalProperties: false`。**不支持** `$ref`、`allOf`/`anyOf`/`oneOf`、`if/then/else`、`format`。

**取舍：**
- **为什么手写**：工程默认约束「零新依赖优先」；且只要子集覆盖，超出子集的关键字**跳过而非报错**（宽松策略），不会因用户写了 `oneOf` 就被拒。使用面只在「模型给的参数是否符合 schema 基本形状」，不做完整 JSON Schema 实现。
- **为什么不校验就放行**：现在完全没有校验，把裸参数直接交给 `execute()`。`editFile` 失配、`fileRead` 传了字符串型 `startLine` 这类问题最终靠工具内部各写 `typeof` 判断，重复且易漏。前置校验把「参数形状错」与「执行失败」分开，错误文案可直接提示模型重试。
- 校验失败**不抛异常穿透**：`invoke()` 捕获后返回 `isError: true` 的 `ToolResult`（与 runner 现状「异常不抛出，转为字符串返回」一致，见 `runner.ts:50` 注释），避免打断 ReAct 循环。

#### D8 工具名约束在注册期同步校验：`^[A-Za-z0-9_-]{1,64}$`

**决策：** `defineTools()` / `registry.register()` 同步阶段校验工具名，不合法立即抛 `ToolsError`（`code: 'TOOLS_INVALID_NAME'`）。规则：非空、长度 ≤64、只含 ASCII 字母/数字/`_`/`-`、不以 `__` 开头（避免与 MCP 的 `server__tool` 命名空间混淆，见 D13）。

**取舍：**
- **硬理由（有外部依据，见 2.3）**：三大模型厂商对 function name 的实际限制高度一致——OpenAI 是 `a-z, A-Z, 0-9, _ , -`、最长 **64**；Anthropic 为 `^[a-zA-Z0-9_-]{1,128}$`；Bedrock/Gemini 亦为 64。MCP 规范本身只 SHOULD 1–128 且允许 `.`，**但 `.` 会被 OpenAI/Anthropic 拒绝**——`multi_tool_use.parallel` 这类名字在真实事故中触发 400。工具名一旦含 `.`，错误发生在**模型 API 边界**（每轮请求都 400），而根因在工具注册处，排查成本极高。把校验前置到挂载期，错误信息能直接指向「哪个插件注册的哪个名字」。
- **为什么取 64 而非 128**：64 是三大厂商的**最低公共上限**；取 128 等于允许写出「本地能注册、上云就 400」的名字。取交集是唯一安全解。
- **为什么禁 `__` 前缀**：主工程 MCP 适配用 `server__tool`（`src/tools/mcp/adapter.ts` `buildToolName`）区分来源。若用户工具也以 `__` 开头，将来迁移到统一目录时会产生歧义；本包保留该前缀为「由适配器生成的命名空间」专用。
- 否决「只告警不报错」：工具名错是**装配期错误**，不是运行期偶发；与 core 的「冲突显式化」哲学一致。

#### D9 行为声明：对齐 MCP `ToolAnnotations` 四 hint + 可选 `display` 段

**决策：**

```ts
export interface ToolAnnotations {
  title?: string;
  /** 不修改环境（纯读）；默认 false */
  readOnlyHint?: boolean;
  /** 修改是破坏性（删除/覆盖）而非追加；默认 true，仅在 readOnlyHint=false 时有意义 */
  destructiveHint?: boolean;
  /** 同参数重复调用无额外影响；默认 false，同上 */
  idempotentHint?: boolean;
  /** 触及开放世界（网络/外部系统）；默认 true */
  openWorldHint?: boolean;
}

export interface ToolDisplay {
  /** 中文展示名（WebUI 卡片标题） */
  label?: string;
  /** 图标 key（WebUI 线性 SVG 体系） */
  icon?: string;
  /** 参数英文名 → 中文标签 */
  paramLabels?: Record<string, string>;
}
```

**取舍：**
- **为什么照搬 MCP 的四个 hint**：这是目前**已有事实标准**（MCP 2025-03-26 起进入规范，2026 版仍是同一 `ToolAnnotations` 接口），语义定义清晰且互不重叠。自造一套「只读/危险/幂等」字段只会与生态对不上，将来桥接 MCP server 时还得翻译。
- **为什么默认值取「悲观」口径**：MCP 规范给的是 `readOnlyHint=false`、`destructiveHint=true`、`idempotentHint=false`、`openWorldHint=true`——即「什么都不声明 = 可能写、可能破坏、可能不幂等、可能触网」。沿用该默认意味着**未声明的第三方工具天然按最保守对待**，宿主将来接确认门禁时不会因缺省字段而误放行。这一条写进 README，避免用户以为「不填就是安全的」。
- **`display` 为什么放契约里**：现状 `webui/src/tool-meta.ts` 把 12 个工具的中文名/图标/参数标签硬编码在前端，导致「新增工具必须改前端」，这正是需求 20261028 系列反复踩的坑。把展示元信息作为**可选**字段随工具契约声明，将来可由后端下发给前端，前端只保留兜底表。**本期不接入**（非目标），只留字段位，避免将来改签名。
- 否决「本期就做权限门禁」：`destructiveHint` 的消费方是宿主（需要 UI 确认流程），属 main 与 WebUI 的职责；tools 只声明，不强制。

#### D10 执行结果：`ToolResult` 结构化（`text` + `isError`），兼容纯字符串

**决策：**

```ts
export interface ToolResult {
  /** 模型可见的观察文本（唯一进入上下文的字段） */
  text: string;
  /** 是否失败；宿主可据此控制重试/中止策略 */
  isError?: boolean;
  /** 结构化输出（P2 预留，本期不消费） */
  structured?: Record<string, unknown>;
}
```

**取舍：**
- **为什么需要 `isError`**：现状只有裸字符串，前端只能靠**正则猜**失败（`webui/src/tool-meta.ts` 的 `BACKEND_TOOL_ERROR` / `toolResultLooksFailed`，注释里明说「已知边界：文件正文恰好以错误词开头仍会误判」）。把失败作为**结构化字段**由工具自报，前端不必再猜；同时保留文本前缀作为向后兼容兜底。
- **为什么不把 `text` 叫 `content`**：`content` 在 llm 包里指消息内容（`LlmMessage.content`），同名不同义易混；`text` 明确是「观察文本」。
- **为什么保留 string 兼容**：见 D6——12 个内置工具全是 `Promise<string>`，迁移时不必改实现体。
- 否决「直接返回 JSON 对象让模型解析」：ReAct 循环的 Observation 必须是文本；结构化字段只服务宿主（UI/统计/门禁），不能顶替文本。

#### D11 注册期唯一性：目录内重名 → 显式冲突错误，不覆盖

**决策：** `registry.register(tool)` 遇同名抛 `ToolsDuplicateError`（`code: 'TOOLS_DUPLICATE'`，携带 `name` 与双方提供者 `providerId`）；`defineTools()` 挂载期若发现 `tools:provider:<id>` 已存在，翻译成可读的 `TOOLS_PROVIDER_EXISTS`。

**取舍：**
- **必须不覆盖**：工具名是模型调用时的唯一寻址键，静默覆盖会导致「明明注册了新工具，模型却调到旧实现」——比崩溃更难查。沿用 core 「冲突显式化」与 `ToolRegistry` 现状（`registry.ts:42` 抛错）语义，只把裸 `Error` 升级为带 `code` 的错误族。
- **为什么错误信息要带 `providerId`**：现状错误只有工具名，用户不知道是哪个插件抢的。带 `providerId` 后可直接对应到 `diagnose()` 的 `ownerFiberId`，定位一步到位。
- 否决「允许覆盖 + 告警」：告警在静默场景会被淹没，且无法回答「当前生效的是谁」。

#### D12 `toToolDefs()` 必须稳定排序 + 参数规范化

**决策：**

```ts
toToolDefs(): ToolDefView[]  // 按 name.localeCompare 升序，parameters 经 canonicalize()
```

`canonicalize()` 为递归键序排序（照搬 `src/tools/registry.ts:1-24` 的既有实现语义）。

**取舍：**
- **硬理由**：`src/tools/registry.ts:108-111` 的注释已明确——「按名称排序 + 参数规范化，确保序列化结果确定性以命中模型前缀缓存」。工具定义是每轮请求的**前缀**部分，键序抖动会让 provider 侧前缀缓存整体失效，直接的后果是**成本和延迟双双上升**，而且不报错、极难察觉。这是本包必须继承的不变量，不是优化项。
- 否决「按注册顺序输出」：注册顺序取决于插件挂载顺序，而 main 的清单顺序用户可调（`PersistentPluginRegistry` 支持顺序调整），顺序一变前缀就变。
- `localeCompare` 与既有实现一致；不用默认 `sort()` 的码点序，避免与现有行为不一致导致迁移前后 diff。

#### D13 MCP 类「集合工具」用 `ToolProvider` 承载，命名空间前缀由适配器负责

**决策：** 提供者只负责「产出工具数组」，**不负责**给工具名加前缀。命名空间前缀（`server__tool`）由宿主侧适配器决定并作为 `ToolSpec.name` 传入。本包只约束：工具名不得以 `__` 开头（D8），把该前缀永久留给适配器。

**取舍：**
- **为什么不在契约里生成前缀**：前缀策略取决于命名空间怎么划分（MCP server 名、插件 id、还是市场包 id），属**装配决策**（main 的职责），不是工具契约的一部分。契约一旦内置「必须 `id__name`」，用户就失去自定义权。
- **为什么仍要禁 `__` 开头**：给适配器保留干净的命名空间，避免「用户工具名与生成名撞车」这种只能靠约定避免的冲突。
- 否决「在 tools 包内置 MCP 适配器」：会把 MCP 协议依赖（stdio/SSE/HTTP 客户端）拉进契约包，`dependencies` 只有 core 的约束立刻破产。

#### D14 错误族继承 `CoreError`；事件用目录自带发射器，不用 core 总线

**决策：**

```ts
export class ToolsError extends CoreError {
  // code: 'TOOLS_INVALID_NAME' | 'TOOLS_DUPLICATE' | 'TOOLS_PROVIDER_EXISTS'
  //     | 'TOOLS_NOT_FOUND' | 'TOOLS_ARGS_INVALID' | 'TOOLS_REGISTRY_MISSING'
  //     | 'TOOLS_CONFIG_INVALID' | 'TOOLS_EXEC_FAILED'
}
```
事件：`tools/registered`、`tools/unregistered`、`tools/invoke`、`tools/result`、`tools/error`，由 `ToolRegistry` 自带小型 emitter（`registry.on(...)`），与 llm 的 `registry.ts:11-13` 同一结论。

**取舍：**
- **错误族继承 `CoreError`**：复用稳定 `code` + `pluginName` + `fiberId` + `cause`，宿主可用 `instanceof CoreError` 统一捕获，不必为每个包写分支。
- **为什么事件不走 `host.bus`**：core 的 `Context` 只暴露 `on()`，**没有 `emit()`**；总线在 `CoreHost.bus` 上，而插件（`apply(ctx)`）拿不到 host。若硬依赖 core 总线，`installTools()` 就得额外要求宿主注入 host，把简单契约复杂化。自带 emitter 后，`ctx.get('tools:registry')` 一个动作就能用全，也便于在无 core 的单元测试里单独验证事件。
- 否决「让 registry 直接 `ctx.emit()`」：core 未提供该能力，改 core 就超出本期范围。

| 真实事故：MCP 工具名超 64 或含 `.`（如 `multi_tool_use.parallel`）导致整轮请求 400，且 MCP 侧 `tools/list` 完全正常，根因定位耗时以小时计 | 佐证 D8「注册期同步校验」的必要性：错误必须在挂载时暴露 | yusufhan.dev 事故复盘、Portkey error #10046、mcp-tool-name-portability-checker |
| 工具定义作为请求**前缀**，键序不稳定会让 provider 前缀缓存失效（成本/延迟上升且无报错） | D12 排序 + `canonicalize` 定为不变量，并列为验收项 | 项目内既有实证（`src/tools/registry.ts:108-123` 注释）+ 本方案对 llm 侧的同类要求 |

### 3.2 领域类型（`src/types.ts`）

```ts
/** 工具参数 JSON Schema（手写子集，不引三方库） */
export type JsonSchema = Record<string, unknown>;

/** 工具规格：纯数据，不含行为（目录 list() 与 toToolDefs() 的返回单元） */
export interface ToolSpec {
  /** 唯一名；`^[A-Za-z0-9_-]{1,64}$`，不以 `__` 开头（D8） */
  name: string;
  /** 给模型看的能力说明；空字符串在注册期拒绝（模型靠它决定何时调用） */
  description: string;
  /** 参数 JSON Schema；必须是 `{ type: 'object', ... }`（D7） */
  parameters: JsonSchema;
  /** 行为声明（D9） */
  annotations?: ToolAnnotations;
  /** 展示元信息（本期不接入 WebUI，仅占位） */
  display?: ToolDisplay;
  /** 单次执行默认超时；缺省 DEFAULT_TOOL_TIMEOUT_MS = 30_000（对齐 runner.ts:65） */
  timeoutMs?: number;
}

/** 执行期上下文：由宿主（runner/agent）每次调用注入，插件**不得**持有 */
export interface ToolInvokeContext {
  /** 取消信号：贯穿 LLM/工具/子进程三层 */
  signal?: AbortSignal;
  /** 工作空间根：相对路径解析基准 */
  workspaceRoot?: string;

  callId?: string;
  /** 只读元信息透传（如 traceId）；不含密钥 */
  metadata?: Record<string, string>;
}

/** 执行结果（D10） */
export interface ToolResult {
  /** 模型可见的观察文本（唯一进入上下文的字段） */
  text: string;
  /** 失败标记；宿主据此决定重试/中止，不再靠正则猜 */
  isError?: boolean;
  /** 结构化输出（P2 预留，本期不消费） */
  structured?: Record<string, unknown>;
}
```

### 3.3 `ToolBase` 抽象基类（`src/tool.ts`）

```ts
export abstract class ToolBase {
  /** 规格在构造时定稿，运行期只读 */
  protected readonly spec: ToolSpec;

  constructor(spec: ToolSpec);

  get name(): string;
  get description(): string;
  get parameters(): JsonSchema;
  get annotations(): ToolAnnotations;   // 已补全 MCP 悲观默认（D9）
  get timeoutMs(): number;              // 缺省 30_000

  /** 投影为纯数据视图（目录 list() 与 toToolDefs() 用） */
  toSpec(): ToolSpec;

  /**
   * 宿主唯一调用入口（D6）：
   * ① 参数形状检查 → ② JSON Schema 校验 → ③ execute() → ④ 归一 → ⑤ 事件
   * 任何环节失败都返回 isError:true 的 ToolResult，不向上抛。
   */
  async invoke(rawArgs: unknown, ctx?: ToolInvokeContext): Promise<ToolResult>;

  /** 子类唯一必须实现的方法 */
  protected abstract execute(
    args: Record<string, unknown>,
    ctx: ToolInvokeContext,
  ): Promise<string | ToolResult> | string | ToolResult;
}
```

**边界与错误处理：**

| 场景 | 行为 | `ToolResult.isError` |
|---|---|---|
| `rawArgs` 为 `null`/数组/原始值 | 不调 `execute()`，返回「参数必须是对象」 | `true` |
| 必填参数缺失 / 类型不符 / enum 越界 | 不调 `execute()`，返回逐条问题清单（最多 10 条） | `true` |
| `parameters` 含本包不支持的 schema 关键字 | 跳过该关键字，继续校验其余部分 | 不触发 |
| `execute()` 返回 `string` | 包成 `{ text, isError: false }` | `false` |
| `execute()` 返回 `ToolResult` | 原样透传（`isError` 缺省为 `false`） | 依实现 |
| `execute()` 抛异常 | 归一为 `{ text: '工具执行失败: <msg>', isError: true }` | `true` |
| `ctx.signal` 已 abort | 返回 `{ text: '工具已取消', isError: true }`，**不调** `execute()` | `true` |

### 3.4 `ToolProvider` 抽象基类（`src/provider.ts`）

```ts
export abstract class ToolProvider {
  /** 提供者唯一 id；非空、不含 `:`（`:` 是服务 key 分段符） */
  abstract readonly id: string;
  /** 展示名；缺省回落 id */
  readonly displayName?: string;
  /** 提供者级硬/软依赖；缺省由 defineTools 注入 tools:registry */
  readonly inject?: Inject;

  /** 产出本提供者负责的全部工具；允许异步（MCP 握手、读磁盘清单） */
  abstract create(options: Record<string, unknown>): ToolBase[] | Promise<ToolBase[]>;
```

**约定：** 提供者不做命名空间前缀、不做去重、不做排序——三件事分别归适配器（D13）、registry（D11）、`toToolDefs()`（D12）。

### 3.7 `defineTools` / `defineToolsFactory`（`src/define.ts`）

```ts
export interface ToolsDefinition {

  id: string;
  displayName?: string;
  /** 代码侧默认配置（JSON 可序列化）；与清单 options 浅合并，清单侧优先 */

  def: ToolsDefinition,

```

**`buildPlugin()` 的 apply 流程：**

1. `getToolRegistry(ctx)` 取目录；
2. 解析 `tools`（数组 / `provider.create(merged)` / 工厂调用）；
3. 逐个工具同步校验（D8/D11）——**任一个不合法即整批失败**（`apply` 抛错 → Fiber `FAILED`），不留半挂载状态；
4. `ctx.provide('tools:provider:<id>', providerFacade)`；
5. `ctx.effect(() => batchRegister(tools, id), 'tools:provider:<id>')` 批量登记，卸载逆序撤销；
6. 若有 `dispose`，`ctx.effect(() => () => provider.dispose?.(), ...)` 兜资源释放。

**与 main 清单接线：** `export default defineTools({...})`（无覆盖）或 `export default defineToolsFactory({...})`（清单可写 `options` 覆盖）。

### 3.8 边界与错误处理

| 边界 | 处理 |
|---|---|
| 提供者 `create()` 返回空数组 | 允许（挂载成功但 0 工具），记一条诊断信息；不视为错误 |
| 提供者 `create()` 抛错 | `apply` 抛错 → Fiber `FAILED`，`diagnose()` 可见；已注册的工具不回滚（因为还没注册） |
| 批量注册中途某个工具重名 | 整批失败并回滚已注册项（先收集校验，全部通过后再落登记） |
| 卸载期 `dispose()` 抛错 | 吞掉并记 `disposeErrors`（core 不变量 3） |
| `toToolDefs()` 时工具被并发注销 | 基于快照遍历，不抛错 |
| 工具名大小写冲突（`FileRead` vs `fileRead`） | 视为不同名（大小写敏感，与 MCP/OpenAI 一致），但 README 建议全小驼峰 |
| 参数 `additionalProperties` 未声明 | 允许多余参数并**原样透传**给 `execute()`（宽松，避免模型加个无用字段就失败） |

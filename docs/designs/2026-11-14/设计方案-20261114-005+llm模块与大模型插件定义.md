## 一、任务目标需求

### 1.1 背景（痛点）

`core` 与 `main` 已经把「插件长什么样、怎么挂、怎么撤」和「挂哪些、存哪、重启怎么还原」两件事解决掉了。但**「一个大模型服务商」在这套体系里还没有契约**，具体表现为三处硬耦合：

1. **模块级单例**：`src/llm/client.ts:664` 是 `export const llm = new LLMClient()`，`src/` 里 15 处直接 `from '.../llm/...'` 引用它。这正是需求 20261114-003 登记的「17 处 `export const x = new X()`」同源问题，无法成组撤销、无法替换实现。
2. **能力边界写死**：`LLMClient` 内部直接 `new OpenAI()`（`client.ts:2`），抽象边界就是「OpenAI 兼容协议」。换一个非 OpenAI 协议的服务商（原生 Anthropic 报文、私有 RPC、本地推理进程），只能改这个类本身，**不能以「加一个插件」的方式扩展**。
3. **无接口层**：`src/llm/` 5 个文件合计 1505 行（`client.ts` 664、`bench.ts` 477、`bench-store.ts` 140、`usage.ts` 139、`connectivity.ts` 85）全部服务于这一个具体实现，**没有一行是「provider 契约」**。于是「默认实现」与「用户自定义实现」无处安放。

用户原话：「新建 llm 子模块，llm 依赖 core 模块，llm 模块基于插件基础上定义大模型插件定义，供后续默认实现和用户自定义实现继承。」

关键信息拆解：
- 「新建 llm 子模块」→ 与 `core/`、`main/` 平级的独立包；
- 「llm 依赖 core 模块」→ `dependencies` 只允许 `@loop-agent/core`；
- 「基于插件基础上定义」→ 产物必须是 **core 可识别的插件**，能交给 `main` 的 `PersistentPluginRegistry` 挂载；
- 「供后续默认实现和用户自定义实现**继承**」→ 契约形态是**可继承的抽象基类**，不是纯 interface；且「默认实现」属后续工作，**本期不做**。

### 1.3 任务目标

1. **新建独立子包 `llm/`**（`@loop-agent/llm`），与 `core/`、`main/` 平级；`dependencies` 只允许 `@loop-agent/core`（workspace 内），零三方运行时依赖。
2. **自持领域类型**：消息、内容分片、工具定义、工具调用、用量、请求、响应、流式事件，全部定义在 llm 包内，有效期内的命名与结构与上游协议解耦。
3. **定义可继承的 provider 契约**：抽象基类 `LlmProvider`（抽象 `complete()` + 默认降级 `stream()` 模板方法 + 可覆写钩子 `onDispose()`），让默认实现与用户自定义实现都通过 `extends` 落地。
4. **把 provider 编译成 core 插件**：`defineLlmProvider(def)` 返回 `PluginObject`；`installLlm()` 是 llm 包自身的 bootstrap 插件，提供目录服务 `llm:registry`；每个 provider 以 `llm:provider:<id>` 占一个服务 key，挂载/卸载由 core Fiber 自动托管。
5. **能力协商**：`capabilities()` 显式声明支持的能力位；请求超出能力时**显式抛错**，不静默忽略参数。
6. **错误族与事件表齐备**：`LlmError` 继承 `CoreError`；事件 `llm/registered`、`llm/unregistered`、`llm/request`、`llm/response`、`llm/error` 供宿主观测。

**数据流①（启动安装目录服务）**
`main.registry.restore()` → 读到 llm 包条目 → `import('@loop-agent/llm')` → `ctx.plugin(installLlm())` → Fiber `ACTIVE` → `llm:registry` 可 `get()`

**数据流②（挂一个 provider）**
`ctx.plugin(defineLlmProvider({id:'my-llm', create}))` → 硬依赖 `llm:registry` 就绪后 `apply` → `create(options)` 得 `LlmProvider` 实例 → `registry.register(provider)` → `ctx.provide('llm:provider:my-llm', provider)` → 卸载时 Fiber 逆序执行 disposer → 自动 `unregister` + `provider.onDispose()`

**数据流③（一次调用）**
`registry.complete('my-llm', req)` → `capabilities()` 契约校验（D5）→ `provider.complete(req)` → 发 `llm/request` → 收 `llm/response` → 返回 `LlmResponse`；抛错则归一为 `LlmError` 并发 `llm/error`

### 2.2 关键设计决策

#### D1 领域类型在 llm 包内自持，不从 `src/types.ts` 提取下沉

**决策：** llm 包内新建 `src/types.ts`，重新定义 `LlmMessage`/`LlmContentPart`/`LlmToolDef`/`LlmToolCall`/`LlmUsage`/`LlmRequest`/`LlmResponse`/`LlmStreamEvent`，**不 import `src/types.ts`**。

**取舍：**
- 否决「把 `src/types.ts` 的 LLM 相关类型下沉到 core」——core 是**领域无关的内核**（`core/README` 的分层判据写死了这点），塞进大模型术语会让 core 变回「又一个业务包」，且 core 的 `boundary.test.ts` 会失去意义。
- 否决「llm 直接 import `src/types.ts`」——违反零反向依赖，且 `src/types.ts` 673 行里混着会话标记（`is_compact`/`is_show`/`msgId`/`attachments`）、后台通知边界常量等**与 provider 契约无关**的东西，引用会把这些杂质带进契约层。
- 代价：短期内 `src/types.ts` 与 `llm/src/types.ts` 存在结构重复，将来迁移时需一次性对账。这是**刻意的**：契约层必须能独立演进，否则抽象形同虚设。

#### D2 provider 契约用**抽象基类**而非纯 interface

**决策：** `export abstract class LlmProvider`，抽象成员只有 `id` 与 `complete()`；`capabilities()`、`stream()`、`onDispose()` 给默认可覆写实现。

**取舍：**
- 用户原话是「供…**继承**」，继承是需求本身，不是可选风味。
- 否决纯 interface + 组合：那会让每个实现自己重复写「流式降级」「能力默认值」等模板逻辑，且无法用 `instanceof` 判别。
- 否决「interface + 独立 helper 函数」：分裂成两套东西，用户要 import 两个符号。
- 抽象面**只留一个必实现方法**（`complete()`），是最小契约——provider 作者负担最低，其余全有默认。这是「接口最小化」原则：默认实现走模板方法，不是逼所有实现都写一遍。

#### D3 服务 key 布局：一个目录服务 + 每个 provider 一个 key

**决策：**
```ts
LLM_SERVICE_KEYS = {
  registry: 'llm:registry',
  providerPrefix: 'llm:provider:',   // 拼 id → 'llm:provider:openai'
}
```

**取舍：**
- **必须这样做的硬理由**：`core/src/service.ts:47` 的 `provide()` 遇重复 key **抛 `ServiceConflictError`，不做覆盖**。若所有 provider 挤在 `llm:provider` 一个 key 下，第二个 provider 挂载即冲突。
- 否决「单 key 存 `Map<string, LlmProvider>`」：虽然能绕过冲突，但会**丢掉 core 的归属追踪**——`diagnose()` 无法按 provider 报 `ownerFiberId`，某个 provider 卸载时也无法靠 Fiber 自动撤销单条，得自己维护 Map 的增删，等于把 core 刚解决的「可成组撤销」又重新破坏一次。
- 一 provider 一 key 的额外收益：`ctx.get('llm:provider:openai')` 可在**不碰目录服务**的情况下直取，插件之间可做精确软依赖（`inject: {optional:['llm:provider:openai']}`）。

#### D4 `defineLlmProvider()` 把 provider 工厂编译成 core 插件

**决策：** 提供两个导出，内部共用同一构建体：

```ts
export interface LlmProviderDefinition {
  id: string;
  displayName?: string;
  /**
   * 代码侧默认配置（JSON 可序列化）。与清单侧的 `PluginManifestEntry.options`
   * 做**浅合并**，清单侧同名键优先——见 3.4。
   */
  options?: Record<string, unknown>;
  /** 工厂：接收合并后的 options，返回实例；可在内部 await（如预热连接） */
  create(options?: Record<string, unknown>): LlmProvider | Promise<LlmProvider>;
  /** 是否设为缺省 provider（同时只能有一个，后者覆盖并告警） */
  isDefault?: boolean;
}

/** 形态 A：直接得到插件对象（无部署侧覆盖） */
export function defineLlmProvider(def: LlmProviderDefinition): PluginObject;

/** 形态 B：得到工厂，供 main 清单注入 options（参数即 `entry.options`） */
export function defineLlmProviderFactory(
  def: LlmProviderDefinition,
): (options?: Record<string, unknown>) => PluginObject;
```

**为什么必须两个形态（已核对 `main/src/registry.ts:46-57`）：** `main` 的 `defaultLoadPlugin` 兼容三种模块导出——`export default (options) => Plugin`、`export default pluginObject`、`export const plugin`，其中 options 由**外层工厂函数**接收；`ctx` 上没有任何 options 通道。若只给形态 A，用户在清单里填的 `options` 会被**静默丢弃**（最难排查的一类「配置不生效」）；若只给形态 B，无覆盖需求时也要多包一层函数。

**要点：**
- 返回的 `PluginObject` 自带 `inject: { required: ['llm:registry'] }`——**硬依赖**，保证 `llm:registry` 未就绪时 provider 停在 `PENDING`、`apply` 不执行，绝不会出现「provider 抢跑后找不到目录」的中间态。
- `create()` 收的是合并后的 `options`，使「同一份实现、多套配置」能靠清单表达，不必改代码。
- 校验前置到 `defineLlmProvider()` **同步阶段**：`id` 空、`id` 含 `:`（会破坏 key 分段）、`create` 非函数 → 立即抛 `LlmConfigError`。理由：配置错误应在挂载前炸，而不是留到运行期第一次调用时。

**与 main 清单的接线（重要，已核对 `main/src/registry.ts:46-57`）：** `main` 的 `defaultLoadPlugin` 把清单条目的 `options` 传给**模块默认导出的工厂函数**，即兼容形态是 `export default (options) => Plugin`；`ctx` 上**没有** options 通道。因此必须同时提供两个导出：

```ts
/** 用法 A：无部署侧覆盖，直接给插件对象 */
export default defineLlmProvider({ id: 'my-llm', create });

/** 用法 B：清单里可写 options 覆盖 */
export default defineLlmProviderFactory({ id: 'my-llm', create }); // → (options) => PluginObject
```

```ts
export function defineLlmProvider(def: LlmProviderDefinition): PluginObject;
export function defineLlmProviderFactory(
  def: LlmProviderDefinition,
): (options?: Record<string, unknown>) => PluginObject;
```

两者内部共用 `buildPlugin(def, runtimeOptions)`，差异仅在于 `runtimeOptions` 从哪来（A 为空对象，B 由 main 注入）。**否决「只提供 A」**：那用户在清单里写 `options` 会被静默丢弃，是最难排查的一类配置不生效；**否决「只提供 B」**：无覆盖需求时还得包一层函数，且不满足 `export default pluginObject` 这一 main 支持的形态。

**取舍：** 否决「直接导出 class，让用户自己 `ctx.provide(...)`」——用户需要自己记得写 disposer、自己记得删目录登记，任一遗漏就是泄漏；也否决「让 provider 类同时实现 `PluginObject`」——继承一个类同时又要满足插件形态，是概念污染。

#### D5 能力协商：显式声明 + 超能力**显式拒绝**

**决策：** `capabilities(): LlmCapabilities`，字段见 3.2；调用前由 `LlmRegistry` 统一校验，不满足则抛 `LlmCapabilityError`。

```ts
export interface LlmCapabilities {
  streaming: boolean;
  toolCalling: boolean;
  vision: boolean;
  jsonMode: boolean;
  /** 已知上下文上限（token）；未知不填，不伪造 */
  maxContextTokens?: number;
  /** 是否回报用量 */
  usageReporting: boolean;
  /** 是否回报缓存命中 */
  cacheReporting: boolean;
}
```

**取舍：**
- 检索结论一致指向同一个坑：**「兼容某协议」不等于可无损替换**，能力不一致时必须显式拒绝或降级，**不能悄悄忽略参数**（见 2.3 检索要点 ①③）。静默忽略 `tools` 是最坏结果——模型收不到工具却照常返回文本，用户会以为是模型能力问题。
- `usageReporting`/`cacheReporting` 单独成位，是因为「用量缺失」必须记作**未知**而非 **0**（检索要点④），否则成本统计会被系统性低估。
- 否决「能力用布尔大杂烩 `Record<string, boolean>`」——失去类型提示与穷举检查。

#### D6 领域类型命名归一为 camelCase

**决策：** llm 包内用 `promptTokens`/`toolCalls`/`finishReason`/`toolCallId`；与上游协议（`prompt_tokens`/`tool_calls`）的差异由**各 provider 实现自己映射**，包内提供 3.2 的对照表。

**取舍：**
- 支持 camelCase：领域层若照搬上游 snake_case，抽象就被上游协议污染了——这正是本需求要解决的问题本身。
- 支持照搬 snake_case：`src/types.ts` 现有 `LLMUsage` 用 `prompt_tokens`，迁移时可零转换直通。
- **本条列在 Q2 交用户拍板**。默认按 camelCase 实施，因为它保住抽象层纯度；若用户更看重「将来迁移零转换成本」，改默认值即可，不影响其余决策。

#### D7 `LlmError` 继承 core 的 `CoreError`

**决策：** `export class LlmError extends CoreError`，`code` 前缀 `LLM_`；子类 6 个（见 3.6）。

**取舍：**
- 继承的理由：`CoreError` 已带稳定 `code` + `pluginName` + `fiberId` + `cause`（`core/src/errors.ts:22`），这些字段在日志、HTTP 状态映射、跨进程边界都需要；自造基类等于把这些重新实现一遍，且 `instanceof CoreError` 的兜底捕获会漏掉 llm 错误。
- 否决「不继承，独立 `Error`」：宿主统一错误处理会分裂成两套。
- 子类划分沿用 `src/llm/client.ts` 的既有语义（401/404 明确中文提示不重试、429 指数退避、abort 短路），保证将来默认实现能平移。

#### D8 流式统一为领域事件，`stream()` 默认由 `complete()` 降级

**决策：**
```ts
async *stream(req: LlmRequest, opts?: LlmCallOptions): AsyncIterable<LlmStreamEvent>
```
基类默认实现：调 `complete()` → 一次性发 `text-delta` → 发 `done`。原生支持流式的 provider 覆写此方法。

**取舍：**
- **接口最小化**：provider 作者只需实现 `complete()`，不实现流式的也能正常工作（只是失去增量体验）。这避免了「每个 provider 都得写一套 SSE 分片拼接」。
- 否决「`stream()` 设为抽象方法」：会把不支持的实现挡在门外，与 D5 的「能力可声明」自相矛盾。
- 事件形态参照 `src/types.ts:668` 的 `StreamChunk` 四态（`delta`/`toolCallStart`/`toolCallDelta`/`done`），另加 `usage`（用量可能在流末尾才到）——这样将来 `LLMClient.chatStream()` 的分片拼接逻辑可原样搬进默认实现。

#### D9 本期不引入中间件链，只留 `hooks` 扩展位

**决策：** 不做 middleware/拦截器链；`LlmCallOptions` 内保留 `hooks?: LlmCallHooks`（`onRequest`/`onResponse`/`onError`，均同步可选钩子）。

**取舍：**
- 重试、限流、预算、降级、路由这些横切关注点，检索到的成熟方案都是**独立一层**（Router/Policy 层），不是塞进 provider。但它们的正确形态强依赖「谁来决定降级」（宿主？配置？用户？），现在定就是拍脑袋。
- 因此本期只留**最小钩子位**，让宿主有机会观测/短路；等真接入 `src/` 有了真实诉求再设计中间件层（列入演进项）。
- 否决「先做一版 middleware 链」：会造出一堆没有调用方的抽象。

#### D10 事件表用 `extends EventMapBase`，命名 `llm/<verb>`

**决策：**
```ts
export interface LlmEvents extends EventMapBase {
  'llm/registered':   (p: { providerId: string; displayName: string }) => void;
  'llm/unregistered': (p: { providerId: string }) => void;
  'llm/request':      (p: { providerId: string; request: LlmRequest }) => void;
  'llm/response':     (p: { providerId: string; response: LlmResponse; elapsedMs: number }) => void;
  'llm/error':        (p: { providerId: string; error: LlmError }) => void;
}
```

**必须注意的实施细节（来自 20261114-003 的实测教训）：** 消费方**不能**直接 `Plugin<LlmEvents>`，必须 `LlmEvents extends EventMapBase`——因为 `EventMapBase` 带字符串索引签名，`interface` 不会隐式获得，否则报 `TS2344`。同时该索引签名会让 `keyof E & string` 退化为 `string`，即**未声明的事件名不会被拒绝**，收益只是「已声明名字有精确签名」。这一点要写进 README，避免使用者误以为有穷举保护。

#### D11 `installLlm()` 幂等，且 `llm:registry` 只由它提供

**决策：** `installLlm(): PluginObject`——llm 包自己的 bootstrap 插件。重复 `ctx.plugin(installLlm())` 时，第二个 Fiber 会在 `provide('llm:registry')` 处拿到 `ServiceConflictError` → `FAILED`，且错误在 `diagnose()` 可见。

**取舍：**
- 否决「静默忽略重复安装」：`core` 的设计哲学是冲突显式化（`service.ts:41-46` 注释明确说「不做后来者覆盖，因为静默覆盖会让原提供者的 disposer 删掉新提供者的值」），llm 不应在这点上另立标准。
- 但**要给出可读提示**：捕获 `ServiceConflictError` 后重抛为 `LlmError('LLM_REGISTRY_EXISTS')`，消息里写「llm 已安装，请勿重复 installLlm()」，避免使用者对着 `CORE_SERVICE_CONFLICT` 猜。

#### D12 本期零接入 `src/`，只用测试内联假 provider 验证

**决策：** `llm/tests/**` 内写 `FakeProvider extends LlmProvider`，覆盖普通调用、流式、能力拒绝、descriptor 卸载、冲突。**不**改 `src/` 任一行。

**取舍：** 沿用 core/main 的「先搭骨架、渐进迁移」原则（需求 20261114-003 D1 / 004 D1）。若本期就接 `initRuntime`，则「契约是否够用」的验证会被「迁移是否成功」的噪音掩盖，且 `src/` 15 处引用要同批改，无法回滚。

#### D13 视觉/多模态只做**能力位 + 内容分片**，不做独立方法

**决策：** 不新增 `completeVision()`；视觉通过 `LlmContentPart` 的 `{type:'image'}` 分片 + `capabilities().vision` 表达，走同一条 `complete()` 通路。

**取舍：**
- 支持独立方法：`src/llm/client.ts` 确实有独立的 `VisionChatOptions`/`VisionChatResult`，且有独立的视觉客户端缓存（`visionClient`）。
- 反对理由：那是**实现层的缓存优化**，不是契约层差异——大多数现代服务商的视觉就是「消息里带图」的同一条 chat 通路。把实现细节提升为契约，会让「不支持视觉的 provider」多出一个永远返回 `LlmCapabilityError` 的方法，纯属噪音。
- 若将来发现某服务商确实是完全不同端点，再加 `completeVision?` 可选方法属于**加法式演进**，不破坏 D2 的「抽象面只有 `complete()`」。

### 3.2 领域类型（`src/types.ts`）

```ts
/** 内容分片：文本或多模态图片（D13） */
export type LlmContentPart =
  | { type: 'text'; text: string }
  | { type: 'image'; mimeType: string; data: string };   // data：base64 或 data URI

/** 消息四态：system / user / assistant / tool */
export type LlmMessage =
  | { role: 'system'; content: string }
  | { role: 'user'; content: string | LlmContentPart[] }
  | { role: 'assistant'; content: string | null; toolCalls?: LlmToolCall[] }
  | { role: 'tool'; toolCallId: string; content: string };

/** 工具定义：与协议无关的形态，不暴露 function.parameters 之类的上游包装 */
export interface LlmToolDef {
  name: string;
  description: string;
  /** JSON Schema 对象；本期手写校验，不引三方库 */
  parameters: Record<string, unknown>;
}

/** 工具调用：arguments 保持 JSON 字符串（与上游一致，避免二次解析/再序列化丢精度） */
export interface LlmToolCall {
  id: string;
  name: string;
  arguments: string;
}

/** 用量：缺失字段一律 undefined，不填 0（检索要点⑤） */
export interface LlmUsage {
  promptTokens: number;
  completionTokens: number;
  totalTokens: number;
  /** 缓存命中 token 数；provider 不回报时为 undefined（≠0） */
  cacheHitTokens?: number;
  cacheMissTokens?: number;
}

export type LlmFinishReason = 'stop' | 'tool_calls' | 'length' | 'content_filter' | (string & {});

export interface LlmRequest {
  model: string;
  messages: LlmMessage[];
  temperature?: number;
  maxTokens?: number;
  tools?: LlmToolDef[];
  toolChoice?: 'auto' | 'none' | 'required' | { name: string };
  responseFormat?: { type: 'text' } | { type: 'json'; schema?: Record<string, unknown> };
  stop?: string[];
  /** 透传元信息（如 sessionId），provider 可忽略；不得含密钥 */
  metadata?: Record<string, string>;
}

export interface LlmResponse {
  content: string | null;
  toolCalls?: LlmToolCall[];
  finishReason: LlmFinishReason;
  usage?: LlmUsage;
  /** 实际使用的模型名（服务商可能改写别名） */
  model: string;
  /**
   * 受控逃生口（检索要点⑧）：服务商专有字段。
   * 消费方必须容忍其为 undefined 或形状随 provider 变化；核心逻辑不得依赖。
   */
  raw?: unknown;
}

/** 流式事件（D8）：四个语义片段 + 收尾 */
export type LlmStreamEvent =
  | { type: 'text-delta'; delta: string }
  | { type: 'tool-call-start'; index: number; id: string; name: string }
  | { type: 'tool-call-delta'; index: number; argumentsDelta: string }
  | { type: 'usage'; usage: LlmUsage }
  | { type: 'done'; response: LlmResponse };
```

|---|---|---|

### 3.3 `LlmProvider` 抽象基类（`src/provider.ts`）

```ts
export abstract class LlmProvider {
  /** 唯一标识；由 defineLlmProvider 校验非空、不含 ':' */
  abstract readonly id: string;

  /** 展示名；缺省回落 id */
  get displayName(): string { return this.id; }

  /** 能力声明（D5）；缺省全 false + usageReporting false —— 保守默认，逼实现者显式声明 */
  capabilities(): LlmCapabilities {
    return {
      streaming: false, toolCalling: false, vision: false, jsonMode: false,
      usageReporting: false, cacheReporting: false,
    };
  }

  /** 唯一必实现的抽象方法（D2） */
  abstract complete(req: LlmRequest, opts?: LlmCallOptions): Promise<LlmResponse>;

  /**
   * 流式（D8）：默认由 complete() 降级——一次性发 text-delta + done。
   * 原生支持流式者覆写；覆写时须保证最后一个事件是 {type:'done'}。
   */
  async *stream(req: LlmRequest, opts?: LlmCallOptions): AsyncIterable<LlmStreamEvent> { /* 见下 */ }

  /** 卸载钩子：释放连接池/子进程等；由 registry 在 Fiber 撤销时调用，异常被捕获记录 */
  protected async onDispose(): Promise<void> {}
}

export interface LlmCallOptions {
  signal?: AbortSignal;
  /** 最小观测钩子（D9）：不得改变请求/响应语义，只读 */
  hooks?: LlmCallHooks;
}

export interface LlmCallHooks {
  onRequest?(providerId: string, req: LlmRequest): void;
  onResponse?(providerId: string, res: LlmResponse, elapsedMs: number): void;
  onError?(providerId: string, err: LlmError): void;
}
```

**默认 `stream()` 实现要点：**
```ts
async *stream(req, opts) {
  const res = await this.complete(req, opts);
  if (res.content) yield { type: 'text-delta', delta: res.content };
  if (res.usage) yield { type: 'usage', usage: res.usage };
  yield { type: 'done', response: res };
}
```
注意：工具调用场景下默认降级**不发** `tool-call-start`/`tool-call-delta`，因为工具调用在 `complete()` 里已是完整结果，伪造增量无意义；`done.response.toolCalls` 足以表达。这一条要写进 README，避免实现者困惑。

### 3.4 `defineLlmProvider`（`src/define.ts`）

```ts
export function defineLlmProvider(def: LlmProviderDefinition): PluginObject {
  return buildPlugin(def, {});
}

export function defineLlmProviderFactory(
  def: LlmProviderDefinition,
): (options?: Record<string, unknown>) => PluginObject {
  return (runtimeOptions) => buildPlugin(def, runtimeOptions ?? {});
}

/** 两者共用的构建体 */
function buildPlugin(
  def: LlmProviderDefinition,
  runtimeOptions: Record<string, unknown>,
): PluginObject {
  // ① 同步校验（D4）：id 非空、不含 ':'、create 是函数
  assertValidDefinition(def);        // 失败抛 LlmConfigError('LLM_CONFIG_INVALID')

  // ② options 两级合并：代码侧默认值 ← 清单侧覆盖值（见下）
  const mergedOptions = { ...def.options, ...runtimeOptions };

  return {
    name: `llm-provider:${def.id}`,
    inject: { required: [LLM_SERVICE_KEYS.registry] },   // 硬依赖，见 D4
    async apply(ctx) {
      const registry = ctx.get<LlmRegistry>(LLM_SERVICE_KEYS.registry);
      if (!registry) throw new LlmError('llm:registry 不可见（不应发生：inject 已声明硬依赖）');

      const provider = await def.create(mergedOptions);
      if (provider.id !== def.id) {
        throw new LlmConfigError(`provider.id ('${provider.id}') 与定义 id ('${def.id}') 不一致`);
      }
      // 服务登记与目录登记都在 Fiber 内，卸载时自动撤销（D3）
      ctx.provide(`${LLM_SERVICE_KEYS.providerPrefix}${def.id}`, provider);
      ctx.effect(() => registry.register(provider, { isDefault: def.isDefault }), `llm:provider:${def.id}`);
    },
  };
}
```

**`provider.id !== def.id` 的校验是刻意的**：key 由 `def.id` 决定，若实例自报的 id 与之不同，`llm:provider:<def.id>` 与实例 `id` 会永久错位，`diagnose()` 与日志都会对不上，属必须早期炸掉的错误。

**`options` 的两级合并（浅合并，后者覆盖同名键）：**

```
最终 options = { ...def.options, ...manifestEntry.options }
```

| 来源 | 语义 | 谁写入 |
|---|---|---|
| `def.options` | **代码侧默认值**：作者认为合理的缺省（如 `baseUrl` 默认指向官方端点） | provider 作者 |
| `PluginManifestEntry.options` | **部署侧覆盖值**：同实现多套配置（`openai-fast`/`openai-slow`，Q3） | 用户 / 宿主编排 |

只做**一层浅合并**，不做深合并：深合并的数组语义（拼接还是替换？）与嵌套覆盖规则每次都要重新争辩，而 provider 的配置项本就是扁平标量为主。若某个实现需要复杂结构，让它自己在其内部解析 `options` 的某个键。

**否决「合并逻辑放在 registry 里」**：合并发生在 `apply` 内、`create()` 之前，属插件自身的装配决策；放 registry 会让 registry 必须知道 manifest 结构，破坏 llm 包对 main 的零依赖（1.4 约束）。

### 3.5 `LlmRegistry` 与 `installLlm`（`src/registry.ts`）

```ts
export interface LlmRegistry {
  /** 已注册 provider 摘要（按注册序） */
  list(): LlmProviderInfo[];
  /** 取实例；未注册返回 undefined */
  get(id: string): LlmProvider | undefined;
  /** 取实例；未注册抛 LlmProviderNotFoundError */
  require(id: string): LlmProvider;
  /** 缺省 provider：isDefault 显式指定者，否则首个注册者 */
  defaultProvider(): LlmProvider | undefined;
  /** 改缺省；目标不存在抛 LlmProviderNotFoundError */
  setDefault(id: string): void;

  /** 便捷调用：契约校验 → 调 provider → 发事件 → 归一错误 */
  complete(id: string, req: LlmRequest, opts?: LlmCallOptions): Promise<LlmResponse>;
  stream(id: string, req: LlmRequest, opts?: LlmCallOptions): AsyncIterable<LlmStreamEvent>;

  /** 由 defineLlmProvider 的 apply 调用；重复 id 抛 LlmProviderConflictError */
  register(provider: LlmProvider, opts?: { isDefault?: boolean }): Disposer;
}

export interface LlmProviderInfo {
  id: string;
  displayName: string;
  capabilities: LlmCapabilities;
  isDefault: boolean;
}

export function installLlm(): PluginObject;   // provide 'llm:registry'
```

**`complete()` 的固定流水线（顺序不可乱）：**
```
require(id)                         → 未注册：LlmProviderNotFoundError
assertCapability(req, caps)         → 超能力：LlmCapabilityError（D5，先拒绝再调用）
emit 'llm/request'                  → 只读观测
await provider.complete(req, opts)  → 实现自身抛错：归一为 LlmError
emit 'llm/response'（含 elapsedMs）
返回 LlmResponse
```

### 3.6 错误族与事件（`src/errors.ts` / `src/events.ts`）

| 类 | code | 触发条件 | 是否重试 |
|---|---|---|---|
| `LlmError` | `LLM_ERROR` | 基类 / 未分类 | 视 cause |
| `LlmConfigError` | `LLM_CONFIG_INVALID` | `defineLlmProvider` 校验失败、`options` 非法 | 否（配置错，重试无意义） |
| `LlmProviderNotFoundError` | `LLM_PROVIDER_NOT_FOUND` | `require`/`complete`/`stream` 指定 id 未注册 | 否 |
| `LlmProviderConflictError` | `LLM_PROVIDER_CONFLICT` | 同 id 重复 `register` | 否 |
| `LlmCapabilityError` | `LLM_CAPABILITY_UNSUPPORTED` | 请求超出 `capabilities()`（如 `tools` 但 `toolCalling:false`） | 否（应换 provider） |
| `LlmAuthError` | `LLM_AUTH_FAILED` | 401/403 类鉴权失败 | 否（沿用 `client.ts:110` 语义） |
| `LlmRateLimitError` | `LLM_RATE_LIMIT` | 429 | 是（交上层退避） |
| `LlmRequestError` | `LLM_REQUEST_FAILED` | 其余服务商侧错误 | 视 code |
| `LlmAbortedError` | `LLM_ABORTED` | `signal.aborted` | 否（短路，沿用 `client.ts:16` 语义） |

事件表见 D10。**事件只读**：监听器抛错不得中断调用链（由 `core` 的 `TypedEventBus` 语义保证，llm 侧不做额外 try/catch 包裹）。

### 3.7 边界与错误处理

| 场景 | 行为 |
|---|---|
| `llm:registry` 未安装就挂 provider | provider Fiber 停在 `PENDING`（`inject.required` 生效），`apply` 不执行；`diagnose().fibers[].missing = ['llm:registry']` |
| 重复 `installLlm()` | 第二个 Fiber `provide` 时撞 `ServiceConflictError` → 重抛 `LlmError('LLM_REGISTRY_EXISTS')`，提示「请勿重复安装」 |
| 同 id 挂两个 provider | `defineLlmProvider` 阶段通过，`apply` 时 `ctx.provide('llm:provider:x')` 抛 `ServiceConflictError` → Fiber `FAILED`，条目仍留清单，`diagnose()` 可见 `loadError` |
| provider 卸载 | Fiber 逆序执行 disposer → `registry.register` 返回的 disposer 注销目录 → `provider.onDispose()`；`onDispose` 抛错被捕获记入 `disposeErrors`，不阻断其他 disposer |
| `complete()` 抛非 `LlmError` | 归一包装为 `LlmError`，`cause` 挂原始错误，`pluginName`/`fiberId` 从 ctx 补全 |
| 请求带 `tools` 但 `toolCalling:false` | 调用前抛 `LlmCapabilityError`，**不发**网络请求（D5） |
| `usage` 缺失 | `LlmUsage` 为 `undefined`，**不构造全 0 对象**（检索要点⑤） |
| `signal` 已 aborted | 立即抛 `LlmAbortedError`，不发请求 |
| 流式实现提前结束（无 `done`） | `registry.stream()` 检测到最后事件非 `done` 时**不上抛错误**，只在末尾补一个 `done`（响应体由已累积分片尽力构造）；此行为写入 README |
| `options` 含不可序列化值 | 属 `main` 清单层的职责（`PluginManifestEntry.options` 只收 JSON）；llm 侧不做二次校验 |

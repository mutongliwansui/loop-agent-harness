A. 现状问题

先问为什么改

当前模型页（ModelsView）沿用 20261029-004 的「行卡 + 页头 scope」结构，功能完整，但对照已落地的工具 / 技能页「卡片流 + 统计条 + 抽屉」范式，有 5 个具体问题：

1
信息层级平，扫视抓不到重点

别名、型号、主机、四位 Key 全部挤在同一行 meta，字号与颜色几乎一致；「哪个是正在用的」只能靠左侧一条细边和一枚 pill 判断。

2
状态语义混杂，没有汇总

未测试、未测速与真实失败共用同一种淡色 pill；失败行只靠红色小点区分，页面顶部也没有「几个模型需要处理」的汇总，异常容易被忽略。

3
每行 4 个操作，图标靠猜

测试 / 测速 / 设置为默认 / 删除平铺在行尾，「测速」与「删除」只隔一个按钮，误触成本高；图标的语义完全依赖 title 悬停。

4
没有详情，测速数据只值一枚 pill

完整 Base URL、temperature、最近一次测速的 p50 / 成功率 / 历史走势都无处查看；排查 401 时只能重新点测试再读 toast。

5
写入位置是页头全局开关

scope 影响登记 / 切换 / 删除三类写操作，却远离操作现场；用户很容易在「全局」状态下删掉工作空间里的模型，或反过来。

6
与相邻页面不像一套

工具、技能、MCP 都已是双列卡片 + 统计条 + 右侧抽屉；模型页仍是行列表，视觉密度与交互手感都不一致。

B. 设计决策

D1–D10

沿用 20261109-001 / 002 / 003 已经建立的「卡片流 + 统计条 + 工具条 + 抽屉」范式；除新增一个编辑端点外，其余接口保持不变。

D1
双列卡片流，生效模型置顶

桌面两列、窄屏单列。卡片 = 服务商 tile + 别名 + 服务商标签 + 型号 / 主机 / Key + 状态胶囊 + 底部操作。生效卡左侧 3px 品牌条 + 极淡品牌底，并恒排第一。

D2
卡片只保留一个主操作

卡片底部只放「设置为默认」（或「当前生效」文字）；测试、测速、复制、删除全部收进右上角 ⋯ 菜单，降低误触，同时把「删除」与常用操作隔开。

D3
统计条：已登记 / 生效中 / 需关注

「需关注」= 连通失败或测速全失败。数字实时联动筛选与分段计数；异常数用红色，未测试 / 未测速不计入异常。

D4
工具条：搜索 + 状态分段 + 排序 + 写入位置

搜索匹配别名 / 型号 / 主机；分段「全部 / 生效中 / 需关注」；排序「生效优先 / 别名 A→Z / TTFT 升序」。写入位置收进工具条右侧，并在添加抽屉、详情抽屉底部就地同步。

D5
详情抽屉承载配置与性能

点卡片或「查看详情」打开右侧抽屉：接入配置（KV 表）→ 连通性（就地重测）→ 性能（TTFT / 吞吐 / 稳定性 + 历史 + 抽屉内测速）→ 危险区（移除）。

D6
测速在抽屉内闭环

「开始测速」→ 进度条 + 四项实时指标 → 完成后结果与历史即时回流到卡片 pill。真实实现复用 BenchDrawer 的四态，原型只演示入口、运行态与结果回流。

D7
添加 / 编辑共用右侧表单抽屉

基础字段（别名 / 型号 / Base URL / API Key / temperature）常驻可见；其余采样与传输参数收进「高级设置」折叠区，默认收起。实时行内校验；编辑时别名只读、Key 留空不改。写入位置在提交区就地可见，不再只存在于页头。

D8
异常前置

失败卡片红色左条 + 「连通失败 / 测速全失败」红 pill；顶部出现汇总告警条，一键直达第一个异常模型的详情。

D9
中性状态降噪

未测试 / 未测速用中性灰 pill，不再用黄色暗示「有问题」；绿色只给成功，红色只给真实失败。

D10
编辑信息：新增 PATCH /models/:alias（需后端配套）

别名是登记簿主键，编辑时只读；可改型号 / Base URL / API Key / temperature，另有「高级设置」折叠区（max_tokens、top_p、top_k、frequency_penalty、自定义请求头、请求超时），默认收起、留空即不下发。上下文窗口不在模型页配置。Key 留空表示保持原值，填写则整体替换并重新遮蔽。保存后清空连通性结果并提示重新测试；改名仍走「移除 → 重新登记」。删除当前生效模型继续由后端 409 兜底。

D11
高级设置默认收起

展开前只在折叠头显示「已配置 N 项」，避免长表单吓退普通用户；校验失败落在折叠区时自动展开并聚焦红框。请求头以「名 = 值」成对维护，Authorization / Content-Type 等系统头拒绝覆盖。

E. 接口映射

后端零改动
GET /models → { profiles: [{ alias, name, baseUrl, apiKey, temperature?, isCurrent }], active }（列表数据源，apiKey 已遮蔽）
GET /model → 当前生效快照；无激活但存在登记时，页面提示“正在使用配置文件 model.* 快照”
PUT /model { alias, scope } → 「设置为默认」；成功后同步 models.active 与 model.* 快照
POST /models { alias, scope, profile } → 添加抽屉提交；同名返回 409，前端在别名字段行内提示
PATCH /models/:alias { scope, profile: { name, baseUrl?, apiKey?, temperature?, advanced? } } → 编辑抽屉保存；别名不可改；advanced 内为 maxTokens / topP / topK / frequencyPenalty / timeoutMs / headers（留空即删除该键，不下发）。若编辑的是当前生效模型，后端需同步刷新 model.* 快照 新增端点，待后端实现
POST /models/:alias/test → 连通性测试，返回 { ok, latencyMs, error? }；卡片与详情抽屉的状态胶囊就地更新
DELETE /models/:alias?scope= → 移除；删除当前激活模型返回 409，前端在生效卡片上禁用删除并说明
POST /models/bench · GET /models/bench/:id/stream · POST /models/bench/:id/stop · GET /models/bench/history → 测速入口、进度、中断与历史；抽屉内“性能”区复用它

编辑接口是新增需求：现有后端没有更新 profile 的端点，本设计新增 PATCH /models/:alias { scope, profile }，更新型号 / Base URL / API Key / temperature，以及高级设置里的 max_tokens、top_p、top_k、frequency_penalty、自定义请求头、请求超时。高级项留空即删除该键（回到服务商默认），不写 null。上下文窗口仍由全局 context.* 管理，不进模型配置。别名是登记簿主键，不可修改；重命名仍走「移除 → 重新登记」。落地前需后端补该端点，并在编辑生效模型时同步 model.* 快照。

F. 响应式

三个断点
≥ 980
桌面 · 双列

卡片两列；统计条 3 项均分；搜索 max-width 320px；写入位置靠工具条右侧。

700–980
平板 · 单列

卡片单列；统计条保持一行；分段与排序折行但仍靠左排列。

≤ 700
手机 · 堆叠

页头纵排，主按钮撑满；搜索独占一行；卡片底部操作换行；抽屉宽度 100%。

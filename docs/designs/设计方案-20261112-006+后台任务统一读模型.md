# 设计方案-20261112-006 后台任务统一读模型（命令任务 + 后台子 Agent 任务）

- 对应需求：`20261112-006`（[需求台账](../requirements/需求.md)）
- 提出日期：2026-11-12
- 状态：**已实施（2026-11-12，待真机验收）**
- 用户决策：统一读模型（不合并执行内核）· 扩展 `commandStatus` · Dock 显示「当前会话 + 无归属」

## 一、背景与现状

### 1.1 两套并行机制

| 维度 | 后台命令任务 | 后台子 Agent 任务 |
| --- | --- | --- |
| 注册表 | [`background-tasks.ts`](file:///d:/trae_workspace/loop-agent-command/src/tools/background-tasks.ts) | [`subagent-registry.ts`](file:///d:/trae_workspace/loop-agent-command/src/agent/subagent-registry.ts) |
| 标识 | `bg_<hex8>_<ts>` | `sub_<callId>` |
| 持久化 | 内存 + `runs/*.json` + `*.log`，重启孤儿扫描 | 仅内存，重启即丢 |
| 状态词 | `running / exited / killed / orphaned-running / orphaned-exited` | `running / done / failed / aborted` |
| 归属 | `task.sessionId`（CLI 首轮可空） | `record.sessionId` |
| 创建 | `commandRun({background:true})` | `delegate({background:true})` |
| 模型查询 | `commandStatus / commandLogs / commandStop` | 无 |
| CLI 查询 | 无 | `/subagent list / show` |
| HTTP | `GET /background/:id`、`/logs`、`POST /stop` | `GET /sessions/:id/subagents` |
| 展示 | ToolCard 内嵌 `BackgroundTaskCard` | `SubAgentDock` + 结果卡片 |
| 单任务停止 | 有 | 无（仅删会话 `abortSession`） |
| 数量控制 | 200 上限 / 列表 50 | 无淘汰 |

### 1.2 问题

1. **模型只能查一半**：`commandStatus` 只读 `backgroundTasks`，子任务运行中不可见，只能等完成通知。
2. **Dock 只能看一半**：只轮询 `/subagents`，命令任务滚出视口后没有常驻入口。
3. **查询范围不一致**：`commandStatus` 全局、只取 5 条、不按会话过滤；子任务按会话过滤。
4. **状态词与停止语义不一致**：合并展示时必须显式表达差异，否则用户误以为两者都能停、都会保留。
5. **重复建设**：两套通知、两套卡片、两套状态词。

## 二、目标与非目标

### 2.1 目标

- 模型一次查询能看到当前会话的命令任务与子任务；
- 输入区上方常驻指示器同时展示两类任务；
- 查询与展示使用同一套状态词、同一套会话过滤规则；
- 执行、持久化、通知路径保持不动，降低回归面。

### 2.2 非目标

- 不合并两个 registry，不改持久化与孤儿清扫；
- 不统一完成通知的注入路径与卡片形态；
- 本期不给子任务提供单任务停止 API（Dock 上子任务不显示停止按钮）；
- 不新增工具（复用 `commandStatus`）。

## 三、总体设计

```
backgroundTasks (命令)          subAgentRegistry (子任务)
        │                              │
        └──────────┬───────────────────┘
                   ▼
          src/background/jobs.ts
          （状态映射 / 会话过滤 / 排序 / 上限）
                   │
     ┌─────────────┼──────────────────────┐
     ▼             ▼                      ▼
 commandStatus   GET /sessions/:id/jobs   CLI /jobs
 （模型查询）      （Dock 轮询 / 外部）      （终端列表）
                   │
                   ▼
            BackgroundDock（原 SubAgentDock）
```

**核心不变量**：只读聚合，不写入两个 registry；原端点与工具全部保留。

## 四、关键设计决策

| 编号 | 决策 | 理由 / 被否决项 |
| --- | --- | --- |
| **D1** | 统一到「读模型」层，执行内核保持两套 | 合并内核需重做持久化、孤儿清扫、并发上限与通知，风险不匹配收益 |
| **D2** | 统一状态词固定为 `running / done / failed / stopped / lost` | 两套状态词无法直接合并；映射集中在一个纯函数，便于单测与 UI 复用 |
| **D3** | 命令任务的 `orphaned-*` 映射为 `lost`，`killed` 映射为 `stopped` | 保留「已结束 / 失联 / 被停止」的语义差异，不伪造统一生命周期 |
| **D4** | 会话范围为「当前会话 + `sessionId` 为空的归属未知任务」 | 用户已确认；避免跨会话串数据，同时不丢 CLI 首轮等无归属任务 |
| **D5** | 扩展 `commandStatus` 的返回内容与 description，不改名、不新增工具、不加参数 | 不增加工具 schema 与 `tools` 数组变化；工具描述改为「后台任务」 |
| **D6** | Dock 数据源改为 `/sessions/:id/jobs`，一次轮询覆盖两类任务 | 避免两套轮询；`run` 状态继续随响应返回，唤醒接管逻辑不变 |
| **D7** | 子任务条目保留 `trace/iterations`，命令条目保留 `canStop` | 现有过程区同步与停止按钮都需要，避免额外请求 |
| **D8** | 统一列表上限 50、终态记录上限 200 | 子任务 registry 目前无淘汰，需要补，防止长时间运行内存增长 |

## 五、详细设计

### 5.1 数据模型

```ts
export type JobKind = 'command' | 'subagent';
export type JobStatus = 'running' | 'done' | 'failed' | 'stopped' | 'lost';

export interface JobSummary {
  id: string;
  kind: JobKind;
  sessionId?: string;
  title: string;
  status: JobStatus;
  startedAt: number;
  finishedAt?: number;
  elapsedMs?: number;
  iterations?: number;
  error?: string;
  /** 子任务过程轨迹（运行中过程区同步用；命令任务为 undefined） */
  trace?: SubAgentTrace;
  canStop: boolean;
  canReadLogs: boolean;
}
```

状态映射（纯函数）：

| 源 | 统一 |
| --- | --- |
| 命令 `running` | `running` |
| 命令 `exited` + `exitCode === 0` | `done` |
| 命令 `exited` + 非 0 / `null` | `failed` |
| 命令 `killed` | `stopped` |
| 命令 `orphaned-running` / `orphaned-exited` | `lost` |
| 子任务 `running` | `running` |
| 子任务 `done` / `failed` / `aborted` | `done` / `failed` / `stopped` |

### 5.2 聚合与过滤

```ts
listJobs(opts?: {
  sessionId?: string;
  includeUnowned?: boolean; // 默认 true；仅 sessionId 有值时生效
  kind?: JobKind;
  status?: JobStatus;
  limit?: number;           // 默认 50，最大 100
}): JobSummary[]

getJob(id: string): JobSummary | undefined
```

- 命令任务取 `backgroundTasks.list()`（已按 startedAt 倒序、最多 50）；
- 子任务取 `subAgentRegistry.list()`，按 `startedAt` 倒序；
- 合并后统一排序、过滤、截断；
- `sessionId` 过滤：`item.sessionId === sessionId` 或（`includeUnowned` 且 `!item.sessionId`）。

### 5.3 子任务 registry 淘汰

`SubAgentRegistry.create()` 超过 200 条时，淘汰最老的终态记录（`running` 永不淘汰）；与命令任务表口径一致。

### 5.4 HTTP

新增 `GET /sessions/:id/jobs`：

- 校验会话存在（与 `/subagents` 同路径）；
- 查询参数 `kind` / `status` / `limit`；
- 返回 `{ items: JobSummary[], run: RunSnapshot | null }`；
- 原 `GET /sessions/:id/subagents` 保留，避免破坏既有消费方。

### 5.5 模型工具 `commandStatus`

- 参数保持不变（仅 `taskId`）；不带 `taskId` 时返回当前会话 + 无归属的最近 5 条，条目含 `taskId / kind / status / title / startedAt`；
- 带 `taskId`：命令任务维持原有详细字段（pid/日志大小/exitCode）；子任务返回状态、轮次、错误与「结果通过完成通知投递」提示；
- `commandLogs` / `commandStop` 遇到子任务 ID 时返回明确提示（不支持日志/停止），避免误判为「任务不存在」。

### 5.6 WebUI

- `chat-stream.ts`：`SubAgentTaskVM` 保留；新增 `JobTaskVM extends SubAgentTaskVM`（增加 `kind`、`canStop`），`jobsOf(sessionId)` 替代 `subAgentTasksOf`；
- 轮询端点改为 `/sessions/:id/jobs`，一次刷新两类任务；`run` 状态与唤醒接管逻辑不变；
- `SubAgentDock.vue` 升级为 `BackgroundDock.vue`：
  - 标题「后台任务」，计数为两类运行中之和；
  - 展开行增加 kind 徽标（命令 / 子任务）；
  - `canStop` 为真时显示停止按钮，调用既有 `POST /background/:id/stop`；
  - `aborted` / `interrupted` 文案沿用现有映射；
- 完成提示按 kind 生成「后台命令任务 / 后台子任务」。

### 5.7 CLI

新增 `/jobs`：

- 列出当前会话 + 无归属任务（最多 20 条），列 `kind / status / id / title`；
- `/jobs show <id>` 输出统一摘要；命令任务附日志路径，子任务附轮次与错误；
- `/subagent`、`/subagent show` 保留。

## 九、风险与回滚

| 风险 | 缓解 |
| --- | --- |
| 查询范围从全局改为会话内，模型可能看不到别的会话任务 | 明确「无归属」兜底；后续可加 `scope=all` |
| Dock 轮询数据量变大（含 trace） | 保持 2s 间隔；列表截断 50；trace 仅运行中项有值 |
| 子任务 registry 淘汰影响 CLI 历史可见性 | 仅淘汰 200 条以上最老终态，运行中永不淘汰 |
| 工具描述变更导致一次缓存 miss | 一次性变化，层内后续稳定 |
| 停止按钮只对命令任务开放可能让用户困惑 | 行内 kind 徽标 + 子任务不渲染按钮 |

回滚：前端恢复 `/subagents` 数据源、隐藏命令任务；后端 `commandStatus` 恢复只查 `backgroundTasks`。新增模块与端点可保留不调用。

## 一、问题与目标

### 1.1 现状

当前图形界面的使用链路是「两条命令 + 一次手输地址」：

```powershell
# 1) 起后端（常驻，占住一个终端窗口）
loop-agent.exe --serve

# 2) 用户自己去浏览器输入地址
http://127.0.0.1:3000
```

对开发机这没问题；对现场（Windows 10 神州网信政府版 19044，**没有源码、没有 node_modules、没有 npm**）的非技术用户，这条链路有三个硬门槛：

| 门槛 | 现象 | 后果 |
|---|---|---|
| 要记命令 | 必须知道 `--serve` 这个参数，还要保持那个黑窗口不关 | 关掉黑窗口 = 服务停 = 页面白屏，误操作率极高 |
| 要记地址 | 必须记住 `127.0.0.1:3000` | 输错、被浏览器补全成 `https://`、搜索框里当关键词搜 |
| 端口独占 | 端口固定 3000 | 现场若已被占用（其他工具/旧实例），启动直接失败，用户看不懂 `EADDRINUSE` |

### 1.2 目标（一句话）

**双击一个图标 → 出应用窗口 → 关窗口即退出**，全程不出现命令行、不需要知道端口，浏览器可以完全不参与。

### 1.3 非目标

- 移动端 App、多用户账号体系
- 系统级开机自启注册（列演进项）
- 把 WebUI 改写成桌面专属原生界面（界面本体一行不改）
- 移除 `--serve` 浏览器访问路径（它要继续原样可用）

## 二、可复用的既有资产（决定方案成本的关键）

检索并核实了代码现状，桌面化几乎是「只加壳」：

| 资产 | 现状 | 对桌面化的意义 |
|---|---|---|
| 动态端口 | `createApiServer().start()` 返回真实监听端口（`src/api/server.ts:286-302`），`--port` 已支持 `--port=N` 形式（`src/config/cli-overrides.ts:42-56`） | 壳可以传 `--port 0` 让系统分配空闲端口，**根治端口冲突** |
| 静态托管 | `resolveStaticHandler()` 支持「磁盘 webui/dist → SEA 内嵌资源 → 降级纯 API」（`src/api/server.ts:249-250`） | 前端无需改动，同源相对路径请求原样可用 |
| 单文件产物 | `npm run build:sea` 已产出 `dist-sea/loop-agent.exe`（实测 102MB，内嵌 WebUI 9.6MB + PTY 原生模块） | 后端已有「零依赖分发」形态，壳只需拉起它 |
| 前端网络层 | `webui/src/api/client.ts` 全部用同源相对路径 `fetch('/sessions')`，不硬编码 localhost | 换任何承载窗口都不需改前端 |
| 鉴权 | 无 token 时只放行回环地址（`src/api/http-utils.ts:89-93`）；非回环无 token 拒绝启动（`src/api/server.ts:242-247`） | 桌面壳绑 127.0.0.1 即可零配置可用，且不会裸奔 |
| 优雅关停 | SIGINT/SIGTERM/SIGBREAK 触发「停调度器 → 跑 Dreaming 晋升 → 关服务 → 断 MCP → 退出」，二次信号立即强退（`src/api/bootstrap.ts:145-161`）；但该序列**只挂在信号处理上**，无 HTTP 关停端点 | **需要注意**：Windows 下父进程发信号等于强杀（见 D7 实测），故此能力**需补一个关停端点**才能被壳复用 |
| 端口覆盖 | `--port` 支持 `--port N` / `--port=N`，但 `parsePort` 只接受 `1..65535`（`src/config/cli-overrides.ts:30-35`） | 传具体端口可用；**`--port 0` 会被静默忽略**，故端口须由壳先探测（见 D3） |

**结论：桌面化的工程量集中在「壳」这一层，后端与前端都不需要为桌面化让步。**

## 三、三条候选路线与取证

### 3.1 路线对比

| 维度 | **A. Electron 全内置壳** ⭐推荐 | B. Tauri 壳 | C. 浏览器应用模式 + 托盘 |
|---|---|---|---|
| 渲染内核 | 自带 Chromium（壳内置） | 用系统 WebView2 | 用系统 Edge/Chrome |
| 现场依赖 | **零**（内核随包） | 依赖 WebView2 | 依赖 Edge/Chrome |
| 交付体积 | 约 180–260MB（Electron 基座 + 后端 exe 可复用） | 约 60–80MB | 约 0.1MB + 后端 exe |
| 构建机要求 | 仅需 Node/npm | **需 Rust 工具链 + VS C++ Build Tools** | 仅需 Node/npm |
| 「像桌面应用」程度 | 高（自绘标题栏、独立图标、任务栏归属） | 高 | 中（应用模式窗口无地址栏，但仍由浏览器进程托管，任务栏常并入浏览器图标） |
| 前端改动 | 零 | 零 | 零 |
| 主要风险 | 体积大；原生模块 ABI 需按 Electron 重编 | 现场 WebView2 缺失/异常时白窗；构建链重 | 与用户日常浏览器会话/单例进程纠缠，行为随浏览器版本漂移 |

### 3.2 取证：现场 WebView2 与 Edge 的实际状态

已在本机（同为目标现场形态）实测：

```text
C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe       → 存在
HKLM\...\EdgeUpdate\Clients\{F3017226-...} pv                       → 157.0.4341.46
```

即 WebView2 运行时**已安装**（157.x）。但**这是本机结论，不能外推到所有现场机**。官方文档明确指出：

> 绝大多数 Windows 10 设备已预装 WebView2 运行时，但**少数设备没有**，建议应用自行检测并兜底。

而且 Tauri 的已知失败模式正是这一类：运行时缺失或不一致时**窗口闪一下就消失**，且不给用户可读错误：

- [tauri#12030](https://github.com/tauri-apps/tauri/issues/12030)：卸载 WebView2 后 Tauri Demo「窗口出现后立刻关闭」，重装运行时才恢复
- [tauri#11969](https://github.com/tauri-apps/tauri/issues/11969)：`tauri-runtime-wry` 创建 webview 失败，报 `HRESULT 0x8007139F / 0x80070002`，**在 10.0.19044 / 19045 上均有用户报告**
- [tauri#12787](https://github.com/tauri-apps/tauri/issues/12787)：`EBWebView` 目录创建失败导致同样闪退，用户侧「运行时明明装了却认不到」

**结论**：路线 B 的失败面恰好落在「无源码、无管理员权限、无法装运行时」的现场，属于不可接受的交付风险。

### 3.3 取证：浏览器应用模式（路线 C）的纠缠点

Chromium 的进程单例是按 `user-data-dir` 合并的（[官方 user_data_dir 文档](https://github.com/chromium/chromium/blob/main/docs/user_data_dir.md)、[Chromium Startup 分析](https://textslashplain.com/2022/06/15/chromium-startup)）：

> 若已有 Edge 实例在跑，**多数命令行参数会被忽略**，请求转交给已有实例；窗口尺寸、位置、`--class` 等均不生效，除非另指定独立的 `--user-data-dir`。

这意味着路线 C 想要「独立应用窗口、不污染用户浏览器」，就必须给壳单独一个 `--user-data-dir`。可行，但带来新代价：

- 独立 profile 目录 = 一份完整浏览器缓存目录，体积与维护成本并不比壳小多少
- 一旦用户机器上 Edge 升级/被策略管控/被卸载，壳的行为随之漂移，**我们无法通过发版控制**
- 任务栏图标归属、窗口标题、Alt+Tab 表现依赖浏览器实现细节（[Chromium issue 40697864](https://issues.chromium.org/issues/40697864) 里这类诉求长期未彻底解决）

### 3.4 取证：Electron 路线的真实代价

代价只有一项，且可控：**原生模块 ABI 差异**。

`@lydell/node-pty` 是原生模块（`node_modules/@lydell/node-pty-win32-x64/prebuilds/win32-x64/conpty.node`）。Electron 的 ABI 与同版本 Node 不同（Chromium 用 BoringSSL），官方要求用 `@electron/rebuild` 重编：

> `Error: The module ... was compiled against a different Node.js version using NODE_MODULE_VERSION $XYZ`

**规避方式（关键）**：本项目的后端**已经是一个独立的 SEA 可执行文件**，终端能力由它在自己的进程内加载 PTY（`src/terminal/pty-embed.ts` 释放到 `%TEMP%/loop-agent-pty-<hash>`）。因此 Electron 壳**不需要把 node-pty 装进 Electron 进程**——壳只负责 `spawn` 那个后端 exe，PTY 全程跑在纯 Node 运行时里。

**这条架构既有的「进程分离」，正好把 Electron 唯一的痛点消掉了。**

## 四、推荐方案：Electron 壳 + 既有 SEA 后端（进程分离）

### 4.1 总体架构

```text
┌──────────────────────────────────────────────────────────┐
│  loop-agent.exe（双击入口，Electron 壳）                    │
│                                                          │
│  ① 单实例检查（拿到锁则继续，否则聚焦已有窗口后退出）          │
│  ② 选端口（优先 3000，占用则退让，最终兜底 0=系统分配）        │
│  ③ spawn 后端：loop-agent-core.exe --serve --port <p>       │
│       └─ 等待 /health 就绪（轮询 + 超时 + 失败可读提示）      │
│  ④ BrowserWindow.loadURL(http://127.0.0.1:<p>)             │
│  ⑤ 窗口关闭 → POST /admin/shutdown → 等后端退出 → app.quit()   │
│       └─ 超时兜底 taskkill /T /F（跳过 Dreaming 的最后手段）     │
└──────────────────────────┬───────────────────────────────┘
                           │ HTTP / SSE（回环，无 token）
┌──────────────────────────▼───────────────────────────────┐
│  loop-agent-core.exe（既有 SEA 产物，零改动）               │
│  静态托管 webui/dist 内嵌资源 · REST · SSE · PTY · Dreaming │
└──────────────────────────────────────────────────────────┘
```

**关键点：壳与后端是两个进程。** 这个选择带来四个直接好处：

1. PTY 原生模块不需要为 Electron 重编（跑在后端进程里）
2. 后端崩溃/卡死不会带崩窗口，壳可以重启它并给用户提示
3. 关窗杀后端 = 杀整棵进程树，不会留孤儿进程
4. 后端产物与 `--serve` 分发共用同一份，**不产生第二套构建链路**

### 4.2 用户可见变化

| 场景 | 现在 | 方案后 |
|---|---|---|
| 获取 | 拷贝 exe、记命令 | 运行安装包，一路下一步（不弹 UAC） |
| 启动 | 开终端敲 `loop-agent.exe --serve`，再去浏览器输地址 | 双击图标 / 开始菜单 |
| 停止 | 关终端窗口（可能留着后台进程） | 关应用窗口 |
| 端口冲突 | 启动失败，看不懂报错 | 自动让位到空闲端口，用户无感 |
| 重复双击 | 起第二份后端，抢同一批会话文件 | 聚焦已有窗口 |
| 忘记地址 | 需自备书签 | 不需要地址 |
| 卸载 | 手动删目录 | 控制面板/设置里卸载 |

### 4.3 与既有分发的关系

```text
npm run build:webui   → webui/dist
npm run build:sea     → dist-sea/loop-agent.exe            （后端，现状保留）
npm run build:desktop → dist-desktop/
                          ├─ LoopAgent-Setup-<ver>.exe      ← 主交付：NSIS 按用户安装包
                          └─ LoopAgent-<ver>-Portable.exe   ← 附带：装不上时的兜底
```

**安装后的实际布局**（electron-builder 标准结构，后端经 `extraResources` 落 `resources/`，见 D11）：

```text
%LOCALAPPDATA%\Programs\LoopAgent\
├─ LoopAgent.exe                  ← 双击/开始菜单快捷方式入口
├─ resources\
│   ├─ app.asar                   ← 壳代码（主进程）
│   └─ loop-agent-core.exe        ← 既有 SEA 后端，原样拷入（102MB）
└─ ...
```

安装过程对用户是「一路下一步」的 one-click 形式：默认装到当前用户目录，**不弹 UAC**，自动建开始菜单与桌面快捷方式。

## 五、关键设计决策（D1–D12，待逐条确认）

| 编号 | 决策 | 取舍与理由 |
|---|---|---|
| **D1** | **选 Electron 全内置壳，否决 Tauri 与浏览器应用模式** | Tauri 的失败面（WebView2 缺失/异常闪退）恰好落在现场无法自救的位置；浏览器应用模式受 Chromium 单例与版本漂移支配，且需独立 profile。Electron 自带内核，行为由我们发版锁定。**代价是体积约 180–260MB，接受。** |
| **D2** | **壳与后端双进程，不做进程内嵌** | 保住「PTY 跑纯 Node、Electron 不碰原生模块」这条既有优势，同时获得崩溃隔离与干净的进程树回收。否决「把后端作为 Electron 主进程的一坨 JS 直接 require」（会立刻触发 ABI 重编与生命周期耦合）。 |
| **D3** | **端口策略：壳先自行探测空闲端口（从配置端口起，被占则顺延），再以 `--port <具体值>` 传给后端；不使用 `--port 0`** | **实测发现 `--port 0` 不可用**：`parsePort()` 明确要求 `1..65535`，`0` 被判非法而**静默丢弃**（`cli-overrides.ts:30-35`），后端会回落到配置里的 3000——即「用 0 兜底」实际不生效。故改为：壳用 `net.Server.listen` 试绑端口判占用，选到一个空端口后传具体值。这样壳在 spawn 前就知道端口，**无需解析后端 stdout**。同时保留「默认沿用 3000」以兼容老书签。**否决一步到位只用随机端口**（会让 `--serve` 与桌面版地址不一致，排障成本上升）。 |
| **D4** | **就绪判定用 `GET /health` 轮询，不用固定 sleep** | `/health` 已返回 `{status,version,model}`（`src/api/router.ts:114-118`）。**实测 SEA 从 spawn 到 `/health` 返回 200 约 2.5s**，故轮询 200ms/次、上限 60s 足够宽裕。超时则展示后端 stderr 尾部而非白屏。**否决「窗口先开、页面自己重试」**——那会退化成白屏 + 用户干等。 |
| **D5** | **默认不配置 token（绑定 127.0.0.1）；若用户已配置 `api.token`，壳在页面加载前用 `executeJavaScript` 写入前端既有的 localStorage 键 `loop_agent_token`** | 既有策略：无 token 时仅放行回环（`http-utils.ts:89-94`）。桌面场景本机单用户，配 token 只增加「令牌输错 → 进不去」的故障点。已配 token 时的兼容**不走 URL 参数**（前端 `client.ts:27-38` 只读写 localStorage，不解析 query），改由壳在主进程侧预置 localStorage，**前端仍零改动**。 |
| **D6** | **单实例用 Electron `requestSingleInstanceLock()`，二次启动聚焦已有窗口** | 官方机制，跨平台。**否决文件锁/端口探测自研**（Win 上文件锁释放时机不可靠，端口探测无法定位到窗口）。 |
| **D7** | **关窗即退，但优雅关停必须由「新增后端关停端点」实现，不能靠 `kill('SIGINT')`** | **实测证伪原设想**：Windows 无 POSIX 信号，Node 官方文档明确「发 `SIGINT`/`SIGTERM`/`SIGKILL` 会**无条件强制终止**目标进程」（[process 文档](https://nodejs.org/api/process.html)）；本机实测确认——子进程装了 `SIGINT` handler，父进程 `child.kill('SIGINT')` 后 **handler 未执行**（`handler-ran=false`），进程被直接杀掉。而 `runAllForShutdown`（Dreaming）目前**只挂在信号处理里**（`bootstrap.ts:146-161`），`router.ts` 中无任何 `/shutdown` 类端点，因此**当前没有任何跨平台手段能触发优雅关停**。故本任务须新增 `POST /admin/shutdown`：仅在回环 + 已鉴权时可用，内部复用既有「停调度器 → `runAllForShutdown(budget)` → `server.close()` → 断 MCP → 退出」序列；壳先调该端点并等待进程退出，超时（默认 `shutdownBudgetMs` + 5s）才 `taskkill /T /F` 兜底。**否决直接 kill**（跳过 Dreaming 即丢记忆），**否决仅 macOS/Linux 优雅、Windows 强杀**（现场就是 Windows，等于优雅关停不存在）。 |
| **D8** | **窗口外观：自绘标题栏可后置，P0 先用系统原生边框** | 原生边框零成本、零 bug、无障碍天然正确；自绘标题栏属视觉精修，放 P2。**否决 P0 就上无边框**（拖拽区、双击最大化、吸附分屏都要自己实现，收益不抵成本）。 |
| **D9** | **⚠️ 实施期修订（2026-11-12）：窗口状态与首选端口不复用主工程配置体系，改存 Electron `userData`** | 原设想为「新增 `desktop.*` 配置节」写入主工程 `config.json`。实施时发现壳打包后**只有自身代码**，无法（也不应）复用主工程的分层 `ConfigLoader`；且窗口宽高位置本质是 UI 状态而非业务配置。故改为：窗口状态存 `app.getPath('userData')/window-state.json`（Win 下 `%APPDATA%\LoopAgent`），首选端口改为**只读** `~/.loop-agent/config.json` 的 `api.port`（读不到用 3000）。**主工程 `config.json` 结构零改动**，`--serve` 完全不受影响。详见任务 03 的 D3-1/D3-2。不设 `closeToTray`（D12 已定不做托盘）。 |
| **D10** | **交付安装包：NSIS 安装器，`oneClick: true` + `perMachine: false`（按用户安装，落 `%LOCALAPPDATA%\Programs\LoopAgent`，**全程不请求管理员权限**）** | 用户确认要安装包。关键约束是现场无管理员权限，故**必须走 per-user 而非 per-machine**——按 [electron-builder 官方文档](https://www.electron.build/docs/api/electron-builder.Interface.NsisOptions)，`perMachine` 默认 `false`，`oneClick` 下即为 per-user 安装，不触发 UAC。**否决 assisted（`oneClick:false`）+ `perMachine:false`**：该组合会出「安装模式选择页」，per-machine 选项在无管理员时会失败，对现场非技术用户是纯粹的误操作入口。同时**仍附带一份 portable 产物**（仅多一行 target 配置，成本近乎为零），用于「装不上时能直接跑」的兜底。 |
| **D11** | **壳的后端定位顺序：安装后 `process.resourcesPath/loop-agent-core.exe` → 便携模式同级 `loop-agent-core.exe` → 开发期 `dist-sea/loop-agent.exe` → 报错指引** | **安装包改变了路径前提**：经 electron-builder 打包后，`extraResources` 落在 `resources/` 下，与 `LoopAgent.exe` **不再同级**，故不能只按「同级目录」找。用 `app.isPackaged` 分支：打包后走 `process.resourcesPath`，未打包走仓库相对路径。这样开发期不必先跑 `build:sea` 也能调试 `--serve` 链路。找不到后端时给出**明确可操作**的提示，不是静默白屏。 |
| **D12** | **托盘图标不做，关闭即退出** | 托盘会引入「关了窗口还在跑」的新困惑，与「关掉黑窗口就停」的旧痛点同源。省掉托盘还需注意的 Windows 原生能力问题（Node 侧建托盘需原生模块，与零依赖约束冲突）。列演进项。 |

## 六、实测取证结论（本机，与目标现场同形态）

方案制定中对三处关键假设做了实测，其中**两处推翻了初始设想**，已回写上述决策：

| 假设 | 实测 | 结论 |
|---|---|---|
| `--port 0` 兜底随机端口 | `parsePort` 要求 `1..65535`，`0` 被静默丢弃 → 回落 3000 | **证伪**，改为壳探测端口（D3） |
| 父进程 `kill('SIGINT')` 能触发优雅关停 | 子进程 handler 未执行（`handler-ran=false`），进程被直接杀 | **证伪**，须新增关停端点（D7） |
| SEA 启动耗时 | spawn → `/health` 200 约 **2.5s** | 成立，60s 超时充裕（D4） |

其他环境事实：`dist-sea/loop-agent.exe` 102.2MB、`webui/dist` 9.58MB/128 文件、WebView2 运行时 157.0.4341.46 已装、Edge 存在。

## 八、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Electron 体积大（约 180–260MB） | 分发体积 | 接受；后端 exe 复用，不做两份；必要时 P2 评估 asar + 裁剪 locale |
| 杀软/EDR 对未签名 exe 拦截 | 现场双击无反应 | 明确「首次可能需加入信任」；预留代码签名演进项 |
| 后端启动慢（MCP 后台监测、记忆初始化） | 用户以为没反应 | `/health` 轮询 + 加载页显示阶段文案；实测当前 SEA 启动日志可作阶段来源 |
| 现场 Edge 被策略禁用 | 路线 A 不受影响 | **这正是选 A 的理由**；壳不依赖系统浏览器 |
| 开发期未构建 SEA 就启动壳 | 找不到后端 | D11 的定位顺序 + 明确提示 |
| 关窗时 Dreaming 被中断 | 记忆丢失 | **高风险，已由 D7 正面解决**：Windows 强杀不会触发 handler，必须新增 `POST /admin/shutdown`；仅靠信号是本方案最大的隐藏坑（已实测证伪） |
| **per-user 安装在「标准用户」账户下卸载可能失败** | 现场无法卸载/卸载不干净 | **检索到的已知坑**：electron-builder [#3430](https://github.com/electron-userland/electron-builder/issues/3430) 记录非管理员账户下卸载会索要管理员凭据但删不掉文件。应对：P1 阶段在**非管理员账户**上真机验证安装→卸载全流程；若复现，改用 `perMachine:false` + 自定义 NSIS 卸载脚本（`SetShellVarContext current`） |
| 首次构建需联网下载 Electron 二进制（约 100MB+） | 构建机离线时 `build:desktop` 失败 | P0 阶段先在构建机跑通一次并缓存，文档写明网络前提；失败时报错指引而非静默 |
| 安装包未代码签名 → SmartScreen「未知发布者」 | 现场用户不敢装 | 文档写明「更多信息 → 仍要运行」；签名需证书与费用，列演进项（与 D1 体积接受同属交付侧取舍） |

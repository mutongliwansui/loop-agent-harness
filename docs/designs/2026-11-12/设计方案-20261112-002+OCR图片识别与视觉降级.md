## 一、背景与目标

### 1.1 问题

当前项目所有「看图」能力都绑在视觉大模型上：

| 场景 | 现状 | 无视觉模型时 |
| --- | --- | --- |
| 用户上传截图提问 | `analyzeImage` → `llm.chatVision` | 报错「视觉功能未启用，请先 /config set vision.enabled true 并配置 vision.model」 |
| `fileRead` 读扫描件 PDF | 抛 `DocumentExtractError('scanned')`，提示「可用 analyzeImage 识别图片」 | 提示指向一条走不通的路 |
| `fileRead` 读 docx/pptx/xlsx | `word-extractor` 只出正文文本，**内嵌图片完全不被提取** | 图片里的文字（很多制度文件、扫描件、截图贴进 Word）永久丢失 |

现场环境（内网、离线、只有纯文本模型）恰恰是最需要读扫描件的场景，当前是硬缺口。

### 1.2 现状梳理

| 所需能力 | 框架现状 | 结论 |
| --- | --- | --- |
| 视觉调用入口 | `src/tools/vision/tools.ts` 的 `runVision()`，`vision.enabled` 为总开关，目标三元组空值回退主模型 | 降级注入点明确，集中在一处 |
| 视觉底层调用 | `src/llm/client.ts` → `chatVision()`，异常原样抛出 | 可作为降级判定边界 |
| 图片解析 | `src/tools/vision/image.ts` 的 `resolveImage()`：URL / dataURI / 本地路径三来源 + 大小/格式校验 | OCR 侧可复用同一定义（MIME 表单一来源） |
| 文档识别与提取 | `src/documents/detect.ts` + `extract.ts`：按 kind 分发到 word/pdf/xlsx/pptx/rtf/odt | 新增「文档内图片」子管线挂在这里 |
| 零依赖 zip 解析 | `src/skill/zip.ts`（`readZipEntries`），已被 `documents/zip-text.ts` 复用，带条目数/解压总量/ZIP64/加密上限 | docx/pptx/xlsx 取 `*/media/*` 无需新依赖 |
| 扫描件判定 | `src/documents/pdf.ts` 已产出 `code='scanned'`，并已有 `pdftotext` 兜底范式（`documents/external.ts`：探测缓存 + 静默回退 + 超时 + 输出上限） | 「外部工具可选」的既有范式可直接套用给 OCR 引擎 |
| 结果治理 | `fileRead` 已有行号 / `maxBytes` / 2000 行截断 / 溢出落临时文件 | OCR 文本并入同一条管线即可，不新造治理 |

### 1.3 本次实测验证（本机 Windows 11 家庭版，非管理员）

为避免方案落空，设计前先做了可行性探测：

| 探测项 | 结果 |
| --- | --- |
| `tesseract` CLI | 未安装 |
| `pdftoppm` / `mutool` / `gs` / `magick` | 均未安装 |
| Python OCR 库（paddleocr / rapidocr / pytesseract） | 未安装 |
| **Windows 原生 OCR（`Windows.Media.Ocr`）** | **可用**，`AvailableRecognizerLanguages` = `zh-Hans-CN`（简体中文） |
| 端到端：扫描版 PDF → 渲染 PNG → Windows OCR | **成功**，正文中文基本可读 |

实测暴露一个**必须处理的坑**：Windows OCR 对 CJK 按「单字 = 一个 word」切分，输出 「信 息 系 统 部 署 方 案」，行内每个字之间都被插入空格；同时中英混排时英文单词内部空格又会丢失。已检索确认这是已知问题（Text-Grab issue #191、tesseract issue #991 同类现象），业界做法是「CJK 字符之间的空格手动合并，CJK 与 ASCII 交界保留一个空格」。另外实测 `苏智问答系统 V1.0` 被识成 `苏智问答系统 0`，属 OCR 精度固有损耗，需在结果中如实标注而非假装准确。

> **此段已被 1.3.2 修正**：「每个字之间都插空格」只在**部分机器**成立。内网 Win10 19044 实测汉字之间基本无空格，故 D4 追加「后处理必须幂等」的硬约束。

**代价（实测确认，不可回避）**：

1. 平台包内含 2 个 native addon（`light_ocr_node.node` 3.71MB、`pdfium.node` 0.39MB）与 5 个相邻 DLL（`onnxruntime.dll` 13.55MB、`pdfium.dll` 6.88MB、`dxcompiler.dll` 17.15MB 等）+ 8MB 字体，**必须保持相对目录结构**。Node 官方明确 native addon 不能从 SEA 虚拟文件系统加载——这与项目现有 SEA 单文件分发直接冲突（见 D9）。
2. 要求 **Node ≥ 22**，而项目 `package.json` 声明 `engines.node >= 20.10`，采用即需上调下限。
3. 新增生产依赖（项目当前 dependencies 仅 6 个，均轻量）。

### 1.3.2 内网真机实测：WinRT OCR 在目标现场可用（2026-11-12 用户验证）

用户在内网目标机用探测脚本 `winrt-ocr-probe.ps1` 实测，**结论：完全可用**。

| 项 | 实测值 |
| --- | --- |
| 系统 | **Windows 10 企业版 G 神州网信政府版（build 19044）** |
| PowerShell | 5.1.19041.6328，Desktop，64 位进程 |
| WinRT 类型加载 | OcrEngine / Language / StorageFile / BitmapDecoder **全部 OK** |
| 识别器语言 | `count = 1` → **`zh-Hans-CN`（中文(中华人民共和国)）存在** |
| 引擎创建 | `TryCreateFromLanguage('zh-Hans-CN')` **成功**，`MaxImageDimension = 10000` |
| 端到端 OCR | **114ms，关键词 4/4 命中** |
| 退出码 | **0（USABLE）** |

两点重要结论：

1. **WinRT OCR 不依赖 Windows 11**。此前只在 Win11 家庭版验证过，这次证明 Windows 10 19044 政府版（内网典型系统）同样可用，且中文语言包已随系统就位、无需额外安装。D1 的 Windows 路径在真实目标环境**已验证成立**。
2. **CJK 空格缺陷是机器相关的，不是普遍行为**。同一份测试图：
   - 本机 Win11 26300：`信 息 系 统 部 署 方 案`（71 字符，**12 个 CJK-CJK 空格对**）
   - 内网 Win10 19044：`信息系统部署方案评审意见`（**汉字之间基本无空格**）

   这修正了 1.3 中「Windows OCR 对 CJK 一律按单字切分」的表述——实际应描述为「**部分版本/部分场景**会插入单字空格」。由此对 D4 追加一条硬约束：**后处理必须幂等**，在已经紧凑输出（cjkPairs=0）的机器上不得产生任何改动。合并 CJK 间空格的算法天然满足幂等性，故该结论支持而非否定 D4。

   同时注意内网机器在数字与中文交界处仍有个别空格（如 `2024 年 9 月 12 日`），这类交界本就应该保留 1 个空格，符合 D4 规则。

   **一处如实记录的待确认点**：本次内网运行的是旧版脚本，其 CJK 检测只输出布尔值 `PRESENT`；但截图肉眼观察汉字之间并无空格。两者可能并不矛盾——只要文本中存在**一处** CJK-CJK 空格（例如 `日 评审` 之间）就会置为 PRESENT，而实拍照片上单个空格极难辨认。为消除歧义，探测脚本已改为**输出 CJK 空格对计数 + 首个样例**（见 §九 Q9），建议在内网重跑一次拿到确切数字后再据此收紧 D4 的规则。

3. **精度对比参考**：内网机器把 `V1.0` 识成 `VI · 0`、`2024 年 9 月 12 日` 正确；本机把 `12` 拆成 `1 2`、`V1.0` 识成 `VI · 0`。两台机器都对版本号有损耗，而 1.3.1 中 light-ocr 能正确输出 `V1.0`——这为 D9 的精度差异提供了第二组独立证据。

### 1.4 目标

1. **新增内置 OCR 工具**（暂名 `ocrImage`）：图片 → 纯文本，全程本地、零 LLM 依赖。
2. **`analyzeImage` 容错降级**：视觉不可用（未启用 / 调用失败）时自动改走 OCR，结果明确标注「本地 OCR 降级」与能力边界（只能给文本，回答不了颜色/布局这类问题）。
3. **`fileRead` 文档内图片 OCR**：docx/pptx/xlsx 解 zip 取内嵌图片、PDF 扫描页光栅化后 OCR，文本以带标注的块并入既有行号/截断/落盘管线。
4. **零新增 npm 依赖**，保持 SEA 单文件可打包；本地 OCR 不向任何外部服务发送图片。
5. **平台范围（2026-11-12 定稿）**：以 **Windows `Windows.Media.Ocr`（WinRT）为唯一正式引擎**——已在本机 Win11 与内网 Win10 19044 双环境验证可用。macOS / Linux 的引擎实现（tesseract CLI、macOS Vision framework、`light-ocr` 等）**统一转为演进项**，不在本需求范围内落地（见 §4.9）。

### 1.5 非目标

- **不做 macOS / Linux 的 OCR 引擎实现**（2026-11-12 定稿，转演进项）。这两个平台本需求内「无 OCR 能力」，行为等同当前版本。
- 不做版面分析（表格结构还原、图文区块切分、阅读顺序重排）。
- 不做手写体识别、公式识别、印章/签名识别。
- 不替换 `analyzeImage`：视觉大模型仍是「理解图片」的首选，OCR 只是「读文字」的兜底。
- 不改 `vision.*` 现有配置语义与缓存机制。
- 不做 WebUI 图片 OCR 预览页、不做 OCR 结果的可视化对照。
- 不在本次引入对 PDF 图片内容（XObject）的纯 JS 解码（JPEG2000/JBIG2/CCITT 等），仍走外部光栅化。

### 1.6 设计约束

- 零依赖优先：**只用系统自带能力**，不引入任何 OCR npm 包。
- **平台策略**：Windows 为一等公民且已双环境验证；非 Windows 平台**不报错、不注册工具、不产生新错误路径**，仅记录一条可观测日志说明「该平台 OCR 能力尚未实现（演进项）」。
- SEA 单文件：随包脚本必须可内嵌读取（`node:sea` 的 `getAsset`）或落地到临时目录，不得依赖 `__dirname` 旁的散文件。
- **前缀缓存**：工具列表是每轮 tools 参数的一部分，增减工具会破一次前缀缓存（项目历次决策都为此把 `vision.enabled` 默认设为 `false`）。OCR 工具的默认开关必须显式决策。
- 外部子进程：参数数组传参、不经过 shell、固定超时、输出上限（沿用 `documents/external.ts` 范式）。

## 二、总体设计

### 2.1 核心思路

把「看图」拆成两条独立管道，同层可互换：

```
                        ┌──────────────────────────────┐
   图片/文档内图片  ──►  │ 图片源解析 resolveImage()     │  （复用 vision/image.ts）
                        └──────────────┬───────────────┘
                                       │
                    ┌──────────────────┴───────────────────┐
                    ▼                                      ▼
        ┌───────────────────────┐              ┌────────────────────────┐
        │ 视觉管道（理解型）      │              │ OCR 管道（抽取型）       │
        │ analyzeImage → LLM    │              │ ocrImage → 本地引擎      │
        │ 问答/描述/字段抽取      │   D2 降级    │ 纯文本抽取              │
        └───────────┬───────────┘ ───────────► └───────────┬────────────┘
                    │        视觉不可用时切换               │
                    └──────────────────┬───────────────────┘
                                       ▼
                              ┌─────────────────┐
                              │ D4 CJK 后处理    │
                              └────────┬────────┘
                                       ▼
                        工具结果（文本 + 元信息 + 边界标注）
                                       ▲
                                       │ D3
                        ┌──────────────┴───────────────┐
                        │ fileRead 文档管线             │
                        │ 文本层 → 内嵌图片 OCR 追加块   │
                        └──────────────────────────────┘
```

### 2.2 引擎能力矩阵（D1 定稿：Windows 唯一正式引擎）

| 平台 | 本需求 | 引擎 | 现场缺失时 |
| --- | --- | --- | --- |
| **Windows** | **落地** | `Windows.Media.Ocr`（WinRT，经 `powershell.exe` 调用，**本机 Win11 + 内网 Win10 双环境实测可用**） | 提示「安装对应语言的 Windows OCR 语言包」（附 `Add-WindowsCapability` 命令）；若配置了 HTTP 端点则可用 |
| 任意（可选） | **落地（P2）** | 用户自配 HTTP OCR 端点（内网 PaddleOCR / Umi-OCR / 云 OCR） | 未配置则不启用该档 |
| macOS | **演进项** | —（预留 macOS Vision framework / tesseract CLI） | 不注册工具，仅日志说明「该平台 OCR 未实现」 |
| Linux | **演进项** | —（预留 tesseract CLI） | 同上 |

引擎选择顺序由配置 `ocr.enginePriority` 决定；本需求默认 `['winrt-ocr']`，配置了 HTTP 端点时可加 `'http'`。**探测结果进程内缓存一次**（同 `pdftotextAvailable()`），避免每次调用都起子进程试探。

> 非 Windows 平台上 `sysOcrSupported=false`，`ocrImage` 不注册（D7），三条链路均退回当前行为，不产生新错误路径。

### 2.3 输出语义

所有 OCR 结果统一带**显式来源标注**，避免模型误以为拿到了完整准确信息：

- 工具结果首行：`[OCR 引擎: winrt-ocr | 语言: zh-Hans-CN | 耗时: 1.2s]`
- 降级路径追加：`[视觉不可用（原因摘要），已降级为本地 OCR；OCR 只提供文字，无法回答颜色/布局/图标类问题]`
- 文档内图片块：`[图片 3（word/media/image2.png）：OCR 文本]` … 块尾 `[/图片 3]`
- 精度提示：当引擎不返回置信度时不臆造；返回时按「低置信度行占比」给一句提示。

## 三、关键设计决策

### D1 引擎选型：正式采用 Windows 原生 OCR（WinRT）为唯一 P0 引擎，其他平台转演进项（2026-11-12 定稿）

**决策**：`ocrImage` 工具、`analyzeImage` 降级、`fileRead` 文档图片三条链路，本需求只落地 **Windows 的 `Windows.Media.Ocr`（WinRT，经 `powershell.exe` 调用）** 一个引擎；另保留一个**用户自配的可选 HTTP 端点**（内网已有 OCR 服务时用）。macOS / Linux 引擎**统一转演进项**（见 §4.9）。

**依据**：

- **双环境实测可用**：本机 Win11 家庭版 26300（§1.3）与内网 Win10 企业版 G 神州网信政府版 19044（§1.3.2）均通过，中文语言包随系统就位、**无需管理员安装**。
- **零新增依赖**：用系统能力，`dependencies` 保持 6 个不增；`.ps1` 作为 SEA asset 内嵌，单文件分发不受影响。
- **实现成本最低**：一个脚本 + 一次子进程调用，无 native addon、无模型分发包、无 Node 版本约束。
- **贴合目标现场**：客户机器就是 Win10 政府版，Windows 不是「顺带支持」而是唯一目标。

**被否决 / 降级的方案**：

| 方案 | 判定 | 理由 |
| --- | --- | --- |
| ~~`tesseract` CLI（跨平台）~~ | **转演进项** | 本机与内网均未安装；纳入会让 P0 膨胀成「三平台引擎 + 三套安装指引 + 三套错误文案」，而目标环境是 Windows |
| ~~macOS Vision framework（swift）~~ | **转演进项** | 需 Xcode CLT，非本需求目标平台 |
| ~~`tesseract.js`（纯 WASM）~~ | 不采纳 | 需下载 `chi_sim.traineddata`（数十 MB）且 SEA 需内嵌 wasm + 模型；中文精度实测最差（字段命中约 0.71） |
| ~~`@arcships/light-ocr` 全量引入（D9-B1）~~ | **转演进项** | 精度确实更好（§1.3.1），但 130MB 体积 + Node ≥22 + native addon 与 SEA 冲突，属发布形态变更，超出本需求 |
| ~~`@arcships/light-ocr` 可选依赖（D9-B2）~~ | **转演进项** | 思路可行，但需长期维护一条并行高精度路径；在 Windows 路径已验证可用时，不作为本需求范围 |
| ~~Node 直调 WinRT 原生绑定~~ | 不采纳 | 需 native addon，与 SEA 及跨平台均不兼容 |
| ~~全部依赖 HTTP OCR 服务~~ | 不采纳 | 离线现场无服务可用，等于没解决原始问题 |

**取舍代价（明确接受）**：

1. `powershell.exe` 子进程启动开销约 0.6–1.5s。可接受——OCR 本身是重操作，`fileRead` 已有 15s 文档预算。
2. **非 Windows 平台本需求内无 OCR 能力**：`ocrImage` 不注册、降级不生效、文档不出图片块，行为**等同当前版本**，不引入新错误路径。
3. **中文精度有限**：本机与内网两台机器均把 `V1.0` 识成 `VI · 0`，靠 D4 后处理 + 结果标注控制预期，不做纠错猜测。

### D9 引擎二次取舍：**已决策为「A + 可选 HTTP」**（2026-11-12 用户拍板）

1.3.1 的实测曾使 D1 从「唯一可行解」变成「两个方案各有硬伤」，此处保留完整对比以供追溯，**结论已定**：

- **采纳 A**：Windows 原生 OCR 为正式引擎，补一个可选 HTTP 端点应对内网已有 OCR 服务。
- **B1 / B2 均转演进项**（§4.9）。这不是否定 light-ocr 的精度优势，而是**当前无需为它变更发布形态**——目标现场是 Windows 且 WinRT 已验证可用，先用零依赖把链路打通；「精度升级」作为后续可选增强，届时按 B2 形态做（optionalDependency + 运行时探测），不必改 SEA。
- 决策依据较 1.3.1 时已补强：内网 Win10 实测通过（§1.3.2），A 从「开发机能用」升级为「**目标现场已验证**」。

| 维度 | A. WinRT（**采纳**） | B. `@arcships/light-ocr`（转演进项） |
| --- | --- | --- |
| 中文精度 | 中（CJK 空格需 D4 后处理，版本号/人名有损耗） | 高（置信度 0.992，无需后处理） |
| 依赖体积 | 0（系统能力） | +130MB |
| Node 下限 | 不变（≥20.10） | 需上调至 **≥22** |
| 跨平台一致性 | 仅 Windows（演进项补齐） | 好（8 平台同一模型） |
| 扫描 PDF 光栅化 | 需外部 `pdftoppm`/`mutool`/`gs`（D8） | 内建 PDFium，免外部工具 |
| SEA 单文件 | **兼容** | 不兼容，须外置依赖目录 |
| 首次延迟 | 0.6–1.5s（进程启动） | 4s（冷启动）+ 0.36s/张（热态） |
| 现场验证 | **内网 Win10 19044 已通过** | 仅开发机验证 |

> **连带作废**：原 Q8「是否接受 `engines.node` 上调至 ≥22」随 B1/B2 转演进项而**不再需要决策**，`engines.node` 维持 `>=20.10`。

### D2 降级触发：`analyzeImage` 失败即降级（fail-open），并回显失败摘要

- 判定顺序：`vision.enabled=false` → 直接 OCR；`chatVision` 抛错 → 尝试 OCR。
- **不按错误码白名单过滤**：现场环境的失败形态多样（401 无 key、404 模型名错、400 不支持图像、ETIMEDOUT、私网不通），白名单必然漏，漏掉的代价是用户完全拿不到结果。改为 fail-open，但**把原始错误摘要写进结果**，让模型与用户都能看出「这次结果来自 OCR，视觉那条为什么失败」。
- **被否决：静默降级**——用户会误以为视觉判断得出的结论，而实际只是 OCR 文本。
- **被否决：降级前先探测视觉可用性**——多一次无意义调用，且探测成功不代表本次调用不超时。

### D3 `fileRead` 文档内图片：默认**开启**，但受三重预算约束

- 覆盖范围：docx/pptx/xlsx 的 `*/media/*`（零依赖解 zip）；PDF 仅在「文本层判定为扫描件 / 指定页无文本」时对相应页做光栅化 OCR。
- 预算：`ocr.doc.maxImages`（默认 20 张/文档）、`ocr.doc.maxCharsPerImage`（默认 4000 字符）、`ocr.doc.timeBudgetMs`（默认 15000，与文档解析预算同源）。
- **被否决：默认关闭、需显式开启**——用户的原始诉求正是「readFile 时文档里有图片也能识别」，默认关闭等于没做。
- **被否决：文档图片一律 OCR 无上限**——一本 300 页扫描 PDF 会跑成分钟级并撑爆上下文。
- 位置语义：图片块插在**原文档流中的相对位置**（docx 按 `document.xml` 里的 `r:embed` 关系顺序，pptx 按幻灯片顺序），段落文本与图片块保持阅读顺序。

### D4 CJK 后处理：仅合并「CJK↔CJK」之间的空格，且**必须幂等**

- 规则：两个 CJK 字符（含中文标点 `，。；：""''（）《》`）之间的所有空格删除；CJK 与 ASCII/数字交界保留 1 个空格；连续多空格压缩为 1。
- 依据：Windows OCR **在部分版本/部分场景**把每个汉字当独立 word 输出（本机 Win11 26300 实测 12 个 CJK-CJK 空格对 + Text-Grab #191）。tesseract 存在同源问题（#991，用 `preserve_interword_spaces` 处理），但它已转演进项，本需求只需对齐 WinRT 一种行为。
- **幂等性硬约束（由 1.3.2 内网实测新增）**：内网 Win10 19044 的 OCR 输出**汉字之间基本无空格**，与本机行为显著不同。因此后处理不能假设「输入一定有单字空格」，在 cjkPairs=0 的文本上必须**逐字节输出不变**。合并 CJK 间空格的算法天然幂等，此约束主要影响实现方式：
  - 不要用「按空格 split 再按规则 join」这类会重排原始空白的写法，改用正则替换（`(?<=[\u4e00-\u9fff])[ \t]+(?=[\u4e00-\u9fff])` → `''`），并对无匹配的输入原样返回。
  - 单测必须覆盖三种输入：全角空格版（本机）、紧凑版（内网）、混合版，断言紧凑版输入输出相等。
- **被否决：统一删除所有空格**——中英混排会把 `load rate` 拼成 `loadrate`，破坏 SQL/字段名这类关键内容。
- 已知残留：繁简/形近字误识（本机与内网**两台机器**均把 `V1.0` 识成 `VI · 0`）不做纠错猜测，只在结果标注 OCR 来源。

### D5 OCR 结果缓存：进程内 LRU，key = 文件指纹 + 引擎 + 语言 + 参数

- 复用 `vision/cache.ts` 的形态（进程内、TTL、有容量上限），键加入 `fileFingerprint`（`size-mtime`）使文件变更自动失效。
- **被否决：落盘缓存**——OCR 结果无跨会话复用价值（重复读取同一文件本身罕见），且落盘涉及清理策略与隐私残留。

### D6 形态：独立工具 `ocrImage` + 内部可复用能力，二者共用同一执行管道

- 工具形态（用户明确要求）：主模型可显式「只读文字、别花钱调视觉模型」，也给出了无视觉模型环境下明确的可调用入口。
- 内部复用：`analyzeImage` 降级与 `fileRead` 文档图片都调同一个 `runOcr()`，避免三份实现漂移。
- **被否决：只做内部能力、不暴露工具**——无视觉模型环境下模型没有显式入口，只能靠 fileRead 隐式触发。

### D7 工具注册与默认开关：`ocr.enabled` 默认 `true`，但**仅当探测到可用引擎时才注册**

- 理由：探测不到引擎时注册一个必然报错的工具，只会诱导模型反复误调用。
- 平台条件：非 Windows 平台 `sysOcrSupported=false`，等价于「探测不到引擎」→ 不注册，仅记一条演进项日志（D1 定稿）。
- 前缀缓存影响：引擎可用环境下 tools 列表会多一个工具，属**一次性**前缀失效（与当年新增 `analyzeImage` 同等代价），之后稳定。
- **被否决：默认 `false`**——与「现场没视觉模型时开箱可用」的目标直接冲突；用户要为此多改一次配置才能用上，违背痛点场景。
- 若用户更在意缓存，可改 `false`（见 §九 Q2）。

### D8 PDF 光栅化：外部命令模板化探测，缺失时给可操作指引

- 探测链：`pdftoppm`（poppler）→ `mutool draw`（mupdf）→ `gs`（ghostscript）→ 自定义 `ocr.pdfRasterizer` 命令模板。
  （`python -m pypdfium2` 未落地：多一条 Python 环境探测链，收益不抵复杂度，列演进项。）
- **本机实测三者皆无**，说明「有 OCR 引擎 ≠ 有光栅化工具」是真实组合，必须把两者分开探测、分别提示。
- **实施约束（已落地）**：150 DPI 渲染；单次最多 5 页（`MAX_RASTER_PAGES`，防扫描件整本打满磁盘）；
  单页 PNG 上限 12MB、单页超时 15s；临时目录每次 `mkdtemp`、无论成败整目录删除；
  自定义模板只做占位符替换（`{input}/{page}/{page0}/{output}`）+ 简单分词，不走 shell。
- 缺失时的提示要具体：`PDF 扫描页需要光栅化工具：推荐安装 poppler（pdftoppm）。当前已探测到 OCR 引擎 winrt-ocr，仅缺 PDF 渲染能力。`
- **被否决：纯 JS 渲染 PDF 页**——需字体/渲染/图像编解码全套，与现有自研最小解析器的定位（只提文本）差距过大。

核心接口：

```ts
export interface OcrEngine {
  readonly id: string;                 // 'winrt-ocr' | 'http'（'tesseract' 为演进项预留）
  readonly langs: string[];            // 支持语言标签
  isAvailable(): Promise<boolean>;
  recognize(image: Buffer, opts: OcrOptions): Promise<OcrResult>;
}

export interface OcrOptions {
  lang?: string;          // 默认 ocr.lang（'auto' 取引擎首选）
  timeoutMs?: number;
  maxChars?: number;
}

export interface OcrResult {
  text: string;
  engine: string;
  lang: string;
  elapsedMs: number;
  /** 引擎不提供则为 undefined，不臆造 */
  confidence?: number;
  warnings: string[];
}

/** 供 analyzeImage 降级、ocrImage 工具、fileRead 文档图片共用的唯一入口 */
export async function runOcr(image: ResolvedImage | Buffer, opts?: OcrOptions): Promise<OcrResult>;
```

### 4.3 `ocrImage` 工具

```ts
name: 'ocrImage'
description: '用本地 OCR 从图片提取文字（不调用大模型、不外发图片）。需要理解画面内容（颜色、布局、图标含义）时用 analyzeImage。'
parameters:
  image:    string   必填，本地路径（URL/dataURI 本版仅 dataURI 支持，见演进项）
  lang:     string   可选，语言标签；省略用配置默认
  maxChars: number   可选，结果字符上限
timeoutMs: 由 ocr.timeoutMs + 余量决定（注册时取 max(30000, ocr.timeoutMs + 10000)）
```

错误分类（回填给主模型，便于自纠）：`engine_missing`（含安装指引）、`lang_unsupported`、`image_too_large`、`unsupported_format`、`timeout`、`empty`（引擎成功但识别为空）。

### 4.4 `analyzeImage` 降级接入

改造 `src/tools/vision/tools.ts` 的 `runVision()`：

```
vision.enabled=false            → 若 ocr.enabled && engine 可用 → runOcr（标注降级）
chatVision 抛错                 → 记录错误摘要 → 若 fallbackFromVision → runOcr（标注降级 + 错误摘要）
OCR 也失败                      → 抛原始视觉错误 + OCR 失败原因（两条信息都保留）
```

要点：
- 降级结果**只对 `describe`/`ask` 有意义**，`extract`（要 JSON）不降级——OCR 无法产出结构化字段，降级会给出误导性的「非法 JSON」。此时直接报错并提示改用 `ocrImage` 后自行解析。
- 缓存 key 增加通道标识（`channel: 'vision' | 'ocr'`），防止两条路径的结果互相命中。
- `visionStats` 增补降级计数，便于观测现场环境实际走的是哪条路。

### 4.5 `fileRead` 文档图片接入

在 `src/documents/` 侧扩展提取结果：

```ts
export interface ExtractResult {
  // …既有字段
  images?: DocumentImage[];   // 按文档流顺序
}

export interface DocumentImage {
  name: string;                        // 'word/media/image2.png' 或 'pdf-page-3'
  data: Buffer;                        // 原始字节（Office 场景不落盘）
  index: number;                       // 1-based，按文档流顺序
  source: 'embedded' | 'pdf-page';     // 区分 OOXML 内嵌图与 PDF 光栅化页
  page?: number;                       // PDF 场景为页码
}
```

`fileRead.readDocument()` 在文本行管线之外，把每张图 OCR 结果作为独立块追加到提取文本尾部
（块头 `=== 文档内图片 OCR ===` 单独一行，块结构如下）：

```
[图片 2（word/media/image2.png）：OCR 文本]
…识别文本…
[/图片 2]
```

块头不带引擎与耗时：块文本要长期留在上下文里，逐块写 `engine/elapsedMs` 会随机器与
缓存状态抖动，且信息对模型无决策价值；引擎与耗时只出现在 `ocrImage` 工具的单次结果中。

超预算处理：超 `maxImages` 的图片逐张给一行 `[图片 21（word/media/image21.png）：未 OCR（超过单文档 20 张上限）]`，
既不静默丢弃，也保留了可直接喂给 `ocrImage` 的条目名；同时汇总一条
`N 张图片超过单文档 20 张上限未 OCR（可用 ocr.doc.maxImages 调整）` 进 warnings。
超时间预算为 `[图片 22（…）：未 OCR（超过 15s 时间预算）]`；单张失败为
`[图片 23（…）：OCR 失败（timeout）：…]`；引擎整体不可用（`engine_missing`/`platform_unsupported`）
时**整块不产出**，只在 warnings 里说一句「文档内图片 OCR 不可用，已跳过 N 张」，保证非 Windows 零影响。

PDF 扫描件路径：现有 `scanned` 错误不再直接抛给用户，而是「若有光栅化 + OCR 引擎 → 对所选页 OCR 后返回文本（标注来源）；若缺任何一个 → 保留原错误并补一句缺的是什么」。

### 4.7 资源与安全

- 子进程：`spawn` 参数数组、不走 shell、固定超时、stdout 上限（复用 `external.ts` 的 `MAX_OUTPUT_BYTES` 形态）。
- 临时文件：光栅化 PNG 落 `os.tmpdir()` 下的专属目录，`finally` 删除；单页 PNG 上限 50MB。
- 隐私：本地引擎不外发；HTTP 端点仅在用户显式配置 `ocr.http.endpoint` 时启用，且默认不带任何主模型 apiKey。
- SEA：WinRT 的 `.ps1` 与可能的 node 脚本作为 SEA asset 内嵌（`node:sea` 的 `getAsset`），运行时写临时文件执行；非 SEA 场景从源码目录读。

### 4.8 对既有行为的影响

| 既有行为 | 影响 |
| --- | --- |
| 纯文本文件读取 | 零影响（不进文档分支） |
| 文档读取（有文本层） | 仅多出图片块；无图片时输出与现在**逐字节一致** |

## 一、背景

`ocrImage` 首版（20261112-002）打通了「离线取字」这条链路，但只把 OCR 当成**纯文本提取器**，丢掉了 WinRT 已经给出的版面信息，导致「能取到字」却「读不出结构」。

用户上传一张资源管理器文件列表截图（1293×1164，21 行文件、每行「名称 + 修改日期」两列）请 OCR 取字，得到的结果是 **21 个文件名连成一坨、21 个日期连成另一坨，名称与日期互不对应**，无法据此回答「哪个文件是什么时候改的」。为辨认误识的字，用户还不得不在 `temp/` 手写放大与裁剪两个临时 PowerShell 脚本 —— 说明能力缺口已外溢成用户手工成本。

## 二、问题取证（2026-11-12 实测）

用探针脚本直连 `Windows.Media.Ocr`（脚本见仓库外 `temp/dump-words.ps1`，验证后已清理），对同一张图取全部字段：

| 观测项 | 实测值 | 说明 |
| --- | --- | --- |
| `result.Lines.Count` | **45** | 引擎其实按行切好了 |
| `result.Text` 长度 | 1261 | 却是一整行 |
| `result.Text` 内控制字符数 | **0** | 换行/回车**一个都没有** |
| `result.Text` 内空格数 | 大量 | WinRT 用**空格**拼行 |
| 图片尺寸 | 1293×1164 | 在 `MaxImageDimension` 之内 |

即 **信息没丢，是没往下传**。由此推出四个缺陷：

1. **`engine-winrt.ts` 只落盘 `result.Text`**（`engine-winrt.ts:205`）。`result.Lines` 拿到了却弃用，`LINES` 虽然经 stdout 回传（`:212`），但 `OcrResult` 里没有这个字段，白取。
2. **`postprocess.ts` 三条规则全部空转**。`mergeCjkSpaces` 不受影响，但 `collapseInnerSpaces`（`:67`）与 `normalizeOcrLines`（`:43`）都以 `\n` 为切分前提，单行输入下「行首缩进保留」「空行收敛」永不触发。更糟的是 `collapseInnerSpaces` 会把**单元格之间的多空格压缩成一个**，连最后的列分隔线索也一并抹掉。
3. **`engine-winrt.ts:206` 的 `Replace(char13,'')` 是死代码**：`Text` 里既无 `\r` 也无 `\n`（实测控制字符数为 0），这行防的是「PowerShell 回传 CRLF」，但实际数据源根本不换行。
4. **文档与实现不符**：`docs/readme/{zh,en}/built-in-tools.md` 已写明 `ocrImage`「保持原始阅读顺序与**换行**」。文档写的是目标态，实现停在了文本态。

### 2.1 关键补充实验：分行不够，需要视觉行重建

把 `OcrResult.Lines` 按行输出（方案 A），以及把全部 `OcrWord.BoundingRect` 按 **y 中心聚类**重建视觉行（方案 B），同一张图对比：

| 方案 | 行数 | 首行输出 | 名称/日期是否同行 |
| --- | --- | --- | --- |
| A：按 `Lines` 分行 | 45 | `小 智 前 后 台 一 问 数 配 方 FAQ 一 20261111 .zip` | ❌ 名称一坨、日期一坨 |
| B：按 y 聚类重建 | **23** | `winrt-ocr-probe.psl \| 2026/11/12 17:19` | ✅ 21 条数据全部同行对齐 |

**结论：`Lines` 的分行粒度与「人眼看到的行」不一致**——名称与日期 y 基线相同但被引擎切成不同 `Line`（中间空白大）。因此：

- **只做「按 Lines 分行」= 把一坨变成 45 行，仍读不出表格**；
- **做 y 聚类（视觉行重建）= 23 行，名称与日期自然同行**，这才是用户要的结果，且**不需要列聚类、不需要猜表头**，风险很低。

这一条直接改变了设计的优先级：**y 聚类是 P0，列聚类（markdown 表格）才是 P1**。

### 2.2 放大收益非单调

手工实验：`调用方案.md` 原图被识为 `调厍方案.md`，**2× 放大后修复**；`电网业务语义提取方案` 原图正确，**3× 放大后反而劣化为 `语必是取`**。说明放大不是「越大越好」，必须**整数倍 + 高质量插值**，且作为**显式参数**而非默认行为。

## 三、总体设计

### 3.1 分层

```
ocrImage(layout, scale, crop)
   └─ runOcrOnSource ─→ runOcr
        ├─ ocrCache（结构化缓存：lines+words）
        └─ engine.recognize
             └─ engine-winrt（PowerShell）
                  ├─ BitmapTransform：scale/crop（新增，预处理）
                  ├─ RecognizeAsync
                  └─ 落盘 out.json（lines+words+bbox）+ out.txt（兼容纯文本）
        ↓
   layout 渲染层（新增 src/ocr/layout.ts）
        ├─ text  ：y 聚类视觉行 → 每行词按 x 排序拼接（P0）
        ├─ table ：text + x 投影列聚类 → markdown 表格（P1）
        └─ words ：词级坐标 TSV（P1）
        ↓
   postProcessOcrText（既有三规则，现在真正生效）
```

**职责切分原则**：引擎只**产出结构**（lines/words/bbox），不决定排版；`layout.ts` 只**消费结构**（纯函数，零 IO，可单测）；`postprocess.ts` 保持在最后一律做 CJK 合并与空白收敛，两条路径共用，避免规则分叉。

### 3.2 向后兼容

- `OcrResult.text` 语义不变（仍是最终可回填文本），新增可选 `lines`/`blocks` 字段；
- `analyzeImage` 降级、`fileRead` 文档图片两条链路**调用签名零改动**，自动享受「分行」收益；
- `out.txt` 继续写（纯文本，按视觉行分行），`out.json` 新增；Node 侧读 json 失败时回落 txt；
- http 引擎无 bbox，`layout!=='text'` 时降级为 text 并追加告警，不报错。

## 四、关键设计决策（D 决策点，需拍板）

> 每项给「推荐 + 备选 + 理由」，可分项否决。

### D1 行结构的传输方式：JSON 文件回传（推荐）

**推荐**：新增 `out.json`（UTF-8 无 BOM），结构 `{width,height,lines:[{text,words:[{t,x,y,w,h}]}]}`；`out.txt` 保留纯文本。脚本内**手写 JSON 拼接 + `Escape-Json` 函数**，不用 `ConvertTo-Json`。

**备选**：① TSV（`lineIdx\tx\ty\tw\th\ttext` 逐词一行）；② 只改 `out.txt` 用 `\n` 分行，不传 bbox。

**理由**：
- 既有约束「中文只走 OutPath 文件回传，stdout 只放 ASCII KEY=VALUE」（`engine-winrt.ts:10-11`），结构必须落文件，不能走 stdout；
- 不用 `ConvertTo-Json`：PS 5.1 该 cmdlet 对**单元素数组会退化为标量**（`Words` 只有一个词时 `words` 变对象而非数组），是隐蔽坑；手写拼接 + `Escape-Json`（转义 `\ " \b \f \n \r \t` 与 U+0000–U+001F）可控且可单测；
- 备选 ②TSV 更简单，但 `lineIdx` 冗余、无法表达嵌套、将来加 confidence 要改协议；备选 ③ 只能分行、做不了 table。

**风险与兜底**：`out.json` 解析失败 → 回落 `out.txt` + 告警「结构化数据解析失败，已退化为纯文本」，绝不因解析失败丢结果。

### D2 `layout` 默认值：`text`（推荐）

**推荐**：默认 `text`，即「y 聚类视觉行 + 后处理」，**不自动猜表格**；表格场景由模型显式传 `layout=table`。

**理由**：`text` 已解决用户核心痛点（名称与日期同行，实测 23 行）；`table` 的列聚类在正文段落、多栏排版上有误判风险（把一句话切成两列），**自动触发不可预期**。工具描述里一句话点明「多列/表格图用 table」，让模型自己选，比隐式猜更可靠。

**备选**：`auto`——行数 ≥ 8 且检测到 ≥2 条稳定空白带时自动转表格。可作 P2 演进，不进首版。

### D3 视觉行重建的聚类参数：相对中位字高（推荐）

**推荐**：容差 `tolY = max(3, median(word.h) × 0.6)`；行中心用**成员词的加权均值**并迭代收敛（原型实测 23 行、名称日期全部对齐）。

**理由**：绝对像素容差在不同 DPI / 字号截图间不可迁移（1200px 与 3000px 宽的同一界面差异巨大）；用中位字高做基准自动缩放。`max(3, …)` 防止超小图（字高 4px）退化为 0 容差。

**边界**：上下标、混排大标题可能被并入同一行，属可接受误差（拼接后仍是正确阅读顺序）。

### D3b 行内词拼接的分隔策略：三档（紧邻 / 单空格 / 列分隔）（推荐）

**推荐**：视觉行内相邻两词按横向空隙 `gap` 分三档拼接：
- `gap > 1.5×medH` → ` | `（列分隔，便于人眼与模型辨认表格列）；
- `gap < 0.4×medH` → 直接相连**不插空格**（视为同一 token 被引擎切开）；
- 其余 → 单空格。
两侧均为拉丁字母时即使小间隙也保留空格（避免 `hello world` 粘连）。

**理由**：WinRT 会把 `2026/11/12 17:19` 切成 `2026` `/` `1` `1` `/` `1` `2` `17` `：` `1` `9` 十余个独立词。若只用「单空格 / ` | `」两档，输出是 `2026 / 1 1 / 1 2 17 ： 1 9`，日期彻底不可读——这正是用户上传截图后「读不出日期」的直接成因。**真机实测（medH=16）**：日期内部字距 1–6px，日期↔时间交界最小 7px（多为 8px）。取 `0.4×medH≈6.4` 恰落在 6 与 7 之间：日期内部合并成 `2026/11/12`，日期与时间之间保留空格（`2026/11/4 15:19` 不会误成 `2026/11/415：19`）。比例取 0.45 会把 7px 交界也吞掉，取 0.3 又会让 6px 的 `11` 重新被拆开。

**备选**：固定像素阈值（不可跨 DPI 迁移，否决）；后处理正则修补日期（脆弱、易误伤正文，否决）。

### D4 列聚类（`layout=table`）：x 投影空白带（推荐）

**推荐**：把视觉行内所有词投影到 x 轴，取「所有词都未覆盖」的空白带作为列分隔；阈值 `median(word.h) × 1.5`，并过滤宽度小于该阈值的列（合并碎片列）。

**备选**：词起点一维聚类（原型用的方法）。

**理由**：原型实测起点聚类切出 **7 个碎簇**（`2026`/`/`/`11`/`/`/`12` 各成一簇），因为日期内部也有空格；**投影法看的是"整列空白"**，日期内部的空格在别的行被日期数字覆盖，因此不会成为列边界——这正是表格识别的正确判据（该方法是 OCR 版面分析的通行做法）。

**输出格式**：markdown 表格（`| 名称 | 日期 |`），首行为表头（取第一视觉行）；用户在 WebUI 与对话里都能直接读懂。列数 >1 且行数 ≥3 才输出表格，否则回落 `text`。

### D5 `layout=words` 输出格式：TSV（推荐）

**推荐**：`x\ty\tw\th\ttext` 逐词一行，坐标为原图像素整数。

**理由**：该模式是给模型做**精确几何推理**（如「第 3 行第 2 列是什么」）用的，TSV 最省 token；JSON 同信息要多 3–4 倍字符。坐标不放归一化，避免模型做除法。

### D6 预处理参数：`scale` 与 `crop`（推荐）

**推荐**：
- `scale`：整数 **1–4**，默认 1。在脚本内用 `BitmapTransform`（`ScaledWidth/Height` + `InterpolationMode=HighQualityCubic`）做，**不引入 Node 图像库**；
- `crop`：`[x, y, w, h]` 原图像素，默认整图；同样走 `BitmapBounds`；
- 放大后若超过 `MaxImageDimension` → 明确报 `image_too_large` 并提示「放大后超限，请降 scale 或 crop」。

**理由**：用户已在手工做这两件事（`temp/` 两个脚本）；放进参数后模型可自行重试小字区域。整数倍避免插值伪影，`HighQualityCubic` 优于默认 `Linear`（放大场景）。

**备选**：只给 `scale` 不给 `crop`（少 1 个参数、省预算）。可裁剪掉，但裁小区域放大是辨认小字的**最有效组合**，建议保留。

### D7 `maxChars` 语义修正（推荐）

**推荐**：`ocr.maxChars` 改为**默认值**而非硬顶；工具入参可上调至硬上限 `200000`；截断改为**按行截断**（不把一行切成两半）并在结果里标注「已截断 N 行」。

**理由**：现实现 `Math.min(入参, cfg.maxChars)`（`ocrImage.ts:54`）导致「只能缩小不能放大」，与参数描述「本次结果字符上限」不符；`text.slice(0, maxChars)`（`:63`）会把一行切一半，模型看到残句。

### D8 耗时口径修正（推荐）

**推荐**：脚本内 `Stopwatch` 分三段（`decode` / `recognize` / `transform`），Node 侧另记端到端 `Date.now()` 差值；结果头显示 `耗时: 1.1s（识别 0.3s + 进程与解码 0.8s）`，缓存命中时显示 `耗时: 0s（缓存）`。

**理由**：现 `elapsedMs` 只含 `RecognizeAsync`（`engine-winrt.ts:197-210`），用户看到的「0.3s」与体感「1.1s」不符，排查性能时被误导。

### D9 缓存：结构化存储 + 版本与预处理进 key（推荐）

**推荐**：
- 缓存值由 `string` 改为**结构化快照**（`{text, lines, width, height}` 的 JSON 字符串），使**同一张图在不同 `layout` 下复用同一份缓存**（现在 layout 若进 key，切一次 layout 就重新 OCR，代价 1s+）；
- key 加入预处理参数：`[VERSION, engine, lang, scale, crop, imageHash]`；
- `OCR_CACHE_VERSION` 递增到 `v2`（删掉对 `postprocess` 语义的错觉：它靠手工递增，改规则必须同步改常量，在 `postprocess.ts` 顶部加醒目注释提醒）。

**理由**：`cache.ts:13` 的 `OCR_CACHE_VERSION` 确实在 key 里（此前误记为缺失），但它是**手工常量**，改规则忘递增就会读到旧后处理结果；且不含 scale/crop，放大前后会串味。

### D10 幂等性（推荐，硬约束）

**推荐**：`layout` 渲染与 `postProcessOcrText` 组合必须幂等——对已分行、已合并的文本重复执行逐字节不变。补单测覆盖两种输入：**有字间空格（本机）** 与 **无字间空格（内网机）**，结果须一致。

**理由**：`postprocess.ts` 已有幂等硬约束（其文件头 `:8`），新增布局层若破坏它，会让「同一张图两次识别结果不同」，还会让缓存与直算结果不一致。

### D11 工具描述预算：**必须重定基线**（推荐，需用户知情）

**实测现状**：`tests/tool-description-budget.test.ts` 断言总量 ≤ **4400** 字符，实测当前 **4379**（11 个工具），余量 **21 字符**。而该测试的注册集**不含 `ocrImage`**（它需 `ocr.enabled` + 引擎探测才注册，测试只开了 `vision.enabled`）。

**这意味着**：真实 Windows 环境下（`ocrImage` 已注册）总量约 **4700**，**现行预算早已"实际超标"、测试却绿**——预算测试存在口径漏洞。

**推荐**：
1. 该测试补一个「模拟引擎可用」的注册分支，把 `ocrImage` 纳入预算口径；
2. `BUDGET_CHARS` 由 4400 → **5000**、`BUDGET_TOKENS` 1100 → **1250**，并在注释里写明「含 ocrImage，20261112-003 新增 layout/scale/crop」；
3. 同时**压缩既有描述**：`ocrImage.description` 控制在 70 字符内，三个新参数 `description` 各 ≤ 30 字符（只写「取值 + 默认」，使用手册留给 `built-in-tools.md`）。

**备选**：新增参数全部塞进已有 `options` 对象（单个参数），省 2 条 schema 开销。**但**嵌套对象会让模型多一层拼装、且与 `fileRead` 等扁平参数风格不一致，不推荐。

### D12 非 Windows / http 引擎降级（推荐）

**推荐**：`layout` 仅 `winrt-ocr` 支持；http 引擎或无 bbox 引擎在 `layout !== 'text'` 时**降级为 text 并追加告警**「当前引擎不提供坐标，已按纯文本输出」，不抛错。非 Windows 平台行为与现在完全一致（工具不注册）。

### D13 表格渲染细节（推荐）

**推荐**：单元格内文本先过 `mergeCjkSpaces`（否则表格里全是「小 智 前 后 台」）；空单元格输出空串而非 `-`；列宽不做对齐填充（markdown 源码里用单空格，渲染器自会处理）。

## 七、风险与回滚

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 手写 JSON 转义漏字符（引号/反斜杠/控制符） | 解析失败或文本损坏 | `Escape-Json` 单测覆盖全特殊字符；解析失败回落 `out.txt` |
| PS 5.1 兼容性（内网机 Win10） | 脚本报错 | 只用 5.1 特性；`BitmapTransform` 在 5.1 可用（WinRT 投影，非 PS 语言特性） |
| 脚本 ASCII 约束被 JSON 拼接破坏 | 内网机乱码 | 既有 `tests/ocr-winrt-script.test.ts` 已锁「脚本纯 ASCII + 无 PS7 语法（?? / ?. / $PSStyle）」，新增 `Escape-Json` 与 JSON 拼接须继续通过该测试（中文只能来自运行时变量，不得写进脚本字面量） |
| y 聚类把大标题并入正文行 | 行错位 | 容差用中位字高，异常大字号天然不合并；实测 23 行无错并 |
| 缓存版本升级致首轮全 miss | 冷启动多 1s | 可接受；`v2` 一次性失效 |
| 预算基线抬高 600 字符 | 每轮多约 150 token | 可接受（相当于 1 句话）；同时压缩既有描述对冲 |

**回滚**：全部改动集中 `src/ocr/*` + 一个工具文件，`layout` 默认 `text` 且 `out.txt` 保留 → 出问题可把 `runOcr` 的 layout 渲染短路回「直接返回 `out.txt`」，改动面 3 行内。

## 八、阶段划分

| 阶段 | 内容 | 价值 |
| --- | --- | --- |
| **P0** | 行结构回传（out.json）+ y 聚类视觉行 + 行数/词数标注 + 后处理生效验证 | 直接解决「名称日期不对应」，风险最低 |
| **P1** | `layout=table`（投影列聚类）+ `layout=words` + `scale`/`crop` + 结构化缓存 + 预算重定 | 覆盖表格图与小字图 |
| **P2** | `layout=auto` 自动判别、`confidence` 字段用引擎 `TextAngle`/词数粗估、批量 `images[]` | 增强，进演进项 |

## 九、演进项（本需求不做）

- `layout=auto` 自动判别（依赖 P1 实测样本积累后再定阈值）；
- `confidence` 真实置信度：WinRT `OcrResult` **不返回**置信度（只有 `TextAngle`），任何「置信度」都是伪值，故继续留空，不臆造；
- 批量 `images[]` 一次识别多图（省进程启动，但工具调用语义变复杂）；
- macOS/Linux 引擎（20261112-002 已定演进项）。

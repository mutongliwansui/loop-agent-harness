# 📊 LLM Token 统计

> [⬅ 返回 README](../../../README.md)

Agent 内置 LLM Token 统计（Task-15）：每轮 LLM 调用结束后输出上下文/输入/输出 token 与缓存命中率，会话结束后输出会话级汇总（总 token、平均缓存命中率、上下文峰值）。

```
[迭代 2/5] 上下文 3214/8000 (40%) | 输入 2588 | 输出 412 | 缓存 72.3% | 1.2s
[统计汇总] 3 轮 | 总输入 7842 | 总输出 1230 | 总 token 9072 | 平均缓存命中 68.5% (首轮 45.0% / 后续 80.1%) | 上下文峰值 4500/8000 (56%)
```

- **开关**：配置 `agent.showTokenStats`（默认 `true`），关闭后不再打印统计行
- **事件**：可监听 `onLLMStats`（每轮）与 `onLLMStatsSummary`（会话结束）获取结构化数据
- **上下文警示**：上下文 token 接近/超过 L1 压缩阈值时，统计行以黄色高亮警示
- **双口径命中率**（20261021-008）：汇总行在平均命中率后追加「(首轮 x% / 后续 y%)」——首轮含 system/工具 schema 冷启动 miss 天然偏低；**第 2 轮起命中率（subsequentIterationsHitRate）是前缀缓存优化效果的主指标**。两者均只统计有缓存字段的轮次（服务商未提供缓存字段时为 N/A）

## 前缀缓存友好化（20261021-008）

DeepSeek 风格的前缀缓存要求请求从第 0 个 token 起逐字节一致才命中。为此上下文组装保证同一 run 内请求序列稳定：

1. **L2 检索结果 run 级冻结**：同一 run（同 userMessage+sessionId）内检索只做一次，工具写入 L2 的新条目不会改变本轮注入内容（对下一 run 可见），同时消除检索超时导致的「有注入 ↔ 无注入」前缀翻转
2. **system prompt 单一来源**：每轮组装复用 run() 首轮构建的 system prompt（含 workspaceDir/视觉能力段），不再独立重建
3. **L3 Curated 缓存**：记忆文件 mtime+size 未变化时直接复用上次拼接结果，文件变化才重读
4. **效果**：同一 run 内除尾部新增消息外请求逐字节一致，第 2 轮起前缀可稳定命中

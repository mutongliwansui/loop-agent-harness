# 从零构建 PPT 的教程

## 制定任务计划

> **任务命名约束（强约束）**：本表仅为内部执行参考。在创建 TODO / 任务或向用户汇报进度时，**必须使用面向用户的术语**（如「内容大纲 / 风格设计 / 创建演示文稿 / 逐页制作 / 检查页面 / 交付」），**禁止暴露任何内部实现字眼**（如 `DSL`、`*.py`、`slidep`、`OOXML`、`success=true`、源码、组件文件名等）。

| Step | 职责（内部） | 产物（内部） |
| ---- | ---------------------------------------------------------------- | ------------------------------------------------ |
| 1    | 信息收集（可选） | 背景资料 / 行业数据 |
| 2    | 需求澄清 + 依据主题构建 PPT 的叙述逻辑 | `STORY.md` |
| 3    | 风格路由 + 构建页面风格的设计逻辑 | `DESIGN.md` |
| 4    | 逐页生成 PPT（在 `pages/` 下按大纲顺序写完全部页面源文件） | 全部页面源文件 |
| 5    | 校验页面（`slidep validate`，设计规范门禁） | 全部页面校验通过 |
| 6    | 编译产出 `.pptx`（`slidep build`） | `dist/*.pptx` |
| 7    | 启动预览（`slidep serve`，可选） | 预览画廊已打开，用户可实时观察 |
| 8    | 交付 | 目标 `.pptx` 已交付给用户 |

## 各步骤要求

### Step1：信息收集（可选）

当模型的信息不足、数据过时或需要行业标杆案例时，主动调用网络搜索收集有深度、有据可查的实时内容。

判断信号：
- 主题涉及 `数字 / 市场 / 行业 / 新闻 / 分析` 等具有时效性的信息时 → 需要最新统计数据。
- 主题含 `陌生缩写 / 专业术语 / 生僻词组` → 先查清楚。
- 用户明确要求，或用户需要"有说服力"但未提供素材 → 补充外部佐证。

若用户已提供完整参考材料（长文本、`.docx`、`.pdf` 等），本步可跳过或降级为只查陌生概念。

### Step2：需求澄清 + 构建叙事逻辑（STORY.md）

动笔前必须确认以下信息（用户未明确时按默认值）：

| 问题 | 为什么重要 | 默认值 |
|---|---|---|
| 听众是谁？ | 决定语气、专业深度、信息密度 | —（必须明确） |
| 听完要做什么？ | 唯一目标：决策 / 认知 / 行动 | 认知 |
| 多少页？ | 1 分钟 ≈ 1 页，可上下浮动 20% | 10 页 |
| 什么场合？ | 决定风格路由（见 Step3） | 通用 |
| 内容边界？ | 什么必须讲、什么必须不讲 | —（需要确认） |

阅读 [story-principle.md](story-principle.md)，将以上答案与叙事规划写入 `STORY.md`（含全篇页面角色、节奏曲线），并向用户确认后进入下一步。

### Step3：构建页面风格的逻辑（DESIGN.md）

#### 风格路由

收到用户需求后，用 `route_query`（关键词子串匹配，多包命中取得分最高）从 **4 个内置风格包**中确定风格：

| 风格包 id | 名称 | 硬关键词（keywords） | 软关键词（soft_keywords） |
| :--- | :--- | :--- | :--- |
| `academic` | 学术 | 论文、答辩、学术、研究、论文答辩、学位、科研、课题、学术报告、研究汇报、实验室、review、paper、thesis、research | 报告、汇报、分析、数据、统计 |
| `business` | 商务 | 商业、商务、季度、汇报、项目、产品、市场、营收、增长、战略、商业计划、项目总结、business、quarterly、report、strategy | 总结、计划、方案、目标、团队 |
| `government` | 政务 | 政务、政府、政策、工作、年终、工作报告、政策解读、政府工作报告、机关、单位、部门、government、policy、official | 总结、报告、规划、建设、发展 |
| `general` | 通用 | 通用、默认、普通、general、default | （不参与软匹配） |

路由三态：
- **matched**：query 命中某风格包的硬关键词 → 完全命中，采用该风格包全套参数；
- **soft_match**：仅命中软关键词 → 软降级，仅结构层参考该风格；
- **no_match**：无命中 → 使用 `general` 通用风格。

**匹配后的执行**（对应设计文档）：
- `academic` → 读取 [designs/design-principle.academic.md](designs/design-principle.academic.md)
- `business` → 读取 [designs/design-principle.consulting.md](designs/design-principle.consulting.md)（商务咨询规范：Action Title、Navy 权威感、结构图优先）
- `government` → 读取 [designs/design-principle.redgold.md](designs/design-principle.redgold.md)（红金政务规范：红金主视觉、中文优先、密度优先）
- `general` → 读取通用 [design-principle.md](design-principle.md)

**判断示例**：
- "季度业务汇报" → 命中 `business` → 商务咨询规范 ✅
- "政府工作报告" → 命中 `government` → 红金政务规范 ✅
- "论文答辩" → 命中 `academic` → 学术规范 ✅
- "产品发布会" → 无命中 → `general` 通用 ✅

> 原则：预设风格是为特定垂直领域定制的，不应泛化使用。大量常见场景（产品介绍、项目提案、技术分享、团队介绍等）走通用设计原则即可。

#### 内容规划

1. 根据 `STORY.md` 规划页面结构（封面 → 目录 → 章节 × N → 结尾）；
2. 每页确定：页面类型（cover / toc / content / section / ending）、角色（hero / supporting / transition）、节奏（peak / valley / transition）；
3. 版式骨架分配：相邻页不同骨架，非对称布局占比 ≥ 40%。

将页面清单（页码 + 类型 + 标题 + 角色 + 节奏）、风格包选择结果（色板 / 字号 / 字体）、版式骨架分配写入 `DESIGN.md`，并向用户确认后进入下一步。

### Step4：逐页生成 PPT（按大纲顺序）

> 动笔前的心智校准：每一页是一个 `.py` 源文件，但**它不是普通 Python 程序**——文件只是页面结构的声明，由引擎直接编译成 `.pptx`。把它当"结构声明"来写，禁止引入任何副作用的执行逻辑。文件必须导出 `slide`（单页）或 `slides`（多页列表）变量。

> 动笔前必读：
> - `STORY.md` — 当前 PPT 的叙事逻辑
> - `DESIGN.md` — 当前 PPT 的设计稿（画布、配色、字号、布局、元素、密度）
> - 相关组件规范 — 本页用到哪个组件，就读取 `references/component-*.md` 中对应文档

> **动笔前禁读**：本项目目录之外的任何 PPT 项目源码。本页页面结构的全部依据应来自 `DESIGN.md` + 命中分支的 `design-principle.<id>.md` + `component-*.md`，不得"借鉴"历史项目的写法或视觉选择。

> 严禁仅靠记忆动笔。

约束如下：
- 充分结合 `STORY.md` 和 `DESIGN.md`，按照大纲顺序从第 1 页生成到第 N 页，一次写完全部页面；
- 写入页面源文件：写到 `pages/slide_{NN}_{描述}.py`（`NN` 为零填充页码，如 `slide_01_cover.py`、`slide_03_research_bg.py`）；
- 组件清单：`Slide` / `Box` / `Text` / `Chart` / `Image` / `Table` / `FAIcon` / `SVG` / `QRCode` / `CodeBlock` / `Math`，各组件规范见 `references/component-*.md`；
- 配图前置：若涉及生图内容，必须在写内容前完成生图流程，并将图片放入项目 `resources/` 目录供 `Image` 组件引用；对生成的图片进行视觉检查，确认图片清晰、无水印且符合上下文后方可使用；
- 动笔自检（每页提交前 10 条硬约束，逐项确认；任意不通过 → 当页返工）：
  1. 母版区齐全：默认三区（A 标题块 / B 内容区 / C 页脚条含右下页码），全篇位置严格一致；
  2. 标题块右侧不得塞装饰小图；
  3. 本页 L1 主视觉占 B 区面积 ≥ `DESIGN.md` 规定；不得用 L3 角标顶替 L1；
  4. 仅使用项目 `DESIGN.md` 列出的 ≤ 4 种 hex 与 ≤ 2 套字体家族；
  5. 与上一页版式不重复；本页留白比例 ≤ `DESIGN.md` 上限；
  6. 本页有 ≥ 1 个视觉锚点（≥ 44px 元素或 ≥ 40% B 区面积的图）；如无 → 必须补充巨型数字 / 大图 / 大色块；
  7. 本页与上一页视觉重量有显著差异（最大元素面积比 > 1.5:1 或版式结构明显不同）；连续 ≥ 2 页等宽卡片横排 → 返工；
  8. 本页色彩分配符合 `DESIGN.md` 页面映射表：强调色只出现在焦点元素上，主 / 辅 / 强调色面积比合规；
  9. 本页的 role 与 `STORY.md` 一致：hero 页必须有 ≥ 40% B 区主视觉或 ≥ 48px 锚点数字；supporting 页不得使用 hero 级视觉投入；
  10. 本页无元素溢出画布（`LAYOUT_OVERFLOW` 不允许出现）。

### Step5：校验页面

所有页面写完后，一次性跑全量校验：

```bash
slidep validate
```

- 校验不产出文件，只检查语法与设计规范门禁；
- 如有 error，根据返回结果（错误码 + 定位 + 提示）修复对应页面，重新校验直到 0 error；
- `--strict` 可让 warning 也视为失败；`slidep validate <文件>` 可只校验单页。

### Step6：编译产出 `.pptx`

校验通过后执行编译：

```bash
slidep build
```

- 输出文件在 `dist/` 目录下，默认文件名为项目目录名；
- 可用 `--filename` 指定输出文件名（默认使用中文，如 `"季度汇报.pptx"`，仅在用户明确要求时才用英文文件名）；
- 编译内含 lint 门禁：未通过则构建中止（`--no-lint` 可跳过，不推荐）。

### Step7：启动预览（可选）

```bash
slidep serve
```

- 浏览器打开 `http://localhost:8000/` 查看页面画廊；
- 修改 `pages/` 下任意文件，自动重编译并在浏览器刷新；
- 可用 `--port` 指定端口；`--action stop` 停止服务。

### Step8：交付

全部页面编译通过后，向用户交付最终成果：

- 使用面向用户的语言（禁用 `slidep` / `OOXML` / `DSL` 等内部字眼）简要说明本次 PPT 的主题、页数与风格要点，交付 `dist/` 下的 `.pptx` 文件。

## 生成后的编辑（后续行为指导）

**PPTX 交付后，用户提出修改需求时，回到本项目 `pages/` 下对应的页面源文件进行修改，修改后重新执行 `slidep validate`（可选）与 `slidep build` 重新编译；若预览服务运行中，改动会自动反映到预览画廊。**
